# Targeted migration table identity audit — 2026-09-29

Audited synced `origin/main` `cd3251a5aedd8ef6d7bc15bf00f018a56b66e34d`. BUG-095 is a new high-severity data-isolation finding. No implementation was made.

## Finding: long workspace names collide after PostgreSQL truncates migration table names

`Sol_cli_migration.table_name` (`cli/lib/base/sol_cli_migration.ml:8-18`) builds the unquoted SQL identifier `sol_<workspace>_schema_migrations` without a length limit or distinguishing hash. `Sol_cli_workspace.workspace_name` (`cli/lib/workspace/sol_cli_workspace.ml:56`) takes the workspace directory basename. `Sol_cli_kubernetes_name.namespace_of_parts` (`cli/lib/base/sol_cli_kubernetes_name.ml:45-47`) permits a workspace name of 60 lowercase letters with a one-character domain: the namespace is 62 characters. The pinned `pg-eio` `Migration.apply` interpolates the validated identifier into SQL (`~/Code/pg-eio/lib/migration.ml:254-276`); `Pg_table.Identifier.of_string` checks characters but not length (`~/Code/pg-eio/lib/pg_table.ml:53-70`). PostgreSQL's [identifier rule](https://www.postgresql.org/docs/current/sql-syntax-lexical.html) truncates an identifier after 63 bytes by default.

Concrete pair: workspace names `a` repeated 59 times followed by `x`, and `a` repeated 59 times followed by `y`, each with domain `d`. Both produce valid, distinct 62-character Kubernetes namespaces. Their migration table names are 82 characters and share the same first 63 bytes: `sol_` plus 59 `a` characters. PostgreSQL therefore addresses one migration table for both. In a supported shared-Postgres deployment, applying version 1 in workspace X makes workspace Y's different version 1 appear applied; Y skips its own schema change. Positive control: names with 58 shared `a` characters followed by `x`/`y` have different 63rd bytes in the SQL identifier and address different tables.

The deterministic name calculation and PostgreSQL's documented truncation establish the collision. No local PostgreSQL server or `psql` was available for a live `Migration.apply` reproduction. `rg -n -i 'migration table.*collis|table.*truncat|long workspace' internal/pipeline/tickets internal/pipeline/audits` found no existing ticket; `Sol_cli_migration.table_name` and the `pg-eio` SQL path are the positive source control. BUG-091 concerns job-table isolation, not migration-version isolation.
