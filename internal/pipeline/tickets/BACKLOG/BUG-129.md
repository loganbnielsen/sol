## Observed

The required `test` check failed on a **main push** — the post-merge backstop — for
`AUDIT-087`'s implementation commit, in *Framework integration tests (broker and database
backed)*: all 20 `sol_jobs_pg` cases failed in 68 ms, each with a connection error rather than
an assertion. The same commit re-run is green, and the two neighbouring commits' runs are green.


This is `VERIF-023`'s Instance A recurring. That ticket's `Integration failure diagnostics` step
now answers the question it could not: **the server did not die** — it had just been *created*.

So: exit 0, `oom=false`, `restarts=0`, and `docker ps` shows a container created ~15 seconds
before the diagnostics ran — while its own log tail is still the **initdb sequence**. The server
that "terminated abnormally" was never running yet; the gate said ready while it was initializing.

## The mechanism, in the script

`platform/local/scripts/ensure-postgres.sh` starts the container and then gates on two things:

```bash
docker run -d --name "${CONTAINER}" ... postgres:16-alpine > /dev/null
echo "Waiting for port ${PORT} ready."
wait_for_port "${PORT}" 30 0.5 || exit 1

for i in $(seq 1 20); do
  if docker exec "${CONTAINER}" pg_isready -q 2>/dev/null; then break; fi
  sleep 0.5
done

echo "Postgres ready at localhost:${PORT}"
```

Two independent reasons this can pass before the server can serve:

1. **A TCP connect is not evidence the container's server is up.** The port is published, so
   *something* (the container's network namespace once the entrypoint binds, or Docker's
   published-port proxy) can accept the connection while the image's entrypoint is still in its
   `initdb` phase — which is exactly the shape the log shows: "Waiting for port 5432 ready." at
   17:13:41.8, "Postgres ready" at 17:13:42.97, first client at 17:13:43.27, initdb still
   printing at 17:13:56. The first server the image runs during initialization is not the server
   the suites connect to afterwards; when the entrypoint stops it and starts the real one, a
   connection made in that window is closed — `server closed the connection unexpectedly`.
2. **The `pg_isready` loop is not a gate.** `break` on success, then unconditional "ready": if it
   never becomes ready within its 10 seconds, the script still prints "Postgres ready at
   localhost:5432" and exits 0. The result of the loop is never used, so the one check that *does*
   look inside the container can fail silently. (`wait_for_port` at least exits 1 on timeout.)

Both are deterministic readings of the script; the timeline above is the observed instance.

## Why it matters

`test` is a required check on every PR and the post-merge backstop on `main` (this occurrence
was on `main`, not a PR). The failure looks like a test failure, costs a full CI cycle to
attribute, and is only distinguishable from a real regression by re-running — the cost
`VERIF-023` named. It reproduces on a PR whose diff is unrelated (`AUDIT-087`'s is
`internal/qualification/transport/` and `internal/ci/`, nowhere near `framework/`).

## Recommended remediation

In `ensure-postgres.sh`, make the gate observe the server the suites will use, and fail when it
cannot:

- gate on a **real query through the published port** — `pg_isready -h 127.0.0.1 -p <port>` from
  the host, then `psql "postgresql://postgres:<pw>@127.0.0.1:<port>/<db>" -c 'SELECT 1'` (or the
  same through `docker exec` against TCP inside the container) — rather than a bare TCP connect;
- **fail** (`exit 1` with the container's last log lines) when the readiness loop exhausts, so a
  server that is not ready is a named failure instead of a suite-level connection error;
- keep the `Integration failure diagnostics` step: it is what made this diagnosable, and it
  should also print the container's creation time and the elapsed time since it was started, so
  the next occurrence shows the race in one place.

`platform/local/scripts/ensure-broker.sh`/`start-redpanda.sh` deserve the same review: the same
`wait_for_port` pattern is used for the broker, and a broker that accepts a connection before it
serves would fail the same way.

The fix is CI and local-tooling behaviour, so it belongs to whoever owns that surface (the
`VERIF` workstream), not to this review; it is filed rather than implemented here.

## Acceptance criteria

- A Postgres that is not ready cannot make the script print "Postgres ready" and exit 0: the gate
  waits for a query that only the real server answers, or fails with the container's log.
- The gate's failure mode is visible in one line, and a re-run is not needed to tell "the runner
  was unlucky" from "the code is wrong".
- The change is exercised by the existing local-dev and CI paths (a fresh container on a clean
  runner), and `platform/local/scripts/` has a test or a documented manual check for the
  not-ready path.
