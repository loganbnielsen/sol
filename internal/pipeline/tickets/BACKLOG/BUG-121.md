title: Rollback prunes a removed workload's Deployment but leaves its Service, ConfigMap, RBAC and volumes behind

**Depends on:** None.

When a bad deploy adds a workload, it renders, for that workload, a
`ServiceAccount`, a `<name>-env` ConfigMap, a `NetworkPolicy`, and (depending on
the primitive and settings) a `Service`, an `Ingress`, a PodDisruptionBudget, and
one PersistentVolumeClaim per declared volume, in addition to the workload
itself. A rollback to the older release finds the added workload as an
*unexpected* live workload and prunes it — but `Sol_cli_rollback.prune_workloads`
deletes only `kind_resource id.kind`, i.e. the `Deployment`/`Rollout`/`CronJob`:

```ocaml
Sol_cli_kubectl.delete ~ctx ~resource:(kind_resource id.kind) ~name:id.name ~namespace:id.namespace
```

## Impact

The restored cluster is not the recorded release: every auxiliary object the
removed workload created is still present. Most are inert but untidy (a
`Service` with no endpoints, a stale `<name>-env` ConfigMap, an unused
`ServiceAccount`/`NetworkPolicy`). Two are not: a lingering `Ingress` can keep a
hostname bound, and a lingering PersistentVolumeClaim keeps billable storage
alive with no owner, which on a managed cloud is a real recurring cost. The
release record, the pointer and the workload label all say the rollback
succeeded, so nothing surfaces the leftovers.

## Decision Required

Whether rollback may delete a workload's PersistentVolumeClaims, and any other
stateful auxiliary, is a storage-lifetime decision rather than a bookkeeping one:
deleting a PVC destroys data, and today's `sol cloud destroy` path already treats
retention as deliberately undecided (`DEC-033`). This ticket must not pick that
silently. Resolve, then implement:

1. Which auxiliary kinds rollback prunes (at minimum: Service, ConfigMap,
   ServiceAccount, NetworkPolicy, Ingress, PodDisruptionBudget).
2. What rollback does with PersistentVolumeClaims — refuse to prune the workload
   while a PVC holds data, leave and report them, or delete them.
3. How the prune report distinguishes "removed the workload" from "left these
   objects behind", so an operator is never told the boundary was restored when
   storage was.

## Out of scope

Deploy-time pruning generally, and `DEC-033`'s retention semantics — this is
specifically the rollback path dropping a workload the target release does not
contain.

## Acceptance criteria

- The decision above is recorded before implementation.
- A rollback that drops a workload removes the auxiliary objects the decision
  selects, and reports every object it deliberately left.
- The qualification harness's restore case asserts the post-rollback object set,
  not just the workload labels.
