**Depends on:** None. Builds on INFRA-025 (merged): the deploy identity's
namespace-scoped RBAC and its `sol-deploy-bootstrap` create-only bootstrap
grant.

**Related:** ADR 0002 (provisioner/publisher/deployer/operator negative
boundaries), AUDIT-072.

## Open Questions

Is a Kubernetes admission-control layer (`ValidatingAdmissionPolicy` or an
external controller such as Kyverno/OPA Gatekeeper) worth adopting — for
this boundary alone, or as infrastructure Sol wants for other reasons too —
and if so, which mechanism? Not decided here; this ticket exists to raise
the question with the concrete gap that motivates it, not to pick the
mechanism.

## The gap

INFRA-025 gave the deploy identity a namespace-scoped `RoleBinding` to a
`sol-deploy` `ClusterRole` (`Deployment`/`Service`/`Job`/`ConfigMap`/`Secret`/
etc.), applied per application namespace at runtime by
`Sol_cli_substrate.ensure` — not a `ClusterRoleBinding`, specifically so
deploy cannot reach platform namespaces. Bootstrapping that first binding for
a brand-new namespace needed a second, minimal `sol-deploy-bootstrap`
`ClusterRole`+`ClusterRoleBinding` (`namespaces`/`rolebindings`
`get,list,watch,create` only, plus `clusterroles: bind` restricted to
`sol-deploy` by `resource_names`).

That bootstrap grant has a real residual gap: **`rolebindings: create`
cannot be restricted by namespace** when bound via a `ClusterRoleBinding` —
Kubernetes RBAC's `resourceNames` is not honored for `create` at all (the
object doesn't exist yet), and there is no partial-cluster-scope
`ClusterRoleBinding`. So a deliberate holder of the deploy IAM role's
credential could, by issuing the `kubectl create rolebinding` call directly
(bypassing `sol deploy`/`sol migrate` entirely — Sol's own CLI has a
client-side refusal, `Sol_cli_substrate.reserved_platform_namespaces`, but
that only stops *ordinary* use through Sol, not a deliberately crafted raw
API call), create a `RoleBinding` named `sol-deploy` directly inside a
platform namespace (`cert-manager`, `argocd`, `redpanda`, `monitoring`,
`ingress-nginx`, `postgresql`). That binding would then grant the deploy
identity `sol-deploy`'s full `Secret`/`Deployment` mutation rights inside
that platform namespace too — the exact outcome the namespace-scoped design
exists to prevent.

## Why this isn't closed already

Plain Kubernetes RBAC has no "except this namespace" or "deny" rule; it is
purely additive. The only way to express "deploy may create RoleBindings in
namespaces it doesn't already know about, but never in this fixed set of
platform namespaces" is a policy layer that evaluates the *namespace itself*
at admission time, which RBAC's resource/verb model cannot express. A
`ValidatingAdmissionPolicy` (built into Kubernetes since 1.30, CEL-based, no
extra controller) or an external policy engine both can.

## What's already true and doesn't need to change

- The steady-state deploy grant (the namespace-scoped `RoleBinding` to
  `sol-deploy`) is already correctly scoped — this ticket is about the
  narrow bootstrap window only.
- The client-side reserved-namespace refusal in `Sol_cli_substrate.ensure`
  already closes the *accidental* path (an ordinary `sol deploy`/`migrate`
  invocation can never target a platform namespace name). What remains is
  the *deliberate* path via raw `kubectl`/API access with the deploy
  credential.
- This is a real narrowing already, not a claim of a fully closed boundary:
  before INFRA-025, there was no deploy RBAC scoping at all.

## What's blocked on this

Nothing currently — INFRA-025 shipped with this residual gap explicitly
documented, and Maturity A's threat model (a legitimate operator/CI holds
the deploy credential; the concern is accidental over-reach, not insider
attack) tolerates it for now. This becomes higher-priority if/when Sol's
threat model or a customer's compliance posture requires defense against a
compromised or malicious deploy credential specifically, not just accidental
misuse.

## Recommendation

Revisit once there is a second driver for an admission-control layer (a
customer requirement, or another finding that needs one) rather than
adopting one for this single gap in isolation — the mechanism choice
(built-in `ValidatingAdmissionPolicy` vs. an external engine) has real
tradeoffs (dependency footprint, policy language, cluster version
requirements) that deserve to be made once, for the platform's actual
policy needs, not per-finding.
