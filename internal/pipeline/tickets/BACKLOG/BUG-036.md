id: BUG-036
type: bug
severity: medium
source: FEAT-082 golden-path walk, 2026-09-16 — `sol up --scope=demo_ts` in examples/pluto
---

`sol up` leaves a persistent copy of the workspace behind, and that derived state
changes how tooling interprets the original repository.

**Observed.** Running `sol up --scope=demo_ts` in `examples/pluto`:

```text
Preparing build context...
[svc] demo_ts/order_svc
  packaging localhost:5000/pluto/order-svc:cf75d54c...
```

Afterwards, `examples/pluto.docker-ctx/` existed — a full copy of the workspace —
and was left in place. Because Pluto is nested inside the Sol repository, that
copy made the root Dune project see the `pluto` package twice:

```text
Error: The package "pluto" is defined more than once:
- examples/pluto.docker-ctx/pluto.opam:1
- examples/pluto/pluto.opam:1
```

`dune build` then failed until the directory was removed. A user whose workspace
sits inside another Dune project gets an identical failure. `*.docker-ctx/` is now
gitignored so it cannot be committed, which stops the bleeding but does not fix
the behaviour.

**Invariant violated:**

> Temporary build preparation must not leave persistent workspace copies that
> alter subsequent workspace discovery or build behaviour.

A command may not leave derived state behind that makes a previously-valid
workspace or repository invalid. Note this is not merely untidiness: the leftover
copy is *interpreted* — Dune discovers it as a second project with the same
package name — so the damage is to the user's original repository, not just disk
usage.

**Likely fix — determine whether the copy is needed at all.** DEC-025 removed the
reason the build context was materialised: there are no longer `vendor/framework`
symlinks to resolve, because a workspace now consumes the framework as installed
opam packages. So the first question is not "how do we clean up the context" but
"does the materialisation still have any purpose". Options in preference order:

```text
A. build directly from the workspace root
   ← ideal if materialisation has no remaining purpose (probably true after DEC-025)

B. temporary isolated build context
   → always cleaned, including on failure/interrupt paths

not:

C. persistent <workspace>.docker-ctx sibling      ← current behaviour
```

If (A) is viable, this likely collapses into deleting the materialisation step
rather than adding cleanup logic, which is the cleaner outcome and matches
DEC-025's direction.

**Acceptance criteria:**

- No persistent `<workspace>.docker-ctx` (or equivalent) remains after `sol up`,
  on success or failure.
- `dune build` in the enclosing repository is unaffected by having run `sol up`
  in a nested workspace.
- If materialisation is retained for any reason, the reason is documented in the
  code, and an automated test covers the "runs and leaves nothing behind"
  property — this was found by hand, and nothing in the suite would have caught it.
