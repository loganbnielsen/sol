## The invariant

> **Declared configuration determines where. Execution identity determines whether.
> Ambient local configuration determines neither.**

`current-context`, a default AWS profile's account, a default region, the active gcloud
project, and any other machine-local setting may not select or alter the deployment
destination. They may at most supply *credentials*, and those credentials are then
checked against the declared destination.

```text
repo declaration → destination → execution identity → validate access against destination → act
```

## What this decision establishes

1. **`--env X` resolves its destination from committed Sol configuration**, plus
   authoritative state discoverable *from* that configuration where unavoidable. Prefer
   putting destination facts directly in committed declarations: driver, account or
   project, region, and cluster identity.
2. **Execution identity cannot change which destination is selected.** If AWS `prod`
   declares account `1234` and the caller is authenticated to `5678`, fail with a message
   naming both. Never fall back to looking for a similarly named cluster wherever the
   caller happens to be. The same applies to the GCP project.
3. **Every driver checks the access it obtained against the declared destination before
   acting.** On AWS: caller account, then the cluster's ARN. On GCP: project, then
   cluster resource name. On `byo`: a declared, verifiable cluster identity. A supplied
   kubeconfig credential *authenticates* access; it does not *define* where the deploy
   goes.
4. **Fresh-machine bootstrap is closed end to end.** If remote state is needed, its
   location is itself discoverable from committed configuration. The CI cloud identity
   and the Kubernetes RBAC/access mapping for it are part of the contract, not
   an exercise for the operator. GitHub uses OIDC / short-lived identity, never a stored
   bearer credential.

## Consequence for today's code

`FEAT-059`'s destination is `{ context; kubeconfig option }`
(`cli/lib/base/sol_cli_kube_destination.mli`), resolved by
`Sol_cli_destination.resolve` → `Sol_cli_config.destination_of_target`. The context
*name* is committed, but what it *means* (API server, CA, and credential) lives in a
local kubeconfig file. So under this invariant, `kube_context` is ambient local
configuration deciding *where*, and it cannot remain the destination for `aws`/`gcp`.
The likely shape: these drivers derive the API endpoint and CA from the declared cluster
identity, and get a credential for each invocation from the provider's exec plugin. The
`DEC-030` rule 2 export then becomes a *rendering* of that destination, not its source.

## Scoping questions this resolution closes

1. **`byo` cluster identity.** Kubernetes has no canonical cluster ID. Candidates are a
   declared API server endpoint plus CA fingerprint, and/or the `kube-system` namespace
   UID read back after authenticating. Which one counts as "declared and verifiable",
   and what happens to it on a cluster rebuild?
2. **What remains of `kube_context`.** Does it become an optional credential source for
   `byo` only (checked against rule 3's identity), or is it removed entirely in favour
   of a declared endpoint plus a credential mechanism?
3. **Where destination facts live.** Target file fields, or values read back from
   Terraform state whose location is itself committed? Rule 1 prefers the declaration.
   Any fact that has to come from state needs its state location to be committed.
4. **The CI identity's RBAC binding.** `INFRA-025` binds `deploy_role_arn`. Is the CI
   OIDC role that same principal, or a second one with its own access entry? This is the
   input `FEAT-109`'s trust configuration has to match.

## Resolution (2026-10-02)

**Evidence:** the current contract and provider roots, read directly —
`Sol_cli_config.target` (`cli/lib/workspace/sol_cli_config.ml`),
`Sol_cli_kube_destination` (`cli/lib/base/sol_cli_kube_destination.mli`),
`Sol_cli_destination.resolve` (`cli/lib/deploy/sol_cli_destination.ml`),
`platform/cloud/aws/cluster/outputs.tf`, `platform/cloud/gcp/cluster/outputs.tf`,
and `INFRA-025`'s `deploy_role_arn` binding. No live run is needed: this is a
contract decision.

### Answers to the open questions

1. **`byo` cluster identity.** The declared identity is the **API server endpoint
   plus a CA public-key fingerprint** (SHA-256 over the cluster CA certificate).
   The driver performs the TLS handshake and refuses unless the presented chain
   ends in that CA/fingerprint, then authenticates. The `kube-system` Namespace UID
   is read back as a **secondary observed assertion** recorded for drift
   detection, not the declared identity: it is unreadable before authenticating
   and it changes on a rebuild. On a rebuild the endpoint or CA changes, so the
   declared identity no longer matches and the deploy **fails closed**, naming both
   the declared and observed values; updating the declaration is the explicit
   migration. There is no "find a similarly named cluster" fallback.
2. **What remains of `kube_context`.** For `aws` and `gcp` it is **removed as the
   destination**: the endpoint and CA come from the declared cluster identity, and
   a credential comes from the provider's exec plugin / credential chain. There is
   **no shim** (`~/Code/CLAUDE.md`): `kube_context` and `kubeconfig` leave the
   `aws`/`gcp` target schema, and `sol target show --check` reports the declared
   destination instead. For `byo` only, a kubeconfig/context remains a
   **credential source**, validated against the declared endpoint+fingerprint; it
   never defines *where* the deploy goes. `FEAT-059`'s `kube_context` therefore
   survives as a `byo`-only field.
3. **Where destination facts live.** In the **committed target file**: `region`,
   `cluster_name`, and the provider account or project. The driver reads back only
   the endpoint and CA *for that declared cluster*, so nothing selects a
   destination from ambient state. `state_bucket` and the lock table are already
   declared, so remote state remains reachable from committed configuration; the
   `cluster_endpoint` / `cluster_access_role_arn` / `deploy_kube_context` outputs
   become validation inputs, not selectors.
4. **The CI identity's RBAC binding.** The CI OIDC role **is** the same
   `deploy_role_arn` principal `INFRA-025` binds, federated from GitHub OIDC
   (`token.actions.githubusercontent.com`) with a repository/environment-scoped
   trust policy — not a second access entry. One deploy identity, one RBAC
   binding, and the `…-deploy` context the qualification harness already uses is
   that principal. This is what `FEAT-109`'s trust configuration must match.
   `DEC-062`'s authorization reconciler is deliberately a *second*, separate
   identity because it mutates IAM; it never shares `deploy_role_arn`.

### Driver validation steps (rule 3)

- **`aws`:** resolve the declared account (add a declared `account` field); the
  active credential's `sts:GetCallerIdentity` account must equal it, then
  `eks:DescribeCluster` for the declared `cluster_name`/`region` must return the
  declared account and its API endpoint, and the credential must authenticate
  against that endpoint as the declared cluster. Any mismatch fails naming both.
- **`gcp`:** the declared `project_id` and region select the cluster; the active
  credential's project must equal `project_id`, then `container.clusters.get`
  returns the cluster, and the credential authenticates against it.
- **`byo`:** the declared endpoint + CA fingerprint gate the TLS handshake; then
  the credential authenticates, and the `kube-system` UID is recorded as the
  observed assertion.

### Migration

No shim. `kube_context`/`kubeconfig` leave `aws`/`gcp` targets; those targets gain
the declared account (GCP already carries `project_id`), and `byo` gains the
declared endpoint+fingerprint. `examples/pluto/sol/environments.yml` gains the
declared account for its `aws/us-east-1` target, and
`sol target show <target> --check` is the surface that proves the declared
destination.

### Demo/example obligation

Target-file destination fields are app-author-visible, so the implementing unit
updates `examples/pluto/sol/environments.yml` and the deployment guide (and the
`sol target show --check` output shown there) in the same change. No
language-parity impact (`DEC-022`): deployment configuration only.

### Deferred

The exact `byo` fingerprint encoding (CA certificate SHA-256 vs certificate SPKI)
is deferred to implementation, with the trigger being the first `byo` target that
needs a declared identity. The `account` field name for `aws` is likewise
implementation detail.
