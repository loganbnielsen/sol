## The invariant

> **Declared configuration determines where. Execution identity determines whether.
> Ambient local configuration determines neither.**

`current-context`, a default AWS profile's account, a default region, the active gcloud
project, and any other machine-local setting may not select or alter the deployment
destination. They may at most supply *credentials*, and those credentials are then
checked against the declared destination.

```text
repo declaration → destination → execution identity → validate access against destination → act
```

## What this decision establishes

1. **`--env X` resolves its destination from committed Sol configuration**, plus
   authoritative state discoverable *from* that configuration where unavoidable. Prefer
   putting destination facts directly in committed declarations: driver, account or
   project, region, and cluster identity.
2. **Execution identity cannot change which destination is selected.** If AWS `prod`
   declares account `1234` and the caller is authenticated to `5678`, fail with a message
   naming both. Never fall back to looking for a similarly named cluster wherever the
   caller happens to be. The same applies to the GCP project.
3. **Every driver checks the access it obtained against the declared destination before
   acting.** On AWS: caller account, then the cluster's ARN. On GCP: project, then
   cluster resource name. On `byo`: a declared, verifiable cluster identity. A supplied
   kubeconfig credential *authenticates* access; it does not *define* where the deploy
   goes.
4. **Fresh-machine bootstrap is closed end to end.** If remote state is needed, its
   location is itself discoverable from committed configuration. The CI cloud identity
   and the Kubernetes RBAC/access mapping for it are part of the contract, not
   an exercise for the operator. GitHub uses OIDC / short-lived identity, never a stored
   bearer credential.

## Consequence for today's code

`FEAT-059`'s destination is `{ context; kubeconfig option }`
(`cli/lib/base/sol_cli_kube_destination.mli`), resolved by
`Sol_cli_destination.resolve` → `Sol_cli_config.destination_of_target`. The context
*name* is committed, but what it *means* (API server, CA, and credential) lives in a
local kubeconfig file. So under this invariant, `kube_context` is ambient local
configuration deciding *where*, and it cannot remain the destination for `aws`/`gcp`.
The likely shape: these drivers derive the API endpoint and CA from the declared cluster
identity, and get a credential for each invocation from the provider's exec plugin. The
`DEC-030` rule 2 export then becomes a *rendering* of that destination, not its source.

## Open Questions

1. **`byo` cluster identity.** Kubernetes has no canonical cluster ID. Candidates are a
   declared API server endpoint plus CA fingerprint, and/or the `kube-system` namespace
   UID read back after authenticating. Which one counts as "declared and verifiable",
   and what happens to it on a cluster rebuild?
2. **What remains of `kube_context`.** Does it become an optional credential source for
   `byo` only (checked against rule 3's identity), or is it removed entirely in favour
   of a declared endpoint plus a credential mechanism?
3. **Where destination facts live.** Target file fields, or values read back from
   Terraform state whose location is itself committed? Rule 1 prefers the declaration.
   Any fact that has to come from state needs its state location to be committed.
4. **The CI identity's RBAC binding.** `INFRA-025` binds `deploy_role_arn`. Is the CI
   OIDC role that same principal, or a second one with its own access entry? This is the
   input `FEAT-109`'s trust configuration has to match.

## Acceptance criteria

- The invariant and rules 1–4 are recorded, with each driver's validation step named
  (`aws`, `gcp`, `byo`).
- Every open question above has an answer, or is deferred explicitly with a trigger.
- The fate of `kube_context` (`FEAT-059`) is stated, with its migration (no shim, per
  `~/Code/CLAUDE.md`).
- The implementing unit states its demo/example obligation: target-file destination
  fields are app-author-visible (AGENTS.md § *Demo/example coverage*).
- No language-parity impact (`DEC-022`): this is deployment configuration only.
