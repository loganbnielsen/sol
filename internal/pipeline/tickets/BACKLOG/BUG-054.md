A direct deploy, `sol up` or rollback must not overwrite workload Secret values that `sol secret set` owns

**Depends on:** None.

**Finding:** FND-0052 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-24** against `origin/main @ fd5c7e0c`. Sol's live render with
`POSTGRES_URL`/`SOL_API_KEY` unset writes both as `""`. Replayed against a disposable
k3s: a deploy after a `sol secret set` rotation restored the pre-rotation credential
and blanked `SOL_API_KEY`.

## Problem

With `Kubernetes_live`, the default for direct and local deploys and hard-coded for
rollback, every apply re-renders `<svc>-secrets` from the CLI's environment. Declared
keys are required from the environment. The defaults `POSTGRES_URL` and
`SOL_API_KEY` become `""` when unset: `sol deploy` checks only `POSTGRES_URL`, and
rollback checks neither. `sol secret set` writes the same objects and is documented as
the create and rotation path. So the next deploy or rollback reverts a rotation to
whatever the deployer's shell holds, or blanks the key. A blanked key breaks every
API-key service's next start.

## Decision Required

Who owns Secret values once a workload exists? Options:

- **(a) `sol secret` owns values (recommended).** A direct deploy creates
  `<svc>-secrets` from the environment only when it does not exist. Once it exists,
  deploy and rollback never write values. They read the live Secret and fail before
  applying when a key the workload needs (declared, or a default it uses) is absent.
  Rotation stays with `sol secret set`.
- **(b) Deploy owns values.** Keep rendering from the environment, but require every
  key (defaults included) to be set and non-empty, and document that `sol secret set`
  is overwritten by the next deploy. This contradicts `credential-rotation.md`.
- **(c) Merge.** Render from the environment, but prefer the live value when one
  exists. Two owners remain, and "which value won" is invisible.

Whichever is chosen, no path may ever write an empty value.

## Remediation

Per the decision, in `sol_cli_deployment_render.ml` (`Kubernetes_live`),
`cmd_deploy.ml`, `cmd_up.ml` and `cmd_rollback.ml`. Update
`docs/deployment/credential-rotation.md` and the tutorial.

## Acceptance criteria

- Test: after a rotation-shaped change to the live Secret, a deploy and a rollback
  leave it unchanged (a), or refuse (b).
- Test: no render ever emits an empty secret value.
- Demo/example: tutorial secret flow; state it in completion notes.
