**Depends on:** None.

**Related:** `DEC-029` (internal keys leave its scope), `DEC-062` (not a dependency:
this needs no cloud IAM), `BUG-088`/`BUG-089` (`calls`/`called_by` derived from the whole
workspace), `DEC-026` §7 (no ambient Kubernetes token), `DEC-022` (OCaml and TS parity),
`DEC-051` (BYO capability facts).

## Question

When `orders` calls an internal endpoint on `payments`, how does `payments` know who is
calling and whether that caller may call it? The common answer is a shared
`PAYMENTS_INTERNAL_API_KEY`. That proves only that the caller is one of the parties who
know the key. It is long-lived, has several holders (so rotation needs an overlap
window), and it is one more secret to store, grant and rotate.

## Decision direction (operator, 2026-10-01)

> **Sol-to-Sol authentication derives from workload identity; authorization derives from
> the declared `calls` graph. Not shared application secrets.**

Authentication and authorization stay separate. The token proves *which unit is calling*.
The `calls` graph decides *whether that unit may call this one*.

```text
declaration           calls = ["payments/payments_svc"]      (orders' sol.toml)
        │
        ├─► NetworkPolicy        can packets from orders reach payments?       (exists today)
        └─► framework authz      may authenticated unit orders invoke payments' internal interface?
```

The two controls are **deliberately redundant, not substitutes**. If NetworkPolicy is
loosened, application authentication still holds. If application authorization has a
bug, NetworkPolicy still limits connectivity.

The developer never handles the token:

```text
Service.call Payments.create_order request          (OCaml; TS equivalent)
  orders: obtain short-lived token, aud = payments ──► Authorization: Bearer <token>
  payments: issuer/signature valid? aud = payments? caller = orders? calls graph permits orders? ──► allow
```

## What already exists (checked 2026-10-01)

- **Each unit already has its own ServiceAccount** with
  `automountServiceAccountToken: false` (`cli/lib/workspace/sol_cli_manifest_yaml.ml:130`,
  `serviceAccountName` at `:412`). So a per-unit identity exists, and no ambient API
  token is mounted.
- **The `calls` edge is already declared** (`examples/pluto/app/payments/charge_svc/sol.toml:13`)
  and derived into `calls`/`called_by` (`cli/lib/deploy/sol_cli_deployment_plan.mli:64-65`),
  which renders NetworkPolicy ingress.

## Proposed mechanism to qualify: projected ServiceAccount tokens

The direction is decided. **The mechanism is a candidate to qualify**, not settled. A
projected ServiceAccount token volume with `audience: <callee>` gives each pod a
short-lived JWT, signed by the cluster and refreshed by the kubelet. Its audience is
*not* the API server's, so it grants no Kubernetes API access, and `DEC-026` §7 ("no
ambient Kubernetes token") holds. That claim must be verified, not assumed.

## Scoping questions this resolution closes

1. **Verifying the token.** Either check it offline against the issuer's JWKS, or ask the
   API server with `TokenReview`:
   - **JWKS:** no API round-trip, but a token stays valid until it expires even after its
     pod is deleted, and the callee must be able to reach issuer discovery.
   - **`TokenReview`:** catches deleted pods, but the callee needs `system:auth-delegator`
     RBAC, and every call (or cache miss) costs an API round-trip.

   Pick one, with the reasons.
2. **Issuer discovery and the trust root for each driver.** EKS and GKE publish an OIDC
   issuer. In-cluster discovery needs `system:service-account-issuer-discovery` access.
   For `byo`, decide whether issuer discovery is a required capability the driver checks
   (`DEC-051`), and what happens when it is missing.
3. **Key rotation.** JWKS caching, re-fetching on an unknown `kid`, and how long a
   rotated-out key is still trusted.
4. **Claims → unit mapping.** `sub = system:serviceaccount:<ns>:<sa>` and the
   `kubernetes.io` claim (namespace, SA, pod). The mapping from those to a Sol unit
   identity must be exact and must not depend on mutable labels.
5. **Token lifetime.** The minimum projected `expirationSeconds` is 600. Decide the value
   and how the framework re-reads the refreshed file.
6. **Which routes are "internal"**, and the default: verification on unless a route is
   declared public, so it cannot be forgotten.
7. **Callers from other runtimes later** (Cloud Run ID tokens, any Lambda path). The
   callee accepts a configured *set* of trusted issuers. Keep that open, but implement
   only the Kubernetes issuer now.

## Out of scope (non-goals)

- SPIFFE/SPIRE, mTLS, or a service mesh. These could become useful if Sol later needs
  stronger transport or workload-attestation properties. They are far more machinery
  than this problem needs.
- External callers into Sol, which `DEC-029` covers: identity-based authentication where
  practical, with shared keys as a fallback.

## Resolution (2026-10-02)

**Evidence:** repo inspection — each unit already has its own ServiceAccount with
`automountServiceAccountToken: false` (`sol_cli_manifest_yaml.service_account_doc`),
`serviceAccountName` is set on every workload, and the `calls` edge is declared in
`sol.toml` and derived into `calls`/`called_by` (`sol_cli_deployment_plan`), which
renders NetworkPolicy ingress. The projected-token mechanism and its claims are the
upstream Kubernetes ServiceAccount-token contract
(<https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/>,
<https://kubernetes.io/docs/reference/access-authn-authz/authentication/#service-account-tokens>).
The live mechanism is gated on the operator's authorization and is filed as
`VERIF-022`.

### Answers to the open questions

1. **Verifying the token: offline JWKS.** The callee discovers the issuer from the
   token's `iss`, fetches its OIDC discovery document and JWKS, and verifies
   signature, `iss`, `aud`, `exp`/`nbf` locally — no API round-trip per call, and
   the callee does not need `system:auth-delegator`. The cost is that a token from
   a deleted pod remains valid until it expires; that window is bounded by the
   token lifetime (below) and the callee is inside the cluster behind
   NetworkPolicy. `TokenReview` is deferred, with a trigger: switch (or add it on
   a per-callee basis) if a Sol scenario requires a deleted pod's token to be
   rejected *before* expiry, which needs `system:auth-delegator` and an API
   round-trip.
2. **Issuer discovery and the trust root.** The callee reads the `iss` claim and
   must be able to reach that issuer's discovery endpoint; on `aws` (EKS) and `gcp`
   (GKE) the cluster publishes a discoverable OIDC issuer. For `byo`, issuer
   discovery is a **required capability the driver checks** (`DEC-051`): if the
   cluster does not publish a reachable issuer, the driver reports the capability
   missing and Sol does **not** claim framework-authenticated calls — it never
   silently falls back to NetworkPolicy as if it were equivalent. The invariant
   that a projected token with a caller-chosen audience grants no Kubernetes API
   access is verified in `VERIF-022`, not assumed.
3. **Key rotation.** The callee caches the JWKS with a short TTL and re-fetches
   immediately on an unknown `kid`. A rotated-out key stays trusted only while it
   is still published plus one cache TTL, so the issuer must keep a signing key
   published for at least the maximum token lifetime after it stops signing; with
   the lifetime below, that is the stated trust window.
4. **Claims → unit mapping.** The identity is `sub =
   system:serviceaccount:<namespace>:<serviceaccount>`. `<namespace>` is the unit's
   `domain` namespace and `<serviceaccount>` is its k8s name, so the mapping to the
   Sol unit `domain/unit` is exact and derived from committed declarations only —
   never from mutable labels. The `kubernetes.io` claims (`namespace`,
   `serviceaccount.name`, `pod.name`) are cross-checks on the token, not the
   identity. The callee additionally checks that the caller's `aud` equals its own
   unit, then consults the declared `calls` graph.
5. **Token lifetime.** `expirationSeconds: 3600` (well above the 600 minimum). The
   kubelet refreshes the projected file before expiry; the framework re-reads the
   file when it changes (and on a short bound) rather than caching the token for
   the process lifetime, so a rotated token is picked up without a restart.
6. **Internal is the default.** Framework authentication is **on for every route
   unless the route is explicitly declared public** in the workspace declaration,
   so a forgotten declaration denies rather than exposes. `sol-svc`'s existing
   public routes (`/healthz`, `/readyz`, and `/metrics` where the deployment
   exposes it) are the explicit public set; everything else is internal.
7. **Other runtimes later.** The callee accepts a configured **set** of trusted
   issuers. Only the Kubernetes issuer is implemented now; Cloud Run ID tokens and
   any Lambda path are `Not_implemented` with the trigger "when a `sol-fn` runtime
   ships", and the set keeps the design open.

### Mechanism and driver verdicts

The mechanism is a **projected ServiceAccount token volume** with
`audience: <callee unit>` and `expirationSeconds: 3600`, mounted at a stable path;
the framework presents it as `Authorization: Bearer` and the callee verifies it as
above. NetworkPolicy and framework authorization stay **redundant**: loosening
either leaves the other.

| Driver | Verdict |
|---|---|
| `aws` (EKS) | mechanism `to qualify` in `VERIF-022`; EKS publishes the OIDC issuer |
| `gcp` (GKE) | mechanism `to qualify` in `VERIF-022`; GKE publishes the OIDC issuer |
| `byo` | `to qualify`, and issuer discovery is a required checked capability (`DEC-051`); missing means the capability is reported absent |

### Framework API (OCaml and TS, `DEC-022`)

- **Caller.** `Service.call Payments.create_order request` resolves the callee
  unit, reads the projected token for that audience, and attaches
  `Authorization: Bearer <token>`. The developer never handles the token. The
  callee is known from the declared `calls` graph, so an undeclared call site is a
  build/plan-time error, not a runtime one.
- **Callee.** Verification is middleware: it validates the token (question 1), maps
  the subject to a unit (question 4), and checks that the mapped unit is in the
  callee's `called_by` set. On success it exposes the authenticated caller to the
  handler; on failure it returns `401` (unauthenticated) or `403` (authenticated
  but undeclared caller) without running the handler.
- **Parity.** Both languages implement the same contract — audience, file path,
  claims mapping, error codes — as capability and behavioural parity, not shared
  implementation (`DEC-022`). The TS framework gets the same `Service.call` shape
  and the same verification middleware semantics.

### Demo/example obligation

The implementing unit updates the pluto `calls` edge
(`payments/charge_svc` → `checkout/checkout_svc`) so the call is authenticated and
authorized, and adds a negative case: a caller not in `called_by` is refused with
`403`. Both OCaml and TS parity must be stated in that unit's completion notes.
