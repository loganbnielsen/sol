title: A promoted ticket still reads as blocked because the promotion leaves the decision marker in place

**Depends on:** None.

## Problem

`Soldev_ticket.has_human_decision_gate` refuses pickup for any ticket whose body contains one of
a short list of literal marker strings: a heading that asks for a decision, the sibling headings
for a ticket that is blocked or has open questions, and three bare marker words (the "to be
decided" abbreviation, a parenthesised decide-marker, and a shout for a human). The 2026-10-03
adjudication recorded each decision *below* that heading — as
`## Decision (2026-10-03) — …` — and promoted the ticket to `READY_FOR_ENGINEERING`, leaving the
marker in place. The promotion and the gate then disagree: actionable by directory, blocked by
the ticket's own body.

Reproduced on `main @ 8b5b0f0f`, before this stream moved the tickets:

```console
$ soldev pipeline check INFRA-082
worktree: (unpushed commits @ /home/lbendtly/Code/sol-INFRA-082)
status: blocked-for-human-decision
```

At that point INFRA-082 was in `READY_FOR_ENGINEERING/` with its decision recorded in the same
body. The heading is the only cause: renaming it to `## The question (answered 2026-10-03,
decision below)`, with the rest of the body unchanged, is what this stream had to do before the
ticket would validate and submit. INFRA-083 carried the same pair of headings, and INFRA-094
carries both a decision marker *and* a blocked-on marker — all three from the same promotion
commit.

A second consequence of the same substring match: a ticket that *documents* the marker is
itself blocked. This ticket had to be written without the marker's `##` prefix and without the
marker words, because quoting them in prose — as a reader of the gate would — matches. The gate
has no notion of code spans or quoted text.

## Impact

A promoted ticket reads as waiting on a human, so `/work` stops before creating a worktree and
any reader of `pipeline check` sees a promotion that appears not to have happened. The
invariant the gate protects is intact — the marker simply stopped being cleared when the
question it marks was answered.

## Recommended remediation

Make the promotion that records a decision rewrite the marker heading as well: it is the act
that answers the question, so it owns the marker. Add a rule to `soldev pipeline validate`
(which CI runs unconditionally) refusing a `READY_FOR_ENGINEERING` ticket that carries both a
decision marker and a recorded decision section, so the state cannot recur. The same rule
settles the quoting case: a `BACKLOG` ticket that quotes the marker is a documentation act, not
an unanswered question, and should not be reported as blocked.

The alternative shape — teaching the gate that a marker followed by a recorded decision no
longer blocks — is weaker: it leaves a marker that means "unresolved" beside one that means
"resolved", and the two readings of one body keep diverging. A correction in the other
direction is the one this ticket asks for.

## Acceptance criteria

- A ticket promoted with a recorded decision reads as actionable (`soldev pipeline check`
  reports it as pickable, not as blocked on a human).
- A ticket carrying a marker with no recorded decision still reads as blocked.
- A ticket that only quotes the marker — in a code block, a span, or prose — does not read as
  blocked.
- Whichever of the two owns the change, the behaviour is pinned by a test.
- No app-author surface changes, so no `examples/` or tutorial demo applies; no
  language-parity impact (this is maintainer tooling in `internal/tooling/soldev`).
