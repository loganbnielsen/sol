**Related:** DOCS-019, DEC-031, DEC-032, OBS-010, OBS-042, OBS-046.

## What this is

Traces are the only Sol signal a developer cannot reach from the CLI. Logs and
metrics have `sol open logs|metrics`; traces have nothing — even though the
platform installs Tempo, readiness-checks it, emits spans from all three
primitives through `Sol_obs`, and wires a Loki derived field into the Tempo
datasource.

Add the missing view, in the shipped shape (a `sol open` view with a positional
scope; DEC-031 may later change which axis carries the positional, which is not
this ticket's concern):

```bash
sol open traces                                 # workspace
sol open traces payments                        # domain
sol open traces payments/checkout-svc           # unit
sol open traces payments/checkout-svc --links   # raw URL, no browser
```

The user should not need to know the Tempo datasource uid, that the query API is
on port 3200 while OTLP ingestion is on 4318, or what trace search syntax the
Grafana Tempo datasource expects.

The genuinely open part is the *domain and workspace* query. A unit maps to one
service name, but "traces across domain boundaries" and "workspace traces" need a
query across a set of services. The ticket must establish that query shape from
what the emitted spans actually carry — the same identity attributes the metrics
and logs already use — rather than guessing it, and must state what happens when
the available attributes cannot express the requested scope.

## Evidence (2026-09-18, `main` at 790dc3e8)

The view set has no traces case:

```text
cli/sol/lib/sol_cli_open.ml:18   type kind = Logs | Metrics | Dashboard

$ sol open --help | sed -n '/COMMANDS/,/COMMON/p'
       dashboard […] [SCOPE]
       logs […] [SCOPE]
       metrics […] [SCOPE]
```

Tempo is real and already wired, so the missing piece is the CLI surface and the
scope→query mapping, not the plumbing:

- installed by `sol local infra up` — `cli/sol/bin/cmd_local.ml:411`,
  `grafana-community/tempo` (OBS-042);
- readiness-checked as part of the platform lifecycle —
  `cli/sol/lib/sol_cli_cloud_lifecycle.ml:390`;
- Grafana's Loki datasource carries the derived-field link into it —
  `cli/sol/bin/cmd_local.ml:112`, via `Sol_cli_dev_observability`;
- spans are emitted by all three primitives through `Sol_obs`
  (`framework/ocaml/sol-obs`), and logfmt log lines carry `trace_id`/`span_id`.

## Non-goals

- Not trace storage, sampling configuration, or a Tempo replacement.
- Not a trace-query feature set; one good scoped link per scope, the same
  philosophy as `sol open logs`.
- Not a new observability backend mode.
- Not changing which axis carries the scope (DEC-031), and not adding a target
  axis (DEC-032).
- Not an in-CLI trace browser.

## Acceptance criteria

- `sol open traces [SCOPE]` prints a Grafana URL with a pre-built Tempo query for
  workspace, domain, and unit scope, and `--links` prints the raw URL without
  opening a browser.
- The `external` and `self_hosted_durable` backends behave like the existing
  views: a resolved URL, or an explicit "no URL because …" explanation — never a
  broken link, matching `Sol_cli_observability_url`'s existing philosophy.
- The scope→query mapping is derived from attributes the emitted spans actually
  carry. The ticket records which attributes those are, checked against a real
  workspace, instead of assuming the OpenTelemetry semantic conventions.
- Unit scope returns that unit's traces from a real run — the trace of an HTTP
  request through `checkout_svc`, or of a Kafka message through `notify_worker`.
- A scope whose traces cannot be expressed by the available attributes fails with
  an explanation, not an empty view.
- The unit-scope query resolves across domains, so a trace crossing a domain
  boundary (`charge_svc` → `checkout_svc`) appears under both units.

**Demo/example coverage:** A new CLI view changes what an app author does, so
`examples/pluto` and/or `TUTORIAL.md` must document `sol open traces` against a
real trace from the demo path, and the change is demo-facing (`/demo-review`).

**TypeScript parity:** The trace contract is already cross-language (OTel span
propagation, W3C context, shared identity attributes), and this adds a view over
language-neutral telemetry. The TypeScript units' spans must resolve through the
same query; the completion notes record whether they emit the attributes the
query needs, or file the gap.

## Finding (2026-09-18): the spans do not carry the identity attributes the query needs

Established by checking what the emitted spans actually carry, on the running k3d
`sol-local` substrate with `examples/pluto` deployed (workspace `pluto`, domain
`demo-ts`) — not assumed from the OpenTelemetry semantic conventions.

A `POST /orders` to `order-svc` produced one cross-service trace,
`c6c05982a2398cb242ab124c1587d5ea`:

```text
resource service.name="order-svc-ts"           span receive_order  PRODUCER  attrs {order_id, item}
resource service.name="fulfillment-worker-ts"  span fulfill_order  CONSUMER  attrs {}
```

Tempo's searchable attribute scopes for that data:

```text
intrinsic: the standard duration/trace/span keys
resource:  service.name, telemetry.sdk.language, telemetry.sdk.name, telemetry.sdk.version
span:      item, order_id
```

**So spans carry only `service.name`.** There is no `workspace`, `domain`,
`primitive` or `release` attribute — unlike logs, where the same substrate's
streams do carry the taxonomy (Alloy promotes the pod labels; OBS-046 verified
this on the same cluster).

And `service.name` is **chosen by the application**, not by Sol:
`examples/pluto/app/demo_ts/order_svc/src/tracing.ts` passes the app's own string
to `initTracing`, and here that string is the package name `order-svc-ts`. Sol's
unit is `order_svc`, its Kubernetes name is `order-svc`; the `-ts` suffix belongs
to the app.

What that means for the acceptance criteria above:

- **unit scope** is expressible only by matching an app-chosen string
  (`service.name =~ "order-svc.*"`), which happens to work here and is exactly
  the coincidence this series keeps finding;
- **domain and workspace scope cannot be expressed at all** from the available
  attributes, because Sol cannot enumerate the services in a domain — it does not
  control what an app calls itself;
- the ticket's premise that traces carry "the same identity attributes the metrics
  and logs already use" is **false**.

This is the same failure shape as OBS-046 (the namespace convention) and DEC-032
(the ambient backend resolution): a link built from something the identity model
itself calls an implementation detail. Here the implementation detail is the
application's choice of its own name.

## Decision Required

The view cannot be built correctly until the attributes it queries exist. The two
resolutions differ in scope and in whose contract changes, so this is a product
call rather than an implementation detail.

**A — Sol stamps its identity onto the trace resource (recommended).** Carry the
taxonomy as resource attributes (the standard `OTEL_RESOURCE_ATTRIBUTES` channel,
or equivalent wiring in the two language libraries), so every span carries
`workspace`, `domain`, `primitive` and `release` exactly as logs and metrics
already do through the manifest renderer. All three scopes then become the same
selector shape used everywhere else, and this ticket shrinks back to the small
view it was meant to be. Cost: a manifest/renderer plus cross-language change that
applies to every unit, with a demo update and a per-language verdict — well past
"add a view".

**B — Accept `service.name` as the trace identity.** Build the view on a
`service.name` match and document that traces are scoped by an app-chosen name.
Cheap, but it makes the link depend on a convention Sol does not own — the same
defect OBS-046 is fixing for logs — and it cannot express domain or workspace
scope at all.

Until this is settled the ticket is **not actionable**, so it is parked in
`BACKLOG`. The acceptance criteria above stand once a resolution is chosen; under
(A) they should be re-read as "after the resource attributes exist".
