The scaffolded schema-compatibility gate is never run: it is an executable, not a test

**Depends on:** None.

**Finding:** FND-0040 (`internal/pipeline/audits/findings/`). Found in BUG-049's review.

**Premise verified 2026-09-24** on BUG-049's branch: `ws_test_dune`
(`cli/sol/lib/sol_cli_scaffold_templates.ml`) declares `(executable (name test_schemas))`,
and the generated CI (`tpl_github_ci`) runs `dune runtest`, which does not run
executables. So the gate BUG-049 hardened (FULL, 404 parsing, failing under CI without a
registry) runs only when someone invokes it by hand.

## Problem

A generated workspace's CI passes without ever checking schema compatibility. The
tutorial presents the gate as blocking breaking changes before staging.

## Decision Required

Making it a real `(test)` changes what every generated workspace's CI needs. It has to
reach the registry that holds the *published* schema history, because a fresh CI
registry has nothing to be compatible with, and under BUG-049 it fails when
`SCHEMA_REGISTRY_URL` is missing. Choose one: (a) `(test)` + a
`SCHEMA_REGISTRY_URL` repository secret documented as required, failing until
configured; (b) a separate, clearly named CI step that runs the executable when the
secret is set and prints a visible "not checked" warning when it is not; (c) something
else.

## Remediation

Per the decision: change `ws_test_dune` and/or `tpl_github_ci`, and document the secret
in the generated README and `TUTORIAL.md`.

## Acceptance criteria

- A generated workspace's CI either runs the gate against the configured registry or
  says visibly that it did not.
- Demo/example: scaffold templates are the demo; state in completion notes.
