## Question

`docs/reference/substrate.md` states what must exist before `sol deploy` runs —
reachable cluster and kubeconfig, a pullable registry prefix, `POSTGRES_URL` as a
Kubernetes Secret key, `KAFKA_BROKERS` and a schema-registry URL with the **required**
`KAFKA_SECURITY_PROTOCOL` (`SEC-007`), Loki and Pushgateway endpoints, an optional base
domain and cluster issuer. It is prose, and it is the only statement of the contract:
`INFRA-014` exists because nothing has verified that the list can be satisfied anywhere
except AWS, GCP and local k3d, and nothing in the product checks it.

**Should the substrate contract become something Sol establishes per target by
observation — with configuration supplying only what an observation cannot derive — and
should the YAML therefore refuse to carry assertions about substrate facts?**

## The four concepts that must not collapse

An earlier sketch of this design had a per-target block like:

```yaml
substrate:
  database: managed
  kafka: external
```

That conflates four different things. Keeping them separate is the decision:

| Concept | Question it answers | Where it belongs |
|---|---|---|
| **Driver capability** | What does Sol know how to *do* for this target? | The driver record (`Sol_cli_provider_capabilities`), not the YAML |
| **Substrate requirement** | What must be *true* for the application and platform to work at all? | The contract (`docs/reference/substrate.md`), provider-neutral |
| **Observation** | What is true of *this* target right now? | Preflight / readiness, with a three-valued verdict |
| **Configuration** | What must the operator tell Sol to perform the operation or the observation? | `sol.yml` / `environments.yml`, only where not derivable |

**Principle:**

> Configuration tells Sol how to inspect and use the substrate; preflight establishes
> whether the substrate contract is satisfied.

So `database: managed` is not configuration — if Sol needs to know whether Postgres is
managed, it can observe what it is given (a connection string and a Secret), and what it
cannot observe is an *exception*, not a fact: the operator must supply a connection at
all, and today that is `POSTGRES_URL`.

## What is established, so this is not invented

- **The contract already exists as a list.** `substrate.md` § *What You Bring* names
  every required input; this decision is about making it checkable, not about inventing
  a taxonomy.
- **The verdict vocabulary already exists and fails closed.** ADR 0002 uses
  `Established` / `Unmet` with a side and a reason, refuses to infer readiness, and
  distinguishes plan's `Deferred` (Sol lacks prior state to plan a later phase) from
  readiness's `Unmet` (`:55-64`). `sol target show <target> --check` already reports
  live readiness or a named unmet reason (`:32`).
- **Three-valued observation already exists.** `PRESENT` / `ABSENT` / `UNKNOWN` is the
  rule on the destroy path, where an unqueryable answer fails the command
  (`DEC-044`, `DEC-040`). An unobservable substrate input belongs in the same shape.
- **A mode-and-configuration precedent already exists.** Observability is configured as
  a *mode* — `observability_backend ∈ {local, self_hosted_durable, external}`
  (`cli/lib/workspace/sol_cli_observability_url.ml:78,97`,
  `docs/architecture/observability-design.md:148-156`) — plus endpoint URLs. The mode
  says how Sol behaves; it does not assert that the endpoints are healthy. That is the
  shape this decision generalises.
- **Honest non-observation already has a precedent.** When a capability is not
  implemented, the observation reports *not observed* rather than *sufficient*
  (AWS's `disk_quota = None`, `sol_cli_provider_capabilities.ml:105-109`).
- **Not everything is observable.** `substrate.md` is explicit that Sol does not create
  image-pull credentials, DNS records or certificates, and `INFRA-014:26` records the
  consequence for a provider with no IAM equivalent: the DNS-01 credential path is a
  token in a Secret. Those are the exceptions that must be declared.

## Options

| | Shape | Why / cost | Verdict |
|---|---|---|---|
| **A** | The contract becomes an **observation pass**; the YAML carries configuration plus explicitly-labelled exceptions. Unobservable answers are `UNKNOWN` and fail closed. | Uses the verdict vocabulary already in the tree; the honesty is mechanical (a thing that cannot be checked says so), and a new substrate is supported the moment it can be observed rather than when someone asserts the right words. | **Recommended** |
| **B** | A per-target `substrate:` block asserting facts (`database: managed`, `kafka: external`). | The assertion can be wrong, and nothing detects it: it is exactly the failure `DEC-040` names, and it makes the profile preflight trust a declaration over a measurement. It also invites a universal config vocabulary, which is the `DEC-051` non-goal. | Reject |
| **C** | Keep prose; add nothing. | The state that produced `INFRA-014`. A written contract with no observation is a claim, and `sol deploy` will go on failing somewhere later with a worse message. | Reject as the answer; acceptable only if this decision records why the product does not check its own contract |
| **D** | Full per-capability taxonomy (managed database / managed Kafka / registry / identity / observability), one YAML key each. | Rebuilds a configuration vocabulary per capability and per driver, and every key is still an assertion unless something observes it. Speculative work for substrates nobody has asked for. | Reject for now (see non-goals) |

## Recommendation

**A**, with two constraints that make it a decision about the *product* rather than
about a check script:

1. **The requirement side is provider-neutral and written down once.** Every substrate
   input in `substrate.md` gets a verdict from an observation Sol actually performs, and
   the contract is expressed in terms of what Sol consumes (endpoint reachable, secret
   key present, registry pullable), never in terms of which cloud provides it.
2. **The configuration side is the minimum needed to perform the observation, and
   nothing else.** Where an input is supplied by the operator (a connection string, a
   registry prefix, endpoints), that *is* the configuration — Sol observes the
   consequence, it does not ask the operator to characterise it. Where something
   genuinely cannot be discovered (a DNS-01 token path with no IAM equivalent; a
   certificate Issuer selection; a base domain), it is declared as an exception, with
   the reason it cannot be observed recorded next to it.

## Affected invariants

1. **`DEC-040`/`FND-0021` and ADR 0002's "observed, never inferred"** — extended from
   readiness and destruction to the substrate inputs `sol deploy` assumes. This is the
   load-bearing one: a `substrate:` assertion block would be a direct violation, which is
   why it is the rejected option rather than a variant.
2. **"Dev mirrors prod exactly"** (AGENTS.md). The observation must be the same code on
   a local k3d cluster and a cloud target, or local becomes a place where the contract
   is assumed rather than checked.
3. **`SEC-007` — `KAFKA_SECURITY_PROTOCOL` is required, never defaulted.** An
   observation must report its absence as a named `Unmet`, not supply plaintext.
4. **The profile preflight's vocabulary and fail-closed rule** (ADR 0002 `:120-122`,
   `DEC-026`). New substrate verdicts must use `Established` / `Unmet` (+ `UNKNOWN`
   where an answer cannot be obtained) and must never upgrade `UNKNOWN` to `Established`.
5. **`INFRA-014`'s acceptance criteria.** "A reader can stand up the substrate and
   complete `sol deploy` + `sol migrate` from the recipe alone" is only honest if the
   recipe's inputs are the ones the product checks; that ticket's cost table and
   workaround notes become evidence for this contract rather than prose beside it.
6. **`DEC-022` language parity:** none. The contract is consumed identically by OCaml and
   TypeScript applications; no per-language surface changes.

## Smallest migration

1. **Write the contract down as checkable predicates.** One list, next to or inside
   `docs/reference/substrate.md`, each entry naming how Sol observes it and which
   existing command reports the verdict. No new taxonomy, no new YAML keys.
2. **Reuse the existing surface.** `sol target show <target> --check` (and the profile
   preflight that `sol deploy --dry-run` already runs) is where the verdicts belong; the
   first unit adds the predicates it can observe today and reports the rest as
   `UNKNOWN` with a named reason.
3. **Classify the non-observable remainder explicitly.** Every entry that must be
   declared becomes a documented exception with its reason — the DNS/TLS credential path
   (`INFRA-014:26`) is the first.
4. **Refuse assertion-shaped keys.** If any YAML key is proposed that states a
   discoverable substrate fact, it is rejected by pointing at this decision; the
   `DEC-053` key contract is where "which keys exist at all" is enforced.

Nothing here changes an existing target file, and no yml is rewritten: the work is an
observation pass plus a written contract, and it can land before `DEC-051` because the
observation is driver-neutral by construction. Where `DEC-051` is a prerequisite is the
case where an observation needs to know whether a driver owns a root at all.

## Out of scope (non-goals)

- **Do not implement DigitalOcean, Hetzner, Civo or Azure.** No driver, no
  provider-specific observation, no per-provider substrate vocabulary.
- **Do not design a universal capability taxonomy.** Option D is rejected for now; the
  requirement list comes from `substrate.md` and `INFRA-014`, not from a grid.
- **Do not add a new command.** The verdicts belong on the existing readiness/preflight
  surfaces unless a unit shows they cannot be expressed there.
- **Do not decide driver naming, admission, or the `sol cloud *` refusal** — `DEC-051`.

## Acceptance criteria

- The provider-neutral substrate contract is recorded as observable predicates, each
  with the verdict source named.
- Non-observable inputs are enumerated as exceptions, each with the reason it cannot be
  observed.
- A single missing or unobservable required input produces a named `Unmet`/`UNKNOWN`
  verdict that fails closed, and `UNKNOWN` is never reported as satisfied.
- No YAML key asserts a discoverable substrate fact, recorded as a rule (with the
  `DEC-053` key contract named as where it is enforced).
- **No language-parity impact** (`DEC-022`) — stated in the implementing ticket's
  completion notes.
