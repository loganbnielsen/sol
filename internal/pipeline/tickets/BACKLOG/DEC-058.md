**Depends on:** None.

**Related:** `FEAT-106` (part B: driving the environment stages from `sol deploy`),
`AUDIT-072` (Sol does not write your kubeconfig or your target file), `DEC-020` (no
ambient kubectl context), `DEC-030` (authentication for operating an environment from a
fresh machine, still open), `DEC-057` §1/§2 (the stage set and the inline first run),
`DEC-034` (the bounded cluster-access identity), `docs/deployment/production-bootstrap.md`.

## Decision Required

`DEC-057` §1 puts `provision` and `platform` on the happy path, so a single
`sol deploy <target>` is meant to reach a deployed application on an account with no
installation. FEAT-106 part A landed the installation half of that run; the environment
half has a fork that engineering cannot settle on its own, because it decides what Sol
is allowed to do with the caller's cluster credentials.

**The problem.** A deploy needs a cluster connection. `sol cloud apply` provisions the
cluster and prints a `deploy_kubeconfig_command` for the *operator* to run, and
deliberately neither runs it nor writes the user's kubeconfig or target file
(`AUDIT-072`). The deploy identity is a separate trust domain with its own access entry
(`DEC-034`), and Sol refuses an ambient kubectl context (`DEC-020`). So after `sol
deploy` provisions an environment, there is no supported way for *that same run* to
reach the cluster it just created unless one of the three is chosen.

### Option A — Sol establishes ephemeral deploy-identity cluster access for the run

Reach the cluster the way the provisioning path already reaches it for its own role
(`Sol_cli_aws_cluster.provisioner_kubeconfig`: an ephemeral kubeconfig that is never
written into the user's home), but as the **deploy** identity rather than the
provisioner's. The run then continues into `platform`, `migration` and `deployment`
unattended, which is exactly `DEC-057` §2's experience.

- Means: Sol assembles cluster credentials in its own working directory for the
  duration of a run, and the *deploy* identity gets whatever it needs to be usable from
  a workstation rather than only from a CI runner.
- Costs: the deploy identity's current shape is a CI-shaped identity (assumed by a
  pipeline, no cluster access of its own); pointing it at an operator's machine changes
  what it is for, and the security model around it (`DEC-034`) would be redrawn here
  rather than in `DEC-030`.
- Touches: `DEC-020`, `DEC-034`, `AUDIT-072`, and the two identities' separation.

### Option B — the run stops and names the two operator steps (today's behaviour)

`sol deploy` provisions the environment, prints the kubeconfig command and the
`kube_context` it needs, and asks the operator to finish. The first run is two commands
plus one target-file edit, and `sol deploy` stays unable to reach a cluster it created.

- Means: nothing new about credentials; `AUDIT-072` and `DEC-020` stand unamended.
- Costs: `FEAT-106`'s AC1 ("without the user invoking any other command") is not
  reachable this way, and the target file must be edited mid-first-run — which is the
  ritual `DEC-057` §2 exists to remove.
- Touches: `FEAT-106` (its AC1 would need narrowing), `DOCS-026`.

### Option C — provider-dependent: A where the provider has the path, B where it does not

Option A on AWS (whose ephemeral-kubeconfig path exists), Option B for GCP until it has
an equivalent.

- Means: the first-run experience differs by provider, which is honest about what is
  built but makes the on-ramp provider-shaped.
- Costs: two documented first-run flows, and a rule for what "equivalent" means so GCP
  is a recorded deferral rather than drift (`DEC-022`'s vocabulary applies to providers
  here by analogy).

## What is not in question

- Sol still does not write the user's `~/.kube/config` or the target file
  (`AUDIT-072`), whichever option is chosen.
- A deploy still does not fall back to the ambient kubectl context (`DEC-020`).
- The provisioning and deploy identities stay distinct (`DEC-034`); no option widens
  either one's authority.
- `DEC-030` (fresh-machine authentication for *operating* an environment) stays open and
  is not answered here.

## Recommendation

Option C, with Option A on AWS: it does not gate the AWS path — the one provider with a
qualified production profile — on a redesign of `DEC-034`, and it keeps the GCP gap
explicit instead of forcing a provider-shaped fiction. The operator decides.
