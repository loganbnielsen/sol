title: Where Terraform's working state lives when the platform roots come from an installed release
source: FEAT-101 implementation (2026-09-26); DEC-049's bundle model
---

**Depends on:** None.

## Context

DEC-049 ships the Terraform roots inside the release bundle (`share/sol/<version>/platform/cloud/<provider>/{cluster,platform}`), and FEAT-101 does that. But a Terraform root is a *working directory*, not a read-only asset. Sol runs every command as `terraform -chdir=<root> …` (`cli/lib/cloud/sol_cli_terraform.ml`), so Terraform writes into the root:

- `init -reconfigure` writes `.terraform/` (providers, modules, backend config) there;
- a failed state push writes **`errored.tfstate`** there. `Sol_cli_terraform.supervised` then points the operator at it as "the only record of what this run changed".

`git ls-tree -r origin/main platform/cloud | grep lock` shows the provider lock files are committed; `.gitignore` excludes `.terraform/` and state. So a checkout works because it is writable. An installed release works the same way *if its prefix is writable by the user*, and FEAT-101 documents that requirement. A system-wide, read-only install (for example under `/usr/local` via `sudo`) would break `sol cloud`, and on the failure path the state file could not be written at all.

A related issue, independent of releases: every target of a provider shares one `.terraform/` inside the root, switched by `-reconfigure` on each run. Two concurrent `sol cloud` runs for different targets from one checkout would contend for it.

## Decision Required

1. **Keep the root as the working directory; require a user-writable install** (what FEAT-101 ships and documents). Simplest, identical to a checkout. It rules out read-only system installs, and it leaves the shared `.terraform/`.
2. **`TF_DATA_DIR` per target and role, in a writable state directory,** plus `init -lockfile=readonly`. This moves `.terraform/` out of the root and separates targets. It does *not* move `errored.tfstate`, which Terraform writes to its working directory, so a read-only root still loses the failure-path state. Insufficient alone.
3. **A per-target working directory, refreshed from the bundle on every run:** copy `platform/cloud/` (a few hundred KB, including `modules/`, which the roots reference by relative path) into e.g. `<workspace>/.sol/terraform/<target>/`, and run Terraform there, with `.terraform/` and `errored.tfstate` beside it. It is re-copied every invocation, so it can never go stale and is not a cache. It works for read-only installs, separates targets, and gives both forms the same semantics. The costs: a copy per run, and the location of `errored.tfstate` moves, so the supervisor's message and runbooks change with it.

Recommendation: **3**. It is the only option that makes the bundle genuinely read-only *and* keeps the failure-path state safe, and it fixes the shared-`.terraform/` contention for checkouts at the same time. It needs your call because DEC-049 ruled out "first-run extraction caches". This is a per-run copy, not a cache, but it is close enough to that line that it shouldn't be decided implicitly.

## Acceptance criteria (once decided)

- Option 3: `sol cloud plan` from a read-only installed bundle succeeds (installed-layout smoke with a read-only mount and Terraform present), and a forced state-push failure leaves `errored.tfstate` where the supervisor says.
- Demo/example: not applicable; state it.
