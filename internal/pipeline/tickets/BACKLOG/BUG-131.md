**Depends on:** None.

## Problem

`sol.yml`'s `services.<name>.path` names a workload's directory, and `sol plan` /
`sol deploy` take their service list from the declaration (`Sol_cli_config.services cfg`,
via `cli/bin/cmd_plan.ml` and `Sol_cli_deployment_plan.of_services_result`).
`sol check` validates only the workloads it discovers by scanning `app/**`
(`Sol_cli_manifest.scan_workspace` → `Sol_cli_check.run`); it never compares the
declared `path` with the filesystem. A declared service with no directory is
therefore invisible to `sol check` and simultaneously rendered by `sol plan`.

Reproduced on `origin/main @ ed3f041f` with no dependency on other work — move a
real unit's directory aside and both commands still treat it as present:

```console
$ cp -R examples/pluto /tmp/pluto-check && cd /tmp/pluto-check
$ mv app/comms/notify_worker /tmp/notify_worker-away
$ sol check
sol check: ok
$ sol plan prod/aws/us-east-1 | sed -n '/Services:/,/Contract/p'
Services:
  - checkout_svc (http)
  path           app/checkout/checkout_svc
  - charge_svc (http)
  path           app/payments/charge_svc
  ...
  - notify_worker (worker)
  path           app/comms/notify_worker
    uses: app_db, events
    scale: 1..2
  ...
```

`app/comms/notify_worker` does not exist, the plan renders it, and `sol check`
is silent; the exit status of both commands is 0.

FEAT-131 hits the same state without moving anything: it declares
`orders_svc` (path `app/payments/orders_svc`) and `fulfilment_worker` (path
`app/comms/fulfilment_worker`) in `sol.yml` and `sol/environments.yml` while
their directories are `FEAT-132`'s to add. `sol check` reports `ok` and
`sol plan prod/aws/us-east-1` lists both with their paths and scale.

## Consequence

Discovery is directory-based by design (`docs/reference/runtime.md` § *Discovery
contract — purely structural, content never inspected*), and the plan is
declaration-based by DEC-065. The two are not reconciled, so "the declaration
says this unit exists" and "this unit exists in `app/`" are two authorities and
only the second is ever checked. `sol check` is documented as validating the
workspace's declarations without Docker or Kubernetes, yet it reports success
for a declaration naming a workload that cannot be built or deployed, and
`sol plan` presents that workload as part of the change. A reader — or an agent
picking up a ticket — cannot tell a declared-but-unimplemented unit from a real
one from either command's output.

## Remediation (proposed, for triage)

Give the declared `path` a verdict in `sol check`: a `services.<name>.path` whose
directory is absent, whose leaf name carries no workload suffix, or whose suffix
disagrees with the declared `type` is a finding. Warn or fail is triage's call —
a warning is enough to make the state visible without changing the exit status
that FEAT-131's acceptance depends on. `sol plan` should not count a service as
resolvable when its directory is missing. Fix this against the existing
directory scan rather than adding a second discovery authority.
