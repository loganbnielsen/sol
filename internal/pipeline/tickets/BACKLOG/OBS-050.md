**Depends on:** None.

## The gap

`docs/architecture/observability-design.md`'s Identity section: "Every log line,
metric, trace, deploy event, and generated dashboard link must carry the same
ownership identity: `workspace`, `env`, `domain`, `service`, `primitive`,
`release`."

Observed locally (`main @ 2a2c5a7c`): a real trace's OTLP resource attributes
are `service.name` **only**.

```text
$ curl -s 'http://localhost:3200/api/traces/6a7e1de7…' | jq -r '.batches[].scopeSpans[].spans[].name'
receive_order
fulfill_order
$ … | jq -r '.batches[] | .resource.attributes[] | select(.key=="service.name") | .value.stringValue' | sort | uniq -c
      1 fulfillment-worker
      1 order-svc
```

There are no `workspace`/`env`/`domain`/`primitive`/`release` resource
attributes. The code path explains why: `Sol_obs.of_env` creates the Tempo
backend without taxonomy context, and the scaffolded app's `~context` is
`[("team","payments")]`, not the taxonomy. Logs get the taxonomy from Alloy's
pod-label promotion and metrics from Prometheus' pod-label map, but a trace's
resource is written by the application, so no scrape-time relabeling adds it.

This means a trace can only be attributed to a `service.name`; it cannot be
filtered by domain, workspace, environment or release the way the same request's
logs and metrics can. `sol open traces` does not exist either (OBS-045), so there
is no supported way to reach a trace from a scope at all.

## Impact

Cross-signal correlation is incomplete in the direction the design promises:
from a log line or metric you can reach a trace by `trace_id`, but from a trace
you cannot recover the workload identity or release. Traces that span services
(frameworks make that the norm) cannot be grouped by owning domain.

## Decision required

The taxonomy has to be attached to spans somewhere, and the options differ in
where the app-author contract lands:

1. **Injected environment + framework context.** The manifest already knows
   `workspace`/`env`/`domain`/`primitive`/`release`; inject them as environment
   variables (`SOL_*`) and have `Sol_obs.of_env` add them to the OTLP resource
   (and to Loki/Prometheus context). Pro: one vocabulary, works for any OTLP
   backend; the app author changes nothing. Con: new env vars and a scaffold
   change.
2. **Collector enrichment.** Have Alloy (or an OTel collector) add resource
   attributes from Kubernetes metadata on the trace path. Pro: no app change.
   Con: Alloy's metrics/traces scope is currently unused (OBS-039/041), and the
   trace path today is app-push, not collector-received.
3. **App-author-supplied `~context`.** Document that an app must pass the
   taxonomy in `~context`. Con: puts a platform invariant on every author and
   drifts immediately.

The choice changes the app-author contract and the platform's telemetry path,
so it is an operator decision, not an implementation detail. Decide between
option 1 and option 2 (option 3 is recorded only to be rejected explicitly).

## Acceptance criteria (once decided)

1. A trace produced by a scaffolded primitive carries the six labels as OTLP
   resource attributes.
2. `service.name` keeps its current value (the existing trace-lookup contract
   must not break).
3. The local demo's Tempo output is asserted to carry the taxonomy, not just
   `service.name`.
4. The TypeScript framework's verdict is recorded (DEC-022).
