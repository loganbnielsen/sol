**Depends on:** None.

**Related:** `DEC-029` (secret grants are its first consumer), `DEC-063` (Sol-to-Sol
identity, which needs **no** cloud IAM and so does not wait on this), `DEC-016` (access
separation), ADR 0002 § identity table (provisioner vs deployer), `AUDIT-072` (Sol owns the
identity contract, the operator owns role lifecycle), `INFRA-025` (the deploy identity's
namespace-scoped RBAC), `DEC-043` § *Design constraints* 2 (never derive an authority
grant), `DEC-051`/`DEC-052` (driver capabilities, observed substrate).

## Question

A unit's declaration can imply cloud authority: `secret "stripe"` implies
`GetSecretValue` on that secret. The same goes for IAM database auth, MSK IAM auth,
object storage, and any queue Sol adds later. Realising that needs a cloud identity per
unit and a grant per declared edge:

```text
unit declaration ──► required cloud capabilities ──► WHO may reconcile them?
```

`sol deploy` runs as the deploy identity, which `INFRA-025` limited to namespace-scoped
Kubernetes RBAC. Creating per-unit roles at deploy time would need `iam:CreateRole`,
`iam:PassRole` and `eks:CreatePodIdentityAssociation` (or the GCP equivalents). An
identity that can create and pass roles can grant itself anything, which collapses the
provisioner/deployer boundary.

## Invariant (operator, 2026-10-01)

> **The identity performing ordinary workload deployment cannot grant a workload new
> cloud authority.**

The ordering this implies:

```text
declaration changed
      │
      ▼
privileged authorization reconciliation   → unit identities and grants exist
      │
      ▼
sol deploy (constrained)                  → deploys units that reference pre-authorized identities
```

If `sol deploy` runs before the grants exist, it **fails while building the plan**,
naming the unit, the missing grant and the reconciliation to run. It never deploys a pod
that hangs in `ContainerCreating`.

## Options

| | Shape | Verdict |
|---|---|---|
| **1** | A **privileged reconciliation** derives unit identities and grants from the declarations and reconciles them. Today that is `sol cloud apply`; it could later be a narrower command. Adding a grant is an infrastructure change, and that is the point. | **Preferred (operator)** |
| **2** | The deploy identity creates roles, fenced by an IAM permissions boundary (a role path such as `/sol/<env>/`, with only the actions Sol grants). | Not chosen casually. The deploy identity joins the IAM control plane, and the boundary policy becomes security-critical code. |
| **3** | The operator creates every unit role by hand (`AUDIT-072`'s posture taken literally). | Impractical once there is a role per unit, and it pushes per-secret IAM onto users, against `DEC-057`. |

On GCP, Workload Identity Federation can grant IAM directly to a Kubernetes ServiceAccount
principal, with no Google service account to create. The grant still has to be made by a
privileged identity; there is just less to create.

## Open Questions

1. **Is the privileged reconciliation `sol cloud apply`, or a narrower command?** For
   example, an authorization-only reconcile that does not touch cluster infrastructure.
   Either way it must read the *whole workspace's* declarations, not one deploy's scope.
   That is the same lesson `BUG-088`/`BUG-089` taught for consumer groups and caller
   ingress.
2. **Where the derived grant set is recorded** so that `sol deploy`'s plan-time check
   can compare against it, and how that check observes reality rather than trusting a
   record (`DEC-052`: observed, not asserted).
3. **How revocation works.** Removing a `secret` line must remove the grant on the next
   reconciliation, and a deploy of the narrower declaration must not wait for it.
4. **How unit identities are named and scoped** per env, so that a dev unit identity can
   never be granted a prod secret (`DEC-016`).

## Acceptance criteria

- The invariant is recorded, with the guard that enforces it: the deploy identity's
  cloud permissions contain no IAM-mutating action.
- One option is chosen, and each open question has an answer or an explicit deferral with
  a trigger.
- The plan-time refusal for a missing grant has a stated message contract, and the
  implementing ticket asserts it.
- Every capability family that will consume this is listed: secrets (`DEC-029`), IAM DB
  auth, MSK IAM auth, object storage.
- No language-parity impact (`DEC-022`): this is platform authorization only.
