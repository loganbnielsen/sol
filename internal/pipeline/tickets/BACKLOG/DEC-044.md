## Decision

**Decided 2026-09-24** by the operator. Both halves were chosen; one is implemented, the other is
recorded as the next unit's to answer. The text below is the decision as it was framed.

Two halves, and they can be decided separately. **Choose both.**

1. **Recovery ownership.** Does Sol's supported destruction path ever *re-adopt* a
   target-declared, provider-present, state-absent resource in order to destroy it — and if so,
   by which mechanism? Or is the claim restated as "converge what state owns, report the
   divergence"?
2. **Verification coverage.** What is the authoritative *expected-resource* set that the
   postcondition must be established against, given that it cannot be the state inventory?

### Chosen (2026-09-24)

1. **Verification coverage — B2, and it is implemented.** The authoritative expected-resource
   set is the target-declared managed addresses read from a read-only, non-destroy
   `plan -json`, UNIONed with the captured Terraform-state inventory. For an address state does
   not represent, the provider is queried from identity the plan itself can establish:
   PRESENT is a violation, an explicit ABSENT satisfies the obligation, and an unqueryable or
   otherwise unestablished answer fails the command. No adoption, no state mutation and no
   provider deletion in that unit.

   **Landed** in the HARDEN-004 declared-universe unit (FND-0055), offline only. One residual is
   named there and here: `declared \ state` cannot be required to a provider observation when
   the *whole* pre-destroy state is empty and the kind's identity is not derivable from
   declared configuration. That is a recorded coverage limitation, never absence, and closing
   it needs a mechanism stronger than B2 (an ownership record outside disposable state, or
   complete per-kind provider discovery).

2. **Recovery ownership — A1, accepted in principle, deliberately not implemented yet.** The
   supported recovery path will adopt an authoritatively identified target-declared /
   provider-present / state-absent resource into Terraform ownership and then destroy it through
   the ordinary asserted destruction path — so "no create or replace on the destroy path" is
   preserved by the assertion machinery already there, and provider-native deletion does not
   become the normal recovery mechanism (A2 stays rejected).

   What is still undecided, and is the smallest remaining decision before any A1 code: **which
   per-kind identity is authoritative enough to `terraform import` on**, and what authorizes
   Sol to assume ownership of an object it did not record. `terraform import` itself does not
   modify infrastructure, but a wrong id imports the wrong object, and FND-0030's own design
   note leaves the ownership question open — so the import-id recipe per kind and the authority
   that selects it are the next unit's subject, not this one's.

### Not decided here

- The exact import mechanics and per-kind import-id recipes (A1's implementation unit). **No
  implementation unit is materialised by this decision yet** — A1's authority question is
  reviewed first, so the ticket is not created ahead of it.
- Attempt 7's successor. A live re-run needs its own explicit authorization and a fresh Phase-0
  baseline, and is not implied by (1).

## The question, in the shape it was found

Attempt 7 (HARDEN-004) was authorized to qualify: *given a target where a provider resource
exists but Terraform state no longer represents that resource, Sol's supported destruction path
converges target-owned infrastructure toward absence without reconstructing the missing
resource, without target edits, without manual state surgery, and without provider-native
deletion as the normal recovery mechanism.* It was stopped **before creating any live resource**
because the positive postcondition is not reachable as written on current `main`, and the
attempt's own criteria forbid the only mechanism the repository already names for reaching it.
The full record is `docs/qualification/2026-09-24-gcp-attempt7-prelive-falsification.md`; the
analysis is FND-0055 and FND-0056.

The two halves are independent and both blocking:

- **ownership** — a resource removed from state is outside `terraform destroy`'s ownership set,
  and Sol has no import/adoption step, so the destroy completes *around* it and the object
  survives (FND-0030, design point 3: "Converging it requires adopting it and then destroying
  it … a new capability");
- **coverage** — Step 5's provider verification is driven by the *captured* inventory, so a
  resource that was never represented is invisible to it and its survival can be reported as
  "the destruction postcondition is established" (FND-0055).

## What is established, so the decision is not made blind

- `terraform destroy` is `terraform apply -destroy` and acts on Terraform-**managed**
  infrastructure; `terraform state rm` "causes Terraform to 'forget' those items **without first
  destroying them in the remote system**". Reproduced locally, no cloud, no credentials, no
  billable resource (Attempt-7 evidence bundle, `falsification-probes/`).
- `terraform import` documents the opposite property and is the only non-constructive ownership
  mechanism: *"This command will not modify your infrastructure, but it will make network
  requests to inspect parts of your infrastructure relevant to the resource being imported."*
- A **read-only, non-destroy `terraform plan -json`** yields both things a fix needs, computed by
  Terraform from the configuration rather than guessed by Sol: the address set the
  configuration declares, which of those state does not represent (their
  `resource_changes[].change.actions` is `["create"]`), and the identity attributes from
  `planned_values.root_module.resources[].values` (`project`, `region`/`location`, `name` for
  the GCP kinds). Demonstrated locally against a divergent state.
- The read path and the redaction discipline already exist: `Sol_cli_terraform_plan` parses plan
  JSON (`changes_of_plan_json`), and `show_and_record` / `Sol_cli_terraform.show_saved_plan`
  record only classified changes, never the plan document (SEC-008 — a plan carries sensitive
  values such as `TF_VAR_db_password`).
- The lookup machinery is *nearly* reusable but not yet: every GCP recipe begins
  `require_link identity` and derives name/location/project from a self-link
  (`sol_cli_destroy_verification.ml:227, :272…`), because the module deliberately never falls
  back to the target's configuration (`:249-256`). A declared identity has no self-link, so a
  second, declared-identity constructor is part of any ownership or coverage fix.
- Sol's own roots already carry the "declared ∩ state" idea for a narrower set:
  `gcp_guarded_resources` (`cmd_cloud_tf.ml:2213-2215`) with `preparations_eligible` /
  `preparations_unrepresented` (`sol_cli_cloud_lifecycle.ml:411-421`), currently reported only
  as a warning (`cmd_cloud_tf.ml:2242-2273`).
- A provider **cascade** (deleting a parent removes a child) can make a particular orphan
  disappear — but it is provider behaviour, Sol neither targets nor observes the orphan, and it
  is not a qualification of this contract. Whatever is decided, a cascade must not be recorded
  as recovery working.

## Options

### Recovery ownership

| | Mechanism | Cost / risk | Verdict |
|---|---|---|---|
| **A1** | **Adopt, then destroy**: `terraform import <address> <provider-id>` for each divergent address whose identity is authoritatively known, then the normal destroy. Needs a per-kind import-id recipe, and an assertion that the post-import plan for that address is delete-only. | One extra asserted Terraform operation per divergent address. `terraform import` is documented as not modifying infrastructure. Reuses the Step-3 plan-assertion machinery, so "no create/replace on the destroy path" is preserved. | **Recommended** |
| **A2** | Sol deletes the object through each provider's API, from the observed identity set. | Duplicates the resource DAG in OCaml (HARDEN-004 standing constraint 6) and *is* "provider-native deletion as the normal recovery mechanism" — the thing the property excludes. Per-kind delete recipes, per-kind ordering, no Terraform ownership. | Reject |
| **A3** | Reconstructive reconciliation: re-apply to re-adopt, or destroy-then-recreate. | Constructive by definition; it is exactly the Attempt-6 failure (`409 Already exists`). | Reject |
| **A4** | Restate the claim: converge everything state owns, keep the divergence as a *loud* failure and name it as residue requiring an operator decision. | Cheapest, honest, and no new mechanism — but the target does not reach `Absent`, so `INV-DESTROY-1` stays failed for divergence and the operator still has to act. | Interim behaviour until A1 lands; a legitimate permanent answer only if the profile accepts it |

### Verification coverage — what the postcondition is established against

| | Expected set | Why | Verdict |
|---|---|---|---|
| **B1** | The addresses Sol's own cloud root declares — today a constant in the code (`gcp_guarded_resources` plus the bootstrap mechanism), observed with the target-declared identity. | Smallest; no new Terraform read; covers the shape that made Attempt 6 unrecoverable (the guarded resources). Silent about every other kind — the artifact registry, address, service account, subnetwork. | Step 1 if only the guarded shape matters |
| **B2** | The addresses in a **read-only, non-destroy `plan -json`** of the disposable root, unioned with the state inventory. For each address state does not represent, query the provider from the planned identity: PRESENT ⇒ violation, ABSENT ⇒ fine, unqueryable ⇒ UNKNOWN ⇒ failure. | General: Terraform computes the declared set and the identity, so no naming convention is guessed (FND-0045's failure mode). One extra read-only plan on the destroy path. | **Recommended** |
| **B3** | Enumerate the provider's inventory for each target-owned class and match against the target. | Broadest, but the match is name-derived and listing is unbounded in cost; and the cloud roots carry no target-scoping label to filter on today, so "target-owned" would be inferred. | Reject for now |

## Recommendation

**B2 first, then A1, over the declared set B2 produces.** Sequenced, because the first step is
small, offline-testable, and turns a silent wrong answer into a correct failure:

1. **Declared-set observation + failing verdict (B2).** Compute the declared address set from a
   read-only plan of the disposable root; for every declared address state does not represent,
   obtain a provider observation from the planned identity; report it *before* destroy, and feed
   it into the postcondition so that a PRESENT divergence is a violation and an unqueryable one
   is UNKNOWN. No apply, no import, no state change on this path. This is the unit that makes
   Attempt 7 meaningful: it removes the fail-open, so a future attempt fails for the *real*
   reason and says which resource.
2. **Adoption (A1), gated on this decision.** For each divergent address, `terraform import`
   with an authoritatively derived id, then the ordinary destroy — behind the same saved-plan
   assertion the destroy path already uses, so an import can never smuggle a create.
3. **Attempt 7 (or its successor) re-run live** once 1 and 2 have landed, with the property
   restated to name the mechanism (adoption is part of the supported path) or with its
   "no import" clause removed. **That re-run needs its own explicit authorization** and a fresh
   Phase-0 baseline.

Until 1 and 2 land, the honest behaviour is **A4**: fail loudly, name the divergent addresses,
and do not claim the postcondition.

## The implementation this decision would authorize

A follow-up `INFRA-*` ticket is materialised once this decision lands (per this directory's
rule that a decided `DESIGN_GAP` becomes concrete work). Step 1 above is the recommended first
unit; its acceptance criteria:

- **Divergence fails closed.** With a state fixture in which a target-declared address is absent
  from state while the provider answers (stubbed) with the object, `sol cloud destroy` must
  **not** report the postcondition established: the verdict carries a violation naming the
  address and the exact query, and the command exits non-zero.
- **No false positives.** With the same fixture and a provider answer of not-found, the outcome
  is unchanged from today (clean / degraded exactly as before) — a behaviour-preserving
  regression over the existing `test_cloud_destroy.ml` composition cases.
- **UNKNOWN is not absence.** A query that cannot be made (tool absent, permission denied,
  transport failure, unreadable answer) is UNKNOWN, and UNKNOWN fails the command — the same
  three-valued rule Step 5 already applies to captured identities.
- **Read-only on the observation path.** No apply, no import, no `state rm`, no provider
  mutation; the only new Terraform call is a `plan`. Only classified changes (address + action)
  reach the run log — the plan document itself never does (SEC-008), because it carries
  `TF_VAR_db_password` and other sensitive values.
- **The existing assertion boundary is untouched.** Step 3's phase allowlists and the
  bootstrap-access exception are not widened; the negative property (zero target-owned
  creates/replaces executed on the destroy path) still holds and is still asserted.
- **Fixtures.** Pure classification cases in `cli/sol/test/` (declared set from a plan document;
  divergent / non-divergent / unqueryable), plus end-to-end scenarios in
  `internal/ci/test_cloud_lifecycle_offline.sh` (divergent address ⇒ non-zero exit naming it;
  non-divergent ⇒ unchanged exit).
- **Demo/example:** not applicable (cloud lifecycle internals) — stated in the completion notes.
  **No language-parity impact** (DEC-022): nothing application-facing changes.
- **Evidence class:** `STATIC`/`MECHANISM` and offline only. The behavioural claim stays open
  until a live attempt is separately authorized.
