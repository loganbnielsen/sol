`@sol-fab/obs`'s Loki push treats any non-network failure as success.

**Problem.** `makeLokiPusher`'s direct-push branch ends with:

```ts
fetch(`${lokiUrl}/loki/api/v1/push`, { method: "POST", ... })
  .catch((err) => { console.error(`[${service}] loki push failed: ${String(err)}`); });
```

`fetch` rejects only on **network-level** failure. An HTTP error status is a
*fulfilled* promise, so a `400`, `401`, `429` or `500` follows the success path
silently: nothing is logged, nothing is retried, and the log line is simply lost.
`response.ok` is never checked.

So this code does not mean "log failed Loki pushes" — it means "log network-level
rejections". A Loki rejecting every write with `429` or `400` would look identical
to a healthy pipeline from the application's perspective.

**How it surfaced.** While investigating absent TS logs (FEAT-082), the absence of
any "loki push failed" line was briefly taken as evidence the push was succeeding.
It was not evidence of anything, and the real cause turned out to be an unrelated
local environment issue — the push genuinely returned `204`. Worth fixing on its
own merits rather than because it caused that incident; it did not.

**Remediation.**

1. Check the response: log (and count) a non-2xx status, including the status code
   and a truncated body. Loki's push API returns `204` on success, so anything else
   is a failure.
2. Decide and document the delivery policy. Fire-and-forget is a defensible choice
   for logs — dropping a log line must never take down a service — but it should be
   a stated choice, not an accident of `fetch`'s semantics. If a bounded retry or a
   drop counter is wanted, make it explicit.
3. Consider bounding the promise so an unbounded backlog of in-flight pushes cannot
   accumulate if Loki is slow.

**Acceptance criteria:**

- A non-2xx push response is observably reported (log and/or metric), not silently
  ignored.
- A test covers the non-2xx case — the existing coverage exercises only the
  happy path and network rejection.
- The chosen delivery policy (drop on failure, retry, or buffer) is documented in
  the module.

**Not related to:** FEAT-036's lifecycle-ownership question, and not the cause of
the missing logs observed during FEAT-082. This is a correctness issue in the
logging client only.
