(These are the production-single-region profile, credential posture and rotation,

**Related:** `DEC-063` (Sol-to-Sol identity takes internal service keys out of this
ticket's scope), `DEC-051` (capability facts for each driver × runtime cell).

## Question

Today a production target's database master credential is supplied by the
operator: `sol cloud apply` requires and validates `TF_VAR_db_password`, refuses
one passed in the argument vector (the run log records the terraform command
line), and never writes the value to a plan, output, log, release record or
qualification evidence. That is a defensible maturity-A boundary — Sol declares
the capability and enforces the boundary; it does not own the secret.

What is deliberately *not* decided, and should be before the profile is used for
anything beyond a maturity-A pilot:

1. **Which system is authoritative** for production secret state. Kubernetes
   Secrets are a reasonable **runtime delivery mechanism** (`Secret` →
   Kubernetes Secret → pod env var), but they are cluster-local objects, not a
   credential-management system: their lifecycle is coupled to the cluster, and
   they lack IAM-scoped access, a central audit trail, independent versioning,
   rotation machinery and recovery if the cluster is lost.
2. **Whether Sol should own generation and storage at all**, or continue to
   require an out-of-band credential while Sol owns only the reference and the
   access policy.
3. **Whether the RDS master credential should be a Sol-visible value.** For the
   AWS-qualified profile there is a cleaner shape available: AWS manages the RDS
   master credential in Secrets Manager, so no plaintext passes through Sol.
4. **Whether the workload's database identity is the master credential.** The
   master credential is provisioning/administrative authority; an application
   should ordinarily use a narrower database identity, which is a separate
   credential with its own lifecycle.

## Constraints already established

- Maturity A is one team, one region, a fixed-capacity cluster and a real but
  non-critical customer-facing workload.
- DEC-026 §7 already fixes: no ambient Kubernetes token by default, rotation
  completing through the DEC-027 reconciliation authority without hand-edited
  manifests, and no secret value in a plan, release record, log or conformance
  bundle.
- Sol manages desired state and capabilities; provider/Kubernetes mechanisms stay
  below the Sol semantic boundary.
- HARDEN-002 must not be blocked on this: the maturity-A mechanism
  (`TF_VAR_db_password`, operator-supplied, leak-checked) stays as implemented,
  and this decision must not be pre-empted by adding a Secrets Manager
  integration or by making the Kubernetes runtime Secret authoritative.

## Acceptance criteria

- States the required properties of a secret authority, and for each driver × runtime
  cell names the mechanism that satisfies them, the properties it does not meet, or its
  `Not_implemented` / `Not_applicable` status. Kubernetes Secrets are assessed against
  those properties, not rejected or accepted by category.
- States the identity-first rule: what counts as a secret, and which access goes to
  `DEC-062` (cloud authorization) and `DEC-063` (Sol-to-Sol identity) instead.
- States that Sol never persists or logs plaintext, and the exact scope of the one
  write-path exception, if there is one.
- Defines admin, runtime and migration database identities, with IAM database auth
  preferred where supported.
- Defines `Secret.get`'s staleness and change-notification contract for each runtime, and
  the failure semantics for a new unit versus a running unit during an authority outage.
- States the migration path from the maturity-A `TF_VAR_db_password` mechanism, and the
  evidence needed before the profile claims the stronger posture.
- Records the comparison above, including the alternatives considered (Vault as a
  universal backend; the Lambda extension) and why each was chosen or rejected.

## Direction (2026-10-01, operator; revised the same day)

The security goals stand. The AWS-specific architecture the placeholder sketched is
**not accepted as written**. Sol supports `aws`, `gcp` and `byo` (`DEC-051`), and its
units run on more than one runtime kind, so "AWS Secrets Manager is authoritative" is
the wrong level of abstraction. Requiring Vault to get a uniform backend is also
rejected unless a capability only Vault provides turns out to be needed.

### What a secret is

> **A secret is credential material that cannot be replaced by an appropriate identity
> mechanism.**

Prefer identity wherever the other end can verify it, and use secret material only where
it cannot:

| Access | Mechanism | Owner |
|---|---|---|
| Cloud resources (Secret Manager itself, object storage, MSK, queues) | workload identity + cloud IAM | `DEC-062` |
| Databases that support it (RDS / Cloud SQL IAM auth) | workload identity → short-lived DB auth token | this ticket names it; `pg-eio` + framework DB layer implement it |
| Kafka where the broker supports it (MSK IAM auth) | workload identity | `kafka-eio` + framework |
| Sol unit → Sol unit | workload identity token + the declared `calls` graph | `DEC-063` |
| External services (Stripe, vendors), legacy password-only systems, external callers that cannot use an identity mechanism | **secret material** | **this ticket** |

External callers *into* Sol should prefer an identity or authentication mechanism without
a shared static secret where practical (OAuth client credentials, signed JWTs, mTLS).
A shared key is a supported fallback, not the designated external-caller model.

### Four layers

```text
1. DECLARATION      unit declares: secret "stripe"                        portable Sol contract
2. AUTHORITY +      driver: where the secret lives, how this unit's       driver-specific
   AUTHORIZATION    identity is allowed to read exactly that secret
3. PROJECTION       runtime kind: how an authorized unit obtains the      runtime-specific
                    value (Kubernetes → mounted file, ...)
4. CONSUMPTION      framework: Secret.get "stripe" (OCaml and TS)         portable Sol contract
```

- **The application contract is `Secret.get name`**, provided by the Sol framework in
  both languages (`DEC-022` parity). Applications never call a provider secret API and
  never depend on a projection mechanism.
- **Projection belongs to the runtime kind, not the driver.** On Kubernetes it is
  always a file mounted at `/run/secrets/<name>`, whether the driver is `aws`, `gcp` or
  `byo`. That path is documented as stable for consumers that do not use the framework
  (a sidecar, a non-Sol container), but it is the Kubernetes projection, not the
  universal contract.
- **The runtime kind comes from each unit, not the target address.**
  `sol-svc`/`sol-worker` run on Kubernetes, and `sol-fn` runs on its function runtime.
  The address stays `<env>/<driver>/<region>` (`DEC-031`/`DEC-051`).
- **Secrets are named independently of any workload** (for example `sol/<env>/<secret>`).
  A grant is an edge from a unit to a secret, so one secret can be shared, such as a key
  that two units use, without duplicating it.
- **`Secret.get` has explicit staleness.** It returns a value no older than a bound
  stated for each runtime, and it offers a way to notice a change, such as a rebuild hook
  for resources built from the secret. A once-read string would give env-var semantics.
  The framework owns any caching, so Sol owns the staleness contract instead of
  inheriting a component's default.
- **Undeclared names fail clearly.** `Secret.get` of a name the unit did not declare is
  a typed error naming the missing declaration. Catching it at build or plan time is
  preferred.

### Driver × runtime: current reality

Each cell is a `DEC-051` capability fact. A deploy refuses a cell that is not `Present`
while building the plan, not halfway through.

| Driver | Unit → runtime | Authority / authorization | Projection | Status |
|---|---|---|---|---|
| `aws` | svc, worker → Kubernetes (EKS) | Secrets Manager + IAM via the unit's pod identity (IRSA / EKS Pod Identity) | Secrets Store CSI + AWS provider → file | candidate, to qualify |
| `gcp` | svc, worker → Kubernetes (GKE) | Secret Manager + IAM via Workload Identity Federation (granted to the Kubernetes ServiceAccount directly) | GKE Secret Manager add-on (CSI-based) → file | candidate, to qualify |
| `byo` | svc, worker → Kubernetes | Kubernetes Secrets, or an operator-supplied CSI-compatible store (e.g. Vault) | mounted file | to assess against the properties |
| `aws` | fn → Lambda | Secrets Manager + execution role | framework calls `GetSecretValue` directly via `aws-eio` (AWS SDK in TS) and caches it; **not** the Parameters and Secrets Lambda Extension (container-image Lambdas cannot take layers, and the framework should own the cache) | `Not_implemented`: `sol-fn` speaks the Lambda protocol, but `sol deploy` has no Lambda path |
| `gcp` | fn → Cloud Run (containers; Cloud Run functions have no OCaml buildpack) | Secret Manager + service identity | native Cloud Run secret volume → file | `Not_implemented`, and it needs a Cloud Run trigger adapter in `sol-fn` |
| `byo` | fn | — | — | `Not_applicable` |
| local | units under `sol local up` | dev-only source (local Kubernetes Secrets or a gitignored file) | mounted file | needed, so `Secret.get` works in dev; reports the weakest posture |

### The calls

1. **No universal authority.** Sol defines the properties a secret authority must
   provide (below). Each driver satisfies them in its own way and reports which ones it
   meets.
2. **Plaintext never enters Sol's state.** No secret value appears in Sol's state,
   plans, logs, release records or control plane. Sol deals in references, identities,
   grants and projection configuration. For provider-managed resources such as RDS,
   prefer provider-managed credentials, so admin passwords never pass through Sol,
   Terraform or operator environment variables. Putting a value *in* is the one
   exception: a `sol secret set`-style command may pass operator-supplied plaintext from
   the CLI process straight to the provider API, never persisting or logging it.
   Whether that command exists is an open question.
3. **Workloads never receive database master/admin credentials.** Runtime and migration
   (`sol migrate`, which needs DDL rights) are separate identities, and the platform owns
   their lifecycle. IAM database auth is preferred over rotated passwords where the
   database supports it. Before implementing any rotated-password path, propose its
   lifecycle: who creates the principal, grants and revokes, owns and rotates the
   credential, how active connections behave during rotation, and how the principal is
   deleted with the workload.
4. **Granting a unit access to a secret may require cloud IAM changes.** Ordinary
   `sol deploy` must not gain authority to grant cloud permissions in order to realise
   those grants. Who owns and reconciles per-workload cloud authorization is `DEC-062`.
   This ticket consumes its answer.
5. **Secrets Store CSI is the intended Kubernetes projection on managed AWS and GCP,
   subject to qualification.** The question is not "should we use CSI" but "does CSI
   satisfy P1–P8 well enough to join the platform profile". Fixed invariants if it does:
   - **Syncing to a Kubernetes Secret stays off.** `secretObjects` must not be used,
     because it would quietly reintroduce Kubernetes Secret copies.
   - **The provider authenticates as the pod's own identity, never the node's.**
   - **Rotation is explicitly enabled and qualified** (`enableSecretRotation`, with a
     poll interval Sol chooses).

   Joining the profile updates `FEAT-088` and re-runs the `DEC-026`/`HARDEN-002`
   evidence.
6. **Kubernetes Secrets are not rejected by default.** They are judged against the
   properties. Note that on `byo` their isolation is per *namespace*, not per workload:
   anyone who can create a pod in the namespace can mount any Secret in it. The driver
   reports that against P2 rather than implying parity.
7. **Disagreement and failure semantics are explicit,** and two cases are kept apart:
   - **A new pod while the authority is unavailable** fails closed: the mount fails and
     the pod never starts. That is acceptable and stated.
   - **A running workload while the authority is unavailable** keeps its last-known
     value for a bound that is stated for each runtime.

   Sol never reports successful delivery while a workload consumes stale material
   beyond the staleness bound.
8. **Migration and evidence.** `TF_VAR_db_password` is removed from the production path.
   The profile does not claim the stronger posture until the replacement is
   live-qualified and `HARDEN-002` F1–F4 are re-run against it.
9. **Shared static secrets support overlap.** Wherever a static secret has more than one
   holder (a fallback shared key, an external API key held by several units), rotation
   accepts two valid versions during a defined window, otherwise rotation is an outage.

**Demo/example coverage:** applies when implemented. `Secret.get` and the `secrets`
declaration are app-author-visible, so the implementing unit updates an example that
declares a secret and reads it through the framework, in OCaml and TS.

## Runtime delivery direction: files, not environment variables

*(Earlier note, kept for its reasoning. Since the revised direction above, "mounted
files" is the **Kubernetes projection**, not the universal contract. `Secret.get` is
the application contract.)*

Raised while implementing the maturity-A credential boundary, and recorded here
because it changes the shape of the answer above.

**Preferred production interface: secrets are delivered as mounted files.** The
current contract injects secrets as process environment variables
(`envFrom`/`secretKeyRef`), which works but has a lifecycle limitation:
environment variables are immutable for the life of the process. That is exactly
why SEC-004's rotation is "update Secret -> verified rollout -> confirm healthy":
for an env-var contract that is the honest behaviour, not a shortcoming.

A file-mounted contract (a projected volume, or a Secrets Store CSI driver sourcing
the driver's authority, which is one candidate among several; see *Open Questions*)
keeps the same division of authority while allowing a stronger lifecycle:

    driver's secret authority  (authoritative value and lifecycle)
        -> driver's delivery mechanism (e.g. Secrets Store CSI)
        -> pod-mounted volume         (runtime representation)
        -> application reads a file

Sol declares the reference and the access policy; the authority's access control
(IAM on the managed clouds) decides who may retrieve it; Kubernetes/CSI delivers it; the framework gives the application a sane way to
consume it; **Sol never handles the plaintext value.**

### The lifecycle must be split honestly

A file changing does not mean a consumer of that credential has started using the
new value -- a connection pool that already established connections with the old
credential will keep using them regardless. So the contract separates three
things, and must not conflate them:

| Layer | Responsibility |
|---|---|
| Sol guarantee | the secret is delivered as a mounted file at a declared path |
| Optional framework capability | observe the change and reload *dependent resources* where the framework knows how |
| Application responsibility | define what credential rotation means for that resource (rebuild the pool, reconnect, drain) |

Without that split, "mounted file" would be used to imply hot rotation that no
component actually performs.

### Concrete consequences to resolve here

1. **Delivery is not the same as admission.** A mounted secret volume must stay
   distinguishable from an admitted workload volume: DEC-026 §3 caps a workload
   declaring a persistent workload volume at the `single` availability tier
   (`Sol_cli_deployment_plan.validate_availability` inspects
   `service_spec.volumes`). Secret volumes must not be mistaken for that, in
   either direction -- a file-mounted secret must neither forbid
   `node-failure-tolerant` nor be admitted as a persistence claim.
2. **CSI on AWS adds a component.** The Secrets Store CSI driver and its AWS
   provider are not in the currently qualified component set, so adding them is a
   compatibility-matrix change (FEAT-088) and a re-qualification event
   (DEC-026 §9), not an implementation detail.
3. **Changing delivery re-qualifies the credentials row.** HARDEN-002's live
   evidence (F1-F4: no ambient token, rotation with verified restart, old
   credential rejected, no secret value in any artifact) is evidence for the
   env-var contract. Moving to file delivery requires that row to be re-run
   against the new mechanism; it does not invalidate it as evidence of what was
   tested.
4. **Migration path.** The profile should not carry two secret interfaces
   indefinitely: pick the file-mounted delivery, keep env-var injection for
   non-credential configuration only, and state which workloads must migrate.
