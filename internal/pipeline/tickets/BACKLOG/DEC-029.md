**Depends on:** DEC-026 (production-single-region profile), SEC-004 (credential
posture and rotation), DEC-027 (reconciliation ownership).

## Question

Today a production target's database master credential is supplied by the
operator: `sol cloud apply` requires and validates `TF_VAR_db_password`, refuses
one passed in the argument vector (the run log records the terraform command
line), and never writes the value to a plan, output, log, release record or
qualification evidence. That is a defensible maturity-A boundary — Sol declares
the capability and enforces the boundary; it does not own the secret.

What is deliberately *not* decided, and should be before the profile is used for
anything beyond a maturity-A pilot:

1. **Which system is authoritative** for production secret state. Kubernetes
   Secrets are a reasonable **runtime delivery mechanism** (`Secret` →
   Kubernetes Secret → pod env var), but they are cluster-local objects, not a
   credential-management system: their lifecycle is coupled to the cluster, and
   they lack IAM-scoped access, a central audit trail, independent versioning,
   rotation machinery and recovery if the cluster is lost.
2. **Whether Sol should own generation and storage at all**, or continue to
   require an out-of-band credential while Sol owns only the reference and the
   access policy.
3. **Whether the RDS master credential should be a Sol-visible value.** For the
   AWS-qualified profile there is a cleaner shape available: AWS manages the RDS
   master credential in Secrets Manager, so no plaintext passes through Sol.
4. **Whether the workload's database identity is the master credential.** The
   master credential is provisioning/administrative authority; an application
   should ordinarily use a narrower database identity, which is a separate
   credential with its own lifecycle.

## Constraints already established

- Maturity A is one team, one region, a fixed-capacity cluster and a real but
  non-critical customer-facing workload.
- DEC-026 §7 already fixes: no ambient Kubernetes token by default, rotation
  completing through the DEC-027 reconciliation authority without hand-edited
  manifests, and no secret value in a plan, release record, log or conformance
  bundle.
- Sol manages desired state and capabilities; provider/Kubernetes mechanisms stay
  below the Sol semantic boundary.
- HARDEN-002 must not be blocked on this: the maturity-A mechanism
  (`TF_VAR_db_password`, operator-supplied, leak-checked) stays as implemented,
  and this decision must not be pre-empted by adding a Secrets Manager
  integration or by making the Kubernetes runtime Secret authoritative.

## Acceptance criteria

- States the required properties of a secret authority, and for each driver
  (`aws`, `gcp`, `byo`) names the authority that satisfies them or the properties it
  does not meet. Kubernetes Secrets are assessed against those properties, not
  rejected or accepted by category.
- States whether Sol generates and stores secrets, or only declares references
  and access policy, and what Sol therefore must never see.
- Defines how an infrastructure/admin credential (e.g. the RDS master) differs
  from an application database identity, and the intended mechanism for each.
- Defines generation, storage, rotation and recovery semantics, including what
  happens when the authoritative store and the cluster disagree.
- States the migration path from the maturity-A `TF_VAR_db_password` mechanism,
  and what evidence is needed before the profile claims the stronger posture.
- Records the per-driver comparison above, including the alternatives considered
  (Vault as a universal backend among them) and why each was chosen or rejected.

## Direction (2026-10-01, operator)

The security goals stand. The AWS-specific architecture the placeholder sketched is
**not accepted as written**: Sol supports `aws`, `gcp` and `byo` (`DEC-051`), so "AWS
Secrets Manager is authoritative" is the wrong level of abstraction. Requiring Vault to get
a uniform backend is also rejected unless a capability only Vault provides turns out to
be needed. Doing so would add a distributed system on top of the managed stores AWS and
GCP already have.

> **Sol standardizes how workloads consume secrets; the secret authority is
> driver-specific.**

```text
secret authority (per driver) → driver projection/delivery → stable mounted-file workload contract
```

The calls:

1. **No universal authority.** Sol does not standardize on AWS Secrets Manager, Vault or
   any single vendor. It defines the **properties a supported secret authority must
   provide** (below). Each driver satisfies them in its own way and reports which ones it
   meets.
2. **Sol avoids handling plaintext during normal operation.** It deals in references,
   identities, access policy and projection/delivery configuration. For provider-managed
   resources such as RDS, prefer provider-managed credentials where they exist, so
   administrative passwords never pass through Sol, Terraform or operator environment
   variables.
3. **Workloads never receive database master/admin credentials.** They get narrower
   database identities. **Before implementing this part, propose the lifecycle design.**
   It must say who creates the principal, who grants and revokes permissions, who owns and
   rotates the credential, how active connections behave during rotation, and how the
   principal is deleted with the workload. The preference is a **platform-owned**
   lifecycle, not an application-owned one.
4. **The workload contract is mounted files**, conceptually `/run/secrets/<name>`. The
   application cannot tell whether a file came from AWS Secrets Manager, Google Secret
   Manager, Vault or an acceptable `byo` mechanism. The Sol-guarantee / framework /
   application responsibility split in *Runtime delivery direction* below still applies
   unchanged.
5. **Secrets Store CSI is a candidate for the managed-cloud implementation, not yet a
   commitment.** Before committing, confirm the AWS and GCP providers, rotation
   behaviour, operational dependencies, failure semantics and qualification impact. If
   CSI joins the platform profile, update `FEAT-088` and re-run the required
   `DEC-026`/`HARDEN-002` qualification evidence.
6. **Kubernetes Secrets are not rejected by default.** Judge them against the required
   properties. The strong arguments for an external authority are concrete Sol-supported
   scenarios in which a credential must survive cluster replacement, be consumed outside
   the cluster, or have a lifecycle independent of Kubernetes. "Kubernetes Secrets are
   insecure" is not one of them.
7. **Disagreement and failure semantics are explicit.** If the authority holds one
   version and a workload is consuming another, the platform has a defined convergence
   and failure model. Sol does not keep reporting successful delivery while a workload
   runs on stale material.
8. **Migration and evidence.** `TF_VAR_db_password` is ultimately removed from the
   production path. The profile does not claim the stronger posture until the
   replacement has been live-qualified and the relevant `HARDEN-002` evidence (F1–F4)
   has been re-run against it.

**Demo/example coverage:** applies once decided, because the mounted-file contract is
app-author-visible. The implementing unit updates an example that reads a secret from
`/run/secrets/<name>`.

## Open Questions

The next pass turns the authority question into **required properties** and compares
candidate implementations against them *before* CSI or any other mechanism is locked in.

### Required properties (strawman, to be confirmed)

| # | Property | Why Sol needs it |
|---|---|---|
| P1 | Sol never needs the plaintext value to declare, grant or deliver a secret | call 2 |
| P2 | Access is granted to a workload *identity*, scoped per secret, and is auditable | `DEC-016` access separation |
| P3 | Versioned values; a workload can be told which version it holds | call 7 needs a version to compare |
| P4 | Rotation without a hand-edited manifest, completing through the `DEC-027` authority | `DEC-026` §7 |
| P5 | Recovery: the value survives loss or replacement of the cluster, *where a Sol scenario needs that* | call 6: needed only if a scenario requires it |
| P6 | Observable delivery state: the platform can tell "delivered vN" from "stale" or "failed" | call 7 |
| P7 | No new always-on component outside the qualified set unless re-qualified | `FEAT-088`, `DEC-026` §9 |

### Questions the comparison must also answer

1. **Which Sol scenarios need P5?** Cluster replacement, consumers outside the cluster,
   multi-cluster. If none exists at maturity A, Kubernetes Secrets may satisfy `byo`
   outright.
2. **How a driver reports what it meets.** Use `DEC-051`'s three-way capability fact
   (`Present` / `Not_applicable` / `Not_implemented`), so a `byo` target on Kubernetes
   Secrets reports the posture it actually has instead of inheriting the cloud drivers'
   claim.
3. **The migration identity.** Call 3 separates admin credentials from workload ones.
   Schema migrations (`sol migrate`) need DDL rights that the runtime identity should
   not have. Is that a third, platform-owned identity (schema owner), and does it share
   the call-3 lifecycle?
4. **CSI failure semantics.** What a pod does when the provider is unavailable at mount
   time, versus at rotation time, and how that maps onto P6 and readiness.

## Runtime delivery direction: files, not environment variables

Raised while implementing the maturity-A credential boundary, and recorded here
because it changes the shape of the answer above.

**Preferred production interface: secrets are delivered as mounted files.** The
current contract injects secrets as process environment variables
(`envFrom`/`secretKeyRef`), which works but has a lifecycle limitation:
environment variables are immutable for the life of the process. That is exactly
why SEC-004's rotation is "update Secret -> verified rollout -> confirm healthy":
for an env-var contract that is the honest behaviour, not a shortcoming.

A file-mounted contract (a projected volume, or a Secrets Store CSI driver sourcing
the driver's authority, which is one candidate among several; see *Open Questions*)
keeps the same division of authority while allowing a stronger lifecycle:

    driver's secret authority  (authoritative value and lifecycle)
        -> driver's delivery mechanism (e.g. Secrets Store CSI)
        -> pod-mounted volume         (runtime representation)
        -> application reads a file

Sol declares the reference and the access policy; the authority's access control
(IAM on the managed clouds) decides who may retrieve it; Kubernetes/CSI delivers it; the framework gives the application a sane way to
consume it; **Sol never handles the plaintext value.**

### The lifecycle must be split honestly

A file changing does not mean a consumer of that credential has started using the
new value -- a connection pool that already established connections with the old
credential will keep using them regardless. So the contract separates three
things, and must not conflate them:

| Layer | Responsibility |
|---|---|
| Sol guarantee | the secret is delivered as a mounted file at a declared path |
| Optional framework capability | observe the change and reload *dependent resources* where the framework knows how |
| Application responsibility | define what credential rotation means for that resource (rebuild the pool, reconnect, drain) |

Without that split, "mounted file" would be used to imply hot rotation that no
component actually performs.

### Concrete consequences to resolve here

1. **Delivery is not the same as admission.** A mounted secret volume must stay
   distinguishable from an admitted workload volume: DEC-026 §3 caps a workload
   declaring a persistent workload volume at the `single` availability tier
   (`Sol_cli_deployment_plan.validate_availability` inspects
   `service_spec.volumes`). Secret volumes must not be mistaken for that, in
   either direction -- a file-mounted secret must neither forbid
   `node-failure-tolerant` nor be admitted as a persistence claim.
2. **CSI on AWS adds a component.** The Secrets Store CSI driver and its AWS
   provider are not in the currently qualified component set, so adding them is a
   compatibility-matrix change (FEAT-088) and a re-qualification event
   (DEC-026 §9), not an implementation detail.
3. **Changing delivery re-qualifies the credentials row.** HARDEN-002's live
   evidence (F1-F4: no ambient token, rotation with verified restart, old
   credential rejected, no secret value in any artifact) is evidence for the
   env-var contract. Moving to file delivery requires that row to be re-run
   against the new mechanism; it does not invalidate it as evidence of what was
   tested.
4. **Migration path.** The profile should not carry two secret interfaces
   indefinitely: pick the file-mounted delivery, keep env-var injection for
   non-credential configuration only, and state which workloads must migrate.
