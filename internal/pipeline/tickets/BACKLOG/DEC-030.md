## Open Questions

What Kubernetes identity does `sol deploy`/`sol migrate`/`sol status` etc. (the
**deployer**) authenticate as against a Sol-provisioned AWS cluster, and how
does Sol establish and hand back that identity's `kube_context`/`kubeconfig`?
No answer to this exists in any accepted decision or the current
implementation — this ticket exists to get one before INFRA-023 (the
mechanical follow-up) can be written.

## What triggered this

Investigating the `sol cloud init` inconsistency named in the Maturity-A pass:
tutorial (`docs/guides/TUTORIAL.md:629`) and two runtime error messages
(`cli/sol/lib/sol_cli_kube_destination.ml:23`,
`cli/sol/lib/sol_cli_target_report.ml:53`) tell the user "let `sol cloud
init` record it when it provisions the cluster" — but `sol cloud` only
exposes `plan` / `apply` / `destroy` (`cli/sol/bin/cmd_cloud.ml`); there is no
`init`.

This is not a rename that text missed. `git log -S"record_target_destination"`
shows FEAT-068 (`sol cloud init produces target-scoped destinations`, PR #250)
built exactly this: on provisioning success, `configure_kubectl` wrote a
persistent scoped kubeconfig to `.sol/kubeconfigs/<target>.kubeconfig`
(mode 0700) and `record_target_destination` inserted `kube_context:` /
`kubeconfig:` into the target file, so a provisioned target came out with its
destination already set — "zero user input, explicit by construction" per
FEAT-059.

INFRA-022 (`bbc6ac6c`, PR #310, merged 2026-09-17 — the commit immediately
before #311) rewrote the AWS lifecycle per ADR 0002 and deleted
`record_target_destination`, `configure_kubectl`, and
`print_target_destination_lines` outright, replacing them with
`with_provisioner_kubeconfig`: an **ephemeral, temp-file** kubeconfig that
exists only for the duration of one `sol cloud apply`/`plan`/`destroy`
invocation, scoped to the **provisioner** identity, and is always cleaned up.
Nothing replaced the persistent, deployer-facing write. ADR 0002 doesn't
discuss this — it's scoped to "cloud-target lifecycle" (getting the cluster
itself to Ready), not to how an ordinary `sol deploy` afterwards authenticates.

Consequence, verified by reading the actual code path
(`cli/sol/lib/sol_cli_destination.ml:resolve`): `sol deploy`/`migrate`/`status`/etc.
require a **static** `kube_context` (+ optional `kubeconfig`) already present
in the target file — there is no ambient-kubectl fallback (DEC-020) and no
per-invocation dynamic AWS auth path. So today, a target that has been through
`sol cloud apply` to verified Ready still cannot be deployed to: the exact
error a user hits is the one whose own remediation text points at a command
that doesn't exist.

## The invariant at stake

DEC-016: *"safety comes from access separation (a dev deployer holds no prod
credentials)"* and ADR 0002's identity table: provisioner may reconcile
substrate but **must not** directly mutate ordinary application resources
outside platform namespaces — which is enforced by the provisioner's EKS
access entry's RBAC actually excluding those resources. Whatever identity
`sol deploy` runs as must therefore be a *different* principal from the
provisioner, scoped to ordinary application namespaces only, or the two halves
of that boundary contradict each other (either deploys silently fail RBAC, or
the "provisioner can't touch app resources" boundary is meaningless because
deploy actually runs as the provisioner).

## What exists today

- An AWS EKS access entry + group binding for the **provisioner** only
  (`cli/platform/infra/aws/main.tf` — no `access_entry`/`deployer`/`publisher`
  resource of any kind exists in the AWS root; confirmed by grep).
- No terraform, no ticket, no ADR defines a deployer-scoped EKS access entry,
  IAM role, or how a human/CI identity maps to one.
- Publisher identity (image push, `sol up`) is comparatively fine: it shells
  out to whatever `docker` is already authenticated as
  (`cli/sol/lib/sol_cli_docker.ml`) rather than Sol provisioning a principal,
  so it doesn't share this gap — worth confirming with an offline
  effective-permission test (separate, unblocked work), but no open decision
  there.

## Concrete conflict

Restoring FEAT-068's write-back mechanically (call the provider's
`kubeconfig_command`, e.g. `aws eks update-kubeconfig --alias <name>`, write
the resulting kubeconfig + context into the target) is a five-minute change.
But *whose* kubeconfig gets written is the unresolved part:

1. **Write back a kubeconfig authenticated as the provisioner.** Mechanically
   trivial (the machinery already exists in `with_provisioner_kubeconfig`,
   just stop deleting it). But every `sol deploy` would then run with
   provisioner-level Kubernetes RBAC, which ADR 0002 defines as *excluding*
   ordinary application Deployments/Services/Jobs/Secrets outside platform
   namespaces — so deploys would either fail closed against their own
   provisioner's RBAC, or (worse) someone widens the provisioner's RBAC to make
   deploys work, quietly erasing the provisioner/deployer boundary ADR 0002 and
   INFRA-022 just spent an entire ticket establishing.
2. **Establish a real deployer EKS access entry**, mirroring what INFRA-022
   built for the provisioner: the AWS root creates an access entry + policy
   association scoped to application namespaces, bound to a configurable IAM
   principal (the operator's own role, a CI OIDC role, or a Sol-created IAM
   user/role — itself a sub-choice). `sol cloud apply` writes back a kubeconfig
   using AWS's exec-credential plugin (`aws eks get-token`), so the credential
   is never a static embedded secret — it authenticates as whoever's AWS
   identity runs `sol deploy`, mapped through the access entry to namespace-scoped
   RBAC. This matches DEC-016's "access separation" principle exactly, but
   requires deciding: which IAM principal(s) get bound to the deployer group,
   and whether that's operator-configured (a new target field) or
   Sol-provisioned (a new IAM role Sol creates and owns).
3. **Defer the mechanism, fix the text only.** Change the tutorial/error
   strings to describe the actual current gap ("no destination is recorded;
   hand-write `kube_context`/`kubeconfig` after `sol cloud apply`, e.g. via
   `aws eks update-kubeconfig`") instead of pointing at a command that doesn't
   exist. Honest and minimal, but it means Maturity-A ships with the operator
   doing exactly the manual kubectl-plumbing FEAT-059/063/068 were written to
   eliminate — a real regression in the product experience, not just wording.

## Recommendation

Option 2, scoped down: reuse the **operator's own already-authenticated AWS
identity** rather than having Sol provision a brand-new deployer IAM
principal in this pass. Concretely: the AWS root gains a second EKS access
entry bound to a target-declared `deployer_principal_arn` (or, if unset,
whatever ambient AWS identity ran `sol cloud apply`, captured once via STS
`get-caller-identity` at apply time — still explicit-by-construction, no
ambient *Kubernetes* fallback, only an ambient *AWS* identity which the
operator already had to have to run `apply` at all), scoped to RBAC over
application namespaces only. `sol cloud apply` writes the resulting
`kube_context`/`kubeconfig` into the target using the AWS exec-credential
kubeconfig (no embedded secret), restoring FEAT-068's target-file behavior.
This keeps Sol out of the business of minting/rotating IAM principals (a
much bigger commitment deferred for later) while still giving deploy a
distinct, namespace-scoped identity instead of overloading the provisioner's.

This is a recommendation, not a decision — option 1 is a real security
regression if chosen, and option 2's sub-choice (Sol-provisioned principal vs.
operator-supplied one) has its own tradeoffs (Sol-provisioned is more
"batteries included" but adds IAM lifecycle Sol now owns; operator-supplied
keeps Sol's footprint smaller but pushes IAM setup back onto the user, which
cuts against Maturity-A's "no DevOps knowledge required" thesis).

## What's blocked on this

- The `sol cloud init` text fix (can't be "make it true" until something is
  true to describe — a pure text fix is option 3, which is itself a decision
  to make, not a no-op).
- Any HARDEN run 3 evidence involving `sol deploy` against a freshly
  `sol cloud apply`'d target (there is currently no destination to deploy
  to).
- Does **not** block: RDS destroy-prep (finding 9b), publisher identity
  effective-permission tests, or secrets — independent work, proceeding
  separately.
