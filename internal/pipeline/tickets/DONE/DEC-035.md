## The question

Sol destroys a GCP target including the VPC peering created by the Cloud SQL
private-service connection. Deleting the connection is refused while the service
producer still tracks the instance's resources:

```text
Failed to delete connection; Producer services (e.g. CloudSQL, Cloud Memstore, etc.)
are still using this connection.
```

Sol sets `deletion_policy = "ABANDON"` on
`google_service_networking_connection.sql`, which removes the connection from
Terraform management without deleting it in the API. The provider documents that
`ABANDON` "leaves [the peering] in place, which will block deletion of the
network", while Attempts 3 and 4 both reached network-absent and peering-absent,
verified through the provider API rather than through Terraform's exit status.
Which policy should the destroy use?

## Options

1. **`DELETE` (the provider default).** Rejected: the delete is refused while the
   producer holds the instance's resources, so the destroy fails and the network —
   and with it the whole target — cannot be removed by Terraform.
2. **`REMOVE_PEERING`.** The connection is deleted and, when the API refuses, the
   peering is removed so the network can be deleted. Rejected *for now*: it was
   added in `terraform-provider-google` **8.1.0 (2026-09-01)** and Sol pins
   `google = { version = "~> 5.25" }` (`cli/platform/infra/gcp/main.tf:20-24`).
   Adopting it means a 5.x → 8.x major provider upgrade, which re-opens every
   other GCP resource in the root to qualification — a separate change, not a
   consequence of this decision.
3. **`ABANDON` with compensating verification (chosen).** The connection is
   abandoned, the network is deleted in the same destroy, and the destroy then
   asks the provider for the network *and* the peering instead of trusting
   Terraform's exit status.

## Decision (2026-09-20) — Option 3, keep `ABANDON`

`ABANDON` is acceptable **because network deletion plus the post-destroy provider
query is the compensating mechanism**, not because the documented risk is
considered absent. The documented failure mode — a peering left in place that
blocks deletion of the network — is covered by a check that can see the abandoned
object and fails closed, rather than by Terraform's lifecycle tracking, which
`ABANDON` gives up.

## Constraints (all four are part of the decision)

- **The post-destroy network/peering verification must remain** while `ABANDON` is
  used. It *is* the compensating mechanism; without it the choice is bare
  abandonment and the decision does not hold.
- **Fail-closed absence recognition must remain part of that verification.** An
  unrecognised response is a verification failure, never absence. (#363's
  `gcp_absence_message` matches the provider's own 404 wording case-insensitively;
  anything else stays a failure.) A verification that cannot fail would make the
  compensation blind.
- **Revisit when `google >= 8.1` is itself qualified.** At that point
  `REMOVE_PEERING` is available and is the more complete mechanism: it attempts
  the real connection deletion first and keeps the resource in Terraform's graph.
- **Revisit immediately if a live run observes the documented failure mode** — the
  network still present, or the peering still listed, after the connection was
  abandoned. That is the evidence that would show the compensation is insufficient.

## Consequences

- FND-0005 moves from an open qualification row to `ACCEPTED`: a deliberate,
  recorded residual with a named trigger, rather than a contradiction left
  unresolved.
- For this one object, the destroy's correctness rests on the verifier instead of
  on Terraform's dependency graph. That is a real weakening of `INV-DESTROY-3`'s
  mechanism, which is why the verification constraints above are not optional and
  why they are stated here rather than left to the code comment.
- No code changes now. When the provider is upgraded, this decision carries a
  follow-up: switch to `REMOVE_PEERING` and re-qualify the destroy path.
