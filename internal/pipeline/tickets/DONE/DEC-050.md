**Depends on:** None.

## Context

DEC-049 ships the Terraform roots inside the release bundle (`share/sol/<version>/platform/cloud/<provider>/{cluster,platform}`), and FEAT-101 does that. But a Terraform root is a *working directory*, not a read-only asset. Sol runs every command as `terraform -chdir=<root> …` (`cli/lib/cloud/sol_cli_terraform.ml`), so Terraform writes into the root:

- `init -reconfigure` writes `.terraform/` (providers, modules, backend config) there;
- a failed state push writes **`errored.tfstate`** there. `Sol_cli_terraform.supervised` then points the operator at it as "the only record of what this run changed".

`git ls-tree -r origin/main platform/cloud | grep lock` shows the provider lock files are committed; `.gitignore` excludes `.terraform/` and state. So a checkout works because it is writable. An installed release works the same way *if its prefix is writable by the user*, and FEAT-101 documents that requirement. A system-wide, read-only install (for example under `/usr/local` via `sudo`) would break `sol cloud`, and on the failure path the state file could not be written at all.

A related issue, independent of releases: every target of a provider shares one `.terraform/` inside the root, switched by `-reconfigure` on each run. Two concurrent `sol cloud` runs for different targets from one checkout would contend for it.

## Decision (operator, 2026-09-26): option 3

The packaged `platform/cloud/...` Terraform roots are immutable Sol-owned program assets. Before Terraform runs, Sol materializes the selected root into a target-specific mutable working directory and runs Terraform there. This is an execution workspace, not a cache: the assets stay authoritative, and it has no invalidation semantics. Properties to preserve:

1. read-only Sol installations work;
2. checkout and installed-release execution share one Terraform execution model;
3. targets cannot contend over `.terraform/`;
4. cluster and platform roots stay isolated;
5. every invocation starts from the authoritative assets;
6. backend and state identity is exactly the target's existing one;
7. `errored.tfstate` and similar failure artifacts survive for recovery and diagnosis;
8. a recovery artifact is never deleted or overwritten for a fresh tree;
9. supervision and interruption guarantees stay intact;
10. no consumer requires the bundle to be writable.

The location follows Sol's operational-state conventions: target-isolated, and recoverable after a crash (not an anonymous temp directory). Optimize for correctness over avoiding the copy.

## Options considered

1. **Keep the root as the working directory; require a user-writable install** (what FEAT-101 ships and documents). Simplest, identical to a checkout. It rules out read-only system installs, and it leaves the shared `.terraform/`.
2. **`TF_DATA_DIR` per target and role, in a writable state directory,** plus `init -lockfile=readonly`. This moves `.terraform/` out of the root and separates targets. It does *not* move `errored.tfstate`, which Terraform writes to its working directory, so a read-only root still loses the failure-path state. Insufficient alone.
3. **A per-target working directory, refreshed from the bundle on every run:** copy `platform/cloud/` (a few hundred KB, including `modules/`, which the roots reference by relative path) into e.g. `<workspace>/.sol/terraform/<target>/`, and run Terraform there, with `.terraform/` and `errored.tfstate` beside it. It is re-copied every invocation, so it can never go stale and is not a cache. It works for read-only installs, separates targets, and gives both forms the same semantics. The costs: a copy per run, and the location of `errored.tfstate` moves, so the supervisor's message and runbooks change with it.

Recommendation: **3**. It is the only option that makes the bundle genuinely read-only *and* keeps the failure-path state safe, and it fixes the shared-`.terraform/` contention for checkouts at the same time. It needs your call because DEC-049 ruled out "first-run extraction caches". This is a per-run copy, not a cache, but it is close enough to that line that it shouldn't be decided implicitly.

## Acceptance criteria (once decided)

- Option 3: `sol cloud plan` from a read-only installed bundle succeeds (installed-layout smoke with a read-only mount and Terraform present), and a forced state-push failure leaves `errored.tfstate` where the supervisor says.
- Demo/example: not applicable; state it.

## Completion notes (2026-09-26)

**Contract** (`cli/lib/cloud/sol_cli_terraform_workdir.{ml,mli}`):

```
<Sol state>/terraform/<provider>-<cluster|platform>-<16 hex>/
  platform/cloud/...        rewritten from the assets on every run
  platform/shared/...       (the shared module reads ../../../shared)
  platform/cloud/<provider>/<role>/    Terraform's -chdir: .terraform/, errored.tfstate, crash.log
  .sol-materialized         the source files Sol wrote last time
```

- `<Sol state>` is `Sol_cli_state.dir` (`$XDG_DATA_HOME/sol`, else `~/.local/share/sol`), beside the supervisor's `operations/` records and `runs/`. It is absolute and persistent, so a crash of Sol leaves it where the next command looks.
- `<16 hex>` digests the provider, the role and the *sorted backend configuration*, which is exactly the remote state the directory works on. The backend configuration itself goes to `terraform init` unchanged.
- `chdir` is pure, so the previous operation is checked before anything is written. Every init entry point (`run_terraform_init`, `run_terraform_init_result`, apply's `platform_init`) materializes first. The destroy sequence gets a failure as its typed result, never an exit (REFAC-091).
- Materialization walks `platform/cloud` and `platform/shared` in the asset root, skipping runtime artifacts (`.terraform`, `*.tfstate*`, `errored.tfstate`, `crash.log`, lock info), which a checkout can still hold from before. It writes each file atomically (temporary file and rename) with owner write added. Then it removes only those paths from the previous manifest that the assets no longer have, and writes the new manifest.

**The ten properties, and the evidence for each:**
1. **Read-only installations work.** The installed-release smoke runs `sol cloud plan prod/aws/us-east-1` from the release archive in a container where `/opt/sol` is a read-only mount, the root is read-only, and there's no network. A stand-in `terraform` ran `init`, `plan` and `output` with `-chdir=/tmp/xdg/sol/terraform/aws-cluster-b30d8a7e369c095e/platform/cloud/aws/cluster` and created `.terraform/` there. A control proves `/opt/sol` is unwritable in that container. The offline harness runs the same command with `SOL_HOME` pointed at a `chmod -R a-w` copy of the assets.
2. **One model for both forms.** The same `Sol_cli_platform_assets` root feeds `materialize`, whether it is a checkout or a bundle; nothing branches on the form.
3. **Targets don't contend.** The identity includes the backend configuration; see `test_terraform_workdir.ml`, `identity isolates states`.
4. **Cluster and platform are isolated.** The role is in the identity (same test); the harness finds four distinct working directories: AWS and GCP, cluster and platform.
5. **Every run starts from the assets.** The harness tampers with `main.tf` and plants a manifest-listed stale file; the next plan restores the one and removes the other. The unit test covers an edited source following the assets, an added one appearing, and a removed one disappearing.
6. **Remote state unchanged.** Backend arguments are computed from the target as before. In the smoke, `-backend-config=key=sol/prod/aws/us-east-1/cloud.tfstate` plus the bucket and lock table are identical to a run on the host.
7. **Failure artifacts survive.** The harness writes `errored.tfstate` into the AWS cloud working directory. `apply` is refused, and the message names `<workdir>/errored.tfstate`. The file is byte-identical after the refused apply, a plan, and an `--accept-unresolved` apply, both of which re-materialize.
8. **Never deleted or overwritten.** Removal is manifest-only, and runtime artifacts are never manifest entries. Unit test: `errored.tfstate`, `.terraform/` and an operator's `notes.txt` survive two re-materializations. Harness: an `operator-notes.txt` survives.
9. **Supervision intact.** Operation keys are still `operation_key ~chdir ~backend_config`, and `chdir` is now identity-derived. The full `test_cloud_lifecycle_offline.sh` passes, including INFRA-076's running, unresolved and accepted scenarios and AUDIT-POST-004's platform-root guard. Two fabricated running records now name the real working directory in `root=`. A side effect: a state's records are the same from every worktree. They used to be keyed by the checkout's path, so two worktrees on one target could not see each other's operations; on this machine today's GCP records carried keys from both `sol-qual9` and `sol-qual9run`.
10. **No consumer needs a writable bundle.** Covered by (1). `refuse_sensitive_vars` still reads the asset root, read-only.

**Ownership (REFAC-114's guard caught it).** The first version hard-coded `"platform/cloud"` and `"platform/shared"` in the working-directory module. `check_platform_assets_owner.sh` flagged it once the file was tracked; its earlier green run had predated `git add`. The trees are now `Sol_cli_platform_assets.terraform_trees`, so the platform layout still has exactly one owner.

**Changeover.** Records under the old path-derived keys are not carried over (pre-alpha; no compat shim). Checked on this machine: every existing record's latest outcome is `exited 0`, and `find … -path '*/platform/cloud/*' -name errored.tfstate` found nothing in any checkout. The runbook (`docs/deployment/production-bootstrap.md`) now says where Terraform works and how to push a recovered `errored.tfstate`.

**Docs.** The README and tutorial no longer ask for a writable install, and they state the one remaining checkout dependency: *generated OCaml workspaces still require source framework packages until RELEASE-005 publishes them.*
