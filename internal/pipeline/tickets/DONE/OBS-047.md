Starter alerts for message drop and diversion: decode drops, DLQ inflow, relay publish failures

**Depends on:** None.

**Finding:** FND-0049 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-23** against `origin/main @ f3e9480b` while filing (see the finding).

## Problem

The starter alert set has consumer lag but nothing on `sol_worker_decode_errors_total`, `sol_worker_messages_total{status="dead_letter"}` or `{status="relay_failed"}` — the three signals that messages are being dropped or diverted.

## Remediation

Add three rules next to `SolKafkaConsumerLagHigh` in `cli/platform/infra/base/main.tf` (any increase over 5m for decode drops and relay failures; sustained DLQ inflow), with runbook entries in `docs/deployment/alert-runbooks.md`.

## Acceptance criteria

- `promtool check rules` (or the existing alert-rule test) passes with the new rules.
- Runbook entries exist for each.
- Demo/example: not applicable — state in completion notes.

## Completion notes

- Three rules in `cli/platform/infra/base/main.tf` (`sol-starter-alerts`, beside the
  Kafka pair). Each is grouped by the Sol taxonomy
  (`workspace, env, domain, service`) like `SolHighErrorRate`:
  - `SolWorkerDecodeDrops` (critical): any increase of
    `sol_worker_decode_errors_total` over 5m. These messages were acked and dropped.
  - `SolWorkerRelayPublishFailed` (critical): `sol_worker_messages_total{status="relay_failed"}`
    is nonzero, i.e. at least one failure since the pod started (BUG-029's signal). This
    is a value test, not `increase()`: the labelled series is absent until its first
    failure and appears already at 1, which `increase()` never counts, and the relay
    stops after that failure (review round 1).
  - `SolWorkerDeadLetterInflow` (warning): a nonzero 10m rate of
    `{status="dead_letter"}`, sustained for 15m.
- Runbooks: `docs/deployment/alert-runbooks.md` gains a table row and a
  "Message drop / diversion" section with first-response steps, plus a note that the
  worker metrics exist only when the worker runs with `?ot` (without it the rules are
  silent, never false). `docs/deployment/observability-backends.md`'s alert table
  lists all three.
- Verification: `promtool check rules` and `promtool test rules` (Prometheus v3.14.0,
  downloaded to the session scratchpad, not added to the repo). The rules file is
  extracted from `main.tf` so the test cannot drift from the source. Fixtures model how
  the worker exports each series. The unlabelled decode counter is pre-seeded at 0.
  Labelled `relay_failed` and `dead_letter` series are absent (`_`) until their first
  event. The tests fire on one decode drop and on a relay series that first appears at
  1, stay quiet on a flat counter and on a single dead-letter burst, and fire on
  sustained dead-lettering only after 15m.
- Observed (2026-09-24): `promtool check rules` → `SUCCESS: 3 rules found`;
  `promtool test rules` → `SUCCESS`. Negative controls, each run on a copy of the
  rules: raising the decode threshold to `> 5`, misspelling `relay_failed`,
  shortening the dead-letter `for` to 1m, and restoring the original
  `increase(...relay_failed...)` rule each made `promtool test rules` fail. The
  restored rules pass. CI has no promtool, so this is not wired into CI; the
  extraction script and `test.yml` live in the session scratchpad.
- Demo/example: not applicable (platform alert rules, no author-facing change).
- Language parity (DEC-022), checked against the TS demo
  (`examples/pluto/app/demo_ts/fulfillment_worker/src/metrics.ts`, names from
  `@sol-fab/obs`):
  - `SolWorkerDecodeDrops`: **equivalent**. The TS worker exports
    `sol_worker_decode_errors_total`.
  - `SolWorkerRelayPublishFailed` and `SolWorkerDeadLetterInflow`: **gap**. The TS
    status vocabulary is `{ok, error, retry, ack_failed}`, so these two rules are
    silent for a TypeScript worker. Tracked as FEAT-095.
