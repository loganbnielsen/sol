The database-backed suites are served from cache, and one of them describes a stale job table

**Depends on:** None.

**Premise verified (2026-10-02):** At `origin/main` `d025bfed`. `.github/workflows/ci.yml`'s *Framework integration tests* step ran `dune test framework/ocaml/sol-jobs/ framework/ocaml/sol-outbox/` without `--force`, after the unit step had already run those same two targets with `POSTGRES_URL` unset — where their database cases skip themselves with `[skip] POSTGRES_URL not set`. And `framework/ocaml/sol-outbox/test/test_sol_outbox.ml`'s `jobs_ddl` still created `sol_jobs` without the `workspace` column BUG-091's `enqueue` writes. Running `dune test framework/ocaml/sol-outbox/ --force` against a fresh database failed with `column "workspace" of relation "sol_jobs" does not exist`, which is how the stale table was found.

## Problem

Three failures, and the second and third are the ones that matter: the first is
what they concealed.

1. **A suite that cannot pass.** `framework/ocaml/sol-outbox/test/test_sol_outbox.ml`'s
   `jobs_ddl` still creates `sol_jobs` without the `workspace` column `Sol_jobs.enqueue`
   writes, so its composition test — a job enqueued inside the outbox transaction, the
   whole point of that package — cannot succeed against a database.
2. **CI false success.** The *Framework integration tests* step runs the two
   database-backed suites without `--force`, after the *Unit tests* step has already run
   those same dune targets with `POSTGRES_URL` unset, where their database cases skip
   themselves. Dune records those targets as satisfied, the integration step's invocation
   is a cache hit, and the step that exists to run the database cases does not run them:

   ```text
   unit step        POSTGRES_URL unset   →  dune test jobs/ outbox/
                                              database cases [skip]
                                            →  dune records the targets satisfied
   integration step POSTGRES_URL set     →  dune test jobs/ outbox/
                                            →  cache hit
                                            →  database cases never execute
   ```

   Green CI therefore says nothing about the integration assertions in that step. A
   suite that could not pass — the one in (1) — stayed invisible that way.
3. **Integration-test isolation.** Both suites are independently runnable and both
   destructively own the same schema: each drops and recreates the one `sol_jobs` table in
   the one database. Run from a single `dune test` invocation they execute concurrently,
   so either can drop the table under the other. Observed directly while verifying:
   `relation "sol_jobs" does not exist` raised in the middle of a suite, from the other
   suite's `DROP TABLE IF EXISTS`. This is not flakiness to retry: the two suites have an
   implicit shared-resource constraint that a parallel invocation violates.

Chain: (1) should have failed the integration step, (2) is why it did not, and forcing (2)
is what exposed (3).

The same class of gap is in the coverage BUG-091 left behind: its isolation regression
proves a poller cannot *claim* another workspace's rows, not that its retention *sweep*
cannot delete them, and `validate_workspace`'s refusals have no unit test.

## Remediation

Give the outbox suite's job table the contract `sol-jobs` actually writes; make the
integration path run its suites for real, by forcing them and running one suite per
invocation; and make that execution *evidenced* rather than assumed, so a cached run fails
instead of passing; then cover the sweep boundary and the identity's validation.

## Acceptance criteria

- `dune test framework/ocaml/sol-outbox/ --force` passes with `POSTGRES_URL` set.
- The integration step's invocations are forced and sequential, so the Postgres cases run
  there rather than being served from the unit step's cache.
- **The database cases cannot be skipped, cached or interleaved away.** They are their own
  dune targets (`runtest-integration`), not the unit targets whose meaning depends on an
  ambient variable: the unit step cannot build them, they fail rather than skip without
  `POSTGRES_URL`, and the integration step runs one alias per invocation. The step's exit
  status — not a reading of anything it printed — is the statement that the Postgres-backed
  cases ran and passed.
- A poller in one workspace leaves another workspace's expired terminal row alone, and
  removing the sweep's workspace predicate fails that case.
- `validate_workspace`'s refusals are covered by a unit test.

## Completion notes

- **The stale job table.** `framework/ocaml/sol-outbox/test/test_sol_outbox.ml`'s `jobs_ddl` now creates
  `workspace TEXT NOT NULL` and the dedupe index as `(workspace, kind, dedupe_key)`, matching `sol-jobs`'
  contract and the jobs suite's own DDL. `dune test framework/ocaml/sol-outbox/ --force` with a database is
  green (7 cases), and its composition assertion — a job enqueued inside the outbox transaction — is now the
  check that the two packages agree on the table.
- **The false success is closed structurally.** The two database suites are now dune
  integration targets — `(rule (alias runtest-integration) (action (run ./test_…_pg.exe)))`,
  the idiom `kafka-eio-service` already uses — so they are not the unit targets under a
  different ambient environment. The unit step cannot build them; `dune build
  @framework/ocaml/sol-jobs/test/runtest-integration` and the same alias for `sol-outbox` are
  what the integration step runs, one per invocation, and their `with_pool` **fails** when
  `POSTGRES_URL` is missing rather than printing a skip. The step's exit status is therefore
  the statement that the Postgres-backed cases started, did not skip and passed. Verified
  both directions on this machine: without `POSTGRES_URL` each integration target fails with
  *"POSTGRES_URL is not set: this target exists to exercise Postgres, and a run without a
  database is not a passing run"*, and with it both pass (jobs 20 cases, outbox 7). The unit
  target runs without a database and no longer mentions one.
- **A log-parsing guard was written for this and then removed, and the reason matters.** The
  first version captured each suite's console output into a log and required the suite's
  Postgres-backed case to appear as `[OK]`. CI's first run of it failed — correctly — because
  alcotest fits its summary lines to 80 columns when there is no terminal and truncated the
  case name to `another w...`, so the guard matched the *group* instead. That fix was still
  the wrong shape: it made correctness depend on a presentation detail that its author's
  terminal happened to render differently from CI's. Observed evidence does not have to mean
  scraping the terminal — a suite that cannot return success without a database *is* the
  observation — so the guard, its mutation suite and its CI step are deleted rather than
  maintained, and the marker is in the dune target instead. (`SOL_REQUIRE_DATABASE`, an
  interim flag for the same job, is gone with it.)
- **The suites cannot interleave.** The integration step runs one suite per invocation, so the shared
  `sol_jobs` table each suite drops and recreates cannot be dropped under the other.
- **The sweep boundary.** `test_sol_jobs_pg.ml` gains *a poller sweeps only its own terminal rows*: `alpha`
  completes a job and its terminal row is aged past any retention, then a `beta` poller runs with
  `terminal_retention_s:0.0` and must leave that row alone. **Mutation check:** replacing the sweep's
  `workspace = ?` predicate with a typed always-true one (`?::text IS NOT NULL`) fails exactly that case.
- **Two false starts worth recording.** The first mutation used an untyped `? IS NOT NULL`, which Postgres
  cannot type-infer, so the sweep failed *silently* — `sol-jobs` logs a failed sweep and carries on — and the
  mutation looked harmless: a mutation that breaks the query is not a mutation of the predicate. And the new
  case was first written with an unbounded poller, which simply polls forever when it has nothing to claim;
  it is now bounded the way the suite's own isolation case is.
- **The identity's shape is unit-covered.** `test_sol_jobs.ml` gains `validate_workspace`: a plain name and
  dots/dashes/case accepted; empty, whitespace-only, inner space, slash and over-63-character refused.
- **Verified:** the two suites with a real database (`sol-jobs` 24 cases, `sol-outbox` 7), the unit suite
  (12), the demonstration above, the guard's mutation suite, the format check, the no-comments guard, and
  every guard whose subject is a file this change touches.
- **Demo/example:** not applicable — test fixtures, one regression case, a harness flag and CI sequencing,
  none of which an app author runs or reads. **Language parity (DEC-022):** unchanged; the
  `workspace`-on-the-job-module contract is BUG-091's.
