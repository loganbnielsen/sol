## The question

A deploy can fail to record its release and still report success. Observed live:

```text
error when patching "sol-release-current-pluto": configmaps "sol-release-current-pluto"
is forbidden: … cannot patch resource "configmaps" in API group "" in the namespace "default"

Done. 1 service(s) deployed.
```

The release pointer still named `r-6d35ecdb68a52996` while the deploy was recording
`r-33d8e08d02d2a45c`.

Today that is by design: `cmd_deploy.ml:487-490` treats a record failure as a
warning, because recording was considered best-effort bookkeeping.

## What the pointer is

Not bookkeeping. Established from the code:

| Consumer | Depends on the pointer for |
|---|---|
| `Sol_cli_release_store.current` | "which release is live" |
| `sol rollback` (`cmd_rollback.ml:91`) | which release to restore — DEC-018's whole point |
| `Sol_cli_release_retention.prune ~current` | the retention anchor |

So the pointer is the **authoritative release state**, and a deploy that does not
advance it leaves recovery and retention describing a past that is no longer true.

## Decision (2026-09-20)

**A deployment is not successful unless the authoritative release state is
successfully recorded.**

Concretely:

1. Applying the workload and recording the release are **one outcome**. If the
   release record cannot be written, `sol deploy` fails: nonzero exit, no `Done.`,
   and a message naming what could not be recorded.
2. The failure must be **visible before success is claimed** — never a warning that
   precedes a successful completion line.
3. This is a property of the *profile's* guarantee, not of the Kubernetes objects:
   the workloads may well be running, and that is exactly why the deploy must say
   so rather than implying everything is consistent.
4. The two fixes this implies are **separate** and must be delivered separately:
   - **`INFRA-054`** — make release-record failure fatal to deploy (the semantic
     guarantee above);
   - **`INFRA-055`** — correct the ConfigMap write mechanism and/or the
     authorization, so the record can actually be written.

   The first does not depend on the second. A deploy that cannot record must fail
   *whether or not* the authorization is fixed afterwards.

## Why both

Fixing only the semantics without the mechanism makes every deploy fail on a target
whose pointer already exists — honest, but temporarily unusable, and it would be
tempting to revert. Fixing only the mechanism leaves the guarantee absent for every
other cause of record failure (a full API server, a denied RBAC change, a version
skew). The invariant is what the profile promises; the mechanism is how it holds
today.

## Acceptance criteria

1. When the release record cannot be written, `sol deploy` exits nonzero and does
   not print a successful completion.
2. When it can be written, the deploy behaves exactly as now, and the pointer names
   the release that was just applied.
3. A regression case exists where the **workload application succeeds** and only
   the record write fails, and in it the deploy still exits nonzero — the case the
   live run actually hit.
4. The write path does not require broadening the deploy identity's grant to
   generic `patch` unless the narrower mechanism is shown to be wrong; see
   `INFRA-055`.

## Consequences

- A deployment can now fail *after* its workloads are running. The message must say
  that, so an operator does not redeploy unnecessarily.
- `sol deploy` on a target where the pointer cannot be written fails until
  `INFRA-055` lands. That is the intended order: the guarantee first.
