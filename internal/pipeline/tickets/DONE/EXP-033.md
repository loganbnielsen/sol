**Depends on:** None.

**Related:** `FEAT-111` (the outbox that consumes the answer, and does not wait on it),
`FEAT-112` (idempotent enqueue, the same shape), `framework/ocaml/sol-jobs/sol-jobs.md`,
and the external `pg-eio` package (`~/Code/pg-eio`).

## The question

`pg-eio`'s transaction callback receives the same handle it was given:

```ocaml
val transaction : pool -> (pool -> ('a, Pg_error.t) result) -> ('a, Pg_error.t) result
```

So nothing in the type system separates "inside the transaction" from "outside it":

```ocaml
Sol_jobs.Make(J).enqueue pool job   (* atomic only if called inside the callback *)
Outbox.publish pool event           (* same hole, once FEAT-111 lands *)
```

Both guarantees are conventions today. `sol-jobs.md` documents the convention in prose —
calling `enqueue` "with the `pool` handle from inside `Db.transaction`'s callback"
enqueues in the same transaction — and nothing prevents a caller from doing it outside,
where it commits immediately and the atomicity silently disappears. `FEAT-111` is about to
add a second instance of the same hole.

Should Sol represent transaction scope in the type system, so the atomic path is the only
one that compiles?

```ocaml
Db.transaction pool @@ fun tx ->
  let* () = Domain.update tx … in
  let* () = Outbox.publish tx event in
  let* () = Jobs.enqueue tx job in
  Ok ()
```

## What the spike must answer

1. **Is a `tx` capability cheap?** The deciding question is whether `tx` can be a zero-cost
   phantom over the value `pg-eio` already passes — `type 'a conn`, with
   `pool = [`Pool] conn` and `tx = [`Tx] conn`, and query functions polymorphic in the
   capability — or whether it needs real connection plumbing. If the former, it is a small
   change, and the cheapest moment is before `sol-outbox` exists and before more scaffolds,
   examples and generated workspaces adopt the `pool` convention. If the latter, say so and
   stop.
2. **What would it not prove?** A `tx` value can escape the callback and be reused after
   commit, so the compiler would establish *you entered a transaction*, not that you are
   currently inside one. Closing that needs linearity or regions, which OCaml does not give
   us cheaply. Record the limit explicitly: this is a large ergonomic win, not a soundness
   proof, and the atomicity test stays regardless.
3. **What is the cross-repo cost?** `pg-eio` is an external package, so the change spans
   repos. State the size, and the blast radius on `sol-jobs`, the future `sol-outbox`, the
   scaffolds and the examples.
4. **If adopted, does `sol-jobs.enqueue` move with it?** It has the identical hole today.
   If only the outbox moves, the two packages disagree about how to be transactional, which
   is worse than either answer alone.

## Deliverable

A written decision on this ticket: adopt a typed transaction scope, or keep the convention
with the atomicity test as the guard. Either is acceptable — leaving it implicit is not.
This is a time-boxed investigation, not an implementation; if the answer is "adopt", the
implementation is its own ticket.

## Non-goals

- Not implementing the outbox; that is `FEAT-111`.
- Not gating `FEAT-111`. The outbox can be built on the convention if the answer is "keep
  it", and `FEAT-111` says so.
- Not changing effect handlers, the Eio layer, or connection pooling semantics.

## Decision (2026-10-01): adopt the typed transaction scope

**1. The capability is cheap, and zero-cost at runtime.** `pg-eio`'s `pool` is already a
record whose single field is a polymorphic use function, and `transaction` already builds
the callback's handle as `{ use_conn = fun g -> g conn }` — the callback handle *is* a
distinct value today, it is just typed the same as the pool. Parameterizing the type
changes nothing about the representation:

```ocaml
type 'a handle = { use_conn : 'b. (connection -> ('b, Pg_error.t) result) -> ... }
type pool = [`Pool] handle
type tx   = [`Tx] handle
```

The parameter is a phantom — erased, no allocation, identical call path. `exec`, `find`
and `collect` become `'a handle -> …`, so pool and tx share one query API instead of
gaining a second. Demonstrated in a standalone sketch: a `pool` where a `tx` is expected
is refused with ``This expression has type pool = [ `Pool ] handle but an expression was
expected of type tx = [ `Tx ] handle / These two variant types have no intersection``,
while `exec` accepts either.

**2. What it does not prove.** A `tx` is an ordinary value, so it escapes the callback and
can be used after commit — demonstrated: the sketch's stored handle is used after
`transaction` returns. The compiler establishes *you entered a transaction*, not that it
is still open. Linearity or regions would be needed to close that, and neither is
available cheaply. This is a large ergonomic win and a real bug-class removal, not a
soundness proof; the atomicity test stays.

**3. The hazard it removes is real, not theoretical.** Nested `Pg_db.transaction tx f`
type-checks today, because a `tx` *is* a `pool`. The nested `BEGIN` is a no-op with a
warning, and the nested `COMMIT` ends the **outer** transaction — so a later `Error` in
the outer callback rolls back nothing. Reproduced against the live database before the
change (outer transaction inserts, nests a transaction, then returns `Error`):

```
outer: Error -> query error: outer fails after the nested commit
rows surviving the outer rollback: [1,2]
```

After the change the same program does not compile: `transaction` accepts only a `pool`.

**4. Cost, in repos, files and call sites.**

- `pg-eio`: `lib/pg_db.mli`, `lib/pg_db.ml` (the capability types; the callback handle),
  `lib/pg_table.mli` (four accessor signatures), `CHANGES.md`. Landed as two PRs —
  [pg-eio#25](https://github.com/loganbnielsen/pg-eio/pull/25) (`pg_db`) and
  [pg-eio#26](https://github.com/loganbnielsen/pg-eio/pull/26) (`pg_table`).
- Sol: `sol_jobs.mli`/`sol_jobs.ml` — `enqueue` takes `Pg_db.tx`, the one deliberate
  breaking change; `support-refs.txt`; and the specs and tutorial that showed the old
  shape (`sol-jobs.md`, `sol-worker.md`, `docs/guides/TUTORIAL.md`).
- Blast radius on call sites was **zero in application code**. The app helpers
  (`Notification.insert`, `FulfilledOrders.insert`) are `Pg_table.Make` instances; making
  the accessors polymorphic kept them usable both on the pool and inside the callback, so
  the notify workers and the demo harnesses needed only their callback parameter renamed
  to `tx`. Exactly **three test sites** called `enqueue` on a pool *outside* a
  transaction — each was a genuinely non-atomic enqueue — and now wrap it in
  `Pg_db.transaction`. That is the guarantee doing its job on the first build.

**5. `sol-jobs.enqueue` moves with it.** Yes. It is the other instance of the identical
hole, and an outbox that took `tx` while `enqueue` took `pool` would leave the two
packages disagreeing about what transactional means — worse than either answer alone.

**TypeScript parity (DEC-022):** no impact from the investigation. The `@sol-fab/*`
packages expose no transaction-scope composition and no outbox today; if the TypeScript
outbox lands (FEAT-119's family), it must answer the same question, and this decision is
the reference. Recorded here rather than filed separately, because there is no
TypeScript code to change yet.

**Non-goals confirmed:** no effect handlers, no Eio-layer changes, no pooling-semantics
change. This is a type-only change over the existing value.
