**Related:** INFRA-066 (the ticket-move guard), `internal/ci/check_ticket_transitions.sh`
(the guard that passes such a ticket), FEAT-103 (the ticket that exposed it).

**Premise re-verified (2026-09-27, `origin/main` `c1f650b3`):** half of the
defect below had already been fixed by REFAC-137, which reads frontmatter with
the yaml library and marks an unparseable block in `ls`. What survived is that
nothing *enforced* it and CI never parsed a ticket at all; the title above names
that. The reproduction of both states, and what each surface does now, is in
**Completion notes** at the end of this file.

## The defect

Ticket frontmatter is read by two things that disagree about a malformed file:
`soldev` (which parses it as YAML and fails) and the CI guard (which validates
moves and never parses it). A ticket whose frontmatter is not valid YAML is
therefore **invisible** — `soldev pipeline ls` omits it and still exits 0, so a
worker sees a queue that does not contain it — while the guard reports a clean
pass and the PR goes green.

A hand-written `source:` line is enough to do it: a plain (unquoted) YAML scalar
containing `": "` is a syntax error, and quoting *part* of the line does not help
(the quotes are characters inside the plain scalar). That is exactly how FEAT-103
was filed:

```yaml
source: operator review (2026-09-27) of the TypeScript path - "TypeScript has an E2E path but not a real Sol inner loop: users still have to run Node manually, and the live-dev roadmap is OCaml-only"
```

## Evidence (2026-09-27, `origin/main` `2fff2cef`)

```text
$ soldev pipeline check FEAT-103
internal/pipeline/tickets/READY_FOR_ENGINEERING/FEAT-103.md: frontmatter is not valid YAML: error calling parser: mapping values are not allowed in this context character 0 position 0 returned: 0
$ echo $?
1

$ soldev pipeline ls >/dev/null; echo $?
0                      # FEAT-103 is simply absent from the listing

$ bash internal/ci/check_ticket_transitions.sh; echo $?
0                      # the guard CI runs is happy
```

A scan of every ticket's frontmatter with a YAML parser finds 2 of 785
unparseable: FEAT-103 (filed that same day) and `DONE/INFRA-042.md`, which has no
frontmatter block at all — an older, already-merged instance of the same class,
invisible in the same way.

## Remediation

- Make the failure gating and loud, using the parser that already exists rather
  than a second one: `soldev` should fail (non-zero) when it cannot parse a
  ticket's frontmatter, and CI should run that command. `internal/tooling/soldev`
  is built by the `test` job's Build step, which runs before the guard steps, so
  the guard can call it directly. Decide whether that is a new
  `soldev pipeline lint` (a full-tree check with the file named) or `pipeline ls`
  learning to exit non-zero; the former is clearer about intent, the latter is
  free.
- Until then, `internal/ci/check_ticket_transitions.sh` passing a ticket it never
  parsed is the misleading part: its message should say it validates moves only,
  or it should gain the parse.
- Fix `DONE/INFRA-042.md` (give it the frontmatter its siblings have, with the
  fields the era used) or record why it is exempt.

## Acceptance criteria

- A ticket whose frontmatter does not parse fails CI, naming the file and the
  parser's message — reproduced by planting one in the guard's mutation test
  (`internal/ci/test_ticket_transitions.sh` or the mutation test of whichever
  guard gains the check), which must fail without the fix.
- `soldev pipeline ls` either lists every ticket in the tree or exits non-zero
  naming the ones it could not read; it never silently omits one.
- `DONE/INFRA-042.md` parses, or the exemption is recorded in the guard.
- Demo/example: not applicable (internal tooling). Language parity: no impact.

## Completion notes

**Recon first, and the premise had moved (2026-09-27, `origin/main` `c1f650b3`).**
REFAC-137 (merged after this ticket was filed) replaced the hand-split
frontmatter read with the YAML parser and made `ls` and `check` report a
frontmatter that does not parse. Reproduced both known cases against the
built binary before touching anything:

```text
# invalid YAML (planted BACKLOG/X-1.md, the FEAT-103 shape)
$ soldev pipeline ls
  X-1           -      -   depends on: none   invalid-frontmatter: frontmatter is not valid YAML: …
$ echo $?
0
$ soldev pipeline check X-1
internal/pipeline/tickets/BACKLOG/X-1.md: frontmatter is not valid YAML: …
$ echo $?
1

# no frontmatter block at all (the real DONE/INFRA-042.md)
$ soldev pipeline ls --all | grep INFRA-042
  INFRA-042     -      -   depends on: none   -            INFRA-042 — a partially-installed …
$ soldev pipeline check INFRA-042
INFRA-042  state: DONE
depends on: none
status: not-ready-state
$ echo $?
0
```

So the half of the defect that read as "silently disappears" was already fixed
(tickets are listed with a reason, and `check` refuses), and what remained was
the half this ticket is really about: **nothing enforced it**. `ls` still exited
0, so a pipeline that ran it could not tell a queue with an unreadable ticket
from a healthy one; a ticket with no frontmatter at all was not an error
anywhere (`INFRA-042` read as a ticket with empty columns, and `check` answered
for it); and CI never parsed a ticket, which is why the guard was green. The
guard's trace: `internal/ci/check_ticket_transitions.sh` is an `awk` over
`git diff --cached --name-status` rows that classifies ticket *moves* — it never
opens a ticket file, so no malformed content can fail it.

**What landed.**

- `Soldev_ticket.unreadable ~path content` — one rule, in the library, used by
  every surface: a ticket is unreadable when it has no frontmatter block, when
  the block does not parse with the same `frontmatter` parser the pipeline uses,
  or when `id`, `type`, `severity` or `source` is missing or blank. The message
  is path-prefixed inside the library, so "names the file" is structural rather
  than something each caller must remember. Nothing about a ticket's *content* is
  policed: the body, the dependency prose and any extra fields are the author's
  (`premise:` is explicitly exercised as an accepted extra field).
- `soldev pipeline validate` — new command, whole tree (BACKLOG,
  READY_FOR_ENGINEERING and DONE) by design, because those are exactly what the
  other two surfaces cannot cover between them: `ls` is a queue view that does
  not read DONE by default, and `check` only ever looks at the ticket it is
  handed. It prints every failure with its reason and exits 1. A state directory
  that is missing is a failure too, not an empty state — the same silent
  degradation in a different form.
- `pipeline ls` now **fails closed**: an unreadable ticket is still shown in its
  row with the reason (kept, because the row is where a reader looks), and the
  command exits 1 naming it, instead of exiting 0.
- `pipeline check` uses the same rule, so a ticket missing its frontmatter block
  or a required field is refused rather than answered for.
- A ticket the listing has rejected is not *acted on*: its row short-circuits the
  decoration chain, so no premise probe runs (that is a command the ticket
  supplies), and no PR or worktree lookup happens for it. The guard pins this with
  a probe that touches a marker file, plus the control that the same probe does
  run for a readable ticket.
- CI: `.github/workflows/ci.yml` runs `internal/ci/test_pipeline_validate.sh`
  unconditionally (a ticket-filing change is docs-only, which is the PR shape
  this exists for) and not gated on `classify`. The script runs the validator
  over the repository's own tree and is its mutation test: it builds a throwaway
  tree with readable tickets that must pass (so a later failure cannot come from
  the harness), then plants malformed frontmatter, a no-frontmatter ticket in
  DONE and a missing field, and requires each to be rejected with the file named.
  It also asserts `ls` and `check` fail closed, that a rejected ticket is not
  acted on, and that removing the plants turns the listing green again.
- `AGENTS.md` records `pipeline validate` in the soldev roles.
- Tests: `internal/tooling/soldev/test/test_ticket.ml`'s tree-wide test now uses
  `unreadable` (so it covers the missing-block and missing-field classes, not
  only YAML validity) and six new cases pin the rule.

**Non-vacuity, checked rather than assumed.** With `unreadable` temporarily
returning `None` — the pre-fix behaviour — the guard fails at its first mutated
case (`validate, malformed frontmatter: the command accepted it`) while its
control steps still pass; restored, it is green. So the guard tests the fix, not
the harness.

**Content corrections (separate from the tooling, per the ticket).**
`DONE/INFRA-042.md` gained the frontmatter its siblings have (`id`, `type: bug`,
`severity: high`, and the `Discovered:` line it already carried as `source`);
its body is untouched, including the historical `**Status:** Done` line. The
whole tree then validates: `pipeline tickets: 786 read across 3 state(s) — all
readable`.

**Deliberately not fixed here.** `DONE/DEC-049.md` and
`DONE/DEC-049-gke-standard-is-the-supported-gcp-substrate.md` are two different
decisions declaring the same id, so `find_ticket "DEC-049"` can only ever reach
one of them and `ls` shows two rows for one id. That is an *identity* defect
rather than a readability one — both files parse — and fixing it means
renumbering the GKE decision and editing references in the GCP stream
(`platform/cloud/gcp/cluster/variables.tf`, `internal/planning/WORK_SUMMARY.md`,
INFRA-093's `source:`), which is out of scope while a live qualification attempt
is running. Filed as `BACKLOG/BUG-061.md` with the reproduction, the exact
references, and the open question of whether `validate` should enforce id
uniqueness and id-equals-filename (this ticket kept the validator to
readability so the enforcement could not force a content change into it).

**Behaviour changes.** `pipeline ls` can now exit 1 (it previously always exited
0); `pipeline check` refuses a ticket with no frontmatter block or a missing
required field (it previously answered `not-ready-state`); `pipeline validate` is
new; CI has one more unconditional guard step. Valid tickets are unaffected: the
whole tree passes, and the tree-wide unit test asserts it.

**Demo/example: not applicable** (internal tooling; no app-author surface
changes). **Language parity: no impact** (no framework-level concept, contract or
convention changes — this is the repo's own ticket metadata).
