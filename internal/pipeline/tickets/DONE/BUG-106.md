Own one migration-directory contract in pg-eio, and roll back by recorded file identity

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `7f6aa377` with `pg-eio` pinned at `1cfc9b51`:

- `pg-eio` `lib/migration.ml:11-35` parses migration file names and silently drops any `.sql` file it cannot parse.
- Sol re-implements the same grammar strictly in `cli/lib/base/sol_cli_migration.ml:20-101`, and every `sol migrate` path calls it first (`cmd_migrate.ml:183`) to compensate.
- `Migration.rollback` rebuilds the down file name as `%04d_<name>.down.sql` (`migration.ml:316`).
- Sol's own error text recommends `001_create_orders.sql`.
- `sol migrate apply --dry-run` prints every migration file, not the pending ones (`cmd_migrate.ml:60-81`).

**Premise re-verified (2026-10-01) at `origin/main` `69035715`, resuming [PR #797](https://github.com/loganbnielsen/sol/pull/797):**

- The `pg-eio` half had landed: the pin (`53ad394`, pg-eio #26) descends from `8a53710` (pg-eio #24), so `Migration.read_migrations` is strict and `Migration.rollback` resolves the down file from the recorded up path. No pin change is needed.
- Sol's half had not: `cli/lib/base/sol_cli_migration.ml` still owned a second grammar (`let parse_version`, `duplicate_versions`), and `cmd_migrate.ml`'s `print_pending_sql` still previewed every `*.sql` file with no database read. The ticket stayed stale-but-actionable, and `PR #797`'s branch was 32 commits behind.

## Problem

- **Rollback cannot find down files it should.** A migration named as Sol recommends (`001_create_orders.sql`, `001_create_orders.down.sql`) is recorded as version 1, `create_orders`. Rollback then looks for `0001_create_orders.down.sql` and fails. The same happens for any width other than 4.
- **Two grammars for one contract.** The library that applies migrations silently skips files the CLI would reject, so correctness depends on every caller remembering to run Sol's validator first. Any other `pg-eio` consumer, or a new Sol path, gets the lax behavior.
- **`--dry-run` shows the wrong SQL.** The output is labelled pending, but applied migrations are included.

## Remediation

Make `pg-eio` own the strict directory contract: an unparseable or duplicate-version `.sql` file is an error. Expose the parsed migration list, and have Sol use it instead of its own parser. Rollback resolves the down file from the same parsed identity (the up file's actual name), never by reformatting the version. Dry-run prints exactly the migrations `apply` would run, which requires a database read of applied versions. Update the pin and Sol's call sites in the same pass.

## Acceptance criteria

- `001_x.sql`/`001_x.down.sql` and `0001_x.sql`/`0001_x.down.sql` both roll back.
- `pg-eio` `apply` refuses a directory containing an unparseable `.sql` file, and Sol has no second parser.
- `--dry-run` against a database with some applied migrations prints only the pending ones.
- Update a runnable migration example. No application-language parity impact (migrations are CLI/library tooling).

## Completion notes

- pg-eio PR #24 owns strict `.sql` filename validation, numeric ordering, duplicate-version rejection, original-path rollback, and read-only pending migration inspection.
- Sol uses pg-eio's parser for prerequisite checks and queries pending migrations for `--dry-run`. Against local PostgreSQL, applying `001_create.sql` then previewing with `002_drop.sql` printed only `002_drop.sql`.
- Pluto includes a companion down migration and a dry-run example. No application-language parity impact: migrations are CLI and database tooling, independent of application language.
- `Sol_cli_migration.required` fails closed on a missing `--dir` again: `cannot read migrations dir: <dir>: No such file or directory`, produced before any port-forward or database connection. The first cut of this branch lost that (`Absent -> Ok []`) along with `print_pending_sql`, so `sol migrate apply --dry-run --dir nope` reached the database and reported a raw `Eio.Io` string instead of failing fast.
- The deploy gate's other reading — a workspace with no `db/migrations` declares nothing, so `sol deploy` proceeds — is now explicit as `required_if_present`, used by `sol_cli_migration_gate.verify` and `sol_cli_deploy_run.migration_prerequisite`. Both readings share the one pg-eio parser; only the absent-directory answer differs.
- `Sol_cli_workspace_scan.discover_migrations` no longer counts a companion `*.down.sql` as a migration (found by adding pluto's down file, which the example in the acceptance criteria asked for).

Reproduced on this branch against local PostgreSQL (`POSTGRES_URL=postgresql://postgres:dev@localhost:5432/sol_dev`),
in a throwaway workspace holding `001_create.sql`/`001_create.down.sql` and
`002_more.sql`/`002_more.down.sql`:

```
$ sol migrate apply --dry-run
-- 001_create.sql
CREATE TABLE t (x int);

-- 002_more.sql
CREATE TABLE u (x int);

$ sol migrate apply
Applying migrations from .../db/migrations...
Done.

$ sol migrate apply --dry-run
(no pending migrations in .../db/migrations)

$ sol migrate rollback
Rolled back.

$ sol migrate apply --dry-run
-- 002_more.sql
CREATE TABLE u (x int);
```

So three-digit names roll back through their own `001_create.down.sql` — the defect this
ticket names, where rollback looked for `0001_create.down.sql` — and `--dry-run` reports what
`apply` would actually run rather than every file on disk.
