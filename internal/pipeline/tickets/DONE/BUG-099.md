Make Kafka worker readiness hold for replicas that own no partition

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `7f6aa377`:

- `framework/ocaml/kafka-eio-service/lib/kafka_service_config.ml:55` fixes `partitions = 1` for every topic Sol creates.
- `framework/ocaml/sol-worker/lib/worker_health.ml` reports `/readyz` 200 only while partitions are assigned.
- `cli/lib/workspace/sol_cli_manifest_yaml.ml:288-293` renders both the worker `startupProbe` (`failureThreshold 60 × periodSeconds 5`) and its `readinessProbe` on `/readyz`.
- `cli/lib/deploy/sol_cli_deployment_plan.ml:571-579` requires `replicas >= 2` for a `node-failure-tolerant` worker, and `Sol_cli_deployment_render` adds a PDB with `minAvailable = replicas - 1`.

## Problem

With one partition, only one member of a consumer group can own it. Every other replica is idle by design, but Sol reports it as not ready, and its startup probe never passes. As a result:

- **Idle replicas crash-loop.** After 300s of unready `/readyz`, the kubelet restarts the standby container, and restarts back off exponentially. The replica that should take over after a node loss is often in `CrashLoopBackOff` when the node goes. `node-failure-tolerant` is the profile this breaks, and Sol requires it to have at least two replicas.
- **Node drains block.** The PDB counts only the owning replica as healthy (1 of `minAvailable` 1), so evicting that replica is never allowed. `kubectl drain` of its node hangs.
- **Rollouts can stall.** Under the default `RollingUpdate` (`maxUnavailable` rounds to 0 below four replicas), a new pod becomes ready only if the group rebalance happens to give it the partition. If it doesn't, the old pod keeps it, the new pod's startup probe kills it at 300s, and the rollout makes no progress.

Readiness here conflates "healthy and in the group" with "currently owns work". The hard-coded single partition also means extra replicas can never add throughput.

**Reproduction** (local Redpanda, two `Worker.Make_with_retry` processes with one `group_id`, each serving `/readyz` on its own port): polled at 10s, 20s and 30s, replica 1 returned `200` and replica 2 returned `503` every time. `rpk` showed one partition, owned by a single member.

## Remediation

Two changes, both required:

1. **Readiness means healthy group membership, not owning work.** `/readyz` reports ready once the consumer has joined its group and is polling. Assignment is exposed as a metric, not a readiness condition. Liveness still tracks poll cadence (BUG-014). An idle standby is a correct state; it is what `node-failure-tolerant` asks for.
2. **Partitioning is part of the event contract.** Remove the hard-coded `partitions = 1`. The topic's declared contract (`events/<team>/`) states its partition count and its message key. `Kafka_service.publish` takes the key the contract declares, so per-entity ordering survives more than one partition, and consumers scale up to the declared partitions. Changing either is a contract change the plan shows. It never silently repartitions a topic (the existing partition-reduction guard stays).

## Progress

**Part A — readiness (landed 2026-09-30).** Premise re-verified at `origin/main`
`24f45f43`. The root cause turned out to sit upstream of Sol: kafka-eio's
`on_assigned`/`on_revoked` fire only on **non-empty** assignment transitions
(`lib/kafka_consumer.ml`), so a member that owned nothing emitted no lifecycle
observation at all and was indistinguishable — at every layer above it — from a
consumer that had never joined. kafka-eio now reports membership separately
(`Consumer.hooks.on_assignment : int -> unit`, plus `Kafka_raw.memberid`, which
is what separates "joined with nothing" from "not joined yet"; kafka-eio#32, and
covered there by a two-member one-partition integration test). Sol's
`Worker_health` makes readiness that membership latch, latches it (a rebalance
no longer flaps readiness) and exposes `sol_worker_assigned_partitions` as a
gauge instead of a readiness condition; liveness is unchanged. This addresses
the crash-loop, the blocked drain and the stalled rollout, and it satisfies the
`docs/deployment/workload-availability.md` acceptance criterion.

**Part B — partitioning and message key (landed 2026-09-30).** `config.partitions`
is gone; a topic's contract is its event module. `Kafka_service.MESSAGE` gains
`partitions : int` and `key : t -> string option`, and `register` uses the
declared count for the topic it creates, for the reduction guard, and for the retry
and DLQ topics — all three read the same declaration, so they cannot drift.
`publish` sends the declared key, which is what lets per-key ordering survive more
than one partition. A declared count below 1 is a `Config` error rather than a
broker round-trip. `Kafka_service.Admin` now exposes `query_topic_partitions`
alongside the `decode_topic_partitions` it already had, so what Sol actually
created is observable.

One acceptance criterion changed shape during implementation, and the reason is
recorded rather than worked around. "Changing either is a contract change the plan
shows" cannot be satisfied by the plan reading the declaration: the value lives in
compiled code, and `key` is executable domain logic that a manifest cannot own —
duplicating it into `events/<team>/sol.toml` needs a guard to stay honest, which
is the synchronisation machinery this design exists to avoid. Code is the
canonical contract; how the CLI inspects contracts expressed in *application
code* is its own problem, filed as `FEAT-116`, and `BUG-107` records that the
scaffold already lists a topic name the application never uses.

**Evidence.** `dune build @all` clean; framework doc signatures clean. The
broker-backed `kafka-eio-service` integration suite is **17 tests** (was 16),
including the new `partitioning` case: it creates a 3-partition topic, asserts
from the admin API that the topic got the declared count rather than a default,
publishes interleaved records for three keys, consumes them with two members of
one group, and asserts each key arrived exactly once in publication order handled
entirely by one member. It was mutation-checked — with `key _ = None` it fails on
`one member handled every record for alpha`, so it detects the absence of keying
rather than merely exercising the new field. Also green: `sol-worker` 17 tests,
`local-demo` e2e 9 tests with a now 3-partition keyed topic.

**TypeScript parity.** Deferred with a trigger, tracked as `FEAT-117`:
`@sol-fab/kafka` is an external npm package, so a TypeScript application cannot yet
declare a partition count or key its records. The obligation is recorded for both
languages in `internal/specs/framework-conventions.md` § Partitioning and key.

**Evidence limits.** Acceptance criterion 1 is a live-cluster observation (two
replicas over a 10-minute window) and is *not* claimed here: the mechanism is
covered offline by kafka-eio's two-member integration test and by
`sol-worker`'s readiness unit tests, and the live observation belongs in the
qualification ledger rather than in this ticket.

## Acceptance criteria

- Two replicas of one worker on a one-partition topic both pass their startup and readiness probes, and neither restarts over a 10-minute window.
- `kubectl drain` of the node running the owning replica succeeds under the rendered PDB.
- A `replicas = 1` rolling update completes whichever member the rebalance assigns.
- No topic's partition count is hard-coded. Partition count and message key come from the declared event contract, and `publish` sends the declared key. A test with a multi-partition topic shows same-key records processed in order by one consumer while load spreads across replicas.
- `docs/deployment/workload-availability.md` states the new readiness meaning. Update a runnable example and record the TypeScript worker parity verdict in completion notes.
