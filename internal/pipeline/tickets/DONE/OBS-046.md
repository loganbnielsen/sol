## What this is

`sol status` and `sol open` link into Grafana. At unit scope the link selects on
the `service` label; at workspace and domain scope it selects on the Kubernetes
**namespace** string, assuming the convention
`namespace = <workspace>-<domain>`:

```text
Workspace -> {namespace=~"<workspace>-.+"}
Domain    -> {namespace="<workspace>-<domain>"}
Unit      -> {service=~".*<k8s-name>.*"}
```

That contradicts the project's own identity model, which
`docs/architecture/observability-design.md` states as a product rule: the six
labels (`workspace`, `env`, `domain`, `service`, `primitive`, `release`) are the
API, and "Kubernetes namespaces, pod names, Helm release names, bucket names and
cloud resource names are implementation details."

The labels are available today, so this is a link fix rather than new plumbing:
`Sol_cli_manifest_yaml.render_taxonomy_labels` puts the taxonomy on the pod
template, and Alloy promotes pod labels into Loki stream labels —
`cli/platform/infra/base/alloy/logs.alloy.tftpl` maps
`__meta_kubernetes_pod_label_<label>` → `<label>` for every taxonomy label. The
workspace and domain links can therefore select on `workspace` and `domain`
directly.

The failure this produces is silent, which is what makes it a bug rather than a
nice-to-have: a workspace whose namespace does not follow
`<workspace>-<domain>` — a GitOps-emitted namespace, a renamed one, or any future
hosted shape — opens an Explore view that is empty, and nothing tells the user
whether that means "no logs" or "wrong query".

## Evidence (2026-09-18, `main` at 790dc3e8)

```text
cli/sol/lib/sol_cli_open.ml:106  let logs_url ~base_url ~workspace scope =
cli/sol/lib/sol_cli_open.ml:112      ~logql:(Printf.sprintf {|{namespace=~"%s-.+"}|} workspace)
cli/sol/lib/sol_cli_open.ml:121        ~logql:(Printf.sprintf {|namespace="%s"}|} ns))
```

The unit-scope path already uses the intended vocabulary
(`cli/sol/lib/sol_cli_logs.ml:49` → `{service=~".*<k8s_name>.*"}`), and
`cli/sol/lib/sol_cli_logs.ml:46` documents that intent — "the label is
`<workspace>_<unit>`-shaped, not `namespace`/`app`" — which makes the
workspace/domain paths the outlier rather than a deliberate design.

## Non-goals

- Not changing the namespace naming convention itself (`<workspace>-<domain>`,
  locked in the roadmap). This is about what Sol's own links *select on*.
- Not adding workspace- or domain-wide Loki queries to `sol logs`, which is
  deliberately unit-only (`cli/sol/bin/cmd_logs.ml`). A dashboard link and a
  streaming command are different surfaces.
- Not a metrics or traces change.
- Not a wholesale rewrite of the dashboard JSON; if the provisioned dashboards
  themselves select on a namespace-derived variable, that is confirmed and either
  fixed here or filed separately with evidence.

## Acceptance criteria

- Workspace, domain, and unit log links all select on identity labels the emitted
  logs actually carry. The ticket records which labels were confirmed present in
  a real Loki stream — pod-stdout lines via Alloy versus app-pushed lines via
  `obs-loki-eio`, which use different label sets — before choosing.
- `cli/sol/lib/sol_cli_open.ml` builds no LogQL selector from a namespace string,
  and a test asserts the generated query for each scope contains no `namespace`
  selector.
- A test or completion note records the exact query produced for a real
  workspace, so the change is observable rather than asserted.
- The change is verified against a running local substrate
  (`sol local infra up` → `sol local run` → `sol open logs`), not only in unit
  tests.
- If some log path turns out *not* to carry the identity labels, that is recorded
  as a finding rather than met by widening the namespace dependency.

## Answer: which labels the streams actually carry

Confirmed against a running local substrate (k3d `sol-local`, with
`examples/pluto` deployed as workspace `pluto`, domain `demo-ts`), read through
the in-cluster Loki rather than an ambient context:

```text
label names present: __stream_shard__ container domain instance job namespace
                     pod primitive release service service_name stream workspace
```

A real series for `{workspace="pluto"}`:

```json
{"workspace":"pluto","domain":"demo-ts","service":"fulfillment-worker",
 "primitive":"worker","release":"r-41ba2f2fae2ad579",
 "namespace":"pluto-demo-ts","pod":"...","container":"...",
 "job":"loki.source.kubernetes.pods"}
```

So `workspace`, `domain`, `service`, `primitive` and `release` are stream labels
on real data, alongside `namespace` rather than instead of it.

**On the two log paths.** Every stream in this substrate reports
`job="loki.source.kubernetes.pods"` — the Alloy pod-stdout path; no app-pushed
streams were present to compare. That is recorded as a finding rather than
assumed equivalent: app-pushed lines via `obs-loki-eio` were not observed here, so
their label set is *unknown*, not known-equal. It does not block this change,
because Alloy tails pod stdout for every unit, so a unit's output is on a stream
carrying the taxonomy labels whether or not the application also pushes a copy.
If app pushes turn out to lack `workspace`/`domain`, the failure is a *missing
duplicate*, not a missing log line, and it is a separate finding about the push
path rather than a reason to widen the namespace dependency.

## Completion

`logs_url` builds every selector from identity labels:

| Scope | Before | After |
|---|---|---|
| workspace | `{namespace=~"<workspace>-.+"}` | `{workspace="<workspace>"}` |
| domain | `{namespace="<workspace>-<domain>"}` | `{workspace="<workspace>", domain="<domain>"}` |
| unit | `{service=~".*<k8s_name>.*"}` | unchanged — already the intended vocabulary |

Values go through `Sol_cli_kubernetes_name.sanitize_label_value`, the same
function the manifest renderer uses for the label value itself, so the query and
the emitted label cannot drift into two different transforms for one conceptual
value (OBS-021). Domain scope keeps its existing name validation, so an invalid
domain still fails exactly where it did before; only the selector changed.

Verified on the running local substrate — the exact queries produced for the
deployed workspace, and the stream count each returns:

```text
{workspace="pluto"}                       -> 2 streams
{workspace="pluto", domain="demo-ts"}     -> 2 streams
{namespace=~"pluto-.+"}   (the old query) -> 2 streams
```

The new selectors return the same streams as the old one *where the naming
convention happens to hold*, which is what makes this a fix rather than a
behaviour change: a workspace whose namespace does not follow
`<workspace>-<domain>` now returns its logs instead of an empty Explore view.

Unit tests: `url logs` in `cli/sol/test/test_open.ml` now asserts "no namespace
selector" for all three scopes, plus that the workspace and domain labels are
carried. `dune runtest cli/sol/test` passes (25 tests in that suite), `dune fmt
--preview` is clean.

**Demo/example coverage:** Verified against the deployed `examples/pluto`
workspace as above. No `TUTORIAL.md` change is needed — the Explore URL is not
documented there, and the only other `namespace=` selectors in the tree are
unrelated Prometheus `up{}` alert expressions in `docs/deployment/`.

**TypeScript parity:** No language-parity impact — the labels are emitted by the
language-neutral manifest renderer and apply to TypeScript units identically.
The workspace used for verification is itself a TypeScript workspace.
