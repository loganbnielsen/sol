**Depends on:** None.

**Related:** FEAT-079 (execution-semantics ticket that follows this one;
touches the same `cronjob_doc`/`Render_fn` call site, so land this first to
avoid the two overlapping).

`-fn`'s generated `CronJob` ignores `sol.toml`'s `cpu`/`memory` and always
emits hardcoded resource requests/limits.

## Problem

`Sol_cli_toml.t` — the one parsed representation of a `[service]` table
shared by `-svc`/`-worker`/`-fn` — already carries `cpu : cpu_quantity
option` and `memory : memory_quantity option`, parsed with the same
`cpu_quantity`/`memory_quantity` machinery `-svc`/`-worker` use for their own
resource requests/limits. `-svc`/`-worker` render these through
`sol_cli_deployment_render.ml`'s `deployment_resources`. `-fn` does not: its
`Render_fn` branch skips `deployment_resources` entirely and calls
`cronjob_doc` (`sol_cli_manifest_yaml.ml`), which hardcodes:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 250m
    memory: 256Mi
```

So a `-fn` app author can set `cpu = "2"` / `memory = "4Gi"` in `sol.toml`
and the generated manifest silently ignores it, deploying a function that
needs 2 CPU / 4 GiB with a 250m / 256Mi limit — which either OOM-kills or
CPU-throttles the function, with no error or warning anywhere in the
pipeline. This is not a missing feature; it's parsed, validated
configuration being thrown away at render time.

## Remediation

- Thread `deployment.cpu`/`deployment.memory` from the already-parsed
  `Sol_cli_toml.t` into `cronjob_doc`'s `resources.requests`/`resources.limits`,
  the same values `deployment_resources` already computes for `-svc`/`-worker`
  (`cpu_quantity_to_string`/`memory_quantity_to_string`).
- When `cpu`/`memory` are unset in `sol.toml`, keep today's exact hardcoded
  values as the default — this ticket must not change generated output for
  any `-fn` app that doesn't set them.
- No new TOML schema, no new parsing — this is purely a rendering-path fix.

## Acceptance criteria

- A `-fn` app with `cpu`/`memory` set in `sol.toml` produces a `CronJob`
  whose `jobTemplate` resources match those values.
- A `-fn` app that does not set `cpu`/`memory` produces byte-identical
  resource fields to today's output (golden-test regression coverage).
- No change to `-svc`/`-worker` rendering.

## Completion notes (2026-09-14)

Implemented: `Render_fn`'s `fn_fields` now carries `cpu`/`memory` (same
`Sol_cli_toml.cpu_quantity`/`memory_quantity` types `deployment_fields`
already uses), threaded from `render_spec`'s already-resolved `s.cpu`/
`s.memory` through to `cronjob_doc`, which now takes `~cpu`/`~memory`
string parameters instead of hardcoding them.

**Deviation from this ticket's literal "byte-identical when unset"
acceptance criterion — resolved deliberately, recorded here rather than
silently:** the old hardcoded shape was `requests: 100m/128Mi, limits:
250m/256Mi` — an asymmetric 2.5x/2x request-to-limit ratio nothing else in
the codebase uses. This ticket's own Remediation said to thread cpu/memory
through "the same way `deployment_resources` already does for
`-svc`/`-worker`" — and that path sets `limits = requests` (single value,
no multiplier; see `deployment_doc`/`rollout_doc`). Preserving the old
2.5x/2x ratio literally would have meant inventing a new limit-multiplier
policy under a ticket explicitly framed as "purely a rendering-path fix, no
new policy." I chose consistency with sibling primitives over literal
byte-for-byte preservation: `-fn` now renders `limits = requests = cpu/memory`
(same convention as `-svc`/`-worker`), which does change the *default*
output for a `-fn` app that sets neither field — `limits.cpu` drops from
`250m` to `100m`, `limits.memory` from `256Mi` to `128Mi` (both now equal to
the shared `default_cpu`/`default_memory` of `100m`/`128Mi`, matching every
other primitive's default resource shape). This is a real, minor behavior
change for unset `-fn` apps, not a bug — flagging it explicitly since it
diverges from the criterion as literally written.

Added two direct tests in `test_manifest_render.ml`'s `fn` group: one
confirming a non-default `cpu`/`memory` reaches the rendered `CronJob`
(the actual bug this ticket fixes), one confirming request and limit are
rendered equal (the sibling-consistent policy chosen above). Existing `fn`
tests were unaffected — none asserted exact resource values.

No demo/example update: this is an internal rendering-path fix to an
existing configuration surface (`cpu`/`memory` were already documented and
usable for `-svc`/`-worker`); no new `sol.toml` field, CLI command, or
generated-manifest shape was added.
