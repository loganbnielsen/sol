**Depends on:** None.

## Premise verified

Current `platform/cloud/aws/cluster/main.tf` declares `aws_db_instance.postgres` and `aws_db_subnet_group.main` with `count`. Their state addresses end in `[0]`. `Sol_cli_cloud_destroy.find_address` compares exact addresses, but `Sol_cli_aws_destruction.rds_of_state` asks for `aws_db_instance.postgres`. It therefore reports no database and skips the existing protection-disable preparation. `Sol_cli_resource_identity.aws` also emits unindexed import addresses. The saved AWS state contains the database at index 0 with deletion protection true. The observed import error comes from Sol's product recovery, invoked by the harness, not from a module-qualified resource or a harness import command.

## Remediation

Use concrete Terraform instance addresses when identifying/importing counted resources. Keep resource-block addresses only where Terraform accepts a block-wide target. Check sibling counted identities, including bootstrap access and conditional security/storage resources. Do not treat a represented database as absent when only its address shape differs.

## Acceptance criteria

- A state containing `aws_db_instance.postgres[0]` enters RDS preparation and disables deletion protection before destroy.
- Database and subnet-group recovery use valid counted import addresses.
- An unrepresented or unreadable database is diagnosed accurately; a malformed identity cannot grant a false absence/retention verdict.
- Check the saved AWS state shape without a live provider call. Live absence remains a separately authorized qualification claim.
- Example impact: none; provider lifecycle internals. Language-parity impact: none.

## Completion notes (2026-10-04)

**Premise re-verified at pickup.** `platform/cloud/aws/cluster/main.tf` still declares
`aws_db_instance.postgres`, `aws_db_subnet_group.main` and `aws_security_group.rds` with
`count = var.create_rds ? 1 : 0`; `Sol_cli_aws_destruction.rds_of_state` still asked
`find_address state "aws_db_instance.postgres"` (string equality, `cli/lib/cloud/sol_cli_cloud_destroy.ml`);
`Sol_cli_resource_identity.aws` still emitted the unindexed import addresses. The state shape was
read from the counted root without a live provider call (`aws_db_instance.postgres[0].endpoint` in
`platform/cloud/aws/cluster/outputs.tf`, and the module's `count`), as the ticket authorises.

**Fix.**

- `Sol_cli_aws_destruction.rds_address = "aws_db_instance.postgres[0]"` is the concrete address the
  destroy reads from state; `rds_target` stays the block-wide `-target=aws_db_instance.postgres`
  because Terraform accepts a block-wide target (the ticket's explicit carve-out).
- `rds_of_state` diagnoses a state that represents an `aws_db_instance` at some other address
  instead of reporting it absent, so a malformed identity cannot grant a false absence or
  retention verdict.
- `guard_preparation_policy` and `reconciliation_policy` now match their guarded addresses with
  `Sol_cli_terraform_plan.Resource` (the instance-aware semantic INFRA-081 introduced for
  `preparations_eligible`/`preparations_unrepresented`) instead of `Exact`. This fixed a sibling
  defect the campaign had not yet reached: with the real counted plan change
  (`aws_db_instance.postgres[0]`), destroy reconciliation refused it as *outside this phase's
  scope*. The declared block address still feeds `-target` and `guarded_addresses`.
- `Sol_cli_resource_identity` emits the concrete counted address for the resources whose address is
  actually read — the AWS RDS instance, subnet group and security group, and the GCP Loki/Thanos
  service accounts. The other counted entries are `external_by_contract` or `not_recoverable`, so
  ownership is classified before their address is read and they need no key.
- `internal/ci/check_resource_identity.py` now reads a registry address with a Terraform instance key
  and matches it to a root declaration by resource (`aws_db_instance.postgres[0]` accounts for
  `aws_db_instance.postgres`) — the same model INFRA-081 uses — so the FND-0070 cross-check accepts
  the counted form. Its mutation suite adds a counted entry that names no root declares.

**Tests.** `cli/test/inline/test_cloud_destroy.ml` adds `rds_of_state` coverage: the counted
address is recognised with its guard, a target with no database is `Ok None`, and an
`aws_db_instance` at an unexpected address is an error. `cli/test/inline/test_terraform_plan.ml`
adds the counted guarded-update case for both policies (create still refused during preparation,
delete still refused during reconciliation). The offline lifecycle fake now models the counted
state and plan addresses, and `internal/ci/context/test_cloud_lifecycle_offline.sh`'s
residue assertion follows; the full offline cloud lifecycle suite passes, including
`verify preparation: RDS deletion protection disabled`.

**Offline only.** No provider call was made and no live absence is claimed; live absence remains a
separately authorised qualification claim. **Demo/example:** none — provider lifecycle internals.
**Language parity (DEC-022):** none — no application-facing contract.
