The destroy path writes `terraform show -json <plan>`, including sensitive values, to the run log

**Depends on:** None.

Related (not a dependency): INFRA-074 review, HARDEN-004 step 3.

## Problem

`apply_asserted` (`cli/sol/bin/cmd_cloud_tf.ml`, HARDEN-004 step 3) runs
`Sol_cli_terraform.show_json_plan` inside `Sol_cli_run_log.run_phase ~name:(phase_name ^ "-show")`.
`run_phase` writes the phase's full stdout to `<XDG data>/sol/runs/<id>/<phase>.log`
(created with `open_out`, 0644 under a normal umask; 20 runs kept). A saved plan's
JSON carries sensitive values in plain text. The INFRA-074 reviewer confirmed with a
local terraform that a `sensitive = true` variable set through `TF_VAR_` appears in
`terraform show -json` output. So `db_password` reaches disk on the destroy path,
contrary to `cli/platform/infra/aws/main.tf`'s guidance to pass it via `TF_VAR_` because
Sol logs the command line.

## Remediation

Read the plan JSON outside `run_phase` (call `show_json_plan` directly) and record only
the classified changes (action + address) with `Sol_cli_run_log.append_phase_log`, as
INFRA-074 did for the cloud apply. Consider creating run-log files 0600.

## Acceptance criteria

- No `*-show.log` phase log contains plan JSON. A harness or unit check confirms that a
  `show -json` fixture's value never reaches a run-log file.
- Demo/example: not applicable — state in completion notes.

## Completion notes (2026-09-24)

Premise re-checked against `origin/main @ fd5c7e0c`: `apply_asserted`'s `show_plan`
still ran `Sol_cli_terraform.show_json_plan` inside
`Sol_cli_run_log.run_phase ~name:(phase_name ^ "-show")`.

- New `Sol_cli_terraform_plan.show_and_record ~run_log ~phase ~show` reads the
  plan JSON, classifies it, and appends only `<action> <address>` lines to the
  phase log. It returns the JSON to the caller.
- `Sol_cli_terraform.show_json_plan` is no longer exported. The only way to
  read a saved plan is `Sol_cli_terraform.show_saved_plan`, which always goes
  through `show_and_record`. A future caller therefore cannot route plan JSON
  through `run_phase`: the raw function is not in the interface. Both call sites
  use it: the destroy path (`apply_asserted`) and the cloud apply (INFRA-074's
  inline version, now replaced).
- Run-log phase files are created 0600, both `write_file` and `append_phase_log`
  (previously the umask default and 0644 respectively).
  `Sol_cli_run_log.create` takes `?base` so a test can use a temp directory.
- Checked the remaining JSON dumps: `output_json` and `show_json` are called
  directly and never inside `run_phase`
  (`grep -n "run_phase" cli/sol/bin/cmd_cloud_tf.ml`, then read each thunk).
- Tests (`test_terraform_plan.ml`, "show_and_record (SEC-008)"): a `show -json`
  fixture with a secret in `variables` and in `change.before` goes through
  `show_and_record` into a real run log. No file under the run directory
  contains the secret, every file is 0600, and the classified change is
  recorded. A malformed or failed show is an error.
- Mutation checks (each built and failed the intended test): appending the JSON
  to the phase log, and creating phase logs 0644.
- **Demo/example:** not applicable (internal CLI logging; no author-facing change).
- **Language parity:** no language-parity impact. This is CLI/platform
  behaviour, independent of the application language.
