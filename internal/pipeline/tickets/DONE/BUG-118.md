**Depends on:** None.

`Sol_cli_rollback.decode_workload` parses every other recorded field strictly and
fails closed, but the availability is lenient:

```ocaml
; availability =
    (match Sol_cli_availability.of_string w.availability with
     | Ok a -> a
     | Error _ -> Sol_cli_availability.Single)
```

A record whose `availability` is unparseable is reconstructed as `Single` instead
of being refused.

## Impact

A `node-failure-tolerant` workload renders a PodDisruptionBudget and
`validate_availability` admits persistent volumes under it. Restoring it as
`Single` drops the PDB and can admit a configuration the recorded release did not
choose, while the rollback reports success. The release record is digest-checked,
so reaching this needs a record written with a value a newer CLI does not
understand (a forward skew) or a hand-edited ConfigMap; either way the failure
direction is fail-open, which is the class `FND-0021`/`DEC-040` exist to close.
Every sibling decode in the same function (`cpu`, `memory`, `rollout`, volumes,
ingress) already fails closed naming the workload.

## Remediation

Parse it like the other fields: `Error _` becomes a
`reconstruct_error ~release_id ~workload:w.name` naming the offending value, so
the rollback refuses instead of silently choosing a weaker availability.

## Acceptance criteria

- A record with an unparseable `availability` makes
  `service_specs_of_release` return an `Error` naming the workload and the value.
- A record with a valid `availability` still reconstructs unchanged.
- The transaction's existing fail-closed tests stay green.
- Demo/example: none needed — this reconstructs an already-recorded release, not
  an author-facing surface. Language parity: OCaml and TypeScript share this
  reconstruction path, so one change covers both.
