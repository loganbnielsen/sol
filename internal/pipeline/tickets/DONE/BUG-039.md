**Depends on:** None.

**Related:** INFRA-023 (RDS destroy preparation, finding 9b — the review that
surfaced this), HARDEN-002 (`production-single-region/v1`'s durability
claims).

## Premise

Reviewing INFRA-023's targeted-apply mechanism before authorizing HARDEN run
3 raised a direct question: does an ordinary `sol cloud apply` reliably
restore `rds_deletion_protection` after a prepared-but-failed destroy? The
answer was yes, but only because nothing in `sol_cli_config.ml` ever asked
for `false` — Terraform's own variable default (`true`,
`cli/platform/infra/aws/variables.tf`) was doing all the work. Confirmed by
reading `sol_cli_config.ml`'s `terraform_vars`: `rds_multi_az` is forced by
profile (`is_production_postgres`), but `rds_deletion_protection` was never
mentioned there at all.

That means, before this fix, an **ordinary** `sol cloud apply --var
rds_deletion_protection=false` against a `production-single-region/v1`
target — no destroy involved — would leave a production RDS instance
unprotected indefinitely, and nothing in Sol would refuse it or restore
protection on a later apply. `rds_multi_az` already gets the profile
enforcement this contract needs; `rds_deletion_protection` did not.

## The invariant

For `production-single-region/v1`, deletion protection is a claim of the
*profile*, not a convention that happens to hold because nobody has
overridden Terraform's default. An operator-supplied `--var`/var-file value
must not be able to defeat it — the same standard already applied to
`rds_multi_az`.

## What changed

- `sol_cli_config.ml`: `terraform_vars` now includes
  `("rds_deletion_protection", "true")` when the target is
  `production-single-region` and declares a `postgres` resource — mirroring
  `rds_multi_az`'s condition (`is_production_postgres`), but **not** its
  unconditional-inclusion shape. `rds_multi_az`'s Terraform default is
  already `false`, so stating it for every target is a no-op;
  `rds_deletion_protection`'s default is `true`, so forcing a value for
  *every* target would have meant emitting `false` for every non-production
  target — silently weakening protection for exactly the targets not being
  fixed. The variable is only ever added for the production+Postgres case;
  every other target keeps relying on the same Terraform default it always
  has.
- Extracted the CLI-vs-profile ordering decision out of `cmd_cloud_tf.ml`
  and into `Sol_cli_config.vars_with_profile_precedence` — previously an
  inline `match` in `cloud_init`, untestable at the unit level (this repo's
  `bin/` modules aren't unit-tested; only `internal/ci/test_cloud_lifecycle_offline.sh`'s
  full-binary harness could have exercised it, and never did). Same logic,
  now a named, directly testable function: profile-derived vars go last
  when a profile is declared (so Terraform's last-`-var`-wins resolution
  picks them over any conflicting override), the caller's vars go last
  otherwise.
- `cmd_cloud_tf.ml`'s `cloud_destroy` is unchanged — it was already,
  independently, unconditionally `config_vars @ vars` (caller vars last),
  which is why `prepare_destroy`'s own explicit
  `rds_deletion_protection=false` (appended after everything else,
  `cmd_cloud_tf.ml`'s `prepare_destroy`) already won regardless of profile.
  Verified this holds with the new `rds_deletion_protection=true` in
  `config_vars` too: `-var=rds_deletion_protection=true` (from config_vars)
  followed later in the same argv by `-var=rds_deletion_protection=false`
  (from `prepare_destroy`) — Terraform takes the last occurrence, so the
  destroy-preparation exception is preserved by construction, not by adding
  a special case for it.

## Tests

`test_config.ml`:
- `terraform_vars` returns `rds_deletion_protection=true` for a production
  target with Postgres (mirrors the existing `rds_multi_az` test).
- A non-production target gets **no** `rds_deletion_protection` entry at
  all — not `false` — proving the asymmetry with `rds_multi_az` was applied
  correctly and no target regresses from the previous "rely on Terraform's
  default" behavior.
- `vars_with_profile_precedence` directly, simulating Terraform's own
  last-`-var`-wins resolution: with a profile, a conflicting
  `rds_deletion_protection=false` CLI override is defeated by the
  profile-derived `true`; without a profile, the CLI value wins, preserving
  full operator control for ordinary targets.

`internal/ci/test_cloud_lifecycle_offline.sh` (no fixture changes needed —
its target has no `profile:` declared, so it already exercises and
continues to prove the "no profile → unaffected" path) and
`cli/sol/test/check_production_infra.sh` re-verified green; both were
already covering INFRA-023's mechanism and needed no changes for this fix.
