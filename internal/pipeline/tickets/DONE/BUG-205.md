title: "An environment whose Terraform state does not exist yet is reported as unreadable, so a fresh target cannot be provisioned"

**Depends on:** None.

## What happened

`sol cloud plan qualalpha7/aws/us-east-1 --var-file …`, run with the **published**
`v0.1.0-alpha.7` bundle against a target whose state key has never been written
(`sol/qualalpha7/aws/us-east-1/cloud.tfstate` in the qualification bucket):

```console
[terraform-init] ok (4.3s)
$ terraform -chdir=… 'plan' '-var-file=…' '-var=cluster_name=sol-qual-alpha7' …
[terraform-plan] ok (7.6s)
error: terraform state list failed with exit 1
```

`terraform output -json` succeeds against that state (`{}`), the plan succeeds, and then the
*presence* check fails. Reproduced directly, on the same working directory and backend:

```console
$ terraform -chdir=… state list
No state file was found!                    # exit 1
$ terraform -chdir=… state pull >/dev/null; echo $?
0
```

## Mechanism

`Sol_cli_provider_registry.of_root` reads the outputs and then calls `state_holds_any`, which
calls `Sol_cli_terraform.state_list` and maps **any** non-zero exit to `State_unreadable`
(`"terraform state list failed with exit 1"`). Terraform's state-management commands refuse to
run when the backend holds no state file — and an environment that has never been applied is
exactly that case. "No state file" means *holds nothing*, which is the first-run answer to "is
the substrate present?", not a read failure.

Blast radius: `of_root` is called from `Sol_cli_environment_stage` and `Sol_cli_cloud_wiring`, so
every command that asks whether a target's substrate exists fails on a never-applied target —
`sol cloud plan`, `sol cloud apply`, `sol deploy`, and the destroy path. That is the whole
first-run surface `docs/guides/installation.md` documents.
`Sol_cli_installation_stage.state_addresses` carried the same gap.

The regression test never saw it because its fake `terraform` always answers `state list` with a
resource, so the never-applied case was untested.

## Fix

`Sol_cli_terraform.state_addresses` is now the single place that answers "which addresses does
this state hold": it lists them, and when `state list` fails it asks `terraform state pull` —
which succeeds for both an empty and a populated state — returning `[]` when the state exists
but is empty, and propagating the original error only when the state genuinely cannot be read.
Both call sites use it, so the elaboration lives in one place and a real read failure still
fails closed.

## Acceptance criteria

- The first-run test drives a target whose `terraform state list` fails with
  `No state file was found!`, and asserts the run is **not** reported as
  `terraform state list failed` and **does** reach `apply`. Verified to fail on the old code for
  exactly that reason, and to pass with the fix.
- A state that cannot be read at all (`state list` **and** `state pull` failing) still fails
  closed.

## Completion notes

Landed with the regression test in `cli/test/test_deploy_first_run.sh` (new scenario: "a
never-applied environment is provisioned anyway"; `state list` fails behind a `fresh-state`
marker while `state pull` succeeds, as it does on a real empty backend). Reverting the fix
fails that scenario for exactly the reported reason (verified by mutation: the run reports
`terraform state list failed` and never reaches `apply`). A second scenario drives both
`state list` and `state pull` failing behind an `unreadable-state` marker and asserts the run
still exits 1 without applying, so the fallback cannot swallow a genuine read failure.
`state_pull` stays private to `Sol_cli_terraform`; only `state_addresses` is exposed.

**BUG-094 is preserved, and its guard now models the new discriminator.** BUG-094 requires a
destroy whose state *cannot be listed* to refuse. "Cannot be listed" now means both `state list`
and `state pull` fail; an absent state file fails only `state list`. The offline lifecycle fake
(`internal/ci/lifecycle_fakes/terraform`) had no `state pull` case, so a read the backend refused
still answered success for the new probe and looked empty. It now fails `state pull` under the
same `STATE_LIST_FAILS=1` condition that fails `state list`, which is what a refused backend read
actually does, so the BUG-094 scenario still drives and asserts the refusal.

**Adjacent gap, not fixed here.** `cli/bin/cmd_uninstall.ml` still calls
`Sol_cli_terraform.state_list` and parses its stdout itself, so it carries the same
"never-applied backend is unreadable" shape on the uninstall path. That path was not part of
the provisioning surface this ticket demonstrates, so it is recorded rather than widened into
this fix.

**This blocks the alpha AWS qualification.** `v0.1.0-alpha.7` is published and immutable, so the
AWS run cannot provision a fresh target on it: the attempt stopped at the first `sol cloud plan`
with no resource created and nothing billed. The next candidate carries this fix; `HARDEN-007`'s
attempt section records that. Language parity: no application-facing contract change — the fix
is in the CLI's Terraform boundary.
