## The question

ADR 0003 invariant 2, `production-bootstrap.md` and matrix row I3 all state that
the steady-state provisioner "cannot manufacture a more powerful identity". On
AWS that is true of the Kubernetes RBAC layer but not of the *identity*: the
provisioner IAM policy grants `eks:*`
(`cli/platform/infra/bootstrap/main.tf:81`), which includes
`eks:AssociateAccessPolicy`, `eks:CreateAccessEntry` and
`eks:UpdateAccessEntry`. The same identity can therefore associate
`AmazonEKSClusterAdminPolicy` with its own access entry and obtain full cluster
administrator access through the EKS control plane at any time, with no Sol
action and nothing for a `kubectl auth can-i` probe to see.

The tension is structural rather than a coding slip: one identity is asked both
to build the cluster (which requires managing access entries) and to be the
bounded steady-state cluster-access identity (which must not be able to
escalate).

## Options

1. **Narrow the single provisioner.** Deny access-entry / policy-association
   mutations on the one identity. Rejected: the identity applies the cloud root,
   so an unconditional deny breaks its job; a conditional grant leaves the
   escalation path present for the window, which is the thing the invariant
   forbids.
2. **Split the identities (chosen).** One cloud-provisioning identity that owns
   `eks:*` and the GCP equivalents because it creates/updates the cloud
   substrate and the bootstrap access entry; one steady-state cluster-access
   identity assumed by the scoped platform paths, which must not hold
   `eks:AssociateAccessPolicy`, `eks:CreateAccessEntry`,
   `eks:UpdateAccessEntry` or `iam:*`.
3. **Accept and document.** Rejected: it leaves the invariant overbroad, so a
   reader or a probe would still report a boundary that is not there — the
   failure mode HARDEN-003 exists to prevent.

## Decision (2026-09-19) — Option 2, split the identities

Split provisioning authority from steady-state cluster access. This supersedes
ADR 0002's "no fifth identity" for the provisioning axis. It mirrors the deploy
policy's existing explicit `NoInfrastructureOrIdentityMutation` deny
(`cli/platform/infra/bootstrap/main.tf:141-154`), and it is the only shape in
which `INV-AUTH-4` / `INV-AUTH-5` can hold on AWS as well as GCP.

Implementation: **INFRA-046**.

## Acceptance criteria

- The steady-state cluster-access identity's IAM policy contains no
  access-entry / policy-association permission and no `iam:*`.
- An offline guard compares what the steady-state identity holds against what
  the provisioning path needs, so the over-grant cannot return unnoticed.
- ADR 0002, `production-bootstrap.md` and matrix row I3 state the split model,
  and no Sol document still claims the single provisioner "cannot manufacture a
  more powerful identity".
- A live probe records that the steady-state identity's attempt to associate a
  cluster-admin policy (or to create/update an access entry) is denied.
- INFRA-045 reconciles the GCP side to the same model, so the split is
  provider-neutral rather than an AWS-only fix.

## Consequences

- ADR 0002's identity table gains or re-scopes an identity, and the bootstrap
  root and lifecycle change accordingly.
- The qualification claim changes from "the provisioner cannot escalate" to "the
  steady-state identity cannot escalate" — a claim a run can actually falsify.
