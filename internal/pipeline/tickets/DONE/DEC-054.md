## Decision

**Decided 2026-09-27** by the operator, choosing option 1 (size the substrate to the platform) when
the question below was put with its tradeoffs. It is implemented as *the driver defaults adopt the
shape the profile already recommends*, not as a new sizing policy:

- `Sol_cli_profile.platform_capacity_envelope` already declares `min_vcpu_per_node = 4`,
  `largest_pod_vcpu = 2`, `platform_vcpu = 10` and `platform_memory_gib = 20`, and
  `recommended_node_shape` is `m6i.xlarge` **x 4**. The GCP driver defaulted to 3 x `e2-standard-2`
  (2 vCPU / 8 GiB, 1.93 CPU / 5.88 GiB allocatable) and the AWS driver to 3 x `m6i.large` — both
  below the profile's own per-node minimum, and both one node short of its headroom rule.
- So the defaults move to the recommended shape in each provider's own terms: GCP
  `node_machine_type = "e2-standard-4"` with `node_count = 4`, AWS `node_instance_types =
  ["m6i.xlarge"]` with `node_desired_size = 4`.
- `internal/ci/check_node_shape_fits_platform.py` (with its mutation test) holds the fit, reading the
  requirements out of the profile rather than restating them, and adding the one constraint the
  envelope does not yet carry: the loki chart's chunks cache asks 9.6 GiB allocatable, measured live
  in Attempt 16.
- The `Platform_capacity` preflight applies the envelope to `recommended_node_shape` — a constant —
  so it never saw the substrate actually being provisioned. That gap is **recorded, not closed** here:
  whether the preflight should also read the driver's declared defaults (and refuse before a run
  spends an hour) is its own decision, and `FND-0066` states it.
- The AWS half is inference from the platform's shared requests (no AWS run has reached a platform
  install); the first one that does confirms or refutes it.

## Question

Attempt 16 failed the full platform apply because two required pods ask for more than a single node
can hold, on the substrate the GCP driver declares by default:

| Pod | Request | `e2-standard-2` allocatable | Ratio |
|---|---|---|---|
| each `redpanda-*` (3 replicas) | `2000m` CPU | `1930m` CPU | 1.04 × a node |
| `loki-chunks-cache-0` | `9830Mi` memory | `6026Mi` memory | 1.63 × a node |

Adding nodes cannot help; the pod must fit *one* node. So the question is not "how many nodes" but:

> **What is the product's minimum node shape for the production profile, and who owns the number —
> the platform's declared requests, or the substrate's defaults?**

Both halves are currently declared in this repository and neither defers to the other: the platform
asks for `redpanda_cpu_cores = 2` / `redpanda_memory = "4Gi"` with three replicas, and the GCP driver
offers `e2-standard-2` x 3 (the AWS driver offers the same class, `m6i.large`). Loki's chunk cache adds
a request that is not declared here at all — it is the upstream chart's default, inherited because
Sol's values never mention `chunksCache`.

## Options considered (the remedy space)

The remedy space, with what each costs:

1. **Size the substrate to the platform.** `e2-standard-4` (4 vCPU / 16 GiB) fits both requests with
   little headroom; `e2-standard-8` (8 / 32) fits the platform's stated intent. Cost scales with the
   machine type; `SSD_TOTAL_GB` scales with `node_disk_gb` and is unaffected by the machine type.
2. **Bring the requests down to the substrate.** Lower `redpanda_cpu_cores` and/or override the loki
   `chunksCache` request. This changes what the platform asks any cluster for — a production contract
   change — and should be argued from the platform's sizing intent, not from what a cheap default fits.
3. **Both: state the product's minimum node shape, and let the qualification profile adopt it.**
4. **Something else**, including "the profile's declared node shape was never a product claim, and the
   qualification runs should size up deliberately" — which is a legitimate answer, but it should be
   *chosen* and written where the defaults live.

Ruled out, and worth recording as ruled out rather than tried:

- **Autoscaling or a larger node count.** A per-node fit failure is not a capacity failure; horizontal
  scaling cannot schedule a pod larger than a node.
- **A longer Helm timeout.** It changes how long the failure takes, not its cause.

**Explicit non-goals:** do not change the Helm timeout, do not add machine-type or node-count fallback
logic to provisioning, do not quietly lower the requests to make a run pass, and do not treat this as a
GCP-only question — the same arithmetic holds for the AWS driver's default, and the first AWS run that
reaches a platform install should be recorded as confirming or refuting it.

## Why this is a decision and not a fix

Every candidate changes the system under qualification rather than the qualification machinery: node
machine type and sizing, the platform's request profile, or the product's minimum-cluster contract.
Attempt 16's evidence establishes the failure; it does not select the remedy.

## Acceptance criteria

- The decision is recorded with its rationale and the arithmetic it rests on.
- Whatever is chosen is expressed **where the defaults live**, so the next reader does not have to
  re-derive the fit from a failed run.
- A fresh live GCP attempt reaches at least `Ready`, or fails past resource fit with these four pods
  scheduled.
- The AWS half is stated: either confirmed by a run, or recorded as inference from declarations with
  the reason it has not been observed.
