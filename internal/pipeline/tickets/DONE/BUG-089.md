Keep cross-domain caller ingress when deploying a callee alone

**Depends on:** None.

**Premise re-verified (2026-10-02):** At `origin/main` `c7762725` the premise held exactly: `of_services_result` derived each callee's `called_by` from `resolved_services` (the units this run selects), while the outgoing `calls` were already resolved against every loaded unit by `lookup_call`, and `sol_cli_deployment_render.render_spec` renders `called_by` as the NetworkPolicy's ingress peers. The existing tests exercised the full-plan and caller-selected cases only, which is what the 2026-09-29 verification at `2485a3af` recorded.

## Problem

Deploying only a callee excludes its unselected cross-domain caller from `called_by` and replaces the callee's NetworkPolicy without that ingress rule. The caller remains running, but its requests to the callee are denied by network policy. A full-workspace plan includes the edge; existing tests exercise only that case.

## Remediation

Derive incoming call edges from all declared workspace callers while keeping the rendered/deployed workload set limited to the requested scope. Preserve the existing rejection of calls to nonexistent targets.

## Acceptance criteria

- Render a callee-only scoped plan with a caller in another domain; its NetworkPolicy retains the caller namespace and pod selector, while the plan still deploys only the callee.
- A full plan renders the same ingress edge, and a misspelled call target fails closed.
- Verify the network-policy document emitted by the command path, not only the `called_by` list. Update a runnable cross-domain scoped-deploy example and record the per-language verdict.

## Completion notes

- **Incoming edges come from the workspace, the deployed set stays the scope.** The one line that
  derived `called_by` from `resolved_services` now derives it from `workspace_services` — every unit the
  workspace declares, the same material BUG-088 introduced for the consumer-group set, so the two halves
  of "a scoped deploy still knows the whole workspace" now agree. `plan.services`, and therefore what is
  rendered and applied, is untouched: a scoped deploy of a callee still deploys exactly the callee.
- **Nothing else moved.** `lookup_call` already resolved outgoing `calls` against every loaded unit and
  already fails closed naming the units on a misspelled target, so that behaviour is unchanged and still
  covered.
- **Coverage.** `cli/test/test_deployment_plan.ml` gains *a scoped callee keeps its cross-domain caller
  ingress (BUG-089)*: with `payments/charge_svc` selected, `orders/order_svc` in the inventory and calling
  it, and `~requested_scope:"payments"`, it asserts the plan deploys only `charge_svc`, extracts the
  NetworkPolicy document from the *rendered* workload (`Sol_cli_deployment_render.render_spec`, the
  renderer the command path uses) and requires the caller's namespace
  (`kubernetes.io/metadata.name: myworkspace-orders`) and pod selector (`app: order-svc`), then renders the
  full plan and requires the identical policy. The fail-closed case is the pre-existing
  `test_unknown_service_call_fails_and_names_the_units`.
- **Mutation check.** Reverting the derivation to `resolved_services` fails the new case on the *document*
  assertion — "the rendered network policy allows the caller's namespace" — rather than only on the
  `called_by` count, which is the criterion's point; restored, rebuilt and re-run green (89 cases).
- **Demo/example.** `examples/pluto/README.md` — the reference workspace, whose `payments/charge_svc`
  really does call `checkout/checkout_svc` — now shows
  `sol deploy pilot/aws/us-east-1 --scope checkout --dry-run` and states that the rendered NetworkPolicy
  still admits `payments/charge_svc`, so the example is runnable against a workspace in the tree. The
  `--scope` block in `docs/guides/TUTORIAL.md` carries the same sentence where a user learns the flag.
- **Language parity (DEC-022).** No application-facing impact: cross-domain calls and the NetworkPolicy
  they render are workspace metadata and platform rendering, treated identically for OCaml and TypeScript
  applications. No tracking ticket needed.
