Preserve External Secrets selection in emitted GitOps artifacts

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `cli/bin/cmd_deploy.ml:176,298,499; cli/lib/deploy/sol_cli_factory.ml:29; cli/lib/deploy/sol_cli_executor.ml:81` and representative callers/tests at origin/main `6eb36b2c`. The audit records reproduced behavior, positive controls and practical limits.

## Problem

The CLI accepts External_secrets and dry-run renders the chosen ExternalSecret/store. Actual Emit_to execution unconditionally replaces the selected backend with Kubernetes_placeholder, emitting an ordinary blank Secret. Applying the artifact prevents ESO from supplying credentials and can overwrite existing values with blanks. Preview and actual output disagree while both exit successfully.

## Remediation

Preserve safe External_secrets and Kubernetes_placeholder backend choices through emission. Reject Kubernetes_live at the shared artifact boundary rather than overriding every backend. Keep CLI and library callers on the same safety contract.

## Acceptance criteria

- The same deploy command in dry-run and actual --emit-to preserves ExternalSecret kind, store reference, key prefix and refresh interval, with no ordinary Secret for that workload. Kubernetes_live cannot emit plaintext. Add a shared executor regression and update a runnable GitOps/ESO example; record no language-specific application-contract divergence.
- Completion notes identify runnable example/demo coverage and the per-language capability verdict, or explain why either is not applicable.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `788e688d`: `Sol_cli_executor.run_plan` computed `backend` as `Emit_to _ -> Kubernetes_placeholder | Dry_run | Apply -> secret_backend`, so an emit discarded the caller's `External_secrets` selection (which `sol deploy` had already resolved and passed through `Sol_cli_factory.execute`) and rendered an ordinary blank Secret; `Sol_cli_executor.gitops` had the same emit path.
- **Fix.** A shared `artifact_backend` boundary now returns `External_secrets`/`Kubernetes_placeholder` unchanged and refuses `Kubernetes_live` with a named error; both `run_plan`'s `Emit_to` branch and `gitops` use it, while `Dry_run`/`Apply` keep passing the backend through. CLI and library callers therefore share one safety contract, and preview and actual emit agree.
- **Tests** (`cli/test/test_executor.ml`, `gitops` group, with a spec carrying two secrets): `External_secrets { store_ref = "probe-store"; store_kind = "ClusterSecretStore"; key_prefix = "myapp/"; refresh_interval = "1h" }` emits `kind: ExternalSecret` with the store ref, `key: myapp/DATABASE_URL` and `refreshInterval: 1h`, and no `kind: Secret`; `Kubernetes_live` returns an `Error` naming `kubernetes-live` and writes nothing; `Kubernetes_placeholder` still emits a `kind: Secret` and no ExternalSecret. **Mutation-checked**: forcing the backend back to `Kubernetes_placeholder` fails the ExternalSecret case while the fix passes. 10 executor tests pass, plus the related suites (`test_deployment_phases` 51, `test_manifest_render` 156, `test_release` 26, `test_factory`, `test_change_set`, `test_deploy_run`, `test_secret_strategy`, `test_env_target`, `test_deployment`).
- Validation: full `dune build`; `dune fmt --preview` and `check_no_comments.sh` clean.
- **Runnable example**: `docs/guides/TUTORIAL.md` § GitOps deploy now shows the `--emit-to` command with `--secret-backend external-secrets --secret-store-ref --key-prefix` and states that `kubernetes-live` is refused for an emit; `docs/architecture/devops-pipeline.md` records the same contract. **Language parity: no divergence** — the secret-backend selection is a CLI/manifest contract rendered identically for OCaml and TypeScript workloads, so no per-language behavior changed.
