**Related (not dependencies):** FEAT-118 (the `Ack | Fail` alignment that removes

TypeScript DLQ routing this names the destination of).

## Problem

The two implementations of the canonical consumer-group segment disagree, so a
TypeScript worker and an OCaml worker on the same logical group dead-letter to
**different topics**. The contract is defined once
(`internal/specs/framework-conventions.md` § DLQ) and pinned by the OCaml tests
(`framework/ocaml/kafka-eio-service/test/test_kafka_service.ml:332-360`):

- OCaml (`framework/ocaml/kafka-eio-service/lib/kafka_service_dlq.ml:29-57`)
  **always** appends `-` + the first 12 hex of MD5 of the original group id, on
  every id, and truncates the readable prefix to 51 characters when it is long.
- TypeScript (`loganbnielsen/sol-kafka`, `src/retry.ts:111-117`, `origin/main`
  `3956fea`) appends a hash **only when the sanitized id exceeds 64 characters**,
  and then the first **8** hex of MD5.

Observed names, computed from the two rules (commands in the audit, § 7):

| group id | OCaml DLQ topic | TypeScript DLQ topic |
|---|---|---|
| `payments` | `orders.payments-84d5eaf713c9.dlq` | `orders.payments.dlq` |
| `sol-demo-ts-fulfillment-worker` | `orders.sol-demo-ts-fulfillment-worker-a239c8cce37d.dlq` | `orders.sol-demo-ts-fulfillment-worker.dlq` |

The TypeScript test that is titled "match the OCaml naming" asserts the
divergent values (`sol-kafka@3956fea`, `test/retry.test.ts:64-67`), so the suite
currently pins the bug rather than catching it.

The consequence is cross-language interop: an operator or a DLQ reader watching
the contract name sees only one language's undecodable records, and the two
languages cannot share a DLQ. This diverges from `Sol`'s own OCaml side and from
ADR/DEC-022's requirement that the same resolution hold in both languages.

**Premise checked 2026-10-02** against `sol-kafka@3956fea` (`origin/main`):


Positive control: the same search over the OCaml `Kafka_service_dlq` finds the
always-hash rule it does not match.

## Remediation

In `loganbnielsen/sol-kafka`'s `src/retry.ts`, make `canonicalGroupSegment`
match the OCaml rule exactly:

- sanitize the group id to `[A-Za-z0-9-]`, empty → `unscoped`;
- compute the first 12 hex of MD5 of the **original** group id;
- truncate the readable prefix so that `prefix + "-" + hash` is at most 64
  characters (i.e. prefix ≤ 51), then **always** append `-` + the hash.

Update `test/retry.test.ts` so the fixtures assert the OCaml names
(`orders.payments-<12 hex>.dlq`, etc.) and add the boundary cases the OCaml suite
has: an empty group id, punctuation variants producing distinct topics, and a
200-character group id staying deterministic and under Kafka's 249-byte limit.
This is the naming rule FEAT-118 must satisfy when it rebuilds DLQ publication,
so land it before or with that work rather than re-deriving it there.

## Acceptance criteria

- `canonicalGroupSegment` and `relayTopicName` produce the OCaml names for at
  least the fixtures the OCaml suite pins, asserted by a test whose values were
  computed independently of the code under test.
- A TypeScript worker's undecodable record and an OCaml worker's on the same
  source topic and group id resolve to the same DLQ topic name.
- The `test/retry.test.ts` case titled "match the OCaml naming" asserts the
  hashed names instead of the bare sanitized ones.

**Demo/example coverage:** the `examples/pluto/app/demo_ts` worker pins
`@sol-fab/kafka`; bump the pin once the package is released so the demo runs
against the corrected naming.

**Language parity:** this ticket *is* the parity fix — it brings the TypeScript
implementation of a convention into line with the OCaml one.

## Done (2026-10-02)

**Premise checked before starting.** Re-verified at `sol-kafka@3956fea`: the
conditional `hashSuffix` branch and `.slice(0, 8)` described above were present,
and `test/retry.test.ts` still asserted `orders.payments.dlq` under a title
claiming to match the OCaml naming. Premise held.

**What landed.** `loganbnielsen/sol-kafka#3` (merged `b311e93`) changes
`canonicalGroupSegment` to append `-` + the first 12 hex of MD5 of the original
group id on **every** id, truncating the readable prefix to 51 characters so the
whole segment stays at 64 — matching
`framework/ocaml/kafka-eio-service/lib/kafka_service_dlq.ml:29-57`.
`relayTopicName` and `provisionRelayTopics` inherit the corrected segment, so a
TypeScript and an OCaml worker on the same source topic and group id now compute
the same DLQ topic. The stale `kafka_service_retry_topics.ml` references
(removed from Sol by FEAT-113) and the README's description of the rule were
corrected in the same change.

**Checks run.** In a `sol-kafka` worktree at `origin/main`: `npm test` → 60
tests, 0 fail (4 skipped: broker-bound integration); `npm run build` (`tsc`) →
clean. The new fixtures were computed independently with `python3 hashlib.md5`.

**Demo/example coverage.** `examples/pluto/app/demo_ts` already pins
`@sol-fab/kafka@^0.3.0`, and the npm `latest` is `0.3.0`; the fix reaches the
demo through the next `@sol-fab/kafka` release under the existing caret range,
with no pin or code change. `sol-kafka` is released by its own OIDC publish
workflow, so the release is the remaining operational step, not a code one.

**Language parity.** This is the parity fix for DLQ naming. It survives FEAT-118:
that ticket removes the retry relay but keeps decode-failure DLQ publication, so
the canonical-group rule this pinned is the one its new code must satisfy.
