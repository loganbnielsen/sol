**Depends on:** None.

**Premise (verified 2026-10-04 at `9c59d4be`):** holds. `Sol_outbox.Make(E).relay` scans
`oldest_per_key`, which has no `kind` predicate, and `drain` publishes and deletes every row it
reads through the injected `publish` callback. `E.kinds` is consulted only by
`Make(E).publish` (the enqueue side), never by the relay (the drain side). The reference
workspace declares its events in one `sol_outbox` table and runs one relay per unit, so every
relay drains every kind.

`Order_placed` and `Order_fulfilled` (`examples/pluto/events/orders/`) have identical fields
and identical `encode`/`decode`, so a relay that owns one decodes the other's payload
successfully and publishes it to its own topic. On the local k3d cluster, one `POST /orders`
for `qual-b6-20261004052530` produced two records on **each** topic, both carrying the same
`correlation_id` and the same bytes:

```console
$ timeout 8 rpk topic consume orders.v1 -o start | grep qual-b6-20261004052530
  "key": "qual-b6-20261004052530", "value": "...{\"order_id\":\"qual-b6-20261004052530\",...,\"correlation_id\":\"4bc5fdd2\"}"
  "key": "qual-b6-20261004052530", "value": "...{\"order_id\":\"qual-b6-20261004052530\",...,\"correlation_id\":\"4bc5fdd2\"}"
$ timeout 8 rpk topic consume orders-fulfilled.v1 -o start | grep qual-b6-20261004052530
  "key": "qual-b6-20261004052530", "value": "...{\"order_id\":\"qual-b6-20261004052530\",...,\"correlation_id\":\"4bc5fdd2\"}"
  "key": "qual-b6-20261004052530", "value": "...{\"order_id\":\"qual-b6-20261004052530\",...,\"correlation_id\":\"4bc5fdd2\"}"
```

The worker's own log shows the same key delivered twice as `OrderPlaced` — the second delivery
is the `OrderFulfilled` payload that the *service's* relay decoded as `OrderPlaced` and wrote
back to `orders.v1`. The domain-row, job and effect dedupe absorbed both deliveries (one
`fulfilled_orders` row), which is why B6's only failing assertion was the fact count: the
duplicate is at the publication layer, not at the effect layer. The checkpoint's leading
hypothesis — that relay deletion removes a durable dedupe memory and a redelivered
`OrderPlaced` recreates the intent — is falsified: `Fulfilment_worker.handle` gates the intent
on `inserted` from `Orders.insert_fulfilled`, so a redelivered fact never re-enqueues
`OrderFulfilled`.

The TypeScript half does not have the defect:
`examples/pluto/app/demo_ts/order_svc/src/index.ts` refuses a publication whose `kind` is not
the one it owns before decoding. `@sol-fab/outbox`'s `runRelay` is structurally kind-blind
exactly like the OCaml relay, so the guard lives in the caller there.

## Remediation

`Sol_outbox.Make(E).relay` drains only the kinds in `E.kinds`: `Q.oldest_per_key` gains
`kind = ANY(string_to_array(?, ','))` and `drain` passes `String.concat "," E.kinds`. A row of
another kind stays in place for its owner's relay; the per-key minimum subquery is left
unfiltered, so a relay still cannot publish a key's later event before an earlier one of
another kind. The library spec (`sol-outbox.md`) becomes "one logical relay owner per kind".

## Acceptance criteria

- A relay built from one `E` publishes and deletes only rows whose `kind ∈ E.kinds`; a row of
  another kind stays pending, and a second relay owning that kind drains it.
- `framework/ocaml/sol-outbox/test/test_sol_outbox.ml` proves it (`a relay publishes only the
  kinds it owns`) and fails on the old scan for the reason under test.
- Demo/example coverage: `examples/pluto`'s OCaml relays now behave as their callers already
  assumed, and `internal/fixtures/venus` is unaffected; no example source change is needed
  because the fix is below the example.
- Language parity: no observable change — the TS relay's callers already refuse foreign kinds,
  so the two languages already agreed on the behaviour; the OCaml library now enforces it too.
