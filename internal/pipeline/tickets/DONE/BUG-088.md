Preserve workspace consumer groups through scoped deploys

**Depends on:** None.

**Premise re-verified (2026-10-01):** At `origin/main` `9b0e272a` the premise held in every particular that mattered: `of_services_result` derived `consumer_groups` from `resolved_services`, the units the run selects, at the plan record; and both commands checked that list *before* taking the workspace boundary lease (`cmd_deploy.ml:617`, `cmd_up.ml:378`) and then recorded it under the lease. The 2026-09-29 verification at `2485a3af` was correct.

## Problem

A normal scoped deploy of worker A reports unchanged worker B as a removed consumer group and refuses. Confirming the change writes only A to the workspace guard record, although B remains live. A later change removing B can then bypass the warning. Both commands check the group state before taking the workspace lease, so the check can also become stale before apply.

## Remediation

Compare against and record the complete post-deploy workspace consumer-group set for scoped operations, preserving unaffected groups. Perform the check and state transition under the workspace boundary lease so the decision and apply share one state epoch. Keep explicit confirmation for actual group removals and unreadable-state behavior.

## Acceptance criteria

- With A and B recorded, scoped updates of A and of a non-worker unit succeed without confirmation and leave both groups recorded.
- A real removal of B requires `--confirm-group-change` and, after confirmation, records the new complete set.
- An intervening update between command start and lease acquisition cannot make the check use stale group state.
- Exercise both `sol up` and `sol deploy` command paths. Update a runnable scoped-deployment example or tutorial and record the cross-language verdict.

## Completion notes

- **The plan carries the workspace's complete post-deploy group set.** `of_services_result` now derives
  `consumer_groups` from `collect [] loaded` — every unit the workspace declares — rather than from the
  selected ones. For a full deploy that is the same list as before; for a scoped deploy it is the set that
  exists after the run, which is what a workspace-wide guard record means. Deriving it from the loaded units
  (rather than from a union with the recorded set) is what keeps a real removal detectable: a group whose
  worker is gone from the workspace is still reported, while a worker that is merely not selected is not.
- **One guard, called from inside the lease in both commands.** The two per-command copies are replaced by
  `Sol_cli_deploy_run.confirm_consumer_groups`. `sol deploy` runs it in `apply`, immediately after
  `ensure_held` and before the boundary read and any apply; `sol up` runs it in the epoch's
  `read_boundary_holding`, whose parameter *is* the held lease, so a pre-lease check is no longer expressible
  against the code that ships — the ordering BUG-087 established and tested. Neither command reads the record
  before acquiring the lease any more.
- **The refusal text is unchanged for the operator.** `removed_groups_message` no longer embeds its own
  `error:` prefix, because both paths now reach the operator through the run's `run_failed`, which adds
  exactly one; the unreadable-record refusal gains the same prefix it previously lacked. The unreadable-record
  policy is untouched: refuse, unless `--confirm-group-change` was passed, which warns and proceeds.
- **Coverage.** `cli/test/test_deployment_plan.ml` (88 cases): a scoped plan
  (`~requested_scope:"comms"`, `~inventory:[notify; charge]`, `[notify]` selected) carries both workers'
  groups; a workspace that no longer declares the second worker reports only the first. `cli/test/test_deploy_run.ml`
  (5 cases): against a fake `kubectl` that logs every call and echoes the boundary lease back,
  `Sol_cli_deploy_run.apply` refuses a record the plan no longer carries, and the log shows the recorded groups
  read *after* the boundary lease is written with no `apply` at all — the shipped `sol deploy` path run through
  the real guard. `test_deployment_state.ml` (12 cases) still covers the guard mechanism, the unreadable
  record, the failed write and the corrected hazard text; `test_boundary_epoch.ml` (3 cases) covers the
  ordering `sol up` now relies on.
- **Mutation checks.** Reverting the derivation to `resolved_services` compiles and fails
  "a scoped plan carries the whole workspace group set"; hoisting the guard above `with_boundary_lease` in
  `apply` compiles and fails "the record is read under the boundary lease" (the run refuses before the lease
  exists — the staleness the criterion names). Both mutations restored, rebuilt and re-run green.
- **Command paths, recorded rather than claimed.** `sol deploy`'s path is driven by the new
  `test_deploy_run.ml` case. `sol up`'s wiring is compile-checked and its ordering is the epoch's tested
  contract, not driven end to end: `sol up` builds images and needs a local cluster, so this repository has no
  offline harness for it, and the shared guard helper means the decision itself is one tested function.
- **Demo/example.** No `sol.toml` field, framework primitive or generated manifest changes. The user-facing
  behaviour is documented where a user learns `--scope`: the `# --scope` block in `docs/guides/TUTORIAL.md`
  now states that a scoped deploy compares and records the workspace's complete consumer-group set, and that
  the record is read under the lease; `docs/guides/deployment.md`'s flag list says the same beside `--scope`
  and `--confirm-group-change`. No new runnable example was needed.
- **Language parity (DEC-022).** No application-facing impact: the guard, the plan's group set and the lease
  ordering are CLI-side and language-neutral, so OCaml and TypeScript workspaces are treated identically. No
  tracking ticket needed.
