**Depends on:** None.

## The defect

A target's `terraform_var_file` is passed to Terraform after `normalize_var_file` in `cli/bin/cmd_cloud_tf.ml`:

```ocaml
let normalize_var_file path =
  if Filename.is_relative path then Filename.concat (Sys.getcwd ()) path else path
```

So a relative path means something different depending on where `sol` was run from. That contradicts DEC-024 clause 4, as `Sol_cli_config` states it: "Config and target paths resolve relative to the resolved workspace root, not the invocation cwd, so `sol plan`/`sol deploy` work from any descendant directory."

## Evidence

Pluto's `dev` and `customer_cloud` targets (before REFAC-105) set `terraform_var_file: ../../../../../internal/qualification/aws/smoke-test.tfvars`. That path was clearly written relative to the target file's own directory:

```
$ cd examples/pluto && realpath -m ../../../../../internal/qualification/aws/smoke-test.tfvars
/home/logan/internal/qualification/aws/smoke-test.tfvars          # does not exist
$ cd sol/dev/aws && realpath -m ../../../../../internal/qualification/aws/smoke-test.tfvars
/home/logan/Code/sol-cloud/sol-REFAC-105-pluto/internal/qualification/aws/smoke-test.tfvars   # exists
```

`sol cloud apply dev/aws/us-east-1` run from the workspace, which is how `live-smoke.sh` invoked it, would have handed Terraform a var file that doesn't exist. REFAC-105 removed that reference, but not the resolution rule.

## Remediation

- Resolve a relative `terraform_var_file` against the **workspace root** (`Sol_cli_config.workspace_root ()`), not `Sys.getcwd ()`. That is the rule DEC-024 clause 4 already applies to config and target paths.
- Leave absolute paths unchanged.
- **Keep the `--var-file` CLI flag cwd-relative.** `cmd_cloud_tf.ml:1667` defines `--var-file`, and when it's given it replaces the target's key (`match var_file with Some _ -> var_file | None -> config_var_file`, around line 1000). Today both go through the same `normalize_var_file`. A path typed on the command line is conventionally relative to the shell, so it stays cwd-relative. Resolve the two separately, before they are merged, so the rule depends on where the path came from.
- Document the rule where `terraform_var_file` is documented (`docs/reference/substrate.md` or its successor under `docs/reference/`).

## Acceptance criteria

- A test runs from a *subdirectory* of a workspace and shows that a target's relative `terraform_var_file` resolves to `<workspace-root>/<path>`, and that an absolute path passes through unchanged.
- A test shows a relative `--var-file` still resolves against the invocation directory.

## Completion notes

- **Premise re-verified (2026-09-25, `origin/main` `67bdef8e`):** `normalize_var_file` in `cli/bin/cmd_cloud_tf.ml` concatenated a relative path with `Sys.getcwd ()` for both the flag and the target key.
- **Fix.** `Sol_cli_terraform_vars.var_file ~cwd ~workspace_root ~flag ~target` is a pure function holding the rule:
  - the `--var-file` flag wins and is relative to `cwd`;
  - a target's `terraform_var_file` is relative to the workspace root (DEC-024 clause 4);
  - absolute paths are unchanged.

  `cmd_cloud_tf.ml`'s two call sites (apply/plan and destroy) resolve through it *before* the two sources are merged, and `normalize_var_file` is removed. The workspace root comes from `Sol_cli_workspace.find_root`, falling back to `cwd` outside a workspace.
- **Tests:**
  - **Unit:** `test_config.ml` "var file resolution (BUG-057)" covers target-relative, flag-relative, flag-wins, absolute passthrough and none.
  - **End to end:** a new scenario in `internal/ci/test_cloud_lifecycle_offline.sh` runs the real binary's `sol cloud plan` from `app/deep/`, a subdirectory of the workspace, and asserts the exact argument the fake `terraform` receives: `-var-file=<workspace>/vars/bug057.tfvars` for the target key, and `-var-file=<workspace>/app/deep/flag.tfvars` for `--var-file flag.tfvars`, with the flag winning.
  - **Positive control:** the same harness against the old `cmd_cloud_tf.ml` fails that scenario, with Terraform receiving `-var-file=…/work/app/deep/vars/bug057.tfvars`, exactly the defect.
- **Docs:** `docs/guides/TUTORIAL.md` now states both rules next to its `--var-file` example. No other user doc describes `terraform_var_file`.
- **Verified:** `dune build` and `dune test cli/test/` pass (0 `[FAIL]`); the offline lifecycle harness passes; the format check is clean.
- **Demo/example:** after REFAC-105 none of pluto's targets set `terraform_var_file`; the tutorial text is the user-facing reference. **Language parity (DEC-022):** no application-facing impact.
