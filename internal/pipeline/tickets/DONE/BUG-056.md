`sol up` builds its plan without the resolved `sol.yml`, so it renders different manifests than `sol deploy` for the same workspace

**Depends on:** None.

**Premise verified 2026-09-24** on `origin/main`: `local_plan` called
`of_services_result` with no declared configuration, while `sol deploy` passed
one. **Re-verified 2026-09-27** on `origin/main` `c9564314` (paths moved since,
by REFAC-139): `Sol_cli_up_execution.local_plan` still omitted it, and the
divergence is visible in rendered output -- see **Completion notes**.

## Problem

Everything `of_services_result` reads from the resolved `sol.yml` is absent under
`sol up`: each service's declared `language` (`sol_yml_language`), its replica
override (`sol_yml_replicas_override`), and its declared resource use, which feeds
`derive_consumer_groups`. So a workspace deployed locally is rendered from less
information than the same workspace deployed to a target. That breaks "dev mirrors
prod exactly".

It surfaced in INFRA-073 part B. The readiness path depended on the declared
language, and the TypeScript golden-path smoke (`sol up --scope=demo_ts` on
`examples/pluto`, whose `sol.yml` declares `language: typescript`) rendered
`order_svc` as language-less. Its pods were probed on `/readyz`, got 404, and never
became ready (CI run 36038850472). INFRA-073 now treats an undeclared language as
unknown (`/healthz`), which is correct regardless. The divergence remains.

## Remediation

Resolve the workspace `sol.yml` in `sol up` the same way `sol deploy` does (the local
target's defaults), and pass it to `of_services_result`. Check what else changes for
existing local workspaces: replica overrides and consumer groups now apply locally.

## Acceptance criteria

- Test: for one workspace, the service specs from `sol up`'s plan and from
  `sol deploy`'s plan agree on language, replicas and consumer groups.
- A pluto OCaml `-svc` rendered by `sol up` gets its declared language (and so
  `/readyz`).
- Demo/example: the local demo is unchanged or the change is noted in the completion
  notes.

## Completion notes

**Premise re-verified (2026-09-27, `origin/main` `c9564314`).** The bug had moved
with REFAC-139 but was intact, and rendered output shows it directly: the same
copy of `examples/pluto`, `sol up --dry-run` before and after this change --

```text
before (origin/main)                      after (this branch)
  charge-svc    readiness=/healthz          charge-svc    readiness=/readyz
  checkout-svc  readiness=/healthz          checkout-svc  readiness=/readyz
  order-svc     readiness=/healthz          order-svc     readiness=/healthz   (TypeScript, unchanged)
```

-- every OCaml unit was probed on the path its declared language does not use.
Not a *shape* problem: `sol up` had no configuration to plan from at all.

**What landed.**

- `Sol_cli_config.declared` — the part of a configuration a plan actually reads:
  the services `sol.yml` declares (with their language, scale range and resource
  uses) and the resources themselves, plus the profile a resolved target
  selects. With `declared_of_config : t -> declared` (what `sol deploy` supplies,
  the same facts it always passed) and `load_declared ~root` (what `sol up`
  supplies: sol.yml alone, so no profile — a profile is selected by an
  environment or a target, never by sol.yml, DEC-026).
- `of_services_result` and the factory take `?declared:Sol_cli_config.declared`
  in place of `?resolved_config:Sol_cli_config.t`, and the five helpers that read
  it (replica override, language, resource use, workload capabilities, profile
  claim) are unchanged in behaviour. The narrowed type is the point: it is what
  the plan reads, so every deployment mode can supply it, and a mode that cannot
  (there is no local `provider` to put in a `target`) is no longer able to pass
  nothing silently.
- `sol up` resolves it at the command edge beside the workspace model
  (`Sol_cli_config.load_declared ~root`) and threads it into the plan, so a local
  plan now carries the declared language (`/readyz` for a declared OCaml `-svc`),
  the `sol.yml` scale override, and the resource uses that derive consumer
  groups.

**Behaviour changes, stated rather than discovered later.** A local plan now
carries what `sol.yml` declares, which changes what `sol up` renders for any
workspace that declares it: an OCaml unit gets the `/readyz` readiness probe its
language implies (before, every unit looked undeclared and got `/healthz`); a
`scale:` range overrides sol.toml's `replicas` locally as it already did against
a target; and a worker that `uses:` the declared kafka resource now gets its
consumer group locally, so `sol up`'s consumer-group-change guard sees the same
set a deploy would. For a workspace that declares none of these -- pluto's
replicas come from sol.toml and it declares no scale range -- the rendered output
is unchanged apart from the probe path.

Nothing else was in scope: `omit` is a *target* declaration ("not in this
target's default set", DEC-041), so a local plan with no target has nothing to
omit and the selection is unchanged.

**Tests.** New `cli/test/test_up_plan.ml` (4 cases) builds one fixture workspace
and plans it both ways, which is the acceptance criterion: the two plans agree on
language, replicas and consumer groups; the local plan's declared facts are
really there (`scale: { min: 3 }` beating sol.toml's `replicas = 2`, a worker
using kafka getting `ws.comms.notify_worker`); a local plan renders
`/readyz`/`/healthz` for its declared OCaml service; and a workspace that
declares nothing still plans, as unknown, with no consumer group. **Checked
non-vacuously** rather than assumed: with the declared facts dropped inside
`local_plan`, three of the four fail with `language: Expected "ocaml", Received
"<none>"`; restored, all four pass. The stale comments that recorded "this is
what `sol up` renders for every service today (BUG-056)" in
`sol_cli_deployment_render.ml` and `test_manifest_render.ml` are updated.

The whole CLI suite (84 suites, 0 failures), `dune build`,
`check_ocamlformat.sh --all`, the full `internal/ci/test_*.sh` mutation suite and
the affected guards (`result_syntax`, `library_output`, `single_runner`,
`manifests_are_values`, `examples_self_contained`) all pass.

**Demo/example: the local demo is unchanged** (`internal/fixtures/local-demo` is
run through `dune exec`, not `sol up`). `examples/pluto` is a real local
workspace, and its `sol up` output changes exactly as described above -- the
probes in the table at the top of these notes are from a copy of it, so its
rendered manifests are the evidence rather than a separate example. No new
`sol.toml` field, command or manifest shape, so the `example-dockerfile-smoke`
matrix is untouched.

**Language parity: an improvement, not a new obligation.** The declared language
was already the plan's input for a target; local now reads the same declaration
instead of rendering every workload as language-less. No contract changes: no
wire format, retry/DLQ, metric vocabulary, lifecycle or secrets surface moves,
and nothing infers a language from build metadata (DEC-022 §7).
