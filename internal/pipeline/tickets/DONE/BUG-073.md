Accept request bodies exactly at the configured maximum

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `framework/ocaml/sol-svc/lib/service.ml:40-56` with callers and existing tests at origin/main `2dfa5694`. Evidence and reproduction limits are recorded in the source audit.

## Problem

Passing max_body_bytes as Eio Buf_read max_size makes take_all reject a body exactly equal to the maximum: EOF detection requests one additional byte. The public contract rejects requests exceeding the limit, not requests equal to it.

## Remediation

Use a bounded read that can distinguish exactly N bytes from N+1 and explicitly enforce the public length limit. Keep memory bounded and handle numeric edge cases instead of blindly overflowing N+1.

## Acceptance criteria

- HTTP fixed-length and chunked tests accept N-1 and N bytes, reject N+1 with 413 before the handler, and preserve empty-body behavior. Record that this corrects the OCaml implementation to the existing language-neutral limit contract; existing demo remains applicable.
- Record the application demo and per-language verdict in completion notes wherever the change affects an application contract.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `788e688d`: `read_body_limited` read with `Eio.Buf_read.of_flow body ~max_size:max_bytes` and `take_all`, and the audit's own probe showed `max_size=50` rejects a 50-byte body (accepted lengths stop at `max_size - 1`), so exactly-at-the-limit requests were refused with 413.
- **Fix.** The bounded read now uses `probe_limit = max_bytes + 1` (guarded against `max_int` overflow) so the EOF probe can distinguish exactly N from N+1, and the decoded string is length-checked against `max_bytes` before it is returned. The `content-length` pre-check and everything downstream (`body_result` → `Response.payload_too_large` → 413) are unchanged.
- **Tests** (`framework/ocaml/sol-svc/test/test_service.ml`, live HTTP against the real server, `max_body_bytes=50`): fixed-length bodies of 49 and 50 return 200 with the body echoed intact and 51 returns 413; an empty body returns 200 with an empty echo; a raw **chunked** request (no `content-length`, so only the Eio read limit applies) returns 200 at 50 bytes and 413 at 51. **Mutation-checked**: setting `probe_limit` back to `max_bytes` fails the exact-limit case, so the test catches the regression. All 32 service tests pass.
- Validation: `dune fmt --preview` clean; no-comments policy holds.
- **Demo/example and language parity**: no new framework primitive or convention; the change corrects the OCaml body-limit implementation to the existing language-neutral contract (`max_body_bytes` accepts exactly N, rejects N+1). The existing Pluto/demo services stay applicable and needed no edit; there is no TypeScript `-svc` body-limit divergence to reconcile, so no parity impact.
