**Depends on:** None.

## The problem

`sol_cli_dockerfile` (`cli/bin/cmd_migrate.ml`) runs `opam pin add obs-eio …#main`, and the same for `obs-loki-eio` and `pg-eio`. A runner built today from an old checkout gets today's support libraries, not the ones that checkout was built and tested with.

## Finding: the checkout has no authoritative record of the CLI's support-library revisions

Checked 2026-09-26 on `origin/main`:

- `sol.opam` (the CLI) depends on `obs-eio`, `obs-loki-eio`, `pg-eio`, `kafka-eio`, `aws-eio` and others with **no `pin-depends`** and no version constraints.
- `.github/actions/pin-opam-packages/packages.txt` lists each support package's **URL only**.
- `internal/ci/resolve-support-packages.sh` resolves every package to **`main` HEAD at CI time** ("one run tests one dependency snapshot"), and every CI job pins to that snapshot. The CLI is therefore built and tested against whatever `main` is when CI runs, and that snapshot is not recorded in the repository.
- The framework `.opam` files *do* carry commit pins (`sol-obs.opam`: `obs-loki-eio`, `obs-tempo-eio`; `sol-jobs.opam`: `pg-eio`; `sol-fn.opam`: `lambda-eio`). But those govern framework consumers, not the CLI. `obs-eio` is pinned nowhere, and no CI job builds against those pins.

So the runner's `#main` matches how the CLI itself is built. The float is repository-wide, and deriving the runner's revisions "from the checkout" has nothing to derive from. Picking one of the existing lists would silently make it authoritative for something it was never meant to govern.

## Decision (operator, 2026-09-26): option 1

One committed, authoritative declaration, `support-refs.txt`, consumed by source CI, the source-built migration runner and release builds. Invariant: *a Sol revision declares the exact support-library revisions it builds against*, so a bump is a reviewed diff. Don't duplicate it into generated `sol.opam`. Add a guard proving no consumer can silently return to a floating branch.

## Options considered

Where is the CLI's support-library snapshot recorded, so the runner (and a release) can use the checkout's own?

1. **Commit the snapshot.** A `support-refs.txt` (package → commit) beside `packages.txt`, updated by a bot or a `soldev` command. CI pins from it instead of resolving `main`, and the runner Dockerfile reads the same file. One source of truth; the cost is an explicit bump step when a support package changes.
2. **`pin-depends` in `sol.opam`,** made the source for CI and the runner as well. It's opam-native and consistent with the framework packages, but `sol.opam` is dune-generated today (generation would have to be disabled, as it was for the framework packages under DEC-025), and it would duplicate the framework files' pins for shared packages.
3. **Accept the float for source builds; record it only in releases.** The release workflow writes its resolved snapshot into the bundle, and the published runner is built from it (FEAT-101 does this either way). A source-built runner keeps `#main`, documented as the development form's snapshot semantics, the same as CI.
4. **Wait for RELEASE-005** (support packages published to opam with versions), then use ordinary version constraints.

Recommendation: **1**. It removes the float everywhere (CI, runner, release) with one file, and it makes a support-package change a reviewed diff instead of an ambient event.

## Acceptance criteria (once decided)

- The source-built runner uses the checkout's recorded revisions, and a test fails if the Dockerfile contains `#main`.
- Demo/example: not applicable; state it.

## Completion notes (2026-09-26)

**The declaration.** `support-refs.txt` at the repository root: one `<package> <git url> <40-hex commit>` line per support package, in pin order (`https-eio` first). It replaces `.github/actions/pin-opam-packages/packages.txt`, which held URLs only. The initial commits are the snapshot `main`'s last green CI run tested (run `36254565375`, `main` at `05a1df2f`). They agree with the four framework `.opam` `pin-depends` that name the same packages.

**Consumers, all reading it through one implementation, `internal/ci/pin-support-packages.sh`:**
- source CI: the `pin-opam-packages` action is now a one-line call to the script. The per-run `support-refs` job, which resolved `main` HEAD, is gone (it was not a required check; `test` is the only one), along with the jobs' `refs` inputs;
- release builds (`release.yml`): the same action, and the bundle's `SUPPORT_REFS` is this file;
- the source-built migration runner (`cmd_migrate.ml`'s `sol_cli_dockerfile`): it copies the file and the script into the build, pins from them, then installs exactly `sol.opam`'s dependencies. It used to pin three packages at `#main` and install a hand-picked subset. A new root `.dockerignore` keeps `_build/` and `.git` out of that build context;
- `fn-svc-isolation-spike.yml`, and the developer instructions in `README.md` and `DOGFOOD.md`. Those pinned every package at its default branch, and DOGFOOD's loop also pinned in the wrong order.

**Bumps are diffs.** `internal/tooling/scripts/bump-support-refs.sh [package...]` resolves `main` for the named packages (all, by default) and rewrites the file, plus any framework `pin-depends` on the same package, in lockstep. `internal/ci/resolve-support-packages.sh` and its test are deleted.

**Guard.** `internal/ci/check_support_refs.sh`, unconditional in CI, enforces three things:
- the file is well-formed and has no duplicate packages;
- no tracked file outside the pin and bump scripts references a support repository without `#<40 hex>` (this catches `#main`, a bare URL, and a `$p.git` loop), runs `opam pin add <support package>`, or resolves `refs/heads/main`;
- every framework `pin-depends` agrees with the file.

Historical records (tickets, audits, dated dogfood runs, qualification records, `internal/planning/`) are out of scope. On first run it found the README and DOGFOOD instructions above; it now passes: `11 support package(s) declared; every consumer uses the declared commits`.

`internal/ci/test_support_refs.sh` covers 11 cases:
- 8 for the guard: a baseline pass; failures for a `#main` Dockerfile string, a default-branch loop, `ls-remote refs/heads/main`, an out-of-script pin, a branch in the declaration, and disagreeing `pin-depends`; and a pass for an exact-commit reference;
- the bump moving only the named package, plus its `pin-depends`;
- the pin script pinning each package in order at its commit, via a fake `opam`, and refusing a non-commit declaration.

**Evidence the source-built runner uses the checkout's revisions.** A real `docker build` of the new runner Dockerfile from this checkout succeeded. Its log shows `https-eio is now pinned to …#e548f47c…`, `kafka-eio …#784bf37c…`, `obs-eio …#b425c55e…`, `pg-eio …#3ef3a20f…`, and so on, all eleven at the declared commits, with no `#main` anywhere. The image runs `sol migrate apply --help`.

**Not changed, deliberately:** the scaffolded workspace's framework pins (`sol.git#main` in `examples/pluto/pluto.opam`, `internal/fixtures/venus/venus.opam`, and the scaffold template). Those track the Sol *framework* for app workspaces, not support libraries, and are RELEASE-005's to replace. `sol.opam` gets no `pin-depends`, as decided.
