Keep the Retry_topics relay polling while it waits for a retry to come due

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `f63663d4`, with `kafka-eio` pinned at `b2881b31`, `framework/ocaml/kafka-eio-service/lib/kafka_service_retry_topics.ml:490-493` sleeps inside the retry handler until `X-Sol-Retry-At` without pausing the partition. `kafka-eio` `lib/kafka_consumer.ml` blocks `routing_loop` on a full 16-slot partition stream (`:544-560`), and the poll fiber blocks in `Eio.Stream.add` on the full 256-slot consumer stream (`:152`). The audit reproduced the eviction on a local broker.

## Problem

BUG-014 fixed consumers leaving their group every `max.poll.interval.ms` by adding a 3s keepalive poll. The `Retry_topics` relay defeats that fix. While the relay handler waits for a record's `retry_at`, later retry records fill the 16-slot partition stream. `routing_loop` then blocks, the 256-slot consumer stream fills, and the poll fiber stops calling `rd_kafka_consumer_poll`. If the wait exceeds `max.poll.interval.ms` (librdkafka default 300s), librdkafka evicts the member.

A single retry delay can exceed 300s: `max_delay_s` is documented with a 600s default in `sol-worker.md:94`, and `max_delay_s = 600.0` is the documented way to reproduce the old schedule (`:125`). Such a backlog, with about 273 records waiting behind a long delay, is expected during a downstream outage, which is when `Retry_topics` matters most.

After eviction:

1. every `ack` in the relay fails (`Broker: Unknown member`);
2. `execute_action` returns that error, and `consume_partitioned` with `no_retry` treats it as exhausted;
3. the relay reports `RETRY_RELAY_STOPPED`, closes the source consumer, and the worker exits (`kafka_service_retry_topics.ml:139-151, 503-541`);
4. `W.handle` has already run for every record whose commit was lost, so those records are redelivered and handled again after the restart. The loop can repeat while the backlog still holds future `retry_at` values.

The documented head-of-line latency (`kafka-eio-service.md:344-346`) is accepted behavior. Losing group membership, crashing the worker, and duplicating side effects are not.

**Reproduction** (scratch program against pinned `kafka-eio`, local Redpanda, one-partition topic, `max.poll.interval.ms=10000`, `session.timeout.ms=6000`; the `consume_partitioned` handler sleeps 15s on the first record to stand in for a >300s `retry_at` wait):

- Control, 5 records: max gap between polls 3.0s, no revocation, all acks succeed.
- 600 records: `MAXPOLL ... Application maximum poll interval (10000ms) exceeded ... leaving group`, `REVOKED`, then `ack #1..#N FAILED: Broker: Unknown member`. Afterwards `rpk group describe` shows `TOTAL-LAG 275`, meaning 275 handled records whose commits were lost.

`In_memory` sleeps in the partition fiber after `pause_partition`. Records already queued before the pause can fill the same buffers, so check that path under the same test. It is documented as the dev option, so `Retry_topics` is the priority.

## Remediation

Fix this where it originates, in `kafka-eio`: a consumer's poll loop must never be blocked by its own downstream buffers. When `consume_partitioned` cannot route a record because a partition's queue is full, it pauses that partition at the librdkafka level and keeps polling, then resumes it once the queue drains. It must not block the poll fiber in `Eio.Stream.add`. This makes every consumer safe regardless of how long its handler holds a record, not just the relay.

**Evidence that pausing is the right mechanism (2026-09-29 amendment):** the same 600-record backlog run through `consume_partitioned`'s own retry path, which pauses the partition during its backoff (a 15s backoff standing in for `In_memory`), kept a 3.0s maximum poll gap and was never evicted, with zero lag. The original filing claimed pausing was insufficient; that claim is withdrawn.

Change `kafka-eio`'s API if needed, and update Sol's pin and call sites in the same pass.

## Acceptance criteria

- A regression against a real broker, with `max.poll.interval.ms` reduced and a retry-topic backlog larger than the consumer's buffers waiting behind a delay longer than that interval, shows no `MAXPOLL` eviction, no failed ack, and no `RETRY_RELAY_STOPPED`, and each record is handled once.
- A `kafka-eio` regression: a handler that holds one record longer than `max.poll.interval.ms`, with more records fetched than the buffers hold, keeps the poll cadence under the keepalive interval and keeps group membership.
- Any `Retry_topics` delay up to `max_delay_s` is supported with no librdkafka tuning and no startup cap on the delay.
- `sol-worker.md` and `kafka-eio-service.md` describe the resulting guarantee. Record the TypeScript retry-topic parity verdict in completion notes.

## Completion notes

- kafka-eio PR #30 pauses a partition at its queue high-water mark while routing and the poll fiber continue. The broker regression holds a handler for 12 seconds behind 400 records with a 10-second max poll interval; every ack succeeds, poll gaps remain below the interval, and group membership remains intact.
- librdkafka pause and resume errors are surfaced; a failed pause stops consumption with a consumer error. Already prefetched messages can exceed the high-water mark, bounded by librdkafka's finite fetch queue.
- Sol's broker regression reproduces MAXPOLL and failed acknowledgments with the old pin, then drains all 400 retry records exactly twice with the new pin. The relay accepts explicit consumer properties so the regression can lower the max poll interval without waiting five minutes.
- TypeScript retry-topic parity: no new retry contract; this repairs the OCaml poll implementation. TypeScript must uphold the same no-eviction behavior for its retry relay under FEAT-080's capability matrix.
