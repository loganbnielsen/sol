**Related:** FND-0007, HARDEN-004, `docs/qualification/gcp-bootstrap-inventory.md`
(§"DNS and TLS prerequisites", §"Proposed GCP capability mapping" DNS/TLS row),
`docs/qualification/production-single-region-v1-matrix.md` row I14.

## The rule this decides (provider-neutral)

A qualification profile that must prove **public DNS → ACME → TLS** needs the run to
be *authoritative* for a real DNS namespace: cert-manager's DNS-01 challenge writes a
`_acme-challenge` record that the certificate authority must be able to resolve, so
the run has to control the zone that answers for it.

**That is a property of the capability, not of the cloud.** It applies identically to
GCP (Cloud DNS) and to AWS (Route 53). What differs today is *which profile chooses
to qualify the capability*:

| | GCP (`production-single-region/v1` on GKE) | AWS (same profile on EKS) |
|---|---|---|
| Public-TLS row in the matrix | **Yes** — HARDEN-004's TLS row | No — row I14 states `Ready` does **not** require an external ACME round trip |
| DNS-01 solver | **Missing** — hard-wired to Route 53 (`FND-0007`) | Route 53, present |
| Delegated namespace needed | **Yes, now** | Not today; reserved |

So the asymmetry a reader will notice is **qualification scope**, plus one real
GCP-only implementation gap (the solver). It is *not* "Cloud DNS needs a subdomain
and Route 53 does not": if the AWS matrix gained an equivalent row tomorrow, AWS
would need the same delegation, and every rule below applies to it unchanged.

## Question

Which name(s) are delegated, to whom, and how narrowly — given that a delegation
hands a disposable qualification project authority over part of the domain's
namespace?

## Options

- **A. Dedicated subdomains of the product domain, one per cloud, delegated to that
  cloud's DNS provider.** Recommended.
- **B. A separate qualification-only domain.** Cleanest separation, but another
  registration and renewal to own for a name no product surface uses.
- **C. Consume operator-managed records (external DNS operator).** Sol is handed
  records rather than a zone; the `ClusterIssuer` still needs a solver, so every
  attempt depends on a human or another system. This is the inventory's documented
  alternative, not a way to avoid needing a name.
- **D. Accept the gap.** Record the TLS row `BLOCKED`/`ACCEPTED` permanently and
  qualify GCP without a public-TLS capability.

## Decision (2026-09-22)

**Option A, with symmetric per-cloud labels:**

| Cloud | Name | Zone created by | Status |
|---|---|---|---|
| GCP | `qual-gcp.sol-fab.dev` | Sol's GCP cloud root (`create_dns_zone = true`) | **Delegate now** — GCP carries the row |
| AWS | `qual-aws.sol-fab.dev` | Sol's AWS cloud root (`create_route53_zone = true`) | **Reserved** — delegate when the AWS matrix carries an equivalent row |

**One label per cloud, not one shared label.** A name can be delegated exactly once,
so a single `qual` could never point at two providers. Deciding both names now costs
nothing, and a rename later would not be cosmetic: the zone's nameservers are baked
into the registrar, so renaming means re-delegating, re-issuing, and a new CT entry.

**The zone is Sol's resource, not a hand-created one.** Both cloud roots already
declare it as an opt-in zone — `google_dns_managed_zone.main`
(`cli/platform/infra/gcp/main.tf`) and `aws_route53_zone.main`
(`cli/platform/infra/aws/main.tf`) — and both expose the hand-off as an output whose
description *is* the instruction:

```text
output "dns_nameservers"      # GCP — "Nameservers to set at your domain registrar"
output "route53_nameservers"  # AWS — "Nameservers to set at your domain registrar"
```

Creating the zone by hand instead (`gcloud dns managed-zones create`) would put it
outside Terraform state and collide with the product's own declaration of the same
name on the next apply. The zone is created by the cloud bootstrap
(`--var create_dns_zone=true --var base_domain=qual-gcp.sol-fab.dev …`) and read back
from that output.

**The registrar step is the deliberate human half.** The parent zone is managed at
Squarespace, which has no API, so four `NS` records are pasted once by hand. That is
the whole grant, and it is the boundary rather than a gap: Sol owns the zone, the
owner owns the parent.

## Scoping rules

1. **Never delegate the apex or a name the product serves** (`sol-fab.dev`, `www`,
   mail records, …). A dedicated per-cloud label only.
2. **Revocation is the kill switch:** removing the four `NS` records ends the grant
   with no residual authority in the qualification project, whatever credentials
   remain.
3. **The zone is durable and must not be part of the disposable substrate.** GCP
   assigns *new* nameservers when a zone is recreated, so a teardown that removes the
   zone silently invalidates the pasted delegation — and the TLS failure that follows
   does not name the cause. Treat the delegated zone as a standing prerequisite that
   outlives target teardown, which is also why its cost (~$0.20/month on GCP) does
   not go away with the target.
4. **Identity: as narrow as the provider actually allows.** Cloud DNS (and Route 53)
   permissions are project/hosted-zone-level by nature — `roles/dns.admin` is not a
   per-zone role you can simply scope down, and an earlier draft of this decision said
   otherwise. The controls that are real: the zone lives in a project whose **only**
   zone is this one; the apex is not in Google Cloud at all (it is Squarespace-managed),
   so there is no apex zone for that identity to reach; and an optional IAM condition
   can restrict it further. Prove it with a negative test rather than asserting it.
5. **Stage, then produce once.** Qualify against the ACME **staging** directory first,
   then a single production issuance for the row's evidence — the row is "public TLS
   issuance", so staging alone is mechanism, not qualification.

## Why this is appropriate (not an abuse of the product domain)

- It is precisely what the inventory already requires: *"control of a qualification
  subdomain; either delegated Cloud DNS nameservers or an external DNS operator; … a
  publicly resolvable hostname …"*.
- A dedicated subzone **confines the blast radius**: the qualification project can
  answer only for `qual-gcp.sol-fab.dev`. A misconfigured or compromised qualification
  project cannot affect `sol-fab.dev` or any product name — the same
  install-authority-bounded-to-a-window discipline ADR 0003 applies to credentials,
  applied to DNS authority.
- It **raises fidelity rather than lowering it**: the target's `base_domain` becomes a
  real, publicly-resolvable name with a real publicly-trusted certificate, which is the
  production shape the profile exists to prove. The certificate's name appears in public
  Certificate Transparency logs — expected, and one reason the label is unmistakably a
  qualification name.

## Roadmap fit

This is one HARDEN-004 row, not the whole GCP workstream: the identity/authority rows
and reaching platform `Ready` do not need it and should proceed in parallel. But it is
a genuine step on the "real-world ready" line — the **first time Sol issues and serves
a publicly-trusted certificate from an owned domain** — and on the GCP side it is
coupled with the other half of FND-0007 (replacing the hard-wired Route 53 DNS-01
solver with a Cloud DNS solver). GCP parity (HARDEN-004) plus the AWS workload path
(HARDEN-002) together feed `PROD-001`, the first maturity-A pilot.

## Acceptance criteria

- The delegated name (`qual-gcp.sol-fab.dev`), its Cloud DNS zone, the NS delegation
  and the exact IAM grant are recorded, with a note that the product's own names are
  untouched; `qual-aws.sol-fab.dev` is recorded as reserved **with the condition that
  triggers it** (an AWS matrix row requiring a public hostname and a real certificate).
- The zone is created by Sol's cloud root (`create_dns_zone = true`) rather than by
  hand, and `dns_nameservers` is what gets pasted at the registrar.
- A qualified Cloud DNS solver replaces the Route 53 solver on the GCP path (the second
  half of FND-0007), with a scoped workload identity.
- Staging issuance observed, then one production issuance recorded as the TLS row's
  behavioural evidence.
- The qualification project is demonstrated (or argued with evidence) able to write
  only within the delegated subzone.
- Teardown does not silently break the delegation: either the zone outlives it, or the
  run records that the delegation must be redone.

## Status

**Decided 2026-09-22** by the repository owner (who controls `sol-fab.dev`): option A
with symmetric per-cloud labels — `qual-gcp.sol-fab.dev` delegated for GCP now,
`qual-aws.sol-fab.dev` reserved. HARDEN-004's TLS row is unblocked on the decision; the
remaining work is implementation (delegation, then the solver swap and issuance).
