Keep build-context copying from dereferencing workspace symlinks

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `cli/lib/base/sol_cli_fs.ml:127-146; cli/lib/deploy/sol_cli_up_execution.ml:63-74` with callers and existing tests at origin/main `2dfa5694`. Evidence and reproduction limits are recorded in the source audit.

## Problem

copy_tree uses Unix.stat and follows workspace symlinks. A link to a file outside the workspace becomes a regular file containing that external data in the Docker context; directory links recurse outside the workspace, including ancestor cycles. Docker sees the already-dereferenced copy, so this can expose external data to COPY . and break local builds.

## Remediation

Inspect entries with lstat and preserve link identity without reading external targets, or reject links with an explicit diagnostic if that is the supported policy. Do not introduce a new copying framework. Preserve current regular-file permissions and exclusions.

## Acceptance criteria

- Tests cover external file links, external directory links, dangling links and ancestor cycles: none imports external contents or recursively follows a cycle. A regular-file positive control still copies correctly. Update a runnable build-context example or document the existing symlink behavior at the user boundary.
- Record the application demo and per-language verdict in completion notes wherever the change affects an application contract.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `788e688d`: `copy_tree` matched on `Unix.stat src`, so a symlink was resolved before the `st_kind` test — an external file link became a regular file holding external data, and a directory link (including `..` ancestor cycles) was recursed. There is one production caller, `prepare_build_context` in `cli/lib/deploy/sol_cli_up_execution.ml`, which copies the workspace root into the Docker build context. (Note: an earlier `rg` of mine hid this caller because I filtered `_build`, which the caller line contains.)
- **Fix (preserve link identity).** `copy_tree` now matches on `Unix.lstat`, and a new `S_LNK` branch recreates the link with `Unix.readlink` + `Unix.symlink`. No target is ever opened and no linked directory is traversed, so external contents cannot be imported and cycles cannot recurse. This is also the faithful policy: Docker does not dereference context symlinks, so the pre-copy now matches what `docker build` sees on the original tree. Regular-file modes and the `exclude` list are unchanged.
- **Tests** (`cli/test/test_fs.ml`): the old `copy_tree` case asserted "a symlink is followed"; it now asserts regular files/modes/excludes only, and a new `test_copy_tree_preserves_symlinks` covers an external **file** link (destination is `S_LNK` and its target string is preserved, so contents are not imported), an external **directory** link (kept as a link, not recursed), a **dangling** link (preserved and still dangling), an **ancestor cycle** (`-> ..`, preserved, copy returns `Ok`), and a regular-file positive control. **Mutation-checked**: reverting to `Unix.stat` fails the symlink case while the fix passes. All 8 fs tests pass.
- Validation: full `dune build`; `cli/test/test_scaffold.exe` 52/52 (the template README is rendered, not golden-compared); `dune fmt --preview` clean; no-comments policy holds.
- **Demo/example**: no runnable build-context example exists, so the behavior is documented at the user boundary in the scaffolded workspace `README.md` (`platform/shared/templates/workspace/README.md`): `sol up` copies the root into a temporary context and symlinks stay symlinks, never followed. **Language parity: no impact** — filesystem/build-context handling, not a framework or application contract.
