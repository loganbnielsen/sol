**Depends on:** None.

A workspace-wide `sol up` registers the contracts of only one scope. The reference
workspace declares two event languages (`events/orders` + `events/payments` +
`events/comms` in OCaml, `events/demo_ts` in TypeScript), and its
`contract/run` dispatcher routes every scope but `demo_ts/*` to the OCaml
runner — including the whole-workspace scope `sol up` passes for an unscoped
deploy. The TypeScript scope's two events are therefore never registered, and its
units fail at startup against the registry they correctly address:

```console
$ kubectl -n pluto-demo-ts logs deploy/order-svc
[order-svc-ts] brokers=redpanda.redpanda.svc.cluster.local:9093 \
  registry=http://redpanda.redpanda.svc.cluster.local:8081 topic=sol-demo-ts-orders
[order-svc-ts] fatal: Error: subject 'sol-demo-ts-orders-value' has no registered schema \
  matching the declared contract
    at lookupSchema (…/@sol-fab/kafka/dist/schemaRegistry.js:122:15)
    at async connectTopic (…/@sol-fab/kafka/dist/register.js:67:26)
```

`kubectl get pods -n pluto-demo-ts` → `order-svc … CrashLoopBackOff`, with the
startup probe failing (`/healthz` connection refused) because the process exits
before it listens. The same deploy's OCaml units are `Running`: their four
subjects (`orders.v1-value`, `orders-fulfilled.v1-value`,
`pluto-payments-charges-value`, `pluto-comms-notifications-value`) are in the
registry, and only the TypeScript scope's two are missing.

The registry is not the problem here: `order-svc` addresses the in-cluster
registry (`redpanda.redpanda.svc.cluster.local:8081`), which is the same
destination the manifests name. This is independent of `INFRA-102`, which fixed
*where* the registration is sent; this one is *what* is registered.

## Remediation

`examples/pluto/contract/run`: the whole-workspace scope runs every runner the
workspace declares — the OCaml events first, then the TypeScript scope — instead
of falling through to the OCaml runner alone. Scoped deploys are unchanged
(`--scope demo_ts` still runs only the npm runner; a single-language scope still
needs only its own toolchain), which is the property the dispatcher exists for.

## Acceptance criteria

- An unscoped `sol up` of `examples/pluto` leaves every declared scope's subjects
  in the registry, and `pluto-demo-ts/order-svc` becomes `Ready` without a second,
  scoped deploy.
- `sol up --scope demo_ts` and `sol up --scope payments` still run one runner each.
- Demo/example coverage: this is the example's own glue; the resumed `VERIF-027`
  run is the observation that closes the row.

## Completion notes (2026-10-04)

Fixed in the same PR. The dispatcher now names the OCaml scopes explicitly and
treats every other scope (the whole workspace) as "run all of them", with the
OCaml runner's exit status preserved. Verified by re-running the unscoped
`sol up` against the recorded `VERIF-027` cluster: the TypeScript scope's subjects
appear in the cluster registry and `pluto-demo-ts/order-svc` reaches `Ready`
without a scoped deploy (evidence appended to the run record).

Language parity (DEC-022): no contract change — this is the reference workspace's
own dispatch glue, and it now covers both languages' scopes equally.
