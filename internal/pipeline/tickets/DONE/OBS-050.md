**Depends on:** DEC-064.

## The gap

`docs/architecture/observability-design.md`'s Identity section: "Every log line,
metric, trace, deploy event, and generated dashboard link must carry the same
ownership identity: `workspace`, `env`, `domain`, `service`, `primitive`,
`release`."

Observed locally (`main @ 2a2c5a7c`): a real trace's OTLP resource attributes
are `service.name` **only**.

```text
$ curl -s 'http://localhost:3200/api/traces/6a7e1de7…' | jq -r '.batches[].scopeSpans[].spans[].name'
receive_order
fulfill_order
$ … | jq -r '.batches[] | .resource.attributes[] | select(.key=="service.name") | .value.stringValue' | sort | uniq -c
      1 fulfillment-worker
      1 order-svc
```

There are no `workspace`/`env`/`domain`/`primitive`/`release` resource
attributes. The code path explains why: `Sol_obs.of_env` creates the Tempo
backend without taxonomy context, and the scaffolded app's `~context` is
`[("team","payments")]`, not the taxonomy. Logs get the taxonomy from Alloy's
pod-label promotion and metrics from Prometheus' pod-label map, but a trace's
resource is written by the application, so no scrape-time relabeling adds it.

This means a trace can only be attributed to a `service.name`; it cannot be
filtered by domain, workspace, environment or release the way the same request's
logs and metrics can. `sol open traces` does not exist either (OBS-045), so there
is no supported way to reach a trace from a scope at all.

## Impact

Cross-signal correlation is incomplete in the direction the design promises:
from a log line or metric you can reach a trace by `trace_id`, but from a trace
you cannot recover the workload identity or release. Traces that span services
(frameworks make that the norm) cannot be grouped by owning domain.

## Decision (DEC-064, 2026-10-02)

`DEC-064` settles the ownership: **Sol framework/runtime instrumentation emits
Sol's semantic workload identity; collectors enrich infrastructure identity.**
The injected-environment + framework-context option is chosen; an app-author
`~context` is rejected as a platform invariant on every author; collector
enrichment stays allowed for *infrastructure* identity only and is not the
mechanism for the taxonomy.

## Observed in addition on 2026-10-02 (`main @ 3d29d043`)

Rendering a scaffolded workspace (`sol up --dry-run`) shows the other half of the
gap: the framework's `service` value and the pod label's `service` value
disagree.

```text
rendered pod label:   service: "charge-svc"          (bare Kubernetes name)
scaffold's app:       ~service:"obsdemo-charge-svc"  (workspace-prefixed)
```

So app-emitted traces and app-pushed logs use a different `service` than the
Alloy/Prometheus-promoted logs and metrics for the same workload. The app-pushed
Loki stream is `{service="obsdemo-charge-svc", team="payments"}` — it is not even
selected by `sol logs`' `{workspace,domain,service}` query. `DEC-064` requires
the values to agree.

## Remediation

1. The manifest injects the semantic identity as environment variables (the same
   values it renders as pod labels), including `service` as the bare
   Kubernetes name.
2. `Sol_obs.of_env` reads them and composes the signal context: Loki stream
   labels, OTLP resource attributes, and — if `obs-prometheus-eio` gains a
   const-label capability — metric labels.
3. The scaffold templates stop hardcoding
   `~service:"<workspace>-<unit>-<primitive>"` and `~context:[("team", domain)]`;
   runtime identity comes from the injected values, with `~service` reduced to
   the unit name the caller already has.
4. Reference apps and their docs use the bare unit name as `service`.

## Acceptance criteria

1. A trace produced by a scaffolded primitive carries `workspace`, `env`,
   `domain`, `service`, `primitive`, `release` as OTLP resource attributes, and
   its `service` equals the pod label `service` (and therefore the Loki stream
   label and the Prometheus `service` label).
2. Trace lookup by `service.name` still works (the demo's `order-svc` value is
   unchanged).
3. The local demo's Tempo output is asserted to carry the taxonomy, not just
   `service.name`.
4. A guard ties the framework's emitted label set to the manifest taxonomy and to
   the Alloy promotion list, so the three cannot drift.
5. The TypeScript framework's verdict is recorded (DEC-022).

## Completion (2026-10-02)

**Premise verified.** `rg -q 'SOL_WORKSPACE' framework/ocaml/sol-obs/lib/sol_obs.ml`
exited 1 before this change and exits 0 after it: `Sol_obs.of_env` had no workload
identity, and the scaffolded workspace's `app/payments/charge_svc` rendered
`~service:"{{name}}-charge-svc" ~context:[("team","payments")]`.

**What changed.**

- `Sol_cli_manifest.observability_taxonomy` / `identity_env` render the six
  identity values once; the pod labels (`taxonomy_labels`) and the injected
  `<name>-env` ConfigMap now derive from the same function, so a label and its
  `SOL_*` variable cannot disagree.
- `Sol_cli_deployment_render` injects `SOL_WORKSPACE`/`SOL_ENV`/`SOL_DOMAIN`/
  `SOL_SERVICE`/`SOL_PRIMITIVE`/`SOL_RELEASE` for every primitive (svc, worker,
  fn) and strips any declared service `config` key of the same name, so the
  platform owns the vocabulary.
- `Sol_obs.of_env` reads the six `SOL_*` values, uses `SOL_SERVICE` in place of
  the `~service` argument when present, composes them into the Loki stream labels
  and the OTLP resource attributes, and lets the injected value win over an
  application `~context` field of the same name.
- `sol local up` injects the workspace/domain/service/primitive identity per
  launched recipe (no `env`, no `release` locally, matching the design), so the
  local process mirrors the cluster's manifest.
- The workspace and component templates pass the bare Kubernetes name
  (`{{binary}}`, `charge-svc`, `notify-worker`) and no longer hardcode a
  workspace-prefixed `service` or a `team` context.
- The reference apps (`examples/pluto`, the venus fulfillment worker) use the
  bare Kubernetes name.
- `docs/reference/runtime.md` gains § Sol workload identity;
  `docs/architecture/observability-design.md` § Identity records the DEC-064
  ownership; the tutorial and application-authoring guide match the new shape.
- `internal/ci/check_platform_component_drift.py` gains the structural tie
  requested by acceptance criterion 4: it parses `Sol_obs.taxonomy`, the
  manifest's `observability_identity` map and the deployment render's use of
  `Sol_cli_manifest.identity_env`, and requires all three to be the documented
  six labels under the same `SOL_*` names. Four new mutations fail the guard
  for the right reason.

**Acceptance criteria.**

1. Covered by `test_svc_identity_configmap_carries_the_taxonomy`,
   `test_worker_...`, `test_fn_...` (manifest) and
   `test_taxonomy_env_reaches_tempo_resource_attributes` (framework). The
   `service` value is the workload's Kubernetes name in both the pod label and

2. `internal/fixtures/local-demo` and `internal/fixtures/venus/bin/run.ml` keep
   `~service:"order-svc"`/`"charge-svc"`/`"notify-worker"`; the standalone

3. The framework test asserts the Tempo OTLP body carries the taxonomy values;

4. `check_platform_component_drift.py` plus its mutation suite.

   records what `@sol-fab/obs` would need and the demo it must update.
