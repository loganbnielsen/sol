## Decision

> **A destructive lifecycle may instantiate an explicitly declared, plan-asserted, ephemeral
> authority mechanism required to perform destruction. It may not construct or reconstruct target
> resources.**

In Sol's terms: during destroy, `CREATE`/`REPLACE` of the provider-declared temporary
bootstrap-authority mechanism is permitted — and nothing else is. This is not new behaviour. It is
what REFAC-094 recorded, what `Sol_cli_cloud_destroy.reconciliation_policy` implements, and what
Attempt 8 broke by being unable to *express* it for GCP's mechanism. It is recorded here so a
guard, a provider declaration or a future reader cannot re-litigate it by accident, and so the
boundary has one citable home.

## What the authority operation is, and what it is not

| It is | It is not |
|---|---|
| An ephemeral lifecycle mechanism Terraform manages (GCP: a `count`-indexed root-level ClusterRoleBinding; AWS: the `module.eks` access-policy association) | Target desired state: no application or target workflow asks for it |
| Created to grant, used, and removed inside the same command | A resource the target ends the run with (the target ends absent either way) |
| Declared by the provider as data (`bootstrap_matchers`, `bootstrap_scope`) | Provider logic in the generic lifecycle |
| Bounded to the mechanism by the plan assertion | A general permission to create during destroy |

## The invariants this decision preserves

1. **Not target reconciliation.** A `CREATE` of any target resource in a destructive plan remains
   refused, whether it would rebuild a half-built target (FND-0044, FND-0030) or reconstruct one the
   state lost. The harness scenario `PLAN_CREATES_MISSING_CLUSTER` pins the refusal end to end.
2. **Acquisition is plan-asserted.** The apply that acquires authority is planned first and
   classified from the saved plan before it runs; an unreadable plan, an unrecognised action, or a
   change outside the phase's allowlist refuses the apply.
3. **Bracketed.** Acquisition, the protected operation, and removal are one structure
   (`with_elevated_access`). Removal runs on every exit path — success, the operation's failure, and
   the failure of the acquisition itself, whose access may be half-open (FND-0047).
4. **Removal failure is visible.** It is returned as evidence and reported; it is never swallowed.
5. **Least authority.** The mechanism grants exactly what the protected operation needs, for
   exactly as long as it needs it; identity is not widened.
6. **Identity is not permission.** A matcher answers only "is this change the declared mechanism?";
   the rule's allowed actions decide whether the action is permitted. A phase that forbids `CREATE`
   refuses it even on the mechanism (the removal policy does, and its test pins it).
7. **The declaration must be able to name what Terraform emits.** A mechanism Terraform indexes
   (`count`/`for_each`) is declared with `Sol_cli_terraform_plan.Resource`, which matches the
   resource and every instance of it; `Exact` names one address and cannot match an indexed plan.
   FND-0058 is what happens when the declaration and the plan address disagree.

## Why the alternative — "destroy must never construct anything at all" — is not the rule

It is unachievable for an in-cluster teardown: removing platform objects needs in-cluster
authority, and on GCP that authority is itself a Kubernetes object. A rule that forbids acquiring it
does not prevent construction; it prevents *destruction*, and leaves a half-built target with
nothing able to unwind it (which is exactly what Attempt 8 observed: stale platform state, no
supported way to clear it). The safe version of the rule is the one above: authority yes, target no.

## Consequences for a provider implementation

A provider declares its mechanism once, as data: the matchers that identify it, and the scopes that
bound the applies that acquire and release it. A provider whose mechanism Terraform indexes uses
`Resource`; one whose address is unstable inside a module uses `Type`. A provider that needs **no**
mechanism cannot say so today — an empty matcher list means "nothing is permitted" rather than
"nothing to acquire", and an empty scope is rejected — so that gap is `INFRA-083`, tracked as a
decision rather than speculatively implemented.

## What this decision does not cover

- **Recovering state that is already stale** — a target whose cloud root is gone while its platform
  state is not. That is a recovery question with an absence claim of its own, tracked as `INFRA-082`;
  it is not part of the authority rule and must not be bundled with it.
- **Who may run the acquisition** — the existing credential and identity rules are unchanged.
