## Question

A unit's declaration can imply cloud authority: `secrets = ["stripe"]` implies
`GetSecretValue` on that secret, and IAM database auth, MSK IAM auth and object storage
imply grants of their own. Realising that needs a cloud identity per unit and a grant per
declared edge. **Who is allowed to reconcile those?**

`sol deploy` runs as the deploy identity, which `INFRA-025` limited to namespace-scoped
Kubernetes RBAC. Creating per-unit roles at deploy time would need `iam:CreateRole`,
`iam:PassRole` and `eks:CreatePodIdentityAssociation` (or the GCP equivalents). An
identity that can create and pass roles can grant itself anything.

## Decision (2026-10-01, operator)

**Decided.** Workload cloud authorization is a third category, separate from
infrastructure and from deployment. It changes at application cadence but needs more
privilege than deployment, and that combination is what earns it its own boundary:

```text
sol cloud apply      destination infrastructure (VPC, cluster, databases, secret authority)
                     + the authorization reconciler's identity and its fence
        │
        ▼
grants plan/apply    workload identities + cloud grants, derived from the whole workspace
        │
        ▼
sol deploy           workloads consume established identities; grants nothing
```

`sol cloud apply` is **not** the reconciler. Having enough credentials today does not make
it the owner of the resource. The command name (`sol grants`, `sol auth`, …) is cosmetic
and is chosen during implementation; the separate lifecycle is not.

### The six rules

1. **Separate privileged lifecycle.** A dedicated reconciler derives unit identities and
   cloud grants from the workspace declarations, and reconciles them idempotently. Its
   plan is readable on its own terms (`+ payments-api → secret/stripe`,
   `- old-api → secret/legacy`), so a reviewer can see that a change grants a unit a
   production credential.

2. **The reconciler is structurally fenced.**

   > The authorization reconciler MUST be structurally incapable of granting authority
   > outside the destination's Sol-managed authorization vocabulary and resource
   > boundary.

   The fence is created by the provisioner during `sol cloud apply`, together with the
   reconciler's identity. The reconciler cannot alter its own fence.
   - **AWS:** the reconciler may create roles only under an environment-scoped role path
     (for example `/sol/<env>/`), and every role it creates must carry a **mandatory
     permissions boundary**. That boundary allows only Sol's grant vocabulary on that
     environment's resources, for example `secretsmanager:GetSecretValue` on
     `sol/<env>/*`, `rds-db:connect` on that env's databases, and MSK actions on that
     env's clusters. The reconciler has no VPC, cluster or database creation rights.
   - **GCP:** grants are on individual resources (`setIamPolicy` on Sol-managed secrets,
     granted directly to Workload Identity Federation principals). The reconciler's
     authority is limited to those resources and roles; it creates no service accounts.

   Growing the vocabulary (a new capability family) means changing the fence in
   `sol cloud apply`. That is an infrastructure change, not something the reconciler can
   do for itself.

3. **Additions happen before deployment.** A unit that declares a grant the cloud does not
   yet hold is refused by `sol deploy` at plan time (rule 6). The plan names the unit, the
   missing grant and the reconciliation to run. It never deploys a pod that hangs in
   `ContainerCreating`.

4. **Removals are gated on observed deployed state.** A grant is revoked only when *the
   declarations no longer require it* **and** *no deployed workload still uses it*:

   ```text
   desired says remove + observed deployed state says unused = revoke
   ```

   This prevents the outage from revoking before the deploy that stops using the grant.
   If the deployed state cannot be observed (the cluster is unreachable), the reconciler
   keeps the grant and says so; it never revokes on a guess. Additions are not held back
   by a pending removal.

5. **Reconciliation covers the whole target, always.**

   > Authorization reconciliation is target-wide and atomic with respect to the
   > workspace authorization graph; it MUST NOT accept unit or domain scope.

   This is an invariant of the operation, not just of the CLI's flags, so no future API
   or automation path can reintroduce partial reconciliation. A partial reconcile would
   revoke every unselected unit's grants (the `BUG-088`/`BUG-089` bug class).

6. **Deploy verifies effective access, read-only.** `sol deploy` proves that each unit
   has the effective cloud access its declarations require, by observing the provider.
   It never trusts a Sol-generated record that grants were applied
   (`DEC-052`: observed, not asserted). The deploy identity gets read-only IAM visibility
   and nothing that mutates IAM.
   - **AWS, the intended mechanism, subject to qualification:** `iam:SimulatePrincipalPolicy`
     against the unit's role for each required action and resource. Qualification must
     show that the simulation reflects the real evaluation, including permissions
     boundaries, resource policies and SCPs. Where it does not, the verification uses a
     mechanism that does.
   - **GCP:** read the IAM policy of each granted resource for the unit's principal, with
     the same requirement to reflect effective access.

### Implementation default: a Terraform root Sol generates input for

The reconciler is implemented as a fourth per-driver Terraform root, **`authorization`**.
It is planned and applied on its own lifecycle, which is what justifies a separate root.
Terraform supplies plan, apply, drift detection and idempotence.

**Terraform is not the authority on what to destroy.** Sol computes the *safe* grant set
first (rule 4), and only that set becomes the root's generated input:

```text
workspace desired grants + observed deployed requirements
        │
        ▼
Sol computes the safe grant set          ← rule 4 is enforced here
        │
        ▼
generated Terraform input → terraform plan/apply
```

Otherwise `terraform apply` would perform the premature revocation rule 4 forbids. To make
deployed requirements observable, each deployed workload records the grants it was
deployed against (for example as an annotation the reconciler reads with read-only
Kubernetes access). The exact carrier is an implementation choice; the observation is not.

## Consequences to carry into implementation

- **`DEC-046` rule 4 / `internal/ci/check_provider_roots.sh`:** `roles="bootstrap cluster
  platform"` gains `authorization`, and `check_destroy_completeness.sh` must account for
  it. A driver with no cloud IAM (`byo`, `DEC-051`) reports the role as `Not_applicable`,
  not missing.
- **`sol cloud apply`** creates the reconciler identity and its fence (the boundary policy
  and the role-path restriction on AWS; the resource-scoped grant authority on GCP).
- **CI needs two identities.** `FEAT-109` generates a deploy job and a separate
  authorization job, and the authorization job sits behind an approval gate (for example
  a protected GitHub environment).
- **Unit identity naming** is scoped per environment, so a dev unit's identity can never
  be granted a prod resource (`DEC-016`). On EKS the pod-identity association is
  AWS-side (reconciler) and references the namespace and ServiceAccount that `sol deploy`
  creates; the order works because the association can exist before the ServiceAccount.

## Deferred to implementation (not decision questions)

The command name; the exact AWS and GCP permission sets for the reconciler and the
boundary; the CI credential mechanics for the authorization job; the annotation format
for deployed requirements; the plan-output format.

## Acceptance criteria

- The six rules are enforced by tests in the implementing units:
  - The deploy identity's cloud permissions contain no IAM-mutating action.
  - A role created outside the env path, or without the boundary, is refused by the cloud.
  - `sol deploy` with a missing grant is refused at plan time, with the stated message.
  - A removal whose grant is still used by a deployed workload is not revoked.
  - The reconciler has no scope parameter.
  - Deploy-time verification fails for a grant that is declared but not effective.
- The `authorization` root is added to every real driver, with the provider-roots and
  destroy-completeness guards updated.
- `FEAT-109`'s workflow includes the gated authorization job.
- Every capability family that consumes this is listed: secrets (`DEC-029`), IAM DB auth,
  MSK IAM auth, object storage.
- Demo/example: the implementing unit that makes `secrets` live updates pluto to show a
  grants plan, then a deploy. No language-parity impact (`DEC-022`): this is platform
  authorization only.

## Progress (2026-10-02, part A)

**Landed:** `internal/ci/check_deploy_identity_iam.py` reads the generated
`aws_iam_policy_document.deploy` structurally and fails if an Allow statement
grants any IAM-mutating action or if no Deny covers `iam:*`. It enforces the first
acceptance bullet — the deploy identity is structurally incapable of granting
itself or a workload cloud authority — so a later edit that widens the deploy
identity fails a fast guard rather than a live qualification. Mutation test:
`internal/ci/test_deploy_identity_iam_check.py` (an Allow gaining `iam:CreateRole`,
and the `iam:*` deny narrowed). Both run in `run_fast_checks.sh`.

**Still open (this ticket stays `READY_FOR_ENGINEERING`):** the `authorization`
Terraform root and its fence for `aws`/`gcp`; the reconciler's plan/apply with the
rule-4 safe-grant set and rule-5 target-wide invariant; deploy-time read-only
effective-access verification (rule 6); the provider-roots and
destroy-completeness guard updates; and `FEAT-109`'s gated authorization job.

**Landed (part B):** `Sol_cli_authorization` (`cli/lib/deploy/`) is the
target-wide safe-grant-set computation the reconciler feeds to Terraform. It
takes the desired grants, the currently granted set, and the observed deployed
state, and returns the safe `keep` set plus a readable plan. A stale grant that a
deployed workload still uses is **held**, not revoked; when the deployed state is
unobservable every stale grant is held and the reason is recorded; additions are
computed independently of pending removals; and the API has no scope parameter by
construction. Eight tests in `cli/test/inline/test_authorization.ml` cover rules
1 (readable `+`/`-` plan), 4 (held removals, observable and unobservable) and 5
(target-wide). The grant-set computation is the input the `authorization` root
will consume; the root itself and the deploy-time verification remain open, so a
`secrets`-declared grant has no consumer until then.

**Reconnaissance for the root (recorded so the next unit is unambiguous):** a
fourth role is not a directory-only change. `Sol_cli_platform_assets`' role type,
`Sol_cli_terraform_workdir`, `Sol_cli_provider_capabilities`' per-role
`root_declared_vars`, `sol_cli_provider_registry`, the teardown and absence

**Landed (part C, the root and its fence):** `Cloud_role` gains `Authorization`,

## Final contract and implementation split (2026-10-02)

**Resolved.** No architectural question remains: the operator decision of
2026-10-01 and rules 1–6 above are the contract, and everything left is named as
an implementation choice in *Deferred to implementation*. The lifecycle is fixed:

1. `sol cloud apply` creates the destination infrastructure **and** the fenced
   reconciler identity from the `authorization` root. The reconciler cannot
   create or alter its own fence, and the deploy identity holds no
   IAM-mutating action.
2. The reconciler reconciles **workload identities and grants** from the whole
   workspace authorization graph — target-wide, with **no scope parameter** —
   feeding Terraform the safe grant set Sol computes (`Sol_cli_authorization`):
   desired grants plus grants still observed in use. Additions are never held
   back by a pending removal; a removal is revoked only when undeclared *and*
   unused by a deployed workload; an unobservable deployed state revokes nothing.
3. `sol deploy` consumes established identities and verifies effective access
   **read-only**; it never creates, repairs or mutates authority, and it refuses
   at plan time when a declared grant is not yet effective.

structural IAM-mutation guard; `Sol_cli_authorization` (the safe-grant-set
