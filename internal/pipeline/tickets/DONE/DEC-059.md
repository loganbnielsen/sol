## Question

`sol cloud destroy` destroys the substrate (network, cluster, managed database, registry
ownership, platform) and the application workloads through supported lifecycle operations.
Before the substrate is destroyed, FND-0077 added a **workload release** step: discover the
Sol-owned workloads in the target's declared namespaces, remove them, and wait for their
pods — so a managed database is not asked to drop while the application still holds pooled
sessions.

When that release fails, the destroy currently **degrades and continues**: it warns, and then
still runs `terraform destroy`.

The question resolved here:

> If Sol cannot establish that the application workloads have been released before substrate
> destruction, should a normal `sol cloud destroy` stop rather than continue?

## What the code does today

`Sol_cli_cloud_destroy.execute` (`cli/lib/cloud/sol_cli_cloud_destroy.ml:345-357`) calls
`deps.release_workloads ()`; on `Error message` it records a degradation and calls
`deps.destroy_substrate ()` anyway:

```
Releasing the application workloads...
warning: the workloads this target deployed could not be released: <message>. A managed
database whose sessions they still hold refuses to be dropped, so the teardown below may
not converge; if it does not, nothing here claims it did
[deps.destroy_substrate ()]
```

The release (`cli/lib/cloud/sol_cli_cloud_wiring.ml:811-850`) runs as the target's **deploy
identity**, is scoped to the **declared** namespaces, reads each namespace's
`deployment,cronjob,job` (PR #818 broadens this), keeps the workloads whose **pod template**
carries `workspace=<workspace>`, removes them by name with `--wait=true --timeout=300s`, and
then waits for the workspace-labelled pods to go. A release failure is any of: the target's
destination cannot be resolved; a namespaced listing fails; the JSON cannot be read; a named
deletion fails; or the pod wait times out.

The final success claim stays fail-closed regardless: if `destroy_substrate` fails, or the
independent absence verification cannot establish convergence, the destroy exits non-zero and
claims no absence (`Sol_cli_destroy_verification`; FND-0069).

The degrade rule is enforced by `internal/ci/check_workload_release_order.py:74-78`, which
fails the guard if the release block contains `fail (`, and by
`internal/ci/test_cloud_lifecycle_offline.sh:558-577` and
`cli/test/test_cloud_destroy.ml:704-720`, which assert a release failure still finishes the
teardown.

## The rationale that was recorded for degrade-don't-block

FND-0077 states it directly:

> A release failure is a **degradation**: it is reported and teardown continues, because a
> teardown must not be blocked by a step that can fail. Final success stays fail-closed — if
> the substrate destroy or the independent absence verification cannot establish convergence,
> no absence is claimed.

The same rule is a deliberate architecture elsewhere. ADR 0003 invariant 6:

> **A failed or partially installed target is always destructible.** … Destruction also
> observes deliberately less than apply: … a destroy decides only Absent-ness, and never
> depends on a probe that could fail and block teardown.

FND-0069 records the boundary of the rule the same way: a *cleanup* failure degrades and the
substrate destroy proceeds, while a *substrate destroy* failure fails the run and a *platform
teardown* failure blocks. Those distinctions must survive this decision.

## Evidence that the rationale does not extend to the workload release

The rule is correct for a **probe whose only job is to classify the target** (ADR 0003
invariant 6) — a failed read must not make a half-built target immortal. It does not follow
for a **removal that exists to enforce a data boundary**: a step whose stated purpose is to
ensure a managed database is not dropped while clients hold it, and which then proceeds after
it has positively observed that it could not stop those clients, is not enforcing the boundary
it exists for.

The live record shows the cost. On specimen `sol-qual-gcp-32`, the release found
`deployment/notify-worker` and `deployment/charge-svc`, could not remove them (the pre-fix
selector matched nothing), the pod wait timed out, and the substrate destroy ran anyway:

```
warning: the workloads this target deployed could not be released: ... timed out waiting for
the condition on pods/notify-worker-...
[terraform-destroy] FAILED (613.2s)
    Error: ... failed to delete database app. Detail: pq: database "app" is being accessed by
    other users., invalid
```

The harness's independent inventory afterwards: `gke-cluster absent`, but
`sql-instance`, `network`, `address-regional`, `address-global` all `PRESENT` —
`teardown NOT verified: resources remain`. So degrade did not merely warn: it **partially
destroyed** the target and left a state that is neither absent nor usable, and which a second
invocation had to reason about.

Three things follow:

1. **The final absence claim is not the problem — the partial destruction is.** Degrade never
   claims false absence. The defect is an avoidable half-teardown on the first run.
2. **The boundary is delegated to the provider.** On GCP the provider refuses to drop a
   database with open sessions, which is why the failure surfaces at all; AWS RDS does not
   refuse. Nothing in Sol's contract makes the boundary provider-independent, so a provider
   change would silently move it.
3. **DEC-038 already states the principle.** *A read that failed is not an absence of
   evidence.* The destroy currently treats a failed read as licence to proceed; the release
   should treat it as *absence not established*.

## Decision (2026-10-01)

**A `sol cloud destroy` that cannot establish the application workloads are released stops
before it destroys the substrate.** The workload release is a destruction-time precondition,
not a best-effort preparation, because [it exists to keep Sol from asking a provider to drop
durable application state while the workloads that own it may still be running].

### The classification

| Release outcome | Meaning | Normal destroy |
| --- | --- | --- |
| The target declares no workload namespaces | The release has no scope | Proceed — precondition does not apply |
| The substrate is already absent | There is no substrate and no cluster | Proceed — precondition does not apply; a re-destroy stays idempotent |
| A namespaced listing succeeded and found no Sol-owned workload | Workloads are absent | Proceed — absence established |
| A workload kind the cluster genuinely does not serve (an unserved CRD, e.g. `rollout`) | That kind cannot be running | Proceed — absence of that kind (INFRA-097) |
| Workloads found, removed by name, pod wait succeeded | The clients are gone and their sessions closed | Proceed — release established |
| The listing ran against a cluster that answered and failed (refused, decode failure, API error) | Sol could not establish absence on a live cluster | **Stop before the substrate** |
| A named deletion failed | Sol found the clients and could not stop them | **Stop before the substrate** |
| The pod wait timed out | Sessions may still be open | **Stop before the substrate** |
| The cluster/context cannot be reached at all | There is no cluster in which the workloads could run | Proceed, recorded as a degradation; see the carve-out |

A **stop** destroys nothing, claims no absence, exits non-zero, and names the namespace, the
kind and the operation that failed, together with the two ways forward (resolve the release,
or pass the override). It is a distinct failure from a substrate destroy that failed and from
a platform teardown that failed.

### The no-cluster carve-out

The precondition does not apply when the release cannot run because there is no cluster to
release from — the substrate is absent, or the target's cluster cannot be reached. Blocking
there would strand infrastructure, which ADR 0003 invariant 6 forbids, and would make a
destroy of an already-absent target fail instead of being idempotent. The release records a
degradation, and the substrate destroy's own fail-closed outcome and the independent absence
verification remain the backstop. Implementation must distinguish *the cluster answered and
refused* (stop) from *there is no reachable cluster* (not applicable); an API error must never
be read as absence.

The residual risk is named rather than hidden: if the cluster is unreachable because of a
transient partition while the application is in fact running and holding sessions, the destroy
can still drop state the application is attached to. That risk is bounded by the provider's
own guards (GCP refuses) and by production retention (DEC-033 keeps a final snapshot; *a
destroy should not be a data-loss event*), and it is the price of not stranding a target whose
cluster cannot be reached.

### The override

An explicit operator override permits destruction despite an unestablished release. It is
named for what it accepts — **`--accept-unreleased`**, alongside `--accept-unresolved` and
`--confirm-ecr-removal` — never the default, and the completion message records that the
destroy proceeded with the workloads unreleased, so the absence check, not the release,
decided the outcome. A generic `--force` is not used: it reads as a blanket bypass, and
DEC-033 records the concern that an operator or harness argument lets a caller take a safety
default silently. A target-declared form (`release_failure: proceed`) is the DEC-033-consistent
alternative for automation that needs a durable setting; it is not required by this decision.

## Why this and not the alternatives

| Option | Verdict |
| --- | --- |
| **Preserve degrade-don't-block** | Rejected. It permits the observed partial destruction, and it delegates a Sol boundary to provider-specific refusal. Its valid core — never strand — is preserved by the no-cluster carve-out and the override. |
| **Blanket fail-closed on every release failure** | Rejected. It would block a destroy whose cluster is absent or unreachable, reintroducing the immortal-broken-target failure that ADR 0003 invariant 6 and FND-0069 exist to prevent, and breaking idempotency. |
| **Fail-closed with the no-cluster carve-out and an override** | **Chosen.** Sol enforces the boundary whenever it has a live cluster to act on; it does not strand a target it cannot reach; the operator can always choose destruction. |
| **Wait for the provider to report the sessions gone** (FND-0077's alternative) | Rejected as the mechanism. Provider session counts are provider-native and would put provider semantics into generic teardown; removing the clients is the provider-neutral form of the same guarantee. |

## Recovery and idempotency

- A blocked destroy destroys nothing, so a re-run starts from unchanged state. Resolve the
  release — bring the workload down, or repair the deploy identity's authority over the
  declared namespace — and re-run; the release succeeds and the substrate destroy follows.
  This is strictly better than today, whose first run can leave partial state.
- If the substrate destroy fails after an override (GCP still refuses the database), the run
  fails closed and claims no absence. The next run finds the cluster gone or unreachable, the
  release is not applicable, and the destroy converges — FND-0077's recovery, made explicit
  rather than incidental.
- A destroy of an already-absent target is unchanged: the substrate is absent, the release is
  not applicable, and the run still reports verified absence.

## Consequences

- **Provider.** GCP becomes deterministic: Sol enforces the boundary instead of relying on the
  provider's refusal, so the behaviour no longer depends on a provider property. AWS gains an
  early stop where it previously could exit 0 with workloads never released — rare, because the
  deploy identity has namespace access and the kinds are built-in, but real for RBAC drift or a
  transient API failure.
- **UX.** The failure becomes an error that names the namespace, kind and operation and the
  override, instead of a warning that teardown continued past.
- **Automation / CI.** The qualification harness runs `sol cloud destroy` after every failed
  attempt (FND-0058, FND-0069). A disposable specimen whose release cannot be established may
  pass `--accept-unreleased` — correct, because its data is disposable and the alternative is a
  stranded specimen — and the run record must state that it did. The offline lifecycle
  scenario that currently proves "a release failure degrades and the teardown still finishes"
  inverts, and the fake substrate destroy must model the database refusal so the scenario can
  actually reproduce FND-0077 rather than always succeeding.
- **Compatibility.** Pre-alpha; no backwards-compatibility constraint (the repository policy).
  `sol cloud destroy` keeps its 0/1 exit codes.
- **Demo / example.** Not applicable: this changes an internal teardown precondition, no
  `sol.toml` field, CLI surface or generated manifest an application author uses. Stated for
  the record.
- **DEC-022 language parity.** No application-facing convention changes: the workload-release
  contract is platform-internal and applies identically regardless of application language.
  Stated for the record.

## Affected invariants

1. **ADR 0003 invariant 6 — preserved, and clarified.** A failed or partially installed target
   stays destructible: the carve-out keeps an absent or unreachable cluster from blocking, and
   the override keeps an operator in control. What narrows is which steps the rule licenses:
   "a step that can fail" no longer covers a removal that enforces a data boundary. ADR 0003
   should gain one line recording that scope.
2. **FND-0069 — unchanged.** A cleanup failure still degrades and the substrate destroy
   proceeds; a platform teardown failure still blocks; a substrate destroy failure still fails
   the run. Those are different steps.
3. **DEC-038 — reinforced.** A read that failed while the cluster answered is not absence, and
   now stops rather than licensing teardown.
4. **DEC-044 / DEC-040 — unchanged.** Verified absence is still the library's verdict; the stop
   claims no absence.
5. **DEC-033 / ADR 0004 — supported.** Destroy remains a recovery-preserving event, and the
   release protects the running-client boundary before the database is dropped.
6. **DEC-045 — unchanged.** The release removes; it never constructs.

## Non-goals

- **Do not fold this into INFRA-097 / PR #818.** That ticket adds the `Rollout` kind under the
  current contract, and that change remains correct: an unserved optional kind is absence, not
  a failure. It should land first; this decision's implementation re-bases the guard afterwards.
- **Do not turn the release into a provider-session probe.** Provider session counts are
  provider-native; the removal stays the mechanism.
- **Do not add a generic `--force`.** The override names the precondition it accepts.
- **Do not weaken the final absence verification** or the platform-teardown / substrate-destroy
  failure boundaries.

## Implementation work this decision requires

1. **Classify the release.** `Sol_cli_workload_scope` / `Sol_cli_cloud_wiring.release_workloads_result`
   return an explicit outcome — *released* (including "no Sol-owned workload", the INFRA-097
   unserved-kind rule, and "no declared namespaces"), *not applicable* (no reachable cluster /
   substrate absent), or *unestablished* with the failing namespace, kind and operation.
2. **Stop before the substrate.** `Sol_cli_cloud_destroy.execute` handles *unestablished*
   before `destroy_substrate`: no destruction, no absence claim, non-zero exit, an actionable
   message, and a new failure variant (distinct from `Substrate_destroy_failed` and
   `Platform_destroy_failed`).
3. **Override.** Add `--accept-unreleased` in `cli/bin/cmd_cloud_tf.ml` and thread it through
   `deps`; record in the completion message that the absence check, not the release, decided.
4. **Guards.** Update `internal/ci/check_workload_release_order.py` and
   `internal/ci/test_workload_release_order_check.py` to require stop-before-substrate while
   keeping every scope / identity / ordering / pod-wait check, with mutations that reject both
   "proceeds past an unestablished release" and "the release no longer runs at all".
5. **Offline lifecycle.** Invert the release-failure scenario in
   `internal/ci/test_cloud_lifecycle_offline.sh`; teach
   `internal/ci/lifecycle_fakes/terraform` to refuse the database drop while pods hold
   sessions, so the scenario reproduces FND-0077; add the override path.
6. **Unit tests.** Re-base `test_a_release_failure_is_reported_and_the_teardown_continues` in
   `cli/test/test_cloud_destroy.ml` and add a case per row of the classification table.
7. **Documentation.** `docs/guides/operations.md` §7, the `destroy_cmd` man page and its exit
   status text, and one line in ADR 0003 recording the narrowed scope of invariant 6.

## Acceptance criteria

- The contract above is recorded as the source of truth and the FND-0077 rationale is quoted
  and superseded with reasons, not silently dropped.
- The classification table is complete: every listed release outcome has a defined destroy
  behaviour, and "cluster answered and refused" is distinguished from "no reachable cluster".
- The implementation tickets above are named, and INFRA-097 / PR #818 is explicitly left to
  land under the current contract.
- A stop claims no absence and destroys nothing; the override is explicit, named for what it
  accepts, and recorded in the completion message.
- The guard, the offline lifecycle harness and the unit tests encode the new contract, and a
  mutation that lets the destroy proceed past an unestablished release is rejected for the
  reason under test.
- ADR 0003's invariant 6 and FND-0069's cleanup/platform/substrate distinctions are stated as
  preserved, with the narrowed scope of the rule recorded.

## Completion notes

**Premise verified before starting (2026-10-01).** `soldev pipeline check DEC-059` reported
`status: actionable`, and the work it itemises was still missing at `3ff69327`:
`Sol_cli_cloud_destroy.deps.release_workloads` returned `(unit, string) result`, `execute`
recorded a release failure with `degrade` and called `destroy_substrate` regardless, no
`--accept-unreleased` existed in `cli/bin/cmd_cloud_tf.ml`, and `Sol_cli_workload_scope` had no
classification of the read. INFRA-097 / PR #818 had landed, as this decision required it to.

**What changed, item by item.**

1. **The release is classified.** `Sol_cli_workload_scope` now owns the classification and the
   discovery that produces it: `read_workloads ~run ~namespaces ~workspace` walks the declared
   namespaces and the declared kinds, and answers `(scope list, read_error) result` where
   `read_error` is `No_cluster of string` or `Read_unestablished of release_failure`. A
   `release_failure` carries the namespace, the kind it was reading, the operation and the
   reason. The release outcome is `Workloads_released | Workloads_not_releasable of string |
   Workloads_unestablished of release_failure`; the removal and the pod wait complete it in
   `sol_cli_cloud_wiring.release_workloads_result`.
2. **The destroy stops before the substrate** — and, deliberately, before anything else.
   `execute` takes the release decision *before* `teardown`, not immediately before
   `deps.destroy_substrate ()`, because otherwise a stop would already have destroyed the
   platform and the temporary bootstrap authority, and this contract's "a blocked destroy
   destroys nothing, so a re-run starts from unchanged state" would be false. `release_decision`
   returns the new `Release_unestablished of string` failure, distinct from
   `Substrate_destroy_failed` and `Platform_destroy_failed`; `completion_message` renders it
   through `failure_message`, which says nothing was destroyed, that no absence is claimed, and
   names both ways forward. `exit_code` is unchanged (1).
3. **The override.** `--accept-unreleased`, single-sourced as
   `Sol_cli_cloud_destroy.accept_unreleased_flag` so the message that offers it and the flag that
   accepts it cannot drift, threaded through `deps.accept_unreleased`. It is not the default, and
   its run records that the absence check, not the release, decided the outcome. No `--force`.
4. **The guard and its suite** are re-based: the read is per kind and namespaced, the ownership
   label, the removal by name, the pod wait, the declared scope, the deploy identity, the layer
   graph and the no-release-store rule are all held as before; added are the classified outcome,
   the stop (`| Error stopped -> stopped`), the override gating it, the absent-substrate skip, the
   absence of the superseded degrade wording, the reachability carve-out bounded before the first
   answer, the absent-namespace and unserved-kind absences, `--ignore-not-found`, and the
   substrate destroy being unreachable outside the release's released branch. Twenty-seven
   mutations are rejected, each for the reason under test, and the unmutated tree is accepted.
5. **The offline lifecycle scenario is inverted** and now proves both directions:
   `RELEASE_DELETE_FAILS=1 DATABASE_REFUSES_UNRELEASED=1` stops, exits non-zero, reports the
   namespace, operation and override, and the log shows **no** `terraform … destroy` at all; the
   same run with `--accept-unreleased` proceeds, `internal/ci/lifecycle_fakes/terraform` refuses
   the database drop because the pods were never released (reproducing FND-0077's
   `is being accessed by other users`), and the run fails closed with no absence claimed. The
   fake's pod wait writes the marker the fake terraform reads, so the refusal models the
   dependency rather than asserting it.
6. **Unit cases cover the rows of the classification table** — no declared namespace; an unserved
   kind; a declared namespace that does not exist; a live cluster that refuses the read; a listing
   that cannot be decoded; a cluster that cannot be reached at all; a cluster that answered and
   then went away; released; not-releasable recorded as a degradation; unestablished stopping with
   nothing destroyed (platform, authority and substrate all untouched); and the override
   proceeding with the record `cli/test/test_cloud_destroy.ml` — 77 cases green.
7. **Documentation.** `docs/guides/operations.md` §7, the `destroy_cmd` man page with its exit
   status text, `docs/reference/cli.md` (regenerated, so the new flag is documented), one
   paragraph in ADR 0003 narrowing what invariant 6 licenses, and a superseded-in-place note in
   FND-0077 so its degrade rationale is quoted rather than silently dropped. The contract itself
   is recorded in the guard's module docstring, which is where a reader of the mechanism meets it.

**Two rows DEC-059's table implies, and what they cost.** A declared namespace that does not
exist is read as absence of that scope rather than a failed release: a target whose apply never
created its namespace must stay destructible, which is the carve-out's own purpose. And a target
whose substrate is already absent skips the release entirely rather than attempting a kubectl
call against a cluster that is not there — otherwise every idempotent re-destroy would print a
degradation for a precondition that never applied.

**This supersedes the first implementation of the decision (`#821`, merged as `806514da`).**
Another actor landed `#821` at 16:56Z, minutes after this work began, and it did not meet three
