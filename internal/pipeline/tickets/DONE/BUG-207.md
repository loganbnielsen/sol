**Depends on:** None.

## Premise verified

`cli/lib/cloud/sol_cli_cloud_wiring.ml` removes bootstrap access after an install attempt, including failure. The AWS retry ran as steady-state `cluster-access` and was forbidden from platform RBAC mutations. GCP also removed access after its failed install. The GCP retry outcome has not been observed. Under DEC-034 the AWS cloud provisioner intentionally has no cluster access entry; bootstrap admin is temporarily associated with the separate cluster-access principal. Therefore the missing provisioner entry and its Unauthorized kubeconfig do not demonstrate a broken acquisition path. Current cloud apply already plans `provisioner_bootstrap_admin=true`; the exact retry command and effective grant must be traced before changing this logic. The failed objects are in `default` and `kube-system`, outside the steady-state platform namespace bindings.

## Retry evidence observed

The AWS retry was the harness re-running `sol cloud apply`, which resumed as `cluster-access`. The
only manual re-acquisition attempted was `terraform apply -var=provisioner_bootstrap_admin=true`
against the saved cluster root — the form the GCP records show Sol planning — and it created no EKS
access entry: `aws eks list-access-entries` afterwards listed only `cluster-access`, `deploy`,
`operator` and the node role, and the provisioner's kubeconfig answered `Unauthorized`. The durable
lesson stands on its own: the retry must reacquire the window rather than assume it survived. That
sequence, with the exact commands and their outputs, is recorded in
`internal/qualification/records/2026-10-04-alpha7-cloud-campaign.md` — not on a machine-local path,
so it survives the host it was observed on.

Adjacent, and owned elsewhere: the failed-apply recovery that looked up the database by an unindexed
address and skipped its protection-disable preparation is **BUG-209** (stream A). Expect that
recovery path to appear inside this ticket's resume boundary; do not fix it here.

## Remediation

Trace the observed retry entry point and bracket acquisition, including the principal carrying the temporary grant, plan precedence and effective-access propagation. Make the supported retry reopen and verify the temporary install window before reconciling an incomplete platform, with removal on every exit. Preserve the steady-state access boundary; do not grant permanent installation rights to `cluster-access` or `operator`. Surface the original platform failure and the retry procedure separately from an authorization failure.

## Acceptance criteria

- Simulate an install failure, verify the temporary grant is removed, retry, and observe a bounded grant restored for reconciliation and removed again after success or failure.
- Test AWS and GCP lifecycle paths and a post-failure destroy.
- Example impact: none; this repairs internal cloud lifecycle. Language-parity impact: none; both languages share it.

## Retry characterization (2026-10-04)

The harness's `phase_cloud` runs `sol cloud plan` and then `sol cloud apply`
(`internal/qualification/aws/live-row.sh`), so the retry **entry point** is the
plan. The saved retry log (`/tmp/sol-aws-alpha8-run1/cloud-plan.log`, run
`cloud-apply-20261004T190201Z-78879`) shows the refusal came from the platform
plan, not from the harness's `cloud apply` step, which never ran:

- **retry command** — `sol cloud plan qualalpha7/aws/us-east-1 --var-file …`,
  the first step of the re-run `cloud` phase;
- **principal** — `arn:aws:sts::…:assumed-role/sol-qual5-cluster-access/EKSGetTokenAuth`;
- **intended temporary grant** — `AmazonEKSClusterAdminPolicy` associated with the
  cluster-access access entry by `provisioner_bootstrap_admin=true`;
- **actual effective permissions** — the steady-state `sol:platform-provisioners`
  grants (`*` inside the platform namespaces, plus the cluster-scoped
  `sol-platform-provisioner-cluster` role). That set satisfies the Required half
  of `provisioner_authorization_checks`, but it cannot read the platform root's
  `default`/`kube-system` objects, so `get roles -n default` and
  `get configmaps -n kube-system` are forbidden;
- **where authority is removed** — `Sol_cli_cloud_apply.execute`'s failure path
  calls `remove_bootstrap_access` (`terraform apply -var=provisioner_bootstrap_admin=false`)
  after the platform apply fails; AWS attempt 2 recorded
  `[provisioner-bootstrap-access-remove] ok (11.5s)`. The window was gone before
  the retry, as designed, and the retry relies on `cloud apply` reopening it.

The defect: `sol cloud plan` gated the platform on `provisioner_rbac_established`,
which is true precisely when the window is **closed** (the Forbidden checks pass)
and false when it is open. The plan therefore attempted a privileged whole-root
platform plan under the steady-state identity and surfaced an authorization
error instead of a deferred phase and the retry procedure.

## What landed (2026-10-04)

`platform_plan_phases` takes `~install_window_open` and defers the whole-root
platform substrate when the window is closed, with the reason
``requires the installation window that `sol cloud apply` opens``. The window is
detected by the bootstrap-only capability set (`can-i escalate clusterroles`,
`can-i bind clusterroles`) — the same discriminator the AWS window machinery uses,
and one the GCP cluster-admin binding also satisfies. `Sol_cli_cloud_wiring.plan`
probes it read-only; when it is open the whole-root platform is planned as before,
and the prerequisites/substrate still defer on their own prerequisites (cloud
substrate, steady-state RBAC, CRDs). No grant was widened: the fix is in the plan
gate, not the provisioner RBAC, so the steady-state boundary is unchanged.

## Remaining limitation

GCP's `bootstrap_window` is still `Closed_by_platform_root`, so the apply opens
and uses the window but does not run the AWS-style positive/negative capability
verification (`sol_cli_aws_cluster.ml`). That asymmetry predates this ticket and
is recorded rather than absorbed; it is a GCP identity-path gap, not the
demonstrated AWS resume failure.
