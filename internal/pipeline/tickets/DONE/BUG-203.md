**Depends on:** None.

**Premise (verified 2026-10-04 at `origin/main @ d0cff2f6`):** holds.
`framework/ocaml/sol-jobs/lib/sol_jobs.ml` `renew_q` extends `locked_until` only
`WHERE … AND locked_until > now()`. A heartbeat that wakes after the lease has already
lapsed therefore matches no row, logs `sol-jobs: lease lost` (`action=renew`) and stops
renewing for the rest of the handler — even though no other poller has claimed the job and
the handler is still alive. The row is then claimable by any poller for the rest of the
handler's life.

## Problem

A renewal's job is to keep a live claim exclusive while the handler runs (BUG-103). The
`locked_until > now()` guard makes that hold only if *every* heartbeat lands inside the
lease window: one delayed heartbeat — a scheduling stall, a slow pool checkout while
another poller holds the connection, a loaded CI runner — permanently surrenders the
claim, and the next poller to run the claim query executes the handler concurrently.

Two handlers then execute work that should be fenced. BUG-050's fenced finalize keeps the
*row* consistent, but it cannot undo a second execution of the side effect.

Observed: `main @ d0cff2f6`'s post-merge `test` job failed `sol_jobs_pg › lease fencing
(BUG-050) › long handler renews its lease` with `one handler ran: Expected 1, Actual 2`,
on a commit that changes only markdown, while the same content passed the pull request's
own `test`. The re-run passed, so it was intermittent: the runner stalled a heartbeat past
the test's 0.1 s lease.

Reproduced deterministically with the Postgres suite (`test_sol_jobs_pg.ml`, "a late
heartbeat keeps an unclaimed lease"): the handler lapses its own lease without advancing
`attempts`, a second poller runs, and the unmodified library reports `one handler ran:
Expected 1, Actual 2`. The same test passes with the remediation below, five runs in a
row and 40 runs under CPU and Postgres load.

**BUG-050's framing is stale.** It says leases are "set once and never renewed" and that
finalize is keyed on `id` only; BUG-103 added renewal, and BUG-050 keyed finalize on
`attempts`. The fencing BUG-050 introduced still holds and is unchanged — what is
inaccurate is its description of the mechanism.

## Remediation

Drop the `AND locked_until > now()` guard from `renew_q`. The claim
(`id`, `attempts`, `workspace`, `status = 'pending'`) is the correctness fence: if another
poller re-claimed the row its `attempts` moved, and if the row left `pending` the renewal
correctly stops and logs. A heartbeat that lands after the lease lapsed but before any
re-claim still owns the row, so extending it is safe, and it keeps the claim.

## Acceptance criteria

- `test_sol_jobs_pg` "a late heartbeat keeps an unclaimed lease" passes: a handler that
  lapses its own lease with `attempts` unchanged keeps its claim, and no second poller runs.
- The new test fails on the guarded (`locked_until > now()`) renewal for the reason under
  test (`one handler ran: 1 ≠ 2`) — mutation-checked.
- `sol-jobs.md` states the renewal predicate and what `lease lost` now means.
- `test_lost_renewal_is_logged` and `test_expired_holder_cannot_complete_terminal_row`
  still pass: a real re-claim and a terminal row still stop renewal and log.
- Language parity: `sol-jobs` has no TypeScript implementation (DEC-022, deferred; the
  contract lives in FEAT-080's capability matrix).

## Completion notes

- `renew_q` matches `id`, `attempts`, `workspace` and `status = 'pending'`; the lease-clock
  guard is gone. A renewal that finds a re-claimed or non-pending row still returns no row,
  logs `sol-jobs: lease lost` with `action=renew`, and stops.
- `sol-jobs.md`'s lease paragraph now names the `attempts` fence and states that a
  heartbeat landing after a lapsed lease re-extends it.
- Verified against `postgres:16`: 21/21 `sol_jobs_pg` tests pass, five consecutive runs,
  and 40/40 under CPU oversubscription plus 8 `pgbench` clients.
- No runnable app change: the `sol-jobs` API and example calls are unchanged, and no
  demo/example exercises lease lapses. Language parity: as above, TS has no implementation.
