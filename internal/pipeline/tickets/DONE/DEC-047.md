## The problem

`Sol_cli_config` merges exactly two layers: `sol.yml` and the leaf `sol/<env>/<provider>/<region>.yml`. Environment-wide policy (`profile`, `scale`, `size`, alert routing, `base_domain`, `letsencrypt_email`, `node_failure_headroom_nodes`) has no layer of its own, so every region's file has to repeat it. Pluto's `prod` and `pilot` already repeat `base_domain`, `letsencrypt_email` and `node_failure_headroom_nodes`. A second region in an environment would copy the rest.

## Decision

**Decided 2026-09-25 by the operator.**

1. **The three-layer model is accepted:** `sol.yml` → environment → target, where a lower layer overrides a higher one. File-per-target is dropped.
2. **One file: `sol/environments.yml`.** It is keyed by environment name, and each environment has a `targets:` map keyed `<provider>/<region>`. Target addresses (`<env>/<provider>/<region>`, DEC-031) do not change. The per-target files under `sol/<env>/<provider>/` are removed, with no compat shim (pre-alpha).
3. **`omit` stays sticky.** Once any layer sets `omit: true`, a lower layer can't undo it. Nothing an environment turns off can reappear in one region by accident; a region that needs it gets its own environment.
4. **Key names don't change.** The proposal's sample used a nested `alerts:` block for illustration, but the existing flat keys (`alert_receiver_type`, `alert_receiver_url`, `alert_owner`, `alert_runbook_url`) stay. Renaming them is not part of this decision.

### Key placement and merge rules

"Lowest wins" means the value from the lowest layer that sets the key: target over environment over `sol.yml`. The defaults are today's `merge_target` / `merge_resource` / `merge_service` / `merge_provider_fields` in `Sol_cli_config`, so no existing behaviour changes by accident. Two things are new restrictions, both following from "dev mirrors prod": the **app-shape keys** are `sol.yml`-only, and lower layers **can't declare new services or resources**.

**Top-level and `target` keys**

| Key | Allowed in | Merge |
|---|---|---|
| `project` | `sol.yml` only | — |
| `cluster_name`, `kube_context`, `kubeconfig`, `cluster_endpoint_cidr`, `registry` | target only (they identify one cluster or region) | — |
| `profile` | environment, target (**never `sol.yml`**: today's `reject_shared_profile` refuses it there, because every target would inherit it) | scalar, lowest wins |
| `base_domain`, `cluster_issuer`, `letsencrypt_email`, `observability_backend`, `destroy_retention`, `alert_receiver_type`, `alert_receiver_url`, `alert_owner`, `alert_runbook_url`, `node_failure_headroom_nodes`, `terraform_var_file`, `state_bucket` | `sol.yml` `target:` block, environment, target | scalar, lowest wins |
| provider blocks (`aws:`, `gcp:`) | `sol.yml`, environment, target | **deep-merge per key** within each provider block (today's `merge_provider_fields`) |

**`resources.<name>`** (matched by name)

| Key | Allowed in | Merge |
|---|---|---|
| declaring a resource | `sol.yml` only | an environment or target naming an undeclared resource is an error |
| `type`, `partition_key`, `sort_key`, `indexes` | `sol.yml` only (app shape) | — |
| `size` | any layer | scalar, lowest wins |
| `omit` | environment, target | **sticky:** true at any layer wins |

**`services.<name>`** (matched by name)

| Key | Allowed in | Merge |
|---|---|---|
| declaring a service | `sol.yml` only | an environment or target naming an undeclared service is an error |
| `type`, `path`, `language`, `uses` | `sol.yml` only (app shape) | — |
| `scale.min`, `scale.max` | any layer | **deep-merge:** each is its own scalar, lowest wins, so an environment's `min` and a target's `max` both survive |
| `omit` | environment, target | **sticky:** true at any layer wins |

A key set at a layer it isn't allowed in is a parse error naming the layers where it is allowed, never silently ignored. If an existing target or fixture sets an app-shape key or declares a new service or resource, FEAT-100 reports it in its completion notes rather than quietly widening this table.

## Amendment (2026-09-26): account-specific values live in an untracked local file

**Decided by the operator, found while implementing FEAT-100.** Decision 2's single tracked file had no place for values that must not be committed. Qualification writes real account identity (account IDs, role ARNs, the GCP impersonator, real registries and buckets) into an **untracked** target file under `sol/qual*/`, and `check_no_account_artifacts.sh` refuses to let it be tracked (HARDEN-002 run 2 committed one). With one tracked `environments.yml`, the harness would have to write that identity into a tracked file.

These values aren't secrets in the password sense (passwords and API keys already stay out of config, via `TF_VAR_*` and the secret store). They are account *identity*, which is fine in a user's private repo but not in a public one.

**Amended decision:**

1. **A second, optional file: `sol/environments.local.yml`.** It has the same shape as `sol/environments.yml` and is gitignored (`sol new` adds the ignore entry). It holds this machine's account-specific values.
2. **Disjoint: every key comes from exactly one file.** The local file may set keys the tracked file leaves unset. Setting a key the tracked file already sets is a parse error naming both files. There is no precedence between the two files to learn.
3. **The local file may add whole environments and targets, but never change the ones the tracked file declares.** A qualification `qual` environment therefore lives entirely in the local file, and pluto's tracked file (a user-facing example) carries nothing internal (REFAC-105).
4. **Merge order is unchanged.** The two files are unioned into one environments view first; then `sol.yml` → environment → target applies with the key table above. The disjoint rule means union order can't matter.
5. **Guard.** `check_no_account_artifacts.sh` refuses a tracked `sol/environments.local.yml`, as it refuses `sol/qual*/` today.

Decisions 1, 3 and 4 and the key table are unchanged.
