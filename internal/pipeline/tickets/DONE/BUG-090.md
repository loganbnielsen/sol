Reconcile consumer-group safety state after rollback

**Depends on:** None.

**Premise re-verified (2026-10-02):** At `origin/main` `8ebe2da3` the premise held: `Sol_cli_rollback.execute` re-applied the reconstructed workloads, verified the live set, moved the pointer and verified it, and never touched `Sol_cli_deployment_state`; both deploy commands read that separate workspace ConfigMap for the next group-removal check. What the 2026-09-29 note called "the release record contains no consumer-group list" needed one refinement: the record does carry each workload's `consumes_kafka`, which is enough to derive the restored set without adding a field.

## Problem

Rolling back between releases with different workers leaves the consumer-group guard describing the pre-rollback release. The next deploy may warn about an already-absent group or fail to warn about an actual removal, depending on rollback direction. The latter can let a group disappear without `--confirm-group-change`.

## Remediation

Make the restored release's complete consumer-group set available at rollback and update the guard record as part of the verified rollback transition. Do not advance the guard on failed workload or pointer verification; report a failed guard write visibly so the next deploy cannot assume it is current.

## Acceptance criteria

- Roll back A+B to A and A to A+B; after each, the next deploy's removal check reflects the restored workload set.
- A failed rollback leaves the prior guard state, and an inability to write the corrected guard state is reported as an incomplete transition.
- Cover command-level rollback plus the following deploy check. Update the runnable rollback example or tutorial and record the cross-language verdict.

## Completion notes

- **The restored set is derived from the release record, and the record is corrected last.**
  `consumer_groups_of_release` reads the release's own recorded workloads — `primitive = "worker"` and
  `consumes_kafka` — and names each one `<workspace>.<domain>.<name>`, sorted and de-duplicated the way the
  deploy path names them. `execute` calls the new `record_consumer_groups` dep only after the live set and
  the pointer have both verified, so a rollback that fails verification leaves the guard exactly as it was,
  and a rollback that succeeds leaves the record describing the release that is now live.
- **Failure is visible, not assumed.** A guard write that fails returns an error naming the incomplete
  transition — workloads and pointer restored, safety record stale, with what to do — rather than reporting
  a clean rollback. The pointer is not unwound: the rollback itself did happen, and the message says so.
- **One write path.** `Sol_cli_deployment_state.record_consumer_groups` is the single guard write, and
  `record_outcome`'s `Applied` branch now delegates to it, so the deploy and rollback paths cannot drift in
  how they record.
- **Why `consumes_kafka` rather than the durability config key.** A worker that consumes Kafka carries
  `SOL_KAFKA_DURABILITY` in its recorded config, which is the guard's own rule — but keying the guard off a
  config value would break silently if that value were ever renamed, and a guard that under-reports is the
  dangerous direction. `consumes_kafka` is a recorded field; using it can at most over-report (a worker
  declared with topics but no Kafka resource usage), which prompts a confirmation rather than hiding a
  removal.
- **Coverage.** `cli/test/test_rollback.ml` (60 cases): the success path records exactly the restored set
  as its **last** dep call, asserted for both directions the criterion names — A+B (`myapp.comms.notify_worker`
  and `myapp.logistics.fulfillment_worker`) and A alone — and for a non-worker release (no groups); a failed
  workload verification leaves the guard alone; a failed guard write is reported as an incomplete transition
  while the pointer has still moved. `cli/test/test_deployment_state.ml` (13 cases) now carries the
  "following deploy check": the fake `kubectl` reads back the `consumer_groups` it was given, so after
  `record_consumer_groups` the next `check_removed_groups` passes for the restored set and reports a real
  removal against it.
- **Mutation checks.** Removing the correction fails four cases including the ordered one; moving it before
  the verification fails the ordering and the "failed rollback leaves the guard alone" cases. Both restored,
  rebuilt, re-run green.
- **Demo/example.** `docs/guides/TUTORIAL.md`'s rollback section — the runnable example a user follows —
  now states that a verified rollback corrects the consumer-group safety record to the restored release's
  own set, that a failed rollback leaves it alone, and that an uncorrectable record is reported rather than
  passed off as a clean transition.
- **Language parity (DEC-022).** No application-facing impact: the guard record and the rollback transition
  are CLI-side and language-neutral, so OCaml and TypeScript workspaces are treated identically. No tracking
  ticket needed.
