The documented hook-install recovery cannot run from an owned worktree

**Depends on:** None.

## Problem

`CONTRIBUTING.md` § *If nothing seems to be running* gives one recovery for a stale
hook install: `bash internal/tooling/scripts/install-hooks.sh`. REFAC-090 requires
every agent to work in an owned worktree and out of the canonical checkout — and the
installer cannot run there, because it writes to `$REPO_ROOT/.git/hooks`, which in a
linked worktree is a file, not a directory:

```text
$ cd /home/lbendtly/Code/sol-BUG-113-hook-installer
$ bash internal/tooling/scripts/install-hooks.sh

Installing Sol git hooks...

ln: failed to access '/home/lbendtly/Code/sol-BUG-113-hook-installer/.git/hooks/post-commit': Not a directory
$ echo $?
1
```

The value git itself reports from that same worktree is the shared hooks directory,
which is where hooks belong so that every worktree is gated:

```text
$ git rev-parse --git-path hooks
/home/lbendtly/Code/sol/.git/hooks
```

`internal/ci/test_hook_install.sh` installs only into a scratch repository that is
its own `.git` directory, so nothing caught it. The failure hits exactly the actor
the recovery is written for, and it leaves the local pre-commit gate — the format
check and the authority preflight — silently uninstalled.

## Remediation

Resolve the hooks directory the way git does (`git -C "$REPO_ROOT" rev-parse
--git-path hooks`) instead of assuming `$REPO_ROOT/.git/hooks`. Add the linked-worktree
case to `internal/ci/test_hook_install.sh`: create a worktree of the scratch repository,
run the installer from inside it, and assert every hook lands as a resolving symlink in
the shared hooks directory.

## Acceptance criteria

- `bash internal/tooling/scripts/install-hooks.sh` succeeds from a linked worktree and
  leaves every hook installed as a resolving, executable symlink in the shared hooks
  directory.
- `internal/ci/test_hook_install.sh` fails if the installer goes back to writing
  `$REPO_ROOT/.git/hooks`, for that reason and no other.
- `CONTRIBUTING.md`'s recovery instruction stays correct without adding a "but only from
  the canonical checkout" caveat.

## Completion notes (2026-10-01)

**Premise:** confirmed by running the recorded command in this worktree — the installer exited 1
with `ln: failed to access '<worktree>/.git/hooks/post-commit': Not a directory`, and installed
nothing.

- `install-hooks.sh` resolves `HOOKS_DEST` with `git -C "$REPO_ROOT" rev-parse --git-path hooks`, so a
  worktree run installs into the shared `.git/hooks` — where git runs hooks from, per BUG-023's
  record — and gates every worktree.
- `test_hook_install.sh` gained the linked-worktree case: the scratch repository is committed, a
  worktree is added, the hooks are removed, the installer runs from inside the worktree, and every
  hook must land in the shared directory as a symlink resolving to its source. The scratch commit
  uses `--no-verify`, because the installed hook under test is a real hook and the scratch repository
  carries no `internal/ci/`.
- Mutation-checked: reverting only `HOOKS_DEST` to `$REPO_ROOT/.git/hooks` fails the new case with
  `[FAIL] install-hooks.sh failed from a linked worktree` (`ln: failed to access
  '<worktree>/.git/hooks/post-commit': Not a directory`), while the four pre-existing expectations
  still pass — so the case catches the defect under test and not something else.
- No documentation change was needed: `CONTRIBUTING.md` states the command, not a directory.
- **Demo/example coverage:** internal contributor tooling; no runnable app example applies, per the
  exemption rule. The runnable artefact here is the scratch-repository guard test.
- **TypeScript parity (DEC-022):** no language-parity impact — local git hooks and the installer are
  repository tooling, invisible to application languages.
