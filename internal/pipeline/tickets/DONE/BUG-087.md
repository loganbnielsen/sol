Read scoped sol up release boundaries under the workspace lease

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `4bde298f`, `cli/bin/cmd_up.ml:370-383` reads `retained_for_plan` before `with_boundary_lease`; `cli/lib/deploy/sol_cli_deploy_run.ml:260-275` is the positive control that reads it after acquiring the same lease. The source audit records the complete interleaving and verification limit.

## Problem

A scoped `sol up` snapshots the current release boundary before it holds the workspace lease. Before it acquires the lease, another deploy or rollback can change the pointer. When `sol up` later acquires the lease, it applies its selected workload and records out-of-scope workload specs and provenance from the stale boundary. The new current release can describe a workspace state that was never applied; rollback to it can restore stale workloads.

## Remediation

Move the retained-boundary read and validation into the `with_boundary_lease` callback, before applying any service. Keep the scoped refusal when the current boundary is unreadable. Read retention's previous pointer under the same lease so the release and pruning decisions share one boundary epoch.

## Acceptance criteria

- Exercise a pointer change after the local command starts but before it acquires the lease; the scoped release inherits the boundary that is current when the lease is acquired.
- A scoped deploy with an unreadable current boundary still refuses before any workload mutation; a whole-workspace deploy still supersedes the boundary.
- The regression exercises command ordering, not only `Sol_cli_release.of_plan_with_boundary` on preselected records.
- Update the runnable scoped `sol up` / rollback example or tutorial to demonstrate the preserved boundary; record the cross-language verdict in completion notes.

## Completion (2026-09-29)

- **Premise re-verified** at `origin/main` `4bde298f`: `cmd_up.ml` read `Sol_cli_release_store.retained_for_plan` before `with_boundary_lease`, while `deploy_run.ml` (the positive control) reads it inside the lease callback. A deploy or rollback that won the lease in between left `sol up` recording out-of-scope workload specs and provenance from a stale boundary — a release describing a workspace state that was never applied.
- **Change.** The sequence now lives in one place with a name and a contract: `Sol_cli_boundary_epoch.run { acquire_lease; read_boundary_holding; apply }` acquires the lease, *then* reads the boundary, *then* applies, short-circuiting on a read error. `read_boundary_holding` takes the held lease, so "read the boundary without holding it" is not expressible against the signature — the ordering is enforced by the type rather than by call-site discipline, and the field name carries the contract because `cli/lib` `.mli` files carry no prose (`check_no_comments.sh`; documentation lives in the co-located spec or the ticket). `cmd_up.ml`'s apply path delegates to it, which is what makes the shipped ordering the tested one; the scoped refusal for an unreadable boundary is carried through unchanged and still arrives as the command's failure, and the previous-pointer read (`read_previous_release`) was already inside the callback, so release and pruning decisions share one boundary epoch.
- **Tests.** New `cli/test/test_boundary_epoch.ml` runs the epoch with a lease whose acquisition changes the boundary first (the other-actor-wins-the-race case) and asserts `apply` received the boundary current *after* acquisition — this fails against the old ordering, which is what the third case documents; a second case asserts an unreadable boundary refuses before `apply` runs at all. Mutation note: the old read-before-acquire shape cannot be written against this signature, so the regression relies on the type for the ordering and on the command delegating to it. A future `cmd_up` that bypassed the seam would be caught in review, not by this test; folding the local apply path into `Sol_cli_deploy_run`'s tested one would put the command itself under test and is worth its own ticket if we want that.
- **Runnable example.** `docs/guides/TUTORIAL.md`'s scoped-`sol up` note now says the inherited boundary is read while the workspace lease is held, so the release a scoped `sol up` records describes the workspace at apply time — a deploy or rollback that won the lease first is what the new release builds on.
- **Cross-language verdict:** no impact. This is the OCaml CLI's local-deploy path; the TypeScript runtime consumes the manifests Sol renders and has no boundary/lease concept of its own.
