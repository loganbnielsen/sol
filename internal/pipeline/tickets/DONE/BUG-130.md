## Problem

`sol local infra up` decides the k3d cluster exists through `k3d cluster get sol-local`, but
installs every Helm release (Redpanda, PostgreSQL, Loki, Grafana, Alloy, Tempo, Prometheus,
ingress-nginx) through `Sol_cli_helm.upgrade_install`, which builds a `helm upgrade --install …`
argv with **no `--kube-context`**. Helm therefore resolves the cluster from the ambient
kubeconfig's current-context.

Observed 2026-10-03 on this host, with the k3d `sol-local` cluster healthy and its platform
already running, and `~/.kube/config`'s current-context a stale `sol-qual11-…-deploy` EKS context:

```text
$ sol local infra up
[1/4] Provisioning cluster...
  cluster sol-local already exists, skipping
[2/4] Reading the workspace's declared resources...
  kafka=true   postgres=true   loki=true   prometheus=true   tempo=true
[3/4] Deploying infra...
  Redpanda       installing...
  Redpanda       FAILED (exit 1)

--- Redpanda output ---
  $ 'helm' 'upgrade' '--install' 'redpanda' 'redpanda/redpanda' '--namespace' 'redpanda' '--create-namespace' '--version' '26.1.11' … '--wait' '--timeout' '3m'
Error: Kubernetes cluster unreachable: Get "https://…gr7.us-east-1.eks.amazonaws.com/version": …
error: local infrastructure installs: Redpanda failed, …
```

The same command printed `cluster sol-local already exists` and then talked to the ambient
cluster. That is the failure mode DEC-020 exists to remove — *"Every Kubernetes operation becomes
target-scoped: `--context` for kubectl, `--kube-context` for helm, or a scoped `KUBECONFIG`"*.
`Sol_cli_kube_destination.local_context` already supplies `--kube-context k3d-sol-local`
(`helm_args`), and the neighbouring `kubectl` path (`apply_yaml`) passes it; only the Helm
install path lost it.

**Why high.** On this host the ambient context pointed at a deleted cluster, so the run failed
loudly. On a machine whose current-context is a live cluster, `sol local infra up` installs Sol's
local platform — Redpanda, PostgreSQL, Loki, Grafana and the rest — **into that cluster**, under
the same object names it uses locally. `kubectl --context` and `helm --kube-context` are two
halves of one invariant; the local path leaked the ambient read through the half nobody
re-checked.

The same ambient read has a second, quieter symptom. `sol local infra status` prints
`Cluster: sol-local ✓ running` and then an **empty `Pods:` list**, because it runs a raw
`kubectl get pods -A` and swallows the error. On this host, with the stale ambient context:

```text
$ sol local infra status

Cluster:  sol-local  ✓ running

Pods:

Port-forwards:
  …
```

With the local context the same command lists 20+ pods. The operator's own view of the local
platform therefore depended on which cluster the machine happened to be pointed at.

## Remediation

- `Sol_cli_helm.upgrade_install` takes `~ctx:Sol_cli_kube_destination.context` and appends
  `Sol_cli_kube_destination.helm_context_args ctx`; the argv construction becomes a pure
  `upgrade_install_argv` so it is directly testable.
- `cmd_local.ml`'s `helm_install_job` passes `Sol_cli_kube_destination.local_context`.
- `cmd_local.ml`'s `dev_status` reads pods through `Sol_cli_kubectl.get_raw` with the local
  context, and prints a `could not read pods:` line on failure instead of an empty list.
- Regression tests assert the local install carries `--kube-context k3d-sol-local`, and that a
  different context is carried through verbatim — the value is the caller's, not hard-coded.

## Acceptance criteria

- `sol local infra up` completes against `k3d-sol-local` while the ambient kubeconfig's
  current-context names an unreachable cluster.
- `sol local infra status` lists the local cluster's pods in that same condition, and a failed
  pod read is reported rather than shown as an empty list.
- A bogus context fails closed naming the context (`context "…" does not exist`), never falling
  back to whatever cluster the ambient kubeconfig names.
- The `upgrade_install_argv` tests fail when `--kube-context` is removed or changed
  (mutation-checked).
- Language parity: no application-facing contract change; state that in one line.

## Reproduction (2026-10-03)

Run from a workspace (`examples/pluto`) with a k3d `sol-local` cluster running and
`kubectl config use-context <some-unreachable-context>`, then `sol local infra up` and
`sol local infra status`. The install fails against the unreachable context while step 1 reports
`sol-local` present, and the status pod list is empty.

## Completion notes (2026-10-03)

- **Fix.** `Sol_cli_helm.upgrade_install ~ctx` appends `--kube-context`;
  `helm_install_job` passes `Sol_cli_kube_destination.local_context`; `dev_status` reads pods
  through `Sol_cli_kubectl.get_raw ~ctx:local_context` and reports a failed read.
- **Live, the failing condition reproduced.** `~/.kube/config` current-context
  `sol-qual11-116c2637-deploy` (unreachable). Before: `sol local infra up` failed at Redpanda
  against the EKS endpoint. After: `up` completes with all seven releases `ok` and the endpoint
  summary, and `sol local infra status` lists the pods. With a bogus context the install fails
  closed: `Error: Kubernetes cluster unreachable: context "mutated-context" does not exist`.
- **Mutation.** Replacing the context in `upgrade_install_argv` with a fixed value makes
  `helm_argv: the local install targets k3d-sol-local` and
  `helm_argv: upgrade install follows its context` fail; removing the `--kube-context` argument
  does not compile because `~ctx` would be unused.
- **Tests.** `dune build @cli/test/inline/runtest`: `Test_tool_adapters` green. The two
  `Test_scaffold` compile tests fail identically on unmodified `origin/main` (they build a
  scaffold and need a working opam toolchain in the test sandbox) — environmental, not this
  change.
- **Language parity.** No application-facing contract change — a CLI destination fix only.
