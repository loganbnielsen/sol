title: The uninstall path reads the Terraform state listing directly, so a never-applied installation is reported as unreadable
source: discovered while consolidating the state reader for BUG-205 (2026-10-05)
---

**Depends on:** None.

## Relationship to BUG-205

BUG-205 established that "no state file" means *holds nothing*, not *unreadable*: a backend that has
never been written answers `terraform state list` with `No state file was found!` (exit 1) while
`terraform state pull` succeeds. `Sol_cli_terraform.state_addresses` is the one reader that encodes
that: it lists the addresses, and when the listing fails it asks `state pull`, so an empty backend is
`[]` and only a genuine read failure propagates.

## Why the shared reader does not cover this path

BUG-205 converted `Sol_cli_provider_registry.state_holds_any` and
`Sol_cli_installation_stage.state_addresses` to `Sol_cli_terraform.state_addresses`, but
`cli/bin/cmd_uninstall.ml` keeps its own copy of the old elaboration:

```ocaml
Sol_cli_terraform.state_list ~chdir ()
|> Result.map (parse stdout)
```

so it still maps *any* listing failure to an error before the shared reader can apply the
absent-versus-unreadable distinction. It is the last caller of the raw `state_list` outside
`Sol_cli_terraform` itself.

## Observable consequence

`sol uninstall <target>` against an installation whose bootstrap root has never been applied —
exactly the state a fresh, not-yet-provisioned target has — exits 1 with
`terraform state list failed with exit 1` before rendering the uninstall plan, instead of planning
from a state that holds nothing. A genuinely unreadable state must still fail closed.

## Remediation

Read the addresses through `Sol_cli_terraform.state_addresses` and delete the local parse. Keep
`state_list` and `state_pull` private to `Sol_cli_terraform` so the shared reader is the only exposed
state-reading API.

## Acceptance criteria

- `sol uninstall` on a state that has never been written does not report the state as unreadable and
  renders its plan; a state that cannot be read at all (`state list` **and** `state pull` fail) still
  fails closed.
- `cli/bin/cmd_uninstall.ml` reads through `Sol_cli_terraform.state_addresses`; no module outside
  `sol_cli_terraform.ml` reads the raw listing or parses its stdout.
- `state_list` and `state_pull` are not exported by `sol_cli_terraform.mli`, so a second
  state-reading path cannot be reintroduced without a deliberate API change.
- A static guard fails when the raw listing is exported again or referenced outside
  `sol_cli_terraform.ml`, with a mutation that proves it fails for that reason.
- Example impact: none; the uninstall path is CLI-internal. Language-parity impact: none.

## Completion notes (2026-10-05)

**Fix.** `cli/bin/cmd_uninstall.ml` reads through `Sol_cli_terraform.state_addresses` and its local
stdout parse is gone; `state_list` and `state_pull` are no longer exported by
`sol_cli_terraform.mli`, so `state_addresses` is the module's only exposed state reader.

**Drift guard.** `internal/ci/check_state_reader.py` (discovered by `verify.sh static`) requires the
mli to export `state_addresses` and to keep the raw listing private, and fails if any module outside
`sol_cli_terraform.ml` reads `state_list`/`state_pull`. `internal/ci/test_state_reader_check.py`
proves it rejects both a re-exported listing and a module reading it.

**Tests.** `cli/test/test_uninstall_cli.sh` drives a `fresh-state` backend (listing fails with
`No state file was found!`, `state pull` succeeds) and asserts the uninstall plan is still rendered,
plus an `unreadable-state` backend (both commands fail) that still exits 1. Verified by mutation:
reverting `cmd_uninstall.ml` to the raw listing reproduces `error: exited with code 1: No state file
was found!` and fails the plan assertion.

**Demo/example:** none — the uninstall path is CLI-internal. **Language parity (DEC-022):** none.
