Return a bad request for non-object charge JSON

**Depends on:** None.

**Premise verified (2026-09-28):** Read the implementation at `examples/pluto/app/payments/charge_svc/lib/handler.ml:11-38; platform/shared/templates/workspace/app/payments/charge_svc/lib/handler.ml:9-35` and its representative callers/tests on origin/main `6a7b1fb5`. The described boundary remains present.

## Problem

Yojson member raises Type_error for arrays, null and scalar roots. decode_charge_body catches syntax errors only, so valid non-object JSON escapes its Result contract and intended HTTP 400 path.

## Remediation

Validate the root object at decode_charge before reading members, returning an Error for every other JSON variant. Update example and scaffold together.

## Acceptance criteria

- Add [], null, numeric, string and boolean roots to both existing charge decoder checks; all return Error/HTTP 400 without raising, while valid object input still works.
- Update a runnable example/demo for application-facing behavior, or record why this is an internal-only refactor.
- Record the per-language capability verdict for framework/application contracts, or explain why language parity is unaffected.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `788e688d`: `decode_charge` called `Yojson.Basic.Util.member` unconditionally, which raises `Type_error` on a non-object root; `decode_charge_body` only caught `Yojson.Json_error`, so `[]`, `null`, `42` and `"text"` escaped the `result` contract and the HTTP 400 path.
- **Fix** (example and scaffold together): `decode_charge` now matches on the root and returns `Error "request body must be a JSON object"` for any variant other than `` `Assoc _ `` before reading any member. `handle_charge` already maps `Error` to `Response.bad_request`, so the non-object roots now take the 400 path without raising; valid objects and the existing field-level errors are unchanged.
- **Tests**: both `test_charges.ml` decoders gain `[]`, `null`, `42`, `3.5`, `"text"` and `true` roots, asserting `Error "request body must be a JSON object"` (the old code raised `Type_error` here); the existing valid-object and missing-field assertions remain as positive controls. Pluto's `test_charges.exe` and the scaffold suite (`test_scaffold.exe`, 52/52, including the generated charge-operation build) pass; the generated workspace compiles the updated template test.
- Validation: `dune fmt --preview` clean; `ocamlformat --check` clean on all four touched files; no-comments policy holds.
- **Demo/example**: the runnable example *is* the covered demo — `examples/pluto` charge service and its `test_charges.ml` were updated, and the scaffolded workspace template was updated in lockstep. **Language parity: no impact** — this is an OCaml-framework HTTP decoding fix; the request-body contract is language-neutral, and the TypeScript order example has no separate charge-service equivalent in this pass (no new framework primitive or convention).
