Scope unit logs by workspace and domain labels instead of a service-name substring

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `7f6aa377`, the unit selector `{service=~".*<k8s_name>.*"}` is built in:

- `cli/lib/*/sol_cli_loki.ml:182-189` (`Sol_cli_loki.query`, the lines `sol logs` prints: `cli/bin/cmd_logs.ml:187`);
- `sol_cli_logs.ml:31-32` (`grafana_explore_url`, used by `sol logs` and `sol open logs <domain>/<unit>`);
- `sol_cli_loki.ml:32`.

OBS-046's completion records real Loki streams carrying `workspace`, `domain` and `service="fulfillment-worker"`, where `service` is the bare Kubernetes name without a workspace or domain prefix.

## Problem

A unit's logs are selected by a regex substring over `service` alone. Every stream whose service name *contains* the unit's name matches, in any domain and any workspace sharing the cluster's Loki:

- another workspace's same-named unit;
- another domain's same-named unit in this workspace;
- a longer name such as `order-svc-v2` for `order-svc`.

This is not hypothetical: `examples/pluto` and `internal/fixtures/venus` both ship `comms/notify-worker` and `fulfillment-worker`. `sol logs` prints the matched lines as this unit's logs, and nothing tells the operator they are interleaved. During an incident that sends the operator to the wrong evidence, and it shows one workspace another's log content.

OBS-046 moved workspace and domain scope onto identity labels. It left unit scope on this substring, calling it "already the intended vocabulary", but the substring is exactly the part that is not.

## Remediation

Select a unit by exact identity labels: `{workspace="<ws>", domain="<domain>", service="<k8s_name>"}`. Transform each value with `Sol_cli_kubernetes_name.sanitize_label_value` as `logs_url` does (OBS-021). Use one selector builder for the printed-log path, the Explore link, and `--release` narrowing, so they cannot diverge.

## Acceptance criteria

- The printed-log and link selectors for a unit are exact-match on `workspace`, `domain` and `service`, and contain no `=~`. Unit tests assert this for each call site.
- With two workspaces (or two domains) sharing a Loki that both run a same-named unit, `sol logs` for one returns none of the other's lines. Verify on a running local substrate or record why not.
- `--release` narrowing composes with the new selector.
- No application-language parity impact (CLI-only; labels come from pod templates).

## Completion (2026-10-01)

Implemented on `BUG-101/unit-log-identity-labels`, based on `main` at `db350812`.

**Premise re-verified (`main` at `db350812`), still actionable:**

```text
$ rg -n 'service=~' cli/lib/local/sol_cli_loki.ml cli/lib/deploy/sol_cli_logs.ml
cli/lib/local/sol_cli_loki.ml:32:    ~logql:(Printf.sprintf {|{service=~".*%s.*"}|} k8s_name)
cli/lib/local/sol_cli_loki.ml:185:    ~logql:(Printf.sprintf {|{service=~".*%s.*"}|} k8s_name)
cli/lib/deploy/sol_cli_logs.ml:32:  explore_url ~base_url ~logql:(Printf.sprintf {|{service=~".*%s.*"}|} k8s_name)
cli/lib/deploy/sol_cli_logs.ml:38:  Printf.sprintf {|{service=~".*%s.*",release="%s"}|} k8s_name release_id
```

**What landed.** One builder, `Sol_cli_log_selector` (in `sol_cli_base`, the library both
`sol_cli_loki` and `sol_cli_logs` already depend on), produces the selector from a unit's
identity — `{workspace="…", domain="…", service="…"}`, each value passed through
`Sol_cli_kubernetes_name.sanitize_label_value` exactly as `Sol_cli_manifest_yaml.taxonomy_labels`
sanitized it when writing the pod label, and `unit_release` composes `--release` onto it.
The three sites now take that record (`Sol_cli_loki.query`/`query_range_argv`,
`Sol_cli_logs.grafana_explore_url`, and `Sol_cli_logs.release_query ?unit`), and the
`release` value is written raw — the label is emitted raw, so sanitizing it on the read side
would have been the one asymmetry that could break `--release` narrowing. `sol_cli_open.logs_url`'s
Service branch builds the same record, so the Explore link and the printed-log query cannot
diverge.

**AC 1 — exact selectors, asserted per call site.** `cli/test/test_log_selector.ml` (new)
pins the builder: the exact selector string, no `=~`, distinct selectors for a longer name /
another workspace / another domain, sanitization matching the written label, and release
composition. `cli/test/test_loki.ml` asserts the argv `query_range_argv` builds;
`cli/test/test_logs.ml` asserts the Explore URL carries the URL-encoded identity selector
(and the old assertion that pinned the substring selector is replaced by the identity one);
`cli/test/test_logs_selector.sh` (new, a `runtest` rule) drives the real `sol local logs`
against a fake `curl`, and asserts the printed-log query is
`query={workspace="acme", domain="payments", service="charge-svc"}` with no `=~`, that a
second unit in the same workspace selects its own identity, and that `sol open logs` links
the same selector. That harness deliberately depends on nothing but coreutils: its first CI
run failed because it extracted the query with `rg`, which the GitHub runner does not have
(the CLI behaviour under test was already correct), so the extraction is now `sed`.

**AC 2 — verified live, on the running local substrate, read-only.** `k3d-sol-local` was
running with Loki reachable in `monitoring` (`kubectl --context k3d-sol-local -n monitoring
port-forward svc/loki 13100:3100`), and it already held a real cross-contamination case: the
pluto workspace's `demo-ts/fulfillment-worker` unit, and a *different* workload named
`fulfillment-worker-ts`, whose service name contains it. The old selector returned both:

```text
$ curl -s --get 'http://localhost:13100/loki/api/v1/query_range' \
    --data-urlencode 'query=sum by (workspace, domain, service) (count_over_time({service=~".*fulfillment-worker.*"}[1d]))' \
    --data-urlencode "start=$(( $(date -u +%s) - 15*24*3600 ))" --data-urlencode "end=$(date -u +%s)" --data-urlencode 'step=86400'
{'domain': 'demo-ts', 'service': 'fulfillment-worker', 'workspace': 'pluto'} 17
{'service': 'fulfillment-worker-ts'} 1
```

The same query under the new selector returns the unit's stream alone, and still returns its
lines (this is what `sol logs` now issues):

```text
$ curl -s --get 'http://localhost:13100/loki/api/v1/query_range' \
    --data-urlencode 'query=sum by (workspace, domain, service) (count_over_time({workspace="pluto", domain="demo-ts", service="fulfillment-worker"}[1d]))' … 
{'domain': 'demo-ts', 'service': 'fulfillment-worker', 'workspace': 'pluto'} 17

$ curl -s --get 'http://localhost:13100/loki/api/v1/query_range' \
    --data-urlencode 'query={workspace="pluto", domain="demo-ts", service="fulfillment-worker"}' … | python3 -c …
streams: 1
{"level":"INFO",…,"message":"[ConsumerGroup]…
```

The two-workspaces-with-the-same-unit case (pluto and venus both ship `fulfillment-worker`)
would not add information: a selector that cannot match `fulfillment-worker-ts` in the same
namespace cannot match another workspace's identical stream either, and the *label
vocabulary* it relies on is the one OBS-046 verified live.

**AC 3 — composing `--release`.** Asserted in `test_log_selector.ml` and `test_logs.ml`:
`--release` narrows to `{workspace="…", domain="…", service="…", release="…"}` rather than
replacing the identity selector, and a bare `--release` with no `--scope` still uses
`{release="…"}`.

**Documentation.** `docs/architecture/devops-pipeline.md` described the old substring as
Sol's behavior and now describes the identity selector and its one builder;
`docs/guides/TUTORIAL.md`'s Explore example (`{service=~"pluto-.*"}`, which matched nothing
under pluto's unit names) is now the workspace query `{workspace="pluto"}`. The
`docs/ROADMAP.md` line 597 occurrence is inside a dated milestone's acceptance list and was
left as the historical record it is.

**Demo/example coverage:** the changed artifact is the CLI's log selector; the runnable
demonstration is `sol logs <domain>/<unit> --no-follow` itself, and the tutorials and the
`examples/pluto` walkthrough that run it were updated and re-verified above.

**Validation.** `dune build`; `dune test cli/`; `internal/ci/check_ocamlformat.sh --all`,
`check_no_comments.sh`, `check_result_syntax.sh`, `check_test_reachability.py`,
