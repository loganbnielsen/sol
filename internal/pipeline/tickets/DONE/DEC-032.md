title: Formalize target, scope and view as three separate axes

**Depends on:** None.

**Related:** DOCS-019, DEC-031, INFRA-027, OBS-044, OBS-045, FEAT-090, ADR 0003.

## What this was

The review nests a target above the workspace tree
(`Target -> Workspace -> Domain -> svc/worker/fn`) and then addresses the target
through the same selector as everything else. That would make `prod/aws/us-east-1`
a member of the same grammar as `Workspace | Domain | Unit | Resource`, which does
not match the ontology the interface already has.

## Decision

**Target, scope and view are three axes. A target is not a scope.**

```text
target = where?                      prod/aws/us-east-1
scope  = what?                       pluto/checkout_svc
view   = which operational concern?  metrics | logs | traces | infra
```

- **`target` is where.** A deployment destination, selected by `--target` — or
  positionally, on the commands whose *primary* axis is the target
  (`sol cloud plan|apply|destroy`, `sol deploy`, `sol up`).
- **`scope` is what.** The part of the workspace being addressed: the workspace
  itself (the default), `domain`, `domain/unit`, or `resource/<type>/<name>` for a
  managed resource (OBS-044). It is never a node in a tree that contains targets.
- **`view` is which operational concern.** The `sol open` subcommand today
  (`logs`, `metrics`, `dashboard`), extended by OBS-045 (`traces`) and INFRA-027
  (`infra`). A view selects *what is rendered*; it never selects identity.

Nothing requires all three. Infrastructure has a target and a view with no
application scope (`target = prod/aws/us-east-1`, `scope = none`,
`view = infra`); service metrics on that target have all three; local development
has a scope and a view with no target.

### `--target` has one meaning, and the backend is derived from it

`--target` answers "where". The observability backend and base domain are not
selected by the flag — they are **derived from the target's own configuration**
via `Sol_cli_observability_url.effective_backend_and_base_domain ~target`. So the
flag is not overloaded: "whose Grafana" follows from which target was named,
which is the target's business, not the flag's.

Concretely, `sol open logs payments/checkout-svc --target prod/aws/us-east-1` is
the `logs` view of unit `payments/checkout-svc`, resolved against the
`prod/aws/us-east-1` target, whose config supplies the Grafana location. No
precedence rule is needed, because there is only one input; and `--target` does
not become a second way to spell a scope.

Where a command's positional argument is its primary axis, that axis takes the
positional and the others are flags — the rule DEC-031 records. That is why
`scope` is positional on `sol status`/`sol open` and `target` is positional on
`sol cloud`/`sol deploy`/`sol up`.

### Valid axis combinations

| View | Scope | Target | Valid? |
|---|---|---|---|
| `logs` | workspace, domain, unit | any, or none | Yes (link). `sol logs` *streaming* stays unit-only — a different surface, per its own note |
| `metrics`, `dashboard` | workspace, domain, unit, `resource/<type>/<name>` | any, or none | Yes |
| `traces` (OBS-045) | workspace, domain, unit | any, or none | Yes — planned |
| `infra` (INFRA-027) | none | required | Yes — planned |
| `infra` | any scope | any | **No.** Infrastructure has no application scope; the request fails naming infra as target-scoped rather than silently ignoring the scope |
| any view | any | omitted where the view requires one | **No.** Fails naming the view and the required target — never a silent default (DEC-016) |

`resource/<type>/<name>` is a *scope* addressing a managed resource, not a view;
it is valid for the resource-dashboard views and invalid for `logs` and `infra`.

## Evidence (2026-09-18, `main` at 790dc3e8)

The scope type has no target case, and the view is already a separate type
(`cli/sol/lib/sol_cli_open.ml`):

```ocaml
type scope = Workspace | Domain of string | Service of string * string | Resource of string * string
type kind  = Logs | Metrics | Dashboard
```

`kind` is the view axis, already carried as a subcommand rather than as a value
inside `scope` — the shape this decision makes explicit rather than incidental.

Targets are addressed by a separate command family (`cli/sol/bin/main.ml`
registers `Cmd_target.cmd` and `Cmd_cloud.cmd` independently of `Cmd_status.cmd`
/ `Cmd_open.cmd`):

```text
$ sol cloud --help | sed -n '/COMMANDS/,/COMMON/p'
       apply […] TARGET
       destroy […] TARGET
       plan […] TARGET
```

## Consequences

- `Sol_cli_open.scope` does not gain a `Target` constructor, and no future
  addressing concept may add one without stating why it is a scope rather than a
  target or a view.
- **INFRA-027 is unblocked.** It adds a view addressed by a target with no
  scope, and needs no change to the scope grammar.
- OBS-045 adds `Traces` to the view type; INFRA-027 adds `Infra`.
- FEAT-090 stays on the target-inspection surface as a status projection — it
  does not introduce a new addressing concept.
- The three-axis model is stated in the architecture doc by DOCS-019.
- DEC-031's rule (primary axis positional, other axes flagged) follows from this
  and can be recorded independently.

## Not decided here

- The infrastructure views' content or telemetry source — INFRA-027 owns that,
  including the fact that the source may differ per resource (CloudWatch for RDS,
  Prometheus for Kubernetes/Redpanda/Postgres). Unified semantics do not require
  unified storage.
- A target's lifecycle phase — ADR 0003 already defines it, and the phase is not
  an axis of this model.
- Whether `sol open` eventually carries the view as a flag rather than a
  subcommand — that is DEC-031's shape question, not this ontology.
- Any second source of truth: this model adds no state. Every axis resolves to
  the identity the manifests and telemetry already carry.

**Demo/example coverage:** Decision-only ticket; the follow-up implementation
tickets own the runnable examples.

**TypeScript parity:** No language-parity impact — CLI addressing model only.
