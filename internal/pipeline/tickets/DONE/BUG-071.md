Preserve exclusive boundary ownership throughout deploy and rollback

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `cli/bin/cmd_rollback.ml:101; cli/lib/deploy/sol_cli_boundary_lease.ml:30,78-109; cli/lib/deploy/sol_cli_deploy_run.ml:268-291` with callers and existing tests at origin/main `2dfa5694`. Evidence and reproduction limits are recorded in the source audit.

## Problem

Rollback discards its held lease and never heartbeats or verifies ownership. At 301 seconds its lease is reclaimable while it can still apply workloads, prune and move the release pointer. Deploy renews before each workload but does not maintain ownership through a long last apply and recording. Competing operations can therefore mutate the same boundary.

## Remediation

Maintain the existing lease through long-running operations and verify ownership before each subsequent mutation and pointer/record commit. Thread held ownership through rollback rather than discarding it. Raising the TTL alone is insufficient. Document the fencing/stop behavior for an operation already in progress when ownership is lost.

## Acceptance criteria

- A controllable-clock/takeover regression shows the old owner cannot perform further apply, prune, pointer or release-record mutations after losing ownership. Long healthy rollback/deploy renews its lease; release remains ownership-checked. Update a runnable rollback example or explicitly explain why its existing example remains applicable.
- Record the application demo and per-language verdict in completion notes wherever the change affects an application contract.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `788e688d`: `cmd_rollback.run` acquired the lease in `with_boundary_lease` but the body was `fun _lease -> run_locked ...`, so the held lease was discarded and never re-verified; `Sol_cli_rollback.execute` went straight from `apply` to `live_workloads`/`prune`/`move_pointer`, so a rollback outliving the 300 s TTL could be taken over and still mutate. `sol deploy`/`sol up` renewed before each workload but not before recording the release and advancing the pointer.
- **Fix.** `Sol_cli_rollback.transaction_deps` gains `ensure_held : unit -> (unit, string) result`, and `execute` now re-verifies ownership immediately before the workload `apply`, before the surplus `prune` (its failure is reported as the ownership failure, not disguised as a prune failure) and before `move_pointer` — so a takeover can only ever stop the transaction, never let the old owner keep writing. `cmd_rollback.run` threads the held lease into `run_locked`, and `apply_specs` takes `~ensure_held` and calls it before each workload, mirroring deploy's per-workload renewal. `sol_cli_deploy_run.apply` and `cmd_up` now call `ensure_held` before `record_release_and_prune`, so the release-record/pointer commit is ownership-checked too. Each check is a heartbeat CAS write, so a long healthy operation renews as it works.
- **Tests** (`cli/test/test_rollback.ml`, `rollback_transaction` group): `recording_deps` records and can inject an `ensure_held`, and the ordering tests now assert ownership is re-verified before every mutation (`ensure_held, apply, live_workloads, ensure_held, prune, ensure_held, move_pointer, verify_pointer`). Two takeover regressions inject an ownership loss after `apply` and after `prune`: the second one asserts `prune` never ran, the third that `move_pointer`/`verify_pointer` never ran, both requiring the "lost the boundary lease" diagnostic. **Mutation-checked**: deleting the three checks makes four cases fail while the fix passes (53 tests). `test_boundary_lease` (8), `test_deployment_phases` (51), `test_release` (26) and the full `dune build` stay green; `dune fmt --preview` and `check_no_comments.sh` clean.
- **Docs.** `docs/architecture/devops-pipeline.md` § Mutation boundary now states the per-mutation ownership re-verification, that the checks double as renewal, and the fencing/stop behaviour for an operation already in progress when ownership is lost (it completes at most the mutation it was inside and its next check fails; there is no forced kill).
- **Runnable example: the existing one stays applicable.** `docs/guides/TUTORIAL.md` § Day-2 operations already describes `sol rollback <release-id>` for an operator and never exposed the TTL or lease internals, so the user-visible command is unchanged; the new behaviour is covered by the injection tests above rather than by a demo step, since reproducing a takeover needs two concurrent mutators against a live cluster. **Language parity: no impact** — boundary ownership is CLI/cluster bookkeeping outside the application contract.
