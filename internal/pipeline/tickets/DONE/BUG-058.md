**Depends on:** None.

## The problem

When `--image-tag` is omitted, both `sol up` and `sol deploy` default the image tag
to `git_sha ()` (`Sol_cli_command_request.make_up_request` and the deploy request,
`cli/lib/deploy/sol_cli_command_request.ml:52` and `:96`). `git_sha` exists twice,
identically, in `cli/bin/cmd_up.ml:19` and `cli/bin/cmd_deploy.ml:31`:

```ocaml
let git_sha () =
  match Sol_cli_process.run (Sol_cli_process.cmd [ "git"; "rev-parse"; "--short"; "HEAD" ]) with
  | Ok r when r.Sol_cli_process.exit_code = 0 && r.Sol_cli_process.stdout <> "" -> r.Sol_cli_process.stdout
  | _ -> "dev"
```

If git isn't installed, the directory isn't a repository (a CI job without `.git`,
a source tarball), or the command fails for any other reason, the error is
discarded and the tag becomes the literal `dev`. `sol deploy prod/aws/us-east-1`
then pushes and deploys a **mutable, shared tag to a real cluster**, with no
message. Two unrelated builds can overwrite each other's `dev`, and a rollout can
be a no-op because the tag didn't change.

## Remediation

1. One `git_sha` in `cli/lib` (next to the request construction). It returns
   `(string, string) result` carrying git's own error, not a sentinel.
2. `sol deploy` without `--image-tag`, when the SHA can't be resolved, is an error
   that names the cause and says to pass `--image-tag`.
3. `sol up` (local) may keep a fallback, but only with a visible warning on stderr
   naming the fallback tag and why.
4. Consider refusing a dirty tree for `sol deploy`'s implicit tag, or suffixing it
   (`<sha>-dirty`). Decide in the implementation and record why in the completion
   notes.

## Completion notes

Premise checked 2026-09-25 on `origin/main` (`ebdb9263`): both `cli/bin/cmd_up.ml:19` and `cli/bin/cmd_deploy.ml:31` defined `git_sha` with `| _ -> "dev"`.

- `git_sha` now lives once in `Sol_cli_command_request` and returns `(string, string) result` carrying git's reason (`rg -n 'let git_sha' cli/` finds one definition). The request builders take `git_sha:(unit -> (string, string) result)`.
- `sol deploy` without `--image-tag` and without a resolvable SHA is refused. Verified with the real binary in a directory that isn't a git repository:
  ```
  $ sol deploy prod/aws/us-east-1 --dry-run
  error: could not resolve the git commit to tag images with (fatal: not a git repository (or any of the parent directories): .git); pass --image-tag <tag> to deploy
  ```
  (exit 1). With `--image-tag v1`, the same command gets past request validation. Positive control: it stops at the workspace check instead.
- `sol up` keeps the `dev` fallback, but the request now carries `image_tag_warning`, which `cmd_up` prints:
  `warning: could not resolve the git commit for the image tag (fatal: not a git repository ...); tagging images "dev". Pass --image-tag to choose a tag.`
- Tests (`test_deployment_phases.ml`, `request_validation`): the up fallback warns and names git's reason and `--image-tag`; a resolved SHA gives no warning; the deploy refusal names both; positive control: a resolved SHA deploy request is accepted and tagged with it. The existing explicit-tag tests are unchanged apart from the stub type.
- **Dirty trees: decided not to change them here.** The implicit tag stays `HEAD`'s short SHA even with uncommitted changes. Whether the *built image* matches the tag is a property of the build step (which context `docker build` reads), not of tag resolution. Adding `-dirty` here would still let two dirty builds share one tag. If this matters, it's a separate finding about build provenance, not this bug.
- Verification: `dune build`, `dune test cli/ --force` (58 suites, 0 failures), `internal/ci/check_ocamlformat.sh --all` clean.
- Demo/example: no example change. `--image-tag` already exists. Some documented invocations omit it (`docs/guides/TUTORIAL.md:442`, `:684`; `examples/pluto/README.md:52`; checked with `rg -n 'sol deploy ' examples docs/guides`), and those still work in the project's git checkout, where the SHA resolves. Only a project outside git changes behaviour: it now gets the error above, which names the fix, instead of a silent `dev` tag.
- Language parity (DEC-022): no impact; image tagging is language-neutral CLI behaviour.
