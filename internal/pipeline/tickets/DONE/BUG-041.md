Reject duplicate migration versions and stop treating `*.down.sql` as a required migration

**Depends on:** None.

**Finding:** FND-0032 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-23** against `origin/main @ f3e9480b` while filing (see the finding for the command/probe and observed output).

## Problem

Migrations are keyed by integer version in both the pg-eio runner (`pending` filters on version; table PK is `version`) and Sol's deploy gate (`Sol_cli_migration.unsatisfied`). A second `NNN_*.sql` added after `NNN` is applied is never run and the gate reports OK. Sol's `required` also counts `NNN_x.down.sql` as a required migration, which only the version-only comparison makes harmless. Reproduced — see FND-0032.

## Remediation

Reject duplicate versions at read time in Sol's `required` (error names both files) and in pg-eio's `read_migrations`; exclude `*.down.sql` from `required` as the runner does; optionally compare `(version, name)` in the gate.

## Acceptance criteria

- `Sol_cli_migration.required` on a dir with `001_a.sql` + `001_b.sql` returns `Error` naming both files.
- `required` ignores `*.down.sql`.
- pg-eio `Migration.apply`/`status` reject duplicate versions (change lands in `~/Code/pg-eio`, pin bumped).
- Mutation check per `audits/README.md`: removing the duplicate check makes the new test fail with a successful build.
- Demo/example: the scaffolded `db/migrations` convention is unchanged; note in completion notes.

## Completion notes

- **Sol:** `Sol_cli_migration.required` excludes `*.down.sql` (as the runner does) and
  refuses two files that share a version. The error names both files as they are on
  disk, e.g. `migrations 0004_a.sql and 0004_b.sql in <dir> share version 4; ...`.
  `sol migrate apply` (local, `--dry-run`, and the in-cluster Job, which runs the same
  CLI), `status` and `rollback` validate through it before touching the database. The
  deploy gate already calls it.
- **pg-eio** (loganbnielsen/pg-eio#21, merged as `3ef3a20f`): `read_migrations` refuses a
  shared version and names both files; `apply`/`status` read the directory before they
  connect; new `Migration.migrations ~fs ~dir`; README documents unique versions. The pin
  is bumped from `16d8c66e` to `3ef3a20f` in `sol-jobs.opam`, `examples/pluto/pluto.opam`,
  `internal/fixtures/venus/venus.opam` and the scaffold template.
- Tests: Sol `test_migration.ml`, with the shared version named exactly (3- and 4-digit)
  and down files excluded; pg-eio `rejects_shared_version`, `orders_and_skips_down_files`.
- Mutation checks (`audits/README.md`), builds rc=0: removing Sol's duplicate check fails
  "shared version is an error"; not excluding down files fails "down files are not
  migrations"; disabling pg-eio's check fails `rejects_shared_version`.
- Docs: `docs/deployment/migration-ordering.md` (down files excluded, versions unique);
  the pg-eio README.
- The migration checksum question (FND-0032's second half) is FEAT-094, in BACKLOG.
- Demo/example: the scaffolded and example migration layouts are unchanged; the pinned
  `pg-eio` commit moves in the example and fixture opam files.
- Language parity: no language-parity impact (the migration runner is CLI/OCaml-side;
  TypeScript services use the same `sol migrate`).
