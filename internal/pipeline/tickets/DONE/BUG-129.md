## Observed

The required `test` check failed on a **main push** — the post-merge backstop — for
`AUDIT-087`'s implementation commit, in *Framework integration tests (broker and database
backed)*: all 20 `sol_jobs_pg` cases failed in 68 ms, each with a connection error rather than
an assertion. The same commit re-run is green, and the two neighbouring commits' runs are green.

```console
$ gh run view 37139185455 --log-failed
FAIL idempotent enqueue (FEAT-112) › a redelivery after completion is a no-op
DROP SCHEMA IF EXISTS sol_test_sol_jobs_pg CASCADE: connection failed: Failed to connect to
  <***localhost:5432/sol_dev?options=-csearch_path=sol_test_sol_jobs_pg>: Connection failure:
  connection to server at "localhost" (::1), port 5432 failed: server closed the connection unexpectedly
  This probably means the server terminated abnormally before or while processing the request.
20 failed in 68ms. 20 tests run.
```

This is `VERIF-023`'s Instance A recurring. That ticket's `Integration failure diagnostics` step
now answers the question it could not: **the server did not die** — it had just been *created*.

So: exit 0, `oom=false`, `restarts=0`, and `docker ps` shows a container created ~15 seconds

that "terminated abnormally" was never running yet; the gate said ready while it was initializing.

## The mechanism, in the script

`platform/local/scripts/ensure-postgres.sh` starts the container and then gates on two things:

```bash
docker run -d --name "${CONTAINER}" ... postgres:16-alpine > /dev/null
echo "Waiting for port ${PORT} ready."
wait_for_port "${PORT}" 30 0.5 || exit 1

for i in $(seq 1 20); do
  if docker exec "${CONTAINER}" pg_isready -q 2>/dev/null; then break; fi
  sleep 0.5
done

echo "Postgres ready at localhost:${PORT}"
```

Two independent reasons this can pass before the server can serve:

1. **A TCP connect is not evidence the container's server is up.** The port is published, so
   *something* (the container's network namespace once the entrypoint binds, or Docker's
   published-port proxy) can accept the connection while the image's entrypoint is still in its
   `initdb` phase — which is exactly the shape the log shows: "Waiting for port 5432 ready." at
   17:13:41.8, "Postgres ready" at 17:13:42.97, first client at 17:13:43.27, initdb still
   printing at 17:13:56. The first server the image runs during initialization is not the server
   the suites connect to afterwards; when the entrypoint stops it and starts the real one, a
   connection made in that window is closed — `server closed the connection unexpectedly`.
2. **The `pg_isready` loop is not a gate.** `break` on success, then unconditional "ready": if it
   never becomes ready within its 10 seconds, the script still prints "Postgres ready at
   localhost:5432" and exits 0. The result of the loop is never used, so the one check that *does*
   look inside the container can fail silently. (`wait_for_port` at least exits 1 on timeout.)

Both are deterministic readings of the script; the timeline above is the observed instance.

## Why it matters

`test` is a required check on every PR and the post-merge backstop on `main` (this occurrence
was on `main`, not a PR). The failure looks like a test failure, costs a full CI cycle to
attribute, and is only distinguishable from a real regression by re-running — the cost
`VERIF-023` named. It reproduces on a PR whose diff is unrelated (`AUDIT-087`'s is
`internal/qualification/transport/` and `internal/ci/`, nowhere near `framework/`).

## Recommended remediation

In `ensure-postgres.sh`, make the gate observe the server the suites will use, and fail when it
cannot:

- gate on a **real query through the published port** — `pg_isready -h 127.0.0.1 -p <port>` from
  the host, then `psql "postgresql://postgres:<pw>@127.0.0.1:<port>/<db>" -c 'SELECT 1'` (or the
  same through `docker exec` against TCP inside the container) — rather than a bare TCP connect;
- **fail** (`exit 1` with the container's last log lines) when the readiness loop exhausts, so a
  server that is not ready is a named failure instead of a suite-level connection error;
- keep the `Integration failure diagnostics` step: it is what made this diagnosable, and it
  should also print the container's creation time and the elapsed time since it was started, so
  the next occurrence shows the race in one place.

`platform/local/scripts/ensure-broker.sh`/`start-redpanda.sh` were inspected for the same shape;
the result is recorded under *The broker gate* below.

## Acceptance criteria

- A Postgres that is not ready cannot make the script print "Postgres ready" and exit 0: the gate
  waits for a query that only the real server answers, or fails with the container's log.
- The gate's failure mode is visible in one line, and a re-run is not needed to tell "the runner
  was unlucky" from "the code is wrong".
- The change is exercised by the existing local-dev and CI paths (a fresh container on a clean
  runner), and `platform/local/scripts/` has a test or a documented manual check for the
  not-ready path.

## Premise established (2026-10-03) — three ways, before the script changed

1. **The CI evidence in *Observed*** (the diagnostics step `VERIF-023` added): `sol-postgres`
   created 15 seconds before the failure, `oom=false restarts=0`, `initdb` still printing, while
   the script had printed "Postgres ready at localhost:5432".
2. **Live, with real Docker, against a container that accepts connections and answers nothing.**
   A stub listener (`alpine` + `nc -l -p 5432` on a free port, `CONTAINER` renamed so the dev
   containers were untouched) is not a database:

   ```console
   $ psql "postgresql://postgres:dev@host.docker.internal:55432/sol_dev" -tAc 'SELECT 1'
   psql: error: connection to server at "host.docker.internal" (192.168.65.254), port 55432 failed:
     server closed the connection unexpectedly
    exit 2
   ```

   and the pre-fix script declared it ready anyway — `pg_isready` did not even exist inside that
   container, so the loop printed twenty OCI errors, exhausted, and fell through to success:

   ```console
   $ POSTGRES_PORT=55432 bash scripts/ensure-postgres.sh   # pre-fix, from origin/main
   Postgres already running (container: sol-postgres-b129)
   Waiting for port 55432 ready.
   OCI runtime exec failed: exec: "pg_isready": executable file not found in $PATH   (×20)
   Postgres ready at localhost:55432
     URL: postgresql://postgres:dev@localhost:55432/sol_dev

     export POSTGRES_URL=postgresql://postgres:dev@localhost:55432/sol_dev
   PRE-FIX EXIT=0
   ```

   Note that `wait_for_port` (`nc -z localhost 55432`) *did* succeed: the TCP connect that the
   gate accepted is exactly the probe the CI failure went through.
3. **Offline, deterministically**, by `internal/ci/test_ensure_postgres_ready.sh` pointed at the
   pre-fix script: **10 expectations fail**, including
   `a connection-accepting non-database fails readiness (observed exit 0)`,
   `a started container that cannot answer fails readiness (observed exit 0)` and
   `the gate asked a query, not a port`.

## Implemented

`platform/local/scripts/ensure-postgres.sh` now reports ready only after a **real query comes back
through the published port**, and fails loudly when the budget is exhausted:

- the gate runs `psql … -tAc 'SELECT 1'` **from a client container against the host's published
  address** (`host.docker.internal:<port>`, the same address the consumer URL names), using the
  same `postgres:16-alpine` image the server runs, so no host-side `psql` is needed and no
  in-container socket or initialization server can satisfy it;
- the retry budget is a wall-clock deadline (`POSTGRES_READY_TIMEOUT_S`, default 60 — four times
  the ~15s `initdb` window the CI log showed — with `POSTGRES_READY_INTERVAL_S`, default 1) and
  exhaustion is a **failure**: `ERROR: Postgres did not answer a query at <url> within <n>s`, then
  the last **client** error (so an unusable client, e.g. an unsupported Docker flag, cannot
  masquerade as a slow server), then the container's last 20 log lines, then `exit 1`. That
  mirrors `start-redpanda.sh`'s failure shape.
- `wait_for_port` and the socket `pg_isready` loop are gone from this script; the success output
  (`Postgres ready at …`, the URL, `export POSTGRES_URL=…`) is unchanged, so the runner, the CI
  step and the e2e commands see the same contract.
- The `Integration failure diagnostics` step is untouched; the script now also dumps the container
  logs itself on failure, and `.github/workflows/ci.yml` records why the gate is shaped this way
  and what the two knobs do.

## The broker gate — inspected, same defect not established

`start-redpanda.sh` waits on `docker exec redpanda rpk cluster health --watch=false` — the
broker's own health API, not a port — and on exhaustion prints
`ERROR: Redpanda did not become ready within 30 seconds.`, dumps `docker logs --tail 20` and
exits 1. `ensure-broker.sh` runs that first, then `wait_for_port 9092 20 1 || { echo ""; exit 1; }`
(loud on exhaustion), then `create-topics.sh`, whose final `rpk topic list` is unprotected and so
decides the script's exit status with a real Kafka API call.

Its failure path was exercised offline (stubbed `docker`/`nc`/`rpk`: container "already running",
port accepting, broker unreachable): **`ensure-broker.sh` exits 1** with
`rpk: unable to reach the broker at localhost:9092`. So the concrete defect — a false success from
a non-proving probe, or from an ignored budget exhaustion — is not present, and the broker scripts
were left unchanged. One observation, not a defect and deliberately not "fixed": `ensure-broker.sh`
prints `ready.` from the port wait *before* `create-topics.sh` proves the broker usable, and
`create-topics.sh`'s per-topic `create` is `|| true`-swallowed — the exit status is still honest
because the final `rpk topic list` is not.

## Completion notes (2026-10-03)

- **Demo/example coverage:** none applies. This is local/CI infrastructure (a readiness gate in
  `platform/local/scripts/`), with no app-author surface, `sol.toml` field, scaffold or generated
  manifest; the ticket's own runnable check is the new `internal/ci/` test plus the documented
  `run_tests.sh postgres` path.
- **Language parity (DEC-022):** no application-facing contract change — no impact.
- **Limitation recorded:** the client probe uses `--add-host host.docker.internal:host-gateway`,
  which needs Docker 20.10+ (validated here and on the CI runner's Docker). On an older or
  unusual Docker the client run fails and the gate now reports *that* error rather than pretending
  the server was slow. The gate proves a usable database through the published address; it does
  not claim anything about the server's internal state.
- The follow-up this ticket itself suggested — the diagnostics step printing container creation
  time — is left alone: it already prints `State.StartedAt`, which was enough to read the race,
  and changing the workflow's diagnostics was not needed for this fix.
