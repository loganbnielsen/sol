Resolve npm workspace membership from relative paths

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `cli/lib/local/sol_cli_local_run.ml:72-97` with callers and existing tests at origin/main `2dfa5694`. Evidence and reproduction limits are recorded in the source audit.

## Problem

declares treats any workspace entry containing * as matching every service and otherwise compares package name or final directory basename. An ancestor tools/* declaration wrongly captures app/api/api_svc, while the valid exact entry app/api/api_svc is rejected. Generated npm build commands then select the wrong project root.

## Remediation

Resolve membership using the unit directory relative to each candidate npm root and npm's supported workspace semantics. Reuse an installed/native resolver where practical; do not make arbitrary glob strings mean universal membership. Keep standalone packages independently buildable.

## Acceptance criteria

- Unrelated tools/* does not capture app/api/api_svc; a valid nested exact entry and matching supported patterns select the ancestor. The generated build command succeeds in representative standalone and workspace fixtures. Update the runnable TypeScript reference fixture and record capability parity impact.
- Record the application demo and per-language verdict in completion notes wherever the change affects an application contract.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `788e688d`: `declares ~entry ~package_name ~dir_name` returned true for a package-name match, a basename match, or *any* entry containing `*`, so `tools/*` in an ancestor `package.json` captured `app/api/api_svc` while the exact entry `app/api/api_svc` (neither the package name nor the basename) was rejected.
- **Fix.** Membership is now decided from the unit directory **relative to each candidate npm root** (`relative_under ~prefix:parent unit_dir`) matched against the entry with npm's supported subset of workspace semantics: an exact path, `*` (within one path segment) and `**` (across segments), after normalizing a leading `./` and trailing `/`. A bare glob is no longer universal, and the package name / basename heuristics are gone; `package_name` is still used for `npm run build --workspace <name>`. Standalone units (`npm_root = unit_dir`) build with plain `npm run build` in place.
- **Tests** (`cli/test/test_local_run.ml`, `adapters` group): unrelated `tools/*` leaves `app/api/api_svc` standalone; a nested exact entry (`api/api_svc` in an `app/` root) selects the ancestor and builds with `--workspace api`; `api/*` selects it too; `app/*` does **not** reach `app/api/api_svc`. **Mutation-checked**: restoring the "any entry containing `*`" rule fails the three new cases (and the pre-existing exact-entry case) while the fix passes all 8 adapter cases.
- Validation: `dune build`; `dune fmt --preview` and `check_no_comments.sh` clean. Note: the pre-existing `command phases` case ("build gates launch") fails locally on unmodified `origin/main` too (verified by stashing the fix) — it runs the built `sol local run` binary against a fixture and is environment-dependent, not a regression from this change.
- **Runnable fixture / parity.** The runnable TypeScript reference fixture `examples/pluto/app/demo_ts` needed no change: its root `package.json` declares the exact relative entries `order_svc` and `fulfillment_worker`, which resolve identically before and after, and it must stay an ordinary npm workspace; the new nested/glob semantics are covered by the unit fixtures above. **Language parity: no capability impact** — this is CLI build-mode selection for a TypeScript unit (which npm command and project root the CLI uses), not a change to the TypeScript framework contract in `@sol-fab/*`.
