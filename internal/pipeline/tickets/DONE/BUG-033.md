**Depends on:** None.

**Related:** INFRA-016 (the merge that surfaced this).

`soldev pipeline merge`'s post-merge safety net reverts the just-applied
squash commit **locally only** on a local test failure, after the merge to
`origin/main` has already succeeded — this is the wrong place for that
check and produces a misleading or actively risky outcome depending on
whether the revert is ever pushed.

## Problem

`run_merge_finish` (`devtools/soldev/lib/soldev_merge.ml:462-484`, and the
build-failure path at `:617-649`) runs after `merge` has already executed
`gh pr merge --squash --delete-branch --admin` against GitHub. If the
local `run_tests.sh` fails afterward, it does:

```ocaml
SOL_SKIP_HOOKS=1 git revert <merge_sha> --no-edit
```

on the **local** `main` checkout, then prints (unconditionally, whether or
not the revert happened) "Local main has new commits — remember to `git
push origin main`."

This design is broken regardless of whether the revert gets pushed:

- **If it's never pushed** (confirmed to be the actual current behavior —
  neither revert path calls `git push`; the "remember to push" line is
  informational only): the revert accomplishes nothing except diverging
  the local checkout from the authoritative `origin/main`, and prints a
  message ("ticket returns to READY_FOR_ENGINEERING") that is false for
  everyone except this one local checkout. `origin/main` still has the
  merge; the ticket is still done as far as the repo of record is
  concerned. This is what actually happened during INFRA-016's merge: a
  Loki-connection-refused failure caused by Docker not running locally
  produced a local revert commit that was never real, and had to be
  discarded with `git reset --hard origin/main`.
- **If it were ever changed to auto-push** (not current behavior, but the
  existing code path makes this one line away): one developer's ambient
  local infrastructure failure (Docker down, a stale k3d cluster, a
  half-configured laptop) could silently undo a change the repo's own
  authoritative CI already accepted, on a shared branch, with no review.

The safety check is in the wrong place. Everything `merge` can verify
about the *code itself* (build, tests, review-pass marker, CI status)
belongs **before** `gh pr merge` touches `origin/main` — at that point a
failure just blocks the merge, which is cheap and unambiguous. Once the
remote merge has succeeded, a local machine's test run reflects that
machine's environment as much as the code; it is not a trustworthy signal
for silently mutating shared history, and a *local-only* mutation in
response to it is not a safety net at all — it just makes local state
lie about what happened upstream.

## Remediation

**Invariant to satisfy:** All locally enforceable merge preconditions
must be established before mutating authoritative main. Once the remote
merge succeeds, local verification failure must not manufacture a
divergent local rollback state.

Concretely:

- `run_merge_finish`'s functional-test-failure branch
  (`soldev_merge.ml:462-484`) and the post-merge-build-failure branch
  (`:617-649`) must stop calling `git revert` on local `main` when the
  local test run fails after a successful remote merge. A local failure
  at this stage is a **report**, not an action: print what failed and
  that `origin/main` was not touched, and stop.
- If a genuine post-merge revert capability is still wanted (e.g. for a
  real regression caught by this same local suite), it must act against
  the authoritative remote — an explicit `git revert` + `git push
  origin main` pair, done deliberately (e.g. a `soldev pipeline
  revert <sha>` command a human or CI invokes on purpose) — never as an
  automatic side effect of a local `merge` invocation whose local
  environment cannot be assumed representative of `origin/main`'s state.
- Whatever pre-merge checks are cheap enough to run locally before `gh pr
  merge` (build, unit tests) should move there if they aren't already, so
  a real regression is caught before it reaches `origin/main` rather than
  reverted after.
- Update `.claude/CLAUDE.md`'s description of `pipeline merge` /
  `pipeline merge-finish` to match the corrected behavior once
  implemented.

## Acceptance criteria

- A local test failure in `run_merge_finish` after a successful remote
  merge no longer creates any local commit that didn't already exist on
  `origin/main` — it only reports the failure.
- No code path in `soldev_merge.ml` silently diverges local `main` from
  `origin/main` in response to a local-only signal.
- If a deliberate authoritative-revert path is added, it explicitly
  pushes to `origin/main` as part of the same operation (never leaves a
  local-only revert commit that a "remember to push" message treats as
  optional).
- `.claude/CLAUDE.md`'s merge/merge-finish description is updated to
  match.

## Completion (2026-09-22)

**Both revert paths are gone.** `run_merge_finish` and the post-merge
build-failure branch in `run_merge` now report and stop; neither calls `git revert`,
so no path in `soldev_merge.ml` can diverge local `main` from `origin/main` in
response to a local-only signal.

The decision is now a pure value, `post_merge_action_of_rc`, so the rule is pinned
by a test rather than by reading the call sites (`test_merge.ml`, 14 tests):

| rc | action |
|---|---|
| `0` | record the perf baseline |
| `2` | the perf-ratio verdict — informational, still records the baseline |
| anything else (1, 3, 127, …) | `Report_local_failure`, which prints that the merge stands and exits non-zero |

That last row is a second, smaller defect fixed on the way: the old shape tested
`perf_rc = 1` and treated **everything else** as success, so an *unrunnable* suite
(127, or any other code) fell through to "record a baseline" and printed
`✓ merged`. A crashed runner was reported as a merged success — the fail-open shape
this audit series keeps finding. `test_post_merge_action_of_rc` pins 127 and 3.

The failure message now names the deliberate path (`git revert <sha> && git push
origin main`) instead of pretending to have reverted, and it says why the local run
is not a verdict: GitHub's required checks already gated the merge, and the common
failure here is missing local kafka/e2e infra.

**No pre-merge local test run was added**, despite the remediation's suggestion.
That suite fails here for environmental reasons (no local infra), so running it
before `gh pr merge` would block merges on the same non-signal that made the
post-merge action wrong. CI is the authoritative gate and already runs on every PR;
a local pre-merge run would add a false blocker, not safety.

**Docs:** `.claude/CLAUDE.md` is now `AGENTS.md` (the agent files were consolidated
earlier), and its shepherding notes described the old behaviour in detail — including
the `git reset --hard origin/main` recovery it needed. Those are rewritten to the new
behaviour. Worth noting the disclosure in `AGENTS.md`'s pipeline inventory claimed
`merge-finish` "does not gate or revert merges" *before* this change: the document was
right and the code was wrong, and this change makes the code match the document.

**Not in scope, and still true:** `merge-finish` does create one real local commit —
the perf baseline — which is why `merge` still prints "remember to `git push origin
main`". That message is accurate and was deliberately left alone (it was tempting to
delete it, and checking first is what stopped that).
