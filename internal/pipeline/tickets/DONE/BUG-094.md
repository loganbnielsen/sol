Preserve state-list failures when resolving an existing cloud cluster

**Depends on:** None.

**Premise re-verified 2026-10-01** at `origin/main` `32ac6bb7`: `Sol_cli_provider_registry.state_holds_any` still ended `| Error _ -> false`, and `of_root` still turned that into `Ok None` (`cli/lib/cloud/sol_cli_provider_registry.ml`), so an unreadable state listing was still indistinguishable from a confirmed empty one. The original premise (2026-09-29 at `cd3251a5`) named the same defect.

## Problem

An unreadable state listing is reported as an absent cluster. During destroy, `terraform show -json` can establish a represented cloud substrate while the resolver says there is no cluster because `terraform state list` failed. The platform teardown is skipped and cloud destruction proceeds, potentially leaving resources that only platform teardown removes. Apply and plan also inherit the false absence verdict.

## Remediation

Return an error from cluster resolution when `terraform state list` fails, preserving the command failure reason. Keep confirmed empty state distinct from an unreadable listing. When destroy has observed a represented substrate and cluster resolution fails on the state listing, refuse before substrate destruction so a transient read error cannot skip platform teardown.

## Acceptance criteria

- Stub `terraform output -json` with valid cluster outputs and `terraform state list` with a failing exit: `of_root` returns an error, never `Ok None`; a successful empty listing still returns `Ok None`, and a successful identifying listing returns the cluster.
- Apply/plan surface the unknown state instead of reporting bootstrap/deferred platform phases as confirmed absence.
- A destroy with a represented substrate and failed state listing refuses before substrate destruction and reports the failed read; a confirmed absent listing keeps the existing degraded-destroy policy.
- Record why this language-neutral CLI/cloud correction has no app-author demo or cross-language framework impact.

## Completion notes

**What changed.** The distinction now exists in the type, not in a convention. `of_root`
returns `(Sol_cli_cluster.t option, resolution_failure) result`, where `resolution_failure` is
`Outputs_unreadable of string` (the outputs could not be read or built) or `State_unreadable of
string` (the listing failed, carrying `terraform state list`'s own reason). `state_holds_any`
propagates that failure instead of answering `false`, so the three answers are now distinct:
*confirmed empty* (`Ok None`), *the cluster* (`Ok (Some cluster)`), and *unreadable* (an error
that never reaches "absent"). Every caller is forced to say which it means:
`Sol_cli_provider_registry.resolution_failure_to_string` for the apply/plan paths, and — in
`destroy_deps` — `Outputs_unreadable` for the state-listing failure, which is a new third case in
`Sol_cli_cloud_destroy`'s `outputs_read` alongside the existing `Outputs_available` and
`Outputs_unavailable`.

**Why the refusal is specific to the listing.** `terraform output -json` failing is how a target
that never fully installed presents, and FND-0069's policy for that is a recorded degradation:
skip the platform teardown, destroy what Terraform represents, and let the absence check decide.
A state *listing* that fails while the outputs are readable is different — the outputs prove the
state is readable, so a listing that fails is a transient or authorization failure, and reading
it as "no cluster" is what let a destroy skip platform teardown on a target that had one. So
`Outputs_unavailable` keeps the degraded policy and `Outputs_unreadable` refuses.

**The refusal destroys nothing.** `execute` reads the install outputs once, before the workload
release and only when the substrate is represented, and returns the new `Outputs_unreadable`
failure when the listing failed. Nothing runs: no release, no elevated access, no platform
teardown, no substrate destroy, no verification, and no absence claim. The refusal is its own
case in `completion_message`, so it reads as a refusal rather than as a teardown that failed to
converge, and it says why an unreadable listing is not an absence and what to do. A target whose
substrate is absent or unreadable does not reach the read at all — there is no platform teardown
to protect there — so an idempotent re-destroy is unaffected and an unreadable *state observation*
still proceeds to the substrate destroy, where the fail-closed absence check decides.

**Coverage.** The executable protection is three unit cases in
`cli/test/test_cloud_destroy.ml` — the refusal (with the command's reason, the "not an absence"
wording, no convergence wording, and every one of release/platform/reconcile/remove/substrate/
verify at zero), a confirmed absent listing keeping the degraded policy, and an unreadable state
observation being *not* the refusal — plus two offline lifecycle scenarios:
`STATE_LIST_FAILS=1` makes the fake Terraform's `state list` fail with a real error, and the run
is asserted to exit non-zero carrying that reason, to say it is not an absence, and to invoke no
`terraform … destroy` at all; the same toggle with `sol cloud apply` is asserted to surface the
read instead of reporting the platform phases as `DEFERRED — requires cloud substrate to exist`.
The existing `STATE_EMPTY=1` apply scenario is the positive control for the other direction: an
empty listing stays `Ok None` and still reaches Terraform. No structural guard was added: the
invariant is carried by the type (a caller cannot map the failure to `Ok None` without deleting a
constructor) and behaviourally by the harness, which is where the wiring is exercised.

**Acceptance criteria.** All four hold: the stubs give an error for a failing listing, `Ok None`
for an empty one and the cluster for an identifying one, with the empty-listing case already
asserted by the harness; apply surfaces the unknown state instead of a deferred absence; a destroy
with a represented substrate refuses before substrate destruction and reports the failed read
while a confirmed absent listing keeps the degraded policy; and the demo/parity verdict is below.

**One boundary left deliberately as it was.** `apply_deps.substrate_supported` still answers
`Ok ()` for any resolution failure, so an apply whose state cannot be listed does not block on the
existing-substrate acceptability check. That is not the false-absence verdict this ticket is about
— it reports no absence, it skips a check — and it is the long-standing "cannot check, therefore do
not block the apply" policy, with the apply still failing closed later (the cluster-ready check, and
the absence verification). Widening it would be a separate decision about apply preconditions, so it
is recorded here rather than changed.

**Demo/example: not applicable.** This is a language-neutral CLI/cloud correction with no
app-author surface — no `sol.toml` field, framework primitive, scaffolded artifact or generated
manifest changes, and the only operator-visible difference is that a destroy or apply whose state
listing fails now names the failure instead of proceeding. Recorded rather than assumed, per the
coverage rule.

**Language parity (DEC-022): no application-facing impact.** The change is in Sol's cloud
resolution path, which is shared by every application language; no schema-registry convention,
wire format, trace propagation, retry/DLQ semantic, metric vocabulary, lifecycle/shutdown
contract, config/secrets contract or job semantic changes.
