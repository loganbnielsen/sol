Refuse ownership imports when Terraform state cannot be read

**Depends on:** None.

**Premise verified (2026-09-29):** At `f52b946c`, traced `Sol_cli_cloud_wiring.reconcile_ownership` through its apply, destroy, and explicit reconcile callers, `Sol_cli_cloud_destroy.addresses`, and the recovery tests in `cli/test/test_cloud_destroy.ml`.

## Problem

`reconcile_ownership` represents a failed `terraform show -json` or malformed state as `State_unreadable`, but passes that value through `Sol_cli_cloud_destroy.addresses`, which returns `[]`. A provider-present resource is then classified as `Recover` even though its Terraform ownership is unknown. With `act=true`, Sol attempts `terraform import` against the unreadable state. The dry run also reports that the resource is recoverable. The existing tests cover empty and represented address lists, but no unreadable state case at this operation boundary.

This conflates unknown ownership with absent ownership in a mutation path. A transient state/backend failure or malformed state must not authorize an import. The command caller currently treats a reconciliation error as a warning and continues, so the boundary itself must refuse before any import.

## Recommended direction

Preserve the `State_unreadable` distinction when deriving reconciliation candidates. Return a named error or unknown outcome before provider observations are converted into import actions. Keep a genuinely empty readable state eligible for recovery. Decide separately whether the apply/destroy callers should continue after this refusal; that policy must be explicit and tested.

## Acceptance criteria

- A failed `terraform show -json` and malformed state each cause explicit reconcile to refuse before any `terraform import`; dry run does not report candidates as safely recoverable.
- Apply and destroy caller behavior on unreadable state is deliberate and covered by operation-level tests; no path imports while ownership is unknown.
- Readable empty state and readable represented state retain their distinct recovery/already-owned behavior.
- Completion notes state that this is a language-neutral CLI/cloud safety correction and explain why an app-author demo is not applicable.

## Completion (2026-09-29)

- **Premise re-verified** at `origin/main`: `Sol_cli_cloud_wiring.reconcile_ownership` classified the state itself but then passed it through `Sol_cli_cloud_destroy.addresses`, which returns `[]` for `State_unreadable` (`resources` maps it to `[]`). A provider-present resource in an unreadable state was therefore a `Recover` candidate, and `act:true` ran `terraform import` against it; `--explain`/dry run reported it as safely recoverable.
- **Change.** `reconcile_ownership` now matches the state first and refuses with a named error when it is `State_unreadable`, before provider observations are read and before any disposition or candidate exists: *"refusing to reconcile: the Terraform state could not be read (…), so Sol cannot tell which provider resources this target already owns. An unreadable state is not an empty one — nothing is imported while ownership is unknown"*. `State_empty` and `State_represented` keep the existing path unchanged, so a genuinely empty readable state stays eligible for recovery and an already-owned resource stays `Already_owned`.
- **Caller policy, deliberate and documented.** `sol cloud reconcile` (including `--dry-run` and `--explain`) already maps a reconciliation error to a nonzero exit through `Sol_cli_exit.of_msg`, so it now refuses instead of printing "recoverable"/"no changes". The apply and destroy paths (`reconcile_ownership_at`) keep their existing behaviour of reporting the failure as a warning and continuing with the Terraform run they were invoked for — the refusal is inside the reconciliation, so those paths cannot import while ownership is unknown. A destroy does not import anything with or without this change.
- **Tests.** New `cli/test/test_ownership_reconcile.ml` drives `Sol_cli_cloud_wiring.reconcile_ownership` against a stub `terraform` on `PATH` that records every invocation: a failed `terraform show -json` and a malformed state each return the refusal and log no `import`; a readable-but-empty state (`{"values": null}`) is *not* refused, with no imports and an empty `restored` list. Mutation-checked — folding `State_unreadable` back into the readable branch fails the first two cases. The existing `test_cloud_destroy.ml` recovery suite still passes (55 tests).
- Demo/example: not applicable — this is a language-neutral CLI/cloud safety correction to how Sol decides whether it may adopt provider resources. No app-author surface, schema, primitive or generated manifest changes, and no runnable example exercises cloud ownership reconciliation. Language parity: no impact (the TypeScript runtime does not reconcile Terraform ownership).
