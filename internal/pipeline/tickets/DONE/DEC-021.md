**Depends on:** None.

**Related:** FEAT-076, FEAT-077, BUG-027.

Decide whether Sol adds a second messaging substrate (SQS-compatible broker,
RabbitMQ, Pulsar) to get work-queue semantics (per-message ack, visibility
timeout, retry, DLQ) that Kafka doesn't naturally provide.

## Decision

**No second broker. The distinction Sol needs is a programming-model
distinction, not an infrastructure one — and both models are served by
substrates Sol already runs.**

| Work model | Substrate | Primitive |
|---|---|---|
| Stream/event consumption | Kafka | `sol-worker` (existing) |
| Durable leased jobs | Postgres | `sol-jobs` (library, deferred — FEAT-077) |

- **Kafka worker retry/DLQ semantics (FEAT-076) are in scope now.**
  `Ack \| Retry \| Dead_letter` on top of retry/DLQ topics gets most of the
  practical benefit people reach for SQS/RabbitMQ for, without a second
  broker, second security posture, or second service in
  `sol local infra up`.
- **A more queue-shaped substrate was considered and rejected for now:
  ElasticMQ (SQS-compatible), RabbitMQ, Apache Pulsar.** Each is a real,
  capable system, but adding one doubles platform surface (broker, security
  wiring, observability integration, dev/prod parity) to buy semantics —
  native per-message ack/visibility-timeout/DLQ — that are mostly
  synthesizable on what Sol already runs. No current Sol workload demands
  the parts that aren't.
- **`sol-jobs` (Postgres-backed leased jobs) is deferred, not rejected**,
  because it isn't "another broker" operationally — `pg-eio` is already
  provisioned everywhere — and it buys something Kafka structurally cannot:
  transactional enqueue in the same transaction as the application state
  change. It stays in `BACKLOG` (FEAT-077) until a concrete workload proves
  Kafka retry-topics insufficient.
- **The precise boundary (2026-09-14, post-FEAT-076 review) is per-key
  serialization, not per-partition head-of-line blocking.** A partition being
  temporarily stalled by a retry sleep is an *implementation* property —
  fixable by giving the retry topic per-partition fiber isolation the same
  way the source topic already has it (BUG-027) — not a reason `sol-jobs`
  exists. What Kafka retry-topics categorically cannot do, no matter how well
  implemented, is retry two messages that share a key independently of each
  other: same key → same partition → ordered → one retry can still block a
  later same-key message. **`sol-jobs` is warranted only when a workload
  needs independent scheduling/retry of work that would otherwise share a
  Kafka partition/key** — not merely because an early retry-topic
  implementation happened to serialize unrelated partitions too (that part
  was a bug, not a property of Kafka).
- **`sol-jobs`, when built, is a library hosted by an ordinary `-worker`
  process, not a fourth deployable primitive.** Runtime topology
  (`-svc`/`-worker`/`-fn`) and programming model (stream vs. leased job) are
  separate axes; conflating them is how a platform accumulates an
  infrastructure museum one semantic concept at a time.
- **No pluggable backend configuration for either primitive**
  (`Worker backend: kafka | postgres | sqs | rabbitmq` is explicitly
  rejected as premature). The `Ack | Retry | Dead_letter` contract is
  substrate-agnostic in shape; only Kafka implements it today. A backend
  enum gets designed the day a second implementation actually exists, not
  before.

## Consequences

- SQS-compatible/RabbitMQ/Pulsar substrates are off the table until a
  concrete workload demonstrates that neither Kafka retry-topics nor a
  leased Postgres job survives it — this decision is the answer the next
  person should find instead of re-deriving it.
- `sol-jobs` is filed as deferred (FEAT-077), not silently forgotten and not
  built speculatively.
- Anyone re-proposing a new message broker for Sol should read this
  decision and FEAT-077's Blocked On section first.
- BUG-027 fixes the retry-topic's cross-partition head-of-line blocking and
  key-drop-on-republish; it does not change this decision and must not be
  read as evidence for or against `sol-jobs` either way.

## Amendment (2026-09-14): retry partition serialization boundary

The boundary statement above ("the precise boundary is per-key serialization, not
per-partition head-of-line blocking") is too narrow. It was written before BUG-027's
per-partition fiber isolation landed, and it conflates that fix with the residual
limitation: per-partition isolation stops a waiting retry from stalling the whole retry
topic, but it does not eliminate intra-partition head-of-line blocking.

> Any two retries that share a retry-topic partition serialize in Kafka offset order. A
> retry waiting for its backoff delay therefore head-of-line blocks every later retry in
> that partition, including retries for unrelated keys.

```text
source topic
  ↓ Retry
retry-topic partition
  ↓
offset N:   key A, retry in 10m
offset N+1: key B, retry now
```

The retry consumer reaches offset N first and waits inline until A is eligible; B cannot
be processed first even though it is already due.

**Operational rule:** maximum retry backoff is also the upper bound on retry-partition
head-of-line delay in steady state. Configure the cap no larger than the unrelated-retry
delay the system is willing to tolerate. Under backlog or overload, actual delay is
unbounded — Kafka itself is the buffer.

### Ordering consequence

`Retry_topics` deliberately trades source-partition ordering for availability of
subsequent work. A retried message re-enters Kafka at a later offset and may therefore be
processed after messages that originally followed it in the source partition, including
later messages with the same key. This is inherent to delayed retry without blocking the
original partition — not a bug. Workloads whose correctness requires strict
source-partition or per-key order must not use `Retry_topics`.

### Retry versus scheduled work

Retry is **failure-driven**: the failure decides the time (attempt → policy), attempts are
bounded, there is no caller-facing schedule identity, and cancellation/rescheduling is
not part of the contract. Job/timer scheduling is **intent-driven**: the caller supplies
the time and identity, and query/cancel/reschedule may be first-class.

The distinction is independent of absolute duration: a three-day failure backoff is still
a retry; a five-second task with caller-visible cancellation is still a job.

This broadens the `sol-jobs` warrant above from "messages sharing a key" to "work that
shares a Kafka partition/key": unrelated keys that hash to the same retry partition also
serialize. `sol-jobs` (FEAT-077) remains blocked on a concrete workload demonstrating that
this limitation is unacceptable — the corrected boundary does not unblock it.

### Durable principle

> Sol does not conceal its substrate's semantics, and does not add infrastructure to
> avoid naming them. Worker features may build on Kafka's ordering, retry, and scaling
> properties, but must document rather than hide the resulting tradeoffs — and must not
> introduce a second substrate merely to buy semantics it can state honestly on the
> existing one.

See also: FEAT-078 (align the generated worker contract with this boundary),
BUG-028/BUG-029/BUG-030 (retry-path correctness prerequisites), DOCS-015 (document the
tradeoffs in the worker specs).

## Amendment (2026-09-14): DLQ scoping is per-group, locked

BUG-030 left open whether the DLQ should be scoped per-consumer-group (mirroring the
retry topic) or per-source-topic (one shared DLQ, disambiguated by an origin-group
header), pending "the DLQ inspection story." Resolved: **per-group, locked** — this is
not merely consistency with the retry topic, it follows from what dead-lettering
actually is.

> Dead-lettering is a statement about a consumer group's processing of an event, not
> about the event itself. `orders` event X may be `Dead_letter`ed by `payments` and
> `Ack`ed by `analytics` on the very same event — there is no fleet-wide fact "X is
> dead-lettered," only "`payments` could not process X and transferred responsibility to
> its own DLQ."

The ownership model this implies:

```text
source topic
  └── consumer group
        ├── retry topic   (already decided: group-scoped)
        └── DLQ            (now decided: group-scoped too)
```

**Retry and dead-letter destinations both belong to the logical consumer group whose
processing responsibility they receive** — one invariant, not two. This also keeps the
acknowledgement ownership invariant clean: when `payments` publishes to its own DLQ,
responsibility moves from `payments`' retry offset to `payments`' DLQ to `ack`, with no
shared destination and no header required to reconstruct *who* the responsible party was.

The operational-fragmentation cost of per-group DLQs (one dead-letter surface per group)
is real but belongs to the tooling layer, not the storage topology: a future `sol dlq
list` or fleet-wide dashboard can aggregate across group-scoped DLQ topics. Physically
merging dead letters into one topic to make that tooling easier would only make it
worse — `group` becomes a header every producer and tool must preserve correctly instead
of a structural property of the topic name.

**Provenance still travels, even though it isn't required for routing.** Every DLQ
record carries an `X-Sol-Origin-Group` header naming the consumer group that
dead-lettered it, so a record remains self-describing if exported, copied, or inspected
independently of its topic name.

**Naming (BUG-030 implements this):** both retry and DLQ topics use the same canonical,
group-scoped naming helper — `<source>.<canonical-group>.retry` /
`<source>.<canonical-group>.dlq` — with the already-specified sanitization/truncation/hash
behavior for group ids that are missing, empty, over-length, or contain `.`/`_`.

> **Topology follows ownership; tooling may aggregate topology.**
