Check target applied migrations before restoring an old release

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `cli/bin/cmd_rollback.ml:39-44; cli/lib/deploy/sol_cli_rollback.ml:262-287; cli/lib/deploy/sol_cli_migration_gate.ml:read_applied` and representative callers/tests at origin/main `6eb36b2c`. The audit records reproduced behavior, positive controls and practical limits.

## Problem

Rollback computes migrations beyond the historical release from files discovered in the local checkout. After a contracting migration has been applied to the target, running rollback from the old checkout omits that file and passes the guard. Incompatible old application code is then restored against the changed database.

## Remediation

Derive compatibility from the target's applied migration state and durable disposition evidence for applied changes beyond the historical release. Fail closed when evidence or target reads are unavailable. An absent local file is not evidence that the target schema did not change. Reuse existing migration status infrastructure where appropriate.

## Acceptance criteria

- A target with an applied contracting migration rejects old-release rollback even from the old checkout, before any workload mutation. Missing applied-state/disposition evidence also refuses; an applied expansion retains safe rollback. Update a runnable migration/rollback example. This is distinct from FEAT-094 checksum tracking.
- Completion notes identify runnable example/demo coverage and the per-language capability verdict, or explain why either is not applicable.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `da2211f9`: `check_migration_boundary` iterated `current_migrations` — the files the *checkout* has — and filtered out the ones the release records. A contracting migration applied to the target but absent from an older checkout was therefore never examined: `new_migrations` was empty, `go []` returned `Ok ()`, and rollback restored old application code against the changed schema.
- **Fix.** The boundary is now derived from the target's applied set. `transaction_deps` gains `applied_migrations : unit -> (int list, string) result`, which `Sol_cli_rollback.execute` consults after the local check (`check_migration_boundary … ~applied:deps.applied_migrations`), and the check refuses when a version applied beyond the release has no readable local file (`Applied_migration_absent`, naming the version) or when the applied state cannot be read at all (`Applied_state_unavailable`). `release_migration_versions` parses the release's recorded file names and fails closed if one cannot be interpreted, so the boundary between "the schema this release ran against" and "the target's schema now" is never guessed. The local check still runs first (and still refuses an undeclared or contracting local file), so a refusal that needs no cluster contact happens without one. `cli/bin/cmd_rollback.ml` supplies the dep through the deploy gate's existing in-cluster infrastructure — `Sol_cli_migration_gate.read_applied` (the `migrate status` Job), now exported in the mli — using the same target/registry resolution the deploy gate uses, and fails closed when that target or its config cannot be resolved.
- **Tests** (`cli/test/test_rollback.ml`, `migration_boundary_check` and `rollback_transaction` groups): a version applied beyond the release with no local file blocks and names the version; an applied expansion beyond the release passes; an unreadable applied state blocks and names the reason; and at `execute` level an unreadable applied state performs **no** mutation (only `applied_migrations` is called — no `ensure_held`, `apply`, `prune` or `move_pointer`) and leaves the pointer alone. The existing local-file cases (no new migrations, new expand, contracting, undeclared, already-recorded contract) are unchanged and now pass `~applied`. **Mutation-checked**: making the applied-beyond filter empty fails the absent-locally case while the fix passes (57 tests). Full `dune build`, `dune fmt --preview`, `check_no_comments.sh` and `pipeline validate` clean; `test_migration`, `test_migration_gate` and `test_deployment_phases` stay green.
- **Docs / runnable coverage.** `docs/deployment/migration-ordering.md` now states that rollback reads the applied set from the target, that an absent local file blocks, that the offline test coverage is listed there, and keeps the live-behaviour boundary with HARDEN-002; `docs/guides/TUTORIAL.md` § Day-2 operations adds the same two refusal reasons to its list. The runnable path is the operator command itself (`sol rollback <release-id>` against a target with migrations), which is the HARDEN-002 live item rather than a new demo step.
- **Language parity: no impact** — migration disposition and the applied-state read are CLI/cluster contracts applied per workspace, independent of the workload language; no framework or application-facing surface changed.
