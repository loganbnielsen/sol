A direct deploy, `sol up` or rollback must not overwrite workload Secret values that `sol secret set` owns

**Depends on:** None.

**Finding:** FND-0052 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-24** against `origin/main @ fd5c7e0c`. Sol's live render with
`POSTGRES_URL`/`SOL_API_KEY` unset writes both as `""`. Replayed against a disposable
k3s: a deploy after a `sol secret set` rotation restored the pre-rotation credential
and blanked `SOL_API_KEY`.

## Problem

With `Kubernetes_live`, the default for direct and local deploys and hard-coded for
rollback, every apply re-renders `<svc>-secrets` from the CLI's environment. Declared
keys are required from the environment. The defaults `POSTGRES_URL` and
`SOL_API_KEY` become `""` when unset: `sol deploy` checks only `POSTGRES_URL`, and
rollback checks neither. `sol secret set` writes the same objects and is documented as
the create and rotation path. So the next deploy or rollback reverts a rotation to
whatever the deployer's shell holds, or blanks the key. A blanked key breaks every
API-key service's next start.

## Decision and current premise

Re-verified 2026-10-02 against `origin/main @ 9f68429f`: `Kubernetes_live`
render still reads values from the deploy process and includes a Secret in each
workload manifest; `sol up`, direct deploy and rollback apply those manifests.
The overwrite remains real. The September remedy of creating a Secret from the
deploy environment once is superseded by DEC-029's October 1 direction.

Operator confirmed 2026-10-02: ordinary deploy and rollback consume secret
declarations and references, and never own or mutate values. Explicit
`sol secret` operations are the only Sol CLI path that may send plaintext to an
authority. The current Kubernetes Secret path is a maturity-A delivery mechanism,
not the future cross-driver authority or application contract; DEC-029 will
replace it with authority, authorization, projection and `Secret.get` consumption.

## Remediation

Remove value rendering and Secret application from ordinary deploy, `sol up`,
and rollback. Before applying workloads, verify their declared secret
references exist and contain the required non-empty keys; fail closed if they
do not. Keep explicit `sol secret` value writes and update
`docs/deployment/credential-rotation.md` and the tutorial. Do not add a new
provider abstraction before DEC-029's open questions are resolved.

## Acceptance criteria

- Test: after a rotation-shaped change to the live Secret, deploy and rollback
  leave it unchanged, and missing required keys fail before workload apply.
- Test: ordinary deploy render contains no secret values and emits no Secret
  object to apply.
- Demo/example: tutorial secret flow; state it in completion notes.

## Completion notes (2026-10-02)

**Implemented.** With `Kubernetes_live`, rendering no longer reads the deploying
process's environment and emits no Secret object; the workload keeps its
`<svc>-secrets` references. Before applying each workload, `sol up`, direct
`sol deploy` and `sol rollback` call `Sol_cli_secret.verify_workload_secret`,
which reads the live Secret and fails closed — naming every missing or blank
required key — if it is absent or incomplete. Deploy additionally verifies the
workspace runtime Secret `sol-secrets` through `Sol_cli_substrate.ensure`. Apply
mode now refuses the `kubernetes-placeholder` and `external-secrets` backends,
whose value-less Secret would otherwise blank a live one; those remain GitOps
emission backends. `check_runtime_secret_identity.sh` was updated to hold the new
wiring (the substrate verifies the runtime Secret; the verification names it from
`Sol_cli_manifest.runtime_secret_name`).

**Required key set.** A unit's `<svc>-secrets` must carry its declared
`[infra.env] secrets` keys plus the platform defaults `POSTGRES_URL` and
`SOL_API_KEY` — exactly the set the old live render wrote. The runtime
`sol-secrets` must carry the defaults. `SOL_API_KEY` is required even for a unit
that does not use API keys, matching the previous substrate requirement and the
observed failure (a blank key breaks the next start of an API-key service).

**Create path.** With deploy no longer writing Secrets, `sol secret set` is the
sole create path. It now ensures each target namespace exists and, from the
workspace declarations, also creates the per-workload `<svc>-secrets` objects
that do not exist yet, so a fresh cluster can be seeded before the first deploy.
It remains the only Sol CLI path that writes plaintext.

**Tests.** `test_manifest_render.ml` asserts a live render emits no Secret, no
`stringData` and no value while still referencing `<svc>-secrets`;
`test_secret_reads.ml` covers present, missing and blank keys and the runtime
Secret check; `test_executor.ml` asserts an apply with an absent Secret fails
before any manifest is applied; `test_substrate.ml` asserts the substrate
carries no Secret document.

**Demo/example.** Updated `docs/guides/TUTORIAL.md`,
`docs/deployment/credential-rotation.md`, `docs/reference/substrate.md` and
`examples/pluto/README.md` to seed secrets with `sol local secret set` before
`sol up`. No new runnable artifact: the tutorial and the pluto reference
application are the demo, and their commands now show the create path.

**Language parity (DEC-022).** No language-parity impact: platform credential
delivery, not an application-facing contract. `Secret.get` and the cross-driver
authority remain DEC-029.

**Not done / follow-ups.** This fixes the maturity-A Kubernetes path only;
DEC-029 still owns the cross-driver secret authority, projection and `Secret.get`
contract. The apply-mode backend refusal has no dedicated test yet — it is a
straightforward guard and the live path it protects is covered.

**Follow-up (same day).** The first CI run after this merged failed
`golden-path-smoke` and `golden-path-smoke-ts`: both harnesses ran `sol up`
without seeding a Secret, which the old renderer tolerated but the new
verification refuses. `golden-path-smoke`, `golden-path-smoke-ts` and the
on-demand `fn-svc-isolation-spike` now call `sol local secret set` for
`POSTGRES_URL` and `SOL_API_KEY` after `sol local infra up` and before `sol up`.
That is the harness catching the contract change correctly, not a defect in the
fix; the smoke runs are not required checks, so the merge landed first.
