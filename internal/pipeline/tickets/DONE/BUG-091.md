Isolate sol-jobs claims by workspace in a shared database

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `81b15e53`, `framework/ocaml/sol-jobs/lib/sol_jobs.ml:130-150,253-269` uses a fixed table and only `kind` to route jobs. Local Postgres uses one default database, and AUDIT-024 established that multiple workspaces share it. The source audit records the SQL and existing positive control for distinct kinds.

## Problem

Two workspaces sharing Postgres and using the same job kind can claim each other's rows. A foreign handler can run the wrong side effect, or fail to decode and exhaust another workspace's job. `J.kinds` separates different job kinds but is not a workspace boundary.

## Remediation

Give the job table or its rows a required workspace identity and apply it consistently to enqueue, claim, retry, completion and terminal failure. Preserve transactional enqueue in the application transaction and claims across replicas of the same workspace. Update the migration and package contract coherently; pre-alpha does not require a compatibility shim.

## Acceptance criteria

- Two workspaces using the same Postgres database and the same `kind` cannot claim, handle, retry or finalize each other's jobs, even with different payload codecs.
- Two pollers in one workspace still share claims safely; enqueue within an application transaction retains atomicity.
- A missing or invalid workspace identity refuses before enqueue or polling rather than falling back to a shared queue.
- Update a runnable `sol-jobs` example and record the TypeScript capability verdict or tracking ticket in completion notes.

## Completion notes

**Premise re-verified 2026-10-01** at `origin/main @ 0d4fa913`, and it holds: `sol_jobs`
carried no workspace identity, so `claim_q` routed on `kind` alone. `enqueue` inserted
`(kind, payload, run_at, dedupe_key)`, and the dedupe index was `(kind, dedupe_key)`, so two
workspaces using one database and one kind also deduplicated each other's events.

**Design.** The row, not the table, carries the identity. `sol-jobs.md` fixes one
`sol_jobs` table per app and FEAT-077 makes the table name deliberately non-configurable, and
every framework `Make` takes one functor argument — so `JOB` gains a required
`val workspace : string` rather than `Make` gaining a second parameter or `enqueue`/`run`
gaining a labelled one. That choice matters: with a per-call argument a service and its
worker could pass different workspaces and jobs would enqueue into a queue nothing polls,
which is the silent half of the same bug. With one value on the job module, divergence is a
compile error. The workspace is the app's own identity — the directory name Sol already uses
for the migration table and the namespace — so it does not vary per environment.

**Implementation.** `workspace` is written by `enqueue` and filtered by every statement that
touches a row: claim, complete, retry, fail, lease renewal and retention sweep. The dedupe
unique index becomes `(workspace, kind, dedupe_key)` and the claim index `(workspace, run_at)`,
both in the contract DDL and the test DDL. `validate_workspace` runs in both `run` (before
Postgres is touched, as `` `Config ``) and `enqueue` (as an error), refusing empty, malformed
or over-63-byte values. Transactional enqueue is unchanged — `enqueue` still takes the
caller's `Pg_db.tx` — and `FOR UPDATE SKIP LOCKED` still gives same-workspace replicas safe
shared claims.

**Checks.**

- `dune build @all`; `framework/ocaml/sol-jobs/test/test_sol_jobs.exe` 11/11 and
  `test_sol_jobs_pg.exe` 19/19 against a disposable local database (`bug091_check`, dropped
  after).
- New regression `another workspace's rows are never claimed`: an `alpha` poller and a `beta`
  module declaring the same `send_email` kind, both enqueuing under one `evt-1` dedupe key.
  The alpha poller handles only its own job, the beta handler never runs, and two rows
  survive — the beta one still `pending` — which is both the isolation and the per-workspace
  dedupe in one assertion.
- Mutation check: weakening only the claim filter to `(workspace = ? OR TRUE)` builds cleanly
  and fails that test with `the alpha poller ran only its own job`, so it binds the claim
  boundary rather than the schema. A first attempt at the sweep filter had the parameter
  order backwards and the existing sweep test caught it before any commit — recorded because
  it is the reason the parameter order is worth reading twice.
- `check_ocamlformat.sh --all` and `check_no_comments.sh` pass.

**Demo/example coverage.** `examples/pluto/app/comms/notify_worker/lib/notify_worker.ml`
carries `workspace = "pluto"` — the canonical runnable job example — and `sol-jobs.md`'s
`JOB` signature, DDL and workspace paragraphs are updated together, so an author copying the
contract gets a compiling module.

**Language parity.** No new gap introduced, and the existing verdict stands: `sol-jobs` is
recorded as **intentionally deferred** for TypeScript, sequenced after FEAT-082 in FEAT-124's
own text, and there is no `@sol-fab` jobs package to change. FEAT-124 now also inherits this
contract — a TypeScript outbox or job queue sharing a database must carry the same per-app
scope — so its remediation should say so when it is picked up.
