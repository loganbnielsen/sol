Isolate sol-jobs claims by workspace in a shared database

**Depends on:** None.

**Premise re-verified (2026-10-02):** At `origin/main` `0d4fa913` the premise held exactly. `framework/ocaml/sol-jobs/lib/sol_jobs.ml` had `let table = "sol_jobs"` with `claim_q` selecting on status, `kind = ANY(...)`, `run_at` and the lease only, and `enqueue` inserting `(kind, payload, run_at, dedupe_key)`; the word "workspace" appeared neither in the library nor in its documented table, and `examples/pluto` and `internal/fixtures/venus` both created that single table. `platform/local/scripts/ensure-postgres.sh` still starts one database for every workspace, and `test_sol_jobs_pg.ml`'s positive control proved distinct *kinds* do not cross-claim while never running two workspaces with the same kind — the gap the audit described.

## Problem

Two workspaces sharing Postgres and using the same job kind can claim each other's rows. A foreign handler can run the wrong side effect, or fail to decode and exhaust another workspace's job. `J.kinds` separates different job kinds but is not a workspace boundary.

## Remediation

Give the job table or its rows a required workspace identity and apply it consistently to enqueue, claim, retry, completion and terminal failure. Preserve transactional enqueue in the application transaction and claims across replicas of the same workspace. Update the migration and package contract coherently; pre-alpha does not require a compatibility shim.

## Acceptance criteria

- Two workspaces using the same Postgres database and the same `kind` cannot claim, handle, retry or finalize each other's jobs, even with different payload codecs.
- Two pollers in one workspace still share claims safely; enqueue within an application transaction retains atomicity.
- A missing or invalid workspace identity refuses before enqueue or polling rather than falling back to a shared queue.
- Update a runnable `sol-jobs` example and record the TypeScript capability verdict or tracking ticket in completion notes.

## Completion notes

- **The identity is required, and it comes from the framework/app boundary rather than from the app's
  imagination.** `sol-jobs` reads `SOL_WORKSPACE`, validates it (non-empty, at most 63 characters,
  `a-z A-Z 0-9 _ . -`) and refuses without it: `run` fails `` `Config `` before it touches the database, and
  `enqueue` refuses with `Pg_error.Query_error` — the shape the module already used for a kind no poller
  would claim, which keeps the transactional-enqueue contract (`Pg_db.tx` composition) intact. **Sol's
  platform now renders the identity**: every workload's `<name>-env` ConfigMap carries `SOL_WORKSPACE`, and
  the config hash annotated on the pod is computed from the same list, so a deployed workload knows its
  workspace without the app doing anything, while a process run outside one (a local run, a test) sets it
  explicitly — the required-variable rule `KAFKA_SECURITY_PROTOCOL` already follows (SEC-007).
- **The row's owner is a column the database enforces.** The table gains `workspace TEXT NOT NULL`, and every
  statement names it: insert (`ON CONFLICT (workspace, kind, dedupe_key)`), claim, completion, retry,
  terminal failure, lease renewal and sweep. The claim index is `(workspace, run_at)` and the terminal index
  `(workspace, finished_at)`. Both app migrations (`examples/pluto`, `internal/fixtures/venus`) and the
  package test's DDL are updated in place — pre-alpha, no shim, as the remediation allows.
- **Coverage at the level the claim is made.** `framework/ocaml/sol-jobs/test/test_sol_jobs_pg.ml` gains a
  *workspace isolation* group of six cases run against real Postgres: another workspace's poller claims
  nothing and leaves the row pending while the owning poller runs it; a poller with an unusable identity
  refuses before polling and names the variable; an enqueue with an unusable identity inserts nothing; a
  dedupe key is per workspace (two rows where the old unique index allowed one); two pollers in one
  workspace share claims with each job handled exactly once; and a poller's sweep leaves another workspace's
  expired terminal row alone. `test_sol_jobs.ml` unit-tests the identity's shape and the refusal message;
  `cli/test/test_manifest_render.ml` asserts the rendered ConfigMap carries `SOL_WORKSPACE` and that a
  different workspace renders a different identity.
- **Mutation checks, five, each failing the isolation group:** claim without the workspace predicate,
  enqueue without the identity requirement, sweep without the workspace predicate, completion without it,
  and a dedupe key that is not scoped. Each was applied, the group observed failing, the tree restored and
  rebuilt green.
- **The existing suite earned its keep.** Running the full `sol_jobs_pg` suite caught a real mistake in this
  change's own first cut: `sweep_q`'s parameter list did not match the parameter order in its SQL, so the
  sweep bound the retention period where the workspace belonged and failed with *operator does not exist:
  text = double precision*. The fix is the binding order; the 23 pre-existing cases pass alongside the six
  new ones.
- **Verified against:** Postgres 16 in a container on this machine, `dune test framework/ocaml/sol-jobs/
  framework/ocaml/sol-outbox/ --force` (the CI command, including the outbox suite that composes with
  `Sol_jobs.enqueue`), the CLI unit suite, the format check, the no-comments guard, and every guard whose
  subject is a file this change touched, each with its mutation suite. Not run here: the local-demo
  facts-to-jobs end-to-end, which needs Kafka as well as Postgres and runs in CI on this PR's head.
- **Harness friction repaired in place.** The two database-backed suites — `sol-jobs` and `sol-outbox`,
  which composes with it — both create and drop the one `sol_jobs` table in the one database, and CI ran
  them in a single `dune test` invocation, so they could drop the table under each other; the `sol-jobs`
  suite failed exactly that way while this change was being verified. `sol-outbox`'s own `sol_jobs` DDL
  also still described the old table, which it needs to compose a job into its transaction. Both are fixed:
  the DDL carries the workspace identity, and CI runs the two suites in sequence with `--force` (which also
  makes the Postgres cases actually run in that step rather than being cached from the unit step). The
  `sol-outbox` suite's own composition assertion is the check that the two agree.
- **Demo/example.** `examples/pluto/README.md` — the canonical workspace, whose `notify_worker` hosts
  `sol-jobs` — now runs its worker with `SOL_WORKSPACE=pluto` and says why: a process outside a workload
  names its own workspace, a deployed one is given it. The venus fixture's migration carries the same table
  contract, and `docs/reference/runtime.md`, `internal/specs/framework-conventions.md` and
  `framework/ocaml/sol-jobs/sol-jobs.md` record the identity, the required-without-default rule, and the
  table shape an app author must create.
- **Language parity (DEC-022).** `sol-jobs` is the one capability the marker already lists as *intentionally
  deferred, a real parity obligation*, and this change widens the contract a TypeScript implementation will
  owe, so the tracking entry was updated rather than left silent: the verdict cell in
  `internal/pipeline/dogfood/2026-09-07_typescript_demo_spike.md` now names workspace-scoped rows claimed by
  a required `SOL_WORKSPACE` identity alongside claim-by-kind and attempt-fenced finalize.
