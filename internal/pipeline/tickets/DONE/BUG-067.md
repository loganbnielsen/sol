Wake idle workers when graceful stop is requested

**Depends on:** None.

**Premise verified (2026-09-28):** Read the implementation at `framework/ocaml/sol-worker/lib/worker.ml:100-125,209,306; framework/ocaml/kafka-eio-service/lib/kafka_service.ml consume paths` and its representative callers/tests on origin/main `6a7b1fb5`. The described boundary remains present.

## Problem

Signal and external stop promises are sampled only from decoded-message handlers. An empty topic, malformed-only traffic, or stop during the final handler leaves consumption waiting for another message.

## Remediation

Propagate graceful stop through the shared service/consumer boundary so idle consumption wakes, while any active handler completes and acknowledges before closure. Update the pinned support package if that boundary requires it.

## Upstream change (2026-09-29): merged

The mechanism belongs in the pinned `kafka-eio` package, implemented and merged
there as **loganbnielsen/kafka-eio#26** (`b9edb4e0`), and pinned here by this
change:

- `Kafka.Consumer.consume` takes `?stop:unit Eio.Promise.t` and races it against
  the blocking stream take, so an idle consumer ends immediately when stop
  resolves;
- `Kafka.Consumer.consume_partitioned` resolves its existing internal stop
  signal from the same promise, so `routing_loop` and the per-partition loops —
  which already observe it — wake too;
- a running handler is unaffected: the race is between messages, so it still
  completes and acknowledges before closure.

Its CI is green and the two new offline tests in
`kafka-eio-consumer/test/test_consumer_unit.ml` ("idle consume wakes on stop when
no message arrives", "idle consume still blocks without a stop promise") are
mutation-checked. That repository requires an approving review, which cannot be
self-given, so the merge went through the owner's admin bypass at their request.

## Acceptance criteria


- Empty-topic stop and stop during the final handler return within a bound for normal and retry workers; the in-flight handler completes. Correct the existing stop-named test that never requests stop.
- Update a runnable example/demo for application-facing behavior, or record why this is an internal-only refactor.
- Record the per-language capability verdict for framework/application contracts, or explain why language parity is unaffected.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `ed21c195`: `sol-worker`'s `should_stop` was sampled only by the message handler, and the consumer loop blocked on its message stream, so an empty topic, malformed-only traffic, or a stop requested while the final message was in flight left consumption waiting for the next decoded message.
- **Fix, in two parts.** The mechanism is in the pinned `kafka-eio` package (PR #26, merged as `b9edb4e0`): `Kafka.Consumer.consume` takes `?stop:unit Eio.Promise.t` and races it against the blocking take, and `consume_partitioned` resolves the internal stop signal that `routing_loop` and the per-partition loops already observe — a running handler still completes and acknowledges, because the race is between messages. Here, `support-refs.txt` and the three workspace `.opam` files are bumped to that commit (`bump-support-refs.sh kafka-eio`), `Kafka_service.consume`/`consume_partitioned` take and forward `?stop`, and `sol-worker` joins its two stop sources into one handle (`join_stop`, used by `with_runtime_unflushed`) which is passed to whichever consume path the worker uses.
- **Tests, and where each one runs.** `framework/ocaml/kafka-eio-service/test/test_kafka_service_integration.ml`: an idle `consume` on an empty topic is still parked after a second and returns within the bound once stop resolves (normal worker), and an idle `consume_partitioned` with an `In_memory` retry policy does the same (retry worker). Both are broker-backed, and this repository's `test` job deliberately **excludes** `framework/ocaml/kafka-eio-service/` from its unit step because that dune also builds this suite, so they gate through `internal/tooling/scripts/run_tests.sh`'s `run_kafka()` rather than through the PR's required check; they were run here against the local Redpanda (broker, schema registry and admin API up) and pass. The mechanism itself is CI-gated in the package that owns it: `kafka-eio-consumer/test/test_consumer_unit.ml`'s "idle consume wakes on stop when no message arrives" needs no broker and runs in kafka-eio's own CI on the commit this change pins. `framework/ocaml/sol-worker/test/test_worker.ml` (which the `test` job does run): the stop-named test that **never requested a stop** ("two messages both processed") is replaced by "a stop request after a message stops before the next", which resolves the caller's stop promise from inside the handler and asserts the in-flight message completed while the next was never handed to the handler; a new "stop handle wakes from the signal or the caller" test covers the join in both directions and that a second source firing is harmless. **Mutation-checked**: making either forwarding path hand the consumer a promise that never resolves fails its integration case with a timeout while the fix passes; upstream, removing the race fails the idle test there. The one line the required check does not reach is the `~stop:` argument itself — it is covered by the broker-backed cases above, not by a CI-gated test.
- **Spec/doc.** `framework/ocaml/kafka-eio-service/kafka-eio-service.md`'s `## Public API` block carries `?stop:unit Eio.Promise.t` on both entry points, which `internal/ci/check_framework_doc_signatures.py` requires: the first CI run of this PR failed precisely there (a prose paragraph about `?stop` is not a signature), so the spec and the `.mli` are now in step.
- **Validation.** `dune build`, the whole `framework/` test set with the local broker up, `internal/ci/check_ocamlformat.sh --all` (the CI step, which caught a formatting drift `dune fmt --preview` had not) and `check_no_comments.sh` are clean.
- **Runnable example / demo review: internal-only.** `sol-worker`'s `stop` parameter already existed and its contract is unchanged — a resolved `stop` means "stop" — so nothing an app author writes changes; what changed is *when* it takes effect. `examples/pluto`'s workers and the local demo already exercise graceful stop via SIGTERM, and the new behaviour is covered by the integration tests above rather than by a demo step, which would need a live broker and a deliberately empty topic.
- **Language parity.** No shared contract changed: this is OCaml worker-runtime lifecycle behaviour, and `stop` is already part of the worker API. The TypeScript worker runtime (`examples/pluto/app/demo_ts/fulfillment_worker`) does not consume Sol's `?stop`; whether the TS consumer also wakes while idle is a capability row for the TS matrix (FEAT-080/DEC-022), recorded here rather than silently assumed, and this change adds no new parity obligation because no convention or app-author concept was introduced.
