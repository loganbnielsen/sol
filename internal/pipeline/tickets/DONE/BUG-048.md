Make `sol.toml` the single, required source of a `-fn` schedule, key Pushgateway metrics by workload, and actually push them

**Depends on:** None.

**Finding:** FND-0034 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-23** against `origin/main @ f3e9480b` while filing (see the finding).

## Problem

`extract_schedule` defaults an absent `schedule` to hourly; `Fn.Cron "<cron>"` in code is a second schedule the runtime never uses except as the default Pushgateway `job` name (two functions with one schedule would overwrite each other's group); generated `-fn` mains never pass `~pushgateway_url`, so `sol_fn_invocations_total` never leaves the process (EXP-022, still live).

## Remediation

Require `[service] schedule` for `-fn` (plan error naming the file when absent; remove the hourly default and the duplicate re-read — use the plan's loaded `toml`). Change `Fn.trigger` to carry no schedule string (`Cron | Lambda`). Default the Pushgateway job to the workload identity (`<domain>/<name>`, via an env var the manifest renders). Have `Fn.Make.run` read `PUSHGATEWAY_URL` when `?pushgateway_url` is omitted, and update the scaffold. This subsumes EXP-022 — move EXP-022 to DONE in the same PR with a pointer here.

## Acceptance criteria

- A `-fn` with no `schedule` fails `sol plan`/`deploy` with a message naming the `sol.toml`.
- Two generated `-fn`s push to distinct Pushgateway groups (test on the job-name derivation).
- A generated `-fn` with `PUSHGATEWAY_URL` set pushes after a run (test with a stub endpoint).
- `TUTORIAL.md:520` no longer says the schedule is read from source.
- Demo/example: the scaffolded `-fn` and any example `-fn` are updated (author-facing change).
- TS parity: record verdict for TS scheduled functions.

## Completion notes

- **Schedule: one source, required.** The plan takes a `-fn`'s schedule from the
  already-loaded `sol.toml` (`[service] schedule`). A missing one is a
  `Toml_error (Validation …)` naming the file. `Sol_cli_manifest.extract_schedule` (a
  second read that defaulted to hourly) is removed, and so is the render-time
  `Option.value ~default:"0 * * * *"`: a spec without a schedule (e.g. an old recorded
  release) is refused at render.
- **`Fn.trigger` is `Cron | Lambda`**, with no cron string. The scaffold template and
  `sol-fn` tests are updated, and the scaffolded `sol.toml` comment says "(required)".
- **Pushgateway group = workload.** Every `-fn` render adds
  `SOL_PUSHGATEWAY_JOB=<namespace>.<name>` to its ConfigMap env, and `Fn.Make.run`
  defaults `?job` to it (then `"sol-fn"`/`"lambda"`), no longer to the cron string.
- **Metrics actually leave the process.** `Fn.Make.run` defaults `?pushgateway_url` to
  `PUSHGATEWAY_URL`, which manifests already render, so generated mains push. This
  subsumes EXP-022, whose premise was re-checked and which is moved to DONE.
- Tests: plan (a schedule comes from `sol.toml`; no `sol.toml` or no key is a plan
  error), render (a `-fn` carries `SOL_PUSHGATEWAY_JOB`, a svc does not, a `-fn` without
  a schedule is refused), and `sol-fn` (a stub Pushgateway receives
  `PUT /metrics/job/myapp-billing.invoice-fn` with only the env set). The old tests that
  pinned the hourly default are removed. Two unrelated fixtures (`test_function_volume_fails`,
  the profile availability test) now declare a schedule so they keep testing what they test.
- Mutation checks (`audits/README.md`), builds rc=0: the plan's missing-schedule branch
  returning hourly fails the plan tests; no `PUSHGATEWAY_URL` fallback fails the push
  test; ignoring `SOL_PUSHGATEWAY_JOB` fails the push test.
- Docs: `sol-fn.md` (module type, `run` defaults, generated main), `TUTORIAL.md`, the
  `.mli`.
- Demo/example: author-facing change (`Fn.Cron`, required schedule). The scaffold
  templates are the demo here: no `examples/` or fixture workspace contains a `-fn`
  (`rg -n 'Fn.Make|Fn.Cron' examples internal/fixtures` is empty).
- Language parity: TS scheduled functions are outside this repo (`@sol-fab/*`). The CLI
  side (required schedule, `SOL_PUSHGATEWAY_JOB` rendered) applies to both languages; a
  TS fn would need to read `SOL_PUSHGATEWAY_JOB` too. That is recorded here as unassessed
  rather than claimed equivalent.

**CI (2026-09-24):** the first CI run failed golden-path-smoke with
`Error: The constructor Fn.Cron expects 1 argument(s)`: the scaffolded workspace
pins the framework to `sol.git#main`, so its image built this branch's scaffold
(`Fn.Cron`, no argument) against main's `sol-fn` (`Cron of string`). No PR that
changes a framework API used by the scaffold could pass that job. Fixed in
`.github/workflows/ci.yml`: golden-path-smoke and example-dockerfile-smoke now
rewrite the workspace's `sol.git#main` pins to the commit under test
(`pull_request.head.sha`, or `github.sha` on main) before building.
