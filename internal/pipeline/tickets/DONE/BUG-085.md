Keep unobservable provider checks unresolved during cloud reconciliation

**Depends on:** None.

**Premise verified (2026-09-29):** At `3f662e7b`, traced `Unobservable` from both provider adapters through `Sol_cli_ownership_reconciliation.dispositions`, `outcome`, and `cmd_cloud_tf`'s explicit reconcile exit decision. Existing recovery tests exercise `Present` mappings, not an unobservable inventory.

## Problem

Both provider adapters return `Unobservable` on failed API/CLI checks. `dispositions` discards that variant, so an inventory with only failed checks produces no dispositions. `outcome []` prints `Infrastructure ownership is reconciled. No changes.`, and `sol cloud reconcile` exits successfully because `unreconciled []` is empty. The `--explain` mode can show failed observations, but the default success claim conceals that provider reality was not established.

## Recommended direction

Carry provider-observation completeness into the reconciliation outcome and exit decision. Report checks that could not run as unknown, without attempting imports for them. Preserve successful reconciliation for a complete, genuinely empty inventory.

## Acceptance criteria

- An unobservable provider check makes `sol cloud reconcile` report an incomplete/unknown result and exit nonzero, including in dry-run mode; it never prints a reconciled/no-changes claim for that inventory.
- Mixed `Present` and `Unobservable` observations report both recoverable/refused resources and the unresolved checks, without converting unknown to absent.
- A complete all-absent inventory still reports no changes and exits successfully. Tests cover the operation outcome, not only the observation constructor.
- Completion notes state that this is a language-neutral CLI/cloud safety correction and why an app-author demo is not applicable.

## Completion (2026-09-29)

- **Premise re-verified** at `origin/main`: `Sol_cli_ownership_reconciliation.dispositions` mapped every `Unobservable` observation to `[]`, so an inventory whose checks all failed produced no dispositions; `outcome []` printed *"Infrastructure ownership is reconciled. No changes."*, `unreconciled []` was empty, and `sol cloud reconcile` (including `--dry-run` and `--explain`) exited 0 while provider reality had never been established.
- **Change.** A new disposition, `Unresolved { resource_class; reason }`, carries each `Unobservable` observation instead of dropping it. `unreconciled` counts it, which is what drives the reconcile command's `outstanding` check, so the command now reports the unresolved checks and exits 1 — dry run included, because `outstanding` is computed before the `dry_run` outcome text. `candidate` ignores it, so nothing unresolved is ever imported, and observations that are genuinely absent, external or not attributable are unchanged.
- `outcome` now claims reconciliation only for a complete inventory: with unresolved checks it prints *"Infrastructure ownership could not be established"* (or, in a mixed inventory, both the restored/refused detail and the unresolved checks) and never the reconciled/no-changes text. `report` renders them as `UNKNOWN: <class> could not be checked: <reason>`, and `summary` gains an `N unknown` count. The existing text for complete inventories is byte-for-byte unchanged.
- **Tests.** `cli/test/test_cloud_destroy.ml` gains three cases: an all-unobservable inventory is carried as `Unresolved`, is outstanding, and makes the outcome name the check while refusing any reconciled claim; a mixed present-plus-unobservable inventory reports the recoverable resource *and* the unresolved check without calling the result reconciled; and a complete all-absent inventory still reconciles with no changes and nothing outstanding. Mutation-checked — mapping `Unobservable` back to `[]` fails the first two.
- **Scope note.** The apply and destroy paths keep their existing best-effort policy (they warn about refused resources and continue with their own Terraform run); BUG-085 named the reconcile command's outcome and exit decision, and those paths do not claim reconciliation. Making them surface unresolved checks too would be a separate change to their warning policy.
- Demo/example: not applicable — a language-neutral CLI/cloud safety correction to the reconciliation outcome and exit code. No app-author surface, and no example runs `sol cloud reconcile`. Language parity: no impact (the TypeScript runtime does not reconcile Terraform ownership).
