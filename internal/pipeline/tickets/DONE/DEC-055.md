## Decision

**Decided 2026-09-28** by the operator: **GCP gets first-class TLS through a provider-native Cloud DNS
DNS-01 solver using GCP Workload Identity.** AWS keeps Route 53 and its AWS identity mechanism, and the
higher-level contract stays provider-neutral: *if a provider/profile claims TLS support, the provider
implementation must supply a functioning certificate issuance path.* The route-53-everywhere declaration
is treated as what it was — an AWS implementation detail that had leaked across the provider boundary.

The boundary chosen is the one the module already used for Thanos's object-store identity, not a new
certificate-provider abstraction:

- the shared module selects the solver and the pod's identity annotation from `var.cloud_provider`, and
  takes each provider's solver scope and identity as inputs;
- each provider **cluster** root owns the provider-native resources — AWS: the IRSA role and the
  zone-scoped inline policy; GCP: the GSA, two least-privilege custom roles, a zone-scoped record
  binding, a project-level zone-discovery binding and the Workload Identity binding for
  `cert-manager/cert-manager`;
- each provider **platform** root mirrors the shared definition and passes its own values;
- an empty identity fails closed at plan time, so a solver that cannot authenticate never deploys.

Implemented in the same change, with `internal/ci/check_provider_tls_path.py` and twelve mutations as the
executable contract, and the GCP driver's install-time refusal removed — the gate existed to be lifted
once the issuer path was wired. See `FND-0067` for the implementation table and the one AWS observation
(the declared IRSA role was never annotated onto the pod, so the identity it declares was arguably
unreachable there as well; the wiring is now shared, and AWS stays unqualified until an AWS run reaches a
platform install).

## Question

Attempt 17 was the first GCP run to reach `Ready`, and therefore the first to reach the harness's
delegation boundary. The platform installed, the delegation resolved, and then **no certificate could
issue**, because the shared platform module declares exactly one ACME DNS-01 solver for both cluster
issuers:

```yaml
solvers:
- dns01:
    route53:
      region: us-east-1
```

with the IAM role supplied only by `cert_manager_irsa_role_arn`, a variable whose own description says
*"AWS only … Leave empty on GCP."* On GCP the role is empty, cert-manager falls back to the ambient AWS
credential chain, and every challenge ends in
`PresentError … NoCredentialProviders: no valid providers in chain`.

So: **how does a GCP cluster satisfy DNS-01, and what happens when it cannot?** This is a decision rather
than a fix because every answer changes what the product promises — a new cloud-DNS integration and its
identity model, or a stated limitation on the profile, or a refusal at target evaluation.

## Options considered (the remedy space)

The remedy space, with what each costs:

1. **A Cloud DNS solver, selected by provider.** `solvers: [{dns01: {cloudDNS: {project: …}}}]` plus the
   Workload Identity binding that lets cert-manager write the zone, with the shared module choosing the
   solver per provider instead of assuming AWS. This is the option that makes the profile's TLS row
   reachable on GCP, and it needs live evidence of its own: a certificate that issues.
2. **Declare the TLS row unsupported on GCP**, in the profile's capability record and the matrix, so a
   run does not read "delegation observed" as a pass and the limitation is stated once rather than
   rediscovered per attempt.
3. **Refuse the profile on a provider with no solver** — the way the Autopilot refusal does — so a target
   that can never serve TLS says so before installing.
4. Something else.

**Explicit non-goals:** do not give a GCP cluster AWS credentials, do not switch the platform's ingresses
to HTTP-01 (they are DNS-validated by design, and not all of them are publicly reachable), do not weaken
or remove the issuer, and do not make `Ready` depend on certificate issuance — that separation is
deliberate and is what let this run report the install's success separately from the TLS failure.

## Why this is a decision and not a fix

Option 1 introduces a cloud-DNS integration and an identity model (Workload Identity bindings, a service
account with DNS-administrator rights on the zone) that the platform does not have on GCP today; options
2 and 3 change what the product tells an app author about GCP. Attempt 17's evidence establishes the
failure; it does not select among these.

## Acceptance criteria

- The decision is recorded with its rationale and the evidence it rests on.
- Whichever option is chosen, a GCP cluster either issues a certificate for a platform ingress with the
  issuance recorded by a live run, or the profile states the limitation where a target's author reads it.
- The AWS path is unchanged: `cert_manager_irsa_role_arn` still drives the Route 53 solver there.
- `internal/pipeline/audits/QUALIFICATION_STATUS.md` is updated with the outcome.
