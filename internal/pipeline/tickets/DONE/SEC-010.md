**Premise verified 2026-09-24:** `Sol_cli_db_credential.provider_creates_postgres` is `Aws -> true | _ -> false` (`cli/sol/lib/sol_cli_db_credential.ml:21`) and keys on AWS's `create_rds`; the GCP root creates Cloud SQL from `var.db_password` (`cli/platform/infra/gcp/main.tf:202`). On GCP, Sol's refusal of `--var db_password` (the value reaches the logged argv) never runs.

## Problem

One wildcard provider match conflates two concerns: a missing required input, and a secret in logged argv.

## Remediation

Do **not** change the match to `Aws | Gcp -> true`.

- **Missing input → Terraform.** AWS declares `db_password` with `default = ""` (`cli/platform/infra/aws/variables.tf:89`), the only reason Sol's `Missing` check exists; GCP declares no default, so Terraform already refuses. Make AWS fail at plan time too (remove the empty default, or a validation tied to `create_rds`).
- **Secret in argv → Sol process/logging safety.** Refuse `--var db_password` (and any other declared secret variable) on every provider, using or extending `Sol_cli_process`'s `redact` mechanism.

## Acceptance criteria

- AWS: `--var db_password=…` is refused; a missing password fails at `terraform plan`, before any apply.
- GCP: `--var db_password=…` is refused (a regression test that fails on current `main`).
- A root that declares no such variable is unaffected.
- No provider match remains in this logic.
- Every other wildcard match on `Sol_cli_provider.t` is listed in the completion notes with its hazard (known today: `sol_cli_config.ml:1432`, `sol_cli_cloud_lifecycle.ml:52`). Do not refactor them here.

## Completion notes (2026-09-24)

**Missing input → Terraform (already true; no root change needed).**
- AWS: `aws_db_instance.postgres` already carries a plan-time `precondition` requiring a usable
  `db_password` when `create_rds = true` (`cli/platform/infra/aws/main.tf:335`), guarded offline by
  `cli/sol/test/check_production_infra.sh`. The empty default stays, so roots that create no database
  need no password.
- GCP: `db_password` has no default, so Terraform refuses to run without it. Verified locally with
  stdin at `/dev/null`, as Sol runs it: `terraform apply -auto-approve < /dev/null` on a root with a
  required sensitive variable exits 1 with "The root module input variable "db_password" is not set,
  and has no default value" before doing anything.
- So Sol's `Missing` check was redundant, and is deleted.

**Secret in argv → Sol, derived from the root.** `Sol_cli_db_credential` (and its provider match)
is replaced by `Sol_cli_sensitive_vars`: it reads the variables the Terraform root declares
`sensitive = true` from the root's own `.tf` files and refuses any of them in the terraform argv
(`--var` or the target's variables), on `sol cloud plan|apply` **and** `sol cloud destroy` (on GCP the
password is required for destroy too; Attempt 6's recovery passed a placeholder with `-var`). No
provider appears in the logic.

**Evidence.**
- `cli/sol/test/test_sensitive_vars.ml` (7 cases): parser (sensitive vs not, validation blocks, a
  brace inside a string, several files); **positive control against the real AWS and GCP roots** (both
  declare `db_password` sensitive); refusal on both providers; message names `TF_VAR_db_password` and
  never echoes the value; a root without the declaration is unaffected; an unreadable root fails
  closed.
- End to end with the real binary and a logging fake `terraform`, GCP target,
  `sol cloud plan prod/gcp/us-central1 --var db_password=hunter22`:
  - `main @ dc8d2b61`: proceeds to "Initializing cloud infrastructure (gcp)…"; the password reaches the
    terraform argv (1 logged call carries it) — the defect;
  - this branch: refused before any terraform call (0 calls); `--var region=…` proceeds as before;
    `sol cloud destroy … --plan --var db_password=…` is refused the same way.
- `dune test cli/sol/test/` passes in full (exit 0), including the offline lifecycle harness;
  `check_ocamlformat.sh --staged` clean.

**Other wildcard matches on `Sol_cli_provider.t` (recorded, not changed here):**
- `sol_cli_config.ml:1432` — `Aws when is_production_postgres -> rds_deletion_protection=true | _ -> vars`.
  GCP relies on its root default (`sql_deletion_protection` defaults to `true`), so no live defect;
  a new provider would silently get no production deletion protection from Sol. Hazard.
- `sol_cli_cloud_lifecycle.ml:52` — backend-config fallback returns an error for a missing
  `state_bucket`. Fails closed; low hazard.
Both go into REFAC-092's wildcard allowlist with these reasons.
