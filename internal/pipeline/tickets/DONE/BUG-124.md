## The gap

`operations.md` §5 states the contract for `sol check`'s exit status: **0** the
declaration is valid, **2** it ran and the answer is *no* (a check failed, and
the findings name the unit), **1** it could not do the job at all (not inside a
workspace, unreadable file). Exercising the failing and could-not-run cases
(never induced before) shows both are wrong.

### 1. A failed check exits 1, not 2

A scaffolded workspace with `app/payments/charge_svc/Dockerfile` removed:

```text
$ sol check
error: app/payments/charge_svc/Dockerfile: Dockerfile is missing
$ echo $?
1
```

It ran and the answer is *no*, so the documented code is 2.
`cli/bin/cmd_check.ml:32` returns `Sol_cli_exit.reported ()`, whose `code`
defaults to 1 (`cli/lib/base/sol_cli_exit.ml:8`). A `--scope` that matches
nothing already exits 2 via the `fail` helper; a failed check is the only
"answer is no" case that does not.

### 2. An unreadable `sol.yml` is an uncaught exception

```text
$ chmod 000 sol.yml && sol check
sol: internal error, uncaught exception:
     Sys_error("/tmp/obs050-qual/obsdemo/sol.yml: Permission denied")
     Raised by primitive operation at Stdlib.open_in_gen in file "stdlib.ml" ...
     Called from Sol_cli_config.load in file "cli/lib/workspace/sol_cli_config.ml", line 623
$ echo $?
125
```

`Sol_cli_config.load` guards `Sys.file_exists` but not the read
(`In_channel.with_open_bin`). The documented code is 1 with a clean
"could not do the job" message; instead every command that loads the workspace
model (`status`, `logs`, `up`, `deploy`, `check`, …) crashes with an internal
error when `sol.yml` is unreadable. `sol check` is where the contract is
written down, so it is the surface this ticket fixes.

## Remediation

1. `cmd_check.ml` returns `reported ~code:2 ()` when the check ran and found
   errors, matching the documented vocabulary.
2. `Sol_cli_config.load` catches `Sys_error` from the read and returns an
   `error` naming the path, so an unreadable `sol.yml` is `exit 1` with a
   diagnostic instead of an uncaught exception. Other commands that share
   `load` get the clean failure too.

## Acceptance criteria

- `sol check` in a workspace whose declarations fail exits 2 and still prints
  the finding.
- `sol check` with an unreadable `sol.yml` exits 1 and prints a message naming
  the file; it never prints `uncaught exception`.
- `Sol_cli_config.sol_yml_services` returns an `Error` naming the path when the
  file cannot be read.
- A valid workspace still exits 0.

**Demo/example:** internal CLI diagnostic; no app-author surface changes, so no
example update applies.

**TypeScript parity:** no language-parity impact — the exit vocabulary is the
CLI's, and the TypeScript framework does not implement `sol check`.

## Completion (2026-10-02)

**Premise verified.** `rg -q 'reported ~code:2' cli/bin/cmd_check.ml` exited 1
before the fix (the check used the code-1 default) and exits 0 after it.

**What changed.** `cmd_check.ml` returns `reported ~code:2 ()` for a failed
check; `Sol_cli_config.load` wraps the `In_channel.with_open_bin` read and turns
`Sys_error` into an `error` record naming the path (with the duplicated path
prefix stripped so the message reads cleanly).

**Verified end to end** with the built binary on a freshly scaffolded
workspace:

```text
$ sol check                          # valid
sol check: ok
exit=0

$ rm app/payments/charge_svc/Dockerfile && sol check
error: app/payments/charge_svc/Dockerfile: Dockerfile is missing
exit=2

$ chmod 000 sol.yml && sol check
error: /tmp/bug124/w/sol.yml: Permission denied
exit=1
```

The unreadable case previously printed `sol: internal error, uncaught
exception: Sys_error(...)` and exited 125.

**Tests.** `cli/test/inline/test_check.ml` gains: `check: a failed check exits
2` (runs the built binary in a temp workspace), `check: an unreadable workspace
exits 1` (with a root fallback that induces the same clean exit via a directory
`sol.yml`), and `check: an unreadable sol.yml is an error, not an exception`
(directly exercises `Sol_cli_config.sol_yml_services`). The existing
`cli/test/dune` exit-vocabulary script had encoded the bug (`expect 1 … check`
for a missing Dockerfile); it now expects 2, matching `operations.md` §5. The
full suite passes.
