Make scoped deployment release records safe for workspace rollback

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `cli/lib/deploy/sol_cli_deploy_selection.ml:158; cli/lib/deploy/sol_cli_deployment_plan.ml:893-941; cli/lib/deploy/sol_cli_release.ml:76; cli/lib/deploy/sol_cli_release_store.ml:record; cli/lib/deploy/sol_cli_rollback.ml:441-447,480,589-626` and representative callers/tests at origin/main `6eb36b2c`. The audit records reproduced behavior, positive controls and practical limits.

## Problem

A scoped deployment stores only selected plan.services and advances the workspace-wide release pointer. Rollback treats those partial workloads as the entire workspace boundary and prunes every other live workload. Updating A can make rollback to that record delete untouched B. This is a documented valid scope causing an outage, not merely a malformed record.

## Remediation

Keep recorded workspace release boundaries complete after a scoped deploy, preserving unaffected workload facts from a validated current boundary. Reject unavailable/inconsistent prior evidence before unsafe mutation. An explicitly typed scope-owned release model is an alternative only if rollback and pointer semantics change coherently; do not leave a partial snapshot masquerading as a full boundary.

## Design (operator decision, 2026-09-29): per-workload provenance

A boundary conflates two things, and `--scope` is what separates them:

- **desired state** — what the workspace should be running;
- **provenance** — which deploy last applied each workload.

One release id cannot honestly represent both once a deploy can be scoped, so the
record is typed to carry them separately:

```ocaml
type recorded_workload = { spec : workload_spec; applied_by : Release_id.t }
```

`applied_by` is the id of the *deploy* that applied that workload (the plan's own
scope-content id), never a boundary id — the boundary id is derived from the
recorded boundary, so putting it inside every workload would be circular.

### Invariants

1. **A boundary is typed, and its identity covers what it recorded.**
   `release_id = f(workspace, environment, deployed specs, inherited
   (identity, applied_by) pairs)`, and for a boundary that inherited nothing
   (`inherited = []`) that is exactly `f(workspace, environment, specs)` — the
   content id a whole-workspace deploy produced before this change, so
   `of_plan` still yields the plan's own id. Provenance is part of the
   *record's* identity but never part of a *spec's* identity: the spec
   projection carries no release id, so changing who applied a workload cannot
   change that workload's spec or its rendered manifest. The boundary id is
   therefore derived from the record and never from the id being derived, so
   `validate` rederives it and no deploy id can disagree with a record id.
2. **A scoped deploy changes the desired state and the provenance only of the
   workloads inside its scope.** Out-of-scope workloads retain *both* their
   recorded spec and their provenance, taken from a validated current boundary.
3. **A boundary is complete.** It always describes every workload in the
   workspace boundary; a partial snapshot is never recorded as one.
4. **Rollback verifies and re-applies each workload under its own provenance**,
   not under the boundary id. An out-of-scope workload is therefore neither
   re-labelled nor pruned when rolling back to a boundary that did not apply it.
5. **A scoped deploy refuses before any mutation when the current boundary
   cannot be read or does not validate.** An absent boundary means there is
   nothing to retain (a first scoped deploy records what it applied).
6. **A full-workspace deploy supersedes every workload**, so its boundary is
   exactly what it deployed: a workload removed from the workspace is dropped
   from the record and rollback prunes it, as before.
7. **A record's content is a function of its id** (Kubernetes ConfigMaps are
   immutable, and the store only skips a write when the live data already
   matches). This is why the id covers provenance: were it absent — as first
   sketched — re-applying an unchanged unit under a scoped deploy would rewrite
   the same content id with a different `applied_by` and the immutable write
   would fail after the workloads had already been applied. The deployed
   workload list *and* the inherited `(identity, applied_by)` pairs are both in
   the id, so the two boundaries that differ only in provenance are two ids.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `da2211f9`: `sol_cli_release.of_plan` mapped `plan.services` — the *selected* workloads — into the record and nothing else, `Sol_cli_release_store.record_plan` recorded that partial set as the workspace boundary, and rollback's `unexpected_workloads` therefore treated every other live workload as surplus. A scoped update of A made rollback to that record prune untouched B.
- **Fix, per the operator's decision: per-workload provenance.** `Sol_cli_release_id` gains `recorded_workload = { spec; applied_by }`; `Sol_cli_release.t.workloads` is that list; `Sol_cli_release.of_plan_with_boundary ~retained plan` keeps the out-of-scope workloads (spec *and* provenance) from the current boundary, stamps the in-scope ones with the new deploy's id, and derives the record id from `(deployed specs, inherited (identity, applied_by) pairs)` via the new `Sol_cli_release_id.of_boundary`. `Sol_cli_release_store.retained_for_plan` reads the current boundary from the pointer **before** any mutation and refuses a scoped deploy whose boundary cannot be read (`is_whole_workspace` tolerates the read failure, since that deploy supersedes everything); `sol up` and `sol deploy` both read it before applying and use the returned id for retention's `current`. Rollback reconstructs and re-applies each workload under its own `applied_by` (`service_specs_of_release` returns `(spec, applied_by)` pairs, `verify_workloads` compares each live label to its own provenance, `cmd_rollback.apply_specs` renders each spec with its own release id), so an out-of-scope workload is neither re-labelled nor pruned.
- **Identity coherence (design note).** The sketch's literal rule — id from desired-state content only — has a hole: re-applying an unchanged unit under a scoped deploy would rewrite the same content id with a different `applied_by`, and Kubernetes rejects the update of the now-immutable ConfigMap *after* the workloads are applied. The implemented formula keeps a whole-workspace deploy's id exactly equal to its content id (nothing inherited ⇒ `of_content`, so `of_plan` still returns the plan's id and `test_of_plan_rederives_the_plan_identity` is unchanged), while a scoped boundary's id covers the deployed specs *and* the inherited provenance. Invariants 1 and 7 record this; the alternative would have split the deploy id from the record id and broken `sol rollback --commit`, which resolves deployment events to release records by id.
- **Tests** (`cli/test/test_release.ml`, group `scoped boundary (BUG-077)`, five cases): a scoped deploy records a complete boundary (two workloads, the untouched one keeping spec and provenance), a full boundary's id is exactly its content id, a scoped boundary's content rederives its id; rolling back to a scoped boundary covers both workloads, verifies against the live boundary and prunes nothing, while rolling back to the full boundary does the same; a full deploy that drops a workload supersedes it and its boundary reports it as surplus (deliberate removal still prunes); a scoped deploy refuses an unreadable current boundary with a message naming it, and a full deploy proceeds when the boundary is unreadable (both driven by a stub `kubectl` on `PATH`, so the wiring is exercised, not just the predicate). **Mutation-checked**: making the merge ignore retained workloads fails three of the five cases. Full `dune build`, `dune test cli/test` (whole CLI suite), `dune fmt --preview`, `check_no_comments.sh` and `pipeline validate` clean; the pinned canonical record digest is deliberately updated (`1f4ea677…` → `d14c4549…`) because the record JSON now carries `applied_by`.
- **Runnable example.** `docs/guides/TUTORIAL.md` documents the scoped-deploy contract (`--scope` block) and the rollback paragraph, and `docs/architecture/devops-pipeline.md` § release records states the completeness invariant, the per-workload provenance, the refusal on an unreadable boundary and the deliberate-removal behaviour — the operator-facing surfaces an app author reads; `sol up --scope payments` followed by `sol rollback <id>` is the runnable path, and no `examples/pluto` change is needed because the CLI contract is unchanged for a whole-workspace deploy.
- **Language parity: no OCaml/TypeScript impact** — this is boundary bookkeeping in the language-neutral CLI; the workload spec projection and rendered manifests are unchanged, so neither language's framework contract moves.
