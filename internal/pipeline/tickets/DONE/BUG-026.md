**Depends on:** None.

**Related:** FEAT-069 (the projection), FEAT-066 (rollback needs a complete record), `internal/pipeline/audits/TYPE_AUDIT.md`.

**Premise checked 2026-09-14:** `of_services_result` still derives `release_id`
from a `workload` of `{domain; name; primitive; image; config; secrets; schedule;
replicas; cpu; memory; extra_labels}` only, while `service_spec` still carries
`volumes`, `rollout_strategy`, `ingress_host`, `ingress_path`, `cluster_issuer`,
`progressive_delivery`, `calls`/`called_by` and the renderer still turns every one
of those into manifest content. So the gap is real.

The release identity projection omits fields that change the rendered manifests,
so a real change can keep the same `release_id`.

## What happens

`Sol_cli_deployment_plan.of_services_result` derives `release_id` from
`Sol_cli_release_id.content`, whose `workload` carries `domain`, `name`,
`primitive`, `image`, `config`, `secrets`, `schedule`, `replicas`, `cpu`,
`memory`, `extra_labels` — and nothing else. A `service_spec` also carries
`volumes`, `rollout_strategy`, `ingress_host`, `ingress_path`, `cluster_issuer`,
`progressive_delivery`, and `calls` / `called_by`, all of which the renderer turns
into manifest content.

Two plans that differ only in, say, `ingress_host` therefore render **different
manifests** but produce the **same `release_id`**.

## Why it matters

- The `release` label and the release record stop identifying the released
  state: "same id" does not imply "same manifests", which is the converse of the
  FEAT-069 guarantee and the basis of the GitOps "same id ⇒ empty diff" claim.
  A change in ingress, volumes, rollout strategy, progressive delivery, cluster
  issuer, or service calls is invisible to `sol releases`.
- Rollback cannot restore a boundary the record never captured (FEAT-066).

## Fix

Extend the canonical projection so it covers every resolved input that changes
the rendered manifests. Per workload, add the manifest-affecting facts:

- `volumes` (name, size/mount, whatever the toml volume shape carries)
- `rollout_strategy`
- `ingress_host` / `ingress_path`
- `cluster_issuer`
- `progressive_delivery`
- the resolved `calls` (peer domain, k8s name, namespace — sorted)

Keep provenance (`created_at`, commit, dirty, `deployment_id`) and
derived-only/presentation fields (`source_dir`, `environment` name, `mode`,
`requested_scope`, `output_directory`) out. `release_id`s change; that is
deliberate and fine pre-alpha.

The duplicate private projection in `Sol_cli_release` must move in the same
commit, or the record stops rederiving the plan's identity (there is a test that
pins them together — keep it).

## Acceptance criteria

- Two plans differing only in each of volumes / ingress host / rollout strategy /
  progressive delivery / cluster issuer / service calls produce different
  `release_id`s **and** different emitted bundle bytes — one test per field.
- `Sol_cli_release` records the same facts, so `derived_release_id` still
  round-trips and `validate ~name` still holds in both directions.
- The existing invariants still hold: workload order and map order are not
  semantic; provenance does not move the id; two identical scopes are one id.

## Completion notes (2026-09-14)

Fixed. The release identity now covers every resolved input the renderer turns
into manifest content.

### What changed

- `Sol_cli_release_id.workload` gained, per workload: `volumes` (name, mount
  path, size, access mode), `rollout` (the *effective* strategy, with canary
  steps included), `ingress_host`, `ingress_path`, `cluster_issuer`, and
  `calls` (env var, target domain, target k8s name, target namespace).
  `None` and `Some RollingUpdate` still map to the same `rolling_update`, so the
  default spelling is not a spurious identity change.
- Encoding: a canonical `table` encoder for the two set-like fields (sorted by
  the whole row), while the canary step sequence is encoded in order. This
  required `encoding_version` -> `sol-release-v2`, so every id changed
  deliberately; the known vector moved from `r-f4db347c7c7a2d1b` to
  `r-e1ba38330c2dc9cc`.
- **One projection, not two.** `Sol_cli_deployment_plan.release_workload_of_spec`
  is now exported and is the single definition; `Sol_cli_release.workload` is
  `Sol_cli_release_id.workload`, and the record builder calls the plan's
  projection. The hand-mirrored pair that let this drift is gone, so a record
  built from a plan rederives the plan's id *by construction* — the pinning test
  still passes but now has less to pin.
- The record JSON carries the new fields (`volumes`/`calls` as lists of string
  rows, sorted at the serializer), so `of_json`/`derived_release_id`/`validate`
  round-trip unchanged.

### Acceptance criteria

- One test per manifest-affecting field (`test_manifest_affecting_fields_change_identity`)
  proving each moves the id; volume and call order prove order-insensitive
  (`test_volume_and_call_order_is_not_semantic`), canary step order proves
  order-sensitive (`test_canary_step_order_is_semantic`).
- `test_release`'s `of_plan rederives the plan's identity` still passes, now
  because both sides call one projection.
- The pre-existing invariants are untouched: workload/map order not semantic,
  provenance does not move the id, identical resolved state in one environment
  is one release.

### Notes

- Every release id changes with `sol-release-v2`. Pre-alpha, no compatibility;
  old records are superseded rather than migrated.
- Deliberately *not* included: `source_dir` (build input, not released state),
  `k8s_name`/`namespace` (derived from domain/name/workspace), and `called_by`
  (the inverse of the workspace's `calls`, so it double-encodes).
- This unblocks FEAT-066 slice 2, which restores from this record.
