Use a supported AWS API path to inventory tagged load balancers

**Depends on:** None.

**Premise verified (2026-09-29):** At `3f662e7b`, traced the AWS load-balancer check through `Sol_cli_aws_absence.run`, provider observations, and destroy verification. The installed AWS CLI rejected the exact option shape with `Unknown options: --filters` before contacting AWS.

## Problem

`Sol_cli_aws_absence.cluster_tagged` runs `aws elbv2 describe-load-balancers --filters Name=tag:kubernetes.io/cluster/...`. That command has no `--filters` option. Every load-balancer observation therefore becomes `Unobservable`, even when credentials and the provider are healthy. The independent AWS absence check cannot reach a complete verified-absence verdict. The same invalid query also deprives ownership reconciliation of load-balancer reality.

## Recommended direction

List load balancers through supported AWS commands and identify target-owned ones through their tags, keeping an error in either step `Unobservable`. Preserve the existing target-attribution rule; do not infer ownership from a name substring alone.

## Acceptance criteria

- The generated AWS command sequence uses supported CLI/API parameters and checks cluster ownership tags for each relevant load balancer.
- A tagged load balancer yields `Present`; a successful empty/tag-negative inventory yields `Absent`; a failed list or tag read yields `Unobservable`.
- A focused command-level test rejects the old unsupported `--filters` invocation and covers the positive, negative, and error cases without a live account.
- Completion notes explain why an app-author demo and language-parity change are not applicable to this cloud safety correction.

## Completion (2026-09-29)

- **Premise re-verified** at `origin/main`: `Sol_cli_aws_absence.cluster_tagged` built one argv per resource class, and its `"load balancer"` arm passed `--filters` to `elbv2 describe-load-balancers`, which has no such option. Every load-balancer observation was therefore `Unobservable` regardless of account state.
- **Change.** `cluster_tagged` no longer derives the command from the class name — each caller supplies its argv, so a class cannot inherit another class's flags. The three tag-filtered EC2 classes (VPC, subnet, EBS volume) build theirs through a new `ec2_tagged_argv`, where `--filters` is supported; the load-balancer class lists `elbv2 describe-load-balancers --query 'LoadBalancers[].LoadBalancerArn'` and then resolves each returned ARN with `elbv2 describe-tags --resource-arns <arn>` against the `kubernetes.io/cluster/<name>` key, which is supported.
- `check` gained an optional `tagged_with : (string -> string list) option`: when present, `run` resolves every candidate through that second command and keeps the ones that carry the tag. An error in either step is `Unobservable` (including a deleted-since-listed ARN), an empty tag read is `Absent`, and a tagged ARN is `Present` — unknown ownership is never reported as absence. `checked_as` carries the human-readable sequence for the two-step check, since the report previously rendered only the first argv.
- **Tests.** New `cli/test/test_aws_absence.ml` drives the real `observations` path against a stub `aws` on `PATH` that records every argv and answers `describe-load-balancers`/`describe-tags` from a fixture. Four cases: the generated load-balancer call contains no `--filters` while the EC2 calls still do (this fails if the old invocation returns); a tagged ARN is `Present`; a tag-negative inventory is `Absent`; a failed tag read is `Unobservable` with the provider's reason. Mutation-checked both halves — restoring `--filters` fails the first case, and treating every listed ARN as tagged fails the third.
- Demo/example: not applicable — this is a language-neutral CLI/cloud safety correction to how Sol interrogates the provider; no app-author surface changes, and no example exercises AWS absence checks. Language parity: no impact (the TypeScript runtime does not run provider inventory).
