**Depends on:** None.

## Premise verified

`platform/cloud/modules/platform/main.tf` still gives Redpanda a 600-second Helm timeout. The patched alpha.7 AWS run and released alpha.7 GCP run ended at `module.platform.helm_release.redpanda` with `context deadline exceeded` after about 700 seconds. No current ticket owns this paired failure.

## Mechanism characterization and remaining limit

GCP's saved platform state records Redpanda revision 1 as `failed`, first deployed at 22:34:55 UTC, and eight other charts as `deployed`. Its allegedly concurrent API probe ended at 22:23:14, used the previous cluster endpoint, and ran during cloud provisioning. The `platform-failure` capture was from attempt 4. Those files cannot establish an API outage or missing Redpanda objects during attempt 5; INFRA-107 owns this evidence contamination.

Rendering the pinned chart `26.1.11` with attempt 5's saved Redpanda values shows non-optional `redpanda-users` Secret volumes in both the broker StatefulSet and post-install Job. The chart does not create that Secret. Neither provider harness supplies it, and the fresh cloud lifecycle creates the namespace then immediately runs Helm. FEAT-093 requires the operator to create the Secret manually before platform apply. With that input absent, the Kubernetes pods cannot mount their required volumes and Helm cannot converge. This is an established missing-prerequisite mechanism in the fresh-install procedure.

**Confirmed absent in both observed attempts (2026-10-04).** The engineer who ran them created no Kubernetes Secret in either cluster: AWS attempt 2 and GCP attempt 5 used only read-only `kubectl get` (namespaces, node inventories, service-account/role probes) with kubeconfigs from `aws eks update-kubeconfig` / `gcloud container clusters get-credentials`, and the only credential writes were `sol local secret set` against the local k3d workspace, never a cloud cluster. Nothing in the product creates it either: `platform/shared/components.json` only *references* it as the chart's `auth.sasl.secretRef`, and `docs/deployment/production-bootstrap.md` §1 and `examples/pluto/README.md` instruct the operator to create it by hand. The guide states the consequence verbatim — "when that Secret is absent the Redpanda release cannot start" — which is the observed outcome (revision 1 `failed`, then `context deadline exceeded`). The prerequisite was therefore absent in both runs by construction; the uncaptured pod/hook events would add the first failing condition, not change the mechanism.

## Remediation

The missing prerequisite is confirmed, so no further attribution step is needed before fixing the diagnosis. Fail clearly before the release waits on a missing Secret: the absence of an operator-supplied prerequisite is knowable before anything billable, so name it in preflight (and in the install's own error) instead of reporting `context deadline exceeded` after roughly 700 seconds, preserving FEAT-093's operator-owned credential and SASL_SSL contract. Reproduce the failure boundary in a fixture — render the pinned chart, apply the StatefulSet and Job without the Secret — rather than in a live cloud run. Supplying the documented operator input as part of a qualification attempt is INFRA-108, not this ticket. Do not choose a timeout increase from the stale reachability observations.

## Mechanism record (2026-10-04)

`internal/qualification/records/2026-10-04-cold-cluster-redpanda-credential-boundary.md`.
It renders the pinned chart `26.1.11` with the `common` + `durable` Redpanda layers
and reproduces the boundary on a local k3d fixture without a live cloud run. The
**earliest failing operation** is the broker pod's `users` volume mount:

```
MountVolume.SetUp failed for volume "users" : secret "redpanda-users" not found
```

`redpanda-0` never leaves `Init`, so the StatefulSet never reaches `readyReplicas=3`;
the post-install Job is blocked by the same volume, so it never completes; `helm --wait`
then returns `context deadline exceeded` at its 600-second timeout. Creating the Secret
clears the mount condition, so this is the mechanism that holds convergence back, not
merely a correlate of it. The record also states what it does not establish (no live
`Ready`; certificate issuance and capacity are outside the fixture).

## What landed (2026-10-04)

**The supported handoff.** `sol cloud apply` already creates the platform namespaces in
its prerequisite stage, then runs the privileged platform apply. A new preflight sits
between them: before the platform Helm apply, Sol reads the selected Redpanda component
layer's `auth.sasl.secretRef` from `platform/shared/components.json` and verifies that
Secret exists in the `redpanda` namespace. When it is absent the run stops with the
install's own error — the Secret name, why the chart needs it, the exact
`kubectl create secret generic …` command with a `<password>` placeholder, and "re-run
`sol cloud apply <target>` to resume" — instead of reporting a timeout after roughly 700
seconds. The bootstrap window is still removed on that exit (`Cleanup_succeeded`).

**The credential stays out of Sol.** Sol never reads the Secret's value; it only checks
existence. Nothing is passed on a command line, written to Terraform state, a release
artifact or a run log, and the fixture record uses a placeholder only. FEAT-093's
operator-owned SASL_SSL contract is unchanged.

**Files.** `cli/lib/cloud/sol_cli_cloud_lifecycle.{ml,mli}` (credential model, component
lookup, message), `cli/lib/cloud/sol_cli_cloud_apply.{ml,mli}` (`verify_platform_prerequisites`
dep, called after `await_crds`), `cli/lib/cloud/sol_cli_cloud_wiring.ml` (reads the
component layer and checks the Secret), `cli/test/inline/test_cloud_apply.ml`,
`internal/ci/lifecycle_fakes/kubectl` + `internal/ci/context/test_cloud_lifecycle_offline.sh`
(`PLATFORM_CREDENTIAL_ABSENT` scenario), `docs/deployment/production-bootstrap.md`,
`examples/pluto/README.md`, the mechanism record.
