severity: low
title: pipeline ls calls a worktree with unpushed commits when it is merely behind origin/main
source: found while resolving BUG-056 (2026-09-27) - its spent worktree was annotated "unpushed commits" while holding none
---

**Depends on:** None.

## The defect

`worktree_snapshot_of_entry` (`internal/tooling/soldev/lib/soldev_merge.ml`) decides
`ws_unpushed` by comparing commit **shas**, not by asking whether there is anything
to push:

```ocaml
let unpushed =
  if upstream_rc = 0
  then (* local_sha <> remote_sha *) ...
  else (* local_sha <> origin/main's sha *) ...
```

So a worktree whose HEAD differs from the ref is annotated "unpushed commits" —
which is also true of a worktree that is simply *behind* main, or whose commits
landed by squash and are therefore not reachable by sha. A worktree created from
an older `origin/main` and never committed to reads as holding unreviewed work,
and `pipeline ls` marks it as needing attention:

```text
$ soldev pipeline ls
  BUG-056  ...  actionable (unpushed commits @ /home/logan/Code/sol-cloud/sol-BUG-056-up-resolved-config)

$ git -C /home/logan/Code/sol-cloud/sol-BUG-056-up-resolved-config rev-list --count origin/main..HEAD
0
```

That worktree held nothing: the branch was never pushed and no PR ever existed for
it. The annotation is what a worker reads to decide whether a ticket has work in
flight, so a false positive either sends them looking for work that is not there
or gets the worktree ignored when it does matter.

## Remediation

Ask git whether there are commits to push: `git rev-list --count <ref>..HEAD` for
the branch's upstream (`origin/<branch>`) when it has one, and for `origin/main`
when it does not. A count of zero means nothing is unpushed, whatever the shas
are. Both current cases are wrong in the same direction, so both change:

- behind `origin/main`, no upstream → today "unpushed"; must be clean;
- behind its upstream → today "unpushed"; must be clean.

Keep the conservative direction when git cannot answer at all (a missing ref, a
shallow clone): report "unpushed" rather than silently clean, because the
annotation's whole purpose is to warn about work that might be lost. Squash-merged
commits will still read as unpushed (they are not reachable from `main`); that is
the same signal a reader would get from `git log main..HEAD`, so change it only if
`git cherry`-style patch comparison is ever warranted.

## Acceptance criteria

- Test, against a real repository built in a temp dir: a checkout *behind*
  `origin/main` with no upstream is not unpushed; one *ahead* of it is; a checkout
  *behind* its own upstream is not unpushed; one ahead of its upstream is; and a
  ref git cannot resolve stays reported as unpushed.
- `pipeline ls` on a worktree that is behind `origin/main` and clean does not
  annotate it.
- No change to what `dirty` means, and no change to any other `ls` annotation.
- Demo/example: not applicable (internal tooling). Language parity: no impact.

## Completion notes

**Premise re-verified (2026-09-27, `origin/main` `ed7a313a`).** `unpushed` compared
`local_sha` with the upstream's (or `origin/main`'s) sha, exactly as the evidence
above records. The case that exposed it is real and was reproduced again here: a
worktree kept from an older `origin/main`, clean and **0 commits ahead**, was
annotated `unpushed commits @ …` -- and it was that annotation, not the ticket,
that made a spent worktree look like it held unreviewed work.

**What landed.** `worktree_snapshot_of_entry` now asks git whether there is
anything to push: `git rev-list --count <ref>..HEAD` against `origin/<branch>`
when the branch has an upstream, and against `origin/main` when it does not. A
count of zero is clean whatever the shas are. When git cannot answer (a ref that
does not resolve, a shallow clone) the count is unreadable and the annotation
stays in the noisy direction -- `true` -- because the whole purpose of the flag is
to warn about work that might be lost; the previous code reached the same place by
comparing against an empty sha. Squash-merged commits still read as unpushed
(they are not reachable from `main`), which is the same signal `git log
main..HEAD` gives a reader; `git cherry`-style patch comparison would be needed to
go further and is deliberately not attempted.

**Evidence.** The acceptance criterion, end to end on the case that misled me --
a clean worktree 5 commits behind `origin/main`, on a branch named for a ticket:

```text
$ git -C sol-behind-probe rev-list --count origin/main..HEAD
0
$ git -C sol-behind-probe status --porcelain          # (empty)
$ soldev pipeline ls --all | grep BUG-056
  BUG-056  bug  medium  depends on: none  -  `sol up` builds its plan without …
```

No `(unpushed commits @ …)`, where before the fix the same row carried it.

**Tests.** `internal/tooling/soldev/test/test_merge.ml` gains a case against a
**real repository** built in a temp dir, because the defect was in what git was
asked and a pure-function test would not have caught a query that fails (a failed
`rev-list` reads as conservative "unpushed", which is the bug reappearing as
noise). Seven assertions: at `origin/main` is clean; ahead of it is unpushed;
**behind** it is clean; equal to its upstream is clean; ahead of its upstream is
unpushed; **behind** its upstream is clean; an unresolvable ref stays unpushed.
**Checked non-vacuously**: with the previous sha comparison restored, the test
fails at `behind origin/main is not unpushed` -- the regression -- and passes with
the fix. The whole CLI and soldev suites, `dune build`, `check_ocamlformat.sh
--all` and the `internal/ci` guard suite pass.

**Behaviour changes.** A worktree that is behind `origin/main` or behind its own
upstream no longer reads as holding unpushed commits; `dirty` is untouched, and
the listing's text (`@ if wt.ws_unpushed then ["unpushed commits"]`) is unchanged,
so this is only the predicate becoming correct.

**Demo/example: not applicable** (internal tooling; no app-author surface).
**Language parity: no impact.**
