The consumer-group-removal guard must fail closed on unreadable deploy state and describe the real hazard

**Depends on:** None.

**Finding:** FND-0038 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-23** against `origin/main @ f3e9480b` while filing (see the finding for the command/probe and observed output).

## Problem

`load_deployed_groups` returns `[]` on any read failure, so the guard in `sol deploy`/`sol up` passes silently when the cluster misbehaves; a failed `save_deployed_groups` is only a warning. The refusal text says a re-added group resumes from the *latest* offset; every Sol consumer uses `offset_reset = Earliest`.

## Remediation

Distinguish NotFound (legitimately empty) from other failures, which stop the deploy with the reason; make a failed state write fail the outcome or be recorded as unknown; correct the message (reprocessing from committed/earliest offset).

## Acceptance criteria

- Fake kubectl failing the state read makes `check_consumer_group_changes` stop the deploy with the read error; NotFound still passes.
- Message text matches `offset_reset = Earliest` semantics.
- Review round 1 (non-blocking, taken): the failed-write error now says the workloads
  were applied and the release recorded, what the failure breaks (the next deploy's
  removal check), and how to recover.
- Demo/example: not applicable — state in completion notes.

## Completion notes

- `Sol_cli_deployment_state.load_deployed_groups` returns a result. Only kubectl's
  `NotFound` (no record yet, i.e. a first deploy) is `Ok []`; any other failure is an
  `Error` naming the ConfigMap.
- One shared guard, `check_removed_groups`, replaces the two copies in `cmd_deploy.ml`
  and `cmd_up.ml`. An unreadable record refuses the deploy, unless
  `--confirm-group-change` was passed, which already accepts group changes; in that
  case it warns that the check could not run. A removed group is refused with a
  corrected message: while a group is absent nothing consumes its messages; re-added,
  it resumes from its committed offset while Kafka retains it, otherwise from the
  **earliest** retained offset, reprocessing the log (all Sol consumers use
  `offset_reset = Earliest`). The old text said "latest ... silently skipping".
- `save_deployed_groups`/`record_outcome` return a result, and a failed write is now an
  error. Both commands write the record inside `finish_deployment`'s `record_release`,
  so a failure is reported before "Done", in line with DEC-037's "record before
  reporting success".
- Tests: `test_deployment_state.ml` is rewritten on a fake `kubectl` (it used to run the
  real one against the local-cluster context, which on a developer machine with
  `k3d-sol-local` up would have written a ConfigMap). It covers present, missing,
  unreadable, a failed write, the guard (unreadable refuses, confirm proceeds, removal
  refused with the corrected hazard, stable and first-deploy pass), and the helpers. In
  `test_deployment_phases.ml`, the real-kubectl "Applied does not raise" case is removed
  (superseded) and the no-op cases assert `Ok`.
- Mutation checks (`audits/README.md`), builds rc=0: an unreadable read collapsed to
  `Ok []` fails "unreadable is an error" and "refuses on unreadable record"; a failed
  write turned into `Ok ()` fails "failed write is an error".
- Demo/example: not applicable (CLI guard behaviour; `--confirm-group-change` usage is
  unchanged).
- Language parity: no language-parity impact (CLI-only; the guard applies to every
  workload's consumer groups whatever its language).
