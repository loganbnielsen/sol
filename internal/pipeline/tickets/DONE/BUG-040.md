`sol secret set/delete/list` must fail on an unreadable Secret instead of treating it as absent

**Depends on:** None.

**Finding:** FND-0031 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-23** against `origin/main @ f3e9480b` while filing (see the finding for the command/probe and observed output).

## Problem

`Sol_cli_secret.get_named_secret_json` maps every kubectl failure to `Ok None` ("absent"); `list_workload_secrets`, `list_live_workloads` and `list` map read failures to `[]`. With reads failing, `set` applies `sol-secrets` without its existing `data` (client-side apply then drops previously applied keys), patches no per-workload Secret, restarts nothing, and reports success; `delete` sends no patch and reports deletion. Reproduced with a fake kubectl — see FND-0031.

## Remediation

Make the Secret read tri-state (`Present | Absent | Unreadable reason`), with only kubectl NotFound mapping to `Absent`. `set`/`delete` fail on `Unreadable`; the list reads return `Error`; `restart_and_verify` fails when it cannot list workloads.

## Acceptance criteria

- With every kubectl read failing (fake kubectl, as in FND-0031), `set`, `delete` and `list` each return `Error` naming the failed read, and `set` issues no `apply`.
- A NotFound Secret still lets `set` create it (first-time path unchanged).
- `restart_and_verify` returns `Error` when the workload list cannot be read.
- Unit tests use an injected runner / fake kubectl; no cluster needed.
- Demo/example: not applicable (CLI internals, no author-facing change) — state in completion notes.

## Completion notes

- `get_named_secret_json` returns `Ok (Some json)`, returns `Ok None` only when kubectl's
  stderr says `NotFound`, and returns `Error` for everything else (connection failure,
  Forbidden, timeout, spawn failure, unparseable JSON).
- `list_workload_secrets` and `list_live_workloads` return `result`s through a shared
  `listed_names`, so a failed listing is never an empty one. The one tolerated failure is the
  Rollout kind not being served (CRD absent), which the old comment already treated as an
  empty set; it matches the stderr wording `sol_cli_rollback.ml` uses.
- **Every read happens before the first write** (review round 1). `set` and `delete` first
  take one `rotation` per namespace, for all namespaces: `sol-secrets` data, each
  per-workload Secret's data, and the live Deployments/Rollouts. Only then do they apply or
  patch and restart. A read failure anywhere leaves nothing half-rotated. `list` and the
  restart propagate errors, so a rotation over an unreadable workload list is never
  reported as verified.
- Test `cli/sol/test/test_secret_reads.ml`, fake kubectl modes: unreachable, NotFound,
  present, no Rollout CRD, workload-Secret listing Forbidden, Deployment listing Forbidden.
  Asserted: failed reads give `Error`, and nothing is applied, patched or restarted, even
  when the failing read comes after `sol-secrets` was read successfully. An absent Secret
  is still created, existing keys are kept, and a cluster without Rollouts still rotates.
- Mutation checks (`audits/README.md`), all builds rc=0:
  - dropping the `NotFound` guard (any non-zero `get` → absent) fails `set` and `list`;
  - a failed Deployment/Rollout listing → `Ok []` fails "Deployment listing fails";
  - a failed workload-Secret listing → `Ok []` fails "workload Secret listing fails".
  An earlier mutant (`Error _ -> Ok None` ahead of the arms) was rejected by the compiler
  (redundant case), so it was invalid and is not counted.
- Demo/example: not applicable (CLI internals; `sol secret` usage unchanged).
- Language parity: no language-parity impact (CLI-only).
