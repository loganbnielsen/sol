**Depends on:** DEC-051.

**Related:** `DEC-052` (the observation half), `DEC-047` (the deployment-config key
table, whose provider-block row this re-expresses), `REFAC-098` (`sol_keys` — the
provider-block keys Sol consumes itself), `REFAC-092`/`provider_dispatch_allowlist.txt`
(the provider-dispatch baseline), `FND-0033`/`BUG-042` (unknown keys are errors, for
`sol.toml`), `DEC-043` § *Design constraints* 2 (derivation must never invent an
authority grant). `DEC-051`'s non-goal applies unchanged: no universal
AWS/GCP/Azure/DO configuration vocabulary.

## Question

Driver-specific configuration is validated against **three lists that must agree and
nothing checks that they do**:

| List | Where | What it decides |
|---|---|---|
| `owned_legacy_keys` | `cli/lib/base/sol_cli_provider.ml:53-63` | a flat key that belongs in a driver block, so the parser can reject it with a message naming the block |
| `sol_keys` | `sol_cli_provider_capabilities.ml:58`, aws `:186-192`, gcp `:283` | which driver-block keys Sol consumes itself instead of passing through as `-var`s (`REFAC-098`) |
| the parser's flat-key handling | `cli/lib/workspace/sol_cli_config.ml:424-425`, `:871`, `:920` | where a key is accepted, and what "unsupported provider %S" means |

The failure direction is specific and silent-in-one-direction: a key added to a driver
block and not to `sol_keys` is passed through as a `-var` (Terraform rejects it, or worse
accepts a variable no root declares); a key added to `owned_legacy_keys` and nowhere else
is rejected as unknown. Neither disagreement is a test failure today.

**Where should the driver-owned key set live so there is exactly one authoritative
declaration, and how do the schema and the driver-capability representation avoid
becoming independently maintained lists?**

## Direction (proposed)

```text
common Sol target contract          (the common schema; unchanged keys, one owner)
        +
driver-owned configuration          (one declaration per driver: name -> what Sol does with it)
        ↓
driver capabilities                 (the behaviour record, reading that declaration)
        ↓
common Sol lifecycle                (unchanged)
        ↓
observed substrate contract         (DEC-052)
```

Rules:

1. **The common environment schema owns the common keys.** Target keys,
   environment keys and app-shape keys stay where `DEC-047` put them; this decision does
   not add any.
2. **Each driver owns and validates only its own namespace** — the keys inside its
   block — and inherits nothing from another driver.
3. **Unknown keys remain errors**, in both manifests (`sol.yml` today,
   `sol.toml` since `BUG-042`), with the error naming the block the key belongs in.
4. **One declaration, read by both consumers**, or a test that fails when they diverge.
   Which of the two is chosen is this decision's subject; the unacceptable outcome is
   two lists that can drift.

### The dependency direction constrains the answer

`DEC-051`'s investigation and the code layout agree here: `cli/lib/` is a DAG,
`base ← kube ← workspace ← cloud ← deploy`, and the config parser
(`cli/lib/workspace/sol_cli_config.ml`) already reads `Sol_cli_provider` for exactly
this purpose. So a declaration that both the parser and the capability record read must
sit **at or below `base`** — the capability record (cloud tier) can read it, the parser
can read it, and no cycle is created. A declaration living only in the capability record
would make the parser depend on the cloud tier.

## Options

| | Shape | Why / cost | Verdict |
|---|---|---|---|
| **A** | **One declaration per driver in `Sol_cli_provider` (base)**, listing its owned keys and what Sol does with each (consumed here / passed through / identity). The parser's rejection set and the capability record's `sol_keys` are both *derived* from it. | Exactly one list; the dependency direction is already satisfied; adding a driver key is one edit and cannot be half-done. Cost: one new type in the base tier and a small refactor of `owned_legacy_keys`. | **Recommended** |
| **B** | Keep the lists separate and add a test asserting they agree. | Cheapest, and it does catch drift — but it moves the knowledge into a test rather than the declaration, and the next contributor learns the contract from a failure message. | Acceptable minimum if A's refactor is deferred |
| **C** | Declare the keys in a data file (TOML/JSON) and generate code from it. | A build step and a second source of truth for the *generator*; the tree has no such generator today and the sets are tiny. | Reject |
| **D** | One universal driver-block vocabulary (`database`, `kafka`, `identity`, …) valid for every driver. | Explicit `DEC-051` non-goal: it would make a Hetzner target accept AWS-shaped words, and the values would be assertions rather than configuration (`DEC-052`). | Reject |

## Recommendation

**A**, keeping the per-key granularity small: the declaration answers only *who owns this
key* and *what Sol does with it*, not what it means. Two properties make it worth the
refactor:

- **The two consumers stay honest by construction.** `REFAC-098` added `sol_keys`
  because a driver-block key Sol consumes itself must not also be handed to Terraform;
  `owned_legacy_keys` exists so a *flat* key can be rejected with a useful message. Both
  are views of one fact — "this key is mine, and here is how I use it" — and the current
  split is an artefact of which module needed it first.
- **It keeps the never-derive rule visible.** `DEC-043` § *Design constraints* 2 forbids
  deriving an authority grant. A single declaration makes the authority-bearing keys
  (`provisioner_role_arn`, `cluster_access_role_arn`, `deploy_role_arn`,
  `operator_role_arn`, `provisioner_impersonator`) legible as a set, rather than
  discoverable by reading a passthrough.

## Affected invariants

1. **Unknown keys are errors** (`FND-0033`/`BUG-042`, `DEC-047`: "a key set at a layer it
   isn't allowed in is a parse error naming the layers where it is allowed"). Preserved,
   and this decision is what makes the *set* of allowed keys single-sourced.
2. **`DEC-047`'s key table** — the row "provider blocks (`aws:`, `gcp:`) … deep-merge
   per key" is re-expressed per driver; no merge behaviour changes.
3. **The never-derive rule** (`DEC-043`). The declaration may say "Sol consumes this
   key"; it must not invent a value for an authority or accountability key. A key that
   is absent stays absent.
4. **`REFAC-092` dispatch baseline** (`provider_dispatch_allowlist.txt`, "entries may
   only go down"). The refactor must not add an allowlist entry; if it does, a dispatch
   moved into the wrong layer.
5. **`DEC-051`'s non-goal.** No universal vocabulary, and no key that asserts a
   discoverable substrate fact (`DEC-052`).
6. **`DEC-022` language parity:** none — configuration is shared by both application
   languages, and nothing app-facing changes.

## Smallest migration

1. **Declare** the owned-key set (name + disposition) once per driver in
   `Sol_cli_provider`, starting from today's `owned_legacy_keys` and `sol_keys` merged.
2. **Derive** the parser's flat-key rejection set and the capability record's
   `sol_keys` from that declaration; delete the duplicates.
3. **Test the equality in one place** (the config tests already cover the flat-key
   rejection path) so a key that becomes driver-owned is added in exactly one file.
4. **No YAML change, no user-visible change, no data migration.** Every existing target
   keeps parsing identically; the parse-error *message* is the only visible difference,
   and it should be checked in the same pass (`DEC-047` requires it to name the block).

## Out of scope (non-goals)

- **Do not implement a driver for DigitalOcean, Hetzner, Civo or Azure.**
- **Do not widen the accepted scope set** or add keys to the common schema.
- **Do not decide when a driver has a root, or the `sol cloud *` refusal** — `DEC-051`.
- **Do not decide which substrate facts are observable** — `DEC-052`.

## Acceptance criteria

- One authoritative declaration per driver of the keys it owns and what Sol does with
  each, with both consumers derived from it.
- A key added to a driver block is added in exactly one place, and a test fails if a
  consumer's view diverges.
- Unknown keys remain parse errors naming the block; existing targets parse unchanged.
- No universal configuration vocabulary and no assertion-shaped key is introduced.
- **No language-parity impact** (`DEC-022`) — stated in the implementing ticket's
  completion notes.

## Status

**Decided 2026-10-01 by the operator: Option A.** Each driver has one authoritative
declaration in `Sol_cli_provider` (base tier) of the keys it owns and what Sol does with
each. The parser's flat-key rejection set (`owned_legacy_keys`) and the capability
record's `sol_keys` are both **derived** from it. Disagreement is made structurally
impossible rather than tested for, so option B's agreement test is not the fallback. The
implementation is a separate unit; `DEC-051` (the driver model this is keyed by) is
decided.

## Implementation (2026-10-02)

On branch `DEC-053/driver-key-declaration`, stacked on DEC-051.

- **One declaration in the base tier.**
  `Sol_cli_provider` now exposes `type key_disposition = Sol_consumes |
  Passed_to_terraform`, `type owned_key = { key : string; disposition :
  key_disposition }`, `owned_keys : t -> owned_key list`, and derives
  `sol_keys : t -> string list` (the `Sol_consumes` subset). `owned_legacy_key`
  is derived from the same declaration — it is the driver that owns a flat key,
  whichever its disposition.
- **The duplicate list is gone.** `Sol_cli_provider_capabilities.t`'s
  `sol_keys` field is removed, so a driver cannot carry a second, divergent
  view; `Sol_cli_terraform_vars.of_config` reads
  `Sol_cli_provider.sol_keys target.provider`. Adding a driver key is one edit
  in one file.
- **The parser is unchanged** — it already read `owned_legacy_key`, whose
  signature and meaning are unchanged.
- **The static guard reads the declaration, not a literal.** 
  `internal/ci/check_gcloud_interface.sh` extracted the GCP arm
  (`owned_keys`) and checks `provisioner_impersonator` is declared there.

**Verification**

- `dune build` clean; `dune test cli --force` all pass, with three new cases in
  `test_config.ml`: the declaration owns each key exactly once (aws/gcp/byo),
  `sol_keys` is exactly the `Sol_consumes` subset for every driver, and a flat
  key resolves to its owning driver.
- `internal/ci/run_fast_checks.sh` passes (0/7 always, 0/97 static), including
  `check_gcloud_interface.sh` and its mutation suite.
- Live: `sol check` and `sol plan prod/aws/us-east-1` succeed in `examples/pluto`,
  and a flat `deploy_role_arn` still fails with
  `target key "deploy_role_arn" belongs to the aws provider: declare it as
  \`aws.deploy_role_arn\` inside the target block` — the block-naming message
  DEC-047 requires, unchanged.

**Demo/example coverage:** Not applicable — a parser/capability refactor with no
app-author-visible change beyond the identical error message.

**TypeScript-parity note (DEC-022):** No language-parity impact — driver
configuration is shared deployment configuration, and nothing app-facing
changes.
