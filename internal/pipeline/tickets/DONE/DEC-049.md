**Depends on:** None.

## Context

Sol has no release artifact today. Every `sol` binary assumes it runs from a Sol source checkout. `Sol_cli_cmd_new.infer_sol_home` walks up from `/proc/self/exe` to find one, and four consumers read Sol-owned assets from it:

- `cli/bin/cmd_migrate.ml` builds the migration-runner image from the checkout (`push_runner_image`, and the apply path);
- `cli/bin/cmd_cloud_tf.ml` reads the Terraform roots `platform/cloud/<provider>/{cluster,platform}`;
- `cli/lib/local/sol_cli_dev_observability.ml` reads Grafana dashboards and the Alloy template from `platform/shared/observability/`;
- `cli/lib/local/sol_cli_platform_component.ml` reads `platform/shared/components.json`, the Helm values for `sol local infra`.

`rg -n 'infer_sol_home' cli --glob '!cli/test/**'` (2026-09-26) lists exactly these, plus the definition. The runner Dockerfile also pins support libraries to `#main`, so even a source build can produce a runner that doesn't match the CLI beside it.

**Correction (FEAT-101, 2026-09-26).** "Sol has no release artifact today" is wrong. `.github/workflows/release.yml` published `v0.1.0-alpha.1`…`alpha.6` (June 2026; `gh release list`) as `bin/sol` plus the `framework/` source, with no `platform/` tree. So those releases could not run `sol cloud`, `sol local infra` or `sol migrate`, which confirms the diagnosis rather than changing it. The claim came from searching CLI code only, not `.github/`. FEAT-101 replaces that workflow.

## Decision

1. **The distinction is asset resolution, not command behaviour.** Commands have no release-versus-source semantics. A source checkout and an installed release are two distribution forms of one product.
2. **`Sol_cli_platform_assets` owns asset resolution.** Consumers ask it for assets and never call checkout discovery themselves. Discovery of Sol's source tree belongs to the resolver alone, enforced by a CI guard.
3. **Resolution order:** an explicit `SOL_HOME`, then the installed versioned bundle next to the binary, then source-checkout discovery. An explicit `SOL_HOME` that isn't a valid asset root is an error. It never falls through to another source.
4. **Both forms expose the same `platform/` tree,** so consumers join paths onto a root and don't know which form they're in.
5. **Released assets are bundled, not fetched.** No dynamic fetching, and no first-run extraction cache. Installed layout: the binary at `<prefix>/bin/sol`, assets at `<prefix>/share/sol/<version>/platform/`.
6. **Version alignment.** Every Sol-owned asset a released `sol` uses belongs to that release: its platform tree and its migration runner. The runner for release `N` is a published image built from the same commit and dependency snapshot as binary `N`. An installed CLI selects the runner matching itself, and never `main`, `latest`, or anything that floats independently of the CLI. A source build keeps building the runner from its checkout.
7. **Proof:** CI builds the actual release artifact, installs it into a prefix outside the repository in an environment that structurally cannot see the checkout, with `SOL_HOME` absent, and exercises representative consumers there.

**Invariant:** a released Sol installation is self-contained except for its documented external runtime dependencies, and every Sol-owned asset it consumes is version-aligned with that release.

## Consequences

- REFAC-114: the resolver refactor and the ownership guard, with source behaviour preserved.
- FEAT-101 (reshaped): the release bundle, the versioned runner image, installed-layout resolution and precedence tests, and the installed-layout smoke.
- BUG-059: the runner's `#main` support-library pins. Its fix depends on where the checkout's support-library revisions are recorded, which is an open question (see the ticket).

## Non-goals

Separate release and local command implementations; runtime asset downloads; extraction caches.

## Record

Decided by the operator on 2026-09-26, adopting the asset-resolution framing and the release-bundle model above. Recorded without a further approval round, at the operator's direction.
