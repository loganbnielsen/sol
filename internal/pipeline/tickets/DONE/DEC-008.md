Decide the tenancy *mechanism* for Sol-hosted infrastructure.

**Question:** When Sol operates a customer's hosted environment (per DEC-004, the first-class product path), does each customer get infrastructure inside a separate cloud account Sol provisions and controls (e.g. one AWS sub-account per customer via AWS Organizations), or does Sol run one (or a few) of its own cloud accounts with per-customer isolation enforced at the cluster/VPC/namespace level?

**Context:** DEC-002 already decided hosted runtime tenancy is single-tenant per customer ("isolated runtime substrate rather than sharing a cluster with unrelated customers"), and the Ownership Matrix in `PRODUCT_ARCHITECTURE.md` marks Cluster/Registry/Kafka/Postgres/Secrets/Domains as Sol-owned in hosted mode — but neither document says which cloud account(s) that infrastructure actually lives in, or how blast radius/billing/IAM boundaries are drawn between customers. This is the highest-leverage unresolved question for actually building the hosted factory floor: it determines the security review scope, the cost floor per customer (a dedicated EKS control plane alone is a real fixed cost, in tension with a "cheap for small projects" pitch), and what a hosted UI (DEC-009) needs to authenticate against and display.

**Options:**
1. Per-customer AWS sub-account (AWS Organizations), Sol's control plane assumes a role into each. Strongest isolation and blast-radius containment; highest fixed cost per customer and highest account-provisioning complexity.
2. Sol-owned account(s) with per-customer isolation at the cluster level (one EKS cluster per customer, shared AWS account). Matches DEC-002's "isolated substrate" language most literally; lower provisioning complexity than per-account, still a real per-customer cluster cost floor.
3. Sol-owned account(s) with per-customer isolation below the cluster level (shared cluster, namespace/NetworkPolicy/quota isolation) — lowest cost floor, closest to real multi-tenant PaaS economics for small workloads, but contradicts DEC-002 as written and reopens the isolation/noisy-neighbor concerns DEC-002 explicitly deferred.

**Decision criteria:**
- Consistency with DEC-002 (or an explicit, justified revision of it).
- Cost floor per customer versus the "cheap to start" positioning implied by competing with Vercel-style platforms.
- Security/blast-radius review burden Sol takes on by holding customer infrastructure.
- What the hosted UI (DEC-009) needs to authenticate against and display.

**Acceptance criteria:**
- A written decision names the tenancy mechanism and explicitly reconciles it with DEC-002.
- The decision states the expected minimum per-customer infrastructure cost.
- Follow-up implementation tickets are identified for the control-plane/account-provisioning work this implies.

**Decision:**

Hosted infrastructure lives in a single Sol-owned AWS account, with each
customer getting an isolated VPC (and, within it, its own cluster —
consistent with DEC-002's per-customer substrate). Sol's control plane
provisions and operates every customer's VPC from that one account rather
than vending a separate AWS account per customer.

This is chosen over per-customer AWS accounts because account-vending adds
real onboarding latency (account creation, consolidated billing setup) that
works against the "instant" hosted experience (DEC-005), and adds ongoing
AWS Organizations management overhead Sol doesn't need yet at this customer
count. It is explicitly accepted as a *weaker* isolation boundary than
per-account: a compromise or bug in Sol's own control-plane IAM has a wider
blast radius than it would with account-level isolation, because VPC
boundaries stop network traffic, not a control plane's own API calls.

Hosted provisioning must go through the same `platform/infra/aws` Terraform
module used by self-hosted `sol cloud apply`, with **per-customer Terraform
state** (not one shared state file), even though the account is shared. This
is required for two reasons: it bounds blast radius for `terraform apply`
mistakes to one customer's resources, and it keeps the "export to Terraform
and self-host" escape hatch (Exported Self-Managed lane, DEC-004) a literal
state handoff rather than a translation project.

**Implications:**

- The control-plane component that provisions hosted customers needs
  per-customer IAM scoping (resource-tag or VPC-scoped policies) even though
  it operates from one account — not just "the control plane has broad
  account access."
- Per-customer Terraform state (e.g. one S3 state key per customer, or
  Terraform Cloud workspaces per customer) is a hosted-provisioning
  requirement, not an optional nicety — track this as a real implementation
  ticket when hosted provisioning is built, not an afterthought.
- Per-account isolation is deferred, not rejected outright: revisit once
  Sol courts customers with compliance requirements (SOC 2/HIPAA-adjacent)
  that specifically require account-level tenant isolation — that is a
  distinct future decision, not implied by this one.
- AWS per-region service quotas (VPCs per account, EIPs, NAT gateways, etc.)
  become a real operational concern as hosted customer count grows in one
  account; this needs monitoring, not architecture, until it's a genuine
  scaling wall.
