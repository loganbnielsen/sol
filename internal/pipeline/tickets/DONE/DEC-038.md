## The question

`sol deploy` ends by telling the operator `Run 'sol status' to check pod health.`
`sol status` renders unhealthy pods **with their last events**. No identity the
production profile provides can perform that read: the deploy identity is refused
`events` (and `pods/portforward`), `cluster-access` cannot read pods at all, and the
declared operator identity cannot authenticate — `operator_role_arn` appears in
exactly one place in the tree, an output description, and **no access entry or RBAC
is ever created for it**.

Two things are wrong at once, and they are separable: a missing capability, and a
capability whose absence is invisible.

## Decision (2026-09-20)

### 1. The identity boundary

| Identity | Owns |
|---|---|
| provisioner | infrastructure mutation |
| publisher | artifact publication |
| deploy | application/release mutation |
| **operator** | **production observation and diagnosis** |

Diagnosis is not a side effect of deploying. It belongs to the operator identity,
which is why the fix is to make `operator_role_arn` real rather than to hand the
deploy identity more read access.

### 2. `operator_role_arn` becomes an end-to-end identity

- An EKS access entry for `operator_role_arn` with `kubernetes_groups =
  ["sol:operators"]` and **no access policies** — the same shape as the deploy and
  provisioner entries, where the group is the identity's Kubernetes-side name.
- Kubernetes authorization from a ClusterRole, bound **per application namespace at
  runtime** (the namespaces are created dynamically, so a Terraform-time binding
  cannot express them, and a ClusterRoleBinding would read into platform
  namespaces).

### 3. The diagnostic surface, derived from the evidence the commands consume

Not a generic view/admin policy. Every entry below is a read an existing read-only
Sol command actually performs:

| API group | Resource | Verbs | Consumed by |
|---|---|---|---|
| core | `pods` | `get`, `list` | `sol status`, rollout diagnosis (pod phase, container statuses, restarts) |
| core | `pods/log` | `get` | `sol logs` — the workload's own output |
| core | `services` | `get`, `list` | `sol status` (service addressing) |
| core | `events` | `get`, `list` | rollout diagnosis — *the explanation* that is missing today |
| `apps` | `deployments` | `get`, `list` | `sol status` (live image, rollout state) |
| `batch` | `cronjobs` | `get`, `list` | `sol status` for a function primitive |
| core (cluster-scoped) | `namespaces` | `get`, `list` | `sol status` (does the namespace exist) |

`get` and `list` only. Nothing in the read-only surface watches, so `watch` is not
granted. No wildcards, and no mutating verb anywhere.

### 4. Deliberately excluded

- **`pods/portforward`, `pods/exec`.** Interactive debugging, not diagnosis. They
  are excluded *even though port-forward would have made this very investigation
  easier* — that is not a contract. If a future Sol command genuinely requires them,
  it must justify them on its own.
- **`secrets`.** Reading application secrets is an inspection capability, not part
  of explaining an unhealthy workload. The deploy identity holds it because it
  manages runtime secrets; the operator does not need it to diagnose.
- **Anything cluster-wide for the namespaced resources.** Only `namespaces` is
  granted cluster-scoped, and only `get`/`list`, because `sol status` asks whether a
  namespace exists.

### 5. The partial-evidence rule (independent of the grants)

**A read Sol could not perform must never be represented as an absence of
evidence.** Two states must stay distinguishable:

| State | Meaning |
|---|---|
| queried successfully, zero events | *nothing happened* |
| unavailable (authorization, transport, error) | *I could not look* |

`fetch_namespace_events` currently collapses every failure into `[]`, so
`sol status` prints an unhealthy pod with no events and no indication the evidence
was unobtainable. That is the same silent-degradation shape as FND-0014's pointer.

**The status contract is explicit partial evidence, not a hard failure.** The
existing contract is already best-effort reporting — `sol status` prints what it can
about a namespace (`ns_exists`, pod and deployment reads each tolerate their own
failure) — and making one denied part fatal would deny the operator the parts that
*did* work, at the moment they most need them. So:

- the diagnosis stays useful;
- the unreadable part is **named** as unreadable, with the reason;
- and Sol never presents a part it could not obtain as though it had.

## Acceptance criteria

1. An operator holding only the profile's identities runs `sol status` against an
   unhealthy workload and receives the pod state **and** the events explaining it.
2. The same identity is **unable to mutate**: no create/update/patch/delete on any
   resource, in any namespace, and no `pods/portforward` or `pods/exec`.
3. A denied events read is reported as unavailable, with `events` named, and is
   never rendered as an empty event list.
4. A successful read with zero events is still reported as zero — the two states
   are distinguishable in the output.
5. Regression coverage for (2), (3) and (4), which are testable offline.
