Decide what a release is, where it is recorded, and what `sol rollback` restores.

## Decision

> **A release is an immutable record of requested scope, resolved workloads, source provenance, artifact digests, configuration references and migration state. Rollback restores that recorded release boundary; native rollback mechanisms are merely implementation strategies and must not weaken the restoration guarantee.**

The release record is authoritative. `kubectl rollout undo` and Argo Rollouts are **execution mechanisms**, not alternate sources of truth — and that distinction has teeth: rolling a Deployment back to a previous revision does not restore a ConfigMap whose contents changed in place, because the pod template still references `configMapRef` and the referenced object is whatever it is now.

## The release record

```text
release_id          sortable and unique (aligned with the existing run-id shape)
git_commit          provenance, not identity
git_dirty           whether the tree was clean
requested_scope     the semantic boundary — what the user asked for
resolved_workloads  exact historical membership: name + image digest (`@sha256:`)
configuration       rendered configuration and secret *references*, never material
migrations          applied migration ids / watermark, and each one's disposition
created_at
```

A Git revision is not enough to say what ran: two deploys from one commit can differ by configuration, secret references, replica counts, generated manifests, or a rebuilt artifact. So the commit is recorded as provenance and the **digest** identifies the bytes. `git_dirty` is not bookkeeping: for a self-hosted deploy `sol up` builds locally, so the commit may describe nothing that was actually deployed — a dirty build and a clean build at the same commit are different releases and must not be indistinguishable. (A `source_tree_digest` would give stronger provenance for dirty builds later; the two fields above are enough to stop the confusion now.)

**The guarantee is narrow on purpose: a release record restores secret *references*, not historical secret material.** If a referenced secret has been rotated since release N, the restored release runs with the current material. Restoring values Sol deliberately never stored is not something this design can promise, and the same applies to any externally managed dependency whose value is intentionally not captured.

**Storage, for self-hosted:** the cluster must contain enough history to recover itself without Sol Cloud. One **immutable** ConfigMap per release (`immutable: true`, so it cannot be silently edited — only deleted), with labels for lookup (`sol.dev/type=release`, `sol.dev/target`, `sol.dev/scope`) and annotations for anything long, plus one small pointer object naming the current release. A CRD is a later question (indexed status, lifecycle, admission), not a first one. **Secret values are never stored** — only references.

## Rollback semantics

- **Release-scoped.** Rollback restores exactly the boundary of the release being rolled back — which may itself have been unit-scoped (`--scope payments/charge_svc`). Restoring *part* of a release (`just charge, from the release that was the payments domain`) synthesises a state that release never represented, and is refused.
- **Never re-resolve the historical requested scope against today's tree.** If release N recorded `requested: payments` and `resolved: charge, refund`, then rolling back to N restores charge and refund, even if `settle_worker` exists today.
- **Verify structurally, where Sol is the mutator.** "Matches release N" means rendered configuration, image digests and scope membership — never secret values, which are deliberately not stored. Where a controller owns the resources, verification is not *weaker*, it is **not applicable**: the controller reconciles forward, so a point-in-time read would be a green checkmark with a five-second half-life. Report it as such rather than reporting a match:

  ```text
  restored release 01J...
  verification: not applicable
  reason: target is reconciled by an external GitOps controller
  ```

  The record is the *operational recovery record*, not necessarily the desired-state source of truth, and rollback for a GitOps-managed target may need to change the Git source rather than fight the reconciler. Recorded so that "works offline for GitOps" does not promise more than the execution model delivers.
- **In-flight deploys: abort, establish quiescence, then restore** — one verb, because the user's intent is clear and `sol deploy cancel && sol rollback` protects nobody. If Sol cannot establish that the in-flight operation was actually stopped, it **refuses** rather than racing it. Deploy and rollback share one lease per target/scope boundary; two processes must not mutate the same boundary concurrently.
- **Migrations are the hard boundary: refusal, and no `--force`.** Forward-only, expand/contract. **Rollback refuses only when restoring the old application release would cross a schema change declared incompatible with that old release.** "Any migration since N" would make expand/contract largely useless, since the whole point of it is that old code keeps working against a newer schema. That requires each migration to carry an authored **disposition** — `expand` / `contract`, and later perhaps `neutral`/data-only — which is a product and configuration contract rather than implementation metadata, and a genuine cost of this decision. Resist classifying migrations more cleverly than that until something needs it. The error names the release and the migration; a force flag would undermine the invariant that Sol does not knowingly restore code incompatible with the database.
- **Functions are not a no-op.** A release has an artifact and configuration even without a Deployment revision; restoration is reconciliation from the record. Mechanism varies by shape, meaning does not:

| shape | mechanism |
|---|---|
| rolling service/worker | native undo where it provably restores the recorded state, then reconcile configuration |
| canary / blue-green | Argo mechanism, then reconcile and verify |
| function | reconcile the recorded artifact + configuration |
| recreate / batch-shaped | reconcile from the release record |

- **Retention: bounded and configurable, count-based by default** — the initial default is the last **20 successful releases per target**, with current and previous never pruned. Time windows behave badly across teams with different deploy frequencies. Failed and in-progress *operation* history is a different retention question from release history, and should not be pruned by the same rule without thinking about debugging and audit.

## CLI surface

- `sol releases` — release id, commit, scope, created.
- `sol rollback <release-id>`.
- `sol rollback --commit <sha>` — convenience. A commit may map to several releases, so Sol lists the candidates and requires a choice rather than guessing, and echoes the release it resolved to even when there is exactly one.
- `sol rollback --scope <scope>` is allowed only as **release selection** ("the previous release whose boundary was this"), never as re-resolution.

- The decision above is recorded, including the authority of the record over native mechanisms.
- Implementation is tracked by FEAT-066, whose first slice (record on deploy + `sol releases`) is read-only and testable without any rollback execution.
- The GitOps ownership caveat is stated wherever rollback is documented, so the command does not imply control it does not have.

## Status

**The decision is final; implementation waits on plumbing.** The code path is blocked by FEAT-065, because a release record needs the requested scope and the resolved set — two of its fields — and those do not exist in the plan yet. The order is FEAT-065, then FEAT-066 slice 1 (the immutable record plus `sol releases`, read-only and testable), then rollback execution on top of real release objects. Recorded here so FEAT-065 and FEAT-066 build toward something fixed rather than leaving rollback semantics to be invented alongside the plumbing.
