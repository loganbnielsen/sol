Keep migration tables distinct for long workspace names

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `cd3251a5`, `Sol_cli_migration.table_name` can exceed PostgreSQL's default 63-byte identifier limit; `pg-eio` validates identifier characters but no length. The audit report gives two valid, distinct workspace names that PostgreSQL maps to one table.

## Problem

Two workspaces sharing PostgreSQL can use distinct Kubernetes namespaces yet the same migration-tracking table after PostgreSQL truncates their generated table identifiers. A migration version applied by one workspace then causes the other workspace to skip a different migration with that version. Deploy's schema prerequisite can also read the wrong applied-version set. This can leave the second workspace running against an incompatible schema.

## Remediation

Derive a bounded migration-table identifier with a stable distinguishing suffix over the full workspace name, and use it consistently in local migration commands, in-cluster migration Jobs, deploy prerequisites, and rollback checks. Fail clearly if any generated identifier cannot meet PostgreSQL's limit. Pre-alpha permits a direct naming change without a compatibility alias.

## Acceptance criteria

- The 59-`a` plus `x`/`y` pair produces different PostgreSQL identifiers of at most 63 bytes, while the 58-`a` positive control remains distinct.
- Two such workspaces sharing one disposable database can apply different migration version 1 files and independently report both as applied; neither workspace reads the other's migration row.
- All migration call sites use the same table derivation, including deploy and rollback checks.
- Update a runnable shared-database migration example or tutorial and state why the CLI/storage fix has no application-language parity gap.

## Completion notes

**Premise re-verified 2026-10-01** at `origin/main @ 0d4fa913`. `Sol_cli_migration.table_name`
built `sol_<sanitized>_schema_migrations` with no length bound, and every call site routes
through it — `Sol_cli_workspace.migrations_table` (the `sol migrate` default),
`Sol_cli_migration_gate.verify` (the deploy prerequisite), `cmd_rollback.ml`, and the
in-cluster Job args. A 60-byte workspace name produced an 82-byte identifier, so PostgreSQL
truncated to `sol_` plus the first 59 bytes and dropped the only byte distinguishing it.

**Implemented.** `table_name` keeps the readable form while it fits in 63 bytes and otherwise
emits a bounded `sol_<readable prefix>_<12 hex digits>_schema_migrations`, exactly 63 bytes,
where the hex digits are taken from the raw workspace name so the result is stable across
machines and releases. `table_length_error` refuses an explicit `--table` that PostgreSQL
would truncate, wired in as that flag's converter, which closes the same silent-truncation
class through the user-supplied door rather than only the generated one.

**Checks.**

- `dune build cli/bin/main.exe`; `test_migration.exe` 24/24, `test_workspace.exe` 16/16,
  `test_migration_gate.exe` 8/8, `test_migration_job.exe` 4/4.
- Mutation check: forcing the derivation back to unconditional readable form fails
  `table name stays bounded` with `one byte past the limit is shortened`, so the test binds
  the defect rather than the implementation.
- Behavioural, against the local Postgres: two disposable workspaces named `<59 a's>x` and
  `<59 a's>y` each applied a different `0001_*.sql` to one database. PostgreSQL stored
  `sol_aaaaaaaaaaaaaaaaaaaaaaaaaaaa_cdcd54afa488_schema_migrations` and
  `sol_aaaaaaaaaaaaaaaaaaaaaaaaaaaa_d2560d1e08d0_schema_migrations`, both 63 bytes, and each
  `sol migrate status --json` reported only its own version 1 under its own name. The pre-fix
  control, `left(<name>, 63)` of both old identifiers, is the single string `sol_<59 a's>`.
- `internal/ci/check_cli_reference.py` (48 commands, flags unchanged), `check_no_comments.sh`
  and `check_ocamlformat.sh --all` pass.

**Demo/example coverage.** `docs/guides/TUTORIAL.md` — the runnable migration walkthrough —
now states the shortening rule and that two workspaces sharing one database read only their
own table; `docs/deployment/migration-ordering.md` and `docs/architecture/devops-pipeline.md`
carry the same clause where they define the applied set.

**Language parity.** No application-language impact: the CLI derives the name from the
workspace directory and passes it to the migration runner as `--table`; no OCaml or
TypeScript framework library computes it, and `db/migrations` contents are unchanged.

**Remaining limitation, recorded not widened.** Sanitization still folds punctuation to `_`,
so two workspace directory names that differ only in punctuation or case (`My-WS` and
`my_ws`) still share a tracking table. Closing that completely requires folding in a hash for
*every* name, which changes the table of every existing workspace and the `sol_pluto_schema_migrations`
form the tutorial and roadmap document — a naming decision this ticket did not ask for and
that is worth making deliberately rather than as a side effect.
