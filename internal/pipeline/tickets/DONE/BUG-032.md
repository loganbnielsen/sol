**Depends on:** None.

**Related:** FEAT-079 (introduced `sol fn run`), INFRA-016 (the spike that
found this while trying to fire a concurrent burst).

`sol fn run`'s generated Job name has only one-second resolution, so firing
it more than once within the same second produces a name collision.

## Problem

`cli/sol/bin/cmd_fn.ml`'s `generate_job_name`:

```ocaml
let generate_job_name ~k8s_name =
  Printf.sprintf "%s-manual-%d" k8s_name (int_of_float (Unix.time ()))
```

`Unix.time ()` has one-second resolution. Two `sol fn run` invocations of
the same `-fn` within the same wall-clock second generate the identical
Job name, so the second `kubectl create job` fails with `AlreadyExists`.
This was invisible when FEAT-079's own CI coverage only ever fired one
invocation at a time; INFRA-016 needs several concurrent invocations to
generate realistic burst load and hit it immediately.

## Remediation

Add higher-resolution or explicitly collision-resistant entropy to the
generated name — e.g. sub-second time resolution
(`Unix.gettimeofday ()`'s fractional part) or a short random suffix,
following the same "mutex-protected, non-global `Random.State.t`" pattern
already established elsewhere in this codebase for anything jitter/entropy
related (see `kafka_service_retry_topics.ml`'s `produce_rng`/`message_rng`)
if randomness is used. Keep the name short enough to stay within
Kubernetes' Job-name length limit alongside `k8s_name`.

## Acceptance criteria

- Firing `sol fn run`/`sol local fn run` against the same `-fn` multiple
  times within the same second produces distinct Job names every time —
  add a test that calls `generate_job_name` (or an equivalent exposed seam)
  twice in immediate succession and asserts the results differ.
- No change to the mandatory `--from=cronjob/...` mechanism itself.

## Completion (2026-09-22)

The name is now minted in a lib rather than inline in the command, so the uniqueness
rule has a seam a test can drive: `Sol_cli_manual_job_name` (`of_parts` pure,
`mint` = clock + OS entropy), with `cmd_fn.ml` calling `mint`.

**Two deliberate departures from the remediation, both recorded here:**

1. **Entropy comes from `Sol_cli_deployment_id.random_entropy`, not a mutex-protected
   `Random.State.t`.** The collision domain is *across processes* — that is the whole
   bug — so a per-process RNG would need seeding from the same OS source anyway, and
   this codebase already has one definition of "OS entropy where available, with a
   fallback" for exactly this requirement (two actors minting in the same second).
   A second copy of that would be the kind of duplication
   `INFRA-065` exists to clean up.
2. **The result is bounded to 63 characters** (the cap on the `job-name` label
   Kubernetes derives from the Job's name), which the remediation asked for but the
   old code did not honour: a long `k8s_name` already produced an over-long Job name.
   The **base** is shortened to make room, never the suffix — truncating the suffix
   would cut the entropy off the end and bring the collision straight back. That
   asymmetry is asserted directly (`base_of`), not just the length.

**Tests** (`cli/sol/test/test_manual_job_name.ml`, 5 cases): the exact shape for
supplied clock/entropy; two runs in the same second differing (the defect, at the pure
level); `mint` twice in immediate succession differing (the acceptance criterion
verbatim); a 63-character base being shortened while the same-second distinction
survives; and a base whose cut lands on a hyphen still producing a legal name — checked
with the command's own `validate_dns_label`, so "legal" is not re-implemented in the
test.

**Mutation-verified:** stripping the entropy from the name fails 3 of the 5 cases
(the three collision assertions) and the restored code passes, so the tests detect the
defect rather than merely describing the fix. The first mutant attempt did not compile
(unused-variable warning as error), which is not a valid mutant, so it was redone.

**The assumption that was wrong** is recorded where it will be read next: the old
comment justified seconds-resolution with "a manual run is a human typing a command,
not a high-frequency automated path". That premise is what `INFRA-016` disproved by
firing several at once, and the module header now says so instead.

Acceptance criteria: distinct names on repeated same-second invocations (tests 2, 3);
`--from=cronjob/...` untouched (`Sol_cli_kubectl.create_job_from_cronjob` is called
exactly as before, with only the name argument changed).

`dune build`, `dune fmt` and the whole `cli/sol/test/` suite pass.
