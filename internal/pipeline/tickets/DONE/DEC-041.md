## Question

Which layer owns a target's `omit`?

Run 8's target omits the workspace's two TypeScript services (`omit: true` on `order_svc`
and `fulfillment_worker`) with a comment saying they are "omitted here rather than left to
fail the run at step 1" — and the production-profile preflight reports them anyway. The
ticket that opened this framed it as two readings with no implementation. FND-0023 shows
that is not the case: `omit` **is** implemented, in one layer, and bypassed in another.

## Established (FND-0023, reproduced 2026-09-21 on `main` @ `506d71a9`)

- **The config layer honours `omit`.** `Sol_cli_config.active_resources`/`active_services`
  filter omitted units and are exported as the resolved-config accessors
  `resources`/`services`; they are used by config validation and capability derivation.
  Pinned by `test_config.ml`'s `test_target_overlay_can_omit_resources_and_services`.
- **The deploy and preflight layers bypass it.** The deploy inventory is
  `Sol_cli_manifest.discover_services ()` — a filesystem scan — narrowed only by
  `--scope`; that selection becomes `plan.services`, and
  `sol_cli_profile_preflight.ml`'s `Qualified_versions` reads it. With `omit: true` on the
  pair, the plan still lists `demo_ts/order_svc` and `demo_ts/fulfillment_worker` **by
  name**; `--scope` removes them and `omit` does not. The verbatim reproduction is in
  FND-0023.
- **Precedent inside the config layer.** An omitted *resource* is already treated as not
  declared: `test_config.ml` has an omitted `app_db` making a dependent service fail as
  `service "api" uses undeclared resource "app_db"`. So for resources, `omit` already
  means "not in this target's set".

The defect is the split itself: filter here, bypass there. `omit`'s name promises
something the deploy path does not deliver.

## Verified scope grammar (2026-09-22)

`--scope` accepts exactly three forms (`sol_cli_deployment_scope.ml`'s `parse_request`):

| Input | Selects |
|---|---|
| absent | the whole workspace |
| `payments` | **every unit in that domain** |
| `payments/charge_svc` | exactly one unit |

Anything else — including a three-segment path — is an **error**, and there is **no
glob/pattern matching** (`*` would be read as a literal name, match nothing, and fail
closed with `matches no workload`). So a wildcard cannot resurrect an omitted unit — but a
**domain-level scope is a coarse selector** that names no unit, which is why rule 3 of the
decision below exists.

## Options

- **A. `omit` means "not in this target's declared set".** Make the deploy selection derive
  from the omit-filtered resolved config, so an omitted unit is neither deployed nor
  preflighted. Consistent with resource-level behaviour and with the run8 target author's
  intent.
- **B. `omit` is config-layer-only; production is always deployed `--scope`-ed.** Document
  that, and make the deploy path stop implying more (or feed the preflight the filtered
  set) instead of leaving the key's name misleading. Smaller, but leaves the key named for
  a guarantee it does not provide.

### If A is chosen, the fork that must also be decided

Does an explicit `--scope` naming an omitted unit include it, or is `omit` authoritative?

- **A1. `omit` is a default; `--scope` is explicit intent.** `omit` removes the unit from
  the no-`--scope` set; naming it in `--scope` includes it again, and the run *reports*
  that it selected an omitted unit. `--scope` already *is* the operator's explicit
  statement of what an invocation deploys (DEC-036), so `omit` should narrow the default,
  not forbid deployment outright. This keeps an escape hatch and avoids a `--scope` that
  silently selects nothing.
- **A2. `omit` is authoritative.** `--scope` cannot resurrect an omitted unit; naming it is
  refused or diagnosed. Simpler rule, but a `--scope` that names a unit and deploys nothing
  is surprising, and it removes the only way to qualify a unit the workspace still
  contains.

## Decision (2026-09-22) — A1, with the domain-scope exclusion

**`omit` means "not in this target's default set." An explicit unit-level `--scope` may
re-include an omitted unit; a domain-level `--scope` may not.**

1. **The deploy selection derives from the omit-filtered resolved config.** By default an
   omitted unit is neither deployed nor preflighted.
2. **A unit-level `--scope` naming the unit exactly re-includes it**, and the run reports
   that it selected an omitted unit.
3. **A domain-level `--scope` excludes omitted units from its expansion and reports the
   exclusion**, so a routine `--scope payments` never re-includes an omitted unit as
   collateral.

### Why A1 is not a safety hole: the preflight is an independent gate

`omit` answers *"is this unit part of this target's default set?"* — a statement about the
target, held in shared config. It does **not** answer *"can this unit run here at all?"*.

That second question is owned by the profile preflight, which runs **once, in the
plan-building path, before any lease, cluster mutation or emitted file**, on whatever set
the selection produced (`cmd_deploy.ml:241-249`; verified 2026-09-22). It is **not
conditional on how the selection was made**, so a unit re-included by a unit-level
`--scope` still passes through it.

Therefore overriding `omit` can only ever re-include a unit that **is deployable but
non-routine**. A unit that genuinely cannot run on the target — the TypeScript service on a
profile that does not qualify TypeScript — is still refused, by the preflight, on its own
terms, with its own message. Keeping the three questions separate is the point: `omit` is a
default about the target, `--scope` is per-invocation intent, and the preflight is the
capability gate. `omit` is never asked to carry a safety guarantee it does not own.

### Why not A2 — and what a stronger guarantee would look like

A2 would turn a boolean in a shared target file into an absolute veto that no deliberate,
per-invocation action can override: the only way to act on the unit would be to edit shared
config — a broader, longer-lived change that outlives the need unless someone reverts it.
That is a worse failure mode than the accidental re-inclusion it prevents.

If a target ever needs *"never deploy this here, full stop"*, that is a **different
guarantee and belongs in a different key** — e.g. a `forbidden`/`decommissioned` marker
with its own refusal path — rather than a second meaning loaded onto `omit`. The original
defect came from one key implying two things in two layers; the fix must not repeat it.

## Acceptance criteria

- One place states the semantics of `omit` with respect to the profile preflight, and the
  qualification procedure says whether a run is expected to deploy `--scope`-ed or
  whole-workspace.
- The regression matrix is pinned by tests: **no scope → the omitted unit is absent**;
  **unit-level scope naming it → present, preflighted, and the run reports that it selected
  an omitted unit**; **domain-level scope → the omitted unit stays excluded and the
  exclusion is reported**; **domain-level scope covering only omitted units → not silently
  empty**.
- A test pins that the **preflight runs on a re-included unit** — i.e. that the override
  cannot bypass the capability gate (the backstop above, not left implicit).
- The fix removes the unit from the **selection**; repointing `sol_yml_language` alone is
  not sufficient (it would convert the language finding into "does not declare a
  language" and still fail).
- Migration is stated honestly: the two tracked configs
  (`examples/pluto/sol/dev/aws/us-east-1.yml`, `internal/qualification/aws/run8-aws-target.example.yml`)
  can be revisited in the change, but untracked targets that set `omit` will change
  behaviour silently on upgrade and cannot be warned.

**Demo/example coverage:** the example changes are
`examples/pluto/sol/dev/aws/us-east-1.yml` and the run8 target — both set `omit`, and the
change makes their omitted units actually exempt. `INFRA-049` carries the implementation.
