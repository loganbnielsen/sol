## The gap

Production operators legitimately need "restart this workload without changing its
release". Sol has no way to express it: an identical `sol deploy` is idempotent **by
design** — B2 qualifies exactly that no workload restarts and the pointer does not move
— so redeploying a degraded fixture resets nothing. Verified live: `generation` stayed
1, the same pods with the same creation timestamps, still 0/2, still `DEGRADED`.

That idempotence must not be weakened to make a test convenient.

## Decision (2026-09-21)

Add an explicit operational command, `sol restart`:

| | |
|---|---|
| `sol deploy` | make reality match **this** release |
| **`sol restart`** | **recycle reality without changing the release** |
| `sol rollback` | make reality match an **earlier** release |

Contract:

1. **Explicitly scoped** — a domain/unit or a unit, never the whole workspace by
   accident.
2. **Operational, not release-producing**: it recycles the selected deployed
   workload's pods. It does not change image, configuration or manifest to induce a
   rollout, and it **does not manufacture a new release** — the release identity is
   unchanged, because the artefact and configuration are unchanged.
3. **Uses the mutation identity** (deploy), not the operator's diagnostics.
4. **Produces operational evidence** that a new workload generation actually exists —
   new pod identities, the observed rollout, restart counts — recorded as the run log
   does for other operations.
5. **B2 is untouched**: an identical `sol deploy` still restarts nothing.

Naming: `sol restart` rather than a `rollout` family, since there is no existing
`rollout` command group and the intent should be obvious at the call site. The
implementation owns the Kubernetes mechanism (`spec.template.metadata.annotations`
with a restart timestamp) while the user expresses intent.

## Acceptance criteria

- `sol restart --scope <domain/unit>` recycles the workload; the release pointer is
  unchanged afterwards; the run log records the attempt with its evidence.
- It refuses an unscoped or ambiguous selection rather than guessing.
- Regression coverage: a restart produces a new pod generation; an identical deploy
  still produces none (B2 preserved), both offline where possible.
- Live: the preserved `notify_worker` fixture is reset with `sol restart` and observed.
  If that does not restore it to stable health, the run stops rather than repeating the
  restart to manufacture a passing window.
