**Depends on:** None.

`soldev pipeline merge --pr <n>` is documented as the way to queue native squash auto-merge, and
auto-merge is the default landing path. Immediately after a PR is opened — or immediately after a
push to one — `gh pr checks <url> --required` exits non-zero because no check run has registered
yet, soldev turns that into `Checks_unreadable`, and the command *reports and skips* instead of
queuing:

```text
$ soldev pipeline merge --pr 773      # seconds after the PR was opened
[#773]
  could not read the required checks from gh — skipping (https://github.com/loganbnielsen/sol/pull/773)

$ sleep 40; soldev pipeline merge --pr 773
[#773]
  $ gh pr merge '…' --squash --match-head-commit '<sha>' --auto
  GitHub accepted auto-merge
```

Observed three times on 2026-09-30 (`#773`, `#775`, `#776`), each time fixed by a manual retry.
The failure is silent in the sense that matters: the command exits zero, so a caller that does not
read the output believes a merge is queued when nothing was requested. That is the same failure
class as the stale head pin (#773): a read taken too early, at the moment the operator is being
told to queue.

## Premise, checked and corrected (2026-09-30)

The claim this ticket was filed with — that a *freshly opened* PR cannot be queued because its
checks have not registered — is **not current main's behaviour**. Run against a binary built from
`origin/main` (`894a37af`), on a PR opened seconds earlier:

```text
$ gh pr create --base main …            # → https://github.com/loganbnielsen/sol/pull/781
$ pipeline merge --pr 781
[#781]
  $ gh pr merge '…' --squash --match-head-commit '7612a6b2…' --auto
  GitHub accepted auto-merge
```

The three skips recorded on 2026-09-30 came from a local binary built on a base that predated PR
#768's `baseRefName` addition to the `gh pr list --json` field list: with the base ref read as the
empty string, `base_required_checks_configured ~base_ref:""` failed and the refusal reported
`Checks_unreadable`. That fix is on `main`; the stale binary was the problem, not the timing.
(Lesson worth keeping: a tool read at the moment of queuing must be built from the same `main` the
queue decision is about.)

**What survives is the second half of the finding, and it is the half that misled the caller.** A
refusal on a *targeted* invocation printed "— skipping" and still exited zero, so a script or an
agent could not distinguish a queued merge from nothing at all. The fix is smaller than the one
this ticket first proposed: the refusal decides the exit code.

It is not the same as the case soldev correctly refuses: when `gh` cannot be read because of a
credential or network failure, or when the base branch has no required checks configured
(`base_required_checks_configured`), refusing is right.

## Remediation

Carried out in PR #781: a targeted invocation (a ticket id or `--pr`) that was refused exits
non-zero, with a message that says a skip is not a queued merge; a sweep (`pipeline merge` with no
target) may still skip what cannot be queued and exits zero, because skipping is what a sweep is
for. The decision is `merge_outcome` in `Soldev_merge` — a pure function with a test table
covering all three verdicts.

The fresh-PR case needs no further work: it is already correct on `main`, and no-checks-yet does
not have to be distinguished from unreadable.

## Acceptance criteria

- A targeted `merge --pr` or `merge <ticket>` that is refused exits non-zero, and its message says
  the merge was not queued.
- A sweep still exits zero while skipping drafts and unready PRs.
- `test_merge` covers the three outcomes, including that a skip on a targeted invocation is not a
  success.

## Completion notes (2026-09-30)

Fixed in PR #781.

**What was wrong, precisely.** A refused *targeted* invocation — `merge <ticket>` or `merge --pr
<n>` — printed `— skipping` and exited **zero**, so a caller could not tell a queued merge from
nothing at all. That is the residual defect after the premise correction above; the fresh-PR
reading needed no work, because current `main` already queues a PR opened seconds earlier.

**The fix.** `Soldev_merge.merge_outcome ~errors ~refusals ~targeted` is
`All_requested | Some_requests_failed | Nothing_requested`, and a targeted invocation that was
refused exits non-zero with a message saying a skip is not a queued merge. A sweep (`pipeline
merge` with no target) still skips drafts and unready PRs and exits zero, because skipping is what
a sweep is for.

**Verified by driving both binaries on a real refusal** — the same command, the same PR, the
binary as it was before the fix and the binary with it:

```text
$ pipeline merge --pr 781 --immediate --dry-run      # before the fix
  required checks not green — skipping (https://github.com/loganbnielsen/sol/pull/781)
exit=0

$ pipeline merge --pr 781 --immediate --dry-run      # with the fix
error: nothing was reported as queueable: the pull request was skipped, and the message above
says why. A skip is not a queued merge — resolve it and run this again.
exit=1
```

The first line is the defect (`exit=0` while nothing was queued); the second is the fix. Also
validated: `dune build`; `test_merge` 19 cases including the outcome table; and
`check_ocamlformat.sh --all` (which is what the first attempt at this fix's sibling PR missed).

**Demo/example coverage:** none applies — `soldev` is the maintainer's tool, with no app-author
surface.

**Language parity:** no impact; nothing application-facing changed.
