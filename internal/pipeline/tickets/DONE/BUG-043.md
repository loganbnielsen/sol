A stopped Retry_topics relay must fail the worker, not wait for the source consumer to exit

**Depends on:** None.

**Finding:** FND-0035 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-23** against `origin/main @ f3e9480b` while filing (see the finding for the command/probe and observed output).

## Problem

The relay fiber in `Kafka_service_retry_topics.consume` records `relay_failure` and returns; the ref is read only after the source consumer returns, which a healthy consumer never does. Health stays green while retry delivery is suspended indefinitely. BUG-029 deferred this explicitly.

## Remediation

When the relay stops with an error, stop the source consumer (resolve its stop / fail the switch) so `consume_partitioned` returns `Error` promptly; or fail `/livez` from relay state.

## Acceptance criteria

- A test where the relay's `consume_partitioned` fails while the source topic is idle observes `consume_partitioned` returning `Error` within a bounded time.
- `sol-worker.md` / `kafka-eio-service.md` exhaustion-policy text updated to match.
- TS parity: record whether `@sol-fab/worker` has the same relay shape (verdict or tracking ticket) in completion notes.
- Demo/example: not applicable (framework internals) — state in completion notes.

## Completion notes

- `Kafka_service_retry_topics.consume`: when the relay's `consume_partitioned` returns
  `Error` (`Handler_errors` or `Invalid_config`), the relay fiber records the failure,
  logs `RETRY_RELAY_STOPPED`, and closes the **source** consumer. kafka-eio's
  `consume_partitioned` watchdog treats a direct `close` as a stop, so the source loop
  ends and the existing `relay_failure` check turns its result into `Error`. The worker
  exits (and restarts) instead of running with retry delivery dead behind green health.
- Regression, against a real broker: `test_retry_topics_dead_relay_fails_the_worker`
  in `test_kafka_service_integration.ml`. The handler asks for a retry on the source
  delivery, then returns a Kafka error on the relay's redelivery (stopping the relay).
  With the source idle, `consume_partitioned` must return `Error` within 45s. It
  passes, and the suite runs in ~2s.
- Mutation check (`audits/README.md`): making the close a no-op builds (rc=0), and the
  test then fails at its 45s timeout with "the relay stopped (after 2 deliveries) but
  the worker kept running", which is exactly the pre-fix behaviour.
- Review round 1 (non-blocking, taken): if the close interrupts an in-flight source ack,
  the source returns an incidental `Destroy` error, which could mask the relay's error.
  A `relay_closed_source` flag now makes the relay's error the one returned in that
  case. A source that fails on its own before the relay does still keeps its own error
  (BUG-029). The regression asserts the returned error is the relay's (`Partition_errors`
  with `Application`), not just any error.
- **Caveat:** CI does not run the `kafka-eio-service` suite. The unit-test step excludes
  it because it needs a broker; it runs locally through `run_tests.sh`'s `run_kafka()`.
  This test was run locally against the documented Redpanda container
  (`cli/platform/local/scripts/ensure-broker.sh`).
- Docs: `kafka-eio-service.md`'s relay exhaustion policy now says the failure is
  surfaced promptly.
- Demo/example: not applicable (framework internals; the worker's contract,
  "a dead relay fails the worker", is unchanged, only prompt).
- Language parity: the TS `@sol-fab/kafka` relay lives in its own repository
  (loganbnielsen/sol-kafka), which runs its own Redpanda retry/DLQ tests; whether its
  relay failure stops the source consumer promptly is not assessed here. Recorded as
  open parity work in the ticket's finding (FND-0035) rather than claimed equivalent.
