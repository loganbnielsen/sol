## Question

One word in the target address — today `provider` — carries three independent
concepts, and they have different lifetimes:

| Concept | Today, in the address | What actually varies by it |
|---|---|---|
| **Driver**: whose lifecycle behaviour Sol owns | `aws` / `gcp` | whether Sol can provision, plan, destroy, verify |
| **Provisioning ownership**: who made the cluster | *unexpressible* | whether Sol may touch the substrate at all |
| **Capability**: managed database? managed Kafka? native state locking? IAM-shaped identity? | implied by the driver name | what the target can be asked to do |

The conflation is observable, not theoretical. Because the middle segment is a closed
enum of *brands* that all own a Terraform root, a cluster Sol did not provision cannot
be named. It must borrow a brand — and then `sol cloud plan|apply|destroy` resolves
*that* brand's root (`cli/bin/cmd_cloud_tf.ml:36-44`, used at `:937-940` and
`:1172-1175`), so a target whose substrate belongs to someone else is nonetheless driven
as if Sol owned it. `docs/reference/substrate.md:228` promises the opposite ("any
substrate that satisfies the contract works"), and `INFRA-014` exists precisely because
nothing verifies that promise.

**Does the middle segment name a _driver_ — the dispatch key for what Sol knows how to
do — rather than a cloud provider?**

## Preferred direction (proposed)

```text
<env>/<driver>/<region>
```

with, initially:

```text
aws
gcp
byo
```

`byo` is a **real driver** whose defining lifecycle property is that it owns **no cloud
Terraform root**. It is not a placeholder and not "not implemented yet": there is no
`platform/cloud/byo/`, by design, and `sol cloud plan|apply|destroy byo/…` must have a
**defined refusal** rather than accidentally resolving another driver's root.

**Admission rule:**

> A named cloud driver exists when Sol owns provider-specific lifecycle behaviour for
> that cloud. A cluster merely *hosted* by a cloud does not require a driver for that
> cloud.

So Hetzner, DigitalOcean and Civo remain `byo` unless and until Sol actually owns their
provider lifecycle — which `INFRA-014` explicitly declines to do ("a recipe plus a
verification run, not a new provider Terraform module", `INFRA-014.md:40`).

If accepted, rename the internal concept from `provider` to `driver` **where it is
semantically this dispatch key**. Do not churn user-facing terminology, Terraform
variable names, `provider_fields`, or provider-specific modules for naming consistency;
that is a separate, mechanical unit (see *Smallest migration*, step 6).

## Options

| | Shape | Why / cost | Verdict |
|---|---|---|---|
| **A** | Middle segment = **driver**; add rootless `byo`; `sol cloud *` refuses for a driver with no root. | The address grammar does not change (`DEC-031` intact); the enum grows by one; the new behaviour is one refusal at one seam. Makes "whose substrate is this" answerable, which is the question `INFRA-014` and the self-hosted contract both keep re-asking. | **Recommended** |
| **B** | Keep `provider` a brand, add a separate `substrate: external` axis (per target). | Two keys must agree: an external substrate under `aws` is still driven as AWS by the cloud commands unless every call site learns to check the second axis — the same class of two-sources-of-truth defect `FEAT-059` removed from `validate_no_same_cluster`. | Reject |
| **C** | Keep `provider`, add `byo` as *a provider*, create `platform/cloud/byo/`. | A Terraform root that provisions nothing is a fiction; it would have to exist to satisfy `check_provider_roots.sh:21` ("every role"), and it invites exactly the speculation this decision's non-goal forbids. | Reject |
| **D** | Do nothing; document that a BYO cluster picks an existing brand. | Keeps a wrong claim in the product: `sol cloud *` on that target acts on a substrate the operator never handed Sol, and the refusal that should exist cannot be written because the driver is not distinguishable. | Reject |

## Recommendation

**A.** Three properties make it worth the change:

- **The refusal becomes expressible.** ADR 0002 § *Provider and local scope* already
  says an unsupported provider "must report the lifecycle capability as unmet". A
  driver with no root is the case that sentence was reaching for; today the code cannot
  tell it apart from "no root yet", so the verdict is an accidentally-correct failure
  (`asset_root` resolving a path that does not exist) rather than a defined one.
- **The admission rule replaces judgement with a test.** "Does Sol own lifecycle
  behaviour for this cloud?" is answerable from the tree (a directory under
  `platform/cloud/` with all three roles), so adding a cloud stops being a taste
  question. It also tells a future reader why `byo` is permanent rather than pending.
- **Capability stops being inferred from a brand.** That is `DEC-052`'s subject, and
  this decision is what makes the question askable: once the segment is a driver, "what
  this driver can do" and "what this substrate provides" are no longer the same lookup.

## Affected invariants

1. **`DEC-031` / AGENTS.md § primary axis.** The target positional stays
   `<env>/<driver>/<region>`; the axis is unchanged and no flag is added. The grammar
   is identical — only the enum's size and the segment's meaning change.
2. **`DEC-046` rule 4 / `internal/ci/check_provider_roots.sh` (three states become
   four).** Today: *paper* (registered, no directory — legal, "registering a provider to
   measure its change surface must stay legal", `:5-7`), *real* (directory, every role,
   `:21`), and *unregistered directory* (`:54-58`). `byo` adds *rootless by definition*,
   which is **indistinguishable from paper** to that guard — it passes (`:41-43` skips
   it) for the wrong reason. Nothing fails today; the invariant to add is that "no root
   yet" and "no root ever" are different states, so no future reader "finishes" `byo` by
   creating a root.
3. **`check_destroy_completeness.sh:38-43`** already skips a provider with no cluster
   root, and `real >= 1` stays satisfied by `aws`/`gcp`. Mechanically compatible;
   semantically it must be told the difference from (2).
4. **ADR 0002 § *Provider and local scope*** — the refusal must be raised **before**
   `check_terraform ()` and `asset_root` (`cmd_cloud_tf.ml:937-940`, `:1172-1175`), with
   a message naming that the substrate is not Sol-managed. A rootless driver must not be
   reported as a missing-asset error.
5. **`REFAC-095`/`REFAC-100` wildcard-free contract.** `capabilities_of`
   (`sol_cli_provider_capabilities.ml:290-293`) has no `| _` arm and `next`/`all` force
   enumeration, so a new driver cannot compile until its record exists. The new
   pressure is the opposite of before: `byo` makes "not applicable" the common case, and
   the record cannot currently distinguish *not applicable* from *not yet implemented*
   (`disk_quota = None` on AWS means "not implemented; report not observed",
   `:105-109`). At minimum the record needs one field stating that the driver owns no
   root; possibly a small tri-state for capabilities that are structurally absent.
6. **`Sol_cli_provider.all` consumers** (`sol_cli_profile_preflight.ml:20`,
   `cmd_assets.ml:84`, `cli/test/print_providers.ml:7`, and the guards sourcing
   `internal/ci/providers.sh`) must treat a rootless driver as "has no assets", not
   "assets are missing". `print_providers` feeding the CI guards is the load-bearing
   one: a new driver is covered by those guards from the moment it is enumerated.
7. **`provider_dispatch_allowlist.txt`** (REFAC-092 baseline; "entries may only go
   down"). Adding a `Byo` arm must not require an allowlist entry — if it does, the
   dispatch boundary was bypassed rather than extended.
8. **`DEC-022` language parity:** none. Deployment configuration and the provider
   lifecycle are language-neutral; no application-facing contract changes.

## Smallest migration from `<provider>/<region>`

No target file changes, no data migration, no compatibility shim. Steps, smallest first:

1. **Name the concept.** Add `Byo` to `Sol_cli_provider.t`, `of_string` (`"byo"`),
   `to_string`, and the `next`/`all` chain (`sol_cli_provider.ml:1-40`). This is
   compile-forced to be complete, which is `REFAC-100`'s point.
2. **Give the driver one new fact.** Extend the capabilities record with the property
   that distinguishes it (a root, or a provisioning mode), and give `byo` a record whose
   rootless state is explicit rather than inferred from a missing directory.
3. **Refuse before resolving assets.** In `sol cloud plan|apply|destroy`
   (`cmd_cloud_tf.ml:937`, `:1172`), refuse a rootless driver with a named reason,
   ahead of `check_terraform`/`asset_root`.
4. **Teach the guards the fourth state.** `check_provider_roots.sh` and
   `check_destroy_completeness.sh` must accept `byo` as rootless-by-definition, and fail
   if a driver that is *not* rootless-by-definition has no root.
5. **Make `sol deploy` the whole story for `byo`.** It already consumes a destination
   (`kube_context`, `FEAT-059`) and a `registry`; a `byo` target is a normal target
   minus cloud lifecycle. Confirm the same-cluster lint, readiness and preflight
   behaviour is unchanged for it.
6. **Rename internally, separately, mechanically.** `provider` → `driver` only where
   the identifier means the dispatch key. Keep user-facing text, `provider_fields`,
   `owned_legacy_keys`, and Terraform variable names as they are. One pass or none.

Existing `aws`/`gcp` targets and every `sol/environments.yml` in the tree remain
byte-identical: the segment's *values* do not change.

## Out of scope (non-goals)

- **Do not implement DigitalOcean, Hetzner, Civo or Azure** as part of this decision.
  The point is to make their eventual addition unsurprising, not to speculate about
  their mechanics. Azure's on-paper registration test (`DEC-046` rule 4) stays legal and
  is unaffected.
- **Do not rename user-facing terminology** or churn provider-specific modules for
  consistency (step 6 is internal and mechanical).
- **Do not add a root skeleton** for a driver that has no root.
- **Do not decide the substrate contract here** — that is `DEC-052`.

## Acceptance criteria

- The middle segment's meaning is recorded: driver, not cloud brand.
- The admission rule is recorded, with the reason Hetzner/DOKS/Civo stay `byo`.
- `sol cloud plan|apply|destroy byo/…` has a stated verdict (refusal, with its message
  contract), and the implementing ticket asserts it.
- Every invariant in the list above is either preserved or explicitly amended, with the
  guard that enforces it named.
- The implementing unit states its **demo/example** obligation: a `byo` target in
  `examples/pluto/sol/environments.yml` (or the tutorial) is app-author-visible, so the
  repo's demo/example coverage rule (AGENTS.md § *Demo/example coverage*) applies when
  this lands. The decision itself changes nothing runnable.
- **No language-parity impact** (`DEC-022`): recorded in the implementing ticket's
  completion notes.

## Operator clarification (2026-09-26)

Recorded when this decision was promoted, in the operator's words:

1. **`byo` owning no root must be a positive capability fact, not another special case.**
   The representation should say which of three things is true — `Present` (this driver
   owns a root), `Not_applicable` (this driver has no root, by definition), or
   `Not_implemented` (registered, root not built yet). Whether those are literally the
   constructors does not matter; the semantic distinction does. Otherwise `None` becomes
   ambiguous again, exactly as `disk_quota = None` is today.
2. **No scattered `Byo -> …` branches around `cmd_cloud_tf`.** The generic lifecycle
   reads the capability fact; the refusal is the lifecycle's behaviour, not a per-driver
   arm.
3. **`Not_applicable` is the durable part of this decision.** BYO is the first case that
   forces it, and the capability record will need the same three-way distinction in
   several places as drivers diversify.
4. **This stream is independent of the GCP qualification frontier** (GKE Standard /
   FND-0064). Getting the existing GCP driver to `Ready` and making the provider model
   correct for future drivers are separate; neither waits for the other.

## Status

**Decided 2026-09-26 by the operator.** Option A is accepted: the middle target-address
segment names a **driver**, `byo` is a driver whose defining property is that it owns no
cloud Terraform root, and the admission rule above decides when a cloud earns a driver
of its own. The decision, the affected invariants and the migration are recorded here;
the implementation (the enum value, the `Present` / `Not_applicable` /
`Not_implemented` capability fact, the `sol cloud *` refusal, the two CI guards) is
materialised as a separate unit.

## Implementation (2026-10-02)

The migration's steps 1–5 are implemented on branch `DEC-051/driver-model`,
based on `origin/main @ f7d45074`.

- **The driver is named.** `Byo` is in `Sol_cli_provider.t`, `of_string`
  (`"byo"`), `to_string`, and the `next`/`all` chain. `owned_legacy_keys` is
  unchanged — `byo` owns no keys.
- **The root fact is a positive capability.** `Sol_cli_provider_capabilities`
  gains `type root_status = Root_present | Root_not_applicable |
  Root_not_implemented` and a `root_status` field on `t`. `aws`/`gcp` are
  `Root_present`; `byo` is `Root_not_applicable`, its root-dependent fields
  inert and its deploy-reachable fields correct (`production_qualified = false`,
  `scoped_identities = []`, `state_locking = None`,
  `authorization_effective_access = Ok ()`). `owns_root` is the derived
  predicate consumers use instead of pattern-matching a driver.
  `Root_not_implemented` has no instance yet — it is the state a
  registered-but-unbuilt driver (DEC-046 rule 4's "paper") will carry.
- **The refusal is the lifecycle's, not a per-driver arm.** `cmd_cloud_tf.ml`'s
  `require_cloud_root` reads `root_status` and refuses before `check_terraform ()`
  / `asset_root` in `cloud_apply` (plan/apply), `cloud_destroy`,
  `cloud_reconcile`, and `cloud_bootstrap`. Confirmed live: `sol cloud plan
  customer_cloud/byo/onprem` prints the refusal and does not look for a
  Terraform root.
- **The provider-specific registry answers for `byo` without a landmine.** It has
  no root to resolve (`of_root` returns a new `No_root` failure before running
  `terraform`), nothing to observe or identify (`[]`), an inert
  `Sol_cli_destruction.t` (`Nothing_prepared`, `Retention_not_required`), and no
  credentials (`Error`).
- **`all` consumers treat a rootless driver as "has no assets".** `cmd_assets`
  filters to `owns_root`; `readiness_checks` returns `[]` for a rootless driver
  (the platform lifecycle it would check does not exist); `profile_preflight`'s
  `qualified_providers` already excludes it.
- **The guards grew the fourth state.** `cli/test/print_providers.ml` prints
  `name<TAB>root_status`; `internal/ci/providers.sh` and
  `internal/ci/lib/providers.py` parse rows; `check_provider_roots.sh` skips a
  `not_applicable` driver (and *fails* if it has a directory), keeps a
  registered-but-rootless driver as paper, and **fails a `present` driver with no
  root**. `check_destroy_completeness.py` skips a driver with no cluster root as
  before.
- **Demo:** a `byo/onprem` target in `examples/pluto/sol/environments.yml`.
