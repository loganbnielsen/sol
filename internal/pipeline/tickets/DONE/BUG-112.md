The representative consumer is not idempotent for its domain write under duplicate fact delivery

**Depends on:** None.

## Problem

The outbox contract is explicitly at-least-once: a duplicate fact is a legal outcome, and
consumers must tolerate it. `FEAT-120`'s run delivered the same `Charged` domain event
(`q-baseline`) twice and observed:

```text
pluto_notifications = 2      (a second row for the same charge)
sol_jobs            = 1      (the independent effect was deduped by ~dedupe_key)
```

So the *independent effect* is idempotent, but the consumer's own domain insert is not: a
redelivered fact duplicates the notification. The example is the checked-in demonstration of
the architecture Sol recommends, and it does not demonstrate the consumer half of the contract
it documents.

`examples/pluto/app/comms/notify_worker/lib/notify_worker.ml` inserts with
`Notification.insert tx ...` (a plain `INSERT`) and relies on the job's `~dedupe_key` alone.

## Remediation

Make the consumer's domain write idempotent for the delivered fact, so a redelivery of the same
event does not duplicate it — for example an `ON CONFLICT DO NOTHING` on a natural key, or a
version/`event id` guard — and show in the example that a duplicate delivery is absorbed. Keep
the job's `~dedupe_key`, which already holds. Do not weaken the outbox contract to avoid
duplicates; the contract accepts them and the consumer must tolerate them.

## Acceptance criteria

- Delivering the same fact twice leaves exactly one domain row and one independent effect, and
  the fact itself is still acknowledged.
- The example's migration and `lib/notification.ml` carry whatever key the guard needs.
- The runnable example (or the tutorial's worker section) shows the guard, so an app author sees
  how a duplicate is absorbed.
- `FEAT-120`'s record is updated to cite the fixed behaviour on its next run.

**TypeScript parity (DEC-022):** check the TypeScript demo's consumer against the same
duplicate-delivery expectation and record the verdict or a tracking ticket.

## Completion notes (2026-10-01)

**Premise:** confirmed — `examples/pluto/lib/notification.ml` inserted with a plain `INSERT`
and the table had no key the consumer could dedupe on; FEAT-120's record shows the duplicate
notification from a redelivered fact.

### What landed

- `examples/pluto/db/migrations/0004_notifications_charge_id_unique.sql` and the scaffold's
  `0003_notifications_charge_id_unique.sql` put a unique index on `charge_id`.
- Both `lib/notification.ml` files insert with `ON CONFLICT (charge_id) DO NOTHING`, so the
  consumer's domain write absorbs a redelivered fact. The job's `~dedupe_key` already held and is
  unchanged; the outbox still publishes at-least-once, so a duplicate *fact* remains a legal
  outcome — only the domain row and the effect are now single.
- The migration counts in `cli/test/test_workspace_model.ml` (pluto → 4) and
  `cli/test/test_scaffold.ml` (scaffold → 3) are updated.
- `docs/guides/TUTORIAL.md` § The worker states why the insert is idempotent.

### Acceptance evidence

Ran the example's own worker against a fresh database (the four migrations applied; the unique
index present) and an isolated broker, then delivered the same fact twice:

```text
Produced to partition 1 at offset 0 ... -k d1
Produced to partition 1 at offset 1 ... -k d1

notifications=1
jobs=1
outbox=0
sol_worker_messages_total counter=1 labels={status=ok}   (both deliveries)
```

One domain row, one effect, both facts acknowledged. `FEAT-120`'s record cites the fixed
behaviour; a re-run to record the duplicate-delivery row as PASS is the next qualification
run's job, not this ticket's.

### Deviations and notes

- The scaffold template is fixed too, because it is what an app author copies; its stub consumer
  does not yet use `sol-jobs`/the outbox, which is EXP-025's wider drift.
- `internal/fixtures/venus`'s notify worker has the same plain insert and is **not** changed
  here; it is an internal fixture, and the finding is about the representative example.

**TypeScript parity (DEC-022):** the TypeScript worker's consumer has the same question and no
