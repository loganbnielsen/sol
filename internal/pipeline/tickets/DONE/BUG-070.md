Preserve inbound trace context in the TypeScript order example

**Depends on:** None.

**Premise verified (2026-09-28):** Read the implementation at `examples/pluto/app/demo_ts/order_svc/src/index.ts:119-142; internal/specs/framework-conventions.md:34` and its representative callers/tests on origin/main `6a7b1fb5`. The described boundary remains present.

## Problem

The order route starts receive_order without extracting the incoming traceparent. Kafka propagation then forwards a newly rooted trace, severing caller-to-service-to-worker continuity. Provider registration alone does not supply HTTP instrumentation.

## Remediation

Extract the incoming carrier using the existing OpenTelemetry propagation API and pass the resulting context to span creation. Keep the existing Kafka header propagation.

## Acceptance criteria

- An incoming valid traceparent produces the same trace ID in the service span and emitted Kafka header; absent/invalid headers start a valid new trace. Update runnable demo verification and record the OCaml/TypeScript capability verdict.
- Update a runnable example/demo for application-facing behavior, or record why this is an internal-only refactor.
- Record the per-language capability verdict for framework/application contracts, or explain why language parity is unaffected.

## Completion (2026-09-29)

- **Premise re-verified** at origin/main `788e688d`: the `/orders` handler called `tracer.startSpan("receive_order", { kind: SpanKind.PRODUCER })` with no parent, so every inbound `traceparent` was discarded and the Kafka message carried a freshly rooted trace. Confirmed that `NodeTracerProvider.register()` (sdk-trace-node 2.11.0) installs the default `CompositePropagator` with `W3CTraceContextPropagator`, so `propagation.extract` is live without further setup.
- **Fix** (`examples/pluto/app/demo_ts/order_svc/src/index.ts`): `propagation.extract(context.active(), req.headers)` feeds the span as its parent context; the existing `traceparentOf(span)` Kafka header is unchanged, so the emitted header now carries the caller's trace id.
- **Verified**: `npx tsc --noEmit -p order_svc/tsconfig.json` clean against `npm ci`'d dependencies. A throwaway `node` check (registering `NodeTracerProvider`, then starting the span with and without the extracted carrier) observed:
  `trace continuity verified: inbound 4bf92f3577b34da6a3ce929d0e0e4736 preserved (header 00-4bf92f3577b34da6a3ce929d0e0e4736-2d2ff5bba8c6a9e6-01), absent/invalid start fresh traces`
  **Mutation-checked**: replacing the extracted carrier with `context.active()` makes that check fail with `joined trace id was 11eb627696bbc830db8f38b95ab99e2f` (a fresh trace), and the no-parent/invalid-parent cases assert a new valid 32-hex trace id.
- **Runnable demo verification.** `examples/pluto/app/demo_ts/README.md` § Run it locally now shows a `traceparent`-carrying `curl` plus the exact Tempo query (`curl http://localhost:3200/api/traces/<id>` piped to `jq`) that must list both `order-svc-ts` and `fulfillment-worker-ts`. The durable check is in `.github/workflows/ci.yml` `golden-path-smoke-ts`: the smoke request now sends a chosen `traceparent`, and after the Postgres assertion the job polls Tempo for that trace id and fails unless both services appear — i.e. the pre-fix behaviour (two rooted traces) fails the job.
- **OCaml/TypeScript verdict.** The contract was already stated language-neutrally in `internal/specs/framework-conventions.md` ("W3C `traceparent`: read from incoming HTTP headers and Kafka message headers, and written on outgoing peer calls and produced messages") and `Sol_svc` already extracts it into `Request.trace_ctx` (DEC-022, `docs/reference/runtime.md`). The gap was in the TypeScript example, not the convention: provider registration alone supplies no HTTP instrumentation, so the example now extracts explicitly. `@sol-fab/kafka`/`@sol-fab/obs` keep the Kafka-side propagation; worth noting for FEAT-080's capability inventory that an automatic HTTP-extraction hook in `@sol-fab/svc` is what would make this true "for free" rather than per-handler.
