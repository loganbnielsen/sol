Route source-topic decode failures to the DLQ when one exists; make ack-and-drop an explicit opt-in

**Depends on:** None.

**Finding:** FND-0049 (`internal/pipeline/audits/findings/`).

**Decision:** recorded as step 6 ("Runtime track (G)") of `internal/pipeline/audits/HARDEN-004-handoff.md`: *"source-topic decode failures go to the DLQ where one exists, ack-and-drop only as explicit opt-in."* That supersedes the BUG-028 non-goal carve-out (`sol-worker.md:258`).

**Premise verified 2026-09-23** against `origin/main @ f3e9480b`: `default_on_decode_error` (`kafka_service.ml:306-310`) acks and drops, and `Kafka_service_retry_topics.consume` passes source decode errors to it even though `dlq_topic_name` exists.

## Problem

Under `Retry_topics`, a source-topic record that fails to decode is acked and dropped although a group-scoped DLQ is provisioned. A producer deployed with an incompatible schema makes every consumer ack through the topic; the only trace is `sol_worker_decode_errors_total`. `Worker.Make*` offers no override.

## Remediation

In `Retry_topics` mode, route source decode failures to the DLQ with the `X-Sol-Decode-Error` diagnostic header (reuse `route_retry_decode_error`'s relay shape), acking only after the publish succeeds. Expose the decode policy on `Worker.Make*` (`Dead_letter` default when a DLQ exists; `Skip` as explicit opt-in). Under `In_memory` (no DLQ), keep skip-and-ack but make it explicit in the API and docs. Update the acknowledgement-ownership invariant in `sol-worker.md`.

## Acceptance criteria

- Test: under `Retry_topics`, an undecodable source record is published to the DLQ with raw payload, key, headers and the decode diagnostic, and acked only after the publish succeeds; a publish failure leaves it unacked.
- Test: the explicit skip opt-in still acks and drops.
- `sol-worker.md` / `kafka-eio-service.md` invariant text updated.
- TS parity: record the `@sol-fab/worker` verdict or a tracking ticket (DEC-022).
- Demo/example: the retry demo shows the DLQ path, or completion notes say why not.

## Completion notes (2026-09-24)

Premise re-checked against `origin/main @ 4cafc74a`: `Kafka_service_retry_topics.consume`
still passed source decode errors to `default_on_decode_error` (log, ack, continue).

- New `Kafka_service.decode_error_policy = Route_to_dlq | Ack_and_drop`, replacing
  `consume_partitioned`'s `?on_decode_error` callback with `?decode_error_policy`.
  Defaults: `Route_to_dlq` under `Retry_topics`, `Ack_and_drop` under `In_memory`.
  `Route_to_dlq` under `In_memory` is a `Consumer_error` (there is no DLQ).
  `Kafka_service.consume` (no retry strategy) keeps `?on_decode_error`.
- The retry-topic decode route is generalised as `Retry_topics.route_decode_error
  ~stage:(`Source | `Retry)` (and `decode_failure_message`), so both stages use one
  relay shape: raw payload, key and headers, plus `X-Sol-Decode-Error` and
  `X-Sol-Origin-Group`, acked only after the publish succeeds.
- `Worker.Make_with_retry.run` takes `?decode_error_policy` (re-exported type);
  `Make`'s doc states that it acks and drops (no DLQ).
- `sol_worker_decode_errors_total` still counts every source decode failure. Its
  help text, the log line (`routing message to the DLQ` vs `skipping message`),
  the `SolWorkerDecodeDrops` alert text (`main.tf`), `alert-runbooks.md` and
  `observability-backends.md` now describe both dispositions. The runbook's
  relay-failure paragraph also said a failed retry-relay publish leaves the worker
  running; that has been untrue since BUG-043, so it was corrected.
- Tests (broker-backed, `test_kafka_service_integration.ml`, "decode_error_policy"):
  Retry_topics dead-letters an undecodable record with payload, key, header,
  diagnostic and origin group; the `Ack_and_drop` opt-in skips it and nothing
  reaches the DLQ; `Route_to_dlq` under `In_memory` is refused. The unit tests for
  "publish failure does not ack" and "publish before ack" cover the shared route
  function.
- Mutation checks (each built and failed the intended test): default flipped to
  `Ack_and_drop` failed test 0; `Route_to_dlq` acking and dropping failed test 0;
  the `In_memory` refusal removed failed test 2 (that test is bounded by a timeout,
  so a regression fails instead of hanging).
- Specs: `sol-worker.md` (the acknowledgement-ownership invariant no longer carves
  out source decode errors, plus error-handling and signature) and
  `kafka-eio-service.md` (type, signature, Retry_topics doc).
  `check_framework_doc_signatures.sh` passes.
- **Demo/example:** `internal/fixtures/local-demo/bin/retry_demo.ml` now publishes
  one undecodable record and reads it back from
  `sol-demo-jobs.sol-demo-retry-worker.dlq` with its `X-Sol-Decode-Error` header.
  Run locally against Redpanda, it printed
  `[dlq] sol-demo-jobs.sol-demo-retry-worker.dlq key=job-X X-Sol-Decode-Error="wire format: invalid magic byte"`.
- **Language parity:** `@sol-fab/kafka` still acks and drops under `retry-topics`.
  Tracked as FEAT-098.
