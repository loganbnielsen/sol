**Depends on:** None.

## The defect

`Sol_cli_kubectl.presence_of_probe_result` maps **every** non-zero `kubectl`
exit to `Absent`:

```ocaml
| Ok (Failed failure) ->
  Absent (Printf.sprintf "kubectl exited %d: %s" failure.exit_code (…))
```

Only the case where `kubectl` could not be run at all (`Error`) becomes
`Uncheckable`. But an unreachable cluster is the common case: `kubectl` runs,
cannot reach the API server, and exits non-zero. `sol logs` and `sol fn run`
then print a definite negative — `Service <name> not found in namespace <ns>` —
for a fact that was never established.

INFRA-063 (FND-0024) introduced the third state and closed the
"kubectl could not be run" case, but its acceptance criterion 1 was "on an
unreachable/absent cluster, `sol logs` and `sol fn run` say they could not
check". This is that criterion, still failing.

## Premise verified 2026-10-02

Against `main @ 2a2c5a7c`, with the kubeconfig pointing at a refused endpoint
(`0.0.0.0:41467`), from a scaffolded workspace:

```text
$ sol local logs --scope payments/charge_svc --no-follow
Grafana logs: http://localhost:3000/explore?…
(couldn't reach http://localhost:3100: connection failed. Falling back to Kubernetes logs for charge_svc...)
Service charge_svc not found in namespace obsdemo-payments.
Run 'sol status' to see deployed services.
```

`kubectl`'s own output in the same session was
`The connection to the server 0.0.0.0:41467 was refused`. `sol status` reported
`UNKNOWN (…connection refused)` for the same cluster, so the two surfaces
disagreed about the same fact.

## Impact

The two commands an operator reaches for when a deploy looks wrong point at the
wrong problem: "the workload was never deployed" instead of "Sol cannot see the
cluster". The command still exits non-zero, so it is a diagnosis defect, not a
false success — but it is the same class as FND-0017 (a denied read shown as
"no events") and FND-0024.

## Remediation

Make genuine absence and uncheckability distinguishable at the probe, without
parsing stderr:

1. In `cli/lib/kube/sol_cli_kubectl.ml`'s `workload_exists`/presence callers,
   probe with `kubectl get <kind> <name> -n <ns> -o name --ignore-not-found`.
   With `--ignore-not-found`, a missing object is a successful, empty read
   (exit 0, empty stdout), so:
   - exit 0, non-empty stdout → `Present`;
   - exit 0, empty stdout → `Absent`;
   - non-zero exit → `Uncheckable` (naming kubectl's own message).
2. Keep the pure classifier (`presence_of_probe_result` or its successor) so it
   is testable without a cluster; extend the existing
   `test_kubectl_presence_classification` with the three cases above.

## Acceptance criteria

1. On an unreachable cluster, `sol logs` and `sol fn run` print a
   "could not check" message naming the reason and never claim the workload is
   not deployed.
2. A genuine `NotFound` from kubectl still says "not deployed".
3. The pure classifier is pinned by a hermetic test covering present / absent /
   unreachable, so the collapse cannot come back.

## Completion (2026-10-02)

Fixed as the Remediation describes, reusing the existing pure `classify` rather
than adding a second stderr parser:

- `Sol_cli_kubectl.probe` now carries the probe's stdout (`Succeeded of string`)
  and `presence_of_probe_result` reads it: empty stdout with a zero exit is
  `Absent`; non-empty is `Present`; a failure whose `classify` is `Not_found`
  stays `Absent`; **every other failure is `Uncheckable`**, naming the reason
  (`the cluster could not be reached`, `the cluster refused the request`, …) and
  the first line of kubectl's own message.
- `cmd_logs.ml` and `cmd_fn.ml` probe with `kubectl get <kind> <name> -n <ns>
  --ignore-not-found`, so a genuine absence is a successful empty read instead
  of a non-zero exit that cannot be distinguished from a connection failure.
- `cmd_target.ml` follows the constructor's new payload.

Verified:

- Build and `dune test cli/test/inline` pass; the updated
  `test_kubectl_presence_classification` covers present / empty-absent /
  unreachable-uncheckable / NotFound-absent / unrunnable-uncheckable, and pins
  that an unreachable cluster is **not** reported absent.
- Behaviourally, against a refused kubeconfig, from a scaffolded workspace with a
  dead Loki base URL forcing the `kubectl` fallback, the real binary now prints:
  `error: could not check whether service charge_svc exists in namespace
  obsdemo-payments: kubectl exited 1 (the cluster could not be reached): …`
  where the pre-fix binary printed `Service charge_svc not found in namespace
  obsdemo-payments.`

Demo/example: none required (internal diagnostic fix). Language parity: none
(see above). Qualification matrix row OB-S3 (`LOCAL`, was `FAIL`) is resolved by
this fix; the observability workstream's run record is unchanged.
