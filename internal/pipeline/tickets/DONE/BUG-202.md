**Depends on:** None.

**Premise (verified 2026-10-04 at `f2eb0eba`):** holds.
`examples/pluto/app/demo_ts/fulfillment_worker/src/jobs.ts` handles
`send_confirmation` by calling `effects.markConfirmed(order_id)` unconditionally, and
`examples/pluto/app/demo_ts/fulfillment_worker/src/db.ts` `markConfirmed` inserts into
`order_confirmations_ts` and sets `confirmed_at` with no `fulfilled_at IS NOT NULL` guard. The
job is enqueued by `POST /orders` and can be claimed before the worker has consumed
`OrderPlaced`, so an unfulfilled order is confirmed.

On the local k3d cluster, TS row B5 (`qual-ts-b5-20261004064725`) reached `fulfilled` and never
`confirmed`; the persisted row shows the confirmation *before* the fulfilment:

```console
$ psql -tAc "SELECT status, accepted_at, fulfilled_at, confirmed_at FROM orders_ts \
    WHERE order_id='qual-ts-b5-20261004064725'"
fulfilled | 06:47:25.262641 | 06:47:25.629533 | 06:47:25.545747
```

`confirmed_at` precedes `fulfilled_at`, and the later `markFulfilled` overwrote
`status` back to `fulfilled`, so the read-back never reports `confirmed`. The worker log shows
the confirmation running first:

```console
{"service":"fulfillment-worker","level":"info","msg":"confirmation sent","order_id":"qual-ts-b5-20261004064725"}
{"service":"fulfillment-worker","level":"info","msg":"job processed","kind":"send_confirmation","status":"ok"}
{"service":"fulfillment-worker","level":"info","msg":"fulfilling order","order_id":"qual-ts-b5-20261004064725"}
```

The OCaml half already implements the contract: `Orders.confirm` refuses an unfulfilled order
(`WHERE ... fulfilled_at IS NOT NULL`), returns an error so the `sol_jobs` runner retries with
backoff, and is idempotent once confirmed (`examples/pluto/lib/orders.ml`,
`examples/pluto/lib/orders_jobs.ml`). The TypeScript half is the divergence.

## Remediation

`fulfillment_worker/src/db.ts` `markConfirmed` mirrors `Orders.confirm`: a missing order throws,
an already-confirmed order is a no-op, an unfulfilled order throws (so `@sol-fab/jobs` retries
with backoff), and a fulfilled order inserts `order_confirmations_ts` and sets
`confirmed_at`/`status` under the `fulfilled_at IS NOT NULL` guard.

## Acceptance criteria

- Confirming before fulfilment is refused and records no `order_confirmations_ts` row; once the
  order is fulfilled the confirmation succeeds and the read-back is `confirmed`.
- `examples/pluto/app/demo_ts/test/scenario.test.ts` proves it, and the new test fails on the
  old unguarded `markConfirmed` for the reason under test.
- Demo/example coverage: this *is* the TypeScript reference example; VERIF-027 row B5 is rerun
  against the rebuilt candidate.
- Language parity: brings the TypeScript confirmation into behavioural parity with the OCaml
  half (`Orders.confirm`), which already had the guard.
