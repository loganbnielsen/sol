## Question

For resources Terraform is **configured to delete** (not `ABANDON`, `skip_destroy`, `skip_delete` or equivalent), does a normally completed successful `terraform destroy` plus empty state establish Terraform's side of the destroy postcondition? This decision gates every deletion in the plan's S5.

## What to establish (primary sources, at the versions Sol pins)

Provider Delete success/failure contract; asynchronous deletion; state persistence during destroy; failed remote persistence and `errored.tfstate`; interrupted operations; whether Terraform can report success with empty state while the same managed billable resource remains; AWS/GCP exceptions for the kinds Sol's roots declare. Keep separate, and do not count as falsification: intentionally relinquished resources, retained snapshots, controller-created resources, resources removed from state, external/corrupted resources.

Known inputs: every recorded successful destroy was followed by verified absence (`rg -n -i 'terraform-destroy\] ok' docs/qualification` → AWS Run 8, GCP Attempt 4); every residue ever observed was something Terraform did not manage.

## Abandonment inventory and guard

`rg -n 'deletion_policy|skip_destroy|skip_delete|ABANDON' cli/platform/infra` finds exactly one relinquish attribute today: `google_service_networking_connection.sql` (`cli/platform/infra/gcp/main.tf:235`). Each must have declared residue handling; add a CI guard that fails when a new one appears without it.

The decision recorded here, with the evidence (commands and quoted sources). If the premise is falsified for configured-to-delete resources, record the counterexample and stop: the S5 tickets stay in `BACKLOG`. If it holds, promote DOCS-022 and REFAC-093.

## Decision (2026-09-24)

**The premise holds, with four named exception classes, none of which is Terraform misreporting a
deletion.** For resources Sol's roots configure Terraform to delete, a normally completed successful
`terraform destroy` plus empty state is the product-level authority for absence. It means the
provider reported every Delete as successful. Where a provider defines "deleted" as something other
than "gone", that is a declared provider semantic, not a Terraform gap, and it belongs to Sol's
retention/residue handling, not to per-resource re-verification of everything Terraform manages.

Per the stop condition, this was checked for the case "destroy succeeds + state empty +
Terraform-owned resource remains". Two such cases exist in Sol's roots (classes 2a and 2b below).
Both are documented, deterministic provider behaviour that the current per-kind verification would
not be shown to detect either: it has no KMS recipe, and its bucket recipe describes a *live* bucket,
whose answer for a soft-deleted one is not established.
So they are recorded as findings and fixed on their own, not treated as a reason to keep that
verification. **Deletion work may proceed.**

### What Terraform guarantees (primary source)

- **State removal only follows a successful delete.** Terraform v1.9.8,
  `internal/terraform/node_resource_abstract_instance.go` (apply, post-`ApplyResourceChange`): an
  object is dropped from state only in the "non error case, were the object was deleted" (a null new
  value and no error diagnostics). With an error and a null value, *"we'd rather keep the prior state
  so that the error can be corrected on a subsequent run"*. A provider returning a non-null object
  for a delete is itself reported as an error.
- **What "successful" means is the provider's Delete.** terraform-plugin-sdk v2
  `helper/schema/resource.go`: Delete is *"called when the provider must destroy the instance of a
  managed resource"*, and its error return *"will be converted into an error diagnostic"*. The
  provider decides when that is: GKE's delete, for example, returns only after
  `ContainerOperationWait(…, "deleting GKE cluster", …)` (`resource_container_cluster.go`, v5.45.2).
  The other kinds were not individually audited; the qualification record above is the evidence
  that none of them has reported success early.
- Interrupted operations, `errored.tfstate` and failed persistence are covered by the 2026-09-24
  due-diligence investigation (plan § S4 / INFRA-076). None of them produces *success with empty
  state*: they produce failure, a leftover lock, or a local emergency state file.
- Evidence of no counterexample on record: `rg -n -i 'terraform-destroy\] ok' docs/qualification`
  finds AWS Run 8 and GCP Attempt 4, and each was followed by independently verified absence.
  Every residue ever observed was outside Terraform's management: controller load balancers, the
  abandoned peering, snapshots.
- **One observation looks like a counterexample, and was reviewed.** HARDEN-002 Run 5 attempt 1
  (`docs/qualification/2026-09-18-aws-run5-attempt1.md`, "command completion is not infrastructure
  truth") records that *"immediately after Sol reported `Done.`, describe calls still showed 3 EC2
  instances and a NAT gateway, which were gone on subsequent observation"*. The first search above
  missed it: it matched the phase line, not this prose. The record did not capture the objects'
  states. What is established:
  - the NAT gateway's Terraform delete returns only after `waitNATGatewayDeleted`
    (`internal/service/ec2/vpc_nat_gateway.go`, terraform-provider-aws v5.100.0, the locked
    version), so Terraform reported success once the gateway reached its terminal `deleted` state,
    which AWS keeps visible to describe calls for a period;
  - the EC2 instances are not Terraform resources: they belong to the EKS managed node group's Auto
    Scaling group, and terminated instances likewise stay visible to describe calls for a period.

  So the observation fits terminal-state visibility and does not show a Terraform-managed object
  still live after a successful destroy. Because the states were not recorded, this is an
  **inference, not an observation**, and it is recorded as such. The practical rule it leaves for
  qualification inventories is to count an object in a terminal state (`deleted`, `terminated`) as
  absent, and to record its state.

### Exception classes (the only ways "destroy succeeded" ≠ "nothing left")

| # | Class | In Sol's roots today | Billed? | Handling |
|---|---|---|---|---|
| 1 | **Relinquished deletion**: `deletion_policy = "ABANDON"`, `skip_destroy`, `skip_delete` | exactly one: `google_service_networking_connection.sql` (`rg -n 'deletion_policy\|skip_destroy\|skip_delete\|ABANDON' cli/platform/infra`) | the peering is not billed | Residue. **New CI rule** in `check_destroy_completeness.sh`: every such attribute needs a `# residue:` comment naming its handling. Mutation-tested (rejects unannotated `ABANDON` and `skip_destroy`, accepts annotated), and positive-controlled: removing the peering's annotation makes the guard refuse |
| 2a | **Deferred deletion, not billed**: `aws_kms_key` (created by `module.eks` v20.37.2, `create_kms_key = true`, default 30-day window) | AWS root | **No.** AWS KMS pricing: *"There is no charge for customer managed KMS keys that you manage and are scheduled for deletion."* The key is **Pending deletion** and *"cannot be used in any cryptographic operations"* | Accepted. Absence reports and qualification inventories must expect a pending-deletion key and not call it residue |
| 2b | **Deferred deletion, billed**: GCS soft delete on `google_storage_bucket.loki`/`.thanos` (no `soft_delete_policy` declared, so the GCS default applies) | GCP root, when `enable_durable_observability` | **Yes.** GCS docs: soft delete is *"enabled by default … with a default retention duration of 7 days"*, and *"soft-deleted objects continue to accrue storage charges until their retention period expires"*; a deleted bucket is itself soft-deleted and restorable | **Defect** against DEC-033 `destroy_retention: none`: **FND-0057 / INFRA-077** |
| 3 | **Retained backups/snapshots** | AWS final snapshot (DEC-033, observed); Cloud SQL post-deletion backup behaviour **not established** | yes | Retention capability. The Cloud SQL question is open (see Unknowns) |
| 4 | **Controller-created objects** (LoadBalancer, PV disks) | both, via the platform | yes | Residue; prefer prevention before the parent is destroyed |

Classes 1–4 are what the product still observes after destroy (plan § S9). Everything else
Terraform manages is established by the destroy plus the empty-state check.

### Unknowns (recorded, not assumed)

- **Cloud SQL backups after instance deletion.** The GCP root enables automated backups. Google's
  documentation, as read for this decision, did not unambiguously state the default retention and
  billing of automated backups once the instance is deleted. `docs/qualification/gcp-bootstrap-inventory.md`
  already lists "destroy/final-backup semantics" as undecided (item 5). It belongs to INFRA-077's
  investigation or the next GCP run (HARDEN-006), and must be settled before a GCP `none` destroy is
  claimed cost-clean.
