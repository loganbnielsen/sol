id: SEC-011
type: audit-finding
severity: low
title: sol deploy can build and push the migration-runner image when run from a checkout
source: REFAC-139 (moving the deployer's code into cli/lib made the path visible)
---

**Depends on:** None.

`sol deploy`'s migration prerequisite check (AUDIT-069) runs the migration runner as a Job, and when Sol runs from a source checkout the runner image is built and pushed on the way. ADR 0002's identity table says the deployer "must not publish/replace images".

## Evidence

The path, at the REFAC-139 merge:

```
sol deploy (apply, production profile)
  -> Sol_cli_migration_gate.verify
  -> Sol_cli_migration_gate.read_applied
  -> Sol_cli_migration_job.runner_image
       Build_from_source -> Sol_cli_docker.build, Sol_cli_docker.push
```

```
$ rg -n 'Sol_cli_docker\.(build|push)' cli/lib/deploy/sol_cli_migration_job.ml
111:           Sol_cli_docker.build ~tag:image ~dockerfile ~context
119:      Sol_cli_docker.push ~image_ref:image
$ rg -n 'runner_image' cli/lib/deploy/sol_cli_migration_gate.ml
96:  let* image = Sol_cli_migration_job.runner_image ~registry ~workspace ~k8s_name in
```

An installed release takes `Published` (`Sol_cli_platform_assets.migration_runner`: "An installed release uses the image published with it … and nothing else"), so the crossing happens only in checkout mode. `internal/ci/check_publisher_deployer_boundary.sh` checks the deployer's own files by name, so it does not see a call two modules away; this predates REFAC-139 (the path used to run through `Cmd_migrate`).

## Remediation

Decide the question above; then either route checkout-mode deploys to a pre-built runner (and refuse without one), or record the exception in ADR 0002 and in the guard.

## Decision (2026-10-03) — preserve ADR 0002; the deployer never publishes

Question (disposition, 2026-10-03): is Sol's own migration-runner image an
application artifact in ADR 0002's sense? If yes, route checkout-mode deploys to
a published runner (or refuse without one); if not, record the deployer exception
in ADR 0002 and the boundary guard. Consequence: the path builds and pushes the
runner from a checkout, which the deployer row forbids. Surfaced to the operator
as a category-5 decision; not deferred.

Operator decision: **Preserve ADR 0002's invariant that the deployer does not
publish artifacts.** `sol deploy` must consume a pre-built migration-runner image
and fail closed when the required artifact is unavailable, rather than building
and pushing it from a checkout. If the migration runner is genuinely Sol-owned
tooling rather than workspace-specific application code, publish and version it
as part of the Sol release process — that distinction must not grant the deploy
identity registry-write authority. No deployer exception is introduced merely
because checkout mode currently builds the runner. Promoted to
`READY_FOR_ENGINEERING`.

Recorded in `internal/pipeline/audits/2026-10-03_backlog_adjudication.md`.

## Completion notes (2026-10-03)

**Premise verified.** `Sol_cli_migration_job.runner_image` still contained the
`Build_from_source` branch that called `Sol_cli_docker.build`/`push`, reached
from `Sol_cli_migration_gate.read_status` — so `sol deploy`'s migration
prerequisite (and `sol migrate apply <target>`) published the runner whenever
Sol ran from a source checkout, which the deployer row forbids.

**What changed.** Sol never builds or publishes the runner now; it consumes one:

- `Sol_cli_platform_assets.migration_runner_image` (replacing the
  `Build_from_source | Published` variant) resolves a **digest-pinned** image.
  An installed release reads the digest its bundle records, exactly as before.
  A source checkout requires `SOL_MIGRATION_RUNNER_IMAGE` — validated as
  `<image>@sha256:<64 hex>`, so a floating tag is refused — and with neither
  source it fails closed naming both. A set variable is refused on an installed
  release: a release uses only its own assets.
- `Sol_cli_migration_job` lost the embedded runner Dockerfile and both
  `Sol_cli_docker` calls; `runner_image ()` resolves and reports.
  `namespace_and_repository` became `job_namespace` (the k8s name existed only
  to name the image Sol built).
- Because the runner is named rather than built, `sol migrate`'s `--registry`
  flag is gone (it existed only to pick the repository the built runner was
  pushed to). `sol migrate status`/`sol deploy` also no longer need the target's
  registry to run the gate, and `read_applied`/`verify` lost their now-unused
  `~target`.
- `sol assets` reports the runner through the same resolution, so the refusal is
  visible before a deploy.

**The publisher half already existed** (FEAT-101/DEC-049): the release workflow
publishes the runner from `internal/tooling/release/migration-runner.Dockerfile`
and records its digest in the bundle, which `build-release-bundle.sh` refuses to
accept as anything but a digest reference. Nothing in Sol resolves the publisher
identity, per the decision.

**Guard.** `internal/ci/check_publisher_deployer_boundary.sh` no longer checks
three named files: it checks every `cli/lib/deploy/*.ml` (except the local
`sol up` path, which legitimately builds and pushes the workspace's own image),
plus `cmd_deploy.ml` and `cmd_migrate.ml`, and it refuses when the deploy
sources are missing so the check cannot pass vacuously. Its mutation suite now
covers the historical hole (`sol_cli_migration_job.ml`), asserts each mutation
fails *for the boundary reason* rather than any failure, and holds the `sol up`
exclusion as a positive control.

**Cross-stream consequence, filed not absorbed.** Both qualification harnesses
invoke `sol migrate apply <target> --registry …` and run a checkout binary
(`internal/qualification/aws/live-row.sh`, `internal/qualification/gcp/live-qual.sh`),
so they must publish the runner as the publisher and pass its digest. That is
S5 run-procedure work: filed as **INFRA-100** (Depends on this ticket) rather than
implemented here.

**Demo/example coverage.** No app-author surface changed — no `sol.toml` field,
scaffold output, framework primitive or generated manifest. What changed is an
operator input, and it is documented where it is used:
`docs/deployment/migration-ordering.md` states the runner contract and the
fail-closed path, `docs/architecture/devops-pipeline.md`'s in-cluster section no
longer describes a build, and `docs/reference/cli.md` is regenerated from the
commands' own help (the removed flag). `examples/pluto` needs no change: its
local path (`sol local migrate`) never used the runner image.

**Checks.** `dune build cli/`, the full cli inline suite,
`dune fmt`, `internal/ci/check_ocamlformat.sh --all`, the boundary guard and its
mutation suite, and `internal/ci/run_fast_checks.sh` (0/9 always, 0/100 static).
Against the built binary: a checkout reports the new refusal through `sol assets`,
a digest reference resolves and reports "all assets present", and a floating tag
is refused. Local-mode migrations (`sol local migrate`, `sol migrate status`
without a target) are unaffected.

**Not verified here.** The in-cluster Job path (`sol deploy`'s gate and
`sol migrate apply <target>`) needs a cluster and a published runner image; the
resolution and refusal are covered offline, and the end-to-end run belongs to the
qualification campaign once INFRA-100 supplies the runner (HARDEN-007).

**TypeScript parity:** no impact — this is Sol's own tooling and no framework
contract changed.
