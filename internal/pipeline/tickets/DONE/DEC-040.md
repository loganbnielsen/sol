**Audit finding:** `internal/pipeline/audits/findings/FND-0021-disassociated-access-policy-remained-effective.md`

## The falsified assumption

Sol's `De-escalate` phase removes the provisioner's bootstrap access entry with a
Terraform apply (`cmd_cloud_tf.ml`, `deescalate ()` -> `bootstrap_access_vars
~enabled:false`), and the apply's success is the evidence that the privilege is gone.

Live, that assumption was disproved by a different revocation path: an EKS
access-policy disassociation was **accepted**, `describe-access-entry` reported
`accessPolicies: null`, and the cluster's authorizer went on granting cluster-admin for
more than five minutes — established by reading an application's Secrets, from a
principal confirmed at the time of the read. Deleting the access *entry* propagated in
under 45 seconds; the policy disassociation did not.

So: **a control-plane acknowledgement is not evidence that an authorization boundary
has moved.** Anything reasoning from the API's report inherits the error, and this
matters most at exactly the moment the platform is claiming least privilege.

## Decision (2026-09-21)

**Invariant: privilege de-escalation is complete only when the effective authorization
surface demonstrates that the elevated capability is no longer usable.**

1. Sol's `De-escalate` phase verifies the **effective** surface after removing the
   bootstrap access, and `Ready` is not announced until it passes. The check asks the
   component that enforces the boundary — the kube-apiserver's authorizer — for the
   capabilities the bootstrap grant held. It does not ask the cloud API what it
   requested.

   **The probe runs as the principal whose elevation is being removed.** The bootstrap
   elevation is `provisioner_bootstrap_admin`, scoped to the target's
   `provisioner_role_arn`; the probe must therefore assume *that* role and not the
   steady-state `cluster_access_role_arn`. The two are different principals, and
   probing the latter would prove nothing about the former: its refusals would read as
   de-escalation while the provisioner kept the capability — a check that cannot detect
   the privilege it testifies about, which is FND-0021's shape reproduced inside the
   fix meant to catch it.

   So the check also establishes **which principal answered**, from the ARN the
   authorizer resolves:

   | Answer | Verdict |
   |---|---|
   | the expected provisioner ARN, no capability permitted | `Deescalated` |
   | the expected provisioner ARN, a capability still permitted | `Still_elevated`, naming it |
   | a different principal answered | `Undetermined` — the probe establishes nothing |
   | the cluster refused the expected principal | `Deescalated` — the capability needs authentication, so its absence *is* its revocation |
   | the probe could not obtain evidence | `Undetermined` |

   That last row is the one that has to stay precise, because "could not authenticate"
   means two different things:

   | | |
   |---|---|
   | the cluster refused an identified principal | the expected post-de-escalation state → `Deescalated` |
   | STS, token generation, network, API, or any other failure to obtain the evidence | we do not know → `Undetermined` |

   Only the first is evidence. An inability to *measure* is not an observation of
   de-escalation, which is the same rule as everywhere else in this run: the absence of
   evidence must not become evidence of de-escalation.

   A target declaring no `provisioner_role_arn` elevated nothing, and says so out loud
   rather than skipping the check silently.
2. It is **bounded and fails closed**: if the effective surface cannot be shown to be
   de-escalated within the window, the phase fails rather than reporting `Ready` on an
   unverified claim. Access-entry changes are eventually consistent, so a bounded retry
   is expected; an unbounded wait is not, and "the API said so" is not.
3. The rule is stated at the phase rather than the mechanism: a future de-escalation
   that removes a different grant (an access policy, an RBAC binding, an IAM trust
   relationship) inherits the same obligation.

## The qualification-harness lifecycle (INFRA-060 / INFRA-062)

The same reasoning changes how the qualification transport is established. Rather than
narrowing an elevated credential in place and trusting the report:

1. use temporary bootstrap authority to install the qualification RBAC;
2. **delete the elevated access entry** — destruction, not in-place narrowing;
3. verify the elevated capability is gone (the identity cannot authenticate, or the
   authorizer refuses what it used to allow);
4. establish the narrow qualifier entry (`sol:qualifiers`, no EKS access policy);
5. verify the positive capabilities and the negative surface — `portforward` and the
   addressing reads allowed; `secrets`, `exec` and every mutating verb refused.

Step 3 is the point: the qualifier is never used while elevated access remains
effective, whatever the EKS API reports.

## Acceptance criteria

- Every path that revokes privileged access verifies the effective surface before
  declaring the revocation complete, and fails closed if it cannot.
- Regression coverage that a successful control-plane response with a still-effective
  grant **fails** the check (the FND-0021 shape), mutation-verified.
- The qualification transport's establishment follows the destroy-then-establish
  sequence, with the verification recorded as evidence.

**Scope of the first criterion on a destroy path (2026-09-21).** "Every path that
revokes privileged access verifies the effective surface *before declaring the revocation
complete*" binds the **claim of completion**, not every operation that happens to remove a
grant. On `sol cloud destroy` the effective-surface probe runs and its verdict is
**reported**, but it is deliberately not a gate: a destroy does not declare a revocation
complete, it removes the substrate, and the verified absence of that substrate is the
terminal proof -- stronger than the probe. Making the check fatal would violate ADR 0003
invariant 6 and risk stranding billable infrastructure, and the observation runs as the
*provisioner* role while the teardown uses the *cluster-access* role, so a broken
provisioner trust would abort a teardown that would otherwise succeed. The install path,
which does declare `Ready`, keeps the fail-closed check. A reader must not take the
destroy path's probe result as a verified de-escalation.

## Out of scope

ADR 0003's authority model. The model is right; what turned out to be unreliable is how
its completion was confirmed.

## Implementation note (2026-09-21)

`deescalation_verdict` takes the principal and the probes, so the trap is expressible
as a test rather than a comment: `Principal_unexpected` returns `Undetermined`. The
regression case asserting that another principal's refusal is *not* de-escalation is
mutation-verified — rewiring the verdict so an unexpected principal reads as
`Deescalated` fails it with exactly that message.

## Mutation-verification rule (recorded 2026-09-21)

Found by getting it wrong here. A mutant counts as evidence **only if the mutated build
succeeds and the intended test then fails**. Compiler rejection is an *invalid* mutant,
not a killed one — and when a build fails, the test binary that runs is the stale one,
so a "verified" reading taken from its exit code is worthless. Two ways this bit during
this work:

- adding a redundant match arm (rejected as warning 11 under warnings-as-errors, so the
  old binary ran and reported success);
- not checking the build's exit status before believing the test's.

So: mutate the body of the code path that is actually live, confirm the build succeeded,
and only then read the test's result.
