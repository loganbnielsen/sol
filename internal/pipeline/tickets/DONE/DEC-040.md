## The falsified assumption

Sol's `De-escalate` phase removes the provisioner's bootstrap access entry with a
Terraform apply (`cmd_cloud_tf.ml`, `deescalate ()` -> `bootstrap_access_vars
~enabled:false`), and the apply's success is the evidence that the privilege is gone.

Live, that assumption was disproved by a different revocation path: an EKS
access-policy disassociation was **accepted**, `describe-access-entry` reported
`accessPolicies: null`, and the cluster's authorizer went on granting cluster-admin for
more than five minutes — established by reading an application's Secrets, from a
principal confirmed at the time of the read. Deleting the access *entry* propagated in
under 45 seconds; the policy disassociation did not.

So: **a control-plane acknowledgement is not evidence that an authorization boundary
has moved.** Anything reasoning from the API's report inherits the error, and this
matters most at exactly the moment the platform is claiming least privilege.

## Decision (2026-09-21)

**Invariant: privilege de-escalation is complete only when the effective authorization
surface demonstrates that the elevated capability is no longer usable.**

1. Sol's `De-escalate` phase verifies the **effective** surface after removing the
   bootstrap access, and `Ready` is not announced until it passes. The check asks the
   component that enforces the boundary — the kube-apiserver's authorizer, as the
   de-escalated identity — for the capabilities the bootstrap grant held. It does not
   ask the cloud API what it requested.
2. It is **bounded and fails closed**: if the effective surface cannot be shown to be
   de-escalated within the window, the phase fails rather than reporting `Ready` on an
   unverified claim. Access-entry changes are eventually consistent, so a bounded retry
   is expected; an unbounded wait is not, and "the API said so" is not.
3. The rule is stated at the phase rather than the mechanism: a future de-escalation
   that removes a different grant (an access policy, an RBAC binding, an IAM trust
   relationship) inherits the same obligation.

## The qualification-harness lifecycle (INFRA-060 / INFRA-062)

The same reasoning changes how the qualification transport is established. Rather than
narrowing an elevated credential in place and trusting the report:

1. use temporary bootstrap authority to install the qualification RBAC;
2. **delete the elevated access entry** — destruction, not in-place narrowing;
3. verify the elevated capability is gone (the identity cannot authenticate, or the
   authorizer refuses what it used to allow);
4. establish the narrow qualifier entry (`sol:qualifiers`, no EKS access policy);
5. verify the positive capabilities and the negative surface — `portforward` and the
   addressing reads allowed; `secrets`, `exec` and every mutating verb refused.

Step 3 is the point: the qualifier is never used while elevated access remains
effective, whatever the EKS API reports.

## Acceptance criteria

- Every path that revokes privileged access verifies the effective surface before
  declaring the revocation complete, and fails closed if it cannot.
- Regression coverage that a successful control-plane response with a still-effective
  grant **fails** the check (the FND-0021 shape), mutation-verified.
- The qualification transport's establishment follows the destroy-then-establish
  sequence, with the verification recorded as evidence.

## Out of scope

ADR 0003's authority model. The model is right; what turned out to be unreliable is how
its completion was confirmed.
