**Depends on:** None. Refines the hosted provider policy — provider is really a property of an *environment* — and interacts with DEC-008 (hosted isolation) and DEC-004 (hosted vs customer-cloud boundary). The billing model and cost ceilings are platform decisions (DEC-019).

Decide how deployments are triggered, how environments are modelled, and how isolation between them is enforced.

## Decision

**Environments are deployment *targets*, not application concepts, and isolation between them is strict and enforced.**

- **A target is a cluster or cloud account.** Environments never share one. Two environments of the same workspace resolving to the same cluster is a deploy-time error, checked and failed closed.
- **`env` never appears in internal naming.** Namespaces, service names, internal DNS and injected URLs (`CHECKOUT_SVC_URL` and peers) are identical in every environment. FEAT-041's addressing is therefore unchanged.
- **`env` appears in exactly three places:** the target configuration (cluster/account/region, provider, hostname, secrets, size/values); the public hostname at the edge (`acme.com` vs `dev.acme.com`); and a runtime variable handed to the application (`SOL_ENV`) for log/telemetry labels, feature flags, and refusing destructive operations — never for topology.
- **Why:** the same manifests must promote unchanged. Anything that has to be rewritten to move between environments is a divergence point. Safety comes from access separation (a dev deployer holds no prod credentials) and explicitness — baking `env` into names *looks* like protection while still running on one cluster.
- **Selection is explicit and fails closed.** The environment comes from the resolved target; there is no default for anything touching a live environment (local `sol dev up` may default, being ephemeral). `--emit-plan-to` and the dry-run diff record the target.
- **Triggers:** hosted deployments are push-triggered, run by Sol's pipeline. Self-hosted use `sol deploy` from their own CI, or GitOps. `sol deploy` never infers a destination.

**Deliberately not designed for:** running dev-like workloads inside a prod isolation boundary. Customers can do that themselves with the escape hatches; it is not a supported topology and no affordances will be added for it.

## Previews (designed for, deferred)

Previews are non-production, so they do not need per-customer isolation: a **shared Sol-operated cluster with one namespace per preview** is the intended home, keeping per-customer cluster cost for prod alone. This requires a CNI that genuinely enforces namespace isolation — kube-router on k3s does not honour `namespaceSelector` (BUG-024) — which is the one place that finding becomes a security concern rather than a failing test.

State per preview: **ephemeral Postgres and Redpanda, seeded from fixtures by default** — synthetic, deterministic, no PII. Migrations run from scratch, which exercises the same path prod will take. Scrubbed production snapshots are the opt-in upgrade, not the default.

Dependencies: wildcard ingress and certificate for preview hostnames (FEAT-042, FEAT-048); per-preview cost attribution and idle teardown so an abandoned PR does not bill forever.

## The artifact: Sol builds it (Vercel model), and building is billable

**Sol's pipeline performs the build for hosted deployments, and build usage is charged.** The customer pushes; Sol builds the image and deploys the artifact. Source custody for hosted is accepted as part of the service — and it is consistent with the earlier rule that Sol's pipeline is *hosted-only*: a self-hosted customer's source never reaches Sol.

**Why building is worth owning.** It is not only the DX. Owning the artifact is what makes the rest of this decision possible:

- **Immutability and promotion.** A build produces a content-addressed artifact (image digest). "What passed staging" and "what runs in prod" are then the same bytes by construction, which cannot be guaranteed if the two environments build independently.
- **Rollback becomes a repoint**, not a rebuild — the Vercel property that makes rollback fast and safe.
- **Previews become cheap in the right place**: one build, many namespaces.
- **It closes an existing gap**: pinning by digest removes the "fixed `dev` tag means `sol up` doesn't restart pods" problem at the root rather than by forcing a rollout restart.

**What this commits Sol to, honestly.** Building other people's code is the highest-risk infrastructure Sol would own, and the costs are not incidental:

- **Sandboxing untrusted builds.** A customer's Dockerfile runs on Sol's infrastructure. Isolated workers (microVM/gVisor class), no privileged builds, restricted egress, per-build resource caps and timeouts. This is the single largest new risk in the hosted product.
- **A heavier toolchain matrix than Vercel's.** Their builds are commonly seconds of JavaScript; an OCaml service is an opam resolve plus a multi-stage Docker build — minutes and gigabytes. So **build cost is a pass-through with margin, not a profit centre**, and the lever that makes it both cheap and pleasant is **incremental building**: rebuild only the services whose inputs changed (a Sol workspace is already a monorepo of services, so this is natural) plus layer/dependency caching keyed on lockfiles.
- **Secrets and log hygiene.** Builds need build-time secrets (registry tokens, private dependencies) which must be scoped separately from runtime secrets and **redacted from logs** — build logs are the classic place a credential escapes, and Sol would be keeping them (DEC-017).
- **Multi-tenant fairness.** Concurrency caps and queueing per customer, so one customer's build fan-out cannot starve the fleet.
- **A registry story**, which Sol owns per customer since it holds the account.

**Charging follows the ceiling the platform sets:** build minutes become another metered unit alongside egress, requests and storage, bounded by the customer's spend ceiling — and because the customer is the one paying, the ceiling protects them as much as Sol.

**Tier note.** A customer whose compliance posture forbids source leaving their perimeter can still be served by building inside their isolated cluster/account with the same pipeline driving it. That is a per-tier execution target, not a second product — and it stays a documented exception rather than the default path.

## What already exists (reconnaissance 2026-09-11)

The typed half of this decision is built, so what remains is narrower than the criteria below first implied:

- **`Sol_cli_env_target`** — `Local`, `Customer_direct`, `Customer_gitops`, `Sol_hosted`, each carrying exactly the fields its mode needs, so an impossible target cannot be constructed.
- **`env` is a property of the target** (`Sol_cli_config`), with per-environment overlays at `sol/<env>/<provider>/<region>.yml`.
- **Cross-environment references are already rejected** — `uses` refs across environments fail config validation.

**Correction to this ticket's own wording:** an earlier draft of the criteria demanded `sol deploy --env prod` as a *flag*. The implemented design puts the environment in the **target configuration** instead, which is better — the target is the single source of truth for cluster, provider, hostname and secrets, so environment selection cannot disagree with them, and there is no way to name an environment that the target does not already describe. The requirement is therefore "selection is explicit and cannot be inferred", not "there is a flag". No flag is to be added.

## Vocabulary: `local` is not an environment

**`local` names Sol's own ephemeral substrate, not an environment.** It is the *absence* of a target rather than a fourth one: there is no target, no overlay, and consequently no `SOL_ENV` — the environment is deliberately unset locally, which is why application code has to treat "no environment" as a real state.

That makes `local` a **reserved** word:

- **No target may use `local` as its env name.** Config validation rejects it (REFAC-083), because a cluster you run yourself is still a cluster and should be named for what it is (`dev`, `staging`, …). Without that reservation, the one word meaning "no environment" would also mean "an environment".
- **The command that brings the substrate up should use the same word.** `sol dev up` is misleading: `dev` is a common *environment* name, so it reads as "bring up the dev environment", which is a different thing — possibly a real cluster other people are using. REFAC-083 renames it to `sol local up`. The parenthetical in the Decision above ("local `sol dev up` may default") becomes `sol local up`.
- This closes a loop opened by FEAT-059: the destination for the ephemeral cluster is `Sol_cli_kube_destination.local` (context `k3d-sol-local`), named literally because Sol owns that cluster and there is nothing ambiguous to resolve.

**For whoever reaches for a flag:** there is no `--env`, and none should be added. The environment is a property of the resolved target, and the target is the selector — so the collision above is between a *command namespace* and a possible *target name*, not a flag conflict, and adjusting a flag would not fix it.

## Grammar: `sol local <command>` versus `sol <command> --target <name>`

**Decided 2026-09-11. Local operations live under the `local` command namespace; any operation against a configured target requires `--target <name>`; there is no current target and no implicit local fallback.**

```
sol local up | down | status | logs | rollback …   → the Sol-owned local environment (k3d-sol-local)
sol <command> --target <name>                      → a named target, via its configured Kubernetes destination
```

**Why a namespace rather than a flag.** `sol status --local` reads as though `local` were a flag value on a generic Kubernetes command, whereas `sol local status` says **local is a distinct Sol workflow** — which is what it is, and it matches the vocabulary above: no target, no environment, no `SOL_ENV`. It also scales: anything added for the local loop lands under `local` without inventing flags.

Two things are deliberately rejected:

- **Supporting both spellings** (`sol local status` *and* `sol status --local`). Two ways to express one destination is how a CLI accumulates aliases; pick one grammar and keep it.
- **A workspace "current target"** (`sol target use prod`, stored in a file). It buys typing convenience by recreating exactly the invisible state this model removes: `sol target use prod` followed by `sol rollback` is far harder to audit than `sol rollback --target prod` — hardest of all for destructive commands.

The property preserved throughout: **the destination is visible in the invocation.** No ambient kubectl context, no current-target file, and no implicit fallback to local when a target is missing.

## Acceptance criteria

- Internal addresses are demonstrably identical across environments — a test asserting equal rendered manifests modulo target and hostname, so "promotes unchanged" is enforced rather than asserted.
- No environment identifier appears in a namespace, service name, or injected internal URL.
- Selection remains explicit: the environment always comes from the resolved target, never from an inferred default.
