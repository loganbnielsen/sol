**Depends on:** None.

## The defect

`platform/cloud/modules/platform/main.tf`'s `SolKafkaConsumerLagHigh` rule fires on
`redpanda_kafka_consumer_group_lag > 10000`. Redpanda **does not expose that
metric**. Against Redpanda v26.2.2:

```text
$ curl -s localhost:9644/public_metrics | grep -c '^redpanda_kafka_consumer_group_lag'
0
$ curl -s localhost:9644/public_metrics | grep '^# HELP' | grep -i kafka | awk '{print $3}'
redpanda_kafka_consumer_group_committed_offset
redpanda_kafka_consumer_group_consumers
redpanda_kafka_consumer_group_topics
redpanda_kafka_max_offset
redpanda_kafka_records_fetched_total
redpanda_kafka_records_produced_total
redpanda_kafka_replicas
redpanda_kafka_request_bytes_total
redpanda_kafka_request_latency_seconds
redpanda_kafka_under_replicated_replicas
```

The internal `/metrics` endpoint has no lag metric either. Scraping the broker
with Prometheus and evaluating the rule's own expression:

```text
$ curl -s --get localhost:9190/api/v1/query --data-urlencode 'query=redpanda_kafka_consumer_group_lag'
→ 0 series
```

So the rule can never fire, even on a target that exposes a Redpanda scrape —
the documented "silent until scraped" caveat is not the whole story.

A second defect is in the same rule: its annotations render
`{{ $labels.group }}` and `{{ $labels.topic }}`, but the metrics carry
`redpanda_group` and `redpanda_topic`, so a firing alert would name nothing.

The docs repeat the wrong signal:
`docs/deployment/observability-backends.md` and
`docs/deployment/alert-runbooks.md` both list
`redpanda_kafka_consumer_group_lag`.

## Remediation

1. Replace the expression with a lag derived from the two metrics Redpanda does
   expose, and validate it against the broker's own lag:

   ```promql
   -sum by (redpanda_group, redpanda_topic) (
     max by (redpanda_group, redpanda_topic, redpanda_partition)
       (redpanda_kafka_consumer_group_committed_offset)
     - on (redpanda_topic, redpanda_partition) group_left()
       max by (redpanda_topic, redpanda_partition) (redpanda_kafka_max_offset)
   ) > 10000
   ```

   Verified locally on 2026-10-02: a caught-up group returned `0` (broker
   `rpk group describe` `LAG 0`); after five unconsumed records on the same topic
   it returned `5` (broker `LAG 5`).
2. Fix the annotations to `{{ $labels.redpanda_group }}` and
   `{{ $labels.redpanda_topic }}`.
3. Correct the two documentation tables to the derived signal.

## Acceptance criteria

1. The rule's expression references only metrics Redpanda v26.x exposes, and no
   longer references `redpanda_kafka_consumer_group_lag`.
2. The annotations name the labels the expression actually produces.
3. Evaluating the expression against a Prometheus scrape of a real Redpanda
   returns the same lag its own `rpk group describe` reports, for a caught-up
   group and for one with a backlog.
4. The two documentation tables match the rule.
