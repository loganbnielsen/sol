## The gap

`DEC-064` makes Sol's framework/runtime instrumentation the owner of the semantic
workload identity (`workspace`, `env`, `domain`, `service`, `primitive`,
`release`) on every signal, and `OBS-050` delivers it for OCaml: the manifest
injects the six values into the workload's `<name>-env` ConfigMap and
`Sol_obs.of_env` composes them into the Loki stream labels and the OTLP resource
attributes.

The manifest injection is language-neutral, so a TypeScript workload receives the
same `SOL_*` variables. What is missing is the TypeScript side reading them:
`@sol-fab/obs` ([`loganbnielsen/sol-obs`](https://github.com/loganbnielsen/sol-obs))
takes `service` and `labels` from the caller, and the `demo_ts` example passes its
own literals — `service: "order-svc-ts"`, `labels: { team: "demo_ts" }`, and
`initTracing("order-svc-ts", TEMPO_URL)`. So a TS trace still carries
`service.name` chosen by the app and no taxonomy, and its app-pushed Loki stream
disagrees with the pod-label-promoted stream for the same workload.

This is the TS half of the `OBS-050` acceptance criterion 5 verdict
("intentionally deferred"), recorded here rather than left as silent drift.

## What the TypeScript framework would need

1. `@sol-fab/obs` composes the injected identity the way `Sol_obs.of_env` does:
   read `SOL_WORKSPACE`/`SOL_ENV`/`SOL_DOMAIN`/`SOL_SERVICE`/`SOL_PRIMITIVE`/
   `SOL_RELEASE`, use `SOL_SERVICE` as the signal's `service`, and put the other
   five into the Loki push labels and the OTLP resource attributes — with the
   injected values winning over a caller-provided field of the same name, and the
   `service` label equal to the workload's Kubernetes name.
2. The OTLP resource path in `@sol-fab/obs`/the example's tracing setup carries
   those attributes, so a Tempo trace is scoped exactly as an OCaml one is.
3. `examples/pluto/app/demo_ts` (`order_svc`, `fulfillment_worker`) reads the
   injected values instead of hardcoding `order-svc-ts`/`fulfillment-worker-ts`
   and the `team` stand-in, and the `demo_ts` README says so.
4. `docs/deployment/compatibility.md`'s TypeScript row and the DEC-022 parity
   inventory record the verdict.

## Acceptance criteria

- A TypeScript unit run under a Sol manifest emits a trace whose resource carries
  all six identity attributes, with `service` equal to the pod label `service`.
- A TypeScript unit's trace is returned by `sol open traces <scope>` (OBS-045)
  for the same scope an OCaml unit's is: the view selects on
  `resource.workspace`/`resource.domain`/`resource.service`, which this ticket is
  what makes a TS span carry.
- Its app-pushed Loki stream carries the same six labels, so it is selected by
  `sol logs`' `{workspace,domain,service}` query.
- The `demo_ts` example demonstrates it; the completion note names the assertion
  and the file.
- A guard ties the TypeScript identity keys to `Sol_obs.taxonomy` and the
  manifest's `observability_identity`, the same way `OBS-050` ties the OCaml
  side.
