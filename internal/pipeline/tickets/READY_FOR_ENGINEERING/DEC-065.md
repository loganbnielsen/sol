## Decision (2026-10-03)

**Decided by the operator.** `sol plan` cannot see contracts that an
application declares in code (FEAT-116). Rather than teach the plan to parse or
execute application source, the canonical declaration moves back to Sol's
declarative surface, and application code consumes generated bindings:

1. **The declarative Sol contract is the canonical source of truth, not
   application code.** For the properties Sol must reason about — event/schema
   identity, partitions, key semantics, and the other contract facts Sol needs
   to plan and reconcile — the workspace declaration is authoritative.
2. **Generate language-specific bindings from the contract** into a canonical,
   predictable generated destination that application code imports. A developer
   does not independently redeclare generated contract properties in application
   code.
3. **Check the generated bindings into the repository** and enforce them in CI
   by regenerating from the contract and failing when the canonical generated
   files differ. Drift is a CI failure, not a convention.
4. **Keep the declarative surface limited to contract information Sol needs.**
   Application behaviour stays in code; only identity, partitions, key semantics
   and the like are declared.
5. **`sol plan` reads the declarative contract directly.** It does not parse
   application source, and it does not execute an application emitter to
   reconstruct intent.
6. **No separate contract digest** is added unless a concrete provenance gap
   later requires one.

## Reconciliation required

- **BUG-099** rejected writing `partitions`/`key` into `events/<team>/sol.toml`
  because it duplicates executable semantics and needs a synchronisation guard.
  This decision accepts exactly that duplication *with* the guard, and reverses
  the "code is canonical" premise: the contract is canonical and the code is
  generated from it. BUG-099's acceptance criterion is superseded for the
  contract properties the declaration now owns; the part of BUG-099 that is
  about executable-only semantics remains addressed by keeping behaviour in
  code.
- **FEAT-116** becomes the implementation ticket: the declarative surface, the
  generator, the checked-in destination, the CI drift check, and `sol plan`
  reading the contract.
- **FEAT-119** (the language-neutral contract/run projection) must be
  re-examined: now that Sol owns the canonical declaration and can read it
  directly for planning and reconciliation, determine whether the `contract/run`
  path remains necessary or should be folded into the generated-bindings
  mechanism.
- **DEC-022** parity: the same generated-bindings mechanism must serve the
  TypeScript golden path, or the decision must record the TypeScript deferral
  and its trigger.

## Acceptance criteria

- FEAT-116 implements the declarative contract, the generator, the checked-in
  generated destination, the CI drift check, and `sol plan` reading the
  declaration.
- BUG-099's note is reconciled on the record: its premise is superseded for the
  properties the contract owns, with the reason.
- FEAT-119's disposition (keep, fold in, or drop) is recorded.
- Both application languages are addressed with a verdict.

**Demo/example coverage:** `examples/pluto` must show the contract declared and
modified end to end (declare → regenerate → plan reports the change).

**TypeScript parity:** required by the decision; the golden path must cover it
or the deferral and trigger are recorded (DEC-022).

## Disposition (2026-10-03)

Decided by the operator; the implementation is FEAT-116 (promoted to
`READY_FOR_ENGINEERING` in the same pass). This record closes with FEAT-116's
implementation. See
`internal/pipeline/audits/2026-10-03_backlog_adjudication.md`.

## Reconciliation (2026-10-03, ADR 0005)

ADR 0005 fixes the scope of the plan this decision feeds: `sol plan` reads the
declarative contract because that is the Sol-owned boundary. It does not become
a universal plan for the account, and it does not extend Sol's ownership to
infrastructure the user manages outside Sol.
