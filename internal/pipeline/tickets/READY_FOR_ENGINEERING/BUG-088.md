Preserve workspace consumer groups through scoped deploys

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `2485a3af`, `sol_cli_deployment_plan.ml:899-950` derives groups from selected services, while `cmd_up.ml` and `cmd_deploy.ml` check and persist that list via the workspace-wide `Sol_cli_deployment_state` ConfigMap. The source audit records both command paths and an A+B → scoped A sequence.

## Problem

A normal scoped deploy of worker A reports unchanged worker B as a removed consumer group and refuses. Confirming the change writes only A to the workspace guard record, although B remains live. A later change removing B can then bypass the warning. Both commands check the group state before taking the workspace lease, so the check can also become stale before apply.

## Remediation

Compare against and record the complete post-deploy workspace consumer-group set for scoped operations, preserving unaffected groups. Perform the check and state transition under the workspace boundary lease so the decision and apply share one state epoch. Keep explicit confirmation for actual group removals and unreadable-state behavior.

## Acceptance criteria

- With A and B recorded, scoped updates of A and of a non-worker unit succeed without confirmation and leave both groups recorded.
- A real removal of B requires `--confirm-group-change` and, after confirmation, records the new complete set.
- An intervening update between command start and lease acquisition cannot make the check use stale group state.
- Exercise both `sol up` and `sol deploy` command paths. Update a runnable scoped-deployment example or tutorial and record the cross-language verdict.
