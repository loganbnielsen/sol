Read scoped sol up release boundaries under the workspace lease

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `4bde298f`, `cli/bin/cmd_up.ml:370-383` reads `retained_for_plan` before `with_boundary_lease`; `cli/lib/deploy/sol_cli_deploy_run.ml:260-275` is the positive control that reads it after acquiring the same lease. The source audit records the complete interleaving and verification limit.

## Problem

A scoped `sol up` snapshots the current release boundary before it holds the workspace lease. Before it acquires the lease, another deploy or rollback can change the pointer. When `sol up` later acquires the lease, it applies its selected workload and records out-of-scope workload specs and provenance from the stale boundary. The new current release can describe a workspace state that was never applied; rollback to it can restore stale workloads.

## Remediation

Move the retained-boundary read and validation into the `with_boundary_lease` callback, before applying any service. Keep the scoped refusal when the current boundary is unreadable. Read retention's previous pointer under the same lease so the release and pruning decisions share one boundary epoch.

## Acceptance criteria

- Exercise a pointer change after the local command starts but before it acquires the lease; the scoped release inherits the boundary that is current when the lease is acquired.
- A scoped deploy with an unreadable current boundary still refuses before any workload mutation; a whole-workspace deploy still supersedes the boundary.
- The regression exercises command ordering, not only `Sol_cli_release.of_plan_with_boundary` on preselected records.
- Update the runnable scoped `sol up` / rollback example or tutorial to demonstrate the preserved boundary; record the cross-language verdict in completion notes.
