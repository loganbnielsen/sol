A direct deploy, `sol up` or rollback must not overwrite workload Secret values that `sol secret set` owns

**Depends on:** None.

**Finding:** FND-0052 (`internal/pipeline/audits/findings/`).

**Premise verified 2026-09-24** against `origin/main @ fd5c7e0c`. Sol's live render with
`POSTGRES_URL`/`SOL_API_KEY` unset writes both as `""`. Replayed against a disposable
k3s: a deploy after a `sol secret set` rotation restored the pre-rotation credential
and blanked `SOL_API_KEY`.

## Problem

With `Kubernetes_live`, the default for direct and local deploys and hard-coded for
rollback, every apply re-renders `<svc>-secrets` from the CLI's environment. Declared
keys are required from the environment. The defaults `POSTGRES_URL` and
`SOL_API_KEY` become `""` when unset: `sol deploy` checks only `POSTGRES_URL`, and
rollback checks neither. `sol secret set` writes the same objects and is documented as
the create and rotation path. So the next deploy or rollback reverts a rotation to
whatever the deployer's shell holds, or blanks the key. A blanked key breaks every
API-key service's next start.

## Decision and current premise

Re-verified 2026-10-02 against `origin/main @ 9f68429f`: `Kubernetes_live`
render still reads values from the deploy process and includes a Secret in each
workload manifest; `sol up`, direct deploy and rollback apply those manifests.
The overwrite remains real. The September remedy of creating a Secret from the
deploy environment once is superseded by DEC-029's October 1 direction.

Operator confirmed 2026-10-02: ordinary deploy and rollback consume secret
declarations and references, and never own or mutate values. Explicit
`sol secret` operations are the only Sol CLI path that may send plaintext to an
authority. The current Kubernetes Secret path is a maturity-A delivery mechanism,
not the future cross-driver authority or application contract; DEC-029 will
replace it with authority, authorization, projection and `Secret.get` consumption.

## Remediation

Remove value rendering and Secret application from ordinary deploy, `sol up`,
and rollback. Before applying workloads, verify their declared secret
references exist and contain the required non-empty keys; fail closed if they
do not. Keep explicit `sol secret` value writes and update
`docs/deployment/credential-rotation.md` and the tutorial. Do not add a new
provider abstraction before DEC-029's open questions are resolved.

## Acceptance criteria

- Test: after a rotation-shaped change to the live Secret, deploy and rollback
  leave it unchanged, and missing required keys fail before workload apply.
- Test: ordinary deploy render contains no secret values and emits no Secret
  object to apply.
- Demo/example: tutorial secret flow; state it in completion notes.
