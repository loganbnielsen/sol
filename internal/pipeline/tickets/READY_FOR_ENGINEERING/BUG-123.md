**Depends on:** None.

## The defect

`sol logs --no-follow` distinguishes a transport failure from a response it
cannot parse only enough to choose a message; both are rendered through
`Sol_cli_status.unreachable_message`, so a reachable backend that returned a
malformed body is reported as "couldn't reach" it.

Observed 2026-10-02 (`main @ 1eace495`) by pointing `sol logs` at a stub whose
`query_range` body was valid JSON but the wrong shape:

```text
$ sol local logs --scope payments/charge_svc --no-follow --loki-base-url http://127.0.0.1:3301
(couldn't reach http://127.0.0.1:3301: Loki response: a value is not a [timestamp, line] pair. Falling back to Kubernetes logs for charge_svc...)
```

The command *did* reach the backend (`curl` returned HTTP 200 and the body was
parsed as JSON); the failure is a parse failure. The message sends the operator
to the network instead of to the backend's version or response.

## Remediation

1. In `cli/lib/local/sol_cli_loki.ml`, give `fetch_error` a distinct case for a
   malformed response (e.g. `Malformed of string`) instead of folding it into
   `Other`, and return it from `parse_query_range_body`'s error path.
2. In `cli/bin/cmd_logs.ml`, render a malformed response with its own message —
   "Loki returned a response Sol could not read: <reason>" — and keep
   "couldn't reach …" for transport failures only.
3. Pin the distinction with a test at the parser/classifier level (a malformed
   body classifies as `Malformed`, a connection failure as `Connection_failed`).

## Acceptance criteria

1. A malformed-but-reachable response names the parse failure, not
   unreachability.
2. A genuine connection failure still says "couldn't reach …".
3. A test distinguishes the two classifications.

## Demo/example

CLI diagnostic wording; no app-author surface changes, so no example change is
required. State this in the completion note.

## Language parity

No language-parity impact: this is the OCaml CLI's log reader (DEC-022).
