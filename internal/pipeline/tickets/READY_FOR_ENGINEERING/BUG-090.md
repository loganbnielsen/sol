Reconcile consumer-group safety state after rollback

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `2485a3af`, `cmd_rollback.ml:40-91` and `Sol_cli_rollback.execute` restore workloads and the release pointer but never update `Sol_cli_deployment_state`; the release record contains no consumer-group list. Both deploy commands use that separate workspace ConfigMap for the next group-removal check.

## Problem

Rolling back between releases with different workers leaves the consumer-group guard describing the pre-rollback release. The next deploy may warn about an already-absent group or fail to warn about an actual removal, depending on rollback direction. The latter can let a group disappear without `--confirm-group-change`.

## Remediation

Make the restored release's complete consumer-group set available at rollback and update the guard record as part of the verified rollback transition. Do not advance the guard on failed workload or pointer verification; report a failed guard write visibly so the next deploy cannot assume it is current.

## Acceptance criteria

- Roll back A+B to A and A to A+B; after each, the next deploy's removal check reflects the restored workload set.
- A failed rollback leaves the prior guard state, and an inability to write the corrected guard state is reported as an incomplete transition.
- Cover command-level rollback plus the following deploy check. Update the runnable rollback example or tutorial and record the cross-language verdict.
