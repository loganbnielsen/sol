**Depends on:** None.

**Related:** DOCS-019, DEC-031, INFRA-027, OBS-044, OBS-045, FEAT-090, ADR 0003.

## What this is

The review nests a target above the workspace tree
(`Target -> Workspace -> Domain -> svc/worker/fn`) and then addresses the target
through the same selector as everything else. That makes `prod/aws/us-east-1` a
member of the same grammar as `Workspace | Domain | Unit | Resource`, which does
not match the ontology the interface actually has.

The interface addresses three separate things:

```text
target = where?                      prod/aws/us-east-1
scope  = what?                       pluto/checkout_svc
view   = which operational concern?  metrics | logs | traces | infra
```

Nothing requires all three to be present. Infrastructure has a target and a view
with no application scope:

```text
target = prod/aws/us-east-1
scope  = none
view   = infra
```

Service metrics on that target have all three:

```text
target = prod/aws/us-east-1
scope  = pluto/checkout_svc
view   = metrics
```

Local development has a scope and a view with no target.

This is already almost exactly the CLI's shape: the view is the subcommand
(`sol open logs|metrics|dashboard`, plus `traces` from OBS-045 and `infra` from
INFRA-027), the scope is the positional argument where it is the primary axis,
and the target is `--target` where it is secondary. Recording the ontology turns
that coincidence into a rule — and it is what stops a target being added to
`scope` later as a fourth constructor because it looked like one more node in a
tree.

Decide: formalize target/scope/view as three axes, with target deliberately
**not** part of the scope grammar. Record the constraints that follow:

- which views are valid at which scope/target combinations — `infra` at a target
  with no scope; `logs` currently requiring a unit scope (DEC-031); and what each
  invalid combination reports;
- what `--target` means where a command also resolves an observability backend
  from it today (`sol open`, `sol logs`, `sol status` pass it to
  `Sol_cli_observability_url.effective_backend_and_base_domain`), so that
  "where" and "which backend" do not quietly become one concept sharing one flag.

## Evidence (2026-09-18, `main` at 790dc3e8)

The scope type has no target case, and the view is already a separate type
(`cli/sol/lib/sol_cli_open.ml`):

```ocaml
type scope = Workspace | Domain of string | Service of string * string | Resource of string * string
type kind  = Logs | Metrics | Dashboard
```

`kind` is the view axis, carried as a subcommand rather than as a value inside
`scope` — which is the shape this ticket wants to make explicit rather than
incidental.

Targets are addressed by a separate command family (`cli/sol/bin/main.ml`
registers `Cmd_target.cmd` and `Cmd_cloud.cmd` independently of `Cmd_status.cmd`
/ `Cmd_open.cmd`):

```text
$ sol cloud --help | sed -n '/COMMANDS/,/COMMON/p'
       apply […] TARGET
       destroy […] TARGET
       plan […] TARGET
```

`sol open`'s `--target` is not a scope selector today: `cli/sol/bin/cmd_open.ml`
passes it to `Sol_cli_observability_url.effective_backend_and_base_domain`. That
overload — one flag meaning both "where" and "whose Grafana" — is a real input to
this decision.

## Non-goals

- Not the command-line shape (positional vs flag) for a given axis — that is
  DEC-031, which this ticket supplies the rule for.
- Not a target's lifecycle phase — ADR 0003 already defines it.
- Not the infrastructure views' content or telemetry source — INFRA-027.
- Not renaming `workspace`/`domain`/`unit`, and not changing what the scope
  grammar means.
- Not a new command family for target state; FEAT-090 is already constrained to
  extend the existing surface.
- Not deciding that infrastructure is `view = infra` specifically; that is
  INFRA-027's surface to name, under this ontology.

## Acceptance criteria

- The three axes are recorded explicitly, with target outside the scope grammar
  and the reason stated.
- For every view that exists or is planned (`logs`, `metrics`, `dashboard`,
  `traces`, `infra`), the valid scope/target combinations are written down:
  which are valid, which are errors, and what each error says.
- `--target`'s dual meaning (selects a target; resolves an observability
  backend) either gets a stated precedence rule or is split into two inputs,
  with a follow-up ticket filed if it is split.
- A developer adding a new view has a written rule for which axis it belongs to;
  a developer adding a new addressing concept knows why it is not a `scope`
  constructor.
- DOCS-019 states the three-axis model in the architecture doc, replacing any
  implication that a target is a node in the workspace tree.

**Demo/example coverage:** Decision-only ticket; the follow-up implementation
tickets own the runnable examples.

**TypeScript parity:** No language-parity impact — CLI addressing model only.
