## What this is

Sol's commands do not agree on how a scope is written on the command line. Some
take `--scope <domain>/<unit>`; `sol status` and `sol open` take the same
selector as a positional argument. The review's examples assume the flag form
throughout (`sol status --scope payments/checkout-svc`,
`sol open --scope payments/checkout-svc --metrics`), so a reader following the
doc writes commands the CLI rejects.

This is a *shape* decision, not a grammar decision. The selector grammar itself
is already shared — `domain` and `domain/unit` mean the same thing everywhere,
and `Sol_cli_workload_selection`'s own interface calls itself "the one bridge
between discovery and deployment scope". The open question is only which surface
syntax carries it.

DEC-032's three axes supply a rule that makes the current split deliberate rather
than accidental:

> **Each command's primary axis takes the positional argument; every other axis
> is a flag.**

- `sol status` / `sol open` are addressed *by scope*, so scope is positional and
  target is `--target`.
- `sol up` / `sol deploy` / `sol cloud …` are addressed *by target*, so target is
  positional and scope is `--scope`.

That rule is consistent with every command shipped today. Deciding this ticket
means either confirming it and writing it down, or rejecting it in favour of one
of:

1. **Unify on `--scope` everywhere**, moving `sol status` / `sol open` off their
   positional argument. Costs a breaking CLI change, an `examples/pluto` and
   `TUTORIAL.md` pass, and the tests in `cli/sol/test/test_open.ml`.
2. **Unify on the positional form everywhere**, removing `--scope` from
   `sol up` / `sol logs` / `sol deploy` / `sol check` / `sol rollback` /
   `sol local`. Likely wrong: `sol up` and `sol deploy` already take a positional
   target, so a positional scope would be ambiguous with it.

The state this ticket exists to end is neither option being chosen, which is
today's state.

Note the asymmetry any outcome has to preserve: `sol logs --scope` is
deliberately *unit-only* (`cli/sol/bin/cmd_logs.ml` documents that a domain-wide
or workspace-wide Loki query is a different feature), while `sol status` accepts
workspace, domain, unit, and `resource/<type>/<name>`. Unification must keep that
restriction honest rather than silently widen `sol logs`.

## Evidence (2026-09-18, `main` at 790dc3e8)

`--scope` is declared by:

```text
cli/sol/bin/cmd_up.ml:456          [ "scope" ]
cli/sol/bin/cmd_deploy.ml:800      [ "scope" ]
cli/sol/bin/cmd_logs.ml:398        [ "scope" ]
cli/sol/bin/cmd_check.ml:60        [ "scope" ]
cli/sol/bin/cmd_rollback.ml:201    [ "scope" ]
cli/sol/bin/cmd_local.ml:929       [ "scope" ]
```

`sol status` and `sol open` instead declare a positional `SCOPE`:

```text
$ sol status --help | sed -n '/ARGUMENTS/,/OPTIONS/p'
       SCOPE
           Scope to show: omit for the workspace index, 'domain' for one
           domain's services, or 'domain/service' for a single service.

$ sol open logs --help | sed -n '/SYNOPSIS/p'
       sol open logs [OPTION]… [SCOPE]
```

Two parsers, not one: `sol status`/`sol open` call `Sol_cli_open.parse_scope`
(`Workspace | Domain | Service | Resource`), while the `--scope` commands call
`Sol_cli_workload_selection.resolve`. They operate at different layers — one
yields a scope, the other yields resolved services — so neither is simply wrong,
but the user-facing selector strings they accept are declared twice.

## Non-goals

- Not a scope *grammar* change: `domain` and `domain/unit` keep their meaning.
- Not about widening `sol logs` to workspace/domain scope; that restriction is
  deliberate and orthogonal (see OBS-046 for the workspace/domain log link).
- Not an implementation ticket. Code changes follow whatever this decides.

## Acceptance criteria

- The decision is recorded with the chosen option.
- If the primary-axis rule is confirmed, it is written down where a developer
  adding a new command will find it (`cli/sol/` conventions or
  `.claude/CLAUDE.md`), so the next command does not re-guess.
- If either unification option is chosen instead, follow-up tickets are filed for
  the command changes, the `examples/pluto`/`TUTORIAL.md` update, and the
  affected tests — and DOCS-019's examples are updated to match.
- Whichever way it goes, `sol logs`'s unit-only restriction is stated in the same
  place, so a reader does not infer that every command accepts every scope.

**Demo/example coverage:** Decision-only ticket; no demo change in this ticket.
Whichever option wins, the follow-up implementation ticket owns the
`examples/pluto` and `TUTORIAL.md` update.

**TypeScript parity:** No language-parity impact — CLI surface syntax only.
