**Depends on:** None.

## The defect

`sol new workspace` prints a next-steps report: the commands to run, the framework
dependency and how to satisfy it, and the CI/CD notes. It never names
`README.md`, which it just wrote into the same directory — the file that
documents the layout, the framework dependency, and (since REFAC-143) what the
generated Dockerfiles do and why.

That matters more after REFAC-143 removed the Dockerfile comments: an author who
opens the generated `Dockerfile` now sees 15 lines of instructions and no pointer
to the section that explains the glibc pin, where the dependencies come from, the
`opam repository set-url` step or the uid the image runs as. The README is one
directory away and discoverable, but nothing in the scaffold's own output says
so — and the scaffold output is where an author is already reading.

Evidence: the report block at `cli/lib/workspace/sol_cli_cmd_new.ml`, whose
next-steps lines are the commands, the framework note and the CI/CD note. The
string `README` does not appear in that module, and a real `sol new workspace`
run prints no reference to the file.

## Remediation

One line in the report, after the command list and before the framework note,
naming the file rather than restating its content:

```
The workspace README.md documents the layout, the framework dependency and
what the generated Dockerfiles do.
```

Nothing else in the report changes, and no scaffolded file changes: this is a
signpost, not documentation moved again.

## Acceptance criteria

- `sol new workspace`'s report names `README.md`.
- A test asserts that the report names it **and** that the file it names exists in
  the generated workspace, so the pointer cannot dangle.
- No other line of the report changes.
- Demo/example: this is the scaffold surface itself, so `/demo-review` applies —
  a real `sol new workspace` run, and the two personas against the output and the
  workspace it generates.
- Language parity: no impact; no contract or artifact changes.
