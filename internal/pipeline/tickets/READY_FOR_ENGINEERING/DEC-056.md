## Decision

**Decided 2026-09-28** by the operator: **the platform's declared certificates belong in the `Ready`
contract.** Sol declares them unconditionally and exposes no supported no-TLS platform mode, so they are
required platform resources rather than optional external integrations — the lifecycle must not report
the platform `Ready` until the profile's platform-managed certificate path is ready.

The boundary is explicit: **`Ready` covers platform resources Sol declares and controls; it does not
guarantee external or public reachability through infrastructure outside Sol's authority.** In
particular, global DNS resolution and Internet reachability must not become prerequisites for `Ready` as
part of this decision.

Implemented through the existing readiness architecture rather than an ad hoc TLS wait:

- `Sol_cli_platform_tls` declares the certificates the platform requests — name, namespace and
  provenance — the same shape `Sol_cli_platform_storage` uses for the platform's storage requirement;
- `readiness_checks` derives one readiness predicate per declared certificate
  (`kubectl wait --for=condition=Ready certificate/<name> -n <ns>`), so the gate that already refuses
  `Ready` (`sol cloud apply`) now waits for them, provider-neutrally: nothing here is GCP-specific, and
  the AWS path gets the same predicate;
- `internal/ci/check_platform_tls_requirement.py` + five mutations keep the declaration and the platform
  module from drifting apart in either direction — every ingress the module annotates with
  `cert-manager.io/cluster-issuer` must be declared, and every declaration must exist — and refuse a
  readiness gate that stops deriving from the declaration.

Regression coverage: `test_ready_requires_the_declared_certificates` runs the gate over a cluster whose
components are all healthy and whose declared certificates are not — the Attempt 19 sequence — and
requires that the summary is not `Ready` and names the certificates. `test_readiness_fails_each_predicate`
covers the new predicates automatically, because it iterates the whole list.

**Recorded consequence:** a platform whose DNS delegation the operator has not yet published cannot
become `Ready`, and `sol cloud apply` will refuse after the readiness budget
(`SOL_PLATFORM_READINESS_TIMEOUT_S`, 900 s by default) with the certificate named in the reason rather
than a vague timeout. That is the decision's intent — the certificate is a platform resource, and the
usual cause of it never becoming ready is an unpublished delegation or a failing ACME challenge.

## Question

Attempt 17 reported `lifecycle phase: Ready` while the platform's own `argocd-tls` and `grafana-tls`
certificates were `READY=False` and their challenges failing. `Ready` is not a log line: `sol cloud apply`
refuses unless every readiness check passes, so the claim is a product promise. Today that promise is
*"the platform's components are installed, running and addressable"* — ingress-nginx runs and has an
assigned endpoint, every deployment is available, every PVC bound, Redpanda reports healthy — and it says
nothing about a certificate having been issued.

Which of these is the product's answer?

1. **Leave `Ready` as it is and report certificate state separately.** Keep the promise at component
   availability; carry the TLS claim in `sol status`/the qualification ledger; and either remove the
   driver's "provision the platform without public TLS" sentence or make it true.
2. **Include the platform's declared certificates in `Ready`.** A cluster that cannot issue is never
   `Ready`. Cost: DNS-01 cannot validate until the operator publishes the zone's NS records at the
   registrar, so a correctly installed platform waiting on a human would be refused `Ready` unless the
   gate's budget covers that wait.
3. **Make "without public TLS" a real configuration, then gate on it.** The platform would create no TLS
   ingress when the target does not ask for TLS; `Ready` would then require certificate readiness exactly
   when it does. This is the only option that makes the existing refusal sentence accurate, and it
   changes what the shared module renders.

## Options considered (the remedy space)

Pick one, or a fourth answer. The evidence behind each — including why this is a semantic choice rather
than a missing check (the platform requests certificates unconditionally; there is no supported no-TLS
mode; issuance depends on external DNS) — is in `FND-0068`.

**Explicit non-goals:** do not gate the platform *apply* on certificate issuance, do not weaken the
existing readiness checks, and do not settle this as a side effect of implementing `DEC-055` — the TLS
mechanism and the lifecycle's claim are separate changes.

## Acceptance criteria

- The decision is recorded with its rationale.
- The chosen semantics have executable coverage, and a run can no longer claim `Ready` while the platform
  it describes is known to be unable to serve its own endpoints — or the report says plainly that it is.
- If option 2 or 3 is chosen, the unpublished-delegation case is handled explicitly rather than surfacing
  as a failed platform.
- `internal/pipeline/audits/QUALIFICATION_STATUS.md` is updated with the outcome.
