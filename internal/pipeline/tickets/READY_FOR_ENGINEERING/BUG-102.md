Give Kafka workers one durable retry mechanism and retire In_memory

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `7f6aa377`, `Worker.retry_strategy` offers `In_memory | Retry_topics`. `sol-worker.md:102-110` describes `In_memory` as having no DLQ, being "vulnerable to rebalance", and being "the simple/dev option, not the production one". The canonical reference app `examples/pluto/app/comms/notify_worker/bin/main.ml:50`, `internal/fixtures/venus` (`notify_worker/bin/main.ml:72`, `bin/run.ml:164`) all use `In_memory Kafka.Consumer.default_retry`. That policy has `max_attempts = -1` and `max_delay_s = 600` (`kafka-eio` `lib/kafka_consumer.ml`).

## Problem

Sol ships two retry mechanisms with different failure semantics, and its reference application uses the one documented as not for production:

- **A poison message stalls its partition forever.** `In_memory` retries in the partition fiber with the partition paused. With `default_retry` it never gives up, and there is no DLQ to move the record to. With Sol's single-partition topics (BUG-099), that stalls the whole worker, silently apart from logs.
- **Retry state is lost on every restart or rebalance.** It lives only in memory, so attempt counts reset and the record is redelivered from scratch.
- **`Dead_letter` fails closed** under `In_memory`, and `Route_to_dlq` decode handling is refused. The same `W.handle` therefore behaves differently depending on a strategy flag.
- **Dev and prod differ.** "Dev mirrors prod exactly" is a core principle (AGENTS.md), yet the path developers copy from the reference app is not the one the docs say production should run.
- **The API leaks librdkafka-client semantics.** `Kafka.Consumer.default_retry` (unbounded, from the client library) is the value examples pass for a framework-level policy.

## Remediation

Make durable retry-topic delivery the single retry mechanism for `Make_with_retry`. Remove `In_memory` and the `retry_strategy` variant. Give it a Sol-owned default policy with bounded attempts and a DLQ, so a worker needs no strategy argument to be production-correct. Keep `Make` (ack-only) as it is. Update pluto and venus to the one mechanism, and remove the `In_memory`-only branches in `kafka-eio-service`. No compatibility alias.

## Acceptance criteria

- `sol-worker` exposes one retry mechanism with a bounded default and a DLQ. `In_memory` and `Kafka.Consumer.default_retry` no longer appear in Sol's public API or examples.
- In a broker-backed test, a poison record in the reference `notify_worker` reaches the DLQ after the default attempts, and later records keep flowing.
- `Dead_letter` and decode-error handling have one behavior.
- `sol-worker.md`, `kafka-eio-service.md` and the tutorial describe one mechanism. Update pluto/venus and record the TypeScript retry parity verdict in completion notes.
