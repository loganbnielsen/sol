Bound sol-jobs attempts when a job kills its worker process

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `7f6aa377`, `framework/ocaml/sol-jobs/lib/sol_jobs.ml` `claim_q` selects any `pending` row whose lease has expired. It never compares `attempts` with `retry_policy.max_attempts`. The only path to `status = 'failed'` is `finalize_failure`, which runs only when `J.decode`/`J.handle` *returns* `Error`.

## Problem

`sol-jobs.md` promises that "a poison job lands in `'failed'` rather than retrying forever", and that "one bad row can never block any other job's claim". Both are false for a job whose execution ends the process instead of returning. Examples: an OOM kill, a liveness or eviction kill mid-handler, an exception escaping `J.handle`, or a segfault in a C binding.

Each claim increments `attempts`, but nothing reads it at claim time. After `lease_s` (default 300s), the row is reclaimed, and because its `run_at` is oldest (`ORDER BY run_at`) it is claimed first. It kills the worker again, indefinitely. Every kind hosted by that worker stalls while it restarts, and the loop never reaches the documented terminal state.

**Reproduction** (disposable `postgres:16`, `Sol_jobs.Make` with `max_attempts = 2`, `lease_s = 1`, and a handler that SIGKILLs its own process to stand in for an OOM kill; six consecutive worker runs):

- Control, where the handler returns `Error`: the row ends `failed|2|handler failed`.
- Process-killing handler: each run exits 137, and the row reads `pending attempts=1` … `pending attempts=6`. It is never `failed`.

## Remediation

Enforce `max_attempts` at claim time. Implement it with a single atomic statement, so two pollers cannot both act on the exhausted row. For example, move rows whose `attempts` already reached the budget to `'failed'` (with a `last_error` naming the unfinished attempt) instead of handing them to a handler. Decide whether an exception escaping `J.handle` is also caught and recorded as a failed attempt, as `sol-svc` does for route handlers. Keep fenced finalization (BUG-050) intact.

## Acceptance criteria

- The reproduction above ends with the row in `'failed'` after `max_attempts` claims, with no further handler execution. This runs as a regression in the Postgres-backed `sol-jobs` suite that CI already runs.
- Unlimited retries (`max_attempts < 0`) still reclaim indefinitely.
- Two concurrent pollers never both run an exhausted job.
- `sol-jobs.md` describes the crash path. Record the TypeScript parity verdict in completion notes.
