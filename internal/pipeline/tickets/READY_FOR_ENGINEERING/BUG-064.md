**Depends on:** None.

## The defect

The `test` job opens with a toolchain prefix gated `if: needs.classify.outputs.kind != 'docs-only'` -- system
dependencies, the OCaml switch, the opam caches, the pin action, the dependency
install, the product build, kubectl. The guards further down are deliberately
unconditional, several of them because a ticket-only or docs-only change is
exactly their subject (that is the composition BUG-060 and INFRA-066 were built
around). Two of those two decisions are individually right and do not compose:
on a docs-only change the guards run without the toolchain and the artifacts
they invoke.

Observed on a documentation-only PR (`DOCS-025`, run `36346656406`):

```text
step 11  Build: skipped                                     ← gated on `!= 'docs-only'`
step 31  Pipeline ticket validation guard (BUG-060): failure
         [FAIL] soldev is not built at .../internal/tooling/soldev/bin/main.exe
```

`soldev` is the authoritative ticket parser `pipeline validate` reads tickets
with, and `test_pipeline_validate.sh` fails loudly rather than passing vacuously
when it is missing -- correctly, which is why the failure surfaced at all.

The same defect has a second, latent instance the failure above masked:
`check_readiness_invocations.sh` requires `kubectl` (`command -v kubectl`, then it
validates probe argv against the real client), and its mutation test
(`Readiness-probe invocation guard mutation test`) is one of the unconditional
steps, while the pinned kubectl install is gated.

## Remediation

Provide what the unconditional guards need without the conditional product build:

- the toolchain the tooling is built with -- system dependencies, the OCaml
  switch, the opam download cache and the pin action -- becomes unconditional;
- a new unconditional step, `Tooling for the unconditional guards`, installs the
  pin-backed dependency set for `sol.opam` and builds exactly the three targets
  those guards invoke: `internal/tooling/soldev/bin/main.exe`, `cli/bin/main.exe`
  and `cli/test/print_providers.exe`. On a change that already ran the full build
  this rebuilds nothing;
- the pinned kubectl install becomes unconditional, for the readiness mutation
  test;
- the guards' own tooling (pinned Python modules, pinned `shfmt`) moves from two
  inline workflow steps into `internal/tooling/scripts/prepare-guard-tools.sh`,
  which CI and a developer run the same way (see below).

## Regression coverage

`internal/ci/check_unconditional_guard_tooling.py` reads the workflow and asserts,
**derived rather than hard-coded**: every unconditional step whose run reaches a
guard script that invokes a built artifact (`_build/default/*.exe`, or the
`SOLDEV` default) has an earlier unconditional step that builds that exact
artifact; every unconditional step whose reached scripts require a tool
(`command -v <tool>` for the tools a step is expected to provide) has an earlier
unconditional step that *installs* it; and the ticket-validation guard itself is
unconditional. Its mutation test
(`internal/ci/test_unconditional_guard_tooling.sh`) holds six cases, including
that only mentioning a tool does not count as installing it.

## Local-vs-CI tooling contract

The structural Terraform, YAML and Python guard dependencies are pinned in
`internal/ci/requirements.txt`; a distribution whose Python refuses a user install
(PEP 668, as Ubuntu 24.04's does) could not follow the documented
`pip install --user`. `internal/tooling/scripts/prepare-guard-tools.sh` now
provides them the way CI does, falling back to the user site with an explicit
note when pip refuses, and installs the pinned `shfmt`. CONTRIBUTING's *Checks*
section and `AGENTS.md` name it. `test_destroy_completeness_check.sh`, the one
mutation test observed to mislabel a guard that could not run as a guard that
rejected the tree, now checks the import first and names the script.

## Acceptance criteria

- A docs-only or ticket-only PR passes the required `test` check with the guards
  having run: proved end to end by re-running `DOCS-025` after this lands.
- `check_unconditional_guard_tooling.py` fails if the tooling step is gated or
  emptied, if the ticket-validation guard is gated, or if a required tool's
  install step is gated -- and passes on the real workflow.
- Every `internal/ci` guard and mutation test passes locally after
  `bash internal/tooling/scripts/prepare-guard-tools.sh`, with no local-only
  installation beyond it.
- Demo/example: not applicable (CI composition). Language parity: no impact.
