title: Rollback prunes a removed workload's Deployment but leaves its Service, ConfigMap, RBAC and volumes behind

**Depends on:** None.

When a bad deploy adds a workload, it renders, for that workload, a
`ServiceAccount`, a `<name>-env` ConfigMap, a `NetworkPolicy`, and (depending on
the primitive and settings) a `Service`, an `Ingress`, a PodDisruptionBudget, and
one PersistentVolumeClaim per declared volume, in addition to the workload
itself. A rollback to the older release finds the added workload as an
*unexpected* live workload and prunes it — but `Sol_cli_rollback.prune_workloads`
deletes only `kind_resource id.kind`, i.e. the `Deployment`/`Rollout`/`CronJob`:

```ocaml
Sol_cli_kubectl.delete ~ctx ~resource:(kind_resource id.kind) ~name:id.name ~namespace:id.namespace
```

## Impact

The restored cluster is not the recorded release: every auxiliary object the
removed workload created is still present. Most are inert but untidy (a
`Service` with no endpoints, a stale `<name>-env` ConfigMap, an unused
`ServiceAccount`/`NetworkPolicy`). Two are not: a lingering `Ingress` can keep a
hostname bound, and a lingering PersistentVolumeClaim keeps billable storage
alive with no owner, which on a managed cloud is a real recurring cost. The
release record, the pointer and the workload label all say the rollback
succeeded, so nothing surfaces the leftovers.

## Decision (2026-10-02)

Rollback restores the recorded boundary: a workload the target release does not
contain is removed together with the stateless objects Sol rendered for it, and
rollback never deletes storage or secret material.

1. **Pruned**, per dropped workload, by the deterministic name Sol renders: the
   workload itself (`Deployment`/`Rollout`/`CronJob`), `ServiceAccount <name>`,
   `ConfigMap <name>-env`, `NetworkPolicy <name>`, `Service <name>`,
   `Ingress <name>`, `PodDisruptionBudget <name>`, and — when the dropped
   workload is a `Rollout` — the blue-green `Service <name>-active` /
   `<name>-preview` and `Ingress <name>-active`. They are derived from the
   declaration, hold no data, and the next deploy recreates them. The
   `<name>-active`/`<name>-preview` names are skipped when another workload in
   the workspace is named exactly that, so a rollback cannot delete a sibling's
   `Service`. Deletion is `--ignore-not-found`, so an object the workload never
   had is a no-op, and a failed delete fails the whole prune so the
   current-release pointer is not moved.
2. **Never deleted:** `PersistentVolumeClaim <name>-<volume>` and the
   independently managed `<name>-secrets` Secret. Storage lifetime is `DEC-033`'s
   undecided question and rollback does not answer it; this is also the boundary
   the deploy identity can act within, since the `sol-deploy` ClusterRole grants
   no `persistentvolumeclaims` verbs. Leaving the PVCs in place also means a
   service re-added under the same name reuses its data.
3. **Reported:** before deleting a dropped workload, rollback reads its volume
   claim names from the live object, and after a successful restore prints every
   retained `PersistentVolumeClaim` by name. A rollback that dropped a workload
   holding storage therefore never reports itself as a complete restore without
   saying what storage it left behind.

Naming is derived, not guessed: every pruned target is a name Sol's renderer
produces for `<name>`, so an unfamiliar object is never selected.


## Out of scope

Deploy-time pruning generally, and `DEC-033`'s retention semantics — this is
specifically the rollback path dropping a workload the target release does not
contain.

## Acceptance criteria

- The decision above is recorded before implementation.
- A rollback that drops a workload removes the auxiliary objects the decision
  selects, and reports every object it deliberately left.
- The qualification harness's restore case asserts the post-rollback object set,
  not just the workload labels.
