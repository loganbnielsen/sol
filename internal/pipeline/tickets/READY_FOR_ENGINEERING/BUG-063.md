title: pipeline ls calls a worktree with unpushed commits when it is merely behind origin/main

**Depends on:** None.

## The defect

`worktree_snapshot_of_entry` (`internal/tooling/soldev/lib/soldev_merge.ml`) decides
`ws_unpushed` by comparing commit **shas**, not by asking whether there is anything
to push:

```ocaml
let unpushed =
  if upstream_rc = 0
  then (* local_sha <> remote_sha *) ...
  else (* local_sha <> origin/main's sha *) ...
```

So a worktree whose HEAD differs from the ref is annotated "unpushed commits" —
which is also true of a worktree that is simply *behind* main, or whose commits
landed by squash and are therefore not reachable by sha. A worktree created from
an older `origin/main` and never committed to reads as holding unreviewed work,
and `pipeline ls` marks it as needing attention:

```text
$ soldev pipeline ls
  BUG-056  ...  actionable (unpushed commits @ /home/logan/Code/sol-cloud/sol-BUG-056-up-resolved-config)

$ git -C /home/logan/Code/sol-cloud/sol-BUG-056-up-resolved-config rev-list --count origin/main..HEAD
0
```

That worktree held nothing: the branch was never pushed and no PR ever existed for
it. The annotation is what a worker reads to decide whether a ticket has work in
flight, so a false positive either sends them looking for work that is not there
or gets the worktree ignored when it does matter.

## Remediation

Ask git whether there are commits to push: `git rev-list --count <ref>..HEAD` for
the branch's upstream (`origin/<branch>`) when it has one, and for `origin/main`
when it does not. A count of zero means nothing is unpushed, whatever the shas
are. Both current cases are wrong in the same direction, so both change:

- behind `origin/main`, no upstream → today "unpushed"; must be clean;
- behind its upstream → today "unpushed"; must be clean.

Keep the conservative direction when git cannot answer at all (a missing ref, a
shallow clone): report "unpushed" rather than silently clean, because the
annotation's whole purpose is to warn about work that might be lost. Squash-merged
commits will still read as unpushed (they are not reachable from `main`); that is
the same signal a reader would get from `git log main..HEAD`, so change it only if
`git cherry`-style patch comparison is ever warranted.

## Acceptance criteria

- Test, against a real repository built in a temp dir: a checkout *behind*
  `origin/main` with no upstream is not unpushed; one *ahead* of it is; a checkout
  *behind* its own upstream is not unpushed; one ahead of its upstream is; and a
  ref git cannot resolve stays reported as unpushed.
- `pipeline ls` on a worktree that is behind `origin/main` and clean does not
  annotate it.
- No change to what `dirty` means, and no change to any other `ls` annotation.
- Demo/example: not applicable (internal tooling). Language parity: no impact.
