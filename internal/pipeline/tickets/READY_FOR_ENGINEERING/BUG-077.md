Make scoped deployment release records safe for workspace rollback

**Depends on:** None.

**Premise verified (2026-09-28):** Traced `cli/lib/deploy/sol_cli_deploy_selection.ml:158; cli/lib/deploy/sol_cli_deployment_plan.ml:893-941; cli/lib/deploy/sol_cli_release.ml:76; cli/lib/deploy/sol_cli_release_store.ml:record; cli/lib/deploy/sol_cli_rollback.ml:441-447,480,589-626` and representative callers/tests at origin/main `6eb36b2c`. The audit records reproduced behavior, positive controls and practical limits.

## Problem

A scoped deployment stores only selected plan.services and advances the workspace-wide release pointer. Rollback treats those partial workloads as the entire workspace boundary and prunes every other live workload. Updating A can make rollback to that record delete untouched B. This is a documented valid scope causing an outage, not merely a malformed record.

## Remediation

Keep recorded workspace release boundaries complete after a scoped deploy, preserving unaffected workload facts from a validated current boundary. Reject unavailable/inconsistent prior evidence before unsafe mutation. An explicitly typed scope-owned release model is an alternative only if rollback and pointer semantics change coherently; do not leave a partial snapshot masquerading as a full boundary.

## Acceptance criteria

- Deploy A+B, update only A, and roll back to either recorded boundary: B remains present and retains its intended state. Cover an unreadable prior boundary and deliberate full-boundary removal. The test must exercise release recording and rollback selection, not only the surplus predicate. Update a runnable scoped deployment/rollback example.
- Completion notes identify runnable example/demo coverage and the per-language capability verdict, or explain why either is not applicable.
