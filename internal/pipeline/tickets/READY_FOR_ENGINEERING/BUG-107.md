The scaffolded workspace declares one topic name twice, and the two disagree

**Depends on:** None.

## Problem

A newly scaffolded workspace declares the `payments` event's topic name in two
places that do not agree. Both are in `platform/shared/templates/workspace/`:

```text
events/payments/sol.toml   topics = ["{{team}}-{{name}}s"]
events/payments/charged.ml let topic_name = Kafka_service.topic_name_exn "{{name}}-payments-charges"
```

Even if both were substituted with the same values (`payments`, `charged`) the
results differ — `payments-chargeds` against `charged-payments-charges` — and as
written they are also *unsubstituted*: these template files already sit at
concrete paths and keep the placeholders, so the literal text ships. Only
`{{basename}}` is substituted today, for `.opam` files
(`cli/lib/workspace/sol_cli_cmd_new.ml`), so whether `{{team}}`/`{{name}}` are
rendered in `events/` at all is itself a question the fix has to settle.

This is not cosmetic. `Sol_cli_workspace_scan.discover_topics`
(`cli/lib/workspace/sol_cli_workspace_scan.ml`) reads topic names from
`events/sol.toml` and `events/<team>/sol.toml`, so `sol plan` lists a topic that
no unit will ever publish to, and omits the topic the application actually uses.

Found while migrating the topic contract in BUG-099 Part B; it is a correctness
problem independent of that change.

## Remediation

One source of truth for the topic name, and evidence that the two cannot drift.
Either render the workspace template's `sol.toml` from the same value the module
declares, or stop carrying a topic list for events and have the scanner read the
contract where it is declared — BUG-099 settled that the module is the canonical
semantic contract, and `FEAT-116` tracks the general question of how the CLI
inspects contracts expressed in application code.

## Acceptance criteria

- A freshly scaffolded workspace's `sol plan` lists exactly the topic names its
  event modules declare, for the scaffolded `payments` event and for `sol new event`.
- The placeholder question is resolved explicitly: either both template files are
  rendered from the same values, or neither carries placeholders.
- `docs/guides/TUTORIAL.md`'s event section agrees with what the scaffold produces.

## Found alongside: the two format guards disagree about these files

Reported by BUG-099 Part B, which edits both templates. `dune fmt` does not manage
`platform/shared/templates/**` — `dune fmt --preview` prints nothing for those
files — so `internal/ci/check_ocamlformat.sh --all`, which CI runs, never checks
them. The pre-commit `--staged` mode checks each changed file with
`ocamlformat --check`, which does flag them, and both are non-canonical **on
`main` today** (verified: `git show origin/main:…/charged.ml` also fails
`--check`).

The templates' hand-aligned style is deliberate — record fields and `("key", …)`
pairs are column-aligned precisely because a person reads and edits the generated
event — so reformatting them to the janestreet style (`type t = { id : string; … }`,
`Assoc` exploded across lines) would make the scaffold worse. Decide which rule is
right for scaffold templates and make the two guards agree, rather than leaving
editors of these files to bypass a hook that CI does not back.

## Acceptance criteria (additional)

- `--all` and `--staged` agree about `platform/shared/templates/**`: either both
  check those files (and the templates are reformatted, or explicitly exempted by
  an allowlist that both modes read), or neither does.
