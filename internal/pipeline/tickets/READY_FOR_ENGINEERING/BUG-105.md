Stop consumers and every startup from rewriting producer-owned schema subjects

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `7f6aa377`, `Kafka_service.register` (`framework/ocaml/kafka-eio-service/lib/kafka_service.ml:218-286`) runs on every producer *and consumer* startup: `sol-worker` calls it for its source topic (`worker.ml`, both `Make` variants). It PUTs `{"compatibility":"FULL"}` on the subject (`kafka_service_schema.ml:99-115`), then POSTs the process's own `M.schema` as a new version (`:117-139`).

## Problem

Sol's mission is typed event contracts owned by the producing team (`events/<team>/`). The runtime makes every consumer a writer of the producer's contract:

- **A consumer's reader schema becomes `latest`.** Any consumer whose `Message.schema` differs from the producer's registers a new version. Checked on local Redpanda: after the producer registered v1 `{id}`, a consumer registering `{id, note: string}` became v2 and `latest`. No producer emits it.
- **Consumers can veto producer evolution.** Compatibility is then checked against consumer-invented versions. A producer that later adds `note` with a different type is rejected by a schema it never published, and its deploy fails.
- **Every startup overrides operators.** Each restart resets the subject's compatibility to `FULL`, so a deliberate operator setting silently reverts on the next pod start. Verified: `NONE` set by an operator returns to `FULL` at the next startup.
- **Registry writes at runtime.** Every replica needs write access to the registry, and registration is done by whichever process starts first.

## Remediation

Registry writes belong to the contract, not to runtime processes. Register a topic's schema and compatibility level from its declared contract at plan/deploy time, owned by the producing unit. At startup, producers resolve their schema id and fail if the declared schema is not registered. Consumers only verify that their reader schema can read the registered versions (`Schema.check`), and they never register or change configuration. Runtime workloads need read-only registry access.

## Acceptance criteria

- A consumer startup never creates a subject version or changes subject config. A broker-backed test asserts the version list and config are unchanged after consumers start.
- A producer's declared schema is registered by the deploy/contract path. A producer whose schema is not registered fails at startup with a clear error.
- A consumer whose reader schema cannot read the registered writer versions fails at startup.
- Compatibility level comes from the contract and survives restarts.
- Update pluto's contracts/examples and record the TypeScript schema-registry parity verdict (DEC-022) in completion notes.

## Design (2026-09-30, recon + chosen mechanism)

Directive from the operator: keep `MESSAGE.schema` as the single source of truth;
do not duplicate schema JSON into `sol.toml`; do not leave schema-registry
mutation in producer startup; do not add a separately operated `register_schemas`
step. Sol's deployment lifecycle owns registration, via an application contract
projection that Sol consumes, generalizable to the Kafka topic-metadata contract
(partitions/key) and language-neutral.

### Recon (in the tree at `62d76516`)

- `Kafka_service.register` is still the only registry writer and runs for every
  producer *and* consumer startup: `set_subject_compatibility` (PUT
  `{"compatibility":"FULL"}`) then `register_schema` (POST a new version).
  `sol-worker` calls it once per `W.Message`; producer units call it in
  `bin/main.ml`.
- The CLI does not link `kafka-eio-service` and has no registry client.
  `discover_schema_subjects` (`cli/lib/workspace/sol_cli_workspace_scan.ml`)
  derives *subject names* from `events/<team>/*.ml` filenames — it has no schema
  JSON. The plan prints `schema subjects:`.
- `sol deploy`/`sol up` (`cli/lib/deploy/sol_cli_up_execution.ml`) copy the
  workspace, `docker build`/`push` each unit image, then apply manifests;
  `sol plan` is offline by default. `sol local` already runs `dune build` in the
  workspace (`cli/lib/local/sol_cli_local_run.ml`).
- The one-shot in-cluster pattern already exists in
  `cli/lib/deploy/sol_cli_migration_job.ml` (submit Job + ConfigMap, wait, logs).

### Mechanism

1. **Projection, emitted by the application.** A generated executable per
   workspace (`contract/contract.exe`, a sibling of the generated
   `test/test_schemas.ml`) lists every event module and prints one JSON object:
   `{"version":1,"events":[{"module","topic","partitions","keyed","schema",
   "compatibility"}]}`. It reads the framework `MESSAGE` values, so
   `MESSAGE.schema` stays authoritative; the format is a language-neutral wire
   contract a TypeScript projection can emit unchanged.
2. **Sol consumes it.** `sol plan` runs the projection and queries the target
   registry, showing per subject whether the contract is satisfied and what would
   change (read-only; "not checked" when the projection cannot be produced).
   `sol deploy`/`sol up` run it after the image build and **before any workload
   apply**: validate compatibility, then register (PUT `FULL`, POST the declared
   schema) for subjects that need it; any failure stops the deploy before
   rollout. v1 reaches the registry directly (or via `sol local`'s port-forward);
   a one-shot in-cluster contract Job that runs the app image is a hardening
   follow-up for registries not reachable from the operator's machine.
3. **Runtime is read-only.** `Schema.register_contract` is the only write path.
   `Kafka_service.register` (producer) ensures the topic, resolves the registered
   schema id and fails when the declared schema is not the registered one;
   `Kafka_service.verify` (consumer) ensures the topic and runs `Schema.check`,
   never writing. `sol-worker` calls `verify`.
4. **Generalization.** The projection carries `partitions` and `keyed`, so the
   same artifact lets plan/deploy verify the Kafka topic contract (BUG-099), not
   a schema-only special case.

### Implementation plan (each step keeps the tree green)

1. `kafka-eio-service`: `Schema.register_contract` (write),
   `Schema.resolve`/`Schema.verify` (read-only), and
   `Kafka_service.Contract.projection` (serialize a `MESSAGE` list to the JSON
   above). Unit tests.
2. `sol-worker`: call `verify`; spec update.
3. Projection executable in the scaffold template, `examples/pluto`, and
   `internal/fixtures/venus`; Dockerfiles build it.
4. CLI: `sol_cli_schema_registry.ml` (Confluent GET/PUT/POST),
   `sol_cli_contract.ml` (run projection, diff, report); wire `sol plan`,
   `sol deploy`, `sol up`, `sol local up`.
5. Broker-backed tests: consumer startup leaves versions and config unchanged;
   producer with an unregistered schema fails; consumer with an incompatible
   reader schema fails; plan/deploy check-then-register; projection-format
   fixture.
6. Docs (`kafka-eio-service.md`, `sol-worker.md`, `docs/reference/substrate.md`,
   `docs/guides/TUTORIAL.md`, `internal/specs/framework-conventions.md`,
   `CHANGELOG.md`) and the DEC-022 TypeScript verdict.

### Acceptance mapping

- criterion 1 → steps 1, 2, 5; criteria 2 and 4 → steps 3, 4, 5; criterion 3 →
  steps 1, 5; criterion 5 → steps 3, 6.
