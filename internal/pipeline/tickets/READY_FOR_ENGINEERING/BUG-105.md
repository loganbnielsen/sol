Stop consumers and every startup from rewriting producer-owned schema subjects

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `7f6aa377`, `Kafka_service.register` (`framework/ocaml/kafka-eio-service/lib/kafka_service.ml:218-286`) runs on every producer *and consumer* startup: `sol-worker` calls it for its source topic (`worker.ml`, both `Make` variants). It PUTs `{"compatibility":"FULL"}` on the subject (`kafka_service_schema.ml:99-115`), then POSTs the process's own `M.schema` as a new version (`:117-139`).

## Problem

Sol's mission is typed event contracts owned by the producing team (`events/<team>/`). The runtime makes every consumer a writer of the producer's contract:

- **A consumer's reader schema becomes `latest`.** Any consumer whose `Message.schema` differs from the producer's registers a new version. Checked on local Redpanda: after the producer registered v1 `{id}`, a consumer registering `{id, note: string}` became v2 and `latest`. No producer emits it.
- **Consumers can veto producer evolution.** Compatibility is then checked against consumer-invented versions. A producer that later adds `note` with a different type is rejected by a schema it never published, and its deploy fails.
- **Every startup overrides operators.** Each restart resets the subject's compatibility to `FULL`, so a deliberate operator setting silently reverts on the next pod start. Verified: `NONE` set by an operator returns to `FULL` at the next startup.
- **Registry writes at runtime.** Every replica needs write access to the registry, and registration is done by whichever process starts first.

## Remediation

Registry writes belong to the contract, not to runtime processes. Register a topic's schema and compatibility level from its declared contract at plan/deploy time, owned by the producing unit. At startup, producers resolve their schema id and fail if the declared schema is not registered. Consumers only verify that their reader schema can read the registered versions (`Schema.check`), and they never register or change configuration. Runtime workloads need read-only registry access.

## Acceptance criteria

- A consumer startup never creates a subject version or changes subject config. A broker-backed test asserts the version list and config are unchanged after consumers start.
- A producer's declared schema is registered by the deploy/contract path. A producer whose schema is not registered fails at startup with a clear error.
- A consumer whose reader schema cannot read the registered writer versions fails at startup.
- Compatibility level comes from the contract and survives restarts.
- Update pluto's contracts/examples and record the TypeScript schema-registry parity verdict (DEC-022) in completion notes.
