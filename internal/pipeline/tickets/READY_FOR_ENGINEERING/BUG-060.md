**Depends on:** None.

**Related:** INFRA-066 (the ticket-move guard), `internal/ci/check_ticket_transitions.sh`
(the guard that passes such a ticket), FEAT-103 (the ticket that exposed it).

## The defect

Ticket frontmatter is read by two things that disagree about a malformed file:
`soldev` (which parses it as YAML and fails) and the CI guard (which validates
moves and never parses it). A ticket whose frontmatter is not valid YAML is
therefore **invisible** — `soldev pipeline ls` omits it and still exits 0, so a
worker sees a queue that does not contain it — while the guard reports a clean
pass and the PR goes green.

A hand-written `source:` line is enough to do it: a plain (unquoted) YAML scalar
containing `": "` is a syntax error, and quoting *part* of the line does not help
(the quotes are characters inside the plain scalar). That is exactly how FEAT-103
was filed:

```yaml
source: operator review (2026-09-27) of the TypeScript path - "TypeScript has an E2E path but not a real Sol inner loop: users still have to run Node manually, and the live-dev roadmap is OCaml-only"
```

## Evidence (2026-09-27, `origin/main` `2fff2cef`)

```text
$ soldev pipeline check FEAT-103
internal/pipeline/tickets/READY_FOR_ENGINEERING/FEAT-103.md: frontmatter is not valid YAML: error calling parser: mapping values are not allowed in this context character 0 position 0 returned: 0
$ echo $?
1

$ soldev pipeline ls >/dev/null; echo $?
0                      # FEAT-103 is simply absent from the listing

$ bash internal/ci/check_ticket_transitions.sh; echo $?
0                      # the guard CI runs is happy
```

A scan of every ticket's frontmatter with a YAML parser finds 2 of 785
unparseable: FEAT-103 (filed that same day) and `DONE/INFRA-042.md`, which has no
frontmatter block at all — an older, already-merged instance of the same class,
invisible in the same way.

## Remediation

- Make the failure gating and loud, using the parser that already exists rather
  than a second one: `soldev` should fail (non-zero) when it cannot parse a
  ticket's frontmatter, and CI should run that command. `internal/tooling/soldev`
  is built by the `test` job's Build step, which runs before the guard steps, so
  the guard can call it directly. Decide whether that is a new
  `soldev pipeline lint` (a full-tree check with the file named) or `pipeline ls`
  learning to exit non-zero; the former is clearer about intent, the latter is
  free.
- Until then, `internal/ci/check_ticket_transitions.sh` passing a ticket it never
  parsed is the misleading part: its message should say it validates moves only,
  or it should gain the parse.
- Fix `DONE/INFRA-042.md` (give it the frontmatter its siblings have, with the
  fields the era used) or record why it is exempt.

## Acceptance criteria

- A ticket whose frontmatter does not parse fails CI, naming the file and the
  parser's message — reproduced by planting one in the guard's mutation test
  (`internal/ci/test_ticket_transitions.sh` or the mutation test of whichever
  guard gains the check), which must fail without the fix.
- `soldev pipeline ls` either lists every ticket in the tree or exits non-zero
  naming the ones it could not read; it never silently omits one.
- `DONE/INFRA-042.md` parses, or the exemption is recorded in the guard.
- Demo/example: not applicable (internal tooling). Language parity: no impact.
