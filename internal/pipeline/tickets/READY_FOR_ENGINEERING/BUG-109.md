severity: medium
title: soldev merge --pr refuses to queue a PR whose required checks have not registered yet
source: operator-observed while landing DOCS-027/DOCS-028/DOCS-030 and INFRA-096 (2026-09-30)

**Depends on:** None.

`soldev pipeline merge --pr <n>` is documented as the way to queue native squash auto-merge, and
auto-merge is the default landing path. Immediately after a PR is opened — or immediately after a
push to one — `gh pr checks <url> --required` exits non-zero because no check run has registered
yet, soldev turns that into `Checks_unreadable`, and the command *reports and skips* instead of
queuing:

```text
$ soldev pipeline merge --pr 773      # seconds after the PR was opened
[#773]
  could not read the required checks from gh — skipping (https://github.com/loganbnielsen/sol/pull/773)

$ sleep 40; soldev pipeline merge --pr 773
[#773]
  $ gh pr merge '…' --squash --match-head-commit '<sha>' --auto
  GitHub accepted auto-merge
```

Observed three times on 2026-09-30 (`#773`, `#775`, `#776`), each time fixed by a manual retry.
The failure is silent in the sense that matters: the command exits zero, so a caller that does not
read the output believes a merge is queued when nothing was requested. That is the same failure
class as the stale head pin (#773): a read taken too early, at the moment the operator is being
told to queue.

It is not the same as the case soldev correctly refuses: when `gh` cannot be read because of a
credential or network failure, or when the base branch has no required checks configured
(`base_required_checks_configured`), refusing is right.

## Remediation

Distinguish the two readings at `Soldev_merge.required_checks` / `merge_refusal`:

- **checks not reported yet** — `gh pr checks --required` exits non-zero *and* the base branch has
  required checks configured *and* the PR is not a draft: queue the auto-merge anyway. GitHub
  enforces the required checks itself and lands the PR when they pass, which is exactly what
  auto-merge is for; nothing is bypassed by arming it earlier. Say so in the output
  (`required checks have not registered yet — queuing; GitHub merges when they pass`) instead of
  printing a skip.
- **checks genuinely unreadable** (no configured checks on the base, a draft, or a `gh` failure
  that is not "no checks reported"): keep refusing, with today's messages.

Discovering the second state needs `gh`'s actual message ("no checks reported on the
'…' branch" / "no check runs") distinguished from a transport failure. If that distinction cannot
be made reliably from `gh`'s output, the fallback that does not lie is to fail with a non-zero
exit and a message naming the retry, so a caller can never mistake a skip for a queued merge.

## Acceptance criteria

- A PR with no checks registered yet, a non-draft head and a base branch with required checks
  configured is *queued* by `merge --pr`, with output that says the checks have not registered.
- A PR whose base has no required checks configured is still refused.
- A `gh` failure that is not "no checks reported" is still refused, and the command exits non-zero
  rather than reporting a skip as success.
- `test_merge` covers the three verdicts as pure-function cases, and its mutation covers the
  distinction (a fresh-PR reading must not be accepted as "unreadable").
