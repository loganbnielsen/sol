## Question

`sol cloud apply` presents itself as "credentials + target in, usable cloud out", but
it cannot bootstrap a cloud from zero: it refuses to initialize Terraform until the
target declares a state bucket, and a Terraform root cannot create the backend that
stores its own state. AWS resolves this with a separate bootstrap root the operator
must know to apply; GCP has no equivalent at all (`cli/platform/infra/bootstrap/` is
`provider "aws"`).

So: **does Sol grow a named stage that owns durable account prerequisites, and does
`apply` prove a target is executable before spending money — or does the operator keep
supplying those out of band?**

## Options

- **A. Three named stages — `bootstrap → preflight → apply`.** `bootstrap` ensures
  durable account/workspace prerequisites (Terraform state backend; provider
  enablement; any account-level primitive); `preflight` proves a fully resolved target
  is executable and refuses to cross the billable boundary; `apply` owns disposable
  target infrastructure. `destroy` destroys the *target*; durable prerequisites are
  removed only by a separate, explicitly guarded action. **Recommended.**
- **B. Keep provider-specific bootstrap roots.** Mirror AWS's root for GCP and leave
  the knowledge in a runbook: no new CLI surface, no contract change, and the smallest
  step that unblocks a qualification attempt. This is what `HARDEN-004` does **now**,
  and doing it does not prejudge this decision.
- **C. Fold backend creation into `apply`.** Rejected as stated: a root cannot create
  the backend that stores its own state, so any version of this is a hidden pre-step
  with more magic, not less. It also loses the separation between "prerequisites that
  must outlive a target" and "infrastructure a target owns".
- **D. Do nothing.** Keep the checks in documents. Rejected: it is the state that
  produced `FND-0028`, and it makes every fresh project depend on an operator who
  already knows the step.

## Recommendation

**A**, decided as the target contract and implemented outside `HARDEN-004`. Two
properties make it worth the surface area:

- **The preflight is where the value is.** Everything an operator currently checks by
  hand before spending money — credentials reach the account, billing enabled, required
  APIs enabled, state backend present, quotas sufficient (limits **and** usage),
  configuration resolves, identity can impersonate what the install needs, DNS
  configuration valid, deletion policy appropriate — becomes a command that refuses.
  The repository already has this shape twice and both fail closed: `sol check`
  (declaration validity) and the profile preflight (per-profile guarantees). A
  cloud/target preflight is the same pattern applied to the target, and
  "`apply` refuses to cross the billable boundary unless preflight passes" turns the
  qualification workstream's cost rule into product behaviour instead of discipline.
- **The bootstrap stage names the knowledge.** It converts "the operator knows an
  undocumented incantation" into a contract, and makes the provider implementation
  symmetric instead of AWS-shaped.

## Design constraints this decision must preserve

**1. Lifetime distinction — durable prerequisites are not target infrastructure.**

| Lifetime | Members | Rule |
|---|---|---|
| Account / workspace | Terraform state backend; the delegated DNS zone **and its registrar delegation**; bootstrap IAM; provider enablement | A target `destroy` must not remove these, and a run must verify they *survive* teardown rather than assume it |
| Target | VPC/network, cluster, database, NAT, load balancers, ingress, workloads | Must reach provider-side `Absent` with nothing billable retained |

The DNS zone is the awkward case, and its awkwardness is a symptom rather than a
special rule: `DEC-042` had to argue it survives teardown precisely because it is
created by the root that otherwise owns only disposable infrastructure. The state
backend cannot be given that treatment — it necessarily preexists the root whose state
it stores — so the zone's oddity must not be generalised from. A stage-based lifecycle
removes the contradiction rather than documenting it.

**2. Configuration boundary — intent, plumbing, authority.**

| Class | Members | Who supplies it |
|---|---|---|
| Intent | profile, provider, region, project, cluster name, domain | The operator declares it; it *is* the request |
| Plumbing | state bucket naming, registry naming, kube context, issuer selection, retention defaults, standard alert wiring | Sol derives it: these are naming consequences, not policy |
| Authority and accountability | the identities (`provisioner` / `cluster-access` / `deploy` / `operator`), the operator's CIDR, the alert receiver and owner | The operator declares it, always |

**Derivation must never invent an authority grant or an accountability declaration.**
The evidence for that rule is already in the tree: `internal/qualification/aws/run8-aws-target.example.yml`
requires two distinct cluster identities precisely so that a *denied*
`eks associate-access-policy` can be recorded as evidence. A Sol that "helpfully"
derived one identity would erase the observation the qualification exists to make.

Explicitness is preserved by being inspectable, not by being typed: the resolved
configuration must be viewable (the shape `sol plan` already gives the *workload*
plan, and `sol config resolve` would give the *target*), so "Sol derived it" is always
auditable.

## Out of scope

**`Decommission`** — no evidence establishes a requirement, so no such operation is
proposed here. If one is ever added, it must contend with state it cannot clean up
(a delegated zone's registrar NS records live outside every provider API Sol can call)
and possibly the only copy of the state describing everything else; it would have to
refuse what it cannot prove is unshared and unreferenced, and treat a delegated zone as
a hard stop requiring a human. Recorded so a future reader does not add it as an
obvious tidy-up.

## Acceptance criteria

- Each prerequisite is assigned to a named stage, with a provider-symmetric
  implementation path (not one provider's shape copied to another).
- `apply` either preflights and refuses before the billable boundary, or this decision
  records why it does not.
- A target `destroy` provably cannot remove a durable prerequisite, with a test that
  fails if it does.
- A fresh project plus supplied credentials and identity can reach a **planned** target
  using tracked repository artefacts only — the acceptance property
  `internal/qualification/gcp/live-qual.sh` states for itself, raised to the product.
- The configuration boundary above is recorded, including the never-derive list, and
  the resolved configuration is inspectable.

## Decision (2026-09-23): the delegated zone's ownership

Decided, narrowly and without prejudging the bootstrap UX:

> The delegated Cloud DNS zone is a durable prerequisite and must have durable Terraform
> ownership separate from the disposable target cloud state. A target destroy must neither
> destroy it nor remove its ownership. The Attempt-5 zone is **imported into that durable
> owner rather than recreated**, so the delegated NS set is preserved.

**Why the evidence forced it.** Attempt 5 created the zone with the disposable cloud root
and then had to choose between two bad options: let the target's destroy delete a zone
whose registrar delegation Sol cannot repair programmatically (and whose recreation assigns
*different* nameservers, silently), or remove it from state by hand. Neither is
architecture -- and the second is what happened.

**Implementation.** `cli/platform/infra/bootstrap-gcp` -- the root whose lifetime is the
account rather than the target -- declares `google_dns_managed_zone.qualification` behind
`manage_dns_zone`, beside the state bucket it already owned. Both durable prerequisites are
adopted by `terraform import`, which preserves the nameservers. For this target
`create_dns_zone` is false in the target root's variables: two roots must never manage one
zone.

**The durable root is reconciled, not merely checked for presence.**
`cli/platform/infra/bootstrap-gcp` owns the bucket and the zone, so it is an IaC owner: a
target run brings it to its declared state before doing anything else. Presence checking
was adequate while the root's only job was to make a backend exist; it is not adequate now
that the root declares bucket policy and the delegated zone itself, because it leaves
"Terraform declaration" and "live resource" free to diverge while reporting health.

Bootstrap may still use an idempotent presence check **where structurally required** — the
state bucket must exist before Terraform can store state in it, which is the one recursion
a bootstrap root cannot escape — but presence alone is not reconciliation of a
Terraform-owned durable resource.

**A destructive plan stops the run.** Reconciliation may change metadata (bucket labels,
the zone's description) but must never replace or destroy either resource: a recreated zone
gets different nameservers, silently breaking the delegation pasted at the registrar, and a
recreated bucket is the state store for every root. The harness therefore plans with
`-detailed-exitcode`, refuses if the plan contains a replacement or destruction, and leaves
that to a human decision.

**Recorded rather than hidden:** adopting the two resources produced a plan of *0 to add,
2 to change, 0 to destroy* -- the bucket's `sol-role` label and the zone's description,
metadata only. It is **not applied at adoption time**, deliberately: these are live durable
resources and the bucket holds every root's state. It will be reconciled by the next
attempt, because the harness ensures the durable root by applying it -- which is the point
of owning the resources, and worth knowing rather than discovering.

## Completion notes (2026-09-29)

**Resolved by DEC-057, not reimplemented or rewritten.** The question this ticket
opened — whether Sol grows a named stage that owns durable account prerequisites,
and whether `apply` preflights before crossing the billable boundary — is decided
there, together with the rest of the developer-experience contract it belongs to.

What changed by being decided:

- **Option A is accepted, with a wider stage set.** `DEC-057` records
  `bootstrap → preflight → provision → platform → migration → deployment →
  verification → reconciliation`, collapsed for the user into `sol deploy <target>`
  rather than exposed as required knowledge. The `bootstrap → preflight → apply`
  shape recommended here is contained in it.
- **The lifetime distinction in §2 is generalised.** The table here (account/
  workspace vs target) is carried into `DEC-057` §1, and the delegated zone's
  awkwardness is resolved the way this ticket argued it should be: by giving the
  durable prerequisites their own owner rather than special-casing the zone.
- **The `Decommission` non-goal is preserved rather than reversed.** `DEC-057` adds
  `sol uninstall` as the explicit installation-removal operation and keeps the
  zone's external registrar records as a hard stop requiring a human — which is the
  tension this ticket recorded rather than a tidy-up it invited.
- **The acceptance criteria transfer to the implementation.** The preflight-before-
  billable-boundary rule, the "destroy cannot remove a durable prerequisite"
  test, and the provider-symmetric implementation path are now obligations of
  INFRA-096, which is filed against `DEC-057`.

**What is preserved.** The 2026-09-23 decision text above (durable Terraform
ownership for the delegated zone, import rather than recreate, reconcile-not-just-
check, and a destructive plan stopping the run) stands unchanged and is still the
implemented behaviour for the durable root. `DEC-057` extends the ownership rule to
the product; it does not supersede the mechanics recorded here.
