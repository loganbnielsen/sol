Keep migration tables distinct for long workspace names

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `cd3251a5`, `Sol_cli_migration.table_name` can exceed PostgreSQL's default 63-byte identifier limit; `pg-eio` validates identifier characters but no length. The audit report gives two valid, distinct workspace names that PostgreSQL maps to one table.

## Problem

Two workspaces sharing PostgreSQL can use distinct Kubernetes namespaces yet the same migration-tracking table after PostgreSQL truncates their generated table identifiers. A migration version applied by one workspace then causes the other workspace to skip a different migration with that version. Deploy's schema prerequisite can also read the wrong applied-version set. This can leave the second workspace running against an incompatible schema.

## Remediation

Derive a bounded migration-table identifier with a stable distinguishing suffix over the full workspace name, and use it consistently in local migration commands, in-cluster migration Jobs, deploy prerequisites, and rollback checks. Fail clearly if any generated identifier cannot meet PostgreSQL's limit. Pre-alpha permits a direct naming change without a compatibility alias.

## Acceptance criteria

- The 59-`a` plus `x`/`y` pair produces different PostgreSQL identifiers of at most 63 bytes, while the 58-`a` positive control remains distinct.
- Two such workspaces sharing one disposable database can apply different migration version 1 files and independently report both as applied; neither workspace reads the other's migration row.
- All migration call sites use the same table derivation, including deploy and rollback checks.
- Update a runnable shared-database migration example or tutorial and state why the CLI/storage fix has no application-language parity gap.
