**Depends on:** None.

## The problem

When `--image-tag` is omitted, both `sol up` and `sol deploy` default the image tag
to `git_sha ()` (`Sol_cli_command_request.make_up_request` and the deploy request,
`cli/lib/deploy/sol_cli_command_request.ml:52` and `:96`). `git_sha` exists twice,
identically, in `cli/bin/cmd_up.ml:19` and `cli/bin/cmd_deploy.ml:31`:

```ocaml
let git_sha () =
  match Sol_cli_process.run (Sol_cli_process.cmd [ "git"; "rev-parse"; "--short"; "HEAD" ]) with
  | Ok r when r.Sol_cli_process.exit_code = 0 && r.Sol_cli_process.stdout <> "" -> r.Sol_cli_process.stdout
  | _ -> "dev"
```

If git isn't installed, the directory isn't a repository (a CI job without `.git`,
a source tarball), or the command fails for any other reason, the error is
discarded and the tag becomes the literal `dev`. `sol deploy prod/aws/us-east-1`
then pushes and deploys a **mutable, shared tag to a real cluster**, with no
message. Two unrelated builds can overwrite each other's `dev`, and a rollout can
be a no-op because the tag didn't change.

## Remediation

1. One `git_sha` in `cli/lib` (next to the request construction). It returns
   `(string, string) result` carrying git's own error, not a sentinel.
2. `sol deploy` without `--image-tag`, when the SHA can't be resolved, is an error
   that names the cause and says to pass `--image-tag`.
3. `sol up` (local) may keep a fallback, but only with a visible warning on stderr
   naming the fallback tag and why.
4. Consider refusing a dirty tree for `sol deploy`'s implicit tag, or suffixing it
   (`<sha>-dirty`). Decide in the implementation and record why in the completion
   notes.
