type: bug
severity: medium
title: A docs-only change to the generated CLI reference bypasses the guard that keeps it true
source: DOCS-030 (the CLI-reference guard) — found while landing it (2026-09-30)
---

**Depends on:** None.

`docs/reference/cli.md` is generated from the binary's own help, and
`internal/ci/check_cli_reference.py` fails when the page and the binary disagree — an
undocumented command, a command the binary does not register, or a flag a command does not have.

**The guard does not run on the path where the drift can enter.** The classifier treats a change
to `docs/reference/cli.md` as `docs-only`, and the docs-only fast path deliberately skips every
guard. Run rather than reasoned — and note that the script takes a file list, not a path: an unknown
argument makes it emit `source`, which is how a first draft of this ticket quoted an invocation
that does not exist.

```text
$ printf 'docs/reference/cli.md\n' > /tmp/paths
$ internal/ci/classify-changes.sh --files-from /tmp/paths
docs-only

$ printf 'cli/bin/main.ml\n' > /tmp/paths          # positive control
$ internal/ci/classify-changes.sh --files-from /tmp/paths
source
```

The rule is the classifier's own fall-through, where `docs/*` and `*.md` both mean prose:

```sh
    docs/*)                            continue ;;
    internal/pipeline/tickets/*)                continue ;;
    *.md)                              continue ;;
```

and the guard that would catch a hand-edited command row runs only on the other path:

```text
$ grep -n -A 2 check_cli_reference .github/workflows/ci.yml
701-        if: needs.classify.outputs.kind != 'docs-only' || steps.docs_tooling.outputs.cache-hit != 'true'
702:        run: python3 internal/ci/check_cli_reference.py
```

So a PR that hand-edits a command row — the one drift the guard exists to catch — takes the fast
path, where the guard, its mutation test and the product build are all skipped. Landing DOCS-030
recorded this as a known gap.

**The fast path cannot simply run this guard.** It restores a cached *soldev* binary
(`_build/default/internal/tooling/soldev/bin/main.exe`) and never builds `cli/bin/main.exe`, so
there is no binary on that path for the guard to read; `check_unconditional_guard_tooling.py`
fixes the two permitted step conditions, so an arbitrary `always()` step is not available either.

## Remediation

Treat the generated page as an artefact of the code, not as prose: classify
`docs/reference/cli.md` as a source change in `internal/ci/classify-changes.sh`, so a PR touching
it takes the full path where the guard runs. Add the case to `internal/ci/test_classify_changes.sh`
next to the existing `docs/foo.md` docs-only assertions.

The cost is deliberate and worth naming: regenerating the page after a CLI change then runs the
full suite. That is the correct price for touching a generated artefact, and it is the same
reason the page is not hand-maintained.

Do not generalise this to all of `docs/` — the allowlist stays for prose. If a second generated
page appears, it joins this exception, and the classifier should grow a list of generated paths
rather than a special case for one file.

## Acceptance criteria

- `internal/ci/classify-changes.sh docs/reference/cli.md` reports `source`, and
  `test_classify_changes.sh` asserts it (with a prose `docs/*.md` control still `docs-only`).
- A PR that edits only `docs/reference/cli.md` runs `check_cli_reference.py`, demonstrated by the
  guard failing on a hand-introduced wrong row in that PR's own CI, or by the classifier output
  plus the step condition in the completion notes if that is not practical to stage.
- The prose allowlist is unchanged: `docs/foo.md`, `docs/architecture/deep/nested.md` and a
  ticket markdown file still classify as `docs-only`.

## Demo/example coverage

None applies: CI classification and a guard step change no app-author surface — no `sol.toml`
field, framework primitive, generated manifest or CLI command.

**Language parity:** no impact; nothing application-facing changes.
