## Decision (2026-10-01) — Option C

Decided by the operator on 2026-10-01. **Option C: Option A on AWS, Option B on any
provider that has no deploy identity.**

**AWS.** A `sol deploy` run that provisions the environment itself establishes the
*deploy* identity's cluster access for the duration of that run, using the same ephemeral
pattern the provisioning path already uses for its own role
(`Sol_cli_aws_cluster.provisioner_kubeconfig`): a kubeconfig in a temporary file,
`KUBECONFIG`/`KUBE_CONFIG_PATH` scoped to the child processes, removed when the run ends,
never written into the user's home. The run then continues into `platform`, `migration`
and `deployment` unattended, which is `DEC-057` §2's experience and `FEAT-106` AC1.

**GCP, and any provider without a deploy identity.** The run does not degrade to a
stronger identity: it provisions the environment, stops, and names the operator's two
remaining steps — the printed `deploy_kubeconfig_command` and the `kube_context` line to
add — which is today's behaviour. GCP has no deploy principal to establish (evidence
below), and its only cluster-access path impersonates the *provisioner* service account,
which `DEC-034` forbids a deploy from using.

### The shape on AWS

- **Trigger.** The first-run path only: the target declares no `kube_context`, or the
  declared cluster is unreachable, and the run has just provisioned the environment. A
  target that declares a `kube_context` keeps using it — `DEC-020`'s consequence is that
  Sol trusts its own declarative configuration, and the ephemeral path is not a second
  guess at an explicit one.
- **Mechanism.** `aws eks update-kubeconfig --region <region> --name <cluster> --alias
  <cluster>-deploy --role-arn <deploy_role_arn> --kubeconfig <temp>`, with the
  destination's context name being the root's `deploy_kube_context` output
  (`<cluster>-deploy`). The written kubeconfig carries the AWS exec credential plugin
  (`aws eks get-token --role-arn …`), so no static secret is embedded, and the credential
  is the caller's AWS identity assuming a role the operator created and declared.
- **Lifetime.** A temporary file, cleaned up on exit and on failure, exactly as
  `provisioner_kubeconfig` does today.

### Why this is not a widening of authority

Every grant this needs already exists, for this identity, today:

- `platform/cloud/aws/cluster/main.tf:113` creates the EKS access entry mapping
  `deploy_role_arn` to group `sol:deployers`; `platform/cloud/modules/platform/platform_deploy_rbac.tf`
  and the per-namespace `RoleBinding` `Sol_cli_substrate.ensure` applies give it
  namespace-scoped application RBAC, and nothing else (`INFRA-025`).
- The deploy policy contract already allows the discovery call the kubeconfig command
  needs: `LocateTheCluster` grants `eks:DescribeCluster`, `eks:ListClusters`
  (`platform/cloud/aws/bootstrap/main.tf:146`).
- The path is print-only today: `rg -n deploy_kubeconfig_command --type ml` matches only
  error text and a test assertion, so no code assembles a deploy-identity kubeconfig.

So the decision changes *who types the printed command*, not what authority exists, where
it can reach, or whether it persists. An operator who could not assume the deploy role
could not have run that command either; the assumption permission and the role's trust
policy remain theirs to set (`AUDIT-072`: Sol owns the contract, not role lifecycle).
`INFRA-025`'s recorded residual boundary — `rolebindings: create` cannot be
namespace-restricted when bound cluster-wide — is inherited unchanged, because the
identity is unchanged.

### What this does not change

- Sol still does not write the user's `~/.kube/config` or the target file (`AUDIT-072`).
- A deploy still does not fall back to the ambient kubectl context (`DEC-020`).
- The provisioning, cluster-access, deploy and operator identities stay distinct, and no
  option widens any of them (`DEC-034`).
- `DEC-030` (fresh-machine authentication for *operating* an environment) stays open and
  is not answered here. This decision gives a *deploy run* its own access, not the
  operator a persistent one; `sol status`, `sol logs` and `sol migrate` still need a
  declared destination, and `DEC-030` still owns the print-vs-write question for it.

### Options considered

- **Option A — ephemeral deploy-identity access for the run, on every provider.** Chosen
  for AWS; rejected for GCP because there is no deploy identity to establish there. GCP
  would require inventing a deploy service account, its workload-identity binding and its
  cluster RBAC — a `DEC-034`-scale identity redesign, not cluster-access plumbing.
- **Option B — the run stops and names the two operator steps, everywhere.** The fallback
  where no deploy identity exists. Rejected as the sole answer because it makes
  `FEAT-106` AC1 unreachable on the one production-qualified provider, forces a
  target-file edit mid-first-run, and leaves `DEC-057` §2's inline first run undelivered.
- **Sol writes the target file or a persistent scoped kubeconfig.** Excluded before the
  decision: `AUDIT-072` and `DEC-030` both reject Sol writing on the operator's behalf,
  and without a target-file write a persisted kubeconfig is referenced by nothing.

### The evidence the GCP half rests on

- `Sol_cli_provider_capabilities.gcp` declares `installation_identity_contracts = []`,
  `cluster_access_role_arn` returns `Ok None`, and `scoped_identities = []`
  (`cli/lib/cloud/sol_cli_provider_capabilities.ml`); `production_qualified = false`.
- `platform/cloud/gcp/cluster/outputs.tf` has no `deploy_kubeconfig_command`; the only
  cluster-access path is `gcloud container clusters get-credentials …
  --impersonate-service-account <provisioner_service_account>`
  (`cli/lib/cloud/sol_cli_gcp_cluster.ml:85`).

## Status

**Decided 2026-10-01 by the operator.** This ticket sits in `READY_FOR_ENGINEERING`,
matching `DEC-051`/`DEC-052`/`DEC-057`, where a decided contract whose implementation is
materialised separately waits until the implementation lands and moves it to `DONE`. The
implementation is `FEAT-106` part B (driving the environment stages from `sol deploy` and
establishing the run's own cluster access); that ticket's final commit moves this one to
`DONE` with it.

Promoting a provider without a deploy identity to Option A is the recorded deferral's
trigger: it becomes Option A on the same terms once that provider has a deploy identity,
its access entry and its namespace-scoped RBAC, with no new decision required.
