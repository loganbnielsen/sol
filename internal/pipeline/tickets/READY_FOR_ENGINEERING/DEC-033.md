**Related:** ADR 0004 (records the distinction and leaves this open), ADR 0003
(Destroy policy), ADR 0002, INFRA-023 (unique per-attempt snapshot identity),
HARDEN-002 (procedure step 11 and the Attempt 5 record).

## The question

`sol cloud destroy` currently keeps a final RDS snapshot on every destroy: the
Destroy policy sets `rds_skip_final_snapshot = false` with a unique per-attempt
identifier (INFRA-023). For production that is a feature — a destroy should not
be a data-loss event.

For a qualification target it means "cost-clean" is not actually zero. Attempt 5
reported the target destroyed and then needed a manual
`aws rds delete-db-snapshot` before the account was empty:

```text
remaining after sol cloud destroy:
  EKS none, RDS 0, EC2 terminated, NAT deleted, ECR none, EIP/LB/EBS/VPC none
  RDS manual snapshots: 1  ->  <cluster>-postgres-final-<ts>   (20 GB)
```

ADR 0004 states the invariant for *what the lifecycle created*; this is the
adjacent question of what the lifecycle deliberately keeps. Leaving it implicit
means every disposable run depends on an operator remembering, and a forgotten
snapshot is invisible cost.

## Decision required

How should retention be expressed, and what should the default be?

1. **Target-level, explicit (recommended).** A field on the target/profile — e.g.
   `destroy_retention: final-snapshot | none` — defaulting to today's behaviour
   (`final-snapshot`) for production profiles, and set to `none` for disposable
   qualification targets. The Destroy policy reads it; `sol cloud destroy`
   reports what it retained either way, so "cost-clean" is a claim the run can
   make without a manual step.
2. **A flag on destroy.** `sol cloud destroy --retain-snapshot=false` (or
   `--no-final-snapshot`). Cheaper to build, but retention becomes an operator
   argument rather than a property of the target, and a CI/harness path can
   silently take the wrong default.
3. **Leave the default and require the manual step.** Rejected: it puts a
   cost-safety property outside the lifecycle, which is the same shape as the
   INFRA-037 failure — normal use leaving something standing that only a human
   removes.

Whichever is chosen, two properties should hold: **destroy states what it
retained**, and **a disposable target ends with literally nothing billable unless
the run specifically qualifies retention or recovery**.

## Acceptance criteria

- `sol cloud destroy` reports the artifacts it deliberately retained, by
  identifier.
- A disposable qualification target can be destroyed to zero residual billable
  artifacts without any manual step.
- Production's recoverability default is unchanged unless the decision says
  otherwise.
- The chosen mechanism appears in the qualification procedure, so cost-cleanliness
  is verifiable from the run record rather than from an operator's memory.
- Covered offline: the Destroy policy variables for each retention mode, and a
  destroy report naming retained artifacts.

**Demo/example coverage:** The target fixture gains the field if option (1).

**TypeScript parity:** No language-parity impact.
