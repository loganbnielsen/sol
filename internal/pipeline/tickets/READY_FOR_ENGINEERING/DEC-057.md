## Question

The product experience being built toward — a PaaS-simple deployment on
customer-owned infrastructure — implies a lifecycle and a boundary that the
decision records do not yet state in one place:

1. Is there a **durable, account-level Sol installation** distinct from any
   environment, and what owns it? (`DEC-043` left this open: it recommended
   `bootstrap → preflight → apply` but was never decided.)
2. Does `sol deploy` own **first-run onboarding**, or does the user have to know
   and invoke a separate bootstrap ritual?
3. Is removing the installation the same operation as destroying an environment?
4. Where exactly is the **OSS / hosted boundary**, and how is a future hosted
   component justified?

Without one answer, the experience document and the ticket queue disagree with
each other ticket by ticket — which is the state this decision closes.

## Decision

Decided by the operator on 2026-09-29. The contract below is the source of truth;
`docs/DEVELOPER_EXPERIENCE.md` renders it for users, and this record wins on
conflict.

### 1. Two units: a durable installation and disposable environments

| | Installation | Environment |
|---|---|---|
| Scope | The account/workspace | One deployable target |
| Members | Terraform state + locking; the provisioning/cluster-access/deploy/operator identities; the delegated DNS zone when Sol owns one | Network, cluster, database, registry use, platform, workloads |
| Lifetime | Outlives every environment | Disposable |
| Removed by | An explicit `sol uninstall` | `sol cloud destroy <target>` |

This accepts `DEC-043` option A and closes its remainder: durable prerequisites
have a named owner separate from disposable target state, `apply` preflights
before the billable boundary, and a target destroy provably cannot remove a
durable prerequisite. `DEC-043` records the resolution in place; its
implementation obligations transfer to INFRA-096, and the ticket itself moves to
`DONE` when that implementation lands.

The stage set is **`bootstrap → preflight → provision → platform → migration →
deployment → verification → reconciliation`**. The stages are real, explicit and
individually diagnosable in the implementation. They are **not** user-facing
complexity: on the happy path the user runs `sol deploy <target>` and is shown
progress, not stages.

### 2. Onboarding is inline

`sol deploy <target>` detects an uninitialised installation and guides the user
through it in place. An explicit `sol init`-style administrative workflow may
exist for operators who want it, but it must not be required to get started. A
user should never have to learn an internal stage name to reach production.

The first run distinguishes automated work from the irreducible external action,
and asks only for the latter. Today that action is DNS delegation when the parent
zone is not Sol-managed.

### 3. Installation and environment have different destroy semantics

- `sol cloud destroy <target>` destroys that environment, verifies absence
  independently, and leaves the installation intact.
- `sol uninstall` removes the installation, is explicitly separate, and carries
  extra confirmation when it would remove a Sol-created delegated zone, naming
  the exact domain whose external NS records become stale.
- A user-supplied zone is never deleted by ordinary teardown or by uninstall.
- Sol-created durable resources are retained by environment destroy and removed
  only by uninstall; externally owned resources are reported, not touched.
- After uninstall, Sol independently verifies absence and reports what was
  intentionally retained.

Destroying an environment must not — and does not — force registrar or DNS work
before redeploying.

### 4. DNS onboarding: automate what Sol is authoritative for, ask for the rest

Accept the production hostname; create or adopt the managed zone; if Sol manages
the parent, create the delegation automatically; if the parent is external,
display the exact NS records; **wait for and independently verify public
delegation** rather than trusting configuration. Surface ownership clearly
(Sol-created durable zone / user-supplied zone / externally managed parent). This
generalises `DEC-042` from the qualification path to the product.

### 5. The OSS / hosted boundary

`DEC-019`'s one-way boundary is reaffirmed: the hosted platform is a separate,
private product and repository; this repository is the open-source tool plus the
interface a hosted service may consume, and nothing here may depend on anything
private.

The **guiding test** for any proposed hosted dependency, recorded so it outlives
this decision:

> Can this capability instead be executed by the Sol CLI, the user's CI runner,
> or software/resources Sol installs into the user's own cloud account?
>
> - If **yes**: prefer the OSS / customer-owned implementation.
> - If **no**: name the specific always-on coordination, durable shared state, or
>   operational responsibility that requires Sol-hosted infrastructure. That
>   requirement — not monetisation by itself — is the justification.

No Sol-operated control plane is required for deployment, DNS, TLS, CI,
observability or teardown.

### 6. Addressing: environment is a property of the target, and there is no `--env`

The brief expresses the experience with `sol deploy --env production`. That
shorthand is **not adopted**, because it would allow naming an environment that
disagrees with the cluster, provider, hostname and secrets the target carries.
`DEC-016` stands: environment selection is explicit, comes from the resolved
target, and there is no default and no `--env` flag. `DEC-032`/`DEC-031` stand:
target is an axis, not a scope, and it is the positional on target-primary
commands.

The experience document therefore states the target grammar
(`sol deploy <env>/<driver>/<region>`) and may offer only a shorthand *within*
that grammar — for example, resolving the single target that belongs to an
environment. Whether such a convenience is worth adding is `DEC-016`'s to decide;
this decision does not add it.

## Affected invariants

1. **`DEC-031` / `DEC-032` / `DEC-016` — addressing unchanged.** The target stays
   the positional on target-primary commands; no `--env` flag is added; selection
   stays explicit and fails closed.
2. **`ADR 0002` / `ADR 0003` — Sol owns the complete cloud-target lifecycle, and
   phases determine authority and desired-state policy.** The stage set here names
   the phases the experience exposes; it does not change the authority model.
3. **`ADR 0004` / `DEC-044` / `DEC-040` — destruction removes what the lifecycle
   created, and absence is observed, never inferred.** Environment destroy keeps
   its verified-absence obligation; the installation is added as a thing that
   destroy must *not* remove, with a test that fails if it does.
4. **`DEC-042` — the delegated zone is durable and not part of disposable
   substrate.** Generalised here from the qualification subdomains to any
   Sol-created delegated zone.
5. **`DEC-052` — substrate capabilities are observed, not asserted.** Onboarding
   readiness uses the same `Established`/`Unmet`/`UNKNOWN` vocabulary and fails
   closed on `UNKNOWN`.
6. **`DEC-019` — the OSS/hosted boundary and the one-way dependency.** Reaffirmed
   with the guiding test above.
7. **`SEC-007` — `KAFKA_SECURITY_PROTOCOL` is required, never defaulted.**
   Unchanged; onboarding must not supply a default the environment omits.
8. **`DEC-022` language parity:** none. The contract is language-neutral; OCaml
   and TypeScript applications consume it identically, and no application-facing
   surface changes.

## Non-goals

- **Do not add `--env`, a current-target file, or an ambient target.** `DEC-016`
  owns target selection.
- **Do not build a Sol-operated control plane.** `DEC-019` owns the hosted
  boundary; this decision only defines the test a hosted component must pass.
- **Do not fold installation removal into environment destroy,** and do not
  delete a user-supplied DNS zone under any ordinary operation.
- **Do not expose internal stages as required user knowledge.** An advanced
  user may address them; the happy path must not require it.
- **Do not implement the epics here.** The implementation is materialised as
  separate tickets (INFRA-096, FEAT-106…110, DOCS-026…030).

## Acceptance criteria

- The installation/environment distinction, the stage set, the inline-onboarding

  hosted boundary test are recorded as one contract.
- `DEC-043` is closed with its open question resolved here, and the tickets that

- The `--env` conflict is recorded as rejected, with `DEC-016` named as the
  authority.
- No decision record or open ticket is mechanically rewritten: each overlapping
