`sol up` builds its plan without the resolved `sol.yml`, so it renders different manifests than `sol deploy` for the same workspace

**Depends on:** None.

**Premise verified 2026-09-24** on `origin/main`:
`Sol_cli_up_execution.local_plan` (`cli/sol/lib/sol_cli_up_execution.ml:23-26`) calls
`Sol_cli_deployment_plan.of_services_result` with no `?resolved_config`, while
`sol deploy` passes `~resolved_config:ctx.resolved_config`
(`cli/sol/bin/cmd_deploy.ml:225`).

## Problem

Everything `of_services_result` reads from the resolved `sol.yml` is absent under
`sol up`: each service's declared `language` (`sol_yml_language`), its replica
override (`sol_yml_replicas_override`), and its declared resource use, which feeds
`derive_consumer_groups`. So a workspace deployed locally is rendered from less
information than the same workspace deployed to a target. That breaks "dev mirrors
prod exactly".

It surfaced in INFRA-073 part B. The readiness path depended on the declared
language, and the TypeScript golden-path smoke (`sol up --scope=demo_ts` on
`examples/pluto`, whose `sol.yml` declares `language: typescript`) rendered
`order_svc` as language-less. Its pods were probed on `/readyz`, got 404, and never
became ready (CI run 36038850472). INFRA-073 now treats an undeclared language as
unknown (`/healthz`), which is correct regardless. The divergence remains.

## Remediation

Resolve the workspace `sol.yml` in `sol up` the same way `sol deploy` does (the local
target's defaults), and pass it to `of_services_result`. Check what else changes for
existing local workspaces: replica overrides and consumer groups now apply locally.

## Acceptance criteria

- Test: for one workspace, the service specs from `sol up`'s plan and from
  `sol deploy`'s plan agree on language, replicas and consumer groups.
- A pluto OCaml `-svc` rendered by `sol up` gets its declared language (and so
  `/readyz`).
- Demo/example: the local demo is unchanged or the change is noted in the completion
  notes.
