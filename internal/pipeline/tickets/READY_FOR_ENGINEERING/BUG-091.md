Isolate sol-jobs claims by workspace in a shared database

**Depends on:** None.

**Premise verified (2026-09-29):** At `origin/main` `81b15e53`, `framework/ocaml/sol-jobs/lib/sol_jobs.ml:130-150,253-269` uses a fixed table and only `kind` to route jobs. Local Postgres uses one default database, and AUDIT-024 established that multiple workspaces share it. The source audit records the SQL and existing positive control for distinct kinds.

## Problem

Two workspaces sharing Postgres and using the same job kind can claim each other's rows. A foreign handler can run the wrong side effect, or fail to decode and exhaust another workspace's job. `J.kinds` separates different job kinds but is not a workspace boundary.

## Remediation

Give the job table or its rows a required workspace identity and apply it consistently to enqueue, claim, retry, completion and terminal failure. Preserve transactional enqueue in the application transaction and claims across replicas of the same workspace. Update the migration and package contract coherently; pre-alpha does not require a compatibility shim.

## Acceptance criteria

- Two workspaces using the same Postgres database and the same `kind` cannot claim, handle, retry or finalize each other's jobs, even with different payload codecs.
- Two pollers in one workspace still share claims safely; enqueue within an application transaction retains atomicity.
- A missing or invalid workspace identity refuses before enqueue or polling rather than falling back to a shared queue.
- Update a runnable `sol-jobs` example and record the TypeScript capability verdict or tracking ticket in completion notes.
