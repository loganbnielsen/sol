## Friction Log

### Friction 1: Leftover pre-rename `sun-local` k3d cluster blocks `sol dev up` with an opaque error

**Step:** Step 3 — `sol dev up`
**Command:** `sol dev up`
**Expected:** Either reconcile with an existing local substrate, or clearly explain what's blocking a fresh one.
**Actual:** This machine had a k3d cluster named `sun-local` (and a `sun-registry` container bound to host port 5000) left over from before the Sun→Sol rename (FEAT-032). `sol dev up`'s cluster-name is now hardcoded to `sol-local` (`cmd_dev.ml:20`), so it never recognized the old cluster, and instead tried to create a brand-new `sol-local` cluster whose own registry container (`sol-registry`, also hardcoded to port 5000, `cmd_dev.ml:84`) collided with the still-running `sun-registry` on the same host port. `sol dev up` printed only:
```
error: cluster creation failed
```
with **zero** indication of why. The real cause (`Bind for 0.0.0.0:5000 failed: port is already allocated`) was only visible by re-running the exact `k3d cluster create ...` command shown in `sol`'s own `--echo` output, by hand, outside of `sol`.
**Time lost:** ~10 minutes (mostly spent proving the error was reproducible and manually invoking `k3d` to find the real cause).
**Workaround:** `k3d cluster delete sun-local` (destroys the orphaned pre-rename cluster and its registry).
**Blocks two-minute claim?** yes
**Suggested fix:** Two independent fixes, filed together as FRIC-006 (see below) since they're the same root pattern, plus FRIC-008 for the rename-specific half.

### Friction 2: `sol up`'s docker-build and rollout failures are equally opaque

**Step:** Step 4 — `sol up`
**Command:** `sol up`
**Expected:** A failed `docker build` or failed rollout tells the user what actually went wrong.
**Actual:** First attempt: `sol up` printed only `error: docker build failed: app/comms/notify_worker` — the real dune/OCaml compiler error (`Library "sol_obs" not found`, caused by `vendor/framework`'s symlink not being resolved into the `.docker-ctx` build context the way it should have been on that first attempt — root cause not fully pinned down; a second `sol up` run against the same, unmodified workspace built the same image successfully, so this looks state/cache-dependent rather than a permanent defect) was visible only in raw `docker build` output, never surfaced by `sol`. Second attempt: `sol up` got further (`notify-worker` built, pushed, and was reported "✓ deployed") but then printed `error: rollout failed: dogfood-2026-09-07-payments/charge-svc` with no further detail — the real cause (schema-registry 422, see Friction 3 below) was only visible via `kubectl logs`.
**Time lost:** ~15 minutes across both failures.
**Workaround:** `kubectl describe pod` / `kubectl logs` by hand.
**Blocks two-minute claim?** yes
**Suggested fix:** See FRIC-006 below.

### Friction 3: Every generated service crash-loops — Redpanda's schema registry rejects `schemaType: "JSON"`

**Step:** Step 4 — `sol up` (rollout), and independently reproducible against the raw registry HTTP API.
**Command:** `curl -X POST http://localhost:8081/subjects/test-subject/versions -H 'content-type: application/vnd.schemaregistry.v1+json' -d '{"schemaType":"JSON","schema":"{\"type\":\"object\"}"}'`
**Expected:** `200`, with a registered schema ID — this is exactly what `Kafka_service.register` (`integrations/kafka/kafka-eio-service/lib/kafka_service.ml:167-170`, via `kafka_service_schema.ml`'s `register_schema`) sends on every `-svc`/`-worker` startup.
**Actual:** `422 {"error_code":422,"message":"Invalid schema type JSON"}`. The Redpanda broker deployed by `sol dev up`'s Helm chart (`redpanda/redpanda` version `5.8.12`, running Redpanda `v24.1.8` — `kubectl get pod -n redpanda ... -o jsonpath='{.spec.containers[0].image}'`) rejects the `schemaType: "JSON"` field outright. The identical request with no `schemaType` field (defaulting to Avro) returns `200`. Every generated `-svc` and `-worker` calls `Kafka_service.register` unconditionally with `schemaType: "JSON"` at startup, so **both `charge-svc` and `notify-worker` crash-loop immediately and permanently** on any fresh `sol dev up` substrate — confirmed via `kubectl logs`:
```
error: kafka register: schema registry for topic dogfood_2026_09_07-payments-charges: schema registry: HTTP 422: {"error_code":422,"message":"Invalid schema type JSON"}
```
Whether this is a genuine capability regression in the pinned Redpanda version, a config flag Sol's Helm values don't set, or a licensing gate on non-Avro schema types was not determined this run — the broker logs (`pandaproxy - server.cc:125`) give only the same generic exception, no license/config hint.
**Time lost:** ~40 minutes (this was the deepest investigation of the run, including confirming it reproduces identically via direct curl against the registry, independent of any Sol code path).
**Workaround:** none found that doesn't require either changing Sol's protocol (register without `schemaType`, i.e. Avro) or reconfiguring/upgrading the deployed Redpanda.
**Blocks two-minute claim?** yes — this is the single blocker that matters most; nothing past this point in the golden path can be exercised for any new user on a fresh `sol dev up` substrate.
**Suggested fix:** See FRIC-007 below.

## Findings

- **The golden path is currently broken for every new user, not an edge case.** FRIC-007 reproduces deterministically on a completely fresh `sol dev up` substrate with a completely fresh generated workspace — this is not specific to this machine's history the way Friction 1 is.
- **`sol status` correctly reports failure** — it printed `DEGRADED` for both domains rather than falsely claiming health, which is the right behavior; the gap is that it doesn't point the user toward `kubectl logs` or any next diagnostic step.
- **Error-swallowing is a systemic pattern, not isolated incidents.** Grepping `cmd_dev.ml`/`cmd_up.ml` shows the identical pattern at four call sites (cluster creation, docker build, docker push, rollout wait): `Sol_cli_process.run` already captures the child's `stdout`/`stderr` in its result record, but every one of these call sites discards it and prints only a fixed generic message. This is a small, mechanical fix (print the captured output before the generic message) that would have cut this run's diagnosis time from ~50 minutes to a few minutes total.
- **FRIC-001 through FRIC-005 status:** not re-verified in depth this run (this run's time went almost entirely into the two new blockers above), but nothing in this run's friction contradicts their prior resolution. Notably, the Helm chart list now includes `grafana-community/loki` and a separate `grafana`/`alloy`/`tempo` install (FRIC-005's suggested fix — migrating off the deprecated `loki-stack` chart) rather than the old bundled `loki-stack`, so that migration appears to have already happened since the June run.
- **Minor, non-blocking:** `sol new workspace dogfood-2026-09-07` silently scaffolds `dogfood_2026_09_07` (hyphens normalized to underscores) with no note that the name changed — the subsequent `cd dogfood_2026_09_07` hint in the same output is correct, so this never actually misleads, but a first-time user typing a hyphenated, date-based name (a very natural choice) might be confused for a moment. Not filed as a ticket — non-blocking and single occurrence.
