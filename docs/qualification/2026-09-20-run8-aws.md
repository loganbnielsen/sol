### 7.1 The egress-IP change, in detail

- **Symptom:** `Unable to connect to the server: dial tcp 44.213.196.133:443: i/o timeout`.
  AWS credentials were valid throughout (`aws sts get-caller-identity` succeeded).
- **Cause:** `cluster_endpoint_cidr: 24.10.239.81/32` no longer matched this host's
  egress address, which the connection loss had changed to `4.1.2.61`.
- **Recovery:** `sol cloud apply qual/aws/us-east-1`, with the target's
  `cluster_endpoint_cidr` updated first, so the change went through **Sol's normal
  cloud reconciliation path** — the same route a target change always takes. No
  out-of-band `aws eks update-cluster-config`, no console edit, and no change to
  any unrelated infrastructure.
- **Observed:** `Done.`, cluster access restored
  (`kubectl get ns pluto-checkout` → `Active 4h49m`).
- **Procedure friction, recorded not fixed:** a long qualification run behind a
  dynamic address is fragile, and its failure mode is an unreachable API with no
  Sol-side message. A run record should capture the address in use, and the
  procedure should say to re-check the allowlist after any network interruption.

**Why events are missing, and why that is itself the finding.** Every identity the
target provisions is unable to read them:

- `sol-qual5-deploy` (the deploying identity): `events is forbidden … cannot list
  resource "events"`. It also cannot `pods/portforward`, so the `/readyz` body
  cannot be fetched either.
- `sol-qual5-cluster-access`: an access entry exists but carries **no access
  policies** (`list-associated-access-policies` → `[]`), and the cluster-scoped
  provisioner ClusterRole deliberately omits namespaced workload resources
  (`platform_provisioner_rbac.tf`: "Namespaced workload resources are deliberately
  omitted"). So it is refused for pods and events alike. This is consistent with
  the intended design — `AmazonEKSClusterAdminPolicy` is associated only while
  `provisioner_bootstrap_admin` is true (`aws/main.tf:153-166`).
- `sol-qual5-operator` (declared in the target): **no access entry exists at all**,
  so it cannot authenticate (`Unauthorized`).
- The AWS SSO administrator: also `Unauthorized` — the cluster's creator is not
  given standing Kubernetes access once the bootstrap window closes, by design.

Consequence: `sol deploy` tells the operator to `Run 'sol status' to check pod
health`, but a pod that never becomes ready cannot be explained from any identity
the profile provides — no events, no port-forward, no logs. **The run cannot
diagnose its own workload.** The one identity that could (`sol-qual5-operator`, or
a break-glass `enable_cluster_creator_admin`) is either not wired to the cluster or
is not part of this target's declared surface. This is recorded as an observation
about diagnosability, not classified as a defect: the intended contract for the
operator identity has not been established, and `exit 137`/`reason=Error` is
consistent both with a liveness-probe kill and with an OOM kill, which the evidence
available to the run cannot distinguish.

**Classification of the workload state itself: `UNDETERMINED`** on this evidence.
It is not on present evidence a Sol defect — one replica of the same spec is ready,
and the container emits no logs — and it is not a pass either. What would settle it:
pod events (needs a diagnostic identity, above), a `/readyz` response body, or any
