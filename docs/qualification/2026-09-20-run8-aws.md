### 7.1 The egress-IP change, in detail

- **Symptom:** `Unable to connect to the server: dial tcp 44.213.196.133:443: i/o timeout`.
  AWS credentials were valid throughout (`aws sts get-caller-identity` succeeded).
- **Cause:** `cluster_endpoint_cidr: 24.10.239.81/32` no longer matched this host's
  egress address, which the connection loss had changed to `4.1.2.61`.
- **Recovery:** `sol cloud apply qual/aws/us-east-1`, with the target's
  `cluster_endpoint_cidr` updated first, so the change went through **Sol's normal
  cloud reconciliation path** — the same route a target change always takes. No
  out-of-band `aws eks update-cluster-config`, no console edit, and no change to
  any unrelated infrastructure.
- **Observed:** `Done.`, cluster access restored
  (`kubectl get ns pluto-checkout` → `Active 4h49m`).
- **Procedure friction, recorded not fixed:** a long qualification run behind a
  dynamic address is fragile, and its failure mode is an unreachable API with no
  Sol-side message. A run record should capture the address in use, and the
  procedure should say to re-check the allowlist after any network interruption.

**Why events are missing, and why that is itself the finding.** Every identity the
target provisions is unable to read them:

- `sol-qual5-deploy` (the deploying identity): `events is forbidden … cannot list
  resource "events"`. It also cannot `pods/portforward`, so the `/readyz` body
  cannot be fetched either.
- `sol-qual5-cluster-access`: an access entry exists but carries **no access
  policies** (`list-associated-access-policies` → `[]`), and the cluster-scoped
  provisioner ClusterRole deliberately omits namespaced workload resources
  (`platform_provisioner_rbac.tf`: "Namespaced workload resources are deliberately
  omitted"). So it is refused for pods and events alike. This is consistent with
  the intended design — `AmazonEKSClusterAdminPolicy` is associated only while
  `provisioner_bootstrap_admin` is true (`aws/main.tf:153-166`).
- `sol-qual5-operator` (declared in the target): **no access entry exists at all**,
  so it cannot authenticate (`Unauthorized`).
- The AWS SSO administrator: also `Unauthorized` — the cluster's creator is not
  given standing Kubernetes access once the bootstrap window closes, by design.

Consequence: `sol deploy` tells the operator to `Run 'sol status' to check pod
health`, but a pod that never becomes ready cannot be explained from any identity
the profile provides — no events, no port-forward, no logs. **The run cannot
diagnose its own workload.** The one identity that could (`sol-qual5-operator`, or
a break-glass `enable_cluster_creator_admin`) is either not wired to the cluster or
is not part of this target's declared surface. This is recorded as an observation
about diagnosability, not classified as a defect: the intended contract for the
operator identity has not been established, and `exit 137`/`reason=Error` is
consistent both with a liveness-probe kill and with an OOM kill, which the evidence
available to the run cannot distinguish.

**Classification of the workload state itself: `UNDETERMINED`** on this evidence.
It is not on present evidence a Sol defect — one replica of the same spec is ready,
and the container emits no logs — and it is not a pass either. What would settle it:
pod events (needs a diagnostic identity, above), a `/readyz` response body, or any

#### Blocker 1 — the `-svc` half: no identity can transport into an application namespace

Measured, not assumed:

| Principal | platform namespaces (`redpanda`, `monitoring`) | application namespaces (`pluto-payments`) |
|---|---|---|
| `cluster-access` (`sol:platform-provisioners`) | `*.* [*]` — including `pods/portforward` | **no access at all**; `portforward` → `no` |
| `deploy` (`sol:deployers`) | — | read-only on workloads; no `portforward`, no `exec` |
| `operator` (`sol:operators`) | — | read-only diagnostics; `portforward` → `no` by DEC-038 §4 |
| `provisioner` | **no access entry exists** (`ResourceNotFoundException`) | — |
| SSO administrator | **`Unauthorized`** on the cluster (no creator-admin) | — |

So the transport capability exists **only** for platform namespaces, and the
application services are ClusterIP with no ingress path. **Nothing Sol provisions can
inject traffic into an application namespace.** B3's `-svc` step therefore cannot be
executed by the documented procedure — this is a gap in the *procedure's* assumptions,
not a defect to fix by granting `pods/portforward` to operator or deploy: that
capability is excluded deliberately, and B3 is not supposed to prove that ordinary
production operators can interactively port-forward.

#### Blocker 2 — the `-worker` half: the workload itself prevents an unambiguous result

Two messages were produced to `pluto-payments-charges`, with the consumer group
`pluto-comms-notify-worker` observed from the broker.

**First attempt — a methodological correction worth keeping.** Plain JSON was produced
via the broker's HTTP API. The group then showed `CURRENT-OFFSET 1`, lag `0`
— which reads as "consumed and processed". It was **not**:

```
sol-worker: DECODE_ERROR skip=true error="wire format: invalid magic byte"
```

The app's wire format carries a schema-registry envelope, so the worker consumed the
record and **skipped** it. The committed offset was not evidence of processing, and the
platform's own log store is what corrected the inference. (`kubectl logs` for that pod
returns nothing; the evidence lives in the platform log store.)

**Second attempt — correctly framed**: `0x00` + big-endian schema id (`1`, JSON schema,
subject `pluto-payments-charges-value`) + the JSON body, produced through the broker's
binary API. Accepted at offset 1. Observed afterwards:

```
TOPIC                   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG  MEMBER-ID  HOST
pluto-payments-charges  0          1                2               1   (none)     (none)
```

LAG 1 and **no group members**: the consumers had left the group. Earlier the same
group reported `Stable` with 2 members. The worker's consumer set is joining and
leaving — the same instability the readiness probe shows, now observed **independently
from the broker's side** rather than from Kubernetes readiness. The message is
therefore not consumed, and B3's `-worker` assertion ("message observed processed")
cannot be made unambiguously.

#### Why the two halves are coupled

The only way to produce a **correctly framed** message is through the application's own
producer — `charge_svc`'s `POST /charges` — which does the schema-registry framing. That
is precisely what Blocker 1 prevents. So B3 is blocked as a whole, and the root blocker
is the missing application-namespace transport.

#### Stop condition, per the run's own rule

The degraded Deployment **does** prevent B3 and makes its result ambiguous, so the run
stops here rather than modifying the workload to obtain a pass. The fixture decision is
the operator's: repair/reset `notify-worker` before using subsequent §B/§D/§E evidence
that depends on its consumer, or defer that portion. Nothing was repaired silently.

**Result:** B3 `NOT REACHED` — blocked, with the reason preserved. §B4–§B7 `NOT RUN`.

#### Procedure friction observed again (fifth occurrence)

`aws eks update-kubeconfig --alias <ctx> --role-arn <role>` rewrites the **shared user
entry**, so a context named for one identity silently authenticates as whichever
identity was configured most recently. It produced a `Forbidden` in `redpanda` while
appearing to be the `cluster-access` context, and an earlier `migrate apply` ran as the
operator. The mitigation recorded in FND-0017 is the one that works: re-issue
`update-kubeconfig` for the identity under test immediately before each command, and
record which principal actually served each read.
