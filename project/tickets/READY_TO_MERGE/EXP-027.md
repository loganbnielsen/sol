`sol new svc` still generates an observability-dark entrypoint (worker/fn recovered from EXP-022, svc did not)

**Description:** The generic `svc_bin_ml` template used by `sol new svc` (`cli/sol/lib/sol_cli_scaffold_templates.ml:895-903`) generates `Service.run Handler.routes ~env ()` with no `Sol_obs.of_env` call and no `~ot` argument. Contrast with `worker_bin_ml` and `fn_bin_ml` in the same file, which both correctly build an `obs` handle via `Sol_obs.of_env ~net:env#net ~clock:env#clock ~mono_clock:env#mono_clock ~service:"{{name}}-..." ()` and pass `~ot:obs` — and with `ws_svc_bin_ml` (the workspace-scaffold's initial service), which does the same. This is the original EXP-022 finding (all three primitives affected), now only two-thirds recovered: worker and fn appear to have picked up the fix incidentally through later unrelated template edits, but svc never did.

**Impact:** A startup engineer who follows the tutorial's `sol new svc ops/admin` example gets a service that compiles and runs but produces no Loki logs and no `sol_svc_requests_total` metric in Prometheus — silently inconsistent with a `sol new worker`/`sol new fn` sibling added the exact same way, and contradicting the platform's "observability wired automatically" promise.

**Remediation:** Update `svc_bin_ml` in `cli/sol/lib/sol_cli_scaffold_templates.ml` to match the `Sol_obs.of_env` + `~ot:obs` pattern already present in `worker_bin_ml`/`fn_bin_ml`/`ws_svc_bin_ml`.
