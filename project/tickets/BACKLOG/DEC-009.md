Decide whether Sol-hosted mode gets a dedicated web UI, or stays CLI-first with an embedded/white-labeled dashboard shell.

**Question:** DEC-007 already commits hosted UX to showing "release, deployment plan, status, logs, rollback" concepts rather than raw GitOps/Kubernetes mechanics, and `observability-design.md`'s "Hosted Path" section says Sol may "operate the storage itself or broker a managed provider... users should not have to learn that backend." Neither says how a user actually *sees* any of this. Does Sol build and maintain a dedicated customer-facing web application (accounts, RBAC, billing, environment management, dashboards — a genuinely new, large product surface), or does it stay CLI-first (`sol status`/`sol open`) with Grafana (self-hosted today) replaced by a Sol-branded/white-labeled dashboard shell for hosted customers, deferring a full web app until there's evidence customers need one?

**Context:** This is the single largest net-new engineering surface implied by the hosted-factory-floor direction — bigger than any CLI or Terraform work done so far. `PRODUCT_ARCHITECTURE.md`'s hosted factory floor list already names RBAC and audit logs as future concerns a CLI-only surface doesn't naturally support (RBAC in particular implies real user/team/permission management, not just kubeconfig-style access). Building this before hosted infra tenancy (DEC-008) exists, and before a single paying hosted customer exists, risks splitting effort across two unproven products (the open-source CLI/Terraform tool and a hosted multi-tenant SaaS) at once.

**Options:**
1. Full dedicated web UI from the start — accounts, environments, dashboards, logs, billing, RBAC, built as a first-class product alongside the CLI.
2. CLI-first (`sol status`/`sol open`) plus a white-labeled/embedded dashboard shell (Grafana today) for hosted customers; defer a full web app until real hosted usage demands account/team/billing management a CLI can't reasonably provide.
3. Thin hosted web UI scoped to only what a CLI genuinely cannot do (billing, account/team management, RBAC), with all release/status/logs/dashboard interaction staying CLI + dashboard-shell as in option 2.

**Decision criteria:**
- Consistency with DEC-001 (hosted doesn't own builds yet) and DEC-004 (hosted is first-class, but the factory contract should stabilize before over-specifying the control-plane API) — both argue against building the biggest UI surface first.
- What actually blocks the first paying hosted customer versus what's speculative polish.
- Engineering cost relative to Sol's current team size and pre-alpha stage.
- Whether billing (DEC-006) and RBAC genuinely require a web UI (likely yes) versus dashboards/logs (already served by Grafana today).

**Acceptance criteria:**
- A written decision names which option is the first hosted UI investment.
- The decision explicitly sequences it relative to DEC-008 (tenancy mechanism must exist before there's anything for a UI to manage).
- Follow-up tickets are created only for the scoped-in surface, not the full future vision.
