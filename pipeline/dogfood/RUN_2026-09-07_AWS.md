The gap is that *nothing in Sol's own docs or tooling anticipates any of these failure modes* — a real user would hit each one cold, with no Sol-specific guidance.

## Friction Log

**Step:** `sol cloud apply`
**Command:** `sol cloud apply customer_cloud/aws/us-east-1 --var 'ecr_repositories=[...]'`
**Expected:** Provisions cleanly with the checked-in `smoke-test-iam-policy.json`.
**Actual:** Failed 5 separate times on missing IAM permissions the policy didn't grant: `iam:CreateServiceLinkedRole` (RDS's one-time-per-account service-linked role didn't exist), `logs:DescribeLogGroups` (needs `Resource:"*"`, not resource-scoped — an EKS-module quirk), `ec2:RunInstances`/`ec2:TerminateInstances` (missing entirely — node group couldn't launch instances), `eks:DescribeAddonVersions`+addon CRUD actions (missing entirely), `iam:GetRole` on the EKS-nodegroup service-linked role path, `ecr:GetAuthorizationToken` + all ECR data-plane push actions (`BatchCheckLayerAvailability`/`InitiateLayerUpload`/`UploadLayerPart`/`CompleteLayerUpload`/`PutImage`/`BatchGetImage`) — the original policy only had repository *management* actions, none of the actual push/pull actions.
**Time lost:** ~40 minutes across 8 policy-version iterations (also hit the AWS 6144-byte managed-policy size limit and the 5-version-per-policy limit along the way).
**Workaround:** Iteratively added each missing permission as it surfaced, using `Administrator` to update the policy since the scoped provisioner correctly can't self-modify.
**Blocks two-minute claim?** N/A (cloud path, not the local 2-minute claim) but blocks the "provisions cleanly" premise entirely.
**Suggested fix:** Fixed live — `platform/infra/aws/smoke-test-iam-policy.json` now has the complete permission set for a real `create_rds=true` apply+destroy cycle, verified end to end. See findings below for the two real *product* bugs this surfaced along the way (not just policy gaps).

**Step:** `RDS` engine version
**Command:** (part of `sol cloud apply`)
**Expected:** PostgreSQL 16.2 provisions.
**Actual:** `InvalidParameterCombination: Cannot find version 16.2 for postgres` — AWS RDS no longer offers this exact patch version.
**Time lost:** ~5 minutes.
**Workaround/fix:** Bumped `platform/infra/aws/main.tf`'s hardcoded `engine_version` to `16.15` (current latest 16.x). This is a real, live bug affecting **production** deploys too, not just this smoke test — anyone running `sol cloud apply` with `create_rds=true` today would hit this.
**Blocks two-minute claim?** N/A. **Suggested fix:** Fixed live, verified (RDS instance created successfully at 16.15).

**Step:** Docker build (charge_svc, notify_worker)
**Command:** `docker build -f examples/pluto/app/payments/charge_svc/Dockerfile ...`
**Expected:** Builds using the checked-in example Dockerfile.
**Actual:** Two layered failures: (1) `FROM ocaml/opam:ubuntu-24.04-ocaml-5.4.1` — this exact tag no longer exists on Docker Hub (only the untagged-patch `ubuntu-24.04-ocaml-5.4` does); (2) even after fixing the tag, `Command not found 'dune'` — **the example Dockerfiles have no `opam install` step at all**, assuming the base image ships dune and all project dependencies pre-installed, which it never has (verified: the base image's default switch has only the bare compiler toolchain).
**Time lost:** ~15 minutes to diagnose; resolved by discovering the current `sol new` scaffold template (`sol_cli_scaffold_templates.ml`) already has both fixes from earlier real iteration (its own comments reference "observed: https-eio needing tls-eio >= 2.1.0" and a prior "Library jose not found" failure) — the **example fixtures had simply gone stale relative to the template**, never re-synced after those fixes landed.
**Workaround/fix:** Fixed live — all 4 example Dockerfiles (`examples/pluto/{payments/charge_svc,comms/notify_worker}`, `examples/venus/{comms/notify_worker,logistics/fulfillment_worker}`) now match the current scaffold template's build stage exactly.
**Blocks two-minute claim?** N/A (examples, not scaffold). **Suggested fix:** Fixed live. Longer-term: nothing currently guards examples from drifting out of sync with the scaffold template again — worth a CI check that diffs the two, filed as FRIC-014 below.

**Step:** `docker push` to ECR, then EKS pod scheduling
**Command:** `docker push .../charge-svc:smoke0907` then pod creation
**Expected:** Image pulls and runs.
**Actual:** `ImagePullBackOff` with `failed to resolve reference ...: not found` — despite the image genuinely existing in ECR (confirmed via `aws ecr describe-images`). Root cause: modern `docker build` attaches a provenance/SBOM attestation sub-manifest to the image index by default (Docker 23+), which EKS's containerd fails to resolve.
**Time lost:** ~10 minutes.
**Workaround/fix:** Rebuilt with `--provenance=false --sbom=false`, confirmed the pull succeeds. **This is a real product bug, not just an artifact of my manual test** — `Sol_cli_docker.build` (used by `sol up`) and the scaffold-generated CI workflow template (used by any real customer's CI/CD to a real cloud cluster) both build images the exact same way, with no provenance flags. Fixed live in both `cli/sol/lib/sol_cli_docker.ml` and `sol_cli_scaffold_templates.ml` (2 occurrences), verified all existing scaffold tests still pass.
**Blocks two-minute claim?** N/A. **Suggested fix:** Fixed live.

**Step:** `sol deploy customer_cloud/aws/us-east-1`
**Command:** `sol deploy ... --registry <ecr-registry> --image-tag smoke0907`
**Expected:** References the ECR repos Terraform just provisioned.
**Actual:** `sol deploy` referenced `${ecr-registry}/pluto/charge-svc` (workspace-name-based, via `Sol_cli_deployment_plan.image_ref`), but Terraform's `ecr_repositories` variable had provisioned `${ecr-registry}/sol-smoke-test-0907/charge-svc` (**cluster-name**-based, via `main.tf`'s `aws_ecr_repository.services`). These never match unless a user's cluster name happens to equal their workspace/project name.
**Time lost:** ~15 minutes to diagnose; worked around by manually creating ECR repos under the workspace-based name via `Administrator`.
**Blocks two-minute claim?** N/A but **this is the single most severe correctness bug found in this run** — it breaks `sol deploy` for essentially any real-world naming choice. Filed as **FRIC-011** (blocker).

**Step:** `sol migrate apply`
**Command:** `sol migrate apply` (POSTGRES_URL set to the real RDS endpoint)
**Expected:** Connects and applies migrations.
**Actual:** Clean, correct `Connection timed out` after ~2 minutes — confirmed via direct `nc`/`aws rds describe-db-instances` that the RDS instance is `PubliclyAccessible: False` with a security group scoped to VPC-internal traffic only (correct, secure defaults). There is no documented or tooled way (bastion host, SSM port-forwarding, VPN) for an operator's local machine or a CI runner to reach a properly-private production database.
**Time lost:** ~10 minutes to confirm root cause (briefly, reversibly, opened the security group to my IP to verify — then immediately reverted; did not attempt to make the instance genuinely reachable, since that's real infrastructure work beyond this ticket's scope).
**Blocks two-minute claim?** N/A. **Suggested fix:** Filed as **FRIC-012** (high) — this is a real, unaddressed gap in the documented ops loop, not a bug in the error message itself.

**Step:** `sol secret set --env=customer_cloud POSTGRES_URL`
**Command:** `sol secret set ...`
**Expected:** Sets the secret for the services I'm deploying.
**Actual:** `Error from server (NotFound): ... namespaces "pluto-demo-ts" not found` — `sol secret set` iterates over **every** filesystem-discovered service in the workspace (including `examples/pluto/app/demo_ts`, the FEAT-033 TypeScript spike, which I'd deliberately excluded from this deploy via path filters), with no equivalent `--path`/target-filter option that `sol up`/`sol deploy` have.
**Time lost:** ~5 minutes; workaround was to physically move the `demo_ts` directory out of the workspace tree for the duration of the test.
**Blocks two-minute claim?** N/A. **Suggested fix:** Filed as **FRIC-013** (medium).

## Findings

- **`sol status` and `sol logs` both worked correctly against the real EKS cluster** with no local-only assumptions found — `sol status` correctly reported `payments: healthy` / `comms: DEGRADED` matching real pod state, and `sol logs` fell back cleanly to direct pod logs when no in-cluster Loki was configured.
- **`sol rollback` executed successfully** against the real cluster.
- **`sol cloud destroy`'s default `--plan`-only safety behavior is good UX** — it would be easy to accidentally run a real destroy without this guard.
- **The pre-existing `smoke-test.tfvars`/`smoke-test-iam-policy.json`/`setup-provisioner.sh`/`teardown-provisioner.sh` toolkit was clearly built for exactly this kind of test**, but had evidently never been exercised with `create_rds=true` — every IAM gap found was in the RDS/EKS-nodegroup/ECR-push code paths specifically, none in the parts that a `create_rds=false` smoke test (the toolkit's own documented usage example) would exercise.
- **`teardown-provisioner.sh` doesn't handle a policy with multiple versions** (fails with `DeleteConflict`) — a near-certain outcome of any real iterative debugging session like this one. Fixed live.
- Real AWS cost for this run: EKS control plane + 2×t3.medium nodes + db.t3.micro-class RDS instance + NAT gateway, all destroyed within the session — no ongoing charges. Final verification confirmed zero EKS clusters, VPCs, RDS instances, NAT gateways, or Elastic IPs remaining under this test's naming, and both manually-created ECR repos deleted.

## Tickets filed

- **FRIC-011** (blocker) — ECR repository naming (Terraform, cluster-name-based) vs. `sol deploy`'s image reference construction (workspace-name-based) are structurally disconnected.
- **FRIC-012** (high) — No documented/tooled way for `sol migrate` to reach a properly-private production RDS instance.
- **FRIC-013** (medium) — `sol secret set` has no path/target filter, unlike `sol up`/`sol deploy`.
- **FRIC-014** (low) — Example Dockerfiles (`examples/pluto`, `examples/venus`) can silently drift out of sync with the `sol new` scaffold template with nothing to catch it (this run found a real, live instance of exactly that drift).

Fixed live, verified against real infrastructure, not filed as separate tickets (shipped in this same pass — see PR):

- Stale example Dockerfiles missing the opam pin/install steps entirely (4 files).
- `smoke-test-iam-policy.json` missing 6 categories of permissions needed for a real `create_rds=true` apply+destroy cycle.
- `teardown-provisioner.sh` not handling multi-version policies.
