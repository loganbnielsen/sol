**Depends on:** None.

**Related:** DEC-026 (the `production-single-region` profile — specifically its item 2,
application-facing availability semantics), AUDIT-080 (the workload-availability

FEAT-082, DEC-022,
`pipeline/audits/2026-09-16_production_platform_contract_review.md` §4.

**This ticket is an input to DEC-026, not a competing implementation stream.** It
exists so that the maturity-A availability vocabulary decides what a worker's
"available" means, rather than that being settled implicitly by whatever a CI job
happens to need. The implementation vehicle already exists — AUDIT-080, itself
blocked on DEC-026 — so this decision should scope that work's worker-readiness
slice, not spawn a parallel one. Nothing should be implemented from it before
DEC-026 has fixed the failure-tolerance vocabulary it must be expressed in.

## Question

Sol renders two workload shapes, and "ready" does not mean the same thing for
them. For an `Http_service`, Kubernetes' pod `Ready` condition is backed by a
rendered `readinessProbe` against `GET /healthz`: it means the application is
serving. For a `Background_worker` no probe is rendered at all, so `Ready` means
only that the container started.

Should Sol model *worker application readiness* — a state that distinguishes
"the process is running" from "the worker can actually accept work" (for a Kafka
worker, partitions assigned and its consumers joined) — or should it explicitly
declare that a worker's platform-visible availability is just "running", and
correct the surfaces that currently read as if more were promised?

If the former, decide the observable state and how it is surfaced. If the latter,
enumerate what must change so nothing implies a guarantee that is not made.

## Evidence (measured, 2026-09-16/17)

**1. The renderer makes the asymmetry explicit and intentional.**
`sol_cli_manifest.mli`'s `workload_shape` doc says: `Http_service` exposes app HTTP
on 8080 *with probes*; `Background_worker` exposes metrics on 9090 *without
probes*. `sol_cli_manifest_yaml.ml`'s `probe_section` renders `livenessProbe` and
`readinessProbe` (`httpGet /healthz:8080`) only `if shape = Http_service`, and the
empty string otherwise — in both `deployment_doc` and the Argo `rollout_doc`, for
both languages. This is a documented contract, not an oversight.

**2. Consequences, observed rather than inferred (FEAT-087).**
`kubectl wait --for=condition=ready` on a freshly deleted worker pod returned in
~1.1 s; that same pod's own logs showed `[ConsumerGroup] Consumer has joined the
group` ~11.5 s after pod start. In one CI run the marker order was: `sol up`
succeeded, `POST /orders` at `00:31:43.978Z`, worker consumer joined at
`00:31:52.778Z` — 8.8 s later. Because the demo worker subscribes with
`fromBeginning: false`, that message was not *late*, it was invisible to that
consumer permanently. Nothing Sol reports distinguishes these two states.

**3. `sol up` success does not mean a worker can work.**
`sol_cli_up_execution.ml`'s `wait_for_service_rollout` treats
`Sol_cli_deployment_plan.Svc` and `Worker` identically: `kubectl rollout status
deployment/<k8s_name>`. For a probe-less worker Deployment that is satisfied as
soon as containers are running. So `sol up` returning success is evidence the
workload *rolled out*, not that it can accept work.

**4. Sol's own health model applies the same `Ready` to both.**
`sol_cli_rollout_diagnosis.ml`'s `is_healthy` is `phase = "Running" && ready &&
state = Running`, and `sol_cli_status.ml`'s `pod_expectation_of_primitive` maps
`Svc | Worker -> Continuous`. So `sol status` reports a worker as healthy on a
signal whose meaning differs from the one it uses for a service.

**5. The correct readiness event already exists in the OCaml framework — and is
surfaced nowhere.** `framework/sol-worker/lib/worker.mli`'s `Make`/`Make_with_retry`
`run` accepts `?on_ready:(unit -> unit)`, documented as "Called exactly once when
the broker assigns partitions to this consumer." It is a process-local callback
with no platform-visible projection: the same module exposes only `GET /metrics`
on `metrics_port` (default 9090). The TS demo worker's metrics server 404s
anything but `/metrics`. So there is a semantically correct hook on one side, no
endpoint, and no platform consumer of it.

**6. TypeScript parity does not yet include a readiness concept at all.**
`@sol-fab/worker`'s `runWorker` owns lifecycle only — idempotent SIGTERM/SIGINT,
an unbounded drain, ordered shutdown hooks — and explicitly does not own
consuming or metrics. `RunWorkerOptions` has no readiness hook. The OCaml
`on_ready` has no TS counterpart.

**7. A documentation claim that is already wrong for workers.**
`sol_cli_check.mli` states that "`GET /healthz` and `GET /metrics` are guaranteed
by the service/worker frameworks (see `Sol_svc.Service` and `Sol_worker.Worker`)".
`Sol_worker.Worker` guarantees `/metrics`; it serves no `/healthz`. This is a
cheap, independent correction — noted here so it is not lost, and not part of the
decision below.

## Constraints

- **This is platform-contract territory, not a CI problem.** FEAT-087 needed
  synchronization and deliberately did not change this contract to get it: it
  waits on the application's own join evidence inside one CI job. Deciding this
  ticket must not be a side effect of that job, and must not add a
  Kafka-specific probe merely to make a test simpler.
- **The availability vocabulary is DEC-026's to define.** The production platform
  contract review §4 defines maturity-A availability by promised failure
  tolerance (`single`, `node-failure-tolerant`, later `zone-failure-tolerant`) and
  lists "readiness/liveness probes for services" as existing mitigation —
  implicitly leaving workers out. Whatever is decided here must be phrased in
  that vocabulary and land inside that work.
- **A guarantee applies only when the workload uses the capability.** A worker
  with no Kafka dependency must not be forced to satisfy a Kafka-shaped
  readiness promise.
- **Not every worker failure mode is readiness.** Broker-unreachable-at-startup,
  partition rebalance, and retry/DLQ consumer liveness are distinct states; the
  decision should say which (if any) are part of "available".

## Acceptance criteria

- A written decision states whether worker availability is a platform promise.
  If yes: the exact observable state, which primitives it binds to, and how it is
  surfaced (and whether Kubernetes' `Ready` condition is made to mean it). If no:
  every surface that currently implies otherwise, named and corrected.
- The decision is expressed in, or explicitly handed to, DEC-026's
  failure-tolerance vocabulary — this ticket does not define a parallel one.
- The claim is testable without a golden-path retry budget: given a worker whose
  consumers have not joined, the contract says whether Sol reports the workload
  available.
- No new implementation ticket is filed from this decision. It scopes AUDIT-080's
  worker-readiness slice once DEC-026 has fixed the vocabulary it must be
  expressed in.

## Non-goals

- Reproducing FEAT-082's lifecycle experiments (forced shutdown, redelivery,
  retry/DLQ exhaustion). Those are findings on record.
- Redesigning Kafka consumption, group-id strategy, or `fromBeginning` handling;
  `fromBeginning: false` is a legitimate worker choice, and the question here is
  what Sol *promises*, not which offset policy an application picks.
- Fixing the `sol_cli_check.mli` wording (evidence 7) — independently actionable.

**Demo/example coverage:** Not applicable; this is an architecture decision.

**TypeScript parity:** If worker readiness becomes an application-facing contract,
`@sol-fab/worker` must grow the equivalent of OCaml's `?on_ready` — today it has
no readiness concept. That parity work is fallout of this decision, not a
separate ticket filed ahead of it.
