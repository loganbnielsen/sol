**Depends on:** BUG-017 (root-cause hardening should eliminate the main trigger; this ticket covers the remaining local-developer ergonomics).

Running CLI tests or the pre-commit hook after a partially-populated `_build` can produce spurious failures that disappear after `rm -rf _build`.

## Problem

During INFRA-006, the exact same test command behaved differently depending on build-tree state:

- From a clean `_build`, `dune test framework/... cli/sol/test/` passed.
- After running `dune test cli/sol/test/` alone (or after other partial test invocations that populated `_build/default/framework`), the same full command failed with missing dashboard paths and `Multiple rules generated` in scaffold tests.
- The pre-commit hook then failed for the same environmental reason, even though the code itself was valid.

The root trigger is BUG-017, but the developer-facing symptom is broader: local test and commit-gate results are not reproducible across build-tree states. Engineers can waste time debugging non-regressions, and the current workaround (`rm -rf _build` before committing) is undocumented and easy to miss.

## Goal

The unit test suite and pre-commit gate should either be robust to a populated `_build`, or fail with a clear message telling the developer to clean the build tree — never a confusing `Multiple rules generated` / missing-`_build`-file failure.

## Remediation

- Fix BUG-017 first.
- If a populated build tree still leaves the scaffold tests order-sensitive, consider documenting `rm -rf _build` in `.claude/CLAUDE.md`'s Tests section, or having the pre-commit hook detect the known-bad state and print an actionable message.
- Optionally make the local test runner run the CI-equivalent single `dune test` invocation rather than leaving state from prior partial invocations.

## Acceptance criteria

- A developer can run `dune test cli/sol/test/`, then `bash cli/platform/local/scripts/run_tests.sh unit --no-infra`, without a false failure caused by the prior run's build-tree state.
- If a clean build tree is still required for some path, the failure message says so explicitly.
