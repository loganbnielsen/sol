**Depends on:** None.

**Related:** FEAT-076, DEC-021, BUG-028.

Premise note: retry consumers still appear to use `no_retry`; verify before
implementation, but do not use that buggy-state check as a `premise:` probe.

A single transient retry/DLQ publication failure permanently and silently stops retry
delivery for the life of the worker process.

## Problem

Both the source and retry consumers in
`framework/kafka-eio-service/lib/kafka_service_retry_topics.ml` are run through
`Kafka.Consumer.consume_partitioned` with `~retry:no_retry`, i.e.
`{ base_delay_s = 0.0; max_delay_s = 0.0; max_attempts = 0 }`.

In kafka-eio, `max_attempts = 0` with `n = 0` makes `exhausted` true on the first handler
`Error`. For the source consumer that surfaces as `Partition_errors` and fails the
worker. For the **retry consumer**, any `Error` from `retry_handler` — a retry-topic
produce failure, a DLQ produce failure (see BUG-028), or an ack failure — exhausts
immediately. The consumer signals stop, and the forked fiber:

```text
Error (Kafka.Consumer.Handler_errors errs) ->
  List.iter (fun (partition, e) -> Printf.eprintf "warn: ... retry consumer partition %ld: %s\n%!") errs;
  Kafka.Consumer.close retry_consumer
```

logs to stderr and closes the retry consumer. `Kafka_service_retry_topics.consume` already
returned `Ok ()` at that point, so:

```text
main worker keeps consuming the source topic   ← looks healthy
retry delivery is permanently stopped          ← stderr only, no metric
```

The retry consumer has no retry at all, so the first transient produce failure is
terminal for the whole relay. Additionally, `on_retry` fires *before* the produce
(`publish_raw`), so a failed publication is still counted as a scheduled retry.

This violates the acknowledgement ownership invariant (`framework/sol-worker/sol-worker.md`):
a publication that never durably transferred must not be treated as delivered.

## Required behavior

- Retry/DLQ publication must be resilient: bounded in-process retry with backoff and
  jitter around the produce, rather than one attempt whose failure is terminal.
- A relay stop must be observable, not stderr-only: emit a metric and surface the stop
  to the worker's outcome (fail loudly) or emit a distinct degraded-state signal. No
  silent degradation.
- A single transient produce failure must not tear down the retry consumer.
- Decide and document whether a persistently failing relay should stop the worker
  (fail loudly) or keep retrying; either is acceptable, silent stoppage is not.

## Acceptance criteria

- A transient produce failure does not permanently stop retry delivery.
- Relay stoppage/exhaustion emits a metric and an `Error`-level log, and is reflected in
  the worker's result.
- Retry metrics distinguish scheduled vs published vs failed (today `on_retry` counts
  scheduled only).
- The retry consumer's exhaustion policy is explicit and documented, not an accidental
  consequence of `max_attempts = 0`.

## Non-goals

- Retry buckets or a second retry backend.
- Changing the source consumer's exhaustion behavior.

## Completion notes

- **Bounded in-process retry with backoff+jitter** (`retry_produce`,
  `produce_backoff_s` in `kafka_service_retry_topics.ml`): `publish_raw` now
  retries the produce call itself up to 5 times with exponential backoff
  (0.1s base, 5s cap, ±20% jitter) before giving up. A single transient
  produce failure no longer reaches `consume_partitioned`'s zero-tolerance
  policy at all. These are internal constants scoped to this ticket, not the
  user-facing `retry_policy` vocabulary FEAT-078 will introduce. The jitter
  RNG is a module-scoped, mutex-protected `Random.State.t` (never the global
  `Random` module — this repo has been bitten twice by that).
- `retry_produce`/`produce_backoff_s` are extracted and exposed
  (`kafka_service_retry_topics.mli`, `Kafka_service.Retry_topics`) so the
  attempt-counting/give-up behavior is unit-tested with stubbed
  `produce`/`sleep` — no live broker needed. 6 new tests in
  `test_kafka_service.ml`'s `retry_topics` group.
- **Relay failure is observable and fail-loud, deliberately** (`consume` in
  `kafka_service_retry_topics.ml`): the forked relay fiber sets a
  `relay_failure` ref and logs at `error:` level (`RETRY_RELAY_STOPPED`) the
  moment its own `consume_partitioned` call exhausts. Once the source
  consumer itself stops for any reason, the function checks that ref and
  turns an otherwise-`Ok` result into `Error` if the relay had failed. This
  is the documented exhaustion policy: **a relay that died and never
  recovered fails the worker** rather than leaving it running silently
  degraded. Not implemented as immediate, live cancellation of the source
  consumer the instant the relay dies (which would need
  `Eio.Switch.fail`-based teardown-and-race) — the source keeps consuming
  until it stops for its own reasons, at which point the relay failure is
  guaranteed to be reflected. Simpler, still correct against the acceptance
  criterion ("reflected in the worker's result"), at the cost of not being
  instantaneous for a long-lived healthy source sitting on top of a dead
  relay — noted as a possible follow-up if that gap matters in practice.
- **Retry metrics distinguish scheduled vs published vs failed**: a new
  `on_relay_publish:(partition:int32 -> attempt:int -> outcome:[`Published |
  `Failed] -> unit)` callback (required at the `Kafka_service_retry_topics.consume`
  layer, optional with a no-op default on the public
  `Kafka_service.consume_partitioned`) fires once produce either succeeds or
  exhausts retries — distinct from the existing `on_retry`, which still means
  "scheduled" (fires once per record, before publication is attempted, as
  before). Wired into `sol-worker`'s own metrics: `sol_worker_messages_total`
  gained `relay_published`/`relay_failed` status values (`worker.ml`,
  documented in `worker.mli` and `sol-worker.md`). A sustained run of
  `relay_failed` without a matching drop in `retry` is now the metric-level
  signal for exactly the silent-degradation failure this ticket fixes.
  **Known gap, pre-existing and not worsened by this change:** `on_retry`
  (and now `on_relay_publish`) fire only inside `Kafka_service.consume_partitioned`'s
  real `Retry_topics` path; `test_worker.ml`'s `test_consume_loop` injection
  seam drives `W.handle` directly and bypasses that path entirely, so neither
  callback has unit coverage in `sol-worker`'s own test suite (this predates
  BUG-029 — `on_retry` was already untested the same way). Not fixed here;
  would need lifting the metric-emission closures out of `worker.ml` into
  testable functions, which is unrelated scope.
- **`kafka-eio-service.md` documents the exhaustion policy** (added to the
  `Retry strategy` section, right after DOCS-015's ordering/HOL content) and
  `sol-worker.md`/`worker.mli` document the new metric labels. These were
  deliberately deferred past the first commit on this branch until DOCS-015
  (#256) merged, since they're the exact files it was concurrently editing;
  this branch was rebased onto the merged result before adding this content,
  so there was no conflict to resolve.
- Full local suite (unit/kafka/e2e) passes; `dune fmt` clean.
- No demo/example update: this is an internal resilience/observability fix
  to `kafka-eio-service`'s retry relay, not a new app-author-facing
  primitive, CLI command, or generated manifest.
