title: Sol workspace identity and root resolution

**Depends on:** None.

**Related:** DEC-022 (clauses 7, 8), DEC-013, DEC-023, BUG-034, FEAT-082,
FEAT-084.

## Context

There was no Sol-owned answer to *"what workspace am I in?"*. `sol up` inferred
its root with `find_repo_root`, walking up for `dune-project`/`dune-workspace`
(`cmd_up.ml:17-28`), while `sol.yml` was loaded relative to cwd
(`sol_cli_config.ml:1017`). Two incompatible ideas of location, and the only one
that walked upward was keyed on a language build system. It worked while every
meaningful Sol application was OCaml. **BUG-034** exposed it: a workspace without
dune markers resolves its build context outside itself, and a TypeScript-only
workspace (DEC-022) would resolve it to `/`.

## Decision

**A Sol workspace is a directory containing `sol.yml`.** Its *presence*
establishes the workspace boundary; its *contents* define optional workspace
configuration. The analogue is a product-owned manifest (`Cargo.toml`,
`go.mod`) — not because Sol infers identity from ecosystem files, but because
having your own manifest define the project boundary is the well-understood
model.

1. **`sol.yml` is the workspace manifest.** Every workspace scaffold emits it,
   even when defaults suffice. Do **not** add `workspace: <name>` merely to
   justify the file's existence unless Sol actually needs a persistent workspace
   name.
2. **A workspace is a non-nestable application boundary.** `find_root(cwd)`
   walks ancestors until it finds the workspace's `sol.yml`, so commands may run
   from **any descendant directory**. **Nested Sol workspaces are not
   supported**: a workspace must not contain another workspace boundary, and
   validation/discovery fails clearly when one does.

   ```text
   repo/                      company/
   ├── frontend/              ├── product-a/   sol.yml   <- sibling workspaces
   ├── docs/                  ├── product-b/   sol.yml   <- are fine
   └── backend/               └── frontend/
       ├── sol.yml                (no sol.yml)
       └── app/...
   ```

   Multiple Sol workspaces as **siblings** are fine; one inside another is an
   error. Rationale: nesting immediately raises undefined questions (does the
   outer `sol check` include the inner? may `--scope` cross the boundary? is the
   inner part of the outer release/workspace? can inner units reference outer
   events/config?) and buys no product capability in return. It is also the
   **reversible** direction: disallowing nesting now leaves room to define
   nested-boundary semantics later if corporate monorepos ever genuinely need
   it, whereas permitting it and restricting later would break repositories
   users had already structured around it.
3. **`find_root(cwd)` is authoritative.** It is the single boundary abstraction:
   `config = root/sol.yml`, discovery = `root/app/...`, build context derives
   from `root`. No command re-derives location from cwd independently.
4. **Every workspace-aware command resolves the same root from any descendant
   path.** `cd app/payments/api_svc && sol check | sol up | sol logs` act on the
   workspace. Configuration paths resolve relative to the resolved root, not the
   invocation cwd.
5. **No build-system inference or fallback.** Root discovery never consults
   `dune-project`, `package.json`, `pom.xml`, `.git`, or any ecosystem marker,
   and there is no permanent `sol.yml OR dune-project` compatibility path — that
   would preserve the violation (DEC-022 clause 8).
6. **Absence fails closed**, with guidance rather than inference:

   ```text
   sol: not inside a Sol workspace (no sol.yml found)

   A Sol workspace is identified by sol.yml.
   Run this command from an existing Sol workspace, or create one with
   `sol new workspace <name>`.
   ```

   No `sol init` is introduced as migration machinery. Adding `sol.yml` by hand
   is fine during the clean break (there are no external users). If adopting Sol
   into an arbitrary existing repository later shows genuine demand, *that* —
   not this migration — would justify `sol init`.

## Rejected alternatives

- **A separate identity marker** (e.g. `.sol/workspace`) alongside optional
  configuration: a distinction without independent meaning — if `sol.yml` exists,
  the directory is already describing a Sol workspace — and it adds ambiguity
  about which artifact owns the boundary, whether config can be absent, and
  whether there can be nested config.
- **An empty `.sol-root` sentinel.**
- **Adding `package.json`/`pom.xml` to the existing heuristic** — the leak
  DEC-022 clause 8 exists to catch: teaching workspace identity what each
  language is.

## Consequences

- **BUG-034** remains the bug that exposed the violation and becomes the
  *implementation* of this contract; it depends on this decision.
- **DEC-022 clauses 7/8** reference this decision for workspace identity, rather
  than a historical TypeScript build bug.
- **FEAT-084**'s scaffold must emit `sol.yml` for a TypeScript workspace.
- Existing workspaces need `sol.yml` added once (clean break).

## Acceptance criteria

- `find_root(cwd)` resolves the workspace `sol.yml` from any descendant
  directory; config loading, unit discovery and build-context construction all
  consume that root.
- Scaffolds always emit `sol.yml`.
- No ecosystem-marker inference or fallback remains in root resolution.
- The fail-closed message names the fix (`sol new workspace <name>`).
- Regression coverage: workspace with no dune marker; unit build-system markers
  present in an enclosing repo (OCaml and Node); mixed OCaml+TS workspace;
  descendant cwd; sibling workspaces both resolve independently; **nested
  workspace (`outer/sol.yml` + `inner/sol.yml`) → explicit nested-workspace
  error, not silent shadowing.**
