**Depends on:** DEC-026.

## Question

Choose the authoritative reconciliation model for the first
`production-single-region` profile. The current implementation supports two
different ownership shapes and must not blur them into one promise.

DEC-026 goes first so this decision is evaluated against concrete production
guarantees and required evidence, not as a philosophical preference for or
against GitOps.

### Option A: disciplined imperative deployment

Sol renders the complete desired state, acquires the mutation lease, applies,
waits, verifies and records the outcome. Kubernetes owns ordinary object-level
reconciliation after the command exits. `sol status/check` detects collection
drift from the recorded release, but Sol does not silently reverse out-of-band
changes.

### Option B: continuous GitOps reconciliation

Git plus Argo CD/Flux is authoritative. The controller owns drift correction;
Sol must integrate release history, health evidence and rollback with that
authority rather than relying on direct-mode records and leases.

## Existing evidence and constraints

- Direct mode already has render-before-apply, a boundary lease, rollout waits,
  content-addressed releases, deployment attempts and verified rollback.
- GitOps emission exists, but it does not acquire the lease or create Sol's live
  release/deployment history. Rollback correctly refuses controller-owned state.
- Continuous Sol-level reconciliation is not required for maturity A.
- The unselected model may remain available as an explicitly non-conformant
  export/experimental lane; it must not inherit the production claim.

## Acceptance criteria

- One model is named as normative for the first production profile.
- Desired-state authority, drift behavior, secret ownership, rollback ownership,
  failed/partial deployment behavior and operator recovery are explicit.
- The decision says what `sol status/check` compares and whether it detects or
  corrects divergence.
- Downstream tickets can implement and test one unambiguous path.
- The audit's warning-only recommendation is either confirmed for a non-profile
  GitOps lane or replaced by real GitOps integration work; it is not treated as
  a production guarantee by itself.

## Decision (2026-09-17)

**Option A — disciplined imperative deployment — is normative for
`production-single-region`.** This is not a preference call: inspecting the
actual implementation shows Option A's mechanics already exist and work as
described, while Option B's mechanics do not exist at all. Adopting Option B
today would mean building a GitOps integration from nothing under a
production-readiness decision that is explicitly scoped not to add
implementation (DEC-026's own precedent). Concretely, as read from
`cli/sol/bin/cmd_deploy.ml` and `cli/sol/lib/sol_cli_rollback.ml`:

- `run_apply` already renders the complete plan, acquires
  `Sol_cli_boundary_lease` (`holder:Deploy`), applies under the lease
  (refreshing it via `ensure_held` between workloads), and only on a
  successful outcome calls `record_release_and_prune` — a failed attempt is
  recorded as failed and **never** writes a release
  (`execute_deployment_attempt`'s own comment: "a failed attempt cannot claim
  a release exists").
- `run_emit` (`--emit-to`) renders the same plan but calls none of
  `Sol_cli_boundary_lease`, `Sol_cli_release_store.record_plan`, or
  `Sol_cli_deployment_attempt.record` — confirming the audit's finding #8
  exactly: the GitOps path has no lease, no release history, and no
  deployment-event record today, not a smaller version of Option A's
  guarantees but their absence.
- `Sol_cli_rollback.execute` already refuses a `Gitops`-recorded release
  outright (`check_apply_mode`/`Gitops_owned`) — direct mutation cannot
  safely re-verify a controller-owned rollout, so Option A's rollback has
  never been able to operate on Option B's output, and building that bridge
  is exactly the "real GitOps integration work" this decision declines to
  start.

### Desired-state authority

For a target on `production-single-region`, **the recorded release — the
immutable per-release ConfigMap plus the mutable current-release pointer
(`Sol_cli_release`) — is the sole desired-state authority**, not the live
cluster and not a Git repository. A workload's actual live state is evidence
to compare against that authority, never a second source of truth for what
*should* be running.

### Drift behavior: detect, never correct

`sol status`/`sol check` **detect** divergence between the recorded current
release and live cluster state; **Sol never silently corrects it.** The
comparison already has a name and a working implementation — it just isn't
wired to a standalone command yet:

- `Sol_cli_rollback.live_workloads` enumerates every live Sol-owned
  Deployment/Rollout/CronJob for the workspace by its taxonomy label.
- `Sol_cli_rollback.verify_workloads` compares that live set against the
  workload set reconstructed from a given release
  (`service_specs_of_release`), producing a `workload_report` of
  `mismatched` / `missing` / `unexpected` objects.
- This exists and runs today, but only inside `sol rollback`'s own
  post-apply verification. AUDIT-069 owns making it (or an equivalent
  read-only call) the drift check `sol status`/`sol check` run against the
  **current** recorded release outside of a rollback — no new comparison
  primitive needs inventing, only wiring an existing one.
- `report_surplus_workloads` in `cmd_deploy.ml` already establishes the
  "detect, don't correct" precedent in practice: on a whole-workspace deploy
  it reports live objects the new plan doesn't include and says, verbatim,
  "delete them by hand if you want them gone now" — it does not delete them.
  `sol status`/`sol check`'s drift report follows the same rule for every
  divergence category (`mismatched`/`missing`/`unexpected`), not only
  surplus: reported, never auto-reconciled. `unexpected_workloads` describes
  only the surplus category; `verify_workloads`' full mismatched/missing/
  unexpected comparison is what AUDIT-069 wires to the always-on check,
  since surplus is not the only drift a production target must be able to
  see.
- Kubernetes owns ordinary object-level reconciliation (restarting a crashed
  container, replacing an evicted pod) after `sol deploy`/`sol up` exits.
  Sol's drift detection operates one level up: whether the *collection* of
  live objects still matches what the recorded release says should exist.

### Secret ownership

Ownership follows the mechanism already gated by `--emit-to` in
`cmd_deploy.ml`'s `secret_backend_term`: `external-secrets` is rejected
outside `--emit-to` and is the only backend meaningful with it. For
`production-single-region` (Direct mode, below): **Sol templates the Secret
manifest and applies it itself**; populating and rotating the value is an
operator/CI responsibility outside this decision's scope (SEC-004 owns the
rotation mechanism, using this same authority). Sol never stores a secret
*value* in a plan, release record, or evidence bundle (already an existing,
unconditional invariant — DEC-026 §7 restates it). The `external-secrets`
backend remains real and available, but only for the non-profile `--emit-to`
lane below; a target claiming the profile does not get to combine Direct
apply ownership with controller-owned secret sync — that would split
authority exactly the way this decision exists to prevent.

### Rollback ownership

`sol rollback` is the sole rollback mechanism for a `production-single-region`
target, and it already implements the correct ordering
(`Sol_cli_rollback.execute`): refuse a `Gitops`-owned release outright, refuse
across an unresolved migration boundary, reconstruct the target release's
workload set, apply, independently re-verify the live set against it, prune
only the purely-unexpected surplus, and move the current-release pointer only
after that verification passes. No change to this mechanism is needed or
proposed here; this decision only confirms it as the profile's rollback
authority, since Option A is what it already assumes.

### Failed/partial deployment behavior

Already implemented and hereby confirmed as the profile's contract, not
merely today's incidental behavior: a deploy attempt is recorded exactly once
(`Sol_cli_deployment_attempt.record`), whatever its outcome; **the
current-release pointer and the release record advance only on a verified
success.** A failed or partial apply leaves the prior release authoritative,
with the failed attempt itself preserved as a diagnostic event
(`sol deployments`), never silently retried or silently promoted.

### Operator recovery

Recovery after a failed or drifted deploy is human/CI-initiated, not
automatic: the boundary lease is released (or expires by TTL) so it never
strands a workspace; the operator runs `sol status`/`sol check` to see what's
actually live against what's recorded, then either re-runs `sol deploy` (a
repeated desired release is idempotent per DEC-026 §5's evidence bundle
expectations) or `sol rollback`s to the last good release. Sol does not
attempt self-healing beyond what Kubernetes already does at the object level;
this decision does not add one.

### The GitOps (`--emit-to`) lane: confirmed non-conformant export, not upgraded

`--emit-to` remains available exactly as today — a real, useful "Exported
Self-Managed" lane (DEC-018/FEAT-066's existing scope decision) for a team
that wants Argo CD/Flux to own its own reconciliation. This decision does not
withdraw it and does not build the "real GitOps integration" that would be
needed to make it Option B. Two consequences, both already achievable without
new mechanism:

1. **A target selecting `production-single-region` cannot use `--emit-to` as
   its reconciliation path.** FEAT-089's preflight validation (DEC-026 §4)
   must reject `Deploy_emit_to` for a profile-selected target the same way it
   rejects an unsupported Kubernetes version — named, before mutation.
2. **For the non-profile lane, the audit's warning-only recommendation is
   confirmed, not replaced.** `run_emit` should print an explicit notice that
   the emitted bundle carries none of Sol's boundary-lease, release-history,
   or rollback safety — a cheap, honest label on a real and legitimate
   escape hatch, not a claim that it is safe for unattended production use.
   This is the full extent of what this decision requires of the GitOps
   lane; it is explicitly not a production guarantee, and no further GitOps
   integration work is authorized or implied by this decision.

## Consequences

- **Migration ordering (AUDIT-069) is scoped, not decided, here**: this
  decision names Direct mode as the sole production authority so AUDIT-069
  can pick its migration-preflight contract (orchestrate vs. verify-applied)
  against one concrete apply path, but that sub-decision remains AUDIT-069's,
  not repeated here.
- AUDIT-069, AUDIT-072, FEAT-050, FEAT-089 and SEC-004 each have the one
  unambiguous authority, drift, secret, rollback, failure and recovery model
  above to implement against; none of it is implemented in this decision.
- No new mechanism is required to state this decision: every claim above
  cites code that already exists. The remaining work is wiring
  (`verify_workloads` into a standalone drift check, `--emit-to` rejection
  into FEAT-089's preflight, the `run_emit` notice) — small, and downstream's
  to do.
