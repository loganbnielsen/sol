**Depends on:** None (DEC-012 decided the licence; this decides whether a CLA is needed on top of the DCO).

Decide whether contributions require a **CLA** in addition to (or instead of) the DCO sign-off.

## Question

DEC-012 placed the project under Apache-2.0 and INFRA-007 established the DCO sign-off as contributor terms — as *policy*, not an enforced check. That is now known to be narrower than it first appeared: a DCO is an **origin statement, not a rights grant**. It certifies that a contributor had the right to submit under *this* project's licence; it does **not** permit relicensing their contribution under different terms.

So: if Sol ever needs to change the licence for code it did not write — for example tightening it to stop a reseller, which the open-core discussion (DOCS-015) explicitly holds open — a DCO will not be enough. Every notable relicensing (Elastic, MongoDB, Redis, HashiCorp, Grafana) required a CLA for exactly this reason.

## Options

1. **DCO only.** Lightest. Accepts that the project can never tighten the licence for outside contributions without tracking down every contributor.
2. **CLA required for all contributions.** Preserves full licence flexibility; costs a legal document, a signature flow (usually a bot) and real contributor friction.
3. **CLA only for the sensitive parts** (e.g. anything a hosted tier depends on), DCO elsewhere. Preserves the option where it matters, keeps friction off the rest.
4. **Decide later, with a trigger.** Stay DCO-only for now, and revisit *before* actively soliciting contributions — the point at which the choice stops being reversible without chasing people.

## Decision criteria

- Is tightening the licence a realistic future move? If not, option 1 is correct and a CLA is pure overhead.
- Apache-2.0 already permits proprietary derivatives and running a paid service, so **the hosted tier does not itself require a CLA** — this is only about licence *changes* to contributed code.
- The CLA text is the substance, not the decision: it needs counsel, and its terms (licence grant vs assignment, sublicensing rights) determine whether it is worth the friction.
- Timing is asymmetric: cheap now (one contributor, no outside code), expensive after adoption.

## Decision

**The project is not accepting outside contributions yet, and will not until the contributor terms are settled.**

The two mechanisms differ in exactly one way that matters — whether the project can later change the licence for contributed code — and that difference is only meaningful *before* code lands. After several contributors it is not realistically reversible without tracking each of them down. So the honest posture is to decide first and accept contributions second, rather than accept code under DCO-only terms while the question is open and silently foreclose the option.

Concretely, what this means:

- `CONTRIBUTING.md` states plainly that pull requests are not being accepted, why, and what *is* welcome (issues, security reports, questions) — so an uninvited contribution does not land by default.
- The DCO/CLA choice remains open, with both mechanisms described so a prospective contributor understands what will eventually be asked.
- The decision is revisited when contributions are actively solicited, which is the point at which the choice stops being free.

**Why not decide the mechanism now?** Because it is cheap to defer only while nobody is contributing, and the deferral costs nothing: this option is not "decide later and hope", it is "gate the thing that would foreclose it". If the project later wants contributors and a CLA, the gate is already in place.

**Why not DCO-only permanently?** That is a defensible answer too — most small projects take it — but it means accepting that the licence can never be tightened on contributed code, and every notable relicensing (Elastic, MongoDB, Redis, HashiCorp, Grafana) shows what that forecloses. Given the open-core plan (DEC-012/DEC-013) keeps licence options deliberately open, giving one away by default would be inconsistent.

**Acceptance criteria:** the policy is named ✅; no CLA text is required yet, because none is being asked for ⏳; and `CONTRIBUTING.md` reflects the outcome ✅.
