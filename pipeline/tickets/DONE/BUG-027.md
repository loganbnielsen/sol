**Depends on:** None.

**Related:** FEAT-076 (the ticket this closes a gap in), DEC-021.

`Retry_topics`' retry-topic consumer serializes all partitions through one fiber with a blocking sleep, and drops the message key on republish — both violate FEAT-076's own "a poison message does not block unrelated messages" acceptance criterion.

**Description:** `Kafka_service_retry_topics.consume` (`framework/kafka-eio-service/lib/kafka_service_retry_topics.ml:228-273`) provisions the `<topic>-retry` topic with the same partition count as the source topic, but drains it with one hand-rolled `let rec loop () = Kafka.Consumer.fetch retry_consumer ...` fiber instead of `Kafka.Consumer.consume_partitioned` (which the *source* topic already uses, and which `kafka-eio-service.md` documents as giving per-partition fiber isolation for the `In_memory` strategy). That loop does a real blocking `Eio.Time.sleep clock delay` (line 265) before re-running the handler on each retried message, one message at a time, in strict fetch order across all partitions.

Consequence: a message with a long backoff sitting earlier in the retry topic's fetch order blocks every retried message behind it — even ones on unrelated partitions whose own delay has already elapsed. This is exactly the "poison message blocks unrelated messages" failure FEAT-076 exists to prevent; it now just happens one hop downstream, in the retry lane instead of the source topic.

Separately, `publish_raw` (same file, ~line 137) calls `Kafka.Producer.produce_await` without `~key`, even though the original message's key is available (`raw_msg.Kafka.Consumer.key : bytes option`, per `~/Code/kafka-eio/lib/kafka_consumer.mli`). Since the retry topic has the same partition count as the source topic, preserving the key on republish is what makes "same key → same partition" hold for retried messages too; dropping it means a retried message's partition placement is uncorrelated with its original partition/key, which undermines both the fix above (partition isolation only means something if related messages land in a predictable partition) and per-key ordering more generally.

**Remediation:**
1. In `publish_raw`, thread `raw_msg.Kafka.Consumer.key` through to `Kafka.Producer.produce_await`'s `?key` argument, so a retried message hashes to the same partition on `<topic>-retry` that its key would hash to on the source topic (both topics share `svc.partitions`).
2. Replace the retry consumer's manual `fetch` loop with `Kafka.Consumer.consume_partitioned retry_consumer ~sw ~clock ~handler:... ()`, so the per-message backoff sleep blocks only its own partition — matching what `kafka-eio-service.md` already documents for `In_memory` and closing the actual gap against FEAT-076's acceptance criterion.
3. Update `kafka-eio-service.md`'s `Retry_topics` doc block to state both properties explicitly (key preserved; per-partition isolation applies to the retry topic, not just the source topic).
4. Add a regression test pinning key preservation on republish (unit-level: assert `produce_await`'s captured `key` argument matches `raw_msg.key`), and confirm via `framework/kafka-eio-service/test/test_kafka_service_integration.ml`'s existing `retry_topics` suite (or an addition to it) that this doesn't regress.

**Non-goal:** this does not make Kafka retry-topics give true per-message-independent (key-agnostic) leasing — two retries sharing a key still serialize by design, same as the source topic. That's the correct, permanent boundary DEC-021 records as the reason `sol-jobs` (FEAT-077) exists; this ticket only fixes the *accidental* cross-partition blocking, not the *structural* same-key serialization.

## Completion notes

- `publish_raw` now takes `~key` and forwards it (`?key`) to
  `Kafka.Producer.produce_await`; both call sites in `execute_action`
  (`Forward_retry`/`Forward_dlq`) pass `raw_msg.Kafka.Consumer.key`.
- The retry consumer's manual `let rec loop () = Kafka.Consumer.fetch ...`
  is replaced by `Kafka.Consumer.consume_partitioned retry_consumer ~retry:no_retry
  ~handler:retry_handler ()`, run inside the same `Eio.Fiber.fork` as before.
  `retry_handler` parses `X-Sol-Attempt`/`X-Sol-Retry-At`, sleeps for the
  remaining delay, then calls the existing `decode_retry`. Because this now
  runs per-partition (`consume_partitioned`'s own contract), the sleep blocks
  only that partition and librdkafka pauses it for the duration — the
  manual `ack`/`acked`-ref bookkeeping the old fetch loop needed is gone too,
  since `consume_partitioned` supplies a framework-managed `ack` per message
  the same way it already does for the source topic's `decode_and_handle`.
  `no_retry` (`{base_delay_s=0.; max_delay_s=0.; max_attempts=0}`) is hoisted
  once and shared by both `consume_partitioned` calls in this function.
- The stale `ponytail:` comment about `kafka-eio 0.1` hiding `Kafka_raw` is
  removed — the concern it raised (no partition pause during backoff) is
  exactly what `consume_partitioned` already provides, so there's nothing
  left to revisit.
- `kafka_service.mli`'s public `Retry_topics.execute_action` re-export
  (a separate copy of the same type, exposed for tests) needed the same
  `~key:bytes option` addition — caught by the build, not by inspection.
- `kafka-eio-service.md`'s `Retry_topics` doc block now states both
  properties (key preserved on republish; per-partition isolation applies to
  the retry topic) and explicitly names the same-key-serialization limit
  that remains, pointing at DEC-021.
- New unit test `retry_topics — retry publish preserves the message key`
  (`test_kafka_service.ml`) asserts `execute_action`'s `publish_raw` receives
  the original message's key unchanged. All existing `kafka_service`,
  `kafka_service_integration` (live broker), and `sol_worker` suites pass
  unchanged.
- Not added: an end-to-end live-Kafka test asserting two different
  partitions' retries don't block each other under real timing. No such test
  existed before this ticket either (the repo's only `Retry_topics` coverage
  was the unit-level logic tests extended here); a reliable timing-based
  integration test for this is a proportionally bigger effort than this fix
  and is better scoped as its own ticket if it's ever needed.
- No demo/example update: this is an internal correctness fix to
  `kafka-eio-service`'s retry-topic consumer, not a new app-author-facing
  primitive, `sol.toml` field, CLI command, or generated manifest.
