**Depends on:** DEC-026, DEC-027.

## Production guarantee

A production workload receives no ambient Kubernetes credential unless its
declared capability requires one, and supported runtime credentials can be
rotated through the selected reconciliation path without undefined behavior.

Per-workload ServiceAccounts, NetworkPolicies and Secret/ExternalSecret support
already exist. The generated ServiceAccount does not disable token automount,
and no existing ticket owns runtime credential rotation. FEAT-053 covers
build-time secret declarations and is not a substitute.

## Decision boundary

Engineering must decide the smallest Sol-level declaration for a workload that
genuinely needs Kubernetes API access and the supported rotation mechanism for
the authority selected by DEC-027. Do not expose service-account token or secret
volume implementation knobs as the application semantic.

## Implementation scope

- Disable ambient service-account token automount by default.
- Add an explicit, reviewable capability only if a supported workload needs API
  access.
- Define the runtime-secret refresh/restart behavior Sol actually supports.
- Keep workload identity federation, service-to-service authorization, admission
  policy and multi-team RBAC out of maturity A.

## Conformance and acceptance criteria

- A default workload pod has no Kubernetes API token mounted.
- A declared API-access exception, if supported, receives only the documented
  permission and is denied an unrelated operation.
- Rotating a representative database or API credential causes new application
  use of the new value, revokes the old value and returns the workload to healthy
  state without hand-editing generated manifests.
- Logs, plans, release records and conformance evidence contain no secret value.
- HARDEN-002 records the credential-rotation result.

**Demo/example coverage:** The production-profile example documents the supported
rotation operation using disposable credentials; no real secret is committed.

**TypeScript parity:** Credential injection and rotation are platform semantics
and apply equally to every supported language.

## Outcome (2026-09-17)

Implementation and offline proof are here; the live rotation result is
HARDEN-002's, per the ticket's own implementation/evidence split.

- **No ambient token, by construction.** `service_account_doc` renders
  `automountServiceAccountToken: false`, and every Sol workload uses that
  ServiceAccount, so a default pod has no mounted Kubernetes API token. The
  contract doc `docs/deployment/credential-rotation.md` records it.
- **Preflight now establishes `credential_posture`.** It is a Sol-owned property
  of the rendered plan (not a target/application choice), so it is Established
  for every profile plan; the exhaustive preflight test drops it from the
  unmet list, and a dedicated test asserts the direct `establish` result.
- **No API-access capability in maturity A.** Per the decision, no
  `kubernetes_api`-style knob is added: without a meaningful least-privilege
  permission model, the honest posture is "no workload gets ambient API access"
  rather than a switch that grants more than it documents. Workload identity
  federation / multi-team RBAC remain out of scope (DEC-026 §7).
- **Rotation is update + verified restart.** `sol secret set` already patched
  the shared and per-workload Secret objects and requested a restart; SEC-004
  replaces the fire-and-forget restart with `restart_and_verify`: it restarts
  every live Deployment (and Rollout when present), waits for
  `kubectl rollout status --timeout=120s` on each, and **fails the operation**
  if any workload does not return to healthy state. The env-var contract is
  kept deliberately (a running pod never observes a rotated value, so the
  restart is what makes the new value take effect); file-mounted refresh and
  versioned secret names are explicitly out of scope.
- **No secret value in a plan, release record, log line or evidence bundle** —
  the value is written to the same Secret object in place, so there is no second
  copy to leak (DEC-026 §7 invariant).

Premise check: the renderer had no `automountServiceAccountToken` setting, and
the restart call site ignored its result, so both gaps were real.

**Implementation versus evidence:** offline proof is the render test across
`-svc`/`-worker`/`-fn` (ServiceAccount disables automount, pod does not
re-enable it) and the preflight tests. HARDEN-002 must rotate a disposable
credential against a real target — new value in use, old value revoked, every
workload healthy — and confirm no secret value appears in the evidence bundle.

**Demo/example coverage:** `docs/deployment/credential-rotation.md` documents
`sol secret set` as the rotation operation over disposable credentials; no real
secret is committed.

**TypeScript parity:** Credential injection and rotation are platform semantics
and apply equally to every supported language.
