**Depends on:** DEC-026.

## Production guarantee

A required production alert reaches a named accountable human through a tested
route and supplies a usable first response action. Dashboards, firing rules, a
configured receiver, SLOs and runbooks are parts of that guarantee; none is
sufficient alone.

OBS-040 shipped useful alert rules with a deliberate null receiver. The original
OBS-043 proposed one PagerDuty example, while the audit proposed warning about the
null receiver. This ticket replaces both mechanism-level scopes.

## Decision boundary

DEC-026 names the minimal platform/workload indicators and objectives the first
profile claims. Engineering must define a provider-neutral target capability for
alert delivery and ownership. PagerDuty may be the first adapter, but it is not
the Sol-level semantic.

## Implementation scope

- Define the minimal maturity-A SLO/indicator set and alert conditions.
- Require target-owned receiver and owner metadata for the production profile.
- Validate the route rather than merely checking that configuration is non-null.
- Add one-page runbooks for failed rollout, node loss, Postgres dependency
  loss/restore, Kafka lag/broker loss and telemetry loss.
- Provide the smallest working receiver integration needed by the selected pilot
  team; retain null routing for local/dev only.
- Add a synthetic alert path that can prove delivery without causing a real
  outage.

## Conformance and acceptance criteria

- A synthetic alert sent through the production route reaches the named on-call
  destination and is acknowledged.
- Missing/unroutable receiver or missing owner/runbook evidence makes production
  conformance fail before the pilot.
- Every required production alert identifies an owner and links to its first
  response runbook.
- Game-day records show the team used the runbooks for the failure scenarios
  claimed by DEC-026.
- Telemetry loss produces its explicitly documented degraded operating mode; it
  is not assigned the same durability guarantee as business data by accident.

## Non-goals

- Building a paging product, incident-management system or organization-wide
  escalation policy.
- Requiring PagerDuty specifically in the public profile.
- Multi-team ownership/governance.

**Implementation versus evidence:** This ticket defines and wires the response
contract. HARDEN-002 proves end-to-end delivery and records game-day evidence.

**Demo/example coverage:** Document and exercise the synthetic alert against the
production-profile example; do not commit real routing credentials.

**TypeScript parity:** Not language-specific; alert labels and ownership metadata
must remain consistent across supported workload languages.

## Outcome (2026-09-17)

The response loop is defined and wired. Implementation and offline proof are
here; delivered-and-acknowledged evidence is HARDEN-002's, per the ticket's own
implementation/evidence split.

- **The contract is provider-neutral.** `Sol_cli_alerting` owns the vocabulary:
  a receiver *type* (only `webhook` is qualified for maturity A), a routable
  http(s) endpoint, an accountable owner, and a first-response runbook. PagerDuty
  is an adapter over this contract, never the Sol semantic — DEC-026 §8's
  "requiring PagerDuty specifically" non-goal is honoured. A target declares
  `alert_receiver_type`/`alert_receiver_url`/`alert_owner`/`alert_runbook_url`.
- **Preflight fails closed.** `Alert_delivery` is now a real target-side check:
  it names the missing/unqualified declaration, so missing or unroutable
  receiver/owner/runbook fails production conformance before the pilot.
- **The five maturity-A indicators exist as threshold rules** (not burn-rate
  SLOs): failed rollout (`SolRolloutFailed`), node loss (`SolNodeNotReady`),
  Postgres dependency (`SolPostgresUnavailable`), Kafka lag/broker loss
  (`SolKafkaConsumerLagHigh`/`SolKafkaBrokerDown`), telemetry loss
  (`SolTelemetryTargetDown`), each carrying owner + `runbook_url`. Postgres and
  Kafka signals are scrape-dependent and silent (never false-positive) when the
  target exposes no such metric; that dependency is stated in the docs and the
  runbook. The OBS-040 "deploy failure skipped" gap is closed by the
  kube-state-metrics rollout indicator.
- **One-page runbooks** for all five live in
  `docs/deployment/alert-runbooks.md`.
- **The receiver is wired from the declaration.** Applying
  `cli/platform/infra/base` with the alert values routes Alertmanager to a
  `webhook_configs` receiver; empty values keep the deliberate OBS-040 dev null
  receiver.
- **A synthetic alert path exists.** `sol alert test --target <t>` validates the
  same contract and injects one synthetic alert into Alertmanager's v2 API
  (`--dry-run` prints without sending). It proves the route accepts an alert; it
  deliberately does not claim a human was paged.
- **Telemetry loss is documented as an explicit degraded mode**, never assigned
  business-data durability.

**Implementation versus evidence:** the contract, rules, runbooks and synthetic
path are implemented and offline-tested (config parse, `Sol_cli_alerting`
validation, preflight established/refuted, `sol alert test --dry-run` against
the pluto pilot target). HARDEN-002 must (a) deliver and acknowledge a synthetic
alert at the real configured receiver, (b) confirm the scrape dependencies for
the Postgres/Kafka rules where a target relies on them, and (c) record game-day
use of these runbooks.

**Demo/example coverage:** `examples/pluto/sol/pilot/aws/us-east-1.yml` declares
a placeholder webhook receiver, owner and runbook (no real credentials
committed); its README shows `sol alert test`.

**TypeScript parity:** Not language-specific; the target-level owner/runbook
metadata applies to every supported workload language.
