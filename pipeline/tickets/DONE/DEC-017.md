**Depends on:** DEC-016 — the runner determines the surface. Revises the "Deploy & runtime visibility" paragraph in `docs/planning/ROADMAP.md`.

Decide where deploy/run diagnosis and runtime observability live, now that a deploy may be triggered by a push rather than by the user's terminal.

## Decision

**The surface follows the runner.** Whoever ran a deploy owns the record of it:

| Trigger | Runner | Where diagnosis lives |
|---|---|---|
| `sol up` / `sol deploy` locally | the user's machine | the CLI, run logs under `.sol/runs/` |
| their CI calls `sol deploy` | their CI | their CI logs/artifacts |
| push (hosted) | Sol's pipeline | the dashboard, a GitHub commit status, and a configured notification |
| push (self-hosted) | their Argo/CI | their cluster's tooling |

So **the CLI is a client of the platform for hosted deploys, not the owner of them**. For a push-triggered deploy the dashboard cannot be optional — the person who pushed is not at a terminal, and the commit status is what reaches them.

**Logs split by who generated them.** Deploy/run logs live *in the platform*, because the platform ran them: bounded, per-run, finite — an obligation that comes with running the deploy. Runtime logs stay *in the customer's cluster*: unbounded, retention-heavy, continuous — the September decision to avoid becoming a logging company stands. "It ran, so we hold the record" is not "we hold everything they ever emit".

**Diagnosis is factored once and rendered per surface.** One deploy-record + diagnosis model — `ImagePullBackOff` → the registry auth error, `OOMKilled` → the memory limit that was hit, unschedulable → no node with capacity — consumed by the CLI, the dashboard, and commit statuses. Built ad hoc inside `cmd_status.ml` it will be built three times, and the dashboard's version will be the good one while the CLI's drifts.

## Consequences

- The `docs/planning/ROADMAP.md` visibility paragraph is revised: its "`sol status` leads with Kubernetes-derived diagnosis, unconditionally" rule still holds for the local and GitOps modes; for hosted, the **dashboard** is the surface that leads.
- The four visibility items that section marks "not yet ticketed" (Kubernetes-derived diagnosis, `sol logs` runtime fallback, promtail scraping pod stdout, deploy run IDs) are re-scoped onto the factored model rather than implemented directly — and the run-ID/local-log item stays CLI-owned while the diagnosis rendering becomes shared.
- The CLI remains the right home for the *local* and *self-hosted* modes, which is most of Sol's usage today. This decision is about not building the hosted path's diagnosis into the CLI first.

## Acceptance criteria

- One diagnosis model exists and is rendered by at least two surfaces without duplicated interpretation logic.
- A push-triggered hosted deploy surfaces failure as a commit status plus a notification, not only in a dashboard.
- Deploy run records survive the cluster the run may have created or destroyed.

## Completion notes

**The decision above was already correct and needed no changes; what this
ticket found is that its consequences were already carried out by other,
already-`DONE` work before this ticket itself was ever picked up** — the same
pattern DEC-019 (filed the same day, 2026-09-10) closed itself under.
Assessed rather than assumed:

- **Criterion 1 — met.** `Sol_cli_rollout_diagnosis` (`cli/sol/lib/`) is
  already the one diagnosis model: mostly pure, I/O-free parsing/formatting
  (`parse_pods_json`, `format_service_diagnosis`, `format_pod_diagnosis`,
  etc.) — the one exception is `diagnose_service_live`, which fetches
  cluster state itself via `Sol_cli_kubectl.get_raw` rather than taking
  already-fetched JSON (its `.mli` doc comment was stale about this and is
  fixed in this same PR) — with three CLI consumers — `cmd_status.ml` (`sol
  status`),
  `cmd_logs.ml` (the `kubectl` fallback), and `sol_cli_up_execution.ml`
  (`sol up`/`sol deploy`'s own post-apply check). `rg` across `cli/` for the
  diagnosis reason strings (`ImagePullBackOff`, `OOMKilled`, `Unschedulable`)
  finds them nowhere outside `sol_cli_rollout_diagnosis.ml` itself — no
  ad-hoc second copy exists to drift, which is exactly the failure mode this
  criterion guards against.
- **Criterion 2 — not owed by this repository, and that is the correct
  outcome, not a gap.** DEC-019 (also 2026-09-10) decided the hosted control
  plane, its delivery pipeline, and its dashboard all move to the private
  `sol-cloud` repository — "nothing in this repository may reference a
  private resource." A push-triggered *hosted* deploy is `sol-cloud`'s
  runner, so its commit-status/notification surface is `sol-cloud`'s to
  build, consuming this repo's diagnosis model and `--emit-plan-to` output as
  a library rather than this repo growing a hosted-pipeline integration it
  has no way to run or test. Recorded here, as DEC-019 recorded its own
  equivalent gap, rather than left silently unmet.
- **Criterion 3 — met.** FEAT-055 (landed 2026-09-12, one day after this
  ticket was filed) wired `Sol_cli_run_log` into `sol up`/`sol deploy`: a run
  id and a `<run-id>/` directory under `Sol_cli_state.dir`'s `runs`
  subdirectory (`$XDG_DATA_HOME/sol/runs`, falling back to
  `~/.local/share/sol/runs` when `XDG_DATA_HOME` is unset — not a
  project-local `.sol/runs/`) are created before any work starts, entirely on
  the local filesystem — never inside the cluster the run may create or
  destroy — and a failing phase prints the run id, log path, and tail so the
  record outlives the terminal that started it.
- **`docs/planning/ROADMAP.md`'s "Deploy & runtime visibility" paragraph**
  is revised in this change: FEAT-055's landing is reflected (it was still
  marked "the one genuine gap" there), and a new paragraph states the
  runner-owns-the-record split from this decision explicitly — the CLI model
  covers everything this repo owns (local + any CI a user runs `sol deploy`
  from); the hosted/dashboard case is `sol-cloud`'s, named as out of scope
  rather than left unaddressed.
- No new production code was needed — this ticket's actionable work turned
  out to be verifying the decision's consequences against reality and
  closing the loop in the doc, not implementing anything net-new.
