Decide whether Sol-hosted mode gets a dedicated web UI, or stays CLI-first with an embedded/white-labeled dashboard shell.

**Question:** DEC-007 already commits hosted UX to showing "release, deployment plan, status, logs, rollback" concepts rather than raw GitOps/Kubernetes mechanics, and `observability-design.md`'s "Hosted Path" section says Sol may "operate the storage itself or broker a managed provider... users should not have to learn that backend." Neither says how a user actually *sees* any of this. Does Sol build and maintain a dedicated customer-facing web application (accounts, RBAC, billing, environment management, dashboards — a genuinely new, large product surface), or does it stay CLI-first (`sol status`/`sol open`) with Grafana (self-hosted today) replaced by a Sol-branded/white-labeled dashboard shell for hosted customers, deferring a full web app until there's evidence customers need one?

**Context:** This is the single largest net-new engineering surface implied by the hosted-factory-floor direction — bigger than any CLI or Terraform work done so far. `PRODUCT_ARCHITECTURE.md`'s hosted factory floor list already names RBAC and audit logs as future concerns a CLI-only surface doesn't naturally support (RBAC in particular implies real user/team/permission management, not just kubeconfig-style access). Building this before hosted infra tenancy (DEC-008) exists, and before a single paying hosted customer exists, risks splitting effort across two unproven products (the open-source CLI/Terraform tool and a hosted multi-tenant SaaS) at once.

**Options:**
1. Full dedicated web UI from the start — accounts, environments, dashboards, logs, billing, RBAC, built as a first-class product alongside the CLI.
2. CLI-first (`sol status`/`sol open`) plus a white-labeled/embedded dashboard shell (Grafana today) for hosted customers; defer a full web app until real hosted usage demands account/team/billing management a CLI can't reasonably provide.
3. Thin hosted web UI scoped to only what a CLI genuinely cannot do (billing, account/team management, RBAC), with all release/status/logs/dashboard interaction staying CLI + dashboard-shell as in option 2.

**Decision criteria:**
- Consistency with DEC-001 (hosted doesn't own builds yet) and DEC-004 (hosted is first-class, but the factory contract should stabilize before over-specifying the control-plane API) — both argue against building the biggest UI surface first.
- What actually blocks the first paying hosted customer versus what's speculative polish.
- Engineering cost relative to Sol's current team size and pre-alpha stage.
- Whether billing (DEC-006) and RBAC genuinely require a web UI (likely yes) versus dashboards/logs (already served by Grafana today).

**Acceptance criteria:**
- A written decision names which option is the first hosted UI investment.
- The decision explicitly sequences it relative to DEC-008 (tenancy mechanism must exist before there's anything for a UI to manage).
- Follow-up tickets are created only for the scoped-in surface, not the full future vision.

**Decision:**

Sol Cloud's intended primary interaction model is a thin first-party web control plane centered on service and deployment lifecycle. The CLI remains the canonical interface for local development, automation, and self-hosted operation. Specialized operational exploration remains delegated to purpose-built tools such as Grafana, surfaced through contextual links from Sol rather than reimplemented.

This decision establishes an interaction-model *direction*, not an implementation commitment or hosted-product specification. Implementation of the web control plane is deferred until the prerequisites beneath it are sufficiently concrete — particularly a working implementation of DEC-008's tenancy model and a real hosted-executor design. Without those, "push to GitHub, see a deployment go green" isn't a UI-scoping question at all — it's a claim about infrastructure that doesn't exist yet, and designing a UI around it now would mean visualizing abstractions Sol is still discovering.

The eventual onboarding experience should optimize for a simple path from source code to a running backend, but the exact flow — including repository creation, CI/build ownership, deployment triggers, and credential exchange — must follow from those underlying contracts rather than define them prematurely.

`OBS-044` and `sol open dashboard` remain the current operational experience; this decision does not replace or duplicate that work. Today: CLI + Grafana. Being built: tenancy (DEC-008) + a hosted-executor design. Later: the thin Sol deployment control plane described above. North star: going from backend code to a running, observable, billed production service should require learning none of Sol's own infrastructure vocabulary.

**Revisit this decision** once (a) DEC-008's tenancy mechanism has a working prototype — even a single manually-provisioned customer VPC counts — and (b) there's a concrete design for how a push/webhook event turns into an actual build+deploy. Until then, no web control-plane implementation work should be scheduled.

**Guardrails (binding on any future implementation, not just aspirational):**
1. Web-based project/service creation must invoke the same underlying scaffold generator `sol new` uses — never a parallel, hosted-only reimplementation. Two independently-maintained generators producing what's supposed to be the same output is exactly the class of drift `FRIC-014` exists to catch in the CLI-only case; a web-side generator would be a second, unguarded instance of the same risk.
2. Any GitHub App capability that creates repositories, gains write access to a user's GitHub account/org, or receives repository webhook events is its own explicit trust-boundary/security decision, designed and reviewed separately before implementation — not a bullet point inside a golden-path UX description.

**Implications:**
- No web UI implementation work is scheduled now; `AUDIT-065`/`OBS-044`-style CLI and dashboard investment remains the correct near-term default, and directly serves whatever the eventual hosted UI would link out to anyway.
- A prototype ticket for DEC-008's tenancy mechanism is the concrete next step toward this decision's revisit trigger (filed alongside this one).
- When hosted-executor design work eventually starts, it should explicitly address: how a webhook/push event triggers a build, who owns the build (still customer CI per DEC-001, or does this change that), and how release/deployment history gets recorded — before any UI is designed against it.
