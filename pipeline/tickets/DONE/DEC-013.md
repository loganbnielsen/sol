**Depends on:** None.

Decide how a self-hoster obtains Sol, so that "free self-host" is an offer rather than a claim.

**Question:** The repository is public and Apache-2.0. But nothing is published: the TypeScript packages are marked `private`, the OCaml packages live in-tree, and the only distribution path today is `git clone` plus build-from-source. Is that the intended answer, or should Sol ship distributable artifacts?

**Options:**

1. **Source only.** Clone and `dune build`; the README already points at `.claude/CLAUDE.md` for that. Zero ongoing release work, but the weakest onboarding and every self-hoster tracks a moving `main`.
2. **Publish the TypeScript packages** (`@sol/kafka`, `@sol/obs`) to npm and keep the OCaml/CLI source-only for now. These are what an application author imports, and npm is where they would look. Needs an npm scope — check whether `@sol` is actually available *before* announcing anything.
3. **Publish both** — npm for `@sol/*`, opam for the OCaml packages and CLI, with signed releases. Best onboarding, most release engineering (version skew, release CI, signing).
4. **Tagged releases with binaries** for the CLI, source for everything else.

**Decision criteria:**

- What the self-host pole actually needs: a self-hoster must reach a working workspace without cloning `main` and fighting a toolchain.
- Name reservation is cheap now and awkward after adoption — claiming the npm scope and opam names is a reason to decide early rather than late.
- Release engineering cost, against the fact that **publishing is what triggers the dependency-licence obligations** INFRA-007 explicitly left open (no opam/npm licence inventory exists yet).
- Consistency with the toolchain-pinning discipline the repo already applies to k3d/helm/kubectl.

## Decision

**Reserve the names now; publish when the product is worth sharing.**

Shape: `@sol/*` on npm for the TypeScript packages, and opam for the OCaml side — which is **not hypothetical**: `kafka-eio` and `obs-eio` are already published to opam by this author (homepage `github.com/loganbnielsen/…`), so the path, the tooling and the precedent exist.

Name state, checked 2026-09-10:

- **npm:** `@sol/kafka` and `@sol/obs` do not exist, and the registry has no user or organisation named `sol` — the scope looks claimable. **Claiming it is the one irreversible item and should happen now**, independent of readiness; a squatted scope forces a public rename later.
- **opam:** `sol`, `sol-svc` and `sol-env` are free. opam has **no reservation mechanism** — a name belongs to whoever first lands it in `opam-repository` — so the choice there is publish early or accept a low squatting risk. Not a blocker.

Publishing itself is gated on three things, none of them ceremony:

1. **The opam/npm licence inventory** INFRA-007 deferred. Distribution is what triggers licence obligations; nothing is owed while nothing is distributed.
2. **A version story.** The repo pins k3d/helm/kubectl deliberately; published packages need equivalent discipline — what does `@sol/kafka@0.1.0` mean against a moving `main`?
3. **The product being worth sharing.** What this decision withholds is *packaging and support*, not visibility: the repository is already public, so source access has begun.

**Acceptance criteria:** the path is named ✅, name reservation is actionable ✅ (npm scope to claim; opam has none to claim), and the inventory remains a precondition for publishing ⏳.

**Acceptance criteria:**

- A decision names the distribution path, and the README or the substrate contract documents how to obtain Sol.
- Any name reservation required (npm scope, opam package names) is done or explicitly declined.
- The opam/npm licence inventory deferred by INFRA-007 is complete before anything is published.
