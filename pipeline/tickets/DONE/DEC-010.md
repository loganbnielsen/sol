Decide Sol-hosted's compute elasticity model: full serverless (Lambda/SQS
conversion of the primitives) versus autoscaling the existing Kubernetes
primitives.

**Question:** Given spiky customer traffic makes fixed capacity either
wasteful (over-provisioned) or user-visibly broken (under-provisioned),
should Sol-hosted convert `-svc`/`-worker`/`-fn` into Lambda functions and
SQS queues to get AWS-native elasticity, or keep the existing Kubernetes
primitives and add autoscaling underneath them?

**Context:** Two of Sol's own named design principles argue against literal
serverless: "Dev mirrors prod exactly" (there is no meaningful local Lambda
— `sol dev up`'s whole premise breaks), and "Cloud-agnostic Kubernetes / no
vendor lock-in" (Lambda + SQS is AWS-proprietary; a portable equivalent means
maintaining a second serverless backend per cloud). SQS also lacks the
ordering, replay, and consumer-group semantics `-worker`'s Kafka model (and
the schema registry work in `kafka-eio-service`) already depends on — a
Kafka-to-SQS conversion is an event-model regression, not a deployment
detail. Cold starts are a real UX cost specifically for `-svc`'s synchronous
request/response contract. Kubernetes already has mature, cloud-agnostic
answers to the underlying elasticity problem: KEDA (scale-to-zero off Kafka
lag/SQS depth/cron), HPA (request/CPU-based pod autoscaling), Karpenter
(node-level bin-packing and spot usage), and Aurora Serverless v2 (DB compute
autoscaling as a drop-in `aws_db_instance` swap). DEC-008 also already gives
per-customer isolated infra, which makes AWS-native cost attribution
tractable without needing per-invocation serverless billing to make it work.

**Options:**
1. Convert `-svc`/`-worker`/`-fn` to Lambda + SQS/EventBridge as the hosted
   execution model.
2. Keep the existing Kubernetes-based primitives; add KEDA + HPA + Karpenter
   + Aurora Serverless v2 as an autoscaling-by-default executor configuration
   for Sol-hosted, exposed as one more executor over the same typed
   deployment plan (`PRODUCT_ARCHITECTURE.md`'s "executor differences should
   be operational, not architectural").
3. Hybrid: literal Lambda specifically for `-fn` (already under discussion
   for FRIC-012-adjacent work), Kubernetes-native autoscaling for `-svc` and
   `-worker`.

**Decision criteria:**
- Preserves dev/prod parity and cloud-agnostic Kubernetes as stated design
  principles, or explicitly and knowingly abandons them.
- Preserves the Kafka event model (ordering, replay, consumer groups, schema
  registry) `-worker` and the framework libraries already depend on.
- Cold-start impact on `-svc`'s synchronous contract.
- Reuses infrastructure/tooling that already exists versus requiring a new
  parallel execution backend per primitive per cloud.

**Decision:**

Option 2. Sol-hosted stays on the existing Kubernetes-based `-svc`/`-worker`/
`-fn` primitives. Elasticity is delivered by turning on Kubernetes-native
autoscaling by default for Sol-hosted environments: KEDA (workers scale
toward zero on Kafka consumer lag), HPA (services scale on request
rate/CPU), Karpenter (node-level autoscaling/spot usage to shrink the
cluster's own base cost), and Aurora Serverless v2 in place of a fixed-size
`aws_db_instance.postgres` where DB compute is the actual spiky-cost driver.

This is one hosted lane with an autoscaling default, not a second "serverless
tier" product to build and support separately. Self-hosted/customer-cloud
users get the same autoscaling machinery as an opt-in Terraform toggle
(predictable fixed capacity remains the default there, since those customers
own their own AWS bill directly and may prefer it). Customers on Sol-hosted
keep an override knob (e.g. a min-replica floor) for latency-sensitive
services that shouldn't scale from zero, rather than losing right-sizing
control entirely.

Literal Lambda/SQS conversion of the primitives is explicitly rejected: it
breaks dev/prod parity and cloud-agnosticism, degrades the Kafka event model
to SQS's weaker semantics, and isn't a real product differentiator since AWS
already sells "don't think about capacity" directly (Lambda/Fargate/App
Runner) — Sol's differentiation stays typed-code-to-correct-infra, not
better-than-AWS elasticity. (Lambda specifically for the `-fn` job primitive
remains a separate, narrower, already-flagged option from the FRIC-012
discussion, unrelated to this decision.)

**Implications:**

- `platform/infra/aws/main.tf` needs a Sol-hosted-mode Terraform path that
  installs KEDA and Karpenter and provisions Aurora Serverless v2 instead of
  a fixed-size RDS instance; self-hosted customer-cloud keeps today's fixed
  defaults unless a customer opts in.
- The generated Kubernetes manifests need KEDA `ScaledObject`/HPA resources
  added per service/worker when the hosted-autoscaling config is active —
  this is deployment-plan/executor-level config, not a change to the
  `-svc`/`-worker`/`-fn` framework libraries themselves.
- No new hosted product tier or separate marketing SKU is implied — this is
  a default-behavior decision inside the existing Sol Hosted lane.
- Follow-up implementation tickets (KEDA/Karpenter Terraform wiring, Aurora
  Serverless v2 swap, deployment-plan autoscaling config fields) should be
  filed once DEC-008's hosted-provisioning path is actually being built, not
  before.
