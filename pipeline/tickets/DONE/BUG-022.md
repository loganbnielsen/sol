**Depends on:** None.

The pinned dev substrate — k3d v5.6.0 → k3s v1.27.4, whose NetworkPolicy engine is kube-router — does not honour the cross-namespace NetworkPolicy rules Sol generates, so a declared service-to-service call is **denied in dev** even though the policy is correct per the Kubernetes spec.

## Problem

FEAT-041 renders a per-pair NetworkPolicy: caller egress `to: namespaceSelector + podSelector(app: <peer>)`, peer ingress `from: namespaceSelector + podSelector` on 8080. The rendering is unit-tested and spec-correct, but the declared call is denied on the dev substrate. kube-router implements policy denial as **REJECT**, so the caller sees `Connection refused` (curl exit 7) rather than a timeout — which is why this was misdiagnosed twice.

Deterministic local reproduction on k3s v1.27.4+k3s1: two fresh namespaces, a peer Service on port 80 → 8080 with a labeled pod, a labeled caller pod, and the generated-shape policies.

| Test | Result |
| --- | --- |
| Generated-shape pair (caller egress + peer ingress) | **denied** (exit 7) |
| Caller egress only (peer ingress removed) | allowed |
| No policies | allowed |
| Peer ingress `namespaceSelector` — ns-only, ns+pod, with and without ports | **denied** (every variant) |
| Peer ingress `ipBlock` (pod CIDR) | allowed |
| Peer ingress bare `podSelector: {}`, probed cross-namespace | denied (correct) |
| Deny-all **egress** policy on the caller | **allowed** — egress is not enforced |
| Old source namespace (ingress-nginx) → 2-day-old target (dogfood `charge-svc`) | allowed (200) |
| Old source namespace (ingress-nginx) → fresh target | **denied** |

So: `ipBlock` works, `podSelector` semantics are right, **`namespaceSelector` ingress does not match for freshly created namespaces/workloads**, and egress policy is ignored entirely. The one working cross-namespace path is a target that has existed for days, so the behaviour is not simply "always denied".

## Impact

- FEAT-041's "declared cross-namespace call works in dev" criterion cannot be demonstrated on the documented dev substrate; its golden-path assertion has been reduced to deploy-path coverage (the policies are applied as rendered) with a pointer here.
- Anything else that relies on `namespaceSelector` ingress on dev (Prometheus scrape allowances, ingress-nginx → `-svc`) is unverified.
- Customer-cloud CNIs (and the unit tests) are unaffected; this is a dev-substrate gap.

## Remediation

- Reproduce from the table above — two fresh namespaces and no container images are needed.
- Find out whether a newer k3s bundles a kube-router that honours `namespaceSelector`; if so, bump the k3d pin in `.github/workflows/ci.yml` (the current pin is deliberate — see its comment).
- If not, document the limitation where a user reading the service-call/network-policy docs will find it, and leave enforcement coverage to unit tests plus customer-cloud CNIs.
- Do **not** work around this by widening Sol's policies to `ipBlock`: that would discard the per-pair precision that is the point of the feature.

## Acceptance criteria

- Either the dev substrate enforces the generated pair policy, or the limitation is documented in the user-facing networking docs.

## Completion notes

**Root cause established; fixed by bumping the toolchain the dev substrate pins.**

What the pinned substrate does (k3s v1.27.4+k3s1 via k3d v5.6.0):

- Cross-namespace `namespaceSelector` ingress rules are **ignored**, so the generated per-pair policy denies the declared call. kube-router implements denial as **REJECT**, so the caller sees `Connection refused` (curl exit 7) rather than a timeout — which is why this was misdiagnosed twice as a plumbing problem.
- **Egress policy is not enforced at all** — a deny-all egress policy on the caller does not block anything.

What a newer k3s does (k3s v1.35.5+k3s1 via k3d v5.9.0), verified on a separate cluster using the same manifests:

| Test | v1.27.4 | v1.35.5 |
| --- | --- | --- |
| `namespaceSelector` ingress allow (the declared-call case) | **denied** (exit 7) | **allowed** (200) |
| Negative control — deny-all ingress must block | denied | **denied** (exit 7) |
| No policies (control) | allowed | allowed |
| Deny-all egress on the caller | allowed (unenforced) | allowed (unenforced) |

The negative control is the load-bearing row: it proves enforcement is genuinely active on v1.35.5, so the allow result means the rule **matched** rather than policies being ignored altogether. Egress remains unenforced on both — a separate substrate property, not a regression, and one the generated policies do not depend on.

**A partial bump was not possible.** k3d v5.6.0 cannot bring up k3s v1.29.15 or v1.36.4 (the node never reaches `k3s is up and running`), so the k3s version is coupled to the k3d version and the fix has to move both.

**Changes:**

- `.github/workflows/ci.yml` — k3d v5.6.0 → v5.9.0; kubectl v1.29.0 → v1.35.0 (kubectl supports a ±1 minor skew, so it has to move with the server). helm stays, being client-side.
- `docs/dogfood/DOGFOOD.md` — toolchain table and install line updated; the rationale now records *both* reasons the pin is load-bearing: NetworkPolicy semantics and the chart-value compatibility constraint.
- `docs/deployment/service-runtime-contract.md` — the caveat now names the version boundary (k3s ≤ v1.27) instead of describing the toolchain Sol currently ships.

**Residual risk, stated plainly:** chart-value compatibility of the bumped toolchain with `sol dev up` is validated by the golden-path smoke in CI, not locally. DOGFOOD's own warning is that a bump can change chart defaults (Redpanda CPU/replica, node-exporter flag), so if that job fails on chart values the bump should be narrowed or reverted rather than papered over. Live policy enforcement therefore is **not yet asserted end to end**; restoring that assertion — and retiring the caveat entirely — is filed as a follow-up.
