**Depends on:** None.

## Question

Define Sol's first explicit production profile: `production-single-region`.
An environment named `prod` does not imply this profile, and the profile is not
a bag of Kubernetes or provider knobs. It is the compatibility boundary between:

- portable application requirements (artifact identity, availability, resources,
  persistence and configuration);
- target capabilities and operator policy (failure domains, data durability,
  state/access, alert delivery and supported versions); and
- the evidence required to claim conformance.

Engineering must resolve:

1. The one initial provider/substrate combination and exact supported Kubernetes,
   platform-component and framework versions. Supporting both clouds is not a
   maturity-A requirement.
2. Which application-facing availability and persistence semantics Sol supports,
   without exposing PDBs, topology rules, storage classes or provider settings.
3. The guarantees and explicit exclusions for Postgres, Kafka, admitted workload
   volumes, platform/control state and telemetry, including measurable recovery
   expectations where a durability claim is made.
4. Whether OCaml and TypeScript are both in the first profile. DEC-022 keeps both
   first-class overall; this decision may stage their production qualification,
   but any deferral must name its trigger.
5. The evidence artifact and versioning rule for a conformant target.

## Constraints already established

- Maturity A is one team, roughly ten workloads, one region and a real but
  non-critical customer-facing workload.
- Fixed capacity with documented headroom is valid. DEC-010's autoscaling design
  is hosted/target architecture, not a current maturity-A capability.
- Regional failover, multi-team governance, hosted control plane, fleet
  management and metering are outside this profile.
- Provider/Kubernetes mechanisms remain below the Sol semantic boundary.
- A guarantee applies only when the workload uses the relevant capability; for
  example, a workspace with no Kafka dependency need not provision Kafka merely
  to satisfy the profile.

## Acceptance criteria

- A written decision defines the profile's application requirements, target
  capabilities, guarantees, exclusions, supported version set and evidence.
- Target selection and profile selection are distinct; selecting an environment
  named `prod` does not silently select the profile.
- The decision defines observable compatibility failures before any cluster or
  infrastructure mutation.
- The decision states the initial provider/substrate and language scope rather
  than implying untested portability.
- Every maturity-A workstream can point to a precise claimed behavior or is
  explicitly removed from the critical path.

## Decision (2026-09-16)

**Governing invariant, restated so every downstream ticket can be checked against
it:** `production-single-region` is a claim about a specific (target, evidence)
pair, never about an environment name. A target that selects the profile but
fails a capability check, or a capability whose evidence has never been
established, does not get the guarantee for that capability — the profile
degrades to "not conformant," never to "conformant but unverified." Nothing
below grants a guarantee wider than the evidence in §9 can prove.

### 1. What selecting the profile means

Profile selection is a distinct, explicit field on a target, orthogonal to the
target's environment label. `sol.yml`/target configuration gains a
`profile: production-single-region` declaration (FEAT-089 owns the mechanics);
an environment named `prod` with no `profile` field makes no production claim
and is treated exactly like any other unclassified target. A target may only
select a profile whose provider/substrate and version match §2 — selecting the
profile against an unsupported combination is a preflight failure, not a
degraded pass.

Selecting the profile means: every portable requirement a workload declares
(availability tier, persistence semantic, artifact reference, credential
capability) is checked against the target's declared capabilities *once*,
before any render/apply mutation (FEAT-089), and the target's operational
posture (state backend, identities, alert routing — §7, §8) is required to
already be in place. Selecting the profile does **not** by itself change what
a workload renders; a workload that declares nothing beyond the defaults gets
the `single` availability tier and no persistence beyond what FEAT-083 admits
at that tier.

### 2. Initial provider/substrate and framework/language/version scope

**Provider/substrate: AWS EKS**, using the existing `cli/platform/infra/aws` +
`cli/platform/infra/base` Terraform modules, single cluster, single region,
managed node groups at fixed capacity with documented headroom (no cluster
autoscaler is required or claimed).

This is a decision, not a default-by-omission: AWS is the only substrate this
repository has ever exercised against live infrastructure
(`tools/aws-live-smoke.sh`, which already caught one real defect — an
undersized-node OOMKill, per `docs/planning/WORK_SUMMARY.md`), it has the more
complete IRSA/workload-identity writeup the 2026-09-16 adversarial review could
not find a GCP equivalent for, and ECR scan-on-push is already wired. GCP's
module is comparatively more current on exactly one axis (regional/HA Cloud SQL
already has a toggle AWS RDS lacks) — that gap is closed as part of AUDIT-078's
Postgres guarantee below, not by switching substrate. GCP support is not
withdrawn; it is simply not the qualified profile target until it has been
through the same live-provisioning proof AWS has, and re-adding it is a
compatibility-matrix addition (FEAT-088), not a new DEC.

**Kubernetes and component versions are not re-pinned by this decision.** The
profile's qualified version set is *whatever `cli/platform/infra/aws` and
`cli/platform/infra/base` already pin* at the time FEAT-088 publishes the
matrix (as of this decision: `kubernetes_version = "1.36"` per
`cli/platform/infra/aws/variables.tf`, plus that module's already-pinned
provider/chart versions). Sol does not invent a second, aspirational version
set in an architecture decision that the renderer doesn't match — FEAT-088's
job is to publish the matrix that already exists in code and enforce it at
preflight; DEC-026's job is to require that a matrix exists, is exact (not a
range), and is enforced before mutation. Changing the pinned version is a
FEAT-088/HARDEN-002 re-qualification event (§10), not a silent drift.

**Workload shapes in scope:** `Http_service` (`-svc`) and `Background_worker`
(`-worker`) both get an availability tier (§3). `Function` (`-fn`) is **in the
profile but outside the availability-tier vocabulary**: an `-fn` invocation is
a bounded, independently-retried execution, not a continuously-available
process, so "single / node-failure-tolerant" does not apply to it. Its
production guarantee is invocation completion/retry semantics, which
`sol-fn`/`sol-jobs` already define — this decision does not add one. Recording
this explicitly satisfies the "no silent verdict" rule: `-fn` is `not
applicable` to the availability vocabulary, not omitted from it.

**Language scope: OCaml only, in the first (`v1`) profile.** DEC-022's
first-class status for both languages is unaffected — this stages *production
qualification*, which DEC-022 itself anticipates ("this decision may stage
their production qualification, but any deferral must name its trigger").
TypeScript is deferred with three concrete, checkable triggers; when all three
hold, FEAT-088 adds TypeScript to the compatibility matrix as a version-set
update, with no new DEC needed:

1. FEAT-087's deployed TS golden-path-smoke CI job is merged and green (today:
   PR #282, open) — an automated, repeatable deployed proof, not the manually
   exercised one recorded for FEAT-082.
2. The TypeScript worker has a shipped equivalent of OCaml's `on_ready` (§3
   resolves what it must signal); today `@sol-fab/worker`'s `RunWorkerOptions`
   has no readiness hook at all (DEC-028 evidence #6).
3. `examples/pluto`'s `demo_ts` is confirmed cut over to the published
   `@sol-fab/*` packages with the same immutable-ref discipline DEC-025 requires
   for OCaml (the 2026-09-16 adversarial review flagged this as unconfirmed,
   not as failing — it must become a confirmed, not merely assumed, fact).

Until then, a target that selects `production-single-region` and contains a
TypeScript-implemented `-svc`/`-worker` fails preflight validation the same way
an unsupported Kubernetes version would: named, before mutation, not silently
downgraded.

### 3. Application-facing availability semantics (resolves DEC-028)

Two Sol-owned failure-tolerance tiers exist in `v1`, declared per workload
(default `single`):

- **`single`** — one logical instance. Sol makes no claim about surviving node
  loss; a lost pod is rescheduled by ordinary Kubernetes behavior with no
  bound on when capacity returns. This is a legitimate, honestly-labeled
  choice for a maturity-A non-critical pilot workload, not a degraded mode.
- **`node-failure-tolerant`** — requires `replicas >= 2`, and Sol renders and
  validates: pod anti-affinity/topology spread across nodes, a
  PodDisruptionBudget expressing the declared tolerance, a startup probe sized
  so a slow-starting process is not liveness-killed before it can become
  ready, and an explicit `terminationGracePeriodSeconds` set from the
  framework's own drain timeout (closing the 30s/30s race the adversarial
  review found at finding #9 — this stops being implicit coincidence and
  becomes a rendered, checked value). **Target bound (qualification target,
  not a proven guarantee — see the governing invariant above):** required
  ready capacity is restored within 5 minutes of a node becoming
  unschedulable, given headroom equal to at least one full node for every
  node-failure-tolerant workload on that node pool. No cluster autoscaler is
  required to meet this bound — the headroom is what makes it possible, and
  its absence is a preflight failure, not a runtime surprise. This decision
  fixes the number that HARDEN-002 must measure and pass before a target may
  claim `node-failure-tolerant` conformance; it is not itself evidence that
  AWS/EKS meets it.

**Worker readiness — the DEC-028 answer: yes, Sol models it, in this same
vocabulary, not a parallel one, for the case DEC-028's evidence actually
covers.** `Background_worker` is broader than Kafka consumption —
`sol-worker.md` is explicit that `sol-jobs` is "a library hosted by an
ordinary `-worker` binary rather than a Kafka-specific concern of this
module," with its own Postgres `FOR UPDATE SKIP LOCKED` leasing, not a Kafka
consumer loop. So this decision resolves readiness for the concrete case
DEC-028 measured — **a worker that consumes Kafka through `Sol_worker.Worker`
or `Make_with_retry`** — and does not assume every `Background_worker` has an
equivalent signal.

- **Readiness** = the existing OCaml `on_ready` event (partitions assigned,
  consumer group joined) surfaced as a Kubernetes-visible signal (an HTTP
  endpoint alongside the existing metrics port, wired into a rendered
  `readinessProbe`) for a Kafka-consuming worker — AUDIT-080 implements the
  render; this decision fixes only what the signal must mean and that both
  tiers require it, since reporting readiness honestly is a correctness
  property, not a failure-tolerance upgrade. Such a worker whose consumers
  have not joined is **not** ready, at either tier, and Sol must say so
  rather than report `Running` as if it were sufficient. A `Background_worker`
  that hosts no Kafka consumer (e.g. a `sol-jobs`-only worker) has no
  readiness signal defined by this decision — that is a named open question
  for whoever next specifies it, not a silent assumption that one exists.
- **Liveness is a distinct question from readiness, and this decision does
  not mandate a mechanism for it.** The only fixed rule: if AUDIT-080 (or a
  later ticket) models liveness for a given worker capability, that signal
  must be observably distinct from readiness, and must never be inferred
  solely from the worker having been ready at some point in the past — "was
  ready once" is not "is live now." Because `Background_worker` covers
  capabilities as different as Kafka consumption and `sol-jobs` leasing,
  DEC-026 does **not** require a generic poll-heartbeat mechanism across
  every worker shape. Whether a given capability can support a liveness
  signal at all, and what that mechanism is (a Kafka consumer's poll cadence,
  a `sol-jobs` lease heartbeat, or none for a capability with no natural
  liveness signal), is AUDIT-080's implementation question per capability
  actually in use, not something this decision invents.
- **Which readiness states count, for the Kafka-consuming case:**
  broker-unreachable-at-startup blocks readiness (retry with a bound, do not
  report ready) — this is readiness, not a crash loop. Partition rebalance is
  a transient not-ready state, not a liveness failure — a worker
  mid-rebalance must not be killed for it. Retry/DLQ consumer liveness is out
  of scope here: a retry-topic consumer is its own worker with its own
  readiness/liveness signal, not a special case of this one.
- TypeScript parity consequence: `@sol-fab/worker` needs the `on_ready`
  equivalent before TypeScript can hold this tier at all for a Kafka-consuming
  worker — restated from §2's trigger #2, not a new requirement invented
  here.

**Interaction with persistence (bridges to FEAT-083):** a workload that
declares a workload-scoped volume is capped at `single` in `v1`. The reason is
placement/concurrency, not that the volume is welded to a specific node: a
workload-scoped `ReadWriteOnce` volume is AZ-bound, not permanently
node-bound — a cloud block volume can ordinarily detach and reattach to a
different node within the same availability zone. But `node-failure-tolerant`
as defined above requires multiple *concurrently ready* replicas spread across
nodes, and an RWO volume can be mounted by only one pod at a time — it cannot
back two concurrently-available replicas, and it cannot follow a reschedule
that this tier does not rule out. So the combination fails on what
`node-failure-tolerant` actually requires, not on an incorrect claim about how
the storage is bound. `node-failure-tolerant` + a declared workload volume is
therefore an invalid combination and must fail closed, naming `single` as the
supported alternative, until FEAT-083 defines a replica-volume or shared-volume
shape that actually preserves the guarantee. This is the one persistence
constraint DEC-026 fixes directly; the rest of the admitted/invalid matrix is
FEAT-083's to write, against this vocabulary.

### 4. Target capabilities and compatibility validation

A target claiming `production-single-region` must declare, and FEAT-089 must
validate once before any render/apply mutation:

- substrate identity matching §2's qualified provider/Kubernetes/component
  version set (exact match, not "compatible enough");
- documented fixed-capacity headroom sufficient for every
  `node-failure-tolerant` workload's §3 bound;
- an encrypted, locked, remote Terraform state backend (§6);
- named provisioning/deploy/operator identities distinct from any
  cluster-creator admin credential (§6);
- a configured, non-null alert receiver with owner metadata (§8);
- for each data capability a workload actually uses: the corresponding
  durability capability from §5 (replicated Kafka topic policy, Postgres
  HA/backup configuration) — a target that doesn't provide it fails
  validation only for workloads that use it, per the existing "guarantee
  applies only when used" constraint.

Validation failure is reported in Sol's own vocabulary (the unmet guarantee
and which side — application or target — is responsible), never as a raw
Kubernetes/Terraform error surfaced to the operator.

### 5. Data durability and recovery — three independent contracts

Consolidating the audits' own recommendation: application data, platform/
control state, and telemetry are different guarantees with different
RPO/RTO, and a workload only inherits the guarantee for a capability it
actually uses.

**Application data:**

- **Postgres** (when used): production-single-region requires Multi-AZ
  (closing the AWS/GCP asymmetry the adversarial review found at finding #4 —
  AUDIT-078 adds the Terraform toggle). **Qualification targets HARDEN-002
  must measure and pass before a target may claim this guarantee — fixed here
  as the bar for "conformant," not asserted as already true of RDS:** RPO ≈ 0
  for infrastructure failure (synchronous standby), RTO under 2 minutes for
  automatic failover (RDS Multi-AZ's typical bound, verified per-target rather
  than treated as an AWS contractual guarantee). For logical loss (bad
  migration, accidental delete), RPO ≤ 5 minutes via the already-configured
  PITR, bounded by the existing 7-day retention window; RTO ≤ 60 minutes to
  restore into a clean qualification target, verified at the application
  level (not merely "provider job completed") per HARDEN-002 scenario 6.
- **Kafka** (when used): every topic must be created with replication factor
  ≥ 3 and `min.insync.replicas` set so `acks=all` producers cannot
  acknowledge a message that a single broker loss could then lose — closing
  the adversarial review's top finding (replication factor 1, hardcoded).
  **Qualification target, likewise proven per-target by HARDEN-002 rather
  than asserted here as already true of Redpanda:** zero loss of acknowledged
  messages on a single-broker loss; consumers resume automatically (leader
  re-election) without operator action within a target bound of 60 seconds.
  Explicitly excluded: tolerance of simultaneous multi-broker loss, and
  whole-cluster loss recovery beyond restore/replay.
- **Workload volumes** (when used): admitted only at the `single` tier in
  `v1` (§3). Durability is whatever the backing cloud block/file store
  provides by default (already durable, single-AZ bound); no automated
  backup/restore path is part of `v1` — a workload that needs one is outside
  this profile until FEAT-083/AUDIT-078 add a replica/backup-capable shape.

**Platform/control state** (Terraform, Sol release/deployment records):
RPO effectively 0 (encrypted remote state with object versioning, per §6);
RTO is "a documented recovery procedure exists and a clean operator/runner can
execute it" (AUDIT-072 scenario), not a numeric bound — control-plane state
recovery is operator-paced, not a live-traffic SLA.

**Telemetry** (logs, metrics, traces): explicitly the weakest contract on
purpose. Single-replica, non-durable telemetry backends remain acceptable in
`v1`. Telemetry loss is a diagnosability degradation, never assigned the same
RPO/RTO as business data — this is stated so nobody accidentally strengthens
it by analogy with Postgres/Kafka.

**AZ tolerance, stated once so it isn't re-litigated per capability:**
`production-single-region` claims single-AZ-loss tolerance for the Postgres
path (via Multi-AZ, above) and for `node-failure-tolerant` workload placement
(given the node group spans AZs, which the existing AWS module already does).
It does **not** claim AZ tolerance for Kafka/Redpanda broker placement or for
any workload volume, and it does not claim region-level failover at all
(already excluded by the maturity-A constraints). Where a workload uses Kafka
or a volume, its AZ exposure is a named, current exclusion — not a silent gap.

### 6. Artifact identity

FEAT-050's digest model is the artifact-identity contract for
`production-single-region`, made mandatory rather than optional: a target
selecting the profile must reject a mutable-tag deploy before any cluster
mutation, and every workload's resolved digest is recorded in the release and
in the HARDEN-002 evidence bundle. Rollback and promotion operate on recorded
digests, never on tags — closing the "the tag didn't change so nothing
restarted" and the mid-flight-retag failure modes together. No signing, SBOM
policy or provenance gate is required in `v1` (FEAT-050's own stated
out-of-scope; add it when more than one builder/trust domain exists).

### 7. Credential/security expectations

Ambient Kubernetes ServiceAccount token automount is disabled by default for
every workload in the profile; a workload gets a mounted token only via an
explicit, reviewable declaration that it genuinely needs Kubernetes API
access (SEC-004 defines the declaration shape). Runtime secret rotation
(database/API credentials) must complete through the DEC-027 reconciliation
authority without hand-edited manifests, returning the workload to healthy
state and revoking the old credential. No secret value may appear in a plan,
release record, log, or conformance evidence bundle — already true today and
restated here as a hard invariant of the profile, not a best-effort property.
Workload identity federation, service-to-service authorization, admission
policy and multi-team RBAC remain out of maturity A (SEC-004's own scope
boundary).

### 8. Operational/alerting expectations

A target selecting the profile must have a configured, non-null alert
receiver with owner metadata attached to every required alert (closing the
audit's "null receiver" finding as a hard preflight requirement, not an
advisory). The minimal maturity-A indicator/alert set and one-page runbooks
for failed rollout, node loss, Postgres dependency loss/restore, Kafka
lag/broker loss, and telemetry loss are OBS-043's to define against this
profile's guarantees. Conformance requires a synthetic alert to actually reach
the named on-call destination and be acknowledged — static "receiver is
configured" evidence does not satisfy this; only a delivered, acknowledged
test does.

### 9. Guarantees versus explicit exclusions, and the evidence that proves them

| Area | `production-single-region` claims | Explicit exclusion |
|---|---|---|
| Substrate | AWS EKS, one pinned K8s/component version set, one region, fixed capacity + headroom | Multi-cloud, autoscaling, regional failover |
| Language | OCaml | TypeScript (staged, §2 triggers) |
| Availability | `single` / `node-failure-tolerant` for `-svc`/`-worker`, per §3 bounds; worker readiness = consumer-join, distinct from liveness | Zone-failure tolerance; any tier for `-fn` (not applicable, not silently omitted) |
| Postgres | Multi-AZ, PITR restore, bounds in §5 | Cross-region replication |
| Kafka | RF≥3, zero acked-message loss on one broker, §5 bound | Multi-broker/cluster loss recovery |
| Volumes | Durable at `single` tier only | Replica/shared-volume shapes, automated backup |
| Control state | Encrypted, locked, recoverable remote state | Numeric RTO — procedure-based instead |
| Telemetry | Best-effort, non-durable | Business-data-grade durability |
| Artifacts | Mandatory resolved digests, digest-based rollback | Signing, SBOM, provenance |
| Credentials | No ambient token by default, audited rotation | Federation, multi-team RBAC, admission policy |
| Alerting | Delivered + acknowledged synthetic alert, owned runbooks | Incident-management product, org-wide escalation |

*Every numeric bound named above or in §3/§5 is a qualification target this
decision fixes, not a guarantee this decision proves. A target claims the
corresponding row only once HARDEN-002 has measured and passed that target
against it — this document is not evidence that AWS/EKS or Redpanda already
satisfies any of them.*

**Evidence:** the single evidence artifact for a conformant target is the
HARDEN-002 evidence bundle — one command/CI-job output containing profile and
component versions, target identity and selected reconciliation authority,
per-workload artifact digests, each required scenario's outcome, restore/
recovery measurements, alert-delivery acknowledgement, and the explicit list
of capabilities the workload doesn't use (and is therefore not claiming). A
target is conformant only for the profile version its evidence bundle was
produced against, on that specific target, at that timestamp — conformance is
not a permanent certificate, and re-running the bundle is required whenever
the compatibility matrix or a used capability's implementation changes.

**Versioning rule:** the profile identity is `production-single-region`, an
integer version starting at `v1` for the contract in this decision. The
version increments whenever the required-guarantee set, the exclusion list, or
the evidence-bundle schema changes in a way that changes what "conformant"
means (a compatibility-matrix update within an unchanged guarantee set, e.g.
adding TypeScript per §2, does not itself bump the profile version). Every
plan, the deployment event that established a release on the target, and every
evidence bundle records the exact profile version it was produced/validated
against; an older bundle is never silently reinterpreted as satisfying a newer
version.

**Correction (2026-09-17, found implementing FEAT-089):** this rule originally
named the *release record* rather than the deployment event. That was wrong. A
release is immutable, content-addressed workload content and may be deployed by
several targets, while a profile claim is about one target and its evidence.
Recording the claim in the release record would either make it part of release
identity (changing every workload's `release` label, and therefore rolling every
pod, merely by selecting a profile, contrary to §1) or leave it as metadata on an
immutable record, where re-deploying unchanged content with a different claim
cannot update it and the record can keep asserting a claim the target no longer
makes. The claim therefore lives in the plan while it is evaluated and in the
deployment event that put the release on that target. Release identity is
unchanged.
