**Depends on:** None.

## Question

Define Sol's first explicit production profile: `production-single-region`.
An environment named `prod` does not imply this profile, and the profile is not
a bag of Kubernetes or provider knobs. It is the compatibility boundary between:

- portable application requirements (artifact identity, availability, resources,
  persistence and configuration);
- target capabilities and operator policy (failure domains, data durability,
  state/access, alert delivery and supported versions); and
- the evidence required to claim conformance.

Engineering must resolve:

1. The one initial provider/substrate combination and exact supported Kubernetes,
   platform-component and framework versions. Supporting both clouds is not a
   maturity-A requirement.
2. Which application-facing availability and persistence semantics Sol supports,
   without exposing PDBs, topology rules, storage classes or provider settings.
3. The guarantees and explicit exclusions for Postgres, Kafka, admitted workload
   volumes, platform/control state and telemetry, including measurable recovery
   expectations where a durability claim is made.
4. Whether OCaml and TypeScript are both in the first profile. DEC-022 keeps both
   first-class overall; this decision may stage their production qualification,
   but any deferral must name its trigger.
5. The evidence artifact and versioning rule for a conformant target.

## Constraints already established

- Maturity A is one team, roughly ten workloads, one region and a real but
  non-critical customer-facing workload.
- Fixed capacity with documented headroom is valid. DEC-010's autoscaling design
  is hosted/target architecture, not a current maturity-A capability.
- Regional failover, multi-team governance, hosted control plane, fleet
  management and metering are outside this profile.
- Provider/Kubernetes mechanisms remain below the Sol semantic boundary.
- A guarantee applies only when the workload uses the relevant capability; for
  example, a workspace with no Kafka dependency need not provision Kafka merely
  to satisfy the profile.

## Acceptance criteria

- A written decision defines the profile's application requirements, target
  capabilities, guarantees, exclusions, supported version set and evidence.
- Target selection and profile selection are distinct; selecting an environment
  named `prod` does not silently select the profile.
- The decision defines observable compatibility failures before any cluster or
  infrastructure mutation.
- The decision states the initial provider/substrate and language scope rather
  than implying untested portability.
- Every maturity-A workstream can point to a precise claimed behavior or is
  explicitly removed from the critical path.
