# Deployment destinations are explicit

## Decision

**A deployment destination is a function of the target that was selected, not of whatever `kubectl` command ran most recently.**

Sol must never use `kubectl`'s `current-context` to decide where an application operation executes, and must not mutate it as a side effect. The chain is:

```
sol deploy --env prod  →  environments.prod  →  provider / region / cluster / kube credentials  →  kubectl --context <resolved>
```

and never:

```
sol deploy --env prod  →  env = prod (explicit)  +  cluster = current-context (hidden, mutable, machine-global)
```

### The invariant

> Given the same repository configuration and credentials, `sol deploy --env X` selects the same destination regardless of the machine's current `kubectl` state.

## Why

Today one decision — *where does this go?* — has **two sources of truth**. The environment comes from configuration: explicit, versioned, reviewable. The cluster comes from ambient machine state: implicit, invisible, mutable, shared across every terminal and directory. Worse, Sol **changes that state itself** — `sol cloud init` runs `kubectl config use-context` so that later commands "reach the new cluster right away".

That yields a live failure path: you initialise prod, which switches your context; the switch is sticky; days later you deploy with the **dev** target, environment from config and cluster from the environment the machine happens to be in. Nothing compares them. Because names are deliberately environment-agnostic, the render is valid against prod's cluster and replaces objects that share its names — same names, no diff, no warning.

The distinction that matters, and the reason this is worth fixing rather than validating around:

- **Implicit state can be wrong while the configuration is perfectly correct.** A user with a correct `sol.yml` can still deploy somewhere else. That is objectionable, and it is what this decision removes.
- **Explicit-but-wrong configuration is different.** Someone can always write `kube_context: production-cluster` under dev. No amount of cluster UIDs, labels, account IDs or certificates fixes incorrect configuration; at some point Sol trusts its declarative configuration. We protect this cheaply (the config-level same-cluster lint stays) and otherwise trust the config — building deep machinery to second-guess it is deferred, not forbidden (see FEAT-058).

## Consequences

- The target schema gains the destination's Kubernetes identity — a context name and/or a kubeconfig — so a target fully determines where it lands.
- Every Kubernetes operation becomes target-scoped: `--context` for kubectl, `--kube-context` for helm, or a **scoped `KUBECONFIG`**. The scoped credentials are a security gain in their own right: a dev deployment should not need prod credentials to be present at all.
- `sol cloud init` may still *print* the context-switching command for a human's own `kubectl`, but switching context must no longer be load-bearing for Sol.
- Local development keeps an explicit carve-out: the ephemeral `k3d-sol-local` target is Sol's own cluster, so it may be named literally rather than resolved from ambient state. Real environments get no default.
- This is the shape the hosted model needs anyway: a deploy worker has credentials for a particular target, not a "current kubectl context".
- UX changes deliberately: "switch context, then run `sol`" stops applying, so failures must name the context that was expected and the one that would have been used.

## Out of scope

Detecting that two *explicitly named* destinations secretly resolve to one physical cluster — a stale, renamed or mis-generated context. That is the different failure class in FEAT-058, now backlog: explicit removes the hidden input, without making an explicit value correct.
