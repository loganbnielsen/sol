**Depends on:** None.

The pre-commit guardrail's ticket-move exception misfires whenever a ticket's completion notes are large relative to the file, so a legitimate `READY_FOR_ENGINEERING` → `DONE` move is blocked and has to be committed with `SOL_SKIP_HOOKS=1`.

## Problem

`devtools/hooks/pre-commit` permits exactly one kind of `pipeline/tickets/` change inside a worktree: a rename from `READY_FOR_ENGINEERING/<id>.md` to `DONE/<id>.md`. It detects that with `git diff --cached -M`, i.e. git's **default 50% similarity threshold**.

But the workflow *requires* the completion notes to be appended immediately before the move. On a small ticket that is enough to drop below 50%: INFRA-007 went from ~25 lines to ~41, git reported `R048`, the hook saw `A` + `D`, and the commit was refused. The notes are not optional and grow with the amount of work, so this fails *most* on the tickets that deserve the most documentation.

There are two flaws:

1. **The threshold is the wrong test.** What matters is that the basename is unchanged and the file is still the same ticket — not how much prose was added.
2. **The permitted-pattern regex never compares basenames.** It matches `READY_FOR_ENGINEERING/[^/]*\.md` → `DONE/[^/]*\.md`, so `READY/A.md` → `DONE/B.md` would satisfy it. The guardrail is simultaneously too strict in practice and too loose in principle.

## Remediation

- Require basename equality explicitly (extract both paths and compare the file names), and let that do the real work — lower the similarity threshold (e.g. `-M30%`) or drop it entirely once the basename check exists.
- Keep the teeth: any *other* `pipeline/tickets/` change in a worktree must still be refused.
- Reconsider whether "the move rides the final commit" should couple the notes to the move at all. Committing the notes on the branch and special-casing only the move would remove this class of failure; the current arrangement is what makes similarity the deciding factor.

## Acceptance criteria

- A ticket whose completion notes more than double its length can be moved to `DONE` from a worktree without `SOL_SKIP_HOOKS=1`.
- A rename to a *different* ticket id under `DONE/` is still refused.
- The failure message still names the disallowed staged change and the fix.

## Reproduction added 2026-09-11 (second occurrence)

REFAC-084 hit this at the point of its own PR, so the failure is not a one-off and the shape is now measured: a **39-line** ticket with **19 lines** of completion notes appended immediately before the move. The hook printed:

```
  Disallowed staged changes:
    A	pipeline/tickets/DONE/REFAC-084.md
  D	pipeline/tickets/READY_FOR_ENGINEERING/REFAC-084.md
  Fix: git restore --staged pipeline/tickets/
```

Two notes for whoever fixes it:

- **The suggested fix is wrong for this case.** `git restore --staged pipeline/tickets/` leaves the ticket in `READY_FOR_ENGINEERING`, i.e. it "fixes" the guardrail by abandoning the move the workflow requires. A guardrail whose error message recommends the incorrect action is worse than one that only refuses.
- **The ratio is decided by note length, not by ticket size**, which is why it recurs on exactly the tickets with the most to document — REFAC-084 is one of the smallest tickets filed this cycle (a 39-line finding) and it still tripped. Lowering the threshold or dropping it in favour of the basename comparison (flaw 1) fixes both occurrences; the basename check alone would have accepted both.

The escape hatch used, as before, was `SOL_SKIP_HOOKS=1`, with build, the full unit suite and the CLI `runtest` alias run by hand immediately before the commit. That is a workable fallback but it moves the verification responsibility onto the person committing, which the guardrail exists to prevent.
