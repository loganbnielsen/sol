**Depends on:** None.

**Related:** FEAT-079 (execution-semantics ticket that follows this one;
touches the same `cronjob_doc`/`Render_fn` call site, so land this first to
avoid the two overlapping).

`-fn`'s generated `CronJob` ignores `sol.toml`'s `cpu`/`memory` and always
emits hardcoded resource requests/limits.

## Problem

`Sol_cli_toml.t` — the one parsed representation of a `[service]` table
shared by `-svc`/`-worker`/`-fn` — already carries `cpu : cpu_quantity
option` and `memory : memory_quantity option`, parsed with the same
`cpu_quantity`/`memory_quantity` machinery `-svc`/`-worker` use for their own
resource requests/limits. `-svc`/`-worker` render these through
`sol_cli_deployment_render.ml`'s `deployment_resources`. `-fn` does not: its
`Render_fn` branch skips `deployment_resources` entirely and calls
`cronjob_doc` (`sol_cli_manifest_yaml.ml`), which hardcodes:

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 250m
    memory: 256Mi
```

So a `-fn` app author can set `cpu = "2"` / `memory = "4Gi"` in `sol.toml`
and the generated manifest silently ignores it, deploying a function that
needs 2 CPU / 4 GiB with a 250m / 256Mi limit — which either OOM-kills or
CPU-throttles the function, with no error or warning anywhere in the
pipeline. This is not a missing feature; it's parsed, validated
configuration being thrown away at render time.

## Remediation

- Thread `deployment.cpu`/`deployment.memory` from the already-parsed
  `Sol_cli_toml.t` into `cronjob_doc`'s `resources.requests`/`resources.limits`,
  the same values `deployment_resources` already computes for `-svc`/`-worker`
  (`cpu_quantity_to_string`/`memory_quantity_to_string`).
- When `cpu`/`memory` are unset in `sol.toml`, keep today's exact hardcoded
  values as the default — this ticket must not change generated output for
  any `-fn` app that doesn't set them.
- No new TOML schema, no new parsing — this is purely a rendering-path fix.

## Acceptance criteria

- A `-fn` app with `cpu`/`memory` set in `sol.toml` produces a `CronJob`
  whose `jobTemplate` resources match those values.
- A `-fn` app that does not set `cpu`/`memory` produces byte-identical
  resource fields to today's output (golden-test regression coverage).
- No change to `-svc`/`-worker` rendering.
