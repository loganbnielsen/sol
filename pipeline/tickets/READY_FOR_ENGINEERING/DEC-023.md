**Depends on:** DEC-022.

**Related:** DEC-012, DEC-013, FEAT-080, FEAT-082.

**Question:** What is the normal install/distribution story for the
`@sol/*` TypeScript packages, so that the TypeScript golden path
(FEAT-082) can actually be walked by someone outside this repository?

## Context

DEC-013 decided to reserve the npm scope now and publish later, because
distribution triggers dependency-licence obligations (INFRA-007) and no
external consumer existed. DEC-022 changes that premise: TypeScript is now
the adoption funnel, which makes distribution load-bearing rather than
optional. Today the intended experience is contradicted:

```text
README:       TypeScript is first-class!
developer:    npm install @sol/kafka
npm:          404
```

The packages are real enough to be published (built, tested, dogfooded by
`demo_ts`, CI-covered) — but they remain `"private": true` and unpublished,
so a TS developer can only consume them by cloning this repo. That is not a
golden path.

## Options

1. **Publish `@sol/kafka`/`@sol/obs` to npm** (claim the scope), gated on
   FEAT-082's golden path being coherent and INFRA-007's licence inventory
   being done.
2. **Document an in-repo install path** (npm workspace / git dependency)
   until the golden path and licence inventory are ready, so an early user
   can still get started without cloning-by-hand guesswork.
3. Keep source-only, as today.

## Decision (2026-09-15) — Option 2, with npm as the explicit target

**Chosen:** document a working interim install path *now* (option 2), and
publish the supported `@sol/*` packages to npm once **FEAT-082 establishes a
coherent TypeScript golden path** *and* **INFRA-007 clears their distribution
dependencies**. Option 3 (source-only) is rejected: DEC-022 makes TypeScript the
adoption funnel, so the README's "first-class" claim cannot sit next to a 404.

The trigger is deliberately a *destination*, not an open-ended reconsideration —
npm is where this ends up. Using an interim mechanism today does not weaken
DEC-022; it acknowledges that the product is not yet at its external-release
point:

```text
today   TS = first-class product direction   distribution = interim/dev path
target  TS = first-class usable product      distribution = normal npm packages
```

**Reconciles with DEC-013** (reserve the scope, publish when the product is
worth sharing): its two stated reasons for deferring were dependency-licence
obligations and the absence of an external consumer. The second no longer holds
(DEC-022), and the first is precisely INFRA-007's job — hence the gate rather
than a bypass.

**INFRA-007** remains the blocking prerequisite for the *publish* step; its
dependency-licence audit is not assumed away here.

## Resolution detail (2026-09-15): the scope is `@sol-fab`

The `sol-fab` npm organization now exists. That settles *where* the packages
would be published, and it surfaces a naming consequence the original options
did not name:

- npm scopes are org-owned, so the publishable identifiers are
  **`@sol-fab/kafka`** and **`@sol-fab/obs`**. **`@sol/*` cannot be published**
  unless the `sol` org is owned — so today's in-repo names
  (`packages/sol-kafka` → `@sol/kafka`, `packages/sol-obs` → `@sol/obs`) are
  *internal* names, not the public ones.
- Publishing under `@sol-fab/*` therefore requires either renaming the packages
  (plus every import, the demo's dependencies, and the README/CLAUDE.md
  references), or keeping the internal names and telling consumers to alias
  (`"@sol/kafka": "npm:@sol-fab/kafka@^0.1.0"`). Aliasing works, but it is a
  poor first impression for a path whose whole point is a clean DX.

**Recommendation:** adopt `@sol-fab/*` in-repo *before* the publish step, so the
scaffold (FEAT-084), the docs, and the published artifact all agree. Deferring
the rename to publish time would instead churn the scaffold and the README once
the golden path exists. Mechanically it is a rename of the two workspace
packages plus their references — cheaper now than later.

## Remaining work

The decision is made; what remains is the interim path itself — README's
TypeScript section must point at an install mechanism that actually works for an
external developer (verified, not sketched), and the publish step's licence
obligation is discharged via INFRA-007.

## Sequencing corrected by FEAT-082's resume (2026-09-15)

The original plan published `@sol-fab/*` only *after* FEAT-082 established a
coherent golden path. The resumed walk (post-BUG-034 / PR #271) falsified that
ordering: FEAT-082 cannot represent the external-developer path while the only
route to `@sol-fab/kafka`/`@sol-fab/obs` is sitting inside Sol's own source
repository (the fixture's Dockerfile `COPY packages/sol-kafka ...`). The interim
install path is therefore **on the critical path** for FEAT-082, not downstream
of it.

The interim mechanism must have workspace-scoped semantics: a Sol workspace's
`package.json` obtains `@sol-fab/kafka`/`@sol-fab/obs` through normal dependency
resolution, and the Docker build context needs only files inside the workspace
plus that resolution. An "in-repo npm workspace / git dependency" path that
requires the enclosing Sol checkout does **not** satisfy this — that is exactly
the monorepo coupling DEC-024 removes. Options to evaluate (deliberately not
decided here): standalone git repositories per the kafka-eio/obs-eio precedent,
a release-tarball URL, or an interim registry. Public npm remains the DEC-023
target once INFRA-007 clears.

## Decision (2026-09-15, revised) — standalone GitHub repos + npm

The mechanism is decided: each existing capability lives in its own public
GitHub repository under the personal account, is independently
buildable/testable/publishable, and is consumed from npm under `@sol-fab/*`.
GitHub is the source/repository boundary; npm is the normal distribution
boundary. This follows the kafka-eio/obs-eio extraction precedent.

Explicitly rejected: `vendor/ts`, monorepo-relative `file:` dependencies,
`../../packages/...`, widening the Docker build context back to the enclosing
repo, and workspace-root inference from `package.json`/`dune-project`.

## Workflow readiness corrected (2026-09-15, later)

The "publication is ready once a token is supplied" claim above was wrong, and so
was the diagnosis of sol-kafka's red CI. Both are corrected here. The credential
blocker itself still stands.

**sol-kafka's CI was not red because `@sol-fab/obs` is unpublished.** All three
`actions/setup-node` steps in that repo passed `cache: npm` while the repo has no
committed lockfile, and setup-node fails hard in that case:

```text
##[error]Dependencies lock file is not found in /home/runner/work/sol-kafka/sol-kafka.
Supported file patterns: package-lock.json,npm-shrinkwrap.json,yarn.lock
```

Both CI jobs died *inside* setup-node, ~11 s in, before `npm install` ever ran —
so the unpublished dependency was never reached. With caching removed the
workflow proceeds to the real, expected failure (`E404 @sol-fab/obs`), which
resolves itself the moment obs ships.

**Trusted publishing cannot bootstrap either package.** A trusted publisher is
attached to a package that already exists on the registry — npm's own `npm trust`
prerequisites state "Package must exist". Both `@sol-fab/obs` and
`@sol-fab/kafka` 404, so **v0.1.0 cannot be published via OIDC.** The shape is a
one-time bootstrap credential, then OIDC for every release after it:

```text
v0.1.0            bootstrap token (NPM_TOKEN, short-lived, then deleted)
v0.1.1 onward     npm trust github <pkg> --file release.yml --allow-publish
```

**Version floor.** Every Node 22 release ships npm 10.9.8. OIDC trusted
publishing requires npm >= 11.5.1 and `npm trust` requires >= 11.15.0, so the
Node 22 pin in these workflows could not have authenticated that way at all.
Both repos now pin `node-version: 24` (npm 11.19.x).

An `NPM_TOKEN` and a `trust` configuration conflict, so the bootstrap token must
be removed from both release workflows (and both repo secrets deleted) at the
flip. That instruction is recorded in the workflow headers themselves, next to
the `env:` block it refers to.

### State at time of writing

- Done and pushed, credential-free: `node-version: 24` across all four workflows;
  sol-kafka's `cache: npm` removed (to be restored together with `npm ci` once the
  lockfile exists); the bootstrap→OIDC path documented in both `release.yml`.
  Commits `sol-obs@3b083ee`, `sol-kafka@520db9f`. sol-obs CI green on Node 24;
  sol-kafka CI red only at `npm install` (`E404 @sol-fab/obs`) — the honest state.
- The blocker is now genuinely *just* the credential. Supply a bootstrap
  `NPM_TOKEN` for both repos: a granular token with publish rights on `@sol-fab`.
  The 2FA-bypass option is **correct here** — it is what lets CI publish
  unattended. Tag `v0.1.0` obs-first, then sol-kafka. Then run `npm trust github`
  for each package, which is a *separate* credential path: `npm trust` rejects
  granular tokens carrying the 2FA-bypass option, so it must run locally with
  interactive 2FA. Do not reuse the bootstrap token's properties for it.
- The flip needs local npm >= 11.15.0 for `npm trust`; this environment has
  10.9.8 (Node 22.23.0), so local npm must be upgraded before the flip.

## Acceptance criteria

- A written decision names the distribution mechanism and its trigger.
- README's TypeScript section points at a path that actually works for an
  external developer.
- Any publish step's licence obligation is addressed via INFRA-007, not
  assumed away.
- A Sol workspace can obtain `@sol-fab/kafka`/`@sol-fab/obs` from outside the
  Sol repository (the FEAT-082 boundary criterion), without widening the
  workspace's Docker build context.
