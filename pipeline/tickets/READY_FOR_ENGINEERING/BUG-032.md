**Depends on:** None.

**Related:** FEAT-079 (introduced `sol fn run`), INFRA-016 (the spike that
found this while trying to fire a concurrent burst).

`sol fn run`'s generated Job name has only one-second resolution, so firing
it more than once within the same second produces a name collision.

## Problem

`cli/sol/bin/cmd_fn.ml`'s `generate_job_name`:

```ocaml
let generate_job_name ~k8s_name =
  Printf.sprintf "%s-manual-%d" k8s_name (int_of_float (Unix.time ()))
```

`Unix.time ()` has one-second resolution. Two `sol fn run` invocations of
the same `-fn` within the same wall-clock second generate the identical
Job name, so the second `kubectl create job` fails with `AlreadyExists`.
This was invisible when FEAT-079's own CI coverage only ever fired one
invocation at a time; INFRA-016 needs several concurrent invocations to
generate realistic burst load and hit it immediately.

## Remediation

Add higher-resolution or explicitly collision-resistant entropy to the
generated name — e.g. sub-second time resolution
(`Unix.gettimeofday ()`'s fractional part) or a short random suffix,
following the same "mutex-protected, non-global `Random.State.t`" pattern
already established elsewhere in this codebase for anything jitter/entropy
related (see `kafka_service_retry_topics.ml`'s `produce_rng`/`message_rng`)
if randomness is used. Keep the name short enough to stay within
Kubernetes' Job-name length limit alongside `k8s_name`.

## Acceptance criteria

- Firing `sol fn run`/`sol local fn run` against the same `-fn` multiple
  times within the same second produces distinct Job names every time —
  add a test that calls `generate_job_name` (or an equivalent exposed seam)
  twice in immediate succession and asserts the results differ.
- No change to the mandatory `--from=cronjob/...` mechanism itself.
