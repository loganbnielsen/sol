**Question:** A Sol workspace's OCaml services compile against Sol's application
framework (`sol-svc`, `sol-worker`, `sol-obs`, …). What is the supported way for a
workspace to obtain those when it is **not** inside a Sol source checkout?

## Context

This is the boundary DEC-023 resolved for TypeScript, one layer later. DEC-023's
finding was that `@sol-fab/kafka`/`@sol-fab/obs` were only obtainable from a parent
Sol checkout; the answer was standalone source repositories plus npm distribution,
so a workspace consumes them through ordinary package management. The OCaml
services have the identical shape and no equivalent answer.

### This is a product finding, not an example problem

The strongest evidence is the scaffold itself. `sol new workspace` emits a
workspace whose `vendor/framework` is a symlink into a Sol install, and documents
exactly two supported ways to obtain the framework (quoted from
`cli/sol/lib/sol_cli_scaffold_templates.ml`):

> `vendor/framework` is a symlink into the Sol source tree.
> `sol new workspace` creates it automatically.
>
> - **Release tarball install:** The bundle includes framework source — no extra
>   steps needed.
> - **Source checkout install:** Set `SOL_HOME` once (in `~/.bashrc` or
>   `~/.zshrc`), then `sol new workspace` creates the link automatically.

```bash
export SOL_HOME=/path/to/sol
ln -sf $SOL_HOME/framework vendor/framework
```

with the layout table describing `vendor/` as "symlinks to Sol framework source
(not committed)".

**Both documented modes require a Sol distribution to be present on the machine.**
Neither is a package-manager dependency. So FEAT-085 did not discover an
example-level defect; it surfaced the product-level distribution story, which is
currently "you must already have Sol".

Note the asymmetry this makes visible: the ecosystem libraries — `kafka-eio`,
`obs-eio`, `obs-loki-eio`, `lambda-eio`, and the rest of `sol.opam`'s dependency
list — **are** opam packages, and the scaffold comment says so explicitly
("lambda-eio are extracted opam packages: not vendored into `vendor/framework`").
Sol's own application framework is the sole exception, and it is the part every
workspace needs.

### Why the current answer contradicts DEC-024

DEC-024 puts the workspace boundary at `sol.yml` and requires a workspace to be
independently located. FEAT-085's acceptance criterion is that `examples/pluto`
builds "from a copy of itself alone, with no enclosing Sun checkout". A
`$SOL_HOME` symlink is that enclosing checkout under another name. Widening a
Docker build context or committing `vendor/framework` would relabel the coupling,
not remove it — which is precisely the reasoning DEC-023 used to reject `vendor/ts`
for the TypeScript packages.

## Options

1. **Publish the framework to opam**, so a workspace declares
   `sol-svc`/`sol-worker`/`sol-obs` as ordinary opam dependencies. The ecosystem
   already works this way, and `kafka-eio`/`obs-eio` are the author's own
   precedent for doing it.
2. **Keep the `$SOL_HOME` / release-tarball vendor model as the supported
   mechanism**, and make it explicit and robust rather than incidental.
3. **Vendor the framework source into each workspace, committed**, so a workspace
   is self-contained but carries a copy.
4. **Git-based pinning** (`opam pin` against a repository/tag) as an interim
   between 1 and 2.

## What the decision must settle

Committing to option 1 does **not** by itself answer these, and they are the
reason this is a decision rather than a mechanical step:

- **Source vs distribution, separately.** DEC-023 established that GitHub is the
  source boundary and npm the distribution boundary, and that these are distinct
  choices. The opam analogue needs the same treatment: opam is a candidate
  *distribution* mechanism and does not by itself dictate where the framework
  source lives (one repo, several repos, or the `sol` repo).
- **Package granularity.** Whether the framework ships as one opam package or a
  graph (`sol-svc`, `sol-worker`, `sol-obs`, `sol-cli`, …), and how that maps onto
  the existing `framework/*` directory layout.
- **Prerequisites.** Which of the existing standalone `*-eio` libraries would need
  publication or version bumps first, and whether any framework module is
  separable or would force a wider split.
- **Licensing.** INFRA-007 records the **opam dependency graph as not
  inventoried** — no licence scan runs for the OCaml side. Distribution is what
  triggers the obligations, so this is the same gate DEC-023/INFRA-007 applied to
  npm, and it is currently unmet.
- **Versioning and release coordination.** What a `sol-svc` version means against
  a moving `main`, and how framework, CLI and the `*-eio` libraries stay
  compatible. DEC-013 raised the same "a version story" problem and it was never
  answered.
- **Consistency with the TS answer.** Whether the OCaml path should admit the same
  shape of solution (standalone public repos + package-manager distribution), so
  the two languages do not end up with divergent mental models.

## Acceptance criteria

- A written decision names the mechanism by which an OCaml workspace obtains the
  Sol framework, and states explicitly whether a Sol source checkout remains
  required.
- The answer preserves the source-vs-distribution distinction rather than
  conflating "where the code lives" with "how it is delivered".
- The opam licence/dependency inventory obligation is discharged via INFRA-007, or
  explicitly deferred with a stated trigger — not assumed away.
- `sol new workspace`'s emitted README and layout describe the decided mechanism,
  so the scaffold stops documenting a `$SOL_HOME` dependency the contract forbids.
- A workspace copied **physically outside** any Sol checkout builds and runs in
  both languages (the FEAT-085/FEAT-082 proof), without the build context being
  widened to an enclosing repository.
