REFAC-071.

**Question:** A Sol workspace's OCaml services compile against Sol's application
framework (`sol-svc`, `sol-worker`, `sol-obs`, …). What is the supported way for a
workspace to obtain those when it is **not** inside a Sol source checkout?

## Context

This is the boundary DEC-023 resolved for TypeScript, one layer later. DEC-023's
finding was that `@sol-fab/kafka`/`@sol-fab/obs` were only obtainable from a parent
Sol checkout; the answer was standalone source repositories plus npm distribution,
so a workspace consumes them through ordinary package management. The OCaml
services have the identical shape and no equivalent answer.

### This is a product finding, not an example problem

The strongest evidence is the scaffold itself. `sol new workspace` emits a
workspace whose `vendor/framework` is a symlink into a Sol install, and documents
exactly two supported ways to obtain the framework (quoted from
`cli/sol/lib/sol_cli_scaffold_templates.ml`):

> `vendor/framework` is a symlink into the Sol source tree.
> `sol new workspace` creates it automatically.
>
> - **Release tarball install:** The bundle includes framework source — no extra
>   steps needed.
> - **Source checkout install:** Set `SOL_HOME` once (in `~/.bashrc` or
>   `~/.zshrc`), then `sol new workspace` creates the link automatically.

```bash
export SOL_HOME=/path/to/sol
ln -sf $SOL_HOME/framework vendor/framework
```

with the layout table describing `vendor/` as "symlinks to Sol framework source
(not committed)".

**Both documented modes require a Sol distribution to be present on the machine.**
Neither is a package-manager dependency. So FEAT-085 did not discover an
example-level defect; it surfaced the product-level distribution story, which is
currently "you must already have Sol".

Note the asymmetry this makes visible: the ecosystem libraries — `kafka-eio`,
`obs-eio`, `obs-loki-eio`, `lambda-eio`, and the rest of `sol.opam`'s dependency
list — **are** opam packages, and the scaffold comment says so explicitly
("lambda-eio are extracted opam packages: not vendored into `vendor/framework`").
Sol's own application framework is the sole exception, and it is the part every
workspace needs.

### Why the current answer contradicts DEC-024

DEC-024 puts the workspace boundary at `sol.yml` and requires a workspace to be
independently located. FEAT-085's acceptance criterion is that `examples/pluto`
builds "from a copy of itself alone, with no enclosing Sun checkout". A
`$SOL_HOME` symlink is that enclosing checkout under another name. Widening a
Docker build context or committing `vendor/framework` would relabel the coupling,
not remove it — which is precisely the reasoning DEC-023 used to reject `vendor/ts`
for the TypeScript packages.

## Independence criteria

Three properties, each separately testable. They are stated separately because a
solution can satisfy one or two and still be a bad distribution mechanism:

1. **Location independence.** A workspace builds outside the Sol checkout — the
   directory may be moved anywhere.
2. **Installation independence.** The application build does not read
   `$SOL_HOME/framework`, or any other path into a Sol source installation.
3. **Version independence.** The framework version a workspace builds against is
   declared in workspace-owned dependency metadata, and is not changed by
   installing, upgrading or removing the `sol` CLI.

Criterion 3 is the one a `/tmp/foo` copy test cannot catch by itself. `sol new`
could "fix" location independence by **copying** framework source out of
`$SOL_HOME` into the workspace instead of symlinking it: the copy builds anywhere,
the coupling survives in a form that is harder to see, and the framework version
silently tracks whichever Sol install happened to be present at scaffold time.

## What "no Sol source checkout" does and does not mean

The proof is about the *application's dependency graph*, not about a machine being
free of Sol. Expected to be present:

```text
sol CLI installed                          OK -- tooling, not an application dependency
OCaml / opam toolchain installed           OK -- the language toolchain
declared application dependencies          OK -- resolved by the package manager
```

Not acceptable:

```text
Sol source checkout                        X
$SOL_HOME/framework in the build graph     X
vendored or copy-generated framework src   X
parent dune-project                        X
parent opam metadata                       X
```

The distinction to preserve: a workspace may depend on the `sol` **executable as
tooling**; it must not depend on that executable's **source installation as an
undeclared application dependency**.

## Evidence gathered (2026-09-16)

### The framework dependency graph

Eight Dune libraries under `framework/`, **none declaring a `public_name`** —
which is precisely why they resolve only inside this repo's root Dune project:

```text
sol_runtime        -> eio, eio.unix                                   (leaf)
sol_env            -> eio                                             (leaf)
sol_obs            -> obs-eio, obs-loki-eio, obs-prometheus-eio,
                      obs-tempo-eio                                   (leaf)
kafka_eio_service  -> kafka-eio, obs-eio, https-eio, http, yojson,
                      uri, cstruct, eio, eio.unix, unix               (leaf)

sol_svc            -> sol_obs, sol_runtime, cohttp-eio, https-eio,
                      jose, ptime, http, uri, yojson, base64
sol_worker         -> sol_env, sol_obs, sol_runtime,
                      kafka_eio_service, kafka-eio, obs-prometheus-eio
sol_fn             -> sol_env, sol_obs, sol_runtime,
                      lambda-eio, obs-prometheus-eio
sol_jobs           -> sol_env, sol_obs, sol_runtime, pg-eio, caqti
```

A shallow DAG: four shared leaves, four application-shape libraries. The split is
by **application shape** (HTTP service / Kafka worker / scheduled function / job),
not by arbitrary module boundary — which is a good sign for it being a defensible
public API rather than an accident.

### The internal names are already the de-facto public API

Not a hypothetical risk. `sol new workspace` emits service `dune` files that name
these libraries directly:

```lisp
(libraries {{name}}_storage {{name}}_payments_events sol_svc sol_obs yojson)
(libraries sol_worker kafka_eio_service sol_obs pg-eio)
(libraries sol_fn)
```

So `sol_svc`, `sol_worker`, `sol_fn`, `kafka_eio_service` and `sol_obs` are what
users already write. Publishing them formalises an API the scaffold has
effectively already committed to. That cuts both ways: option 1 needs no invented
public API, but these boundaries cannot be redrawn later without breaking
workspaces.

### How the CLI wires the framework today

```text
sol new workspace     creates vendor/framework as a symlink to $SOL_HOME/framework
                      (sol_cli_cmd_new.ml; prints `ln -sf` instructions when absent)
sol up                "resolves vendor/ symlinks into the build context before
                      running docker build" (tpl_dockerfile)
sol_cli_workspace.ml  skips vendor/ when walking the workspace; never follows symlinks
```

The framework therefore reaches the build graph by being **materialised into the
Docker build context out of a Sol installation**. That fails criteria 2 and 3 at
once, and it is the mechanism that has to be replaced.

Separately, `sol_cli_dev_observability.ml` also reads `SOL_HOME` for dashboard
JSON. That is the CLI reading its own bundled resources at development time, not
part of an application build, so it is a different and far lower-severity case —
worth not conflating with the framework dependency.

### opam precedent: the shape is settled, the publication is not

Every `*-eio` library is **one package in its own `loganbnielsen/*` repo**,
independently versioned (`kafka-eio` 0.3.0, `obs-eio` 0.1.2, `https-eio`/`aws-eio`
0.1.1, the rest 0.1.0). Notably `obs-*` is split four ways **by backend**
(`obs-eio`, `obs-loki-eio`, `obs-prometheus-eio`, `obs-tempo-eio`) rather than
shipped as one package with optional dependencies — a boundary drawn by dependency
weight, not by convenience. That is the precedent, and it is a good one here.

But publication is incomplete, as the generated Dockerfile itself records:

> obs-eio/obs-loki-eio/obs-prometheus-eio/obs-tempo-eio/pg-eio/https-eio/
> lambda-eio are extracted opam packages: not vendored into vendor/framework, and
> **not yet published to the public opam-repository** — every generated service's
> bin/dune depends on some subset of them, so the build stage needs the same opam
> pin this repo's own `.github/workflows/ci.yml` uses.

Measured against `ocaml/opam-repository`:

| Published | Not published |
| --- | --- |
| `kafka-eio`, `obs-eio`, `obs-prometheus-eio`, `https-eio`, `aws-eio` | `obs-loki-eio`, `obs-tempo-eio`, `pg-eio`, `lambda-eio`, `s3-eio`, `dynamodb-eio` |

The local development switch resolves **all** of them by git pinning a local
checkout (`git+file:///home/lbendtly/Code/kafka-eio#main`, …), so even the
precedent's own day-to-day path is location-dependent.

### Publication prerequisites

`sol_obs` needs `obs-loki-eio` and `obs-tempo-eio`; `sol_jobs` needs `pg-eio`;
`sol_fn` needs `lambda-eio`. **All four are unpublished.** No coherent
"publish the framework to opam" plan exists that does not publish those first —
each its own repository with its own licence, tests and release process. Opam
publication is therefore a decision *plus* a programme of work, not a step.

## The package-shape question

Deliberately separate from the mechanism question. If the destination is opam,
what does a consumer write?

**A. One `sol` package** — `depends: ["sol"]`. Simplest for consumers, and mirrors
the single `sol` opam package this repo already generates from `dune-project`. But
it bundles all four application shapes and every backend, forcing an HTTP-only
service to depend on `pg-eio`, `lambda-eio` and the Kafka stack; and it makes the
CLI and the framework one versioned unit, which is exactly the coupling criterion 3
forbids.

**B. One package per framework library** (8 packages). Maximum granularity, closest
to the `obs-*` precedent, lets a consumer take only what it uses. But it publishes
`sol_runtime`/`sol_env` — internal plumbing with no independent meaning — as
permanent public API, and multiplies release coordination eightfold.

**C. Packages at the application-shape boundary only** — `sol-svc`, `sol-worker`,
`sol-fn`, `sol-jobs`, `sol-obs`, plus `kafka-eio-service` (the scaffold already
names it), with `sol-runtime`/`sol-env` remaining private implementation detail
folded into them. Matches what the scaffold already tells users to write, avoids
publishing plumbing, and keeps a `sol-svc`-only upgrade from dragging `sol-worker`
with it.

**Open sub-question if C is chosen:** whether `sol-obs` stays whole (matching the
TypeScript `@sol-fab/obs`, which is one package) or mirrors the `obs-*` backend
split. Whole is simpler and keeps the two languages conceptually aligned; split
follows the OCaml precedent and avoids forcing every consumer to take all four
observability backends. This needs deciding rather than defaulting.

## Options (mechanism)

1. **Publish the framework to the public opam-repository**, so a workspace declares
   its framework packages as ordinary opam dependencies. Strongest answer: it
   satisfies all three criteria, matches the `*-eio` precedent's destination, and
   makes `opam` (not `$SOL_HOME`) the source of truth. Gated on the publication
   prerequisites above.
2. **opam via git pin** (`opam pin add sol-svc git+https://…#v0.1.0`). This is what
   the project's own development already does, and pinning to a **tag** satisfies
   criterion 3 (the version is declared in workspace metadata and pinned), while
   needing no upstreaming. Weaker as a "supported distribution story": every
   consumer build needs git access, and it does not give the framework an
   ecosystem home. A credible interim.
3. **Keep the `$SOL_HOME` symlink / release-tarball vendor model** and make it more
   explicit or more robust. Rejected: fails criteria 2 and 3 by construction.
4. **Vendor or copy framework source into each workspace.** Rejected: may pass a
   `/tmp/foo` test while silently tying the framework version to when the workspace
   was scaffolded — the failure mode criterion 3 exists to catch — and it is the
   pattern DEC-023 rejected as `vendor/ts`.

## Decision (2026-09-16)

**Distribution mechanism:** opam is the canonical OCaml framework distribution
mechanism.

**Interim:** immutable tag/commit-pinned git opam dependencies are acceptable
while the packages work their way through the public opam-repository. Public-opam
publication is release engineering and must not block FEAT-085.

**Supported application-facing API:** `sol-svc`, `sol-worker`, `sol-fn`,
`sol-jobs`, `sol-obs`, `kafka-eio-service`.

**Installable internal framework packages:** `sol-runtime` and `sol-env`. These
are shared plumbing, but public framework libraries link against them, so they
**must** be installed and resolvable. They are therefore their own packages —
findlib/opam-visible, documented as internal implementation dependencies and
**not supported for direct application use**. They ride the coordinated release
train, so consumers never choose them independently; opam pulls the matching
version transitively.

"Private" here means *not part of the supported application API*, not *not
installed*. Those are different properties, and Dune's `(public_name)`-less
libraries implement the latter literally. Package managers expose implementation
dependencies routinely; the public-API boundary is a support and compatibility
contract, not a namespace access-control mechanism.

**Deliberately not `sol-svc.runtime`.** Namespacing shared plumbing under
`sol-svc` would make `sol-worker` depend on the HTTP/service package for a purely
artificial packaging reason. The honest graph keeps the shared plumbing its own
identity:

```text
sol-runtime ──┬──> sol-svc
              ├──> sol-worker ──> sol-jobs
              └──> sol-fn
sol-env     ──┬──> sol-worker
              ├──> sol-fn
              └──> sol-jobs
sol-obs     ──┬──> sol-svc / sol-worker / sol-fn / sol-jobs
kafka-eio-service ──> sol-worker
```

**Installed public library names are hyphenated** — `sol-svc`, `sol-worker`,
`sol-fn`, `sol-jobs`, `sol-obs`, `kafka-eio-service`, `sol-runtime`, `sol-env`.
The underscore spellings (`sol_svc`, `kafka_eio_service`, …) were
monorepo-internal identities and are not preserved externally; generated consumer
Dune metadata uses the public names.

**Dependency channels — development vs release** (revised 2026-09-16; the earlier
absolute "mutable branch pins are forbidden" was over-strict for the current
lifecycle):

```text
DEVELOPMENT / DOGFOODING              RELEASE / STABLE
OCaml   opam pin add …#main           versioned opam package
TS      github:loganbnielsen/…#main   @sol-fab/…@x.y.z
```

- **Development workspaces MAY track mutable Git refs** such as `main`, in both
  languages. The workspace owns that choice.
- **Release and stable dependencies MUST resolve through versioned package
  releases or immutable refs.**
- **Build reproducibility comes from the lockfile, not from the ref.** In
  TypeScript `package-lock.json` resolves `github:…#main` to a specific commit;
  in OCaml an opam lock file (or a version constraint) plays that role. So
  `main`-tracking development and deterministic builds coexist: `package.json`
  records intent, the lockfile records the resolved commit.
- Where an upstream repository has no suitable tag, use an **immutable commit
  SHA**. Do not block on public-opam publication and do not manufacture tags
  solely to serve this interim mechanism — RELEASE-005 establishes proper
  releases and public-opam distribution later.

**Version independence does not require immutable source refs.** What it forbids
is the *installed `sol` CLI* determining the application's framework version. A
workspace that explicitly declares `#main` (or a pin, or a version) in its own
metadata satisfies it — the workspace owns the choice, the CLI does not make it.
Release reproducibility is a *separate* property, and it is the lockfile or
version constraint that provides it, not the immutability of the ref.

**TypeScript development channel — verified working, with one required opt-in.** npm
installs a Git dependency from source: it fetches the repository, installs its
devDependencies and runs its `prepare` script. `@sol-fab/obs` and `@sol-fab/kafka`
must therefore be installable **from source**, not merely as published tarballs.
Both declared `prepublishOnly` but no `prepare`, so a `github:` dependency would
have installed an unbuilt package whose `main` pointed at a `dist/` that does not
exist. A `prepare` script was added to both repositories and the channel was then
verified end to end:

```text
$ cat .npmrc          # committed in the workspace
allow-git=all
$ npm install github:loganbnielsen/sol-obs#main
$ node -e "import('@sol-fab/obs')"     -> 12 exports, routeLabel works
$ jq .packages["node_modules/@sol-fab/obs"].resolved package-lock.json
"git+ssh://git@github.com/loganbnielsen/sol-obs.git#d4c3cdc37..."
```

**The blocker is `allow-git`, which npm 12 defaults to `none`.** Without it, npm
refuses outright:

```text
npm error code EALLOWGIT
npm error Fetching packages of type "git" have been disabled
```

So the TypeScript development channel requires `allow-git=all` in a **committed
`.npmrc`** — confirmed sufficient on its own, with no CLI flag. That keeps the
choice in workspace-owned metadata, which is what version independence requires.

Two operational notes:

- Prefer the explicit `git+https://github.com/…` form in `package.json` over the
  `github:` shorthand. The shorthand resolved to `git+ssh://`, which needs an SSH
  key and will not work in CI, where only an HTTPS token is available.
- npm 12 emits an `allowScripts` warning naming the dependency's `prepare` script
  (`npm warn install-scripts … blocked`). Empirically the build still ran — `dist/`
  is gitignored, so it could only have come from `prepare` — but npm is tightening
  install-script policy, so this is worth watching rather than assuming stable.

**Observability:** `sol-obs` stays **one** Sol-facing abstraction. The lower-level
`obs-*` backend split is an implementation/dependency concern and must not leak
into the Sol application API merely to mirror its package graph. (The `obs-*` split
exists to avoid pulling every backend; the Sol-facing API's job is the opposite —
present one naming/shape vocabulary.)

**Versioning:** the Sol framework is a **coordinated release train**. Public Dune
library boundaries do not imply independently versioned framework components, so
`sol-svc` and `sol-worker` move together rather than carrying independent
compatibility ranges.

**Required invariants**, all three, no exceptions:

1. **Location independence** — a workspace builds when moved outside the Sol
   checkout.
2. **Installation independence** — the application build never reads
   `$SOL_HOME/framework`.
3. **Version independence** — the framework version is declared in
   workspace-owned dependency metadata and is unaffected by installing or
   upgrading the `sol` CLI.

Explicitly forbidden: `$SOL_HOME/framework`, copied or vendored framework source,
parent project metadata (`dune-project`/opam), and **mutable branch pins**.

### Consequence for sequencing

The interim path is not a fallback to be avoided — it is the path that unblocks
FEAT-085. Order:

1. Give the framework public opam package definitions and publishable library
   names.
2. Have `sol new workspace` emit workspace-owned opam metadata that declares the
   framework dependencies, and **stop creating `vendor/framework`**.
3. Have `sol up` stop materialising framework source into the Docker build
   context (and stop emitting `#main` pins in generated Dockerfiles).
4. Make the OCaml examples ordinary workspaces under the same mechanism.
5. Prove it: `/tmp/foo` for both languages.
6. Close FEAT-085 and resume FEAT-082.

Public-opam publication — publishing the framework packages and the six
still-unpublished `*-eio` dependencies, plus the INFRA-007 opam licence inventory
— is tracked separately as the release-engineering completion of this decision,
and does not gate steps 1–6.

### Feasibility notes recorded at decision time

- `loganbnielsen/sol` is public and carries tags, so framework pins have an
  immutable ref to target.
- Two required dependencies, **`obs-tempo-eio` (needed by `sol-obs`) and
  `lambda-eio` (needed by `sol-fn`), have no tags at all.** The existing generated
  Dockerfiles pin everything at `#main`, which the invariants now forbid, so those
  two must be pinned by **commit SHA** until they cut releases.

### Implementation constraint: "private" is achievable in API terms, not in packaging terms

Found while starting the packaging work. `sol-runtime` and `sol-env` are shared
*libraries* — four public libraries link against them. A Dune library with no
`public_name` is not installed at all, and a library without a public name is only
resolvable from its own directory subtree, so a shared private library cannot be
consumed by published packages in sibling directories. **Anything a published
library links against must itself be installed and findlib-addressable.**

Experimentally verified, the workable forms are:

1. **Namespace it into an existing public package** —
   `(library (name sol_runtime) (public_name sol-svc.runtime))`. Confirmed to
   install into `lib/sol-svc/` alongside the public library and to link correctly.
   But it is findlib-visible, so "private" becomes a documentation/API convention
   rather than an enforced boundary, and every other package needing it must
   depend on package `sol-svc` — a worker pulling the HTTP package.
2. **Give it its own package** (`sol-runtime`), documented as internal and not for
   direct use. Cleaner dependency-wise and more honest — it *is* a package — at
   the cost of publishing two packages DEC-025 called private.

This does not change the decision's intent: these are not application-facing API
and are not documented for direct use. It changes what "private" can mean
mechanically.

**Resolved 2026-09-16: form 2 — `sol-runtime` and `sol-env` become their own
installable internal packages**, documented as internal implementation
dependencies and not supported for direct application use. Form 1 was rejected
because packaging shared plumbing under `sol-svc` would give `sol-worker` an
HTTP/service package dependency for a purely mechanical reason. See the Decision
section above for the full terminology.

### The coupling is now proven, not argued: public names and `vendor/framework` are mutually exclusive

Attempting the packaging step produced a hard failure rather than a debate. Adding
`(public_name …)` to the framework libraries made the existing scaffold test fail,
because `sol new workspace` **symlinks the framework source into the generated
workspace**:

```text
linked   testapp/vendor/framework -> /home/lbendtly/Code/sun/framework

File "vendor/framework/kafka-eio-service/lib/dune", line 3:
 (public_name kafka-eio-service)
Error: You cannot declare items to be installed without adding a
<package>.opam file at the root of your project.
```

The symlink makes the framework's Dune files part of the **consumer's** Dune
project. So any library declaration that externalises the framework — which is the
minimum a package needs — breaks every generated workspace. This is not a test
artefact: `sol new` produces exactly this layout for real users, so the packaging
change is a *user-visible* break on its own.

Two consequences:

1. **The packaging change and the removal of `vendor/framework` must land
   together.** Neither is independently landable; the intermediate commit is
   broken by construction.
2. It demonstrates, by construction rather than by argument, the claim this
   decision rests on: the vendored symlink is not a convenience, it *is* the
   coupling. A framework that is genuinely a package cannot also be vendored
   source.

The working packaging change (eight `public_name`s, eight `(package …)` stanzas,
generated `.opam` files) is preserved in `git stash@{0}` rather than committed,
pending the scaffold change. It was verified sound in isolation — `dune build`
clean, `dune build @install` generating all nine `.opam` files, `sol-svc.install`
installing into `lib/sol-svc/`, and `sol-svc`'s META correctly requiring `sol-obs`
and `sol-runtime`.

## What this does not decide

- Where the framework **source** lives (one repo, several, or the `sol` repo). Per
  DEC-023 the source boundary and the distribution boundary are separate
  questions; opam is a distribution answer only.
- The licence/dependency inventory, which remains INFRA-007's obligation (opam
  graph still uninventoried) and the separate publication ticket's prerequisite.
- The concrete version string of the coordinated train, and how framework, CLI and
  `*-eio` versions are asserted compatible at release time.

## Acceptance criteria

- A written decision names the mechanism by which an OCaml workspace obtains the
  Sol framework, and states explicitly whether a Sol source checkout remains
  required.
- **All three independence properties hold**: location independence, installation
  independence (no `$SOL_HOME/framework` in the build graph), and version
  independence (the framework version is workspace-declared and unaffected by
  installing or upgrading the `sol` CLI).
- The copy-outside-the-checkout proof holds for the OCaml path — while explicitly
  permitting an installed `sol` CLI, an installed OCaml/opam toolchain, and
  declared application dependencies. The forbidden set is: Sol source checkout,
  `$SOL_HOME/framework` in the build graph, vendored or copy-generated framework
  source, parent `dune-project`, parent opam metadata.
- The package shape is decided deliberately, with the current internal Dune
  library boundaries not adopted as the public API merely because they are the
  easiest thing to publish.
- The answer preserves the source-vs-distribution distinction rather than
  conflating "where the code lives" with "how it is delivered".
- The opam licence/dependency inventory obligation is discharged via INFRA-007, or
  explicitly deferred with a stated trigger — not assumed away.
- `sol new workspace`'s emitted README, dune/opam metadata and layout describe the
  decided mechanism, so the scaffold stops documenting a `$SOL_HOME` dependency the
  contract forbids.
- A workspace copied **physically outside** any Sol checkout builds and runs in
  both languages (the FEAT-085/FEAT-082 proof), without the build context being
  widened to an enclosing repository.
