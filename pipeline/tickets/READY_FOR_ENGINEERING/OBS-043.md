**Depends on:** DEC-026.

## Production guarantee

A required production alert reaches a named accountable human through a tested
route and supplies a usable first response action. Dashboards, firing rules, a
configured receiver, SLOs and runbooks are parts of that guarantee; none is
sufficient alone.

OBS-040 shipped useful alert rules with a deliberate null receiver. The original
OBS-043 proposed one PagerDuty example, while the audit proposed warning about the
null receiver. This ticket replaces both mechanism-level scopes.

## Decision boundary

DEC-026 names the minimal platform/workload indicators and objectives the first
profile claims. Engineering must define a provider-neutral target capability for
alert delivery and ownership. PagerDuty may be the first adapter, but it is not
the Sol-level semantic.

## Implementation scope

- Define the minimal maturity-A SLO/indicator set and alert conditions.
- Require target-owned receiver and owner metadata for the production profile.
- Validate the route rather than merely checking that configuration is non-null.
- Add one-page runbooks for failed rollout, node loss, Postgres dependency
  loss/restore, Kafka lag/broker loss and telemetry loss.
- Provide the smallest working receiver integration needed by the selected pilot
  team; retain null routing for local/dev only.
- Add a synthetic alert path that can prove delivery without causing a real
  outage.

## Conformance and acceptance criteria

- A synthetic alert sent through the production route reaches the named on-call
  destination and is acknowledged.
- Missing/unroutable receiver or missing owner/runbook evidence makes production
  conformance fail before the pilot.
- Every required production alert identifies an owner and links to its first
  response runbook.
- Game-day records show the team used the runbooks for the failure scenarios
  claimed by DEC-026.
- Telemetry loss produces its explicitly documented degraded operating mode; it
  is not assigned the same durability guarantee as business data by accident.

## Non-goals

- Building a paging product, incident-management system or organization-wide
  escalation policy.
- Requiring PagerDuty specifically in the public profile.
- Multi-team ownership/governance.

**Implementation versus evidence:** This ticket defines and wires the response
contract. HARDEN-002 proves end-to-end delivery and records game-day evidence.

**Demo/example coverage:** Document and exercise the synthetic alert against the
production-profile example; do not commit real routing credentials.

**TypeScript parity:** Not language-specific; alert labels and ownership metadata
must remain consistent across supported workload languages.
