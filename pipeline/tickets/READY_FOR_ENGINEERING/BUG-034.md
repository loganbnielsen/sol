## Repro (real run, CLI at 2a5e2da6)

```text
$ cd examples/pluto
$ sol up --scope=demo_ts
Run: up-20260915T222713Z-60890
Workspace: pluto  tag: 2a5e2da6

Preparing build context...
[svc] demo_ts/order_svc
  packaging localhost:5000/pluto/order-svc:2a5e2da6...
[apply] FAILED (6.1s)
  docker build failed: app/demo_ts/order_svc
  exited with code 1: ERROR: failed to build: resolve : lstat
    /home/lbendtly/Code/sun.docker-ctx/app: no such file or directory
```

## Cause

- `cli/sol/bin/cmd_up.ml:17-28` — `find_repo_root ()` walks up from cwd looking
  for `dune-workspace` or `dune-project` and returns the first directory that has
  one.
- `cli/sol/lib/sol_cli_up_execution.ml:16` —
  `build_context_dir ~repo_root = repo_root ^ ".docker-ctx"`.

`examples/pluto` has neither marker (only `sol.yml`), so the walk escapes the
workspace and lands on the enclosing Sol repo (`/home/lbendtly/Code/sun`, which
has both) → `ctx_dir = /home/lbendtly/Code/sun.docker-ctx`, while the build
expects `<ctx>/app/...` (the workspace's own `app/`). No such context exists, so
docker fails resolving the build context.

## Why this is more than a dogfood nuisance

The root-detection heuristic is **OCaml-keyed**. A workspace that legitimately
has no dune markers — most importantly a **TypeScript-only workspace**, which is
precisely what DEC-022 / FEAT-084 introduce — does not merely pick the wrong
enclosing project: with no enclosing dune project at all, the walk reaches the
filesystem root (`if parent = dir then dir`) and the context becomes
`/.docker-ctx`.

So this is a language-neutrality defect, not fixture hygiene: Sol's local build
path currently assumes every workspace is a dune project. That is exactly the
kind of assumption DEC-022 clause 7 argues against.

## The abstraction violation (why the fix is not "also recognise package.json")

```text
        wanted                          happened
   "find the Sol workspace root"   ->  "find the nearest dune-project"
```

Those were equivalent only while every meaningful Sol application was OCaml.
DEC-022 clause 7 makes the difference observable. Adding `|| package.json` would
evolve the heuristic into `dune-project || package.json`, recreating the problem
for the next language and misbehaving in any monorepo with manifests at several
levels. The root cause is that Sol's notion of *its own* boundary is missing
here, so language-ecosystem markers are standing in for it.

## Finding: Sol has no workspace-root abstraction to reuse today

Before implementing (do **not** casually make `sol.yml` authoritative just to fix
this function):

- `sol.yml` is loaded **relative to cwd** (`sol_cli_config.ml:1017`:
  `Sys.file_exists "sol.yml"`), not discovered by walking up — so the config layer
  *assumes* the caller is already at the workspace root.
- The dune-keyed `find_repo_root` (`cmd_up.ml:17-28`) is the only upward walk, and
  it is used as though it enforced that assumption.

Deliverable: **define what identifies a Sol workspace once**, then have root
discovery consume that definition. Language ecosystems (dune, npm) become
downstream details of a unit's build, never inputs to workspace identity.

```text
wanted:  cwd -> find Sol workspace root -> workspace/app/... -> build unit
                                                    |-- OCaml impl
                                                    `-- TypeScript impl

not:     cwd -> infer language-ecosystem root -> pretend it is the workspace
```

## Expected

The build context is derived from the **Sol workspace root** (the directory
holding `sol.yml` / the unit declarations), not from dune markers — or the
context is materialised in a temp dir keyed by the workspace, so nesting inside
another repository is irrelevant.

## Evidence / ordering

1. **Distinguishing experiment — RUN 2026-09-15, diagnosis CONFIRMED.**

   | workspace | markers | `sol up` build context |
   | --- | --- | --- |
   | `examples/pluto` (nested inside the Sol repo) | `sol.yml`, **no** `dune-project` | **FAIL** — `lstat <repo>.docker-ctx/app` |
   | `walkapp` (scaffolded, standalone) | `dune-project`, **no** `sol.yml` | **resolved correctly** — docker actually built (`transferring context: 446.14kB`, `[build 2/7] … CACHED`) |

   Same CLI, same command shape (`sol up --scope=<domain>/<unit>`); only the
   presence of a dune marker at the workspace root differs. So the fault is
   **wrong root detection**, not a context directory that is never created. (The
   `.docker-ctx` dir is materialised transiently and is absent after a run in
   both cases.)

2. **New finding from the experiment: a scaffolded workspace emits no
   `sol.yml`.** `sol new workspace walkapp` produces `dune-project`, `app/`,
   `lib/`, `events/`, `test/`, `vendor/`, `sol/` — and **no `sol.yml` anywhere**
   (`find -maxdepth 2` returns nothing). So:
   - `sol.yml` is *optional*, and is therefore **not** today's workspace marker —
     do not promote it to one merely to patch this function;
   - the only root marker a fresh workspace actually carries is
     **`dune-project`, which is OCaml-specific**. A TypeScript-only scaffold
     would carry no marker at all — which is exactly the `/.docker-ctx` case.

   Consequence: the fix must **define a Sol-owned workspace marker** (and have
   scaffolds emit it), rather than adopting either existing ecosystem marker.

3. **Invocation location is currently inconsistent — decide it explicitly.**
   `sol.yml` is loaded relative to `cwd` (`sol_cli_config.ml:1017`) while
   `find_repo_root` walks *upward* (`cmd_up.ml:17-28`). Those encode different
   contracts: "run from the workspace root" vs "anywhere inside the workspace".
   Preference: **anywhere inside**, so `cd app/payments/order_svc && sol check /
   sol up / sol logs` all act on the same workspace. One boundary abstraction
   (`find_root cwd` → workspace root) consumed by config loading, unit
   discovery, and build-context construction. Do not paper over the
   inconsistency just to get `sol up` green; and do not expand this ticket into
   migrating every command — record any broader migration separately unless it
   is required to make the abstraction internally coherent.

4. Then fix, then resume the FEAT-082 walk unchanged. Do **not** work around this
   while walking: a workaround would contaminate the walk's evidence.

## Regression suite — pin the abstraction, not this one bug

| Layout | Expected root |
| --- | --- |
| Sol workspace, no dune marker anywhere, no `sol.yml` (as scaffolded today) | that workspace |
| Sol workspace nested in a larger OCaml repo (`parent/dune-project`, `child/<marker>`) | `child`, **not** `parent` |
| Sol workspace nested in a larger Node repo (`parent/package.json`, `child/<marker>`) | `child`, **not** `parent` |
| Mixed workspace (OCaml units + TS units) | one common Sol root |

Row 3 stops a future "also detect Node roots" fix; row 4 pins DEC-022 clause 7.

Language-agnostic acceptance criterion for the whole suite (no Java needed to
test it): *given only Sol-owned workspace structure, root discovery must produce
the same result regardless of whether the contained units use Dune, npm, Maven,
Gradle, or some future build system.*
