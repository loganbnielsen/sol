**Related:** DEC-022 (clauses 7 and 8), FEAT-082, FEAT-084.

**The real subject:** Sol has no workspace identity. The Dune-keyed build failure
below is the *symptom* that made it observable.

## Symptom (real run, CLI at 2a5e2da6)

```text
$ cd examples/pluto
$ sol up --scope=demo_ts
Workspace: pluto  tag: 2a5e2da6
Preparing build context...
[svc] demo_ts/order_svc
  packaging localhost:5000/pluto/order-svc:2a5e2da6...
[apply] FAILED (6.1s)
  docker build failed: app/demo_ts/order_svc
  ERROR: failed to build: resolve : lstat
    /home/lbendtly/Code/sun.docker-ctx/app: no such file or directory
```

Cause: `cmd_up.ml:17-28` `find_repo_root ()` walks up from cwd looking for
`dune-workspace`/`dune-project`; `sol_cli_up_execution.ml:16` sets
`ctx_dir = repo_root ^ ".docker-ctx"`. `examples/pluto` has neither marker, so the
walk escapes the workspace, lands on the enclosing Sol repo, and the context is
computed outside the workspace.

## The subject: there is no Sol-owned answer to "what workspace am I in?"

```text
"What workspace am I in?"
        |
        v
No Sol-owned answer
        |
        v
Dune accidentally answers it
```

That is untenable once a workspace can be TypeScript-only or mixed-language.
Language build systems are properties of a *unit*, not of workspace identity:

```text
dune-project     package.json     pom.xml
     |                |              |
 OCaml unit        TS unit        Java unit
              NOT workspace identity
```

Target shape:

```text
Sol-owned workspace marker
          |
   find_root(cwd)
          |
    workspace root
     /     |      \
 config  discovery  build context
```

## Decision — see DEC-024 (canonical)

The platform contract this bug exposed now lives in **DEC-024** *Sol workspace
identity and root resolution*: a Sol workspace is a directory containing
`sol.yml`; its presence establishes the boundary and its contents configure it;
the **nearest ancestor** wins (a nested workspace shadows an enclosing one);
`find_root(cwd)` is authoritative and consumed by config loading, discovery and
build-context construction; no build-system inference or fallback; absence fails
closed with guidance (`sol new workspace <name>`).

**BUG-034 is the bug that exposed the violation and the implementation of that
contract.** The rationale below is retained as this ticket's reasoning; DEC-024
is what other work should cite.

## Rationale (retained)

> **A Sol workspace is a directory containing `sol.yml`.** Its *presence*
> establishes the workspace boundary; its *contents* define optional workspace
> configuration.

This is the contract, stated strongly on purpose — not "`sol.yml` becomes
always-present configuration". "Always present, possibly containing nothing
interesting" is then perfectly natural. The familiar analogue is a product-owned
manifest (`Cargo.toml`, `go.mod`, `package.json`) — not because Sol should infer
identity from those files, but because *having your own manifest define the
project boundary* is the well-understood model.

```text
my-app/
├── sol.yml              <- workspace boundary + workspace configuration
├── app/
│   ├── api_svc/         <- TS  (package.json is the unit's business)
│   └── ledger_worker/   <- OCaml (dune is the unit's business)
└── ...
```

```text
find_root(cwd)
     |  walk upward, looking only for sol.yml
     v
workspace root
     ├── config    = root/sol.yml
     ├── discovery = root/app/...
     └── build     = root/.docker-ctx
```

Config loading needs no separate location rule: `root = find_root(cwd)` then
`config = root / "sol.yml"`. Do **not** add `workspace: <name>` merely to justify
the file's existence unless Sol actually needs a persistent workspace name —
presence alone establishes the boundary.

**Fail-closed:** from anywhere outside a workspace, Sol walks up, finds no
`sol.yml`, and says *not inside a Sol workspace (no `sol.yml` found)*. It never
infers intent from `dune-project`, `package.json`, `.git`, etc.

**Rejected: B (`.sol/workspace` as a separate identity marker).** It creates a
distinction without independent meaning — if `sol.yml` exists, the directory is
already describing a Sol workspace. B would only be right if `.sol/workspace`
without `sol.yml` had to be a fully recognizable, useful workspace; since every
real workspace needs some workspace-level configuration surface, and B would add
ambiguity (which artifact owns the boundary? can config be absent? nested
config?), it buys concepts we do not currently need.

**Not acceptable either way:** an empty `.sol-root` sentinel, or a permanent
`sol.yml OR dune-project` fallback — that would preserve the exact abstraction
violation this ticket removes.

## Migration / compatibility

Existing workspaces have no marker. Since there are no external users yet, a
clean break is preferable to permanent Dune-fallback compatibility:

```text
sol new workspace   -> always emits the marker
existing repo       -> add the marker once
no marker           -> clear "not inside a Sol workspace" error
```

## Invariants to establish

1. **Every workspace-aware Sol command resolves the same workspace root from any
   descendant path** — `cd app/payments/api_svc && sol check | sol up | sol logs`
   all act on `my-app`. Resolves today's inconsistency where `sol.yml` is
   cwd-relative (`sol_cli_config.ml:1017`) but `find_repo_root` searches upward.
2. **Configuration paths resolve relative to the workspace root, not the
   invocation cwd** — otherwise discovery is fixed but subtler cwd-dependent
   behaviour remains.

## Evidence (experiment run 2026-09-15 — diagnosis CONFIRMED)

| workspace | markers | `sol up` build context |
| --- | --- | --- |
| `examples/pluto` (nested in the Sol repo) | `sol.yml`, **no** `dune-project` | **FAIL** — `lstat <repo>.docker-ctx/app` |
| `walkapp` (scaffolded, standalone) | `dune-project`, **no** `sol.yml` | **resolved** — docker built (`transferring context: 446.14kB`, `[build 2/7] … CACHED`) |

Same CLI, same command shape; only the dune marker differs → **wrong root
detection**, not a context that is never created (`.docker-ctx` is transient in
both cases).

**Second finding:** `sol new workspace walkapp` emits **no `sol.yml`** anywhere
(`dune-project`, `app/`, `lib/`, `events/`, `test/`, `vendor/`, `sol/` only). So
`sol.yml` is optional and is *not* today's marker — and the only marker a fresh
workspace carries is `dune-project`, which is OCaml-specific. A TypeScript-only
scaffold would carry none: the `/.docker-ctx` case.

## Regression suite — pin the abstraction, not this bug

| Layout | Expected root |
| --- | --- |
| Sol workspace, no dune marker, no config (as scaffolded today + new marker) | that workspace |
| Sol workspace nested in a larger OCaml repo (`parent/dune-project`, `child/<marker>`) | `child`, **not** `parent` |
| Sol workspace nested in a larger Node repo (`parent/package.json`, `child/<marker>`) | `child`, **not** `parent` |
| Mixed workspace (OCaml units + TS units) | one common Sol root |
| Descendant cwd (`<root>/app/…/unit`) | `<root>` |

Row 3 stops a future "also detect Node roots" fix; row 4 pins DEC-022 clause 7;
row 5 pins invariant 1.

Language-agnostic acceptance criterion for the suite (no Java needed): *given
only Sol-owned workspace structure, root discovery must produce the same result
regardless of whether the contained units use Dune, npm, Maven, Gradle, or a
future build system.*

## Ordering

1. Decide the marker (A or B) — explicit, not incidental.
2. Define `find_root(cwd)`; migrate config loading, unit discovery and
   build-context construction to consume it. Do not paper over the inconsistency
   to get `sol up` green; do not expand this into migrating every command unless
   internal coherence requires it.
3. Land with the regression suite above.
4. Resume the FEAT-082 fixture walk unchanged — no workaround first, or the
   walk's evidence is contaminated.

## Non-goals

- Teaching root discovery about `package.json` (or any language marker).
- Permanent `marker OR dune-project` fallback.
- Whole-CLI migration beyond what coherence requires.
