Decide Sol's application-language strategy: are OCaml and TypeScript both
first-class application languages on a language-neutral platform, or is
TypeScript a thin, demand-gated compatibility layer?

## Context

OCaml-only application development is a severe adoption constraint: the
overwhelming majority of backend developers will not learn OCaml to evaluate
Sol. TypeScript is the natural on-ramp — the population that already
understands `sol new` / `sol local up` / `sol deploy` and expects
`export async function handler(...)`, not Kubernetes, Helm, Kafka retry
topics, Pushgateway, or graceful-termination minutiae.

The platform layer is already proven language-neutral (FEAT-033): the CLI
discovers, builds and deploys any service by suffix + Dockerfile. What was
never decided is the *application-framework* strategy — and because it was
unstated, the TS-parity backlog argued from at least two incompatible
definitions ("thin compatibility layer" vs "second first-class framework").

Demand cannot validate a path when the path that would create the demand
does not exist: gating TS on "real TS demand" is circular if a TypeScript
developer cannot `sol new` a TS app and deploy it.

## Options considered

1. **Language-neutral platform; per-language first-class frameworks** — the
   platform layer is one OCaml implementation with a language-neutral
   contract; application-facing capabilities are implemented idiomatically
   per language, both first-class.
2. **OCaml-only application framework; TypeScript as a thin, demand-gated
   compatibility layer** — the status-quo framing.
3. **OCaml reference runtime only; TypeScript becomes the primary app
   language** — the opposite extreme; discards OCaml's dogfood/reference
   value.

## Decision

**Option 1.** Sol's platform is language-neutral. The platform layer — CLI,
deploy, scaffold, local infra, releases, config/secrets, infrastructure — is
a single implementation (OCaml) exposing one language-neutral contract.
**Application-facing framework capabilities are implemented idiomatically
per supported language, and OCaml and TypeScript are both first-class
application languages.**

1. **Both are first-class.** OCaml remains first/deepest today (where the
   architecture is proven, and itself a first-class app language);
   TypeScript is the adoption funnel. Neither is a second-class path.
   First-class does not require every capability to ship in both languages
   on the same day.
2. **Default: application-facing capabilities target both languages.** A
   capability is not broadly product-complete until both provide a coherent
   developer experience — *unless an explicit, recorded decision defers
   one*. Deferral is an argued exception, recorded with a trigger, never
   silent debt. Every application-facing capability carries a per-language
   verdict: **implemented / already equivalent / intentionally deferred /
   not applicable** (the FEAT-080 mechanism). Silence is not a verdict.
3. **Parity is capability + behavioural parity, not implementation parity.**
   The contract — schema-registry conventions, Confluent wire format, trace
   propagation, retry/DLQ semantics, metric/label vocabulary,
   lifecycle/shutdown, config/secrets, job semantics — must hold across
   languages. The implementation underneath need not be shared: `kafka-eio`
   / `pg-eio` stay OCaml; TypeScript keeps the Node ecosystem
   (`kafkajs`/`pg`/Fastify/`prom-client`) and Sol supplies only the
   semantics and integration glue those libraries do not. Parity is
   measured against the contract, not package count.
4. **Two conformance levels, both required:**
   - **TS golden path (adoption/DX) — necessary but not sufficient:**
     `sol new <app> --language typescript` → `sol local up` → write
     ordinary TypeScript → `sol check` → `sol deploy --target staging` →
     health/metrics/traces/logs work — without reading the OCaml
     implementation or hand-reconstructing the Sol runtime contract.
   - **Capability conformance matrix (architectural parity):** for each
     application-facing capability, both languages' verdict (above). A
     HelloWorld golden path does not satisfy this level.
5. **Priority consequence:** the TypeScript golden path is prioritized
   ahead of additional backend feature breadth. Accessibility to developers
   is currently a bigger missing platform feature than another primitive.
6. **The architecture stays multi-language-extensible.** Because the
   contract is language-neutral, a future Go/Python framework has a
   principled place to live rather than "Sol == the OCaml runtime" being
   baked in.

## Non-goals

- Not mandatory simultaneous shipping in both languages.
- Not sharing implementation across languages.
- Not a commitment to port every OCaml package/module into npm.
- Not abandoning OCaml — it stays first-class and remains the deepest
  implementation.

## Consequences

- README.md and `.claude/CLAUDE.md` language framing updated to state both
  first-class and the per-capability verdict rule (this ticket's
  implementation).
- The CLAUDE.md TypeScript-parity convention is reframed from "gated on
  real TS demand" to "every application-facing capability carries a
  per-language verdict; deferral must be explicit and recorded."
- Follow-ups filed: **FEAT-082** (TypeScript golden-path umbrella,
  journey-based) and **DEC-023** (distribution story for `@sol/*` —
  DEC-013's "reserve names, publish later" is load-bearing now).
- FEAT-036's acceptance test becomes "does a TypeScript service get the Sol
  service contract/DX without it?", not "is duplicating `sol-svc` in
  TypeScript worthwhile?"
- FEAT-080's `-fn` ("not applicable") and `sol-jobs` ("intentionally
  deferred" on ecosystem-equivalence) verdicts are re-read under this
  decision.

## Acceptance criteria

- README.md states OCaml and TypeScript as first-class application languages
  on one language-neutral platform.
- `.claude/CLAUDE.md`'s TypeScript-parity convention requires a
  per-capability verdict with explicit, recorded deferral.
- FEAT-082 and DEC-023 are filed.
