**Depends on:** None.

**Related:** FEAT-076, DEC-021, BUG-028.

A single transient retry/DLQ publication failure permanently and silently stops retry
delivery for the life of the worker process.

## Problem

Both the source and retry consumers in
`framework/kafka-eio-service/lib/kafka_service_retry_topics.ml` are run through
`Kafka.Consumer.consume_partitioned` with `~retry:no_retry`, i.e.
`{ base_delay_s = 0.0; max_delay_s = 0.0; max_attempts = 0 }`.

In kafka-eio, `max_attempts = 0` with `n = 0` makes `exhausted` true on the first handler
`Error`. For the source consumer that surfaces as `Partition_errors` and fails the
worker. For the **retry consumer**, any `Error` from `retry_handler` — a retry-topic
produce failure, a DLQ produce failure (see BUG-028), or an ack failure — exhausts
immediately. The consumer signals stop, and the forked fiber:

```text
Error (Kafka.Consumer.Handler_errors errs) ->
  List.iter (fun (partition, e) -> Printf.eprintf "warn: ... retry consumer partition %ld: %s\n%!") errs;
  Kafka.Consumer.close retry_consumer
```

logs to stderr and closes the retry consumer. `Kafka_service_retry_topics.consume` already
returned `Ok ()` at that point, so:

```text
main worker keeps consuming the source topic   ← looks healthy
retry delivery is permanently stopped          ← stderr only, no metric
```

The retry consumer has no retry at all, so the first transient produce failure is
terminal for the whole relay. Additionally, `on_retry` fires *before* the produce
(`publish_raw`), so a failed publication is still counted as a scheduled retry.

## Required behavior

- Retry/DLQ publication must be resilient: bounded in-process retry with backoff and
  jitter around the produce, rather than one attempt whose failure is terminal.
- A relay stop must be observable, not stderr-only: emit a metric and surface the stop
  to the worker's outcome (fail loudly) or emit a distinct degraded-state signal. No
  silent degradation.
- A single transient produce failure must not tear down the retry consumer.
- Decide and document whether a persistently failing relay should stop the worker
  (fail loudly) or keep retrying; either is acceptable, silent stoppage is not.

## Acceptance criteria

- A transient produce failure does not permanently stop retry delivery.
- Relay stoppage/exhaustion emits a metric and an `Error`-level log, and is reflected in
  the worker's result.
- Retry metrics distinguish scheduled vs published vs failed (today `on_retry` counts
  scheduled only).
- The retry consumer's exhaustion policy is explicit and documented, not an accidental
  consequence of `max_attempts = 0`.

## Non-goals

- Retry buckets or a second retry backend.
- Changing the source consumer's exhaustion behavior.
