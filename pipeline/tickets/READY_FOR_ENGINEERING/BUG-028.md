**Depends on:** None.

**Related:** FEAT-076, DEC-021, BUG-029.

Premise note: retry decode failure still appears to route through `on_decode_error`;
verify before implementation, but do not use that buggy-state check as a
`premise:` probe.

A retry record that can no longer be decoded is acknowledged and dropped, destroying
the last durable copy of the message.

## Problem

`decode_retry` in `framework/kafka-eio-service/lib/kafka_service_retry_topics.ml` calls the
caller-supplied `on_decode_error`, whose default
(`default_on_decode_error`, `framework/kafka-eio-service/lib/kafka_service.ml`) logs the
error, calls `ack ()`, and returns `Continue`.

On the source topic that is a deliberate, documentable skip: the message was never
accepted. On the retry topic it is data loss, because the source offset was already
committed when the message was published to `<topic>-retry`:

```text
source message
  ↓ published to retry topic
  ↓ source offset committed
retry record
  ↓ decode failure
  ↓ ack()                 ← the only remaining copy is gone
```

Schema evolution, malformed headers, payload corruption, or an incompatible decoder
change can therefore delete work Sol had already durably accepted.

**Root cause:** the retry path reuses a source-path API whose `Continue` return means
"skip → ack". The retry path must not be able to reach that behavior at all.

## Required behavior

```text
retry record
  ↓ decode failure
publish raw retry envelope + original headers + decode diagnostics to the group-scoped DLQ
  ↓
DLQ publish succeeds?
  ├─ yes → ack the retry record
  └─ no  → leave the retry record unacknowledged
```

- The retry record must never be acknowledged merely because decoding failed.
- The source-path `on_decode_error` skip contract must not be reachable from the retry
  path. The decode error may still be logged/observed, but not through an API that can
  ack-drop.
- Raw Kafka payload and headers must survive the transfer to the DLQ.

## Invariant

> Once responsibility has transferred from the source topic to the retry topic, Sol must
> not discard the message unless responsibility has successfully transferred to another
> durable destination. For retry decode failure, that destination is the DLQ.

This is the acknowledgement ownership invariant (`framework/sol-worker/sol-worker.md`)
applied to the retry path.

## Acceptance criteria

- A retry record that decodes successfully follows the normal retry path.
- A retry record that fails decoding is published to the DLQ.
- The retry offset is acknowledged only after DLQ publication succeeds.
- DLQ publication failure leaves the retry record unacknowledged.
- Raw Kafka payload and headers survive the transfer.
- The decode error is visible in logs/diagnostic metadata.
- No retry decode-failure path uses the main-topic "log and skip" behavior.

## Non-goals

- Changing the source-topic decode-error policy (unchanged).
- Retry-chain identity headers (`X-Sol-Retry-Id` etc. do not exist yet).
