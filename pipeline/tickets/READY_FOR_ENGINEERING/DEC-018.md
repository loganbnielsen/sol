**Depends on:** DEC-016.

Decide what "rollback" means now that a deploy is a digest-pinned artifact, and be explicit about what it can never restore.

## Question

DEC-016 makes deployments digest-pinned, so *code* rollback becomes cheap: repoint the target at a previously deployed artifact. But two things that look like rollback get conflated, and only one of them is safe:

- **Artifact and configuration rollback** — redeploy a previous release. Instant, reversible, and honest.
- **Data and schema rollback** — redeploying old code does **not** undo a migration. A dropped column stays dropped; a backfill stays backfilled. Down-migrations are usually a fiction, and offering them as a feature invites people to rely on them in exactly the situation where they cannot work.

## Recommendation

**Artifact rollback, forward-only migrations, and expand/contract guidance.**

- `sol rollback` restores a previous **release** — artifact digest plus configuration and secret references as one unit — not the image alone. Rolling back code while leaving the config that was written for the newer release is a partial rollback that presents as a whole one. Sol already records releases; this makes the release the rollback unit.
- **Migrations are forward-only.** To make rollback safe, the *rule* is that schema changes are additive and land separately from the code that depends on them (expand/contract): add the new column/table, deploy code that writes both, then remove the old shape in a later release. Then rolling back one release is always safe, which is the property worth having.
- **Sol knows the migration history, so it should say so.** Rolling back across a migration boundary is a real thing to want and a dangerous thing to do silently. The CLI should refuse by default and name what is in the path — *"rolling back to release N predates migration 0007 (dropped `charges.legacy_id`), which cannot be undone"* — with an explicit override.
- **Retention is part of the decision.** A rollback target must still exist: how many releases stay addressable, and what the customer is told when their intended target has been pruned — retention costs money, so unbounded retention is a real line item.
- **Per target, not per customer.** Rollback applies to one environment. Rolling production back to a digest that previously ran in staging is the promotion story working, not a special case.

## Options considered

1. **Artifact-only rollback, forward-only migrations** (recommended). Simple, honest, requires discipline in how migrations are written.
2. **Full rollback including down-migrations.** Rarely true, encourages reliance on a path that fails under pressure.
3. **No rollback primitive; redeploy the previous commit.** Works only if builds are reproducible and fast, and loses the "what exactly was running" certainty that digest pinning just bought.

## Decision Required

Not yet decided.

**Acceptance criteria**

- A decision states what `sol rollback` restores (artifact, configuration, secrets) and what it explicitly does not.
- The migration policy is stated — forward-only with expand/contract, or something else — along with how it is communicated to application authors.
- The migration-boundary guardrail is specified: what the CLI prints, and what an override requires.
- Release retention and artifact pruning are defined, including what happens when a rollback target no longer exists.
