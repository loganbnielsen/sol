**Depends on:** None.

kube-router on k3s does not honour cross-namespace `namespaceSelector` NetworkPolicy rules on **any version tested** (v1.27.4 and v1.35.5), so Sol's generated per-pair policy **denies** declared service-to-service calls on the dev substrate. BUG-022 concluded this was fixed by a newer k3s; that conclusion was wrong — see [Why BUG-022 got it wrong](#why-bug-022-got-it-wrong).

## Behaviour

Measured on k3d v5.9.0 / k3s v1.35.5: two fresh namespaces, an nginx target on 8080 behind a ClusterIP Service, a labelled caller pod, and the policy **verified applied** with `kubectl get netpol -o jsonpath` before every probe.

| Target ingress rule | Result |
| --- | --- |
| none | 200 (reachable) |
| `namespaceSelector` allow | **refused** (curl exit 7) |
| deny-all (`namespaceSelector` → non-existent namespace) | refused — enforcement is live |
| `ipBlock` allow (pod CIDR) | **200** |

The identical pattern was measured on k3s v1.27.4. Also true on both versions: **egress policy is not enforced at all** — a deny-all egress policy on the caller blocks nothing.

So on the dev substrate the pair policy can deny but never permit: a pod selected by a policy is reachable only from sources matching an `ipBlock` rule.

## Why BUG-022 got it wrong

BUG-022's experiment applied the allow policy as `kubectl apply -f … >/dev/null 2>&1`, discarding the outcome, then probed. The probe returned 200 — which is also exactly what probing with **no policy applied** returns. The negative control in the same run passed for the right reason (it was applied through a visible pipeline), which made the false positive look credible, and the toolchain was bumped on that basis.

Two lessons worth keeping:

1. **Verify the fixture before interpreting the probe.** A probe result means nothing until the object under test is confirmed present and correct. `kubectl apply` output goes to the terminal, not `/dev/null`.
2. **An allow-only test cannot distinguish "permitted" from "unenforced".** `ipBlock` allowing and deny rules blocking are what made the wrong result look trustworthy; only a clean-room re-test with the policy verified settled it.

## Impact

- FEAT-041/FEAT-045's live end-to-end assertion is not achievable on k3s. PR #205 is closed for this reason. The deploy-path assertion — injected URL plus the applied policy pair — is the honest ceiling, and the caveat removed from `service-runtime-contract.md` needs restoring with a corrected cause: not "old k3s", but "kube-router does not implement `namespaceSelector`".
- **BUG-022's toolchain bump rests on a false premise.** It moved a deliberate pin (k3d v5.6.0, kept for chart-value compatibility — see `DOGFOOD.md`) for a reason that does not hold. Its golden-path smoke passed, so the bump is not *broken*, but it carries the chart-compatibility risk DOGFOOD warns about in exchange for nothing policy-related.
- Production CNIs (Calico, Cilium, EKS VPC CNI) are *expected* to honour `namespaceSelector` — that expectation is inherited from BUG-022 and has **not** been verified first-hand.

## Remediation

- **Decide the toolchain**: revert the bump (restoring the deliberate pin, since its justification is void), or keep it with a corrected, non-policy rationale. Reverting is the more defensible default.
- Restore the `service-runtime-contract.md` caveat with the corrected cause; drop any claim that upgrading k3s helps.
- Correct BUG-022's recorded conclusion and the `DOGFOOD.md` rationale, both of which now assert the opposite of what is true.
- Do **not** switch the generated policies to `ipBlock`: that discards the per-pair precision that is the feature's point, for a substrate-specific workaround. Document the limitation instead.
- If app-to-app calls must work locally, the options are a CNI that implements `namespaceSelector` (Calico/Cilium on k3d) or disabling NetworkPolicy enforcement in dev — both substrate decisions, neither a change to policy rendering.

## Acceptance criteria

- One of: the dev substrate honours the generated pair policy, or the limitation is documented in user-facing docs with the corrected cause and no version-upgrade claim.
- `DOGFOOD.md` and BUG-022's conclusion no longer state that a newer k3s fixes `namespaceSelector`.
- The toolchain bump is either reverted or accompanied by a corrected justification.
