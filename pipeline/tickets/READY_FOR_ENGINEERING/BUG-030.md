**Depends on:** None.

**Related:** FEAT-076, DEC-021.

Retry and DLQ topic names are scoped to the source topic, but retry consumption is scoped
to the consumer group, so independent consumer groups can consume each other's retries.

## Problem

```text
source topic:      orders
retry topic:       orders-retry

consumer group A:  payments    → retry consumer group "payments-sol-retry"
consumer group B:  analytics   → retry consumer group "analytics-sol-retry"
```

Both retry consumer groups subscribe to `orders-retry`. A retry published on behalf of
group A is therefore delivered to group B's retry consumer, and group B will process a
retry for a message it never consumed (or never should have). The same shape applies to
the DLQ if it is source-scoped.

This violates consumer-group isolation and makes retry/DLQ traffic land in the wrong
application.

## Required behavior

Retry and DLQ topic identities must include the logical consuming group:

```text
<source-topic>.<group-id>.retry
<source-topic>.<group-id>.dlq
```

The exact encoding may differ, but it must:

- include both source-topic identity and consumer-group identity;
- produce valid Kafka topic names — note the 249-character limit and that mixing `.`
  and `_` produces Kafka metric-name collisions, so the group id must be sanitized
  and truncated (and hashed if truncation would collide);
- be deterministic;
- live in one canonical naming helper used by the producer, topic provisioning, the
  retry consumer, DLQ tooling, and documentation — never reconstructed ad hoc.

### DLQ scoping (open — do not lock by default)

Retry topics must be group-scoped. The DLQ does not follow automatically.

The current lean is **per-group DLQ**, on the grounds that `Dead_letter` is the disposition
of a *consumer group's processing attempt*, not an intrinsic property of the source event:
if `payments` cannot process event X but `analytics` can, that is payments' dead letter.
The countervailing cost is operational fragmentation — one dead-letter surface per group.

Do not lock this until the DLQ *inspection* story is decided: how do operators find, list,
replay, and alert on dead letters, and does the tooling read one surface or many? If
inspection is inherently per-service, per-group DLQ is natural; if there is a single
fleet-wide DLQ console, a per-source DLQ with an `X-Sol-Origin-Group` header is. Record
the chosen scoping in DEC-021 or a successor before implementing naming.

## Invariant

> A retry record produced on behalf of consumer group A must only be consumable by retry
> infrastructure belonging to consumer group A. Dead-letter isolation follows the DLQ
> scoping decision below — per-group: the same rule; per-source: origin is recorded but the
> surface is shared, deliberately.

## Migration

Existing unscoped retry/DLQ topics may contain in-flight records. Migration must not
silently strand them: either drain legacy unscoped topics while routing new failures to
group-scoped topics, or explicitly assert that no legacy records exist before changing
naming. Do not rename topics in place assuming Kafka migrates their contents.

## Acceptance criteria

Given two independent consumer groups A and B on the same source topic:

- A retry produced by A appears only in A's retry topic; B does not consume it.
- A DLQ record produced by A appears only in A's DLQ destination.
- Producer, provisioning, retry consumer, DLQ tooling, and docs all use the same
  canonical naming helper.
- Group ids that are missing, empty, over-length, or contain `.`/`_` are handled by the
  helper without producing an invalid or colliding topic name.
- Existing single-group behavior is otherwise unchanged.
