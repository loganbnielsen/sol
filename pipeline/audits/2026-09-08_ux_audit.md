## Findings

### [EXP-026] — Stage 1 / README install command 404s against the only published release

* **Stage:** 1 Installation
* **Gate:** Reproduction
* **Severity:** Blocker
* **Description:** README.md's Quickstart tells the user to `curl -L .../releases/latest/download/sol-vX.Y.Z-linux-x86_64.tar.gz`. The only published release, `v0.1.0-alpha.6`, predates the `sun`→`sol` rename and ships its asset as `sun-v0.1.0-alpha.6-linux-x86_64.tar.gz`. Verified live: the `sol-` prefixed URL 404s; the `sun-` prefixed one 200s. Separately, `sol --version` always prints the literal string `"dev"` (`~version:"dev"` hardcoded in `cli/sol/bin/main.ml`'s `Cmdliner.Cmd.info`), so there's no way to confirm the installed build's actual version even once install succeeds.
* **Impact:** Following the README's Quickstart exactly as written fails at the very first command with a 404 and no actionable error message (curl piped into tar just produces a gzip error on the HTML 404 body). This is the literal first thing a new user does — it blocks Stage 1 entirely.
* **Remediation:** Cut a new release (push a `v*` tag) using the current, already-correct `release.yml`, which will publish `sol-`-prefixed assets matching both the workflow and the README. Note this is a release-cut action, not just a code change — flag for confirmation before pushing a new public tag. Separately, fix `Cmd.info "sol" ~version:"dev"` to embed the actual build version (e.g. via a version string generated at build time from the release tag or git describe) so `sol --version` is meaningful.

### [EXP-027] — Stage 3 / `sol new svc` still generates an observability-dark entrypoint (worker/fn recovered, svc did not)

* **Stage:** 3 Local Development
* **Gate:** Reproduction
* **Severity:** High
* **Description:** The generic `svc_bin_ml` template used by `sol new svc` (`cli/sol/lib/sol_cli_scaffold_templates.ml:895-903`) generates `Service.run Handler.routes ~env ()` with no `Sol_obs.of_env`, no `~ot`. Contrast with `worker_bin_ml` and `fn_bin_ml` (same file), which both correctly build an `obs` handle via `Sol_obs.of_env` and pass `~ot:obs` — and with `ws_svc_bin_ml` (the workspace-scaffold's initial service, line 700), which does the same. This is the original EXP-022 gap, now only half-recovered.
* **Impact:** A startup engineer who follows the tutorial's `sol new svc ops/admin` example gets a service that compiles and runs but produces no Loki logs and no `sol_svc_requests_total` metric, silently inconsistent with a `sol new worker`/`sol new fn` sibling added the same way.
* **Remediation:** Update `svc_bin_ml` in `sol_cli_scaffold_templates.ml` to match the `Sol_obs.of_env ~net:env#net ~clock:env#clock ~mono_clock:env#mono_clock ~service:"{{name}}-svc" ()` + `~ot:obs` pattern already used by `worker_bin_ml`/`fn_bin_ml`/`ws_svc_bin_ml`.

### [EXP-032] — Process / `DONE` is not a reliable signal: five reverted-and-never-refixed tickets sat unnoticed for three months

* **Stage:** (cross-cutting — not a single numbered stage)
* **Gate:** N/A (pipeline integrity, not a numbered UX stage)
* **Severity:** High
* **Description:** EXP-021 through EXP-025 were each merged and then reverted the same evening (2026-06-13) after breaking tests (`pipeline: test failure blocked EXP-0NN` commits immediately precede each revert). None were refiled, reopened, or fixed forward — all five ticket files remain in `project/tickets/DONE/` with `## Review — automated checks passed` sections describing fixes that no longer exist in `main`. Every subsequent audit/dogfood pass since (`2026-06-22_docs_audit.md`, three `code_layer_audit` runs in September, `RUN_2026-09-07*` dogfood reports) evidently trusted the DONE state rather than re-verifying, since none caught this recurrence — this ux-audit only found it by directly reading current source and diffing against ticket claims.
* **Impact:** The ticket pipeline's `DONE` directory is treated repo-wide as ground truth for "this is live in main" (per this repo's own `CLAUDE.md` state-machine description), but a revert after merge leaves no mechanism to un-DONE a ticket. Any future revert — for any reason, not just a test failure — will silently and permanently misrepresent repo state unless someone happens to notice by reading source instead of trusting the ticket. Given `project/tickets/DONE/` currently holds 385 entries, this class of drift could exist elsewhere undetected.
* **Remediation:** Add a safeguard to the pipeline's merge/revert handling: when a merge to `main` is reverted, the revert commit should identify the original ticket (from the merge commit message or PR reference) and automatically move that ticket file from `DONE/` back to `READY_FOR_ENGINEERING/` with a note explaining the revert reason, rather than leaving it in `DONE/`. As a lower-effort interim measure, `/audit`-family skills could grep recent history for `Revert "Merge branch '<TICKET-ID>` patterns against every `DONE/` ticket ID as part of their "check previous findings" step, to catch exactly this pattern going forward.
