## Findings

### AUDIT-066 — `docs/audits/AUDIT.md` template still uses pre-rename `sun` naming throughout

* **Category:** AI-Agent-First / Framework Boundary
* **Severity:** Medium
* **Location:** `docs/audits/AUDIT.md` (entire file — path references in Sections 1–4, 8–9, and the runbook in Section 5–7)
* **Status:** Open
* **Description:** The repo was renamed `sun` → `sol` (CLI binary, `framework/sol-*` packages, `Sol.Service.Make`/`Sol.Worker.Make`/`Sol.Fn.Make`, `sol.toml`/target-file config) per `.claude/CLAUDE.md`, but the audit checklist template was never updated to match. It still names `cli/sun/bin/`, `cli/sun/lib/sun_cli_scaffold.ml`, `cli/sun/lib/sun_cli_manifest.ml`, `integrations/kafka/kafka-eio-core/...` (now the external `~/Code/kafka-eio` package with a flat `lib/` layout, not `kafka-eio-core/lib/`), `framework/sun-worker/lib/worker.ml`, `Sun.Service.Make`, and `sun.toml` as the config file (superseded by `sol.yml` + `sol/<env>/<provider>/<region>.yml` per the Target Files project in `docs/planning/LIVE_DEV_DEPLOY_ROADMAP.md`).
* **Impact:** Every future `/audit` run — including this one — has to manually re-derive current paths before it can check anything, which costs time and risks a false PASS/FAIL if a path is guessed wrong instead of verified. This is exactly the class of problem Section 9 itself asks the audit to check for ("Spec files match implementation reality") — the audit's own template fails its own invariant.
* **Remediation:** Update `docs/audits/AUDIT.md`'s source-location references and prose to the current layout: `cli/sol/bin/` · `cli/sol/lib/sol_cli_scaffold.ml` · `cli/sol/lib/sol_cli_manifest.ml` + `sol_cli_manifest_yaml.ml`; note that Kafka core/consumer/producer now live in the external `~/Code/kafka-eio` package (flat `lib/kafka_stubs.c`, `lib/kafka_consumer.ml`); `framework/sol-worker/lib/worker.ml`; `Sol.Service.Make`/`Sol.Worker.Make`/`Sol.Fn.Make`; and replace `sun.toml` references with the current `sol.yml`/target-file model. Keep the file as a reusable template (per its own header) — just point it at what exists today.

### AUDIT-067 — `pg-eio`'s `Migration.default_table` still says `sun_schema_migrations`

* **Category:** AI-Agent-First / Naming Consistency
* **Severity:** Low
* **Location:** `~/Code/pg-eio/lib/migration.ml:240` (`let default_table = "sun_schema_migrations"`)
* **Status:** Open
* **Description:** `pg-eio`'s own unused fallback default for `Migration.apply`'s `?table` argument still carries the pre-rename `sun_` prefix. It causes no live bug today because `sol`'s CLI (`cli/sol/bin/cmd_migrate.ml`) always passes an explicit `~table` computed as `sol_<workspace>_schema_migrations` — the workspace-isolation invariant holds at the `sol` layer regardless of this default.
* **Impact:** Low — purely cosmetic today. But it's a live landmine for anyone (a future direct `pg-eio` consumer, or someone extending `Migration.apply` call sites) who forgets to pass `~table` explicitly: they'd silently get a table named after a product that no longer exists, and it wouldn't be namespaced to their workspace either.
* **Remediation:** Rename `default_table` to `"sol_schema_migrations"` in `~/Code/pg-eio/lib/migration.ml`. Per this workspace's cross-package no-backcompat policy (`~/Code/CLAUDE.md`), no deprecated alias or migration path is needed — just change the literal and re-pin `pg-eio` into `sol`'s opam switch.
